Day 142 — GPU Node Pools — Taints and Tolerations

Today's own PR wires nodeSelector, tolerations, and affinity onto vllm-deploy-kit's pod spec — three fields that only do their job together. That pairing isn't new to me; it's the exact discipline I built after watching a Delivery Hero node pool fill with pods that had no business being there, on a cluster with nothing to do with GPUs at all.

Today's code is mine, not a teammate's: vllm-deploy-kit/chart/templates/deployment.yaml adds nodeSelector, tolerations, and affinity to the pod spec so a serving pod that asks for a GPU actually lands on the node pool that has one, tainted so nothing else can land there by accident. I didn't reach for that pairing because a Kubernetes doc told me to. I reached for it because I watched one half of it be missing on a real cluster, and watched what that half-measure actually cost.

A Loading Dock With a Keycard Lock

DS analogy — the loading dock with a keycard lock
A loading dock behind a building gets a keycard lock so ordinary cars can't pull in and take up space meant for delivery trucks — that lock is the taint, and it doesn't ask who's on the other side, it just blocks everyone without a card. A truck's keycard is the toleration: it gets the truck past the lock, but a keycard sitting in the glovebox doesn't drive the truck anywhere. Whether the truck actually pulls into that dock instead of parking on the street out front is the dispatcher's routing instruction — the affinity — and without it, a truck that's fully allowed through the gate might never be told to go there at all.

A Kubernetes taint on a node works the same way: it's a blanket refusal, NoSchedule, that keeps every pod off that node unless the pod carries a matching toleration. A toleration is permission, not preference — it tells the scheduler "you're allowed to place me here," not "place me here." Getting a GPU-hungry pod onto a GPU node pool and keeping everything else off it takes both halves working at once, and it took me finding out the hard way that shipping only the first half is worse than shipping neither.

So what: a taint alone keeps the wrong pods out, and a toleration alone lets the right pods in, but neither one on its own tells the scheduler to actually prefer that node — which is exactly the gap a pod with a toleration and no affinity falls into.

What the EKS Cluster I Ran Actually Looked Like

What's documented, verified against the architecture doc
The Global Logistics Platform's architecture doc lists the OSRM cluster as its own component — a map-matching and routing engine with its own database, separate from Route Service and Route Consumers, which read Order SQS's lifecycle events and produce the Route object the UI reads. The doc documents that OSRM is a distinct piece of the stack; it doesn't itemize which EKS node pool it ran on or how that pool was sized, which is a gap in what I have in front of me, not a claim I'm making about it.
My scope — Global Logistics Platform, Delivery Hero, Jun 2022–Jul 2023
I scaled that platform to 1M+ daily orders on AWS EKS, holding 10k+ concurrent requests with zero downtime, and built the rider tracking on top of OSRM that processed 5k+ real-time route updates a second. OSRM keeps its road-network graph resident in memory to answer map-matching queries fast, which is the reason it ran on a node pool sized differently — and priced differently — from the general fleet Route Service and Route Consumers ran on. That difference is where this post's lesson actually happened.

I'm using "the OSRM pool" as shorthand for a memory-heavy node pool distinct from the general fleet — a framing device to make the pattern concrete, the same way Day 141's post used "12 environments" for Route Service's Helm sprawl without claiming that exact count came from the architecture doc. What I can stand behind is the mechanism: any node pool provisioned for one workload's specific resource shape, sitting in the same cluster as a general-purpose fleet, is exposed to this problem the moment nothing keeps other pods off it.

So what: the precise node count and instance type aren't things I have written down anymore, but the shape of the problem — one pool costs more per node than the rest of the fleet, and Kubernetes' scheduler has no opinion about that cost unless something tells it to — is the part this post is actually about.

The Pool That Kept Filling With the Wrong Pods

Kubernetes' default scheduler places a pod on any node where its resource requests fit, full stop. It has no idea that one node pool costs more per hour than another unless a taint tells it to treat that pool as off-limits by default. Without a taint, an ordinary Route Service or Route Consumer replica — small CPU and memory footprint, nothing GPU- or memory-shaped about it — is just as eligible for a spot on the pricier pool as it is for a spot on the general fleet, and the scheduler will use whichever node clears its bin-packing check first.

The failure mode isn't dramatic. Nothing crashes, no alert fires, no customer notices a thing — the ordinary pod runs exactly as well on the expensive node as it would have on a cheap one. That's precisely why it's the kind of waste that survives for months: every individual placement looks harmless, and the only thing that would surface it is someone actually comparing what each node pool costs against what actually needed to run there.

So what: the scheduler was never the thing that failed here — it did exactly what an untainted pool tells it to do, which is treat every node as equally fair game, cost included.

What Actually Fixed It

The fix had two parts, and skipping either one leaves a real gap. First, taint the pricier pool with a NoSchedule effect, so nothing lands there by default. Second, give the pods that actually needed that pool both a matching toleration and a node affinity naming that pool directly — the toleration alone would have let those pods land there if the scheduler happened to pick that node, but it wouldn't have made the scheduler prefer it over an untainted node with room to spare.

That second half is easy to skip, because a toleration-only pod usually does end up on the intended pool anyway, especially early on when the pricier pool has the most free capacity. It's a bet that quietly stops paying off as the cluster grows and the general fleet's autoscaler starts filling in gaps faster than the tainted pool's does — and by the time it stops paying off, nobody remembers that the affinity was ever the part actually doing the pinning.

So what: the fix that held up wasn't "add a taint," it was "add a taint and treat the toleration and the affinity as one inseparable pair" — which is exactly the pairing I reached for by default in today's chart, not as a best practice I looked up, but as a rule I don't relitigate anymore.

Where That Lesson Lands in Today's vLLM Chart

vllm-deploy-kit's deployment template reads values.nodeSelector, values.tolerations, and values.affinity straight through with toYaml, all three defaulting to empty so the chart is a no-op on a cluster with no tainted GPU pool at all. The moment a cluster does taint one — the standard shape is nvidia.com/gpu=true:NoSchedule — values.example.yaml shows the pairing that pool needs: a toleration matching the taint, and a nodeSelector pulling the pod toward it on purpose. Leaving either one out reproduces the exact gap Route Service's platform lived with, just against a GPU node instead of a memory-heavy one — and a GPU node sitting idle while it bills is a more expensive version of the same mistake, not a different one.

So what: the bridge here isn't a metaphor stretched to fit, it's the same taint-toleration-affinity triple showing up on a pod that happens to want a GPU instead of extra memory — and the fix is the one I already trust, because I watched what shipping only two-thirds of it actually costs.

What I Still Don't Know

I don't have the exact instance type or node count the OSRM pool ran on anymore, or a dollar figure for what the missing affinity cost before it was fixed — I'm not going to invent either one to make this post read cleaner. I also don't know whether today's vllm-deploy-kit chart will ever run against a cluster with a real tainted GPU pool before this arc ends; the values exist and are tested against synthetic taints in scripts/test-chart.sh, but nothing in this repo has deployed to a live GPU node yet.

So what: the taint-toleration-affinity mechanism and the reason all three matter together are the part I'd stake this post on; the precise cost of getting it wrong is a number I know was real and don't have anymore, and I'd rather say that plainly than back-fill a figure that sounds more convincing than it is.
