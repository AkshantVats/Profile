Day 20 — Route Consumer Lag — Why CPU-Based HPA Failed at Lunch Rush

Delivery Hero · Route Consumers · Order SQS depth as the scale signal

AS
Akshant Sharma
June 7, 2026
13 min read
Experience · Day 20 of 150

I was on-call the afternoon our Route Consumers fell three orders of magnitude behind the Order SQS queue. The Kubernetes HPA dashboard showed eight pods running at 30% CPU. Everything looked green. What the dashboard wasn’t telling me was that 18,000 messages had piled up in the queue, and riders across the platform were showing ETAs that were 4–8 minutes stale. Customers were getting phone calls from confused riders asking why the app wasn’t updating. The system wasn’t misbehaving — it was operating exactly as configured. The configuration was just measuring the wrong thing.

CPU-based HPA is the default autoscaling option on EKS, and for stateless request-response services it is often the right choice. Route Consumers are not that. They are I/O-bound queue workers: each goroutine spends most of its cycle waiting on a 20-second SQS long-poll and a 20–80ms OSRM HTTP call. CPU during that wait time is near zero. A scale signal that measures CPU is measuring how hard the pods are working, not whether the work is keeping up with demand. Those are two completely different questions.

The right scale signal for a queue consumer is always the queue depth — the number of unprocessed messages waiting. Everything I learned from the lunch-rush incident traces back to that single sentence.

The system at lunch rush

Route Consumers are an EKS deployment at Delivery Hero’s logistics platform. They poll the Order SQS queue for lifecycle events: PLACED, PICKED UP, RIDER ENQUE, and RIDER PICKED UP. For each consumed event, the consumer fires an HTTP call to OSRM — the Open Source Routing Machine — to get a map-matched route: a polyline, distance, and route revision number. That Route object is what powers the rider ETA display in the customer app.

The work per event was straightforward in sequence but expensive in wall time: poll SQS with up to 20 seconds of long-poll timeout, parse the message, call OSRM (20–80ms), assemble and persist the Route object. CPU consumed per event was roughly 15ms out of a 100–200ms total cycle. The remaining 85–90% of each goroutine’s time was blocked, waiting on external I/O.

The topology is clean on paper. Order Service produces events, Route Consumers drain the queue, OSRM computes the route, the Route object feeds the UI. The failure mode is invisible until you ask: what happens when the queue produces faster than consumers can drain? The answer is that the queue grows, ETAs stale, and CPU stays flat because the goroutines are mostly blocked waiting on the very I/O that’s falling behind. The signal for user experience degradation never shows up in the CPU chart.

What consumer lag actually looks like

SQS lag is measured through the ApproximateNumberOfMessages metric — the visible queue depth. Unlike Kafka, SQS has no per-consumer offset tracking; there is no monotonic counter you can diff against a committed position. You get a snapshot: this many messages are visible right now, waiting to be received. CloudWatch updates this metric approximately every 60 seconds.

During the lunch-rush incident, the queue grew from around 200 messages to roughly 18,000 in six minutes. By the time CloudWatch reflected the full depth, four to five minutes of the spike had already elapsed before our on-call alert fired. Rider ETAs were stale by an estimated 4–8 minutes. The on-call alert was set to trigger at 5,000 messages — which it eventually did — but the damage to user experience was already done by the time the threshold was crossed.

Think of it this way: measuring restaurant wait time by counting kitchen staff tells you nothing about the line of customers at the door. The kitchen workers’ activity rate (CPU) is not what customers experience. The queue of waiting customers (SQS depth) is. When you alert on the wrong signal, you learn about the problem after your users already have. The right signal is always the one that tracks what users directly experience — and for a queue consumer, that is the depth of the queue.

Why CPU was the wrong signal

CPU-based HPA works well for request-response services where each request is CPU-bound: a computation, a serialization, a tight loop. The autoscaler’s logic is sound for that case — more requests means more CPU, add more pods. Route Consumers violated every assumption in that model.

With eight pods and four goroutine workers per pod, the consumer had 32 concurrent OSRM requests in flight at any moment. At 5,000 events per second arriving on the queue, 32 concurrent workers represent a 156-to-one backlog ratio — 156 incoming events for every one the consumer can pick up in a single worker slot. CPU never saw this. Each goroutine was spending ~85% of its time blocked on SQS long-poll or OSRM HTTP, so CPU across all 8 pods averaged ~30% even while the queue grew from 200 to 18,000.

CPU measured infrastructure comfort, not user experience. The right metric was queue depth — the number of riders waiting for an updated ETA.

The CPU-based HPA model and the KEDA queue-depth model produce identical pod counts during normal operation. They diverge catastrophically at the exact moment you need them most — during a lunch-rush surge when the queue outpaces consumers. Measuring the signal users experience, rather than the signal that’s easiest to instrument, is the design decision that separates a system that degrades gracefully from one that silently fails.

The fix: KEDA + queue-depth HPA

KEDA — the Kubernetes Event-Driven Autoscaler — extends HPA with external metrics sources. It runs as a controller in the cluster, polls external systems like SQS, Kafka, or Redis, and creates a standard Kubernetes HPA object targeting a custom metric instead of CPU or memory. For SQS, it queries ApproximateNumberOfMessages via the CloudWatch API and scales the deployment to keep queue depth per replica below a target threshold.

The ScaledObject configuration for Route Consumers looked like this:

apiVersion: keda.sh/v1alpha1
kind: ScaledObject
metadata:
  name: route-consumer-scaledobject
spec:
  scaleTargetRef:
    name: route-consumer
  minReplicaCount: 4
  maxReplicaCount: 32
  cooldownPeriod: 120
  triggers:
    - type: aws-sqs-queue
      metadata:
        queueURL: <Order SQS URL>
        targetQueueLength: "500"
        awsRegion: eu-west-1

The targetQueueLength: "500" means KEDA targets 500 messages per replica. At 18,000 messages queued, the desired replica count becomes 18,000 / 500 = 36, clamped to the 32-pod maximum. The scale-up happens in seconds, not minutes. There is one non-obvious migration caveat: KEDA creates its own HPA object for the deployment. A Kubernetes deployment cannot be targeted by two HPA objects simultaneously — the controllers will fight each other. The existing CPU-based HPA had to be deleted before the ScaledObject was applied.

We scheduled the migration window at 6am IST, 90 minutes before breakfast peak, to minimize exposure. The deletion and reapply took under three minutes. After migration, the first lunch rush hit and the consumer scaled from 4 pods to 28 pods in under 60 seconds. Queue depth peaked at ~1,200 messages and cleared in roughly two minutes. Before the fix, we were clearing peaks of 18,000 in 25–35 minutes or not at all. The right signal — queue depth — gave the autoscaler the information it needed to act before user experience degraded.

OSRM as the second bottleneck

After deploying the KEDA ScaledObject, the consumer scaled to 32 pods at peak. Thirty-two pods times four goroutine workers per pod equals 128 concurrent OSRM requests hitting the cluster simultaneously — four times the previous steady-state load. OSRM P99 latency, which sat around 80ms at baseline, climbed to an estimated 340ms under this load. The queue cleared, which was the primary win, but OSRM became the new bottleneck. We had fixed the scale signal without checking downstream capacity first.

The fix had two parts. First, we requested two additional OSRM replicas from the team that maintained the cluster. Second, I added an in-process LRU cache to the Route Consumer itself, keyed on (origin_cell, destination_cell) pairs quantized to H3 hexagonal grid cells. During lunch rush, pickup hotspots in a city cluster tightly — the same restaurant areas generate dozens of route requests to nearly identical origin-destination pairs within minutes of each other. The cache hit rate during lunch was approximately 18%, reducing OSRM RPS by roughly one-fifth. Combined with the additional replicas, P99 came back to an estimated 120ms — above the 80ms baseline, but well within acceptable range.

Scaling a highway works until the exit ramp backs up. Adding lanes to the highway is the right first step; it just does not help if the exit ramp has its own congestion limit. The lesson is not to avoid scaling — it is to map the downstream capacity before deciding the scale ceiling. Work backwards from what the downstream can absorb, not from what the consumer feels comfortable requesting.

What I’d do differently

I would instrument queue depth as a Prometheus metric from the consumer’s first deployment, not after an incident. The sqs_approximate_number_of_messages CloudWatch metric is one API call away from becoming a Prometheus gauge; there is no engineering complexity, only the discipline to treat it as a first-class operational signal before you need it.

I would design the scale target before choosing the pod count. The calculation is: what is OSRM’s max concurrent request capacity? Divide that by workers per pod to get the safe maximum replica count. Work backwards from the downstream limit, set maxReplicaCount conservatively, then validate with a load test at that ceiling. If we had done this before deploying KEDA, we would have requested the two additional OSRM replicas before the first scaled lunch rush, not after.

I would decouple the SQS polling goroutines from the OSRM request workers into two separate goroutine pools connected by a buffered channel. The 20-second SQS long-poll and the 20–80ms OSRM call have entirely different latency profiles and backpressure characteristics. When they run in the same goroutine, OSRM latency spikes cause the SQS poller to back off, which means the queue drains more slowly precisely when it is deepest. Separate pools let each layer apply backpressure independently without blocking the other.

I would add consumer lag to the morning operational email as a trend line, not just as a threshold alert. A 7-day trend of lunch-peak queue depth would have shown the growing pattern weeks before the 18,000-message incident. By the time an alert fires, you are already in the incident. The trend is the signal that lets you act before the threshold is crossed.

The connection to Day 20 code

Today’s ebpf-llm-tracer work includes a README comparison table that argues for kernel-level eBPF interception over SDK instrumentation. The argument is that SDK tracing measures what the application thinks it is doing, while eBPF interception measures what the kernel actually observes. Those two things diverge under load, under misconfiguration, and under failure — exactly when the measurement matters most. The Route Consumer incident makes the same argument in a different domain: CPU measures what the infrastructure thinks it is doing; queue depth measures what users are actually experiencing.

The KEDA ScaledObject and the eBPF README comparison table share a common design principle — instrument the signal closest to the user outcome, not the signal closest to the infrastructure component. For an LLM inference system, that means intercepting token flow at the kernel boundary, not at the SDK call site. For a queue consumer, that means measuring queue depth, not pod CPU. The right signal is not always the easy signal; it is the one that tells you what you need to know before the user notices.

Both decisions require the same discipline: resist the default instrumentation path, ask what metric tracks user experience most directly, and instrument that first. The default path — CPU for HPA, SDK for LLM tracing — is the path of least resistance and the path most likely to leave you reading a green dashboard while something important quietly falls behind.
