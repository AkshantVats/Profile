Day 86 — Delivery Hero Distributed Tracing — Finding the Slow Span

Delivery Hero's rider tracking pipeline moves a position update through several hops before it becomes a Route object the UI can render: Order Service takes the update in, Order SQS carries the lifecycle events (PICKED UP, RIDER ENQUE, RIDER PICKED UP) that Route Service and Route Consumers both read, and both of those call into the same shared OSRM cluster to map-match a rider's raw GPS point onto the road network. Every one of those components logged competently — timestamps, request IDs, error codes, the works. None of those request IDs meant anything to any other component's logs.

That gap doesn't matter on a good day. It matters enormously the day a dashboard shows OSRM call latency climbing and everyone's first instinct is to reach for the runbook from the last time that exact metric moved.

Mine — trace-ID propagation across the Route Service / Route Consumers / OSRM handoff
I proposed and built the trace-ID propagation this post describes: attaching an ID at Order Service ingress, carrying it as an SQS message attribute, and having Route Service, Route Consumers, and the OSRM call sites log it. I did not own Order Service's own instrumentation beyond the attribute it emits, and this was never a company-wide APM rollout — just enough correlation to answer one recurring question about this one pipeline.

"It's Probably OSRM" Is a Guess, Not a Diagnosis

Route Consumers' own dashboard showed the same shape it had shown during the lunch-rush incident a few weeks before: OSRM call latency trending up, aggregated across every call the consumer made in a rolling window. The obvious read was the obvious read — OSRM's connection pool was saturated again, same mechanism as last time.

Except this time OSRM's own dashboards, on the platform team's side of that call, showed nothing unusual. Per-call latency inside OSRM was flat. Two teams were looking at two dashboards that disagreed about the same system, and neither dashboard could see far enough into the other's territory to settle it.

A dashboard aggregating "OSRM call latency" across a rolling window answers "how slow, on average, over this window" — it can't answer "was this one rider update slow because of one long call, or because of two calls that shouldn't have happened at all." Those look identical in an average. They are not the same problem, and they don't have the same fix.

So what: a metric that's aggregated across many requests can tell you something moved, but it can't tell you whether it moved because one thing got slower or because more things started happening — and treating those as the same question is how you end up re-running last month's fix against this month's actual cause.

Where to Attach an ID Nobody Asked For Yet

OptionWhat it gets youWhy it loses (or wins)
A. Correlate by timestamp across each service's own logsAn approximate join, done by hand, after the factWorks for one investigation if you're patient and the clocks agree closely enough — doesn't scale past a handful of incidents, and silently fails whenever two events land in the same second.
B. Adopt a company-wide tracing vendor across every service at onceFull distributed tracing, everywhere, eventuallyThe right long-term answer and the wrong thing to wait for — that rollout touches every team's service, and this one pipeline needed an answer this week, not this quarter.
C. Attach a trace ID as an SQS message attribute, log it at every hop (chosen)One ID, generated at Order Service ingress, riding the same message the lifecycle events already travel onSQS message attributes already exist for exactly this — metadata that rides with the message but isn't the message body — so this cost a field, not a new system.

Option C works because Order SQS was already the one thing every downstream hop in this specific pipeline reads from. A trace ID didn't need a new transport — it needed to ride the transport that was already there, the same way a shipping container's manifest rides inside the container instead of traveling by a separate courier that might arrive on a different truck.

So what: the cheapest way to add correlation to a pipeline is usually to find the one channel every hop already reads from and attach the ID there — not to stand up a new channel whose only job is carrying IDs.

Order Service mints the ID once, the moment a rider position update comes in, and sets it as an attribute on the SQS message carrying that update's lifecycle event. Route Service and Route Consumers each read the attribute back off the message they already have to read anyway and include it in every log line touching that update, including the OSRM call itself.

Nothing about the Route object's own shape changed. The ID travels alongside the work, not inside the work — the same header-not-body posture the streaming proxy in today's code takes with its own routing metadata, described below.

So what: propagating a trace ID doesn't require touching what a message means, only what rides alongside it — the payload every downstream consumer already expects stays exactly the shape it always was.

The Slow Span Wasn't Where We Guessed

Once every hop was logging the same trace ID, the next time that latency dashboard climbed, the on-call didn't have to guess. Filtering logs by one rider update's trace ID showed something the aggregate dashboard could never have shown: for a slice of updates, the same trace ID had two OSRM calls attached to it, not one.

OSRM wasn't slow. OSRM was being asked to do the same map-matching work twice for the same rider update, and the aggregate dashboard had no way to tell "one call, slow" apart from "two calls, each ordinary speed" — both show up as more OSRM-attributed time per update in a rolling average.

The second call traced back to SQS's own visibility timeout: under mild backpressure, a message could sit unacknowledged in Route Consumers just long enough for it to become visible again and get picked up by a second consumer instance, before the first instance's OSRM call had returned and deleted the message. Two workers, one message, one duplicated OSRM call — and until there was a trace ID tying both calls back to the same rider update, that duplication was invisible inside "OSRM call latency," not a separate line item next to it.

So what: distributed tracing's real value on this incident wasn't pinpointing which hop was slow — it was disproving a specific, plausible, wrong hypothesis fast enough that the team never spent an afternoon re-resizing a connection pool that was never the problem this time.

A metric can tell you something got slower. Only a trace can tell you whether it's actually the same thing happening twice.

Today's TraceForge Hook, Same Discipline

Today's fallback-chain code carries this exact lesson into RouteIQ's own model-routing pipeline. A fallback walk that tries up to three models under the cascading timeout budget is, structurally, the same shape as this rider-tracking incident: multiple attempts that need to be recognizable as belonging to one decision, not read as unrelated calls in an aggregate latency metric.

pkg/trace injects a W3C traceparent header — the standardized version of what Order Service's SQS attribute was doing by hand — on every outbound call to a model provider, and tags every attempt's span with one routeiq.decision_id, generated once per routing decision and shared across however many hops that decision tries. The parallel to the SQS attribute is direct: an ID that rides alongside the request, attached once at the point a decision starts, read back at every hop downstream, so a debugging session (or, eventually, a dashboard) can ask "show me every attempt this one decision made" the same way this post's trace ID let the on-call ask "show me every OSRM call this one rider update made."

So what: the mechanism that let a Delivery Hero on-call catch a duplicate OSRM call is the same mechanism — one ID, minted once, carried on every hop, read back at the point something needs explaining — that makes a model-routing decision debuggable months before anyone building it hits their own version of "the dashboard says X, but is it really X?"
