Day 133 — Sanity Generations — Smell Test Before Eval

The plan line promises the kind of bug you catch by eyeballing output: a model spewing broken JSON because a prompt template got mangled. There's no live model in this sandbox to produce that failure. What actually got caught, by writing the script that would have caught it, was a real ordering bug in the script itself — the smell test smelling something wrong with its own kitchen before it ever plated anything.

The plan line for today reads "Sanity Generations — Smell Test Before Eval," subtitled with a specific failure: a model spewing broken JSON because a prompt template got mangled somewhere. That's a real, common way a fine-tuned adapter goes quietly wrong. It isn't what happened this week, because there is still no live model anywhere in this sandbox to spew anything.

Scope note — what actually shipped vs. what the plan line implies
Every generation this arc produces, including today's, comes from StubGenerationBackend — a deterministic function of the prompt string, not a model forward pass. The real path, HFGenerationBackend, exists in today's code and calls PEFT's actual model.generate(), but nothing in this CI can exercise it: no GPU, no base-model weights on disk. So there is no broken-JSON story to tell from a real run. What this post is actually about is a smaller, truer version of the same idea — a sanity check catching something wrong before it reaches something more expensive to run — except this time the thing it caught was a bug in the sanity check itself.

A Smell Test, Not the Whole Meal

A line cook tastes the sauce before it goes out on a hundred plates. That taste isn't a substitute for the health inspector's full review, and it doesn't catch everything — but it catches the one failure mode that matters most in the moment: something went obviously, cheaply-checkable wrong, and a hundred plates are about to carry it out the door anyway.

generate_samples.py is that taste. It resumes a run's adapter checkpoint through CheckpointManager.latest_step() and resume_dir() — the same resume mechanism Day 130's checkpoint work already built, not Day 132's still-unmerged finalize() trio — runs a fixed set of five SANITY_PROMPTS through whichever GenerationBackend is configured, and writes every prompt and completion to a JSON SampleReport. It is deliberately small: five prompts, read by a person, before anything touches an eval harness that costs real compute to run at scale.

So what: the eval harness this points toward doesn't exist yet in this arc, but the failure it's meant to guard against is universal — a training run can finish clean, checkpoint clean, and still have quietly learned to output garbage. Five prompts and a human skim is the cheapest possible check for that, before anything more expensive gets to disagree.

The Bug the Smell Test Caught in Itself

HFGenerationBackend reads the adapter's files off disk the moment it's constructed — that's how PEFT's from_pretrained works, there's no lazy option. My first draft of generate_samples() built that backend, then downloaded the checkpoint files afterward. Running it against even the stub path exposed the ordering fault immediately: by the time the backend would have looked for files, in the real path, they wouldn't be there yet.

OrderWhat happensResult
Backend first, download secondHFGenerationBackend reads an empty directoryCrashes, or silently loads nothing
Download first, backend secondFiles are on disk before anything reads themWorks, every time

The fix is a checkpoint_already_resumed flag: main()'s real-generation path downloads once, then tells generate_samples() not to repeat it, so the backend is only ever constructed after its files exist. So what: this is precisely the class of bug the sanity check exists to catch downstream — a component built or loaded against stale or missing state, producing something wrong without raising an obvious error. Today it caught that class of bug in its own code, before a single sample was ever generated for real.

Sweeping Without a GPU to Sweep

The other half of today's ticket, sweep.py, hits the same honesty problem generate_samples.py does: "document hyperparameter sweep results" implies real numbers from real runs across learning rate, LoRA rank, and batch size. There are none to document. What exists instead is a small, explicit, deterministic model of how those three knobs plausibly move loss and throughput, run for real, with its real output captured in SWEEP_RESULTS.md and labeled illustrative on the page itself — not hand-typed numbers pretending to be measurements.

The first draft of that synthetic model ran 1000 steps by default. At that length every learning-rate row decayed to the same loss floor, which hid the one variable the sweep exists to differentiate. Dropping the default to the CLI's actual 200-step run made the learning-rate signal visible again in the table that got committed — the same instinct as the ordering bug: run it, look at the actual output, don't trust that the code does what the docstring claims until it's been watched do it.

So what: neither script needed a GPU to be worth building or worth being honest about. The sanity-check pipeline and the sweep-reporting pipeline both now exist, tested and working, ready for the day a real adapter and a real sweep have something true to run through them.

What I Still Don't Know

HFGenerationBackend has never run against a real base model in this environment, so I don't actually know whether the ordering fix is the only integration bug waiting in that path — only that it's the one a dry run could surface. SWEEP_RESULTS.md's numbers are exactly what the doc says they are: outputs of a synthetic model chosen to look plausible, not measurements of how local-Llama-3-8B actually responds to rank or batch size.

The broken-JSON failure the plan line describes is still out there, waiting for a run with a real model to actually produce it. What exists today is the harness that would catch it — and evidence, from catching a bug in itself, that the harness's basic instinct already works.

So what: a smell test is only worth as much as the discipline of actually running it and reading what comes back. This week, that discipline caught a bug in the smell test before it ever got the chance to miss one downstream.
