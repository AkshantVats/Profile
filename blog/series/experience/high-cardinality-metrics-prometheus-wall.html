High-Cardinality Metrics — The Prometheus Wall We Hit

Agoda · schema design · label explosions

There is a moment in every observability build where someone adds one more label "just for debugging" and the metrics pipeline silently begins to collapse. At Agoda's WhiteFalcon team, we found that moment the expensive way. The Prometheus TSDB ran out of memory, scrape targets started failing, and the alert we most needed — the one that would have told us the stack itself was degrading — was the first thing to go dark.

This post is about that incident, the schema discipline it enforced on us, and why the DESIGN.md for today's ebpf-llm-tracer has an explicit cardinality cap written into its ingest contract.

How the label explosion happened

The WhiteFalcon platform was emitting latency histograms for a suite of model-serving endpoints. The original schema was sensible: service, endpoint, and status_code. Cardinality was bounded, scrape latencies were fine, Grafana dashboards loaded in under a second.

Then the team added model_id — a reasonable ask from the ML team who wanted per-model breakdown. Cardinality ticked up but remained manageable because model_id had maybe fifteen distinct values at the time.

The problem arrived over the next six weeks in three increments:

  • A new Kubernetes rollout introduced pod as a label, automatically injected by the metrics exporter. Fifty pods in the fleet.
  • Multi-region expansion added zone. Four zones.
  • A/B testing scaffolding added experiment_id — with hundreds of active experiments at any given time.

At that point the math became unavoidable: 15 model_ids × 50 pods × 4 zones × 200 experiment_ids × 8 endpoints × 6 status_codes. The combinatorial product exceeded three million unique label sets for a single histogram metric family, before even counting the histogram bucket dimensions.

Cardinality does not grow linearly with the number of labels. It grows as the product of every distinct value across every dimension. One bad label multiplies everything that came before it.

Why Prometheus TSDB breaks under high cardinality

Prometheus stores each unique label set as its own time series. Every series requires an entry in the head block's inverted index, plus in-memory chunk heads. Memory footprint scales roughly linearly with the number of active series. At four million active series, a mid-size Prometheus instance with 32 GB RAM was already above the safe headroom threshold for the scrape interval the team was running.

When memory pressure peaks, Prometheus starts dropping samples rather than crashing cleanly. The compaction loop falls behind. WAL replay on restart slows to minutes. Meanwhile the metrics emitted by Prometheus itself — prometheus_tsdb_head_series, prometheus_tsdb_head_chunks_created_total — are stored in the same overloaded TSDB, so the very signals that would have triggered a cardinality alert were unreliable at exactly the moment we needed them.

This is the self-undermining failure mode: a cardinality explosion degrades the observability of the observability stack itself.

Label taxonomy: bounded vs. unbounded dimensions

Not all labels carry equal cardinality risk. The core discipline is distinguishing dimensions that are bounded by design from those whose cardinality can grow at runtime without any schema enforcement.

Label Bounded? Value count Risk class
serviceYes — deploy-time~10Safe
endpointYes — code-defined~8Safe
status_codeYes — HTTP spec~6Safe
model_idSoft — ML registry15 → 150+Medium
podNo — fleet size50 → 500High
zoneSoft — region count4 → 12Medium
experiment_idNo — runtime minted200 → unboundedCritical
user_idNo — per-usermillionsProhibited

The practical rule we arrived at: any label whose distinct value count cannot be known at deploy time must be treated as unbounded and is presumptively rejected from the Prometheus schema. If per-experiment breakdown is needed, the right tool is a log aggregation pipeline or a columnar store, not a time-series counter.

What we actually did to recover

The incident remediation had three phases. The first was emergency triage: drop the experiment_id label entirely from the affected metric families using a metric_relabel_configs drop rule in the scrape config. This halved cardinality within one scrape cycle.

# prometheus scrape_config relabeling
metric_relabel_configs:
  - source_labels: [__name__]
    regex: 'model_serving_request_.*'
    action: keep
  - regex: 'experiment_id'
    action: labeldrop
  - regex: 'pod'
    action: labeldrop

The second phase was a schema review gate. No new label could be added to a production metric without a cardinality impact review. The review asked three questions: what is the bounded maximum of distinct values, what is the product of this label with existing dimensions, and is Prometheus really the right store for this cardinality level.

The third phase was architectural: push high-cardinality dimensions into the trace pipeline instead. Experiment-level breakdown moved to a ClickHouse-backed aggregation layer where columnar storage makes sparse high-cardinality queries far cheaper than Prometheus ever could.

Bounding cardinality at ingest time

Relabeling in scrape config is reactive: it fires after the metric is already emitted. The stronger control is enforcement at ingest time, before the time series is ever written. There are three practical mechanisms:

1. Allowlist-based label acceptance

Define the exact set of labels a metric family may carry. Any label not on the allowlist is stripped at the instrumentation layer, not at the TSDB boundary. This puts schema ownership with the team that writes the metric, not the platform team that manages Prometheus.

2. Cardinality budget per metric family

Assign each metric a maximum number of active series. The instrumentation library checks the live series count before writing a new label combination. If budget is exceeded, the write is either rejected or the metric is emitted without the high-cardinality labels. This is the pattern ebpf-llm-tracer implements: a hard cap of ten thousand series per metric family before the tracer falls back to aggregate-only emission.

3. Label value normalization

Map unbounded values to bounded buckets at write time. A model_id that rotates over hundreds of experiment deployments becomes a model_family with five stable values. Per-experiment detail is preserved in the trace, not the metric.

Personal contribution — WhiteFalcon cardinality gate
I designed and implemented the schema review gate and the per-metric cardinality budget system at Agoda after the incident. The gate became a required step in the metric instrumentation checklist and was eventually codified as a linting rule in the internal SDK: any new metric label that introduced a cross-product exceeding 50,000 series required explicit sign-off from the data platform team. That same instinct — bound cardinality in the schema, not in the query — is what drove me to write the cardinality cap directly into the ebpf-llm-tracer DESIGN.md before any instrumentation code was written.

Approved vs. rejected label combinations

The review gate produced a two-column taxonomy that became tribal knowledge on the team. Here is a condensed version of the patterns that were approved and rejected:

Pattern Decision Reasoning
service + endpoint + statusApprovedAll bounded, product < 500
model_family + zoneApprovedNormalized model_id, bounded zones
model_id + podRejected15 × 500 = 7,500, scales with fleet
model_id + experiment_idRejectedUnbounded experiment count
request_id (any metric)ProhibitedPer-request = millions of series
user_id (any metric)ProhibitedPer-user = millions of series
error_type + endpointApprovedBounded error taxonomy
http_path (raw URL)RejectedQuery params make it unbounded
http_route (template)ApprovedRoute template is bounded

The last two rows are worth calling out explicitly. /api/search?q=paris&checkin=2026-05-01 is unbounded. /api/search (the route template) is not. The distinction between URL path and URL route is one of the most common cardinality mistakes in web service instrumentation.

Why LLM tracing amplifies the problem

LLM inference workloads create a specific cardinality pressure that did not exist in the model-serving context at Agoda. The dimensions multiply further: model_id is no longer a stable list of fifteen models — it includes model versions, quantization variants, LoRA adapter identifiers, and prompt template hashes. A single production LLM platform can have hundreds of distinct model variants active simultaneously.

Add to this the eBPF instrumentation context: when you are tracing at the kernel syscall boundary, you see every process, every socket, every memory allocation. Without aggressive pre-aggregation, the number of distinct label combinations per second is orders of magnitude higher than anything a traditional APM agent would emit.

This is the environment ebpf-llm-tracer is designed for. The DESIGN.md cardinality cap — ten thousand active series per metric family, hard-enforced at the BPF map level before any data crosses the ring buffer to user space — is a direct response to watching a less careful system destroy a metrics stack once before.

Design decision — ebpf-llm-tracer cardinality contract
The DESIGN.md cardinality section states the constraint explicitly: the tracer emits at most ten thousand distinct label combinations per metric family per reporting window. If a new label set would exceed the budget, the tracer falls back to an aggregate-only counter tagged with cardinality_overflow=true. This makes the overflow visible rather than silent, and preserves the shape of the metric even when individual label detail is dropped. The Agoda incident shaped that design directly — the worst outcome was not losing granularity, it was losing the metric entirely while the TSDB was OOM.

Five rules that survived the postmortem

These are the rules that came out of the WhiteFalcon postmortem and that I apply to every observability schema I design today:

  • Rule 1: Know your cardinality budget before you write the first metric. Decide the maximum series count the system is designed to carry. Write it in the repo. Make it a constraint, not a retrospective.
  • Rule 2: High-cardinality dimensions belong in traces or logs, not metrics. Prometheus is a counter / gauge / histogram store for bounded aggregates. It is not a query engine for per-request or per-user analytics.
  • Rule 3: Automatically injected labels are the most dangerous. Pod names, container IDs, and node names are injected by exporters and service meshes. They need explicit stripping unless the fleet size is tightly bounded.
  • Rule 4: Unbounded labels that arrive at runtime must be prohibited at the schema level, not just dropped in relabeling. Relabeling is a last line of defence, not a design strategy.
  • Rule 5: The cardinality overflow path must be visible. When a metric falls back to aggregate-only emission because the budget is exceeded, emit a separate counter that says so. Silent cardinality drops are worse than explicit degradation.

Bridge: why this lives in ebpf-llm-tracer DESIGN.md today

The ebpf-llm-tracer project is a public eBPF-based tracer for LLM inference workloads. It instruments at the kernel syscall boundary and surfaces latency, token throughput, and memory pressure metrics for model-serving pods — without requiring any SDK changes in the model server itself.

The DESIGN.md opens with an observability contract section before any architecture description. That ordering is deliberate. The contract states the cardinality budget, the label allowlist, the overflow behaviour, and the rationale. It exists because I watched the alternative — adding observability incrementally without a schema contract — result in a two-hour partial blindness window at one of Southeast Asia's largest travel platforms.

The bridge from past to present is simple: schema discipline is not a post-incident hygiene task. It is a design requirement that needs to be written before the first BPF probe is attached, before the first prometheus_gauge_vec! macro is called, before the first scrape config is deployed. The cardinality wall is always there. The only question is whether you hit it at design time or at 3 AM.
