Day 75 — Wayfair's Redis Lua Token Bucket at 250k SKU Scale

Atomic INCR across replicas when pricing updates flooded APIs. Day 25's Lua script fixed a race condition. This is what changed operationally once that fix had to hold as the supplier catalog scaled toward 250k+ SKUs.

Today's ticket benchmarked prompt-fingerprinter's exact-match cache: hit rate, lookup latency, the numbers DESIGN.md promised back on Day 70. That's not a story on its own — it's a spreadsheet. What earned a post is the fingerprint cache's key format, because it borrows a discipline I first paid for the hard way on the rate limiter I wrote about on Day 25, at Wayfair, once that limiter had to hold at a scale the original fix was never tested against.

The Limiter Before: A Window That Could Lie to Twelve Pods at Once

Wayfair's supplier pricing path runs submissions through gst-acc-promotions — the HTTP service, running 12 pods, that suppliers' pricing tools call — into PAS (price-adjustment-system), which routes into SPCS, the Supplier Price and Cost Service that actually persists a price change. SPCS caps every client at 8 concurrent batch calls, 100 parts each: 800 parts in flight before it starts returning 429s.

The rate limiter guarding that 800-part ceiling used to be a plain Redis INCR followed by an EXPIRE, two separate round trips. At window reset, all 12 gst-acc-promotions pods could INCR the same just-expired key in the same instant, every one of them get back 1, and every one believe it was first through the door — SPCS's ceiling blown by roughly 12x before any EXPIRE landed to stop it.

Mine — Wayfair, pricing/promotions rate limiter and rollout
The Lua token-bucket fix and this post's rollout — the topology change, the batch-run verification, the reconciliation-window check — are work I owned end to end on the supplier pricing submission path, not infrastructure I inherited and observed.

So what: two Redis commands that look atomic from the client side aren't atomic to Redis at all — the gap between them is exactly wide enough for every pod in a fleet to walk through it at once.

The Fix I Already Wrote About: A Lua Script as One Execution Unit

Day 25 covers the mechanism in full, so I won't re-paste the script here. The short version: a single Redis Lua script reads the token count and last-refill time with HMGET, computes the refill owed, and writes the new state with HMSET plus EXPIRE — all inside one script execution, which Redis guarantees no other command can interrupt.

A token bucket, for anyone who hasn't met the pattern: think of a bucket that refills at a fixed rate and drains one token per request, and a request only proceeds if a token is available — it smooths bursts the way a header tank smooths a pump's flow instead of the pipe seeing every surge directly. That single-execution guarantee is what a naive INCR+EXPIRE pair never had, and it's the reason 12 pods hitting a reset window can no longer each believe they were first.

So what: Redis gives a Lua script the same isolation a database gives a stored procedure inside a transaction — not a faster rate limiter, but a structurally different one where "two commands mid-race" simply can't occur.

What Changed Operationally: The Rollout, Not the Script

Day 25 shipped the mechanism. What this post is actually about is what came after: PAS traffic wasn't flat while that fix aged into production. Average load sat around 3,414 RPS, with batch pricing runs pushing bursts to roughly 15,263 RPS — and the supplier catalog behind those submissions kept climbing toward the 250k+ SKUs per supplier the pricing engine was built to carry.

A rate limiter that's provably correct at moderate load still has to prove it stays correct once the traffic it's gating gets five times spikier. The rollout wasn't a redeploy of new code — the Lua script itself didn't change after Day 25 — it was a period of watching the same atomic mechanism absorb burst shapes closer to what 250k+ SKUs of supplier catalog actually produces during a coordinated batch run.

The Evidence: 800 Parts in Flight, Not 9,600

The signal that mattered wasn't a dashboard counter going green. It was SPCS's own 429 rate staying flat across the highest-volume batch pricing runs, at the 15,263 RPS peak, instead of spiking the way it had under the old INCR+EXPIRE limiter every time a window reset landed mid-burst.

So what: the metric that proves a rate limiter works isn't its own internal counter — it's whether the downstream service it's protecting stops seeing the failure mode the limiter exists to prevent.

The Rollback Check That Almost Blamed the Wrong Thing

Partway through that observation window, a slow stretch of requests briefly looked like the Lua script itself was the new bottleneck — understandable, since "the new atomic thing is slower than the old racy thing" is exactly the kind of tradeoff a rollback plan needs to be ready to catch. The rollback plan itself was simple: the old INCR+EXPIRE code path stayed deployed behind a flag, ready to flip back if the script's own overhead was the real cost.

Before reaching for that flag, a quick redis-cli check with script timing isolated where the latency actually lived: the Lua execution itself ran in single-digit milliseconds, well inside budget, and the slow stretch tracked with SPCS's own 429 backoff and retry behavior instead. Redis looked suspect for about ten minutes and turned out innocent — the rollback flag never got flipped.

So what: a rollback plan's value isn't only in the switch it provides — it's in forcing a verification step before flipping it, which is what turned "Redis looks slow" from an assumption into a ruled-out possibility.

The Same Discipline in Today's Cache Key

prompt-fingerprinter's exact-match cache, the thing I actually benchmarked today, keys every entry as fingerprint:{tenant_id}:{fingerprint} — a SHA-256 hash of the normalized prompt, scoped under a tenant ID rather than stored as a bare hash. DESIGN.md is explicit about why: a hash collision is cryptographically implausible under SHA-256, but "implausible" isn't the bar a shared cache should be built to, so the tenant scope means a collision, if it ever happened, stays contained to one tenant's keyspace instead of leaking a response across tenants.

That's the same shape as Day 25's fix, aimed at a different failure mode. The Lua script made a two-step race structurally impossible instead of merely rare; the tenant-scoped key makes cross-tenant leakage structurally impossible instead of merely unlikely. Neither fix depends on hoping a bad case doesn't line up with a worse one.

Today's benchmark put real numbers on that cache's fast path: TestLatencyPercentiles_L1Hit measured a p50 of 7.47µs for an L1 hit, and TestHitRate_DuplicateWorkload resolved 32.6% of a 35%-duplicate workload without ever reaching the semantic tier. Both numbers come from an in-process Redis stand-in, not a live instance, the same honest caveat this repo's own BENCHMARKS.md logs — but the key format underneath them doesn't depend on that caveat closing.

A racy INCR is wrong sometimes, under load, in a way a load test might not catch. A bare hash key is wrong once in an astronomically unlikely case that a load test can never catch at all. Both get fixed the same way: stop trusting the case won't happen, and make it structurally unable to.

So what: at 250k+ SKUs of supplier catalog and at whatever tenant count this cache eventually serves, correctness can't rest on "this probably won't collide at the same moment" — it has to be true by construction, which is what an atomic script and a tenant-scoped key both buy, in their own corner of the same system.
