A hiring panel rarely clones your repository first. They open the README, scroll for ninety seconds, and decide whether the system looks legible, falsifiable, and runnable. That first scroll is the artifact this post is about.

After two weeks on infra-ai-streaming, the implementation was real but fragmented across services, scripts, and docs. The root README still read like a changelog. Day 13 is the packaging pass that turns “work completed” into “work reviewable.”

The ten-second scroll test

In practice, reviewers ask four fast questions: what problem exists, what shape the system has, what proof supports the claims, and whether they can run it without guessing hidden steps. Missing one of these is often enough to stop deeper review.

Feature bullets without environment context are marketing copy. Staff panels look for reproducibility, operating constraints, and tradeoffs that survived contact with reality.

Proof beats promises

The biggest upgrade is evidence density. Benchmarks moved into a dedicated BENCHMARKS.md with explicit [TBD] markers rather than invented precision. Chaos moved to a compact matrix in the README with links to the full runbook for depth.

The discipline is simple: every claim points to a command, a metric, or an artifact. If a reader cannot verify it quickly, it does not belong in the top half of the README.

Design decisions belong in the open

Three tradeoffs now sit near the top: Rust ingestion on the hot path, ClickHouse for analytics workloads, and an AP ingest boundary. The goal is not architectural theater; it is making consequences explicit before a reviewer has to ask.

Pattern reused from production systems
In Wayfair pricing and Agoda data-platform work, the strongest docs always named rejected options and operating constraints. README design decisions follow that same review pattern.

Five commands or it doesn't count

Quick starts are contracts, not tutorials. If a fresh clone cannot reach running dashboards and observable data flow in a handful of commands, reviewers infer the platform is fragile no matter how strong the architecture section sounds.

  • Clone repo
  • Copy env and start compose
  • Run consumer
  • Run ingestion
  • Run smoke verification script

The README I'd send a Staff panel

The finished Day-13 README is designed to stand alone: architecture image, tradeoff table, benchmark scaffold, chaos summary, and concise run path. It is the link I would send before a Staff panel instead of a slide deck.

That closes week two for infra-ai-streaming and creates a clean handoff into day fourteen, where observability expands toward zero-SDK tracing paths.

Takeaway

Hiring committees scroll before they deep dive. Shipping without a strong README is effectively shipping without a public interface for engineering judgment.

Proof beats promises: clear tradeoffs, reproducible steps, and honest benchmark status make the work reviewable. That is what turns two weeks of code into a credible systems narrative.
