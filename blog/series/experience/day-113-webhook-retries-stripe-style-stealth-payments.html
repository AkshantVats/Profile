Day 113 — Webhook Retries — Stripe-Style at Stealth Payments

A pre-launch payments company's webhook consumer retried every failed delivery immediately, with no backoff and no way to tell "already processed" from "never arrived." Retrying looked like resilience. It was actually how one blip turned into duplicate charges and a self-inflicted traffic spike.

Scope note — pre-launch payments consulting, name withheld
I spent a short stretch consulting for a pre-launch payments startup on infrastructure hardening before their public launch — I'm not naming them, since they were pre-launch and it isn't my story to tell publicly. What follows is one specific webhook bug I found and the general pattern it taught me, not a description of their architecture, their volume, or their team. No system names, no numbers beyond what's necessary to explain the bug.

A Retry Loop That Looked Like Resilience

Their payment processor sent a webhook on every transaction event, and their consumer's job was simple: receive it, update the transaction record, return 200. When that consumer's database connection pool briefly saturated during a load test, some webhook deliveries started timing out on the receiving end.

The processor's client library did exactly what a retry-on-failure client is supposed to do: it retried. Immediately, with no delay, on every single timeout, for every webhook still in flight.

So what: a retry that fires the instant it fails isn't hardening a system under load — it's adding more load to the exact thing that's already struggling, at the worst possible moment to do it.

Two Different Gaps, One Bug Report

Same shape of mistake I'd later see in a Kafka consumer-lag alert at Agoda (Day 112): one incident, two separate gaps, and fixing only one of them still leaves the other one live. The first gap here was pacing — no backoff schedule, so a struggling consumer got hit hardest exactly when it was least able to absorb it.

The second gap was worse: some of those "failed" deliveries had actually succeeded on the receiving end before the response timed out. The connection pool update landed; only the 200 never made it back to the processor in time. Every retry against a request that had already succeeded created a second transaction record for the same event.

So what: a timeout tells you the response didn't arrive, not that the work didn't happen — and a consumer with no way to tell those two apart will treat "I already did this" identically to "I never got the chance."

Idempotency Keys, Taught Properly

The fix Stripe's own API popularized, and the one this company adopted, has two parts matching the two gaps above. Part one: back off between retries — a short delay after the first failure, doubling after each subsequent one, so a struggling consumer gets breathing room instead of a hammering.

Part two is the one that actually stops duplicate charges: every webhook carries a unique idempotency key, and the receiver keeps a short-lived record of every key it has already processed. A redelivered webhook with a key already on that list gets acknowledged immediately without repeating the side effect — the record update, the charge, whatever the webhook was supposed to trigger.

A courier delivering a certified letter is the same idea outside software: the letter carries a tracking number, and the courier's log records which tracking numbers already got a signature. Redeliver the same letter because the first signature confirmation got lost in transit, and the courier's log stops it from being logged as two separate deliveries — the tracking number is what makes "already delivered" a fact the system can check, not something it has to guess at from timing alone.

So what: a backoff schedule protects the receiver from load; an idempotency key protects the data from a retry that arrives after the original request already succeeded — and a system with only the first one is still one lost response away from a duplicate.

What This Buys DriftWatch's Retrain Webhook

Today's code builds the sender's half of this exact contract: `alert-rule-engine`'s new `HTTPRetrainClient` retries FineForge's /hooks/retrain webhook with full-jitter exponential backoff on network errors and 5xx responses, and fails fast on a 4xx instead of hammering a request that's already been rejected. That's the pacing half of what Stealth Payments got wrong on day one.

The idempotency half is honestly the receiver's job, not this client's, and it's worth naming rather than glossing over: FineForge doesn't exist as a real service yet, so nothing on the sending side of today's code can guarantee it. What today's request body already carries — rule_id, the alarmed segment, and the exact time window — is the natural key a real FineForge dedupe table would check before queuing a second retrain job for the same drift episode, the same way a payments webhook's idempotency key is checked before a second charge.

So what: a retry client can only ever fix half of this problem — it can be a well-behaved sender, but whether a redelivered request is safe to receive twice is a decision that has to live on the other side of the wire.

What a Backoff Schedule Doesn't Fix

Exponential backoff makes a retry storm less likely, but it doesn't make retries safe by itself — that's still the idempotency key's job, and a client that only ships backoff can feel done while still being able to double-charge someone. Today's HTTPRetrainClient is honest about this: it's a well-paced sender against a contract whose receiving half doesn't exist yet to verify against.

So what: "we added retries" and "we added safe retries" are different claims, and the gap between them is exactly the idempotency key a backoff schedule alone will never give you — pacing and correctness are two different problems wearing the same name.
