Day 109 — Multi-Tenant Noisy Neighbor — Stealth Ordering Burst

A volume spike that looked exactly like an attack turned out to be one restaurant partner's legitimate lunch rush. The alert couldn't tell the difference — because a five-location café chain and a four-hundred-location franchise cannot honestly share one threshold.

The alert read like the start of a bad week: request volume against our order ingress up several multiples of baseline, sustained, from a client that had never sent anything close to that rate. Every instinct said hostile burst. The instinct was wrong, and the reason it was wrong is the actual subject of this post.

Scope note — Delivery Hero, Global Logistics Platform
I was a Senior Software Engineer on Delivery Hero's Global Logistics Platform in Berlin from June 2022 to July 2023. My resume documents scaling that platform to 1M+ daily orders on AWS EKS (10k+ concurrent requests, zero downtime) and building end-to-end rider tracking on OSRM processing 5k+ real-time route updates per second. A specific franchise-vs-threshold incident is not a logged event or a named alert from that record — it's this post's illustrative framing for a tenant-fairness gap the platform's architecture makes structurally real, not a claimed, measured event.

A Question a Request-Rate Graph Cannot Answer

Order Service is the shared ingress hub for both customer and rider traffic on this platform — every restaurant partner's order flow lands there before anything else happens, persisted through Order Data Service and published as lifecycle events onto Order SQS for Route Service and Route Consumers to pick up.

A single restaurant partner's lunch-rush order volume is, structurally, indistinguishable from a hostile burst at that ingress point. Both are a sustained spike in request rate from one client. Neither carries a label that says "intent: legitimate."

So what: any alert built purely on volume is answering a question about shape, and shape alone cannot tell a real customer surge from an attack — the two produce the identical graph.

Why One Threshold Cannot Serve Every Partner

Delivery Hero's partner roster spans a five-location café chain and a several-hundred-location franchise, all landing on the same Order Service ingress. A threshold loose enough to let the franchise's normal lunch rush through without paging is, by construction, too loose to catch a genuinely hostile burst from the café chain — whose baseline volume is a rounding error next to the franchise's.

Tighten the threshold instead, tuned for the small partner, and the franchise's every ordinary Tuesday lunch rush pages someone. There is no single number that is simultaneously tight enough for the quiet tenant and loose enough for the loud one.

This is the same shape DriftWatch's CUSUM chart hits from the statistics side, days earlier in this arc: a fixed h threshold either misses real drift on a segment with unusually high natural variance, or fires constantly on it. So what: a fleet built from wildly different baselines needs a threshold that is aware of whose baseline it's watching, not one number applied uniformly.

The Fix Is a Preset, Not a Smarter Detector

The honest fix here was not a cleverer anomaly detector that infers intent from a request-rate curve — nothing about the shape of "many legitimate orders quickly" and "many hostile requests quickly" reliably separates the two at the ingress layer. The honest fix was admitting the threshold itself needed to vary by tenant.

A large, historically high-volume partner gets a looser tolerance: more sustained deviation from their own baseline before anyone gets paged, because their baseline naturally swings wider and a page on every lunch rush trains everyone to ignore pages. A smaller or newly onboarded partner gets a tighter one, since a burst from them is more likely to be exactly what it looks like.

Why this is fairness, not leniency
Calibrating "how much deviation is normal for you" per tenant is not giving anyone a pass — it's refusing to apply one fleet-wide assumption to partners with structurally different baseline volumes. A single global threshold is not neutral just because it's the same number for everyone; applied uniformly across a five-location chain and a four-hundred-location franchise, it is under-sensitive for one and paranoid about the other simultaneously.

So what: a preset per tenant is not a workaround for a detector that isn't smart enough yet — it's the correct model of a fleet that was never actually homogeneous in the first place.

The Honest Counterweight

A preset is a human-chosen snapshot, not a live measurement. A franchise that quietly shrinks after being marked "high tolerance" keeps that same loose threshold long after it stopped earning it, and nothing about the mechanism itself notices the drift in the tenant's own baseline.

trust-snapshot: 2024-Q1
  franchise-X: noisy   (400+ locations, high natural variance)
  cafe-chain-Y: strict  (5 locations, low natural variance)
  ... reviewed: never, automatically

That gap is worth stating plainly rather than glossing over: a preset encodes trust as of the day someone picked it, and re-evaluating that trust is a separate, currently-missing step. So what: the fix solves the false-alarm problem honestly, and just as honestly creates a new, quieter one — a static label that nothing keeps current.

The Same Shape Showed Up in Today's Code

Today's drift-detector commit implements the identical idea one arc over, in a different vocabulary: a tenant-selectable sensitivity preset — strict, balanced, or noisy — that scales the CUSUM chart's decision threshold before it starts watching a segment. A tenant whose traffic naturally swings wider gets a threshold that tolerates more accumulated deviation before paging; a tenant where a missed drift is expensive gets one that pages sooner.

It is not a coincidence that an ordering-platform incident and a statistics module land on the same fix in the same week. Both problems are the same problem: one number cannot serve every segment honestly when the segments don't share a baseline. Solve it once, as a tunable multiplier chosen per segment, and the fix generalizes to both a request-rate graph and a control chart.

So what: the interesting decision this week wasn't a new detection algorithm in either system — it was recognizing, twice, that "one threshold for everyone" was never actually a neutral default. It was just the default that happened to be easiest to write down first.
