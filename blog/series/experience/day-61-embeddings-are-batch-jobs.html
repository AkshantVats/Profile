Day 61 — Embeddings Are Batch Jobs

A batch-of-32 embedding worker and a hot-tier compaction cadence are the same decision, made in two different systems: pay a fixed per-call cost once for many items instead of once per item, and only if it's safe to redo the work.

An embedding API call has a fixed cost attached to it before it does a single unit of useful work — authentication, a network round trip, provider-side queuing. Call it once per prompt and you pay that fixed cost as many times as you have prompts. Call it once per 32 prompts and you pay it a thirty-second as often, which is the entire reason semantic-cache-engine's embedding worker batches its calls instead of firing one per incoming prompt.

I'd seen that exact shape of decision before, on a system that had nothing to do with embeddings.

What Shipped Today

Day 60 left semantic-cache-engine as a DESIGN.md — a pgvector schema, a similarity threshold, no runtime code. Day 61 is the first piece of that design that actually runs: an embedding worker that reads incoming prompts, batches them 32 at a time, calls an embedding API once per batch, and upserts the resulting vectors into a prompts(tenant_id, prompt_hash, embedding, created_at) table.

pkg/prompthash normalizes each prompt — trim, lowercase, collapse whitespace — then SHA-256s it into a prompt_hash, the key the rest of the pipeline is built around. pkg/embedder wraps an OpenAIEmbedder over text-embedding-3-small behind a small interface, so the batching logic never has to know which provider is on the other end of the call. pkg/cachestore writes vectors through pgx/v5 with ON CONFLICT (tenant_id, prompt_hash) DO NOTHING, and pkg/worker is the batching and in-run dedup layer that sits between them.

So what: none of these four packages is complicated on its own — normalize a string, call an API, write a row — but the batching and idempotency decisions connecting them are exactly the decisions that determine whether this worker is cheap and safe to run at volume, or neither.

Compaction Cadence Was the Same Decision, Wearing a Different Name

I spent about five months as a Senior Engineer on Core Infrastructure at Agoda, contributing to WhiteFalcon — the in-house TSDB handling roughly 1.5 trillion events a day through Kafka into Rust consumers. WhiteFalcon's hot tier buffers those events in Redis, time-windowed, for the last three to seven days of query traffic. It doesn't merge every new Parquet file into cold storage the instant it lands.

Team-owned — Agoda's compaction pipeline and Rust ingest path
The compaction cadence described here — hourly merges, coarsened to 3-hour, then to daily — is Agoda's design, running against their Kafka-to-Redis-to-Ceph/S3 pipeline. I contributed to the cross-tier query engine and a new cardinality dimension during my time there; I did not design the compaction jobs or the ingest path. This section describes the pattern I operated alongside, not a system I built.

Instead, WhiteFalcon's compaction jobs merge on a fixed cadence: hourly first, then those hourly files get merged into 3-hour files, then daily. Each merge pass is a batch operation over files that have already landed, run on a schedule instead of triggered per-file. The reason is the same reason the embedding worker doesn't call the API per prompt: merging one Parquet file at a time would mean paying a per-file merge overhead as many times as there are files, and at 1.5 trillion events a day, that overhead compounds into real cost.

So what: a compaction cadence and an embedding batch size look like unrelated tuning knobs until you notice they're solving the identical problem — a per-operation cost that's cheap once and expensive multiplied by however many times you pay it.

Batch Size Is a Tuning Knob, Not a Fixed Constant

32 wasn't picked because it's a round number that felt safe. A batch of 1 pays the embedding API's per-request overhead on every prompt, with no amortization at all — correct, but the most expensive possible shape. A batch of 1,000 amortizes that overhead about as well as it can be amortized, but the last prompt to arrive in that batch waits for 999 others before it gets embedded, which turns batch size into a latency knob as much as a cost knob.

Batch sizeWhat it buysWhat it costs
1 (no batching)Lowest per-prompt latencyFull per-call overhead paid every time
32 (worker default)Overhead amortized ~32x, bounded worst-case waitLast prompt in a batch waits for the other 31
1,000+Overhead amortized furtherWorst-case wait grows with batch size; one slow embed call blocks the whole batch

WhiteFalcon's cadence makes the same trade in the opposite direction: hourly compaction accepts a coarser bucket sooner, so recent data stays queryable at fine granularity for the 3–7 day hot window before it gets folded into the 3-hour and daily merges. A batch size and a compaction interval are both answering "how long am I willing to let work accumulate before I pay the fixed cost to process it," just measured in prompts instead of hours.

So what: there's no batch size or compaction interval that's correct in the abstract — both are a bet on how much latency the system downstream can tolerate in exchange for how much fixed cost gets amortized away, and that bet has to be made deliberately, not defaulted to.

Idempotency Is What Makes Batching Safe to Retry

Batching alone isn't the win. A batched call that fails halfway through and gets retried is a liability if the retry re-writes rows that already landed — that's a double-write, not a safe redo. pkg/cachestore's upsert is ON CONFLICT (tenant_id, prompt_hash) DO NOTHING, so a retried batch that re-embeds and re-upserts prompts it already processed simply does nothing extra on the rows that already exist.

My scope — Agoda, Bangkok, Apr–Sep 2024, Sr. Software Engineer, Core Infrastructure
I extended WhiteFalcon's Scala query engine to correctly merge quantiles across the hot/cold tier boundary and added a new Kubernetes cardinality dimension to the RoaringBitmap index. I did not build the compaction jobs described above — this post uses their cadence as the pattern, not a claim that I designed them.

WhiteFalcon's compaction gets the same safety property from a different mechanism: it merges immutable, already-landed Parquet files. A compaction pass that's interrupted and re-run doesn't corrupt anything, because merging the same set of files twice produces the same output as merging them once — the operation is idempotent by construction, the same way ON CONFLICT DO NOTHING makes the embedding worker's upsert idempotent by construction.

So what: without idempotency, a retried batch is a bug waiting for the right failure to trigger it; with idempotency, a retried batch is indistinguishable from success, and that's the property that makes both systems safe to batch aggressively instead of cautiously.

What This Doesn't Prove Yet

The honest gap: 22 of 22 unit tests pass — normalization, batching, and upsert-SQL construction are covered — but the integration test for actual pgvector idempotency is gated behind -tags=integration and a live PGVECTOR_DSN, and there's no Postgres instance with pgvector installed in this sandbox to run it against. The upsert's idempotency is verified at the SQL-construction level, not against a real database yet.

So what: a unit test that checks the upsert statement is shaped correctly is not the same claim as a test that ran the statement against a real table twice and confirmed the second run was a no-op — that gap is logged as follow-on CI scope, not silently dropped.
