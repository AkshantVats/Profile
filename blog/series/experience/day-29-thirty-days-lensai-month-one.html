Day 29 — Thirty Days of Building — What Shipped vs What Matters

LensAI month-one · four repos, one smoke test, and the Agoda go-live checklist that gave me the launch criteria framework

Thirty days of public building has two distinct phases. The first two weeks, you are writing toward something you hope will cohere — each post is a piece of evidence in an argument you haven’t fully formed yet. The last two weeks, the pieces are good enough that each new one makes the previous ones make more sense, and you can see what you were actually building rather than what you told yourself you were building. Today is Day 29, which means it is time to ask the honest version of the retrospective question: what shipped, what I would redo, and what the whole month was actually for.

I will be specific about what shipped because specificity is the only defense against retrospectives that become self-congratulation. The vague answer is “I built an AI inference observability platform.” The useful answer is four repos, a set of PRs, a smoke test, and a landing page. The gap between the vague answer and the useful answer is where the lessons live.

The bridge to today from Day 28’s integration testing post: Show HN and the OpenTelemetry Collector PR are distribution for the integration test I can rerun. Both require the same standard Agoda applied before shipping any cross-tier query extension to production: does this work end-to-end on a clean machine, without manual steps, and does it cover the edge cases that only show up when real infrastructure is running? That standard is the thread that connects WhiteFalcon staging discipline to the LensAI smoke test to the Show HN launch.

What actually shipped

Four repositories form the LensAI stack. I want to be precise about what each one is, because “LensAI” as a product name can obscure the actual moving parts. Each repo has a distinct role and a distinct set of technical decisions that went into it.

infra-ai-streaming is the Rust ingest pipeline. It runs a Tokio async Kafka consumer, reads LLM inference events from a topic, and writes them to ClickHouse via the clickhouse-rs client. The schema it writes is the inference_events table: timestamp, model_id (what the application requested), resolved_model_id (what flagd decided actually ran), token_count_prompt, token_count_completion, latency_ms, request_id. The resolved_model_id field is the column that makes cost attribution honest.

distributed-flagd is the Go feature flag daemon. It uses etcd as the backing store for flag state, exposes a gRPC streaming watch API so inference servers can receive flag updates without polling, and writes every flag change to a Kafka topic as an audit log. Its job in the LensAI stack is controlling which model version handles what percentage of traffic — the resolved_model_id in infra-ai-streaming comes from flagd evaluating the traffic split rule at request time. A flag flip that changes the canary percentage shows up in the audit log and in the inference event stream simultaneously.

ebpf-llm-tracer is the eBPF program that hooks TLS socket operations at the kernel level. It attaches uprobes to SSL_read and SSL_write in the OpenSSL or BoringSSL library loaded by the inference server process. When the inference server makes an HTTPS call to an LLM API — OpenAI, Anthropic, a self-hosted vLLM endpoint — the uprobe fires and captures the HTTP/2 frame headers. The capture includes the request ID, model name from the request, response token counts from the response headers, and latency from the socket timing. Zero SDK changes required. Zero application code modifications. The kernel sees every TLS handshake regardless of what the application code is doing.

lensai-integration is the unified quickstart: a Docker Compose file that wires all three services together, a synthetic load generator that fires inference events at the ingest endpoint, and scripts/smoke.sh — the integration test that ties a bow on the whole thing. The smoke test was the last piece built (Day 28) and it is the most important one. PR #1 in lensai-integration added the smoke test, the health check sequence, and the end-to-end verification that an injected event flows from HTTP POST to Kafka to ClickHouse in under five seconds on commodity hardware.

What surprised me

I expected the eBPF tracer to be the hard part. Writing a CO-RE (Compile Once — Run Everywhere) eBPF program that hooks TLS socket operations and correctly parses HTTP/2 frame boundaries is genuinely tricky: TLS data arrives in arbitrary-sized chunks that do not align with HTTP/2 frame boundaries, and the uprobe fires on each SSL_read call, not on each complete frame. The program needs to buffer across calls, detect frame boundaries, and avoid allocating in kernel context. That is real work.

But what was actually hardest was the schema. Specifically: the resolved_model_id field. The problem is that the eBPF tracer sees the model name from the HTTP/2 request frame. The flagd daemon knows what traffic split it applied. These two pieces of information live in different systems with different timing. The eBPF capture happens at the kernel level when the TLS write fires. The flagd evaluation happens at the application level before the write. Getting resolved_model_id to flow correctly — from flagd’s evaluation result through the application’s request header to the eBPF capture to the ClickHouse row — required three schema design iterations over two weeks.

What I didn’t expect was that the observability design problem was more interesting than the infrastructure plumbing problem. I’ve built Kafka consumers and ClickHouse schemas many times, in different contexts at Agoda and elsewhere. The schema design for an observability product — where the goal is to answer questions you haven’t thought of yet, not just store the data efficiently — is a different kind of problem. The columns in an inference event schema are a bet on what questions will matter in production.

What I’d redo

Three things, in order of how much time they would have saved.

First: start with the schema, not the pipeline. I built infra-ai-streaming before I had a stable schema. This felt efficient at the time — I was making progress on the Rust code while still thinking about the schema design. It was not efficient. I did two ClickHouse schema migrations and one Kafka topic rename because the schema changed under the pipeline. The correct sequence is: finalize the event schema, write a schema migration, write one test that inserts a valid event and queries it back, then build the pipeline that produces that event.

Second: ship the smoke test on Day 1 of the product, not Day 28. The smoke test is the end-to-end integration test. Building it last meant I had 27 days of building four components that I was never certain worked together correctly until Day 28. Building it first would have been harder — it would have required stubbing out services that didn’t exist yet — but it would have given me a failing test to run against every day, making integration failures visible immediately instead of on Day 28.

Third: write the landing page at the halfway point (Day 15), not at launch (Day 29). The process of explaining the product to a reader who knows nothing about it is the fastest way to find gaps in your own mental model of what you built. I discovered three things I’d assumed were true about LensAI while writing today’s landing page that required me to actually check the code. Two were correct. One required a documentation fix. That discovery cost five minutes today. If I’d made it on Day 15, the second half of the build would have been clearer.

Non-software analogy — expedition planning
Starting with the pipeline before the schema is like packing your gear for an expedition before you know the route. You end up with the right general equipment but wrong specifics: the tent stakes are too long for the terrain, the water filter is rated for the wrong micron range, the map is the wrong scale. Repacking mid-expedition is possible but disruptive. Planning the route first — the schema — lets you pack for the actual conditions. The gear — the pipeline — can then be specific rather than general.

The Show HN moment

Today’s code task is the landing page and the Show HN draft. The landing page is not marketing; it is proof. A Show HN post lives or dies on whether the reader can verify the claim independently, and the claim for LensAI is: “you can run this on your laptop in five minutes and see real eBPF-captured LLM traffic in a Grafana dashboard.” The only thing that makes that claim credible is the quickstart that delivers it.

The Show HN post is a specific format. It needs: what the project is in one sentence, why you built it (what problem it solves that existing tools don’t), the key design decisions and why you made them (these are what engineers actually want to read), honest limitations (what it doesn’t do), and a link to a runnable demo. The honest limitations are the engineering credibility. An open-source tool that lists its honest gaps is more trustworthy than one that claims to do everything. I am writing the Show HN draft today because the product is ready for independent verification.

Non-software analogy — product demonstration
The Show HN post is like a chef’s table at a restaurant. The regular dining room has servers who describe the dish. The chef’s table has the chef who cooks it in front of you and explains each decision. The value is not just the dish but the transparency: you can see exactly what went in, ask questions in real time, and form your own opinion about whether you’d want it in your kitchen. The quickstart is the chef’s table. The landing page is the menu. You need both but the chef’s table is the one that builds credibility.

From Agoda go-live criteria to OSS launch criteria

At Agoda, before the cross-tier query extension I built for WhiteFalcon went to production, it had to meet three criteria that the team treated as non-negotiable. I am paraphrasing from memory because I am not claiming ownership of the process — this was team discipline that was in place before I joined.

WhiteFalcon context — Agoda team’s system, my contribution boundary
WhiteFalcon is Agoda’s in-house time-series database, designed by the Agoda team. It handles 1.5T events per day through a Kafka pipeline, Rust consumers writing to Redis (hot tier), and Parquet/S3 cold tier. I was a Senior Engineer on the team for approximately five months. The go-live discipline described in this section was team practice, not something I designed. My contribution was the cross-tier query extension and new Grafana query types. The staging environment and integration test process were established practice.

The first criterion was: the integration test passes in the staging environment on production-like data. Not synthetic data, not hand-crafted test events, but a sample of the actual Kafka stream forwarded to staging. The point of production-like data is that it contains the edge cases that synthetic data misses — the exact distribution of time ranges, the exact compaction windows, the exact query patterns that production traffic generates. The cross-tier query extension’s histogram merge bug — where P99 was inflated by 1.3× during a compaction boundary window — would not have been found with synthetic data. It required the real compaction timing running in a real pipeline.

The second criterion was the clean-machine rule: the integration test starts from an empty Redis, empty S3 prefix, no compaction history. This enforces reproducibility. If a test passes from a pre-warmed state, you do not know whether it passed because the code is correct or because the pre-existing state happened to avoid the failure condition. A clean start means every failure is a system failure, not a state artifact. The test either works or it doesn’t, and there is no ambiguity about whether the test setup caused the result.

The third criterion was edge case coverage: the test must exercise the exact boundary condition most likely to fail. For the cross-tier query, that was queries crossing the hot/cold boundary during a compaction window. For LensAI, the equivalent is: the eBPF tracer captures events correctly when the BPF ring buffer is under pressure from a burst of traffic, the ingest pipeline processes events correctly when Kafka consumer lag spikes, and the smoke test verifies end-to-end flow under these conditions, not just under idle conditions.

The mapping is direct. Agoda’s three criteria — production-like data, clean state, edge case coverage — translate to LensAI’s launch criteria as: smoke.sh exits 0 on a clean Docker state, with a synthetic load burst that exercises the ring buffer under pressure. The discipline is the same. The tooling is different — a Bash script and Docker Compose instead of a Scala integration test suite and a Kafka staging cluster. The principle is identical: before you say the thing works, prove it works under conditions that resemble the conditions where it will fail.

What makes the Show HN and the OpenTelemetry Collector PR distribution for this standard is the same logic. The HN post is a claim. The claim is backed by a quickstart anyone can run. The OTel PR adds a receiver that lets existing OTel Collector pipelines export to LensAI without replacing their current setup. Both are channels through which independent engineers can run the integration test themselves — on their own hardware, with their own traffic, with their own edge cases. The Agoda go-live checklist was internal verification. The Show HN launch is external verification at scale. What passes internal verification does not always pass external. The quickstart is the only way to find out.
