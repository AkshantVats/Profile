Day 52 — Parallel Runs — Respect the Rate Limit

Firing every request at once isn't a stress test of the system you're calling — it's a stress test of your own restraint, and the downstream system loses either way. Delivery Hero's OSRM routing cluster taught that lesson at 5k route updates a second; today's code applies the same fixed-worker-pool discipline to running benchmark repetitions in parallel.

A restaurant with forty tables and eight line cooks does not seat every waiting party at once because the dining room happens to have the floor space. It seats what the kitchen can actually cook for, and everyone else waits in a line that moves at a predictable pace.

The moment a host stops managing that line — sits fifty parties at once because the room technically fits them — the kitchen doesn't serve fifty meals faster. It serves zero meals on time, to anyone.

I learned the distributed-systems version of that lesson at Delivery Hero, on the routing stack behind rider tracking. Today's code puts the same discipline into agent-benchmark-runner: how many repetitions of a benchmark task should ever be in flight at once.

The Dinner Rush the Routing Cluster Couldn't See

Route Consumers on EKS read lifecycle events off Order SQS and call an OSRM cluster to map-match each event to a route. OSRM has a real, physical capacity per instance — a fixed number of route computations it can serve per second before requests start queueing inside it instead of being served. At dinner-rush peak, Order SQS doesn't arrive smoothly; it arrives in bursts, order after order landing within the same few seconds as everyone in a city orders dinner at once.

The naive version of a consumer just processes whatever is in the queue as fast as it can pull messages — one goroutine per event, or a pod count that scales on queue depth alone. That treats "more messages waiting" as license to call OSRM harder. But OSRM's capacity didn't scale just because the queue got deeper.

Unbounded concurrency at the caller doesn't get more route computations out of OSRM — it gets queueing inside OSRM, then request timeouts, then retries stacking on top of a burst that was already too large. That is precisely how a caller turns a downstream dependency's ordinary capacity limit into its own outage.

My role — Delivery Hero, Sr. Software Engineer, Jun 2022–Jul 2023
I scaled the logistics platform to 1M+ daily orders on AWS EKS at 10k+ concurrent requests with zero downtime, and built the rider-tracking path processing 5k+ real-time route updates a second against OSRM. Bounding Route Consumer concurrency to what OSRM could actually sustain — instead of letting it scale unchecked with queue depth — was part of that work, alongside the async SQS + Kinesis decoupling of order processing from notifications that eliminated cascading failures under peak load.

So what: the fix wasn't more OSRM replicas until the symptom went away — replicas cost money and don't fix a caller that doesn't know its own concurrency. The fix was bounding concurrency at the caller, so peak traffic queues predictably at the edge instead of degrading unpredictably downstream.

A Benchmark That DDoSes Its Own Agent

agent-benchmark-runner's orchestrator has the identical shape of problem, at a much smaller scale. Day 52 runs a benchmark task N times against one agent, because a single run is an anecdote, not a benchmark. An agent run makes real outbound calls — to a model provider, to whatever tools the task allows.

Firing all N repetitions at once doesn't test how the agent behaves; it tests what happens when a model provider receives N simultaneous requests from one caller, which is a rate-limit test wearing a benchmark's clothes.

That distinction matters because a benchmark's entire job is to isolate one variable — the agent under test — and hold everything else constant. A batch that trips its own rate limits doesn't fail because the agent is bad; it fails because the harness ran the dinner rush against itself. The result is unusable either way: a false pass if the provider silently throttles and returns cached-looking responses, a false failure if it returns 429s that get graded as agent errors.

So what: an unbounded-fan-out benchmark measures the harness's aggressiveness, not the agent's competence — and those two failure signatures are easy to conflate if nothing in the code forces the concurrency budget to be a decision instead of an accident.

Three Ways to Bound It, and Why Two Were Rejected

Fixing the Route Consumer problem and fixing the orchestrator problem both came down to the same three-way choice:

OptionDescriptionVerdict
Unbounded fan-outOne goroutine per event or repetition, no capRejected — fastest wall-clock, but the caller becomes the rate-limit violator, exactly the failure both systems exist to avoid causing
Serial, one at a timeProcess the queue or run the batch strictly sequentiallyRejected — safe, but a 30-run benchmark batch (or a peak-hour backlog) takes unnecessarily long once the downstream capacity is actually known
Fixed-size worker poolA named concurrency budget, enforced by a bounded semaphoreChosen — bounded and predictable; the budget is a parameter sized from known downstream capacity, not an accident of the runtime's default fan-out

The textbook "better" answer — an adaptive, AIMD-style controller that raises and lowers concurrency based on observed latency or error rate — was left out of both. It's a real technique, but it adds a feedback loop's own failure surface (a controller that itself needs tuning and can oscillate) to solve a problem a fixed pool, sized from capacity you already know, solves directly.

So what: the right amount of engineering here is the amount that names the concurrency budget explicitly — not the amount that makes the budget self-tuning, which is a different, harder problem this one doesn't require solving.

What Stayed With Me

The instinct to treat "the queue is deep" or "there are thirty repetitions to run" as permission to run everything at once is a natural one — it looks like using available resources efficiently. The Route Consumer incident-that-wasn't taught me the opposite: efficiency at the caller is worthless if it's purchased by pushing a downstream system past what it can sustain. A concurrency cap isn't a performance compromise; it's the caller admitting, honestly, what the rest of the system can actually take.

That's the same admission orchestrator.Config.MaxParallel makes on a much smaller stage — a number in a config struct instead of a production incident, because the lesson got learned once already.
