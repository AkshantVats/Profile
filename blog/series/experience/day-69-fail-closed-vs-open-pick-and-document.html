Day 69 — Fail Closed vs Open — Pick and Document

Fail-open and fail-closed aren't a right answer and a wrong one — they're two different bets about what an outage should cost, and the bet only holds if someone writes down which one was made and why. WhiteFalcon's hot-tier retention window at Agoda posed the same question I had to answer for cost-budget-enforcer today.

Every module cost-budget-enforcer has shipped so far has had an unstated policy baked into it: when Redis goes away, the enforcement path forwards the request instead of rejecting it. That was never voted on. It fell out of an if err != nil branch on Day 66, and it stayed that shape through Days 67 and 68 because nobody had a reason to look at it twice — until Day 69's plan item asked, directly, which side of that choice a tenant should actually be on.

The honest answer turned out to be: it depends whose budget it is, and that dependency is exactly the thing worth writing down instead of leaving implicit.

A Boundary I Watched, But Never Owned

I spent about five months at Agoda as a Senior Engineer on WhiteFalcon, the team's in-house time-series database. WhiteFalcon's hot tier is Redis — the last three to seven days of data, bucketed in time windows, queried at per-hour granularity because that's where almost all of the query load lands. Everything older rolls off to Ceph and S3 as compacted Parquet.

That retention boundary has a quiet failure mode built into its shape, whether or not Redis ever actually goes down: a query that spans the hot window has to get its answer from somewhere, and if the hot tier can't serve it, the system has exactly two honest options — answer from the cold tier and be explicit that the answer is coarser than what a fresh window normally returns, or refuse the part of the query that only Redis could have served precisely. I didn't design WhiteFalcon's ingest-to-storage lineage — the Agoda team built that before I joined — and I never watched Redis itself go down while I was extending the query engine on top of it.

What I did watch, from inside the cross-tier quantile-merge work I shipped, was how much the cross-tier merge logic already depended on both tiers agreeing to answer in the same shape. A tier that silently degrades to a different shape breaks that agreement quietly, which is worse than breaking it loudly.

My contribution — Agoda, Senior Engineer, WhiteFalcon TSDB, ~5 months
I extended WhiteFalcon's query engine to merge histogram bucket counts across the hot Redis tier and the colder Ceph/S3 tiers into one correct quantile, and added a new cardinality dimension the query layer could filter on — work that assumed both tiers would answer in a comparable shape, an assumption a silent degrade-vs-refuse choice at the Redis boundary would have put pressure on, even though I never had to resolve that specific choice myself.

So what: a cross-tier system's correctness depends on every tier failing in a way its neighbors can reason about — and "reason about" requires the failure mode to be a documented choice, not whatever an error branch happened to do by default.

Two Ways to Get the Same Outage Wrong

cost-budget-enforcer's enforcement path — pkg/middleware.Wrap and pkg/gateway.Handle — had exactly one behavior when the budget Store went unreachable: forward the request unmetered. That's fail-open, and Day 66's original reasoning for it was sound on its own terms — a missed rate-limit check is bounded and self-correcting, the same bet ingestion/src/rate_limit/token_bucket.rs already makes for fairness.

But a budget check isn't a fairness check. Every request that slips through fail-open during an outage still calls a real model at a real price, and if the outage runs long, that's not a bounded blip — it's an unbounded, undiscovered bill.

The other extreme is just as wrong applied everywhere: fail-closed by default would turn a Redis blip into a customer-visible 503 for every tenant, including the ones who'd rather eat a few minutes of unmetered spend than lose availability entirely. Neither policy is the correct one in general. Each is correct for a specific tenant's risk tolerance, which is the detail a single repo-wide default erases.

PolicyWhat it protectsWhat it costsRight tenant for it
Fail open (existing default)Request availabilityUnbounded spend for the outage's durationInternal tools, tenants who'd rather absorb a rare cost spike than any downtime
Fail closed (Day 69, opt-in)A hard ceiling on spendA visible 503 on every request during the outageTenant-facing products with an SLA, or a fixed-price internal budget that can't flex

So what: when two policies are each correct for different people, the bug isn't picking the wrong one — it's picking one at all and applying it to everyone.

What Changed: a Branch, Not a Rewrite

The fix is config.TenantConfig.FailClosed — one boolean, defaulting to false so every existing tenant config keeps today's behavior with no migration. pkg/middleware.Wrap and pkg/gateway.Handle already had the if err != nil branch that catches a Redis failure; Day 69 just gives that branch a second path instead of one hardcoded outcome.

enforcer.Check itself didn't change at all. It has no opinion about policy — it reports a Store error and lets its two callers decide what to do with it, the same separation of concerns DESIGN.md already drew for the Admin API's fail-closed audit-publish choice back on Day 67. Policy belongs at the edge that has to act on it, not in the package that only discovers the failure.

The Part That Surprised Me

Before writing the benchmark, I assumed fail-closed would cost more per request — reject-and-retry sounded like the "careful but slow" option next to forward-and-move-on. Measured against a loopback miniredis instance, it's the opposite.

~250μsCost of a successful budget check (Pass or Degrade), dominated by one Redis EVAL round trip
~6μsCost of a fail-closed 503 — no Lua script runs, just a fixed response body
~40×How much cheaper rejecting is than succeeding, on this measurement

Fail-closed isn't the expensive option — checking the budget successfully is the expensive part, and fail-closed skips it entirely. What fail-closed actually costs is what the table above already named: availability, for the tenants who opt into it, during the specific window an outage is happening. The benchmark's job was to confirm that cost wasn't hiding a second, unrelated latency tax, and it isn't.

An unbounded bill isn't a rounding error the next window corrects — it's an invoice nobody signed off on.

Chaos Tests, Not Just a Config Flag

A policy that only exists in a config schema and a benchmark isn't proven — it's asserted. pkg/middleware/middleware_test.go and pkg/gateway/gateway_test.go each carry three chaos tests shaped after CHAOS.md's existing Redis-outage scenario: a fail-open tenant whose requests still go through with Redis down, a fail-closed tenant whose requests get a clean 503, and — for the middleware path — an automatic return to normal enforcement once Redis comes back, with no restart and no state stuck open. All three run against a real miniredis instance the test closes mid-run, not a mocked error return, so the assertion is about the actual failure path a production outage would exercise.

So what: "we support fail-closed" is a config field; "fail-closed actually rejects the request, doesn't touch the model, and the tenant's neighbor on fail-open is unaffected" is what the chaos tests exist to prove, and only one of those two claims survives contact with a real outage.

Why This Still Isn't a Global Flag

It would have been simpler to add one repo-wide constant instead of a per-tenant field. It would also have been wrong, for the same reason a single retention policy across WhiteFalcon's hot and cold tiers would have been wrong: different consumers of the same infrastructure have genuinely different tolerances for the same failure, and collapsing that difference into one default doesn't remove the tradeoff — it just hides which side of it every tenant is silently standing on.

Putting FailClosed on config.TenantConfig, next to the same struct that already carries FallbackModel and the three thresholds, means the choice gets made once, explicitly, per tenant — patchable through the same Admin API Day 67 already shipped, not buried in a code path someone has to read Go to discover.

What I'd Still Want to Know

This benchmark ran against loopback Redis with no network hop — a live, cross-AZ Redis would add real round-trip latency to both the successful-check number and the fail-closed number, and could plausibly narrow the 40x gap without closing it, since a failed dial attempt still resolves faster than a completed Lua script. I don't have that number yet, and I'd rather say so than imply this measurement generalizes past its own sandbox.

So what: a benchmark that's honest about what it didn't measure is more useful than one that quietly implies it measured everything — the next person sizing this tradeoff for a real deployment needs to know which number they can trust and which one they still have to go collect themselves.
