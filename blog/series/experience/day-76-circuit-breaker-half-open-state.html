Day 76 — Supplier API Circuit Breakers — Half-Open State in Production

The trip condition shipped years ago. What we tested on purpose, for the first time, ahead of Black Friday wasn't whether the breaker could open — it was whether it could actually come back.

I've written before about the circuit breaker guarding Wayfair's supplier pricing path — a mechanism that stops sending requests to a downstream service once it starts failing, the same way a household breaker cuts power before a fault does real damage. That post covers the trip condition, the 503 it returns, why it exists alongside the token bucket rather than instead of it. It never covers the other half of a circuit breaker's job: what happens after it opens.

Today's ticket, an admin API that changes how prompt-fingerprinter decides two prompts are "the same," is what finally made me write about it.

The Trip Condition, Briefly, Because It's Already Written Up

Supplier pricing submissions run through gst-acc-promotions into PAS, which routes into SPCS — the service that actually persists a price change. The breaker in front of that path trips on five consecutive timeouts, or a 50% error rate in a 30-second window, and once open it returns 503 to every request immediately, without touching SPCS at all. That's the mechanism I built and shipped, and it's covered in full elsewhere — I'm not re-deriving it here.

Mine — Wayfair, supplier pricing circuit breaker and the Black Friday half-open drill
The breaker itself, the trip thresholds, and the manual half-open verification process this post describes are work I owned end to end on the supplier pricing submission path — the same scope as the token-bucket rate limiter and rollout I've written about elsewhere in this series.

So what: a breaker that trips correctly under load has proven exactly one thing — that it can tell "broken" from "working." It hasn't proven it can tell the reverse.

The Half-Open Transition Nobody Had Actually Watched

Standard circuit breaker design has a third state between open and closed: half-open. After a cooldown, the breaker lets exactly one probe request through. If it succeeds, the breaker closes and normal traffic resumes.

If it fails, the breaker reopens and waits again. It's a small piece of logic, and it's correct by construction — either the probe succeeds or it doesn't.

What that correctness doesn't cover is everything happening around the probe at the exact moment it runs. SPCS's real outages, the ones that actually tripped our breaker in production, mostly lasted seconds to low minutes — short enough that the half-open transition ran and resolved without anyone watching it closely, because the incident was already over by the time anyone looked. The path existed, it presumably worked, and nobody had a specific memory of confirming that under real traffic rather than assuming it from the code.

So what: a path that only ever runs during the tail end of an incident nobody was watching is, in practice, an untested path — regardless of how simple its logic is on paper.

The Drill: Forcing Open on Purpose, Before Black Friday

Ahead of Black Friday, we forced the breaker open deliberately — a controlled downstream fault injected against a staging path shaped like the real one, not a real SPCS outage — and watched the half-open probe and recovery run under realistic pricing-submission traffic. The goal wasn't to test the state machine's logic. It was to test everything the logic assumes is well-behaved around it.

Three things got checked that the breaker's own code has no way to check about itself: whether a flood of client retries, all arriving the instant the probe succeeds, could pile onto the newly-half-open breaker and trip it straight back open before it stabilized; whether the monitoring dashboard reflected the open-to-half-open-to-closed sequence quickly enough for someone to notice if recovery stalled; and whether the token bucket's own fail-open Redis policy, from the rate limiter I've written about separately, interacted badly with a breaker that's simultaneously trying to recover.

So what: the drill wasn't testing whether the breaker's logic was correct — it already was, by construction. It was testing whether the system around that logic behaved the way the logic assumes.

Today's Code: The Same Pattern, a Different Mechanism

prompt-fingerprinter's new admin endpoint, PUT /tenants/{id}/fingerprint-rules, lets a tenant configure whether prompts get lowercased or stripped of punctuation before they're hashed. The moment that call lands, what counts as "the same prompt" for that tenant changes — a normalization rule change is a config deploy, live, on a path that decides whether a request costs a Redis GET or an embedding-model round trip.

The logic itself is correct by construction the same way the breaker's half-open state is: the code either applies the configured rule or it doesn't, and the unit tests for Rules.Apply prove it does. What actually matters — the thing worth deliberately exercising before trusting it — is whether the rule change produces the specific outcome it's supposed to under real traffic shape: two near-duplicate prompts that used to miss the cache now hitting it. That's exactly what today's integration test does: configure the rule, send two prompts differing only in case and punctuation, and confirm the second one resolves from the cache instead of paying for a second embedding call.

A mechanism being provably correct and a mechanism being exercised are different claims. The first one comes from the code. The second one only comes from deliberately running the path that matters most before the day it matters most.

So what: whether it's a circuit breaker's recovery path or a cache's normalization rule, "the logic is correct" and "I've watched this specific scenario play out" are different bars — and the second one is the one worth clearing before a deploy that changes production behavior, not after.

What the Drill Actually Bought

Black Friday's batch pricing runs came and went without the breaker tripping at all — SPCS held under peak load, so the drill's specific scenario (recovery under real traffic) never got a live rerun on the day itself. That's not a null result. The value of the drill wasn't insurance against that specific Black Friday; it was insurance against every future incident where the breaker does trip during a peak window, because now the half-open path has a known-good run on record instead of an assumption.

So what: the payoff of exercising a rarely-run path isn't always visible on the day you exercised it for — it's visible the next time that path actually has to run for real, with one less unknown in it.
