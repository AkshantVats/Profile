Day 99 — Using GPT to Grade GPT — BrowserStack Skepticism

We demanded a human-labeled gold set before trusting automation — because a harness that confidently reports the wrong verdict looks identical to one that's actually right, right up until someone checks.

At BrowserStack I worked on device instrumentation — the layer that reverse-engineers native iOS and Android OS APIs so a test running against a remote physical device can trigger things a normal app can't: FaceID and TouchID prompts, answered automatically through Camera Image Injection, a rig that feeds a synthetic face or fingerprint straight into a phone's camera and biometric sensor path instead of a real human touching real hardware. Getting the injection to fire correctly was only half the problem. Something still had to decide whether the device's response to that injected biometric counted as a pass.

Scope note — BrowserStack, Device Instrumentation
My resume documents the role directly: "Reverse-engineered APKs/IPAs to hook into native iOS/Android OS APIs, enabling fully automated FaceID/TouchID testing on remote physical devices via Camera Image Injection and biometrics instrumentation" (BrowserStack, May–Dec 2021, Sr. Software Engineer). What follows is the general shape of a problem that kind of automation runs into as a matter of course — trusting an automated pass/fail verdict without checking it against a human's independent read of the same evidence — not a specific documented incident or a named fix with before/after numbers my resume doesn't itemize.

A Green Checkmark Answers the Wrong Question

A liveness check on the instrumentation bridge answers one question: is the process that translates "trigger FaceID" into an actual Camera Image Injection signal still running. That's a real question worth checking, but it's not the question a test result actually needs answered. Once the bridge is confirmed alive and the injected biometric fires, a harder question remains: did the device's response to that injected face or fingerprint match what a real user's successful — or failed — authentication would have produced.

An automated harness can misread that outcome while reporting total confidence. A false accept can get logged as a false reject. A genuinely correct authentication can get flagged as broken because a screen transition landed one frame later than the parser expected.

None of that shows up as a crash or an error anyone gets paged for — the harness just confidently reports the wrong verdict, at whatever scale the device farm happens to be running that day.

Why We Needed a Human-Labeled Gold Set

The fix for a verdict that can be confidently wrong isn't a smarter harness. It's a small, deliberately hand-checked sample — a human watching the actual injected-biometric attempt and its on-screen result, next to what the harness reported, and confirming whether the two agree.

Not a one-time calibration exercise run once before shipping. A recurring check, because a harness's read of "pass" can quietly drift: an OS update changes how a biometric prompt's screen transition renders, and a parsing assumption baked in months earlier stops matching reality without ever throwing an error.

Skip that recurring check and the automation earns trust once, on day one, and then keeps spending that same trust indefinitely — including on days after the thing underneath it has already changed.

The sample doesn't have to be large to do its job. It has to be recurring, and it has to compare the harness's stored verdict against a human's independent read of the same underlying evidence — not against the harness's own explanation of itself.

An automated verdict earns trust once. Whether it still deserves that trust six months later is a question only a recurring human spot-check can actually answer.

The Same Discipline, a Different Automated Verdict

Today's llm-judge-eval async judge worker (Phase 2A) automates a structurally identical decision one arc later: a cheap model reads a response and reports a verdict — a judge_score — meant to feed DriftWatch's drift detection unattended, the same way BrowserStack's harness read a device screen and reported pass or fail unattended.

The worker doesn't just emit judge_score. It stores criteria_json — the raw per-criterion breakdown behind that score — and a rationale and confidence right alongside it, specifically so a human reviewer can pull a sample of graded requests later and check the judge's reasoning against their own independent read of the same prompt and response, without re-running anything. That's the gold-set discipline translated directly into a storage decision: an automated grade that can't be spot-checked against a human's independent read is a number nobody should fully trust, whether the automation is a mobile test harness reading a screen in 2021 or an LLM judge reading a chat transcript today.

So what: an automation that reports its own verdict confidently and one that reports its verdict correctly are two different claims, and checking that the first one showed up — a green checkmark, a stored judge_score — never proves the second one is true. The fix isn't a smarter harness or a smarter judge model. It's keeping a human-labeled sample permanently in the loop, and storing enough of the automation's own reasoning that running that check is actually possible.
