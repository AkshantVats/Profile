Day 106 — Segmented SLOs — Delivery Hero Peak Zones

A platform-wide SLO is a weighted average across every region and every hour — and a weighted average can sit right inside its target while individual segments sit far outside theirs, canceling out.

6 min read

Every engineer who has ever owned a platform-wide SLO has watched a green dashboard sit calmly on target while some corner of the fleet was quietly having a bad day. I want to be upfront about which parts of this post are grounded in Delivery Hero's documented architecture and which parts are an illustrative framing device I'm using to make a general pattern vivid, because they aren't the same thing.

Scope note — Delivery Hero, Global Logistics Platform
I was a Senior Software Engineer on Delivery Hero's Global Logistics Platform in Berlin from June 2022 to July 2023. My resume documents scaling that platform to 1M+ daily orders on AWS EKS (10k+ concurrent requests, zero downtime) and building end-to-end rider tracking on OSRM processing 5k+ real-time route updates per second, with a separate async SQS + Kinesis pipeline decoupling order processing from notifications to guarantee sub-second delivery status updates. "Bangkok lunch vs. rural night" is not a logged incident or a named dashboard from that record — it's this post's illustrative framing for a pattern the platform's own architecture makes structurally possible, not a claimed, measured degradation event.

A Platform-Wide Number Is a Weighted Average

A single route-match latency P99, or a single SLA-compliance percentage, computed across every region and every hour of a logistics platform is not one measurement — it's a weighted average of thousands of very different local conditions. A dense city at its lunch peak and a low-volume rural zone at 2am are different traffic regimes entirely, and both of them feed into the exact same blended number. That number can sit comfortably inside its target even while one of those regimes is badly outside its own, because the other regime's slack is doing the covering.

So what: a platform-wide SLO that only ever reports one number per metric can be technically "healthy" while telling you nothing true about any specific place or time it's supposed to represent.

The Illustrative Pairing, Stated Plainly

"Bangkok lunch ≠ rural night" is the pairing I'm using to make this vivid, and I want to name it as exactly that — an illustrative device, not a specific dated incident I can point to on the record. A platform running at Delivery Hero's documented "1M+ daily orders" system-wide has enormous headroom for precisely this kind of blending, whether or not any single blended failure was ever logged and filed as a ticket.

The pattern doesn't need a named incident to be real, because it's a property of arithmetic, not of any one outage: average two numbers on opposite sides of a target and the average can land exactly on target. So what: the honest version of this post's claim is structural — the architecture makes the blending possible at this scale — not anecdotal, and I'd rather say that plainly than borrow the drama of a postmortem that never happened.

Where the Aggregation Actually Sits

The documented architecture gives this pattern a real anchor. Order Service sits at the center of the platform — customer and rider ingress, persistence, and the one documented analytics aggregation point, an export to GBQ — while Route Service and Route Consumers on EKS handle the OSRM-backed routing work downstream of it. Any single global rollup computed off that GBQ export, or off Route Service's own metrics, is exactly the shape of number this post is critiquing: one figure standing in for every region, every hour, and every one of the 1M+ daily orders moving through it.

Why I'm not naming a specific SLO tool or dashboard
Neither context doc I have for this system documents a named alerting product, a specific dashboard, or a masked-incident postmortem for this pattern — the real anchor is the architecture itself, not a tool built on top of it. What I can say honestly is the shape of the exposure: a single global rollup off Order Service's GBQ export, at this platform's documented scale, is structurally capable of hiding exactly the kind of segment-level failure this post describes.

So what: you don't need a specific outage on the record to know a blended metric can hide a real problem — you only need to know where the blending happens, and this platform's own architecture tells you that plainly.

The Same Shape in Today's Code

Today's drift-detector work (Phase 2A) is the same fix applied to a different blended metric. Instead of one CUSUM chart watching a single global z-score stream built from every judge score at once, the fleet trains one independent CUSUM per (task_type, model_id) segment — the top 10 by volume — so a shift confined to one segment can't hide behind nine other segments averaging it out. A Grafana heatmap then makes every tracked segment's status visible side by side instead of collapsing all ten into one number a reader has to trust blindly.

The bridge here is direct, not metaphorical: segmenting a global aggregate into per-group signals is the same design move whether the aggregate is a route-match SLO blended across cities or a judge-quality metric blended across task types. Both fixes trade one comforting number for several honest ones.

1M+Daily orders, documented scale
5k+Route updates/sec via OSRM
10k+Concurrent requests on EKS
10Segments tracked, today's fleet

A weighted average can sit right on target while every one of its parts is wrong in a different direction. The fix was never a smarter blend — it was refusing to blend in the first place.

So what: a single global number and a set of segment-level numbers can be computed from the exact same underlying data, and only one of those two choices can actually tell you which region, which hour, or which task type needs attention right now. Delivery Hero's platform-wide SLOs and DriftWatch's global CUSUM are two names for the same exposure — a blended metric is comforting precisely because it's hiding the parts that would make you uncomfortable. Segmenting it is the only way to find out which parts those are before a customer, or a rider, tells you first.
