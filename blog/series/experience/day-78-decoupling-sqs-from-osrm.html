Day 78 — Delivery Hero Async Pipelines — Why We Decoupled SQS from OSRM

5k route updates a second only survived because one slow notification call could no longer sit in the same path as a route recompute — and the fix needed a rollback plan I actually had to use once.

7 min read

At Delivery Hero, Route Service and Route Consumers both read from Order SQS, and both eventually call into OSRM (the routing engine that map-matches a rider's position and produces a polyline) to recompute a rider's route. That part of the topology was fine. The part that wasn't fine is that in an earlier version of the stack, the same request path that triggered a route recompute also triggered the rider notification — "your delivery is on the way," push and SMS both — as one synchronous call chain hanging off Order Service.

A route recompute is fast. A push notification provider having a slow afternoon is not something route computation should ever have to wait on. But it did, because nothing in the code enforced otherwise — the notification call was just the next line after the route update, in the same request.

Mine — Delivery Hero, async pipeline design and rollout for the routing plane
Order Service, Order SQS, and the OSRM cluster itself were existing platform infrastructure I inherited. My contribution was designing and rolling out the SQS-based decoupling between order/routing events and notification delivery, and the dual-write cutover strategy that got the routing plane to 1M+ daily orders and 5k+ route updates/sec on EKS without a rollback that customers noticed.

Before: One Call Chain, Two Unrelated Jobs

Picture the old path: Order Service receives a RIDER PICKED UP event, calls Route Service to recompute the polyline against OSRM, and then — still inside the same handler — calls the notification provider. If OSRM was healthy but the notification provider was throttling us, the handler blocked on the notification call anyway. Every rider whose event landed behind that one in the queue waited for a notification retry that had nothing to do with their own route.

So what: the bug wasn't OSRM being slow — OSRM was fine — it was that two jobs with no real dependency on each other shared one failure domain, so the slower of the two set the ceiling for both.

After: SQS as the Boundary, Not Just a Queue

The fix split the handler into two consumers reading from Order SQS independently: one that only calls OSRM and writes the route object, and one that only sends the notification. Neither can block the other, because neither is inside the other's call stack anymore — they're two consumer groups pulling the same lifecycle events at their own pace.

Order SQS was already the lifecycle event bus — PICKED UP, PLACED, RIDER ENQUE, RIDER PICKED UP all flowed through it before this change. What changed is that notification delivery stopped being a side effect buried inside the routing handler and became its own consumer of the exact same stream, with its own retry policy and its own backlog if the provider degraded.

So what: the queue didn't need to get faster or bigger — it needed a second, independent reader, because the actual bug was architectural coupling, not throughput.

The Rollback Plan I Needed Once

We didn't cut over all traffic at once. The new notification consumer ran in shadow mode first — reading the stream, sending real notifications, but with the old synchronous path still live and authoritative — so we could compare delivery latency and failure rate before removing the old code path. Once shadow metrics matched, we flipped a percentage of riders to the new path behind a flag, watched for a day, then ramped to 100%.

The rollback plan was simple on purpose: flip the flag back to the old synchronous path, leave the new consumer running but ignored. We used it exactly once, early in the rollout, when the new notification consumer's retry backoff was too aggressive and started tripping the provider's own rate limit — a self-inflicted throttling loop that the old path's more conservative retry hadn't triggered. Flipping back cost us a few hours of the old coupling returning, not a customer-visible outage, because the flag was a config change, not a redeploy.

A rollback plan you never test is a rollback plan you don't actually have. We tested ours by needing it.

So what: shadow mode caught the two systems' latency profiles diverging before customers could notice, and the flag-based rollback turned one bad retry-tuning decision into an afternoon instead of an incident review.

The number that mattered most wasn't route throughput — OSRM could already keep up before this change. It was that delivery status updates stayed sub-second even during a notification-provider degradation, because a slow provider now only backed up the notification consumer's own lag metric, not the routing plane's.

So what: the metric that proves a decoupling worked isn't "the fast path got faster" — it's "the fast path stopped caring when the slow path had a bad day."

Today's Code: The Same Shape, a Different Queue

model-quality-scorer, which I implemented today, draws the identical boundary. A sampled request has already been served — cache lookup, budget check, and the model call all completed — before it ever reaches the judge-requests Kafka topic. Grading that response against a rubric is a full model call in its own right, exactly the kind of variable-latency work that has no business sitting in front of a response that already went out.

Same failure isolation pattern, different provider on the other end: instead of a notification API that might throttle, it's a judge model that might time out. Instead of a flag-gated rollback to a synchronous path, it's a circuit breaker that stops pulling new samples once the judge's failure rate crosses 10% over a trailing window — the judge going quiet costs nothing user-facing, the same way a quiet notification provider no longer touched a rider's route.

So what: "does this belong on the hot path" turned out to be a question worth asking again eight years and one industry later — the answer is still no whenever the work downstream of a response doesn't change what that response already was.
