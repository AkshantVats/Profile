We Killed Redpanda on Purpose — Chaos as Commit Message

The broker recovered. The dashboards went green. The queries were wrong for 47 minutes.

AS
Akshant Sharma
May 2026
14 min read
Experience Series · 9 of N

The broker came back. Every health check passed. The Grafana panel for ingestion throughput climbed back to its normal plateau — 1.5 trillion events per day worth of slope, climbing in the same shape it always does after a restart. The on-call engineer closed the incident channel. And for the next forty-seven minutes, every cross-tier query that touched the recovery window returned wrong results.

Not missing results. Not errors. Wrong results — numbers that looked plausible, landed in dashboards, and would have informed decisions if anyone had been looking at that specific time range before the data caught up. The broker was healthy. The pipeline was flowing. The gap between "broker recovered" and "data is correct" was invisible to every monitoring signal we had.

That gap is why we started killing brokers on purpose.

The Incident: Recovery Without Correctness

WhiteFalcon ingested 1.5 trillion events per day across hundreds of Kafka partitions. The architecture was layered: Rust ingestion into Kafka, a hot tier backed by Redis for recent queries, a cold tier on S3 with Parquet files for historical ranges, and a query engine that merged across both tiers. I covered the architecture in Experience 1 and the cross-tier merge problem in Experience 2. This post is about what happened in the seam between them.

A broker in the Kafka cluster went down during a routine maintenance window. Not a crash — a planned restart that took longer than expected because of log segment recovery. The broker was offline for eleven minutes. Kafka's replication factor meant no messages were lost; ISR (in-sync replica) leadership shifted to surviving brokers, and producers continued writing. Standard Kafka resilience, working as designed.

When the broker came back, partition leadership rebalanced. Consumers reconnected. The throughput graph recovered. The on-call engineer, seeing green dashboards and no consumer lag, marked the incident resolved.

The Recovery Gap

The problem was not message loss. Kafka handled that. The problem was query correctness during rebalance convergence.

When partition leadership shifted, consumers in WhiteFalcon's ingestion layer had to re-seek to new leaders and resume consumption. During the eleven-minute window, events that arrived on the rebalanced partitions were buffered on surviving brokers but not yet flushed into the hot-tier Redis cache by the WhiteFalcon consumer fleet. The hot tier had a gap: a time range where events existed in Kafka but hadn't been materialized into the query-visible cache.

The query engine didn't know about this gap. It queried the hot tier for recent data, got back whatever was there, and served it. For a time range overlapping the rebalance window, the query silently returned a partial dataset. Percentile calculations on partial data are not "slightly off" — they are structurally wrong, because the missing events change the distribution shape, not just the count. A P99 computed over 60% of the actual events is not a P99. It is a number that happens to have the label "P99."

The cold tier was not involved — these were recent events, well within the hot-tier TTL. No cross-tier merge, no Parquet compaction lag. Just the hot-tier consumer fleet falling behind during rebalance and the query engine not knowing it was reading from a gap.

The broker was healthy. The pipeline was flowing. The data was wrong. Every signal we monitored said "recovered." None of them measured correctness.

Forty-seven minutes after the broker returned, the consumer fleet had fully caught up — the rebalanced partitions' events were flushed to Redis, and queries over the recovery window started returning complete data. Nobody noticed the forty-seven-minute gap because no query happened to inspect that exact time range while it was incomplete. We found it three days later during a routine data quality audit that compared hot-tier query results against a cold-tier backfill.

Team context
WhiteFalcon, Agoda's in-house TSDB — Rust + Scala on Kafka, Redis hot tier, S3/Parquet cold tier. The ingestion pipeline, query engine, and storage tiers were maintained by the core infrastructure team. Kafka cluster operations (broker restarts, ISR monitoring) were shared between infra and the platform SRE team.
My contribution
I worked on the query engine — specifically the cross-tier merge path and the RoaringBitmap inverted index. The chaos testing initiative came from the gap analysis after this incident. I wrote the broker-kill test harness and the consumer-lag-to-query-correctness correlation check, and proposed the hot-tier freshness watermark that eventually closed the gap.

Root Cause: We Monitored Availability, Not Freshness

The root cause was not Kafka. Kafka did its job. The root cause was that every monitoring signal we had — consumer lag, throughput, error rate, broker health — measured pipeline availability, not data freshness at the query layer.

Consumer lag shows how far behind consumers are from the latest offset. After rebalance, lag spikes briefly and then drops to near zero as consumers catch up. But "near zero lag" means "consumers are now keeping pace with new events." It does not mean "all events from the rebalance window have been flushed to the hot tier." Those are different statements. Lag measures the tail of the stream. It does not measure the backfill of the gap.

What we were missing was a freshness watermark: a per-partition timestamp in the hot tier that says "this cache contains all events up to time T." If the watermark for a partition is behind the query window, the query engine knows the result is partial and can either block, return with a staleness warning, or fall back to a slower path that reads from Kafka directly.

Chaos as Evidence

The incident taught us something uncomfortable: we could not quantify the recovery gap without reproducing it. The original incident was discovered by accident — a data quality audit three days later. Proposing a freshness watermark required proving the gap existed reliably, not just anecdotally. The only way to prove it was to kill brokers on purpose and measure what happened to query correctness during recovery.

We built a test harness. The shape was simple: kill a broker, run queries against time ranges that overlapped the downtime window, and compare results against a known-complete dataset from a delayed Kafka consumer that re-read the same partitions after full recovery.

#!/bin/bash
# run_chaos.sh — broker-kill + query-correctness check
BROKER_ID=${1:?usage: run_chaos.sh BROKER_ID}
QUERY_RANGE_START=$(date -u +%s)

echo "[chaos] killing broker $BROKER_ID"
kafka-broker-stop --id "$BROKER_ID"

sleep 600  # 10 min downtime

echo "[chaos] restarting broker $BROKER_ID"
kafka-broker-start --id "$BROKER_ID"

echo "[chaos] waiting for rebalance convergence"
sleep 120

QUERY_RANGE_END=$(date -u +%s)

echo "[chaos] querying hot tier for recovery window"
HOT_RESULT=$(whitefalcon-query \
  --tier hot \
  --start "$QUERY_RANGE_START" \
  --end "$QUERY_RANGE_END" \
  --metric "request_latency_p99")

echo "[chaos] querying delayed consumer for same window"
DELAYED_RESULT=$(whitefalcon-query \
  --tier delayed-verification \
  --start "$QUERY_RANGE_START" \
  --end "$QUERY_RANGE_END" \
  --metric "request_latency_p99")

echo "[chaos] hot=$HOT_RESULT delayed=$DELAYED_RESULT"
if [ "$HOT_RESULT" != "$DELAYED_RESULT" ]; then
  echo "[FAIL] recovery gap detected — hot tier incomplete"
  exit 1
fi

The first three runs confirmed the gap. Every time, the hot-tier query returned a different P99 than the delayed consumer for time ranges overlapping the broker restart. The delta varied — sometimes 15% off, sometimes 40% — depending on which partitions rebalanced and how much traffic hit those partitions during the window. The gap was real, reproducible, and invisible to every existing alert.

This was the evidence that justified the watermark. Not a theory. Not a whiteboard argument. A repeatable test that showed query results diverging from ground truth during broker recovery, with specific numbers on duration and magnitude. The chaos test was the commit message: it proved the fix was needed and defined the acceptance criteria for when the fix was done.

The Fix: Freshness Watermark

The proposed fix was a per-partition freshness watermark in the hot tier. Each consumer, after flushing a batch of events to Redis, would update a watermark key: freshness:{partition_id} = {max_event_timestamp}. The query engine, before serving a result, would check the watermark for every partition that contributed data to the query range. If any partition's watermark was behind the query window's start time, the engine knew the result was incomplete.

Three response modes for incomplete data:

  • Staleness header: return the result with an X-Data-Staleness header indicating which partitions were behind and by how much. Dashboard consumers could display a warning badge.
  • Block: wait up to a configurable timeout for the watermark to advance past the query window. Useful for automated alerts that need correct data, not fast data.
  • Fallback: if watermark is stale beyond a threshold, route the query to a slower path that reads directly from Kafka consumer offsets — guaranteed complete but higher latency.

We validated the watermark by re-running the chaos test. After the fix, the hot-tier query either returned with a staleness header (correctly signaling the gap) or blocked until the consumer fleet caught up and then returned the correct result. The forty-seven-minute silent-wrong window dropped to zero: the system either told you the data was incomplete or waited until it was complete. No more plausible-but-wrong P99 values.

What We Didn't Do

We didn't add a read-repair path. Some TSDBs handle this by having the query engine itself read from Kafka when the cache is stale. We considered it and rejected it — WhiteFalcon's query engine was optimized for cache reads and adding a Kafka consumer path would have doubled the code surface for a failure mode that occurred only during rebalance. The watermark-plus-block approach was simpler and had a smaller blast radius if the watermark itself was buggy.

We didn't switch to synchronous Kafka consumption. The gap existed because consumption was asynchronous — events buffered in Kafka, consumers flushed to Redis in batches. Making consumption synchronous (write-through from Kafka to Redis on every message) would have killed throughput at 1.5T events/day. The watermark preserved async consumption while making the gap visible.

We didn't run chaos in production on the first iteration. The broker-kill tests ran in a staging environment that replayed sampled production traffic. The fidelity was good enough to prove the gap. Production chaos came later, after the watermark was deployed, as a regression gate.

What Changed After

Three things shifted permanently.

Recovery now had a definition. Before, "recovered" meant the broker was up and consumer lag was near zero. After, "recovered" meant every partition's freshness watermark had advanced past the downtime window. The incident channel could not be closed until the watermark confirmed completeness. This was a process change, not just a code change — the runbook for broker restarts gained a step.

Chaos became a gate, not a project. The broker-kill test ran weekly in staging as a regression check for the watermark. If a code change broke the watermark (delayed its update, dropped a partition), the chaos test caught it before the change reached production. Chaos was not a quarterly experiment. It was the test suite for the correctness contract.

Silent-wrong became a category we named. Before this incident, our failure taxonomy was: crash, slow, or unavailable. After, we added "silent wrong" — the system returns a result that parses, passes schema validation, and looks plausible, but is computed over incomplete data. The cross-tier percentile bug from WhiteFalcon was the same category. IoT identity ghosts at Walmart were the same category. Once you name the failure mode, you start designing against it.

Pattern: From WhiteFalcon to LensAI

The same gap exists in any pipeline that decouples ingestion from query visibility. In the LensAI inference observability stack — Rust ingestion through Kafka into ClickHouse — the question is identical: when the Go consumer restarts or Kafka rebalances, is there a window where Grafana dashboards show correct-shaped but incomplete data? The run_chaos.sh pattern from WhiteFalcon is what I'm porting to the compose-isolated dev environment: kill Redpanda mid-ingest, query ClickHouse for the recovery window, compare against a verification consumer that re-reads after convergence. The freshness watermark will be a ClickHouse materialized view that tracks max ingested timestamp per tenant partition.
