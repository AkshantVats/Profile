Day 83 — Agoda Cross-Tier Read Latency — Snappy Hot, Zstd Cold

Migrating WhiteFalcon's cold-tier Parquet compression from Snappy to Zstd cut storage 18% — and the real work wasn't the config change, it was proving "under 1% average latency impact" meant the same thing at the tail as it did on average.

Agoda's WhiteFalcon time-series database keeps months of history in its cold tier — Parquet (a columnar file format built for scanning specific columns without reading a whole row) files sitting on S3, reached through a Ceph storage layer — long after the hot Redis tier has aged them out past its 3-to-7-day retention window. Every one of those files was compressed with Snappy, a codec chosen for one property above all others: it decompresses fast, which matters when a query has to unpack a block before it can answer anything.

The question I picked up wasn't whether Snappy was wrong. It was whether a denser codec could shrink the cold tier's storage bill without quietly taxing every read that touched it.

Mine — the compression codec migration and its read-latency verification
I own this bullet end to end: choosing Zstd as the candidate, picking a compression level, and verifying the read-path impact before rolling it out. The Ceph/S3 storage layer, the Scala query engine that decompresses these blocks on every cross-tier read, and the histogram-based quantile merge those reads feed into — all Agoda team-built, covered in "When Percentiles Lie."

Compression Ratio Isn't the Only Number That Matters

Snappy trades compression ratio for decode speed. It doesn't squeeze a file as small as it could, but unpacking a block back into rows costs very little CPU.

Zstd — Facebook's Zstandard codec — sits on the other side of that line. At a higher compression level it packs the same rows into noticeably fewer bytes, at the cost of more CPU spent unpacking them later.

For a background job that writes a file once and reads it rarely, that tradeoff is easy: take the smaller file every time, nobody's waiting on the read.

So what: WhiteFalcon's cold tier isn't write-once-read-never archival — it's read on every query whose time range reaches past the hot tier's retention window, so "smaller file" and "cheap to read" are competing goals here, not the same goal wearing two names.

Three Codecs Considered, One Level Chosen

OptionStorage impactWhy it loses (or wins)
A. Keep SnappyNo changeZero migration risk, zero storage savings — the status quo, kept only if Zstd's decode cost turned out to be unacceptable.
B. Zstd at max compression levelLargest storage win availableDecode cost scales with compression level too — the densest setting also unpacks the slowest, and that cost lands on every cross-tier read, not just the migration job.
C. Zstd at a tuned mid-level (chosen)18% storage reductionGives up some of option B's storage win in exchange for a decode cost small enough that the read path barely notices — verified before rollout, not assumed.

Option B was the tempting number on a slide: the biggest storage reduction, in one line. It was also the option most likely to turn a background cost-saving change into a customer-visible latency regression, because Zstd's decode cost isn't flat across compression levels — it climbs as the level does.

So what: the codec with the best storage number in isolation isn't automatically the right choice once that codec sits directly in a live read path — the level that matters is the one where the storage win and the decode cost both stay acceptable together.

Why "Under 1% on Average" Wasn't the Whole Answer

The headline number for this migration ended up under 1% average read-latency impact — a good number on its face, and the one that would go in a summary slide.

An average only says that most requests barely noticed. It says nothing about whether a smaller set of requests absorbed a much larger hit that got smoothed out by everyone else's near-zero change.

Verifying this migration meant checking the same query paths WhiteFalcon's cross-tier quantile merge already tracks by percentile, not inventing a new measurement just for this change — the histogram-bucket infrastructure that makes a correct P95/P99 merge possible across the hot/cold boundary was already there to answer whether the tail moved the same way the mean did.

So what: a compression change that's "under 1% on average" and a compression change that's "under 1% at every percentile including p99" are different claims — only the second one is safe to ship without a caveat attached.

An average that stays flat can still be hiding a p99 that didn't.

Every cross-tier read that reaches into the cold tier now pays a decode cost before its bytes even become histogram buckets — the same buckets "When Percentiles Lie" already merges with the hot tier's own histogram to compute a correct P95 or P99 across a time range spanning both. That merge step doesn't know or care which codec produced the bucket counts it's adding together, which is exactly why it doubled as the verification tool: if Zstd's decode cost had shown up disproportionately at the tail, the merged percentile would have surfaced it directly, not required a separate benchmark harness built just to check.

So what: reusing an existing percentile pipeline as the verification instrument is both less work and more trustworthy than a purpose-built benchmark — it's the same measurement path production traffic actually travels, not a synthetic stand-in for it.

What the Fix Costs, What It Buys

1.5T–1.8TEvents/day
18%Cold-tier storage reduction

The cost is a codec migration touching every cold-tier write path, plus the discipline to verify the read side before calling it done. What it buys is 18% less storage on a tier holding months of history across roughly 1.5 to 1.8 trillion daily events — a percentage that compounds every day the cold tier keeps growing.

So what: at this scale, a storage-percentage win is not a one-time number — it's a recurring saving on every future day's ingest, which is exactly why it was worth the extra step of proving the read-latency side of the tradeoff before shipping it.

Today's Proxy Overhead Metric, One Layer Down

Today's fallback-chain streaming proxy applies the same lesson at a different layer: its overhead histogram is scoped to p99, not to a mean, for exactly the reason this migration's verification was.

A proxy that reports "under 10ms on average" could still be stalling a slice of requests well past that budget, the same way an average latency number here could have hidden a codec-driven tail regression. Measuring and gating on the percentile instead of the mean is the same discipline, applied one system earlier in this arc than a codec choice — before the number ever gets written down as a summary at all.

So what: "check the tail, not just the average" isn't a one-off verification step for a compression migration — it's a default worth building into the metric itself, so the question doesn't have to be asked by hand every time.
