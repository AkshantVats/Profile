The plan's bridge line for today reads: "promote staging→prod gate mirrors semver discipline," and the framing behind it points at a specific claim — a breaking flag-schema change at Agoda that needed a major-version bump. I checked agoda-whitefalcon-tsdb-architecture.md directly before writing this, the same discipline every post in this series has followed, and it doesn't mention feature flags, config schemas, or anything resembling that incident anywhere.

Scope note — what's documented vs. what the plan line implies
The WhiteFalcon architecture doc I have covers ingestion, storage tiers, the query engine, and the RoaringBitmap index — pure infrastructure, not a feature-flag or config-schema layer, so a "flag drama" story wouldn't appear in it even if one existed. What the doc does document, in detail, are two real interface changes I made to that system: a set of new Grafana query types, and a new cardinality dimension added to the index. Those two changes are the actual precedent behind today's post, not a remembered flag-schema postmortem.

A Thread Only Some Wrenches Fit

A pipe fitting's thread pitch is not a label you can repaint. Change the pitch and every wrench, coupling, and fitting built for the old one stops turning it, even though the new fitting looks nearly identical from across the room. The thread is load-bearing; nothing about it is cosmetic.

Paint a fitting a different color, or add a rubber washer to it, and nothing about which wrench fits has changed — because the interface everyone actually depends on, the thread pitch, never moved. That's the entire distinction a semver major.minor.patch number exists to communicate, and it's the same distinction a pipe fitting's thread and its paint job draw for free: one change touches what every existing caller already assumed; the other one doesn't touch it at all.

So what: "is this breaking" was never a question about how big a change looks, it's a question about whether it moves the thread — and that's the test worth applying before reaching for a version number at all.

What Actually Changed at WhiteFalcon

Agoda team's system, not my design
WhiteFalcon's RoaringBitmap inverted index, its Kafka ingest pipeline, its Rust consumers, and its Scala query engine core were the Agoda team's design, running at roughly 1.5–1.8 trillion events/day. I contributed to it as a Senior Engineer for about five months; I didn't design the system underneath what I touched.
What I actually shipped, per the architecture doc
I extended the Scala query engine to support two to three new query types reachable from Grafana, including wildcard tag matching and combined cross-tier range queries. Separately, I added a new cardinality dimension — Kubernetes pod and service-level tags — to the indexing layer, which required cross-product modeling against the existing 10k-per-metric label budget before merge, specifically to avoid a cardinality explosion.

The new query types didn't change what any existing dashboard's queries meant; they added routes into data that were already there, and every query written before that change kept returning the same answer after it. The new cardinality dimension was a different kind of change: it added a new axis to the label budget every existing metric was already implicitly sized against, so the constraint anyone's dashboards were safe under had moved, even though no single existing query broke the moment it shipped.

What I Still Don't Know

I don't have access to a documented flag-schema incident at Agoda, and the system I worked on there was a time-series database, not a feature-flag service — so I can't verify the plan line's specific claim, and I'm not going to write it up as if I'd lived it. What I can verify is that I made exactly this kind of additive-versus-breaking judgment twice on a real system, by hand, with no version field to record the answer in.

Today's model-registry ticket assigns every registered artifact a real major.minor.patch version, and it deliberately never guesses the bump type from the artifact's bytes — the caller supplies major, minor, or patch explicitly, because "was this additive or breaking" is a compatibility judgment only a human can make, the same one I was making by eye at WhiteFalcon. So what: the honest version of today's lesson isn't a remembered incident, it's that I already know what this judgment call feels like from the inside, and today's code just gives it a required field instead of leaving it to whoever remembers to update a wiki page.
