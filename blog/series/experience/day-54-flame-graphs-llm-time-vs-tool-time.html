Day 54 — Flame Graphs — LLM Time vs Tool Time

At Walmart Labs, a facility's monthly energy bill couldn't tell an operator which HVAC actuator needed retuning — only a view sized and colored by draw could. Today's cost flame graph in agent-benchmark-runner makes the same bet for tool-call spend.

A building's energy bill has one number on it. It tells facilities management what last month cost, and nothing about which piece of equipment cost it.

That gap — between a true aggregate and a decision anyone can act on — is the same gap between a benchmark report's total dollar figure and the tool call that actually spent it. I relearned it first at Walmart Labs, on a platform built to watch equipment, not agents.

A Building's Energy Bill Is a Bad Map

WeIoT SmartBuildings ingested telemetry from millions of sensors across dozens of Walmart facilities worldwide, feeding real-time HVAC control loops that automated energy optimization at that scale. The ingestion pipeline could tell you, accurately, how many kilowatt-hours a facility burned in a day. It could not tell you, from that number alone, which damper was stuck open, which compressor was cycling too often, or which zone's setpoint drifted and stayed drifted.

An aggregate is a single number describing a distribution it doesn't show you. A facility's draw isn't spread evenly across its actuators — a handful of them, misconfigured or degraded, account for a disproportionate share of it — and a monthly total treats the well-behaved majority and the handful of offenders as indistinguishable contributors to the same figure.

My contribution — Walmart Labs, Software Engineer II, WeIoT SmartBuildings, Aug 2018–May 2021
I helped architect the SmartBuildings ingestion layer on Azure IoT Hub and the real-time HVAC control loops running on Azure Stream Analytics that drove energy optimization across the facility fleet, plus a fault-tolerant edge-to-cloud OTA firmware framework for keeping distributed device configs in sync under intermittent network conditions. The specific per-actuator visualization work described below reflects the kind of operational view that pipeline made possible, not a single named dashboard I can point to by title three years on.

So what: the pipeline that could report a correct total and the pipeline that could point at a cause were, in principle, the same telemetry — the only thing separating them was whether anyone had built a view that made the distribution visible instead of just its sum.

The View That Made One Actuator Obvious

The operational dashboards a facilities team actually watched were grids: one tile per zone, each the same size, colored green or red by whether it was in range. That layout answers "is anything currently broken," which matters, but it treats every zone as equally worth an operator's attention regardless of how much energy that zone's equipment was actually spending — a zone quietly running its compressor twice as often as it needed to stays the same size tile as one running efficiently, as long as neither trips an alarm threshold.

The fix wasn't a new sensor. It was making the view itself carry the missing signal: size and color the tile by relative draw instead of by pass/fail, so the actuator burning the most immediately reads as the largest, hottest shape on the screen, before an operator reads a single number off it.

ViewWhat it answersWhat it misses
Monthly facility billWhat did the whole building cost, this periodWhich equipment inside it is responsible
Uniform zone-status gridIs any zone currently out of rangeWhich in-range zone is quietly the most expensive one
Draw-weighted viewWhich actuator is spending the most, right nowNothing this question needs — that's the point of building it

So what: correctness and legibility are different properties of the same telemetry, and a monitoring pipeline that only has the first has built half a monitoring system — the missing half is a view shaped by the question an operator is actually asking.

Same Idea, Smaller Stage

agent-benchmark-runner's new pkg/report/flame.go makes the identical bet for a benchmark run's tool-call cost. Day 53's timeline already answers "where did two agents' sequences stop agreeing" — a divergence question, colored accordingly, every box the same fixed width. It has no opinion about cost, because a run can match step for step and still spend wildly differently getting there, the same way two zones can both stay in range while one of them burns twice the energy doing it.

RenderFlameGraphSVG sizes each tool call's box by its dollar cost and colors it on a cool-to-hot gradient, marking the single most expensive call per agent. A reviewer reading the SVG doesn't scan a table of uniform boxes hunting for the priciest row — the widest, hottest box already is the answer, the same way the draw-weighted HVAC tile made the actuator that needed retuning the obvious one without anyone reading a kilowatt-hour figure first.

So what: "wide bars are where budget died" isn't a new idea invented for LLM agents — it's the same design decision a building's HVAC dashboard needed the moment "is anything broken" stopped being the only question an operator had.

What Stayed With Me

The lesson that traveled from a building in a Walmart facility fleet to a Go package rendering SVG boxes is narrower than "visualize your data." It's specifically: an aggregate number and a per-component breakdown are both accurate, and only one of them tells you where to spend the next hour of attention.

A total cost figure on a benchmark report is correct and almost useless for deciding what to fix. A box sized by what it actually cost, sitting next to its neighbors, answers the question before the reader has to ask it.
