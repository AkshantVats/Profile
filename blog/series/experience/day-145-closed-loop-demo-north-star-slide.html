Today's code in vllm-deploy-kit doesn't add a capability to any one module — it wires four days of separately-built pieces into a single runnable path for the first time. closed_loop/ walks a DriftWatch alert through escalation, a retrain webhook, a retrain stub, a RouteIQ canary registration, and a LensAI dashboard clone, in order, and prints a JSON trace of every step. Days 141 through 144 built each of those five pieces in isolation; nothing had chained them together until today.

A Rendering Doesn't Pour Concrete

DS analogy — the architect's rendering
An architect's rendering shows the whole building in one clean elevation before a single beam is poured — the lobby, the mechanical floor, the parking level below grade, all in one drawing. What the rendering can't show is whether the mechanical floor's ductwork, drawn by one consultant, actually lines up with the elevator shaft drawn by another. The rendering is a claim about how the pieces fit; whether they really do only gets tested once someone pours concrete and the trades show up on site.
The same gap, in a diagram I've kept current for years
Delivery Hero's rider-tracking architecture exists today as exactly that kind of drawing: Order Service, Order SQS, Route Service on EKS, Route Consumers reading OSRM, and a Route object assembled from both the live routing path and the Revisit Order System's replay. It's an accurate map — every box and arrow in it is a real component I worked against. But the diagram itself has never executed a single request; it's the thing you point at in an onboarding session or a system-design interview, not the thing a rider's phone actually talks to.

So what: a diagram earns its accuracy from matching the real components, but it earns nothing toward proving those components actually talk to each other correctly — that's a second, separate claim, and it's the one a whiteboard can't settle by itself.

Why Most Interview Diagrams Never Get Tested

A system-design interview asks for exactly the rendering, not the concrete pour: draw the request path end to end, name the real components, explain the failure modes, all in about forty minutes on a whiteboard. Nobody in that room has the time to actually run the five services being drawn, so the diagram itself becomes the deliverable, and a candidate is scored on whether it's a plausible map, not on whether it executes.

That's a reasonable interview format, but it trains a habit worth noticing: over enough of these sessions, drawing the end-to-end picture starts to feel like the hard part, when the harder part is almost always getting five already-working pieces to actually hand off to each other cleanly. This repo's own vllm-deploy-kit/DESIGN.md had exactly that gap for four straight days — a reserved diagram in Day 141, three real pieces built against it, and nothing chaining them until today.

So what: the diagram was never the risky part of this repo's design, and it usually isn't the risky part of a real system either — the risk lives in the handoffs a forty-minute whiteboard session has no time to test.

flowchart LR
  A["DriftWatch alert fires"] --> B["Escalation to retrain webhook"]
  B --> C["Real HTTP POST, single hop"]
  C --> D["Retrain stub, deterministic"]
  D --> E["RouteIQ canary registration"]
  E --> F["LensAI dashboard cloned"]

Only one of those five hops crosses a real process boundary: the retrain webhook, an actual http.server on a real socket, receiving a genuine HTTP POST shaped to match the Go client's own wire format field for field. Everything else — the alert, the retrain stub, the RouteIQ registration — is an in-process Python call that mirrors a real module's shape without importing it, the same boundary discipline this repo has drawn everywhere else two Python packages meet.

So what: closing the loop didn't mean making every hop real overnight — it meant being explicit, hop by hop, about which one actually crosses a wire and which ones are still honest stand-ins, so the diagram stops being read as more finished than it is.

What I Still Don't Know

I don't know whether a hiring panel would accept this simulation as "the system working end to end" the way they'd accept a live demo against a real GPU cluster — there's a real difference between a deterministic stub and a model that actually retrained, and I'm not going to blur that line to make the story land better. I also don't know yet whether wiring a live CUSUM detector in as the alert source, the one explicit gap this addendum leaves open, will require touching any of the four boundaries I kept clean today.

So what: the honest claim I can make is narrower than "the retrain loop works" — it's that four separately-built pieces now hand off to each other correctly in one process, with the one real network hop verified field for field, and the gap between that and a live cluster is named, not hidden.
