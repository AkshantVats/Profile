Day 32 — When the Collector Is the Product

At Walmart Labs I spent more engineering hours on two JSON config files than on all the sensor firmware combined — because the edge aggregation layer was the only component that decided what data survived

AS
Akshant Sharma
Experience · Day 32 of 150

13 min read

The hardest part of building WeIoT at Walmart Labs wasn’t the firmware. It wasn’t the cloud analytics SQL or the real-time HVAC control loops running on Azure Stream Analytics. It was two JSON files — the configuration that told the Azure IoT Edge Hub how to batch telemetry, what to drop when the queue filled, and how many times to retry before giving up.

I spent more hours debugging those two files than everything else combined over three years.

That’s because the edge aggregator was the only component in the system with no retry partner, no visibility into its own failure modes, and no redundancy. When a sensor network at a distribution centre went dark for six hours and came back with a six-hour backlog, the question wasn’t “how do we replay the data” — it was “what did the edge device decide to keep, and what did it silently drop.” The answer lived in those two config files.

I thought about them recently when I was writing otel-collector-traceforge.yaml for TraceForge. The processor pipeline felt familiar in a way I couldn’t immediately explain. Then I recognised the shape: it was the same engineering problem, running in a container with better tooling and reliable networking instead of an ARM gateway device on a 2G uplink.

The WeIoT System at Walmart Labs

My Scope at Walmart Labs
Software Engineer II on the WeIoT SmartBuildings Platform for three years (Aug 2018–May 2021). I architected the ingestion layer on Azure IoT Hub and engineered the real-time HVAC control loops via Azure Stream Analytics. I also designed and built the fault-tolerant edge-to-cloud OTA firmware framework that handled reliable config syncs and updates for millions of distributed devices under intermittent network conditions.

The WeIoT SmartBuildings platform connected 7M+ sensors across 50+ global Walmart facilities — HVAC units, power meters, occupancy sensors, refrigeration monitoring. Each sensor published to a local MQTT broker inside the facility. An Azure IoT Edge Hub gateway device at each site batched that telemetry and forwarded it to Azure IoT Hub in the cloud.

Azure Stream Analytics ran the control loops and energy optimisation queries on the ingested data.

The scale number that actually mattered wasn’t 7M+ sensors. It was tens of millions of telemetry points per minute at peak — which assumed reliable connectivity. The real operational challenge was the burst at reconnect: a six-hour network outage followed by an immediate flood of six hours’ worth of buffered readings.

The edge device had to decide what to do with that backlog, and it made that decision based entirely on the two config files I kept iterating on.

The firmware was commodity hardware running a standard MQTT client — I did not write it per-sensor. The Stream Analytics SQL was standard windowed aggregation — not novel. The engineering that required years of iteration was the Azure IoT Edge Hub configuration: the policies that said “batch every 30 seconds,” “drop when queue exceeds 100,000 messages,” “retry with exponential backoff, maximum three attempts.” The configuration was the product.

The Three Decisions Every Aggregator Makes

Every telemetry aggregation layer — whether it runs on an IoT edge gateway or in a Kubernetes sidecar — makes the same three decisions. The only thing that changes is the constraint that forces the trade-off.

The pattern is identical: a normalised source feeding a configurable aggregation layer feeding a durable sink. The IoT Edge Hub and the OTel Collector solve the same problem with different knobs.

Decision IoT Edge Hub (WeIoT) OTel Collector (TraceForge)
Batching batchTimeout: 30s / maxMessages: 10000 batch processor: send_batch_size, timeout
Drop policy Queue cap + oldest-first eviction memory_limiter + filter processor
Retry Exponential backoff, max 3 attempts retry_on_failure in exporter config

The IoT Edge Hub config was different for every facility tier: distribution centres got larger queue limits and longer batch windows than retail stores, because their connectivity was less reliable and their sensor density was higher. The OTel Collector config varies by pipeline stage: agent spans get 100% sampling, background health-check spans get probabilistic downsampling to 10%. In both cases, the variability lived in the processor configuration — not in the source code or the sink schema.

The configuration is where the business rules live. That’s why it’s the product.

The Silent Drop Problem

Here is the incident that crystallised this for me. A refrigeration unit at a cold storage facility was reporting anomalous temperature readings. The HVAC control loop should have triggered an alert after fifteen minutes of sustained anomaly — the alert didn’t fire for four hours.

Root cause: the edge device was in a high-backlog state from an earlier network outage. The drop policy evicted messages oldest-first when the queue overflowed. The temperature anomaly readings kept getting evicted before they could be forwarded to the cloud — competing with four hours of queued routine telemetry and losing every time.

The fix was a priority queue: refrigeration and HVAC readings got a high-priority lane that bypassed the drop policy. Occupancy sensors and power meters went into the default lane. The config change was six lines; the debugging that led to it took two weeks.

Non-software analogy — hospital triage queue
An emergency department that admits patients first-come-first-served regardless of severity. A low-acuity patient who arrived four hours ago sits ahead of a new high-severity patient in the queue. A triage system adds priority lanes — the severity of the condition, not the arrival time, determines who gets seen next. Applying this to the IoT edge: the criticality of the sensor reading, not the age of the message, should determine which data survives a queue overflow.

The lesson generalised immediately: drop policies encode business priority. A uniform drop policy — evict oldest first, regardless of sensor type — is a product decision disguised as a system default. The day you discover this is typically the day an alert fails to fire.

Every memory_limiter configuration in an OTel Collector pipeline is the same kind of decision. “Drop spans if memory exceeds 80%” sounds like a system config. It is actually a business decision: when the pipeline is under pressure, we prefer to lose some observability rather than drop user traffic. That trade-off belongs in a product document, not a YAML comment — but it usually lives only in the YAML.

The OTel Collector Is the Same System

The otel-collector-traceforge.yaml that Day 31’s TraceForge Go collector ships with starts minimal: a batch processor that flushes every 256 spans or every 2 seconds, and an attributes processor that stamps a pipeline.version on every span. That’s the equivalent of the IoT Edge Hub config at initial deployment: sensible defaults, no facility-specific tuning yet.

In a production deployment, that config grows to include a memory_limiter (the drop policy), a filter/spans processor (the priority lane), a probabilistic_sampler (the throughput budget), and a tail_sampling processor (keep all traces with at least one error span). Each of those four additions is a product decision. The filter/spans rule that drops debug-level spans in production is the same decision as the IoT priority lane that elevated refrigeration readings above occupancy telemetry.

The constraint is different: a WeIoT edge gateway had 256MB of RAM and a 2G uplink. A containerised OTel Collector has 1GB of RAM and reliable networking. The constraint shapes which processor rules matter most — but the design pattern is the same.

The configuration is the choke point. It decides what data the sink ever sees.

What the Python SDK Changes

Day 32’s traceforge.wrap_openai() changes what enters the Collector, not what the Collector does with it. The sensor firmware at Walmart Labs was commodity hardware with a standard MQTT client — I did not control the on-wire format of each sensor reading. The Python SDK is the equivalent layer I do control: it normalises the input before it reaches the aggregator.

Before the SDK, spans arrived at the Collector from ad-hoc HTTP calls — inconsistent shapes, missing token counts, raw argument payloads that would land verbatim in ClickHouse. After the SDK, every span entering the Collector has a trace_id and span_id following the same schema, argument payloads hashed to a 16-character SHA-256 fingerprint (so sensitive prompts don’t reach ClickHouse), and token counts sourced directly from response.usage rather than estimated. The traceforge.openai.tool_call_id attribute also enables dedup: if a retry produces two spans for the same logical tool call, the Collector can filter by tool_call_id to avoid double-counting cost.

SDK is the firmware layer
The sensor firmware standardised what arrived at the IoT Edge Hub — the same MQTT message schema, the same timestamp format, the same sensor ID structure. The Python SDK does the same for the OTel Collector: every span arrives with the same field names, the same types, and the same privacy treatment. The aggregator can then apply rules against a consistent input instead of guessing at the shape.

A sampling policy that keeps 100% of model_call spans only works if every model call span has tool_kind: "model_call". A dedup filter that removes retry duplicates only works if every span carries the original tool_call_id. Without the SDK normalising the input, the Collector configuration has to make assumptions about incoming span shapes.

When those assumptions are wrong, the policy silently misfires. That’s the refrigeration alert problem, repeated in observability.

The Thing That Took Three Years

At Walmart Labs, I kept treating the edge Hub config as infrastructure boilerplate — something to write once and file away. The firmware got version-controlled, reviewed, and tested against simulated failure scenarios. The edge Hub config sat in a shared directory with a comment saying “last updated Q4 2019.”

When I finally started treating the config as a first-class engineering artifact — versioned alongside the application code, reviewed with the same rigour as a schema migration, tested against simulated backlog scenarios — the reliability improved measurably. The priority lane for refrigeration held under load. The alert that should have fired in fifteen minutes started firing in fifteen minutes.

The OTel Collector config deserves the same treatment. It is already version-controlled in deploy/otel/otel-collector-traceforge.yaml. The next step is to treat a filter rule change the same way as a ClickHouse schema migration — written rationale, rollback plan, and a test that verifies spans that should survive actually do.

The sensor firmware at Walmart Labs didn’t change for eighteen months. The edge Hub config changed every three weeks. That ratio will probably hold for TraceForge’s Collector config too — the aggregation rules are where the product evolves, even after the ingestion code stabilises.
