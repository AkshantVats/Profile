Day 129 — Training Metrics — Agoda Ingestion Lag Analogy

Watch consumer lag, not just the loss curve. WhiteFalcon's hot tier could report perfectly normal Kafka throughput while quietly falling behind — and this week's lora_training_metrics stream exists because a training run's loss curve can do the exact same thing.

6 min read

WhiteFalcon's Redis hot tier promised the last three to seven hours of a metric at per-hour granularity. That promise only held if the Rust consumers reading off Kafka were actually current — if they'd fallen behind by even twenty minutes, "last 3 hours" in Redis was quietly the last 2 hours and 40 minutes, and nothing about that would show up as an error anywhere.

I found this out the hard way while extending the query engine, not by watching a dashboard. My cross-tier quantile merge assumed Redis held a genuinely fresh window before stitching it to the cold-tier histogram from S3; if the hot tier was stale, the merge was still mathematically correct on the numbers it received; the numbers themselves were just wrong.

Scope note — the ingestion pipeline is Agoda's, the correctness dependency is mine
Kafka ingestion and the Rust consumers writing into Redis are WhiteFalcon's own infrastructure, built and owned by the Agoda team I contributed to for roughly five months (Apr–Sep 2024, Sr. Software Engineer, Core Infrastructure). I did not design that consumer pipeline. What I own honestly is the dependency: my cross-tier quantile merge and the new Kubernetes-tag cardinality dimension I added to the RoaringBitmap index both assumed the hot tier's freshness, which meant ingestion lag — a standard operational signal for any Kafka consumer group at that throughput — was a correctness input to my own work, not an abstraction I could ignore.

A Metric That Looked Fine, Until It Didn't

WhiteFalcon had a real version of this exact failure shape, just in a different subsystem. Prometheus scrape duration crept up while request rate stayed completely flat — the metric a dashboard-watcher would check first showed nothing wrong. The root cause was a pod label added to a fleet metric, multiplying its series count; no alert fired until scrape targets started failing outright, and the alert built to catch stack degradation was the first thing to go dark.

Ingestion lag is the same shape of blind spot, one layer over. Kafka's own throughput — events produced per second — can hold at 1.5 trillion/day exactly as expected while one consumer group falls behind on committing offsets, because produce-side volume and consume-side progress are two different numbers that happen to usually move together.

So what: "the headline number is normal" and "the pipeline is healthy" are not the same claim, and WhiteFalcon had already taught me that once before I ever had to reason about it for a training run.

Why Lag Catches What Throughput Can't

Consumer lag is the gap between the latest offset Kafka has and the offset a consumer group has actually committed — how far behind the reader is, not how fast the writer is going. A GC pause, a slow downstream write into Redis, or a rebalance storm can all stall a consumer without slowing Kafka down for a single millisecond, because Kafka doesn't know or care whether anyone is reading.

That's exactly the gap that would have broken my quantile merge silently. A consumer twenty minutes behind still reports a perfectly normal produce rate upstream; the only place that twenty minutes shows up is in the lag number itself, and in a hot-tier bucket whose "last 3 hours" label was, at that moment, lying by twenty minutes.

So what: a health signal has to be measured on the side of the pipeline where the actual failure mode lives — consume-side progress, not produce-side volume — or it can't see the failure at all.

The Same Gap in This Week's Training Loop

Day 129's ticket was "log loss and grad_norm to Kafka every 50 steps," and a loss curve trending down is, for a training run, the same kind of headline number request rate was for Kafka: reassuring, and blind to one entire failure mode. A preemptible GPU instance that gets throttled to a fraction of its allocated compute keeps training — loss keeps dropping, just far more slowly — and nothing in train_loss or grad_norm alone would tell you the run's wall-clock cost had quietly tripled.

lora-trainer/DESIGN.md §5 names this directly: tokens_per_second rides alongside train_loss and grad_norm in every lora_training_metrics message specifically so a throughput collapse shows up in the same stream a convergence problem would, instead of requiring a second dashboard nobody remembers to open.

{
  "run_id": "lora-ft-20260821-1",
  "step": 1550,
  "train_loss": 1.842,
  "grad_norm": 0.673,
  "tokens_per_second": 1420.5,
  "logged_at": "2026-08-21T16:40:00.000Z"
}

So what: tokens_per_second in that message is this week's consumer lag — not the metric the ticket asked for by name, but the one that catches the failure mode the named metrics structurally can't.

Two Pipelines, One Blind Spot

SystemHeadline metricWhat it missesThe metric that catches it
WhiteFalcon (Agoda)Kafka produce rateA consumer group silently falling behind on commitsConsumer lag — offset delta, not event volume
lora-trainer (this week)Training lossA throttled or preempted GPU still converging, just far slowertokens_per_second — throughput, not convergence

Both pairs share the same shape: one number describes whether the thing you care about is moving in the right direction, and a second, structurally different number describes whether it's moving at the rate you assumed. Neither number implies the other — a consumer can commit offsets on schedule while lagging, and a model can converge while starved of GPU cycles.

So what: the fix in both cases wasn't a smarter headline metric, it was accepting that one metric was never going to cover two independent failure modes and shipping both.

What This Analogy Isn't

I never built or operated a consumer-lag dashboard at Agoda; the ingestion pipeline was the team's, and lag is a standard enough Kafka concept that I don't need a specific WhiteFalcon dashboard to have relied on the general principle. This week's tokens_per_second field is also unproven in the sense that matters most: no training run has consumed lora_training_metrics yet, so nothing has confirmed the field actually catches a real throttling event instead of just looking correct in a schema.

What did transfer is narrower than "Kafka and GPU training are alike" — it's the specific habit of asking "what failure mode does my headline metric structurally not cover" before shipping a metrics stream with only the headline metric in it.

So what: that habit cost one extra field in a JSON schema this week; at WhiteFalcon it would have cost a debugging session tracing a wrong P95 back through a merge that was never the bug.
