Day 79 — Walmart Stream Analytics Dropped Messages — Switching to Kafka

7M+ sensors across 50+ facilities eventually hit a limit no windowed query can dodge — and the fix wasn't a bigger window, it was a substrate that never forgets what it's already seen.

AS
Akshant Sharma
Experience · Day 79 of 150
August 8, 2026
7 min read

At Walmart Labs, WeIoT's SmartBuildings platform ingested telemetry from 7M+ sensors across 50+ global facilities through Azure IoT Hub, and Azure Stream Analytics ran the windowed queries that turned that firehose into the real-time HVAC control loops and energy-optimization decisions the platform actually shipped. A windowed query is exactly what it sounds like: it holds state for a bounded duration — a tumbling or hopping window — processes whatever arrived inside that window, then emits a result and discards the state. That's a completely reasonable design as long as every event you care about actually arrives inside the window it belongs to.

It mostly did. But a facility coming back online after a network blip doesn't send its sensors' telemetry in evenly — it sends it in a burst, every sensor re-registering and back-filling whatever it buffered while offline, all landing close together instead of spread across the interval Stream Analytics expected.

A window has no concept of "wait a bit longer, more is coming" once its close boundary passes. An event that arrives after that boundary isn't queued for the next window — it's simply outside the query's field of view.

Mine — WeIoT SmartBuildings, ingestion-layer architecture and the Kafka migration for the facility telemetry path
Azure IoT Hub's device registry and provisioning were existing Walmart Labs platform infrastructure. My contribution was architecting the WeIoT ingestion layer on top of it and engineering the real-time HVAC control loops the Stream Analytics windowed queries drove — and, later, owning the migration of that ingestion path onto a durable, replayable log once the windowed model's blind spot became a recurring operational cost instead of a theoretical one.

Before: A Window Has No Memory Past Its Own Boundary

Picture the shape of the failure: a facility's connectivity blips, its sensors buffer locally, then reconnect and flush everything at once. Stream Analytics' window for that time slice has already closed and emitted by the time the backlog lands.

Those events don't error out loudly — there's no exception, no alert. They just don't appear in that window's result, and the window that would have held them is gone.

So what: the bug wasn't that Stream Analytics processed anything wrong — every event it saw, it handled correctly. The bug was structural: a bounded window has no mechanism for "this arrived late, hold it anyway," so a traffic pattern the window's duration wasn't sized for produces silent, undetected data loss instead of a visible failure.

After: A Log Doesn't Discard, It Just Falls Behind

The fix wasn't tuning the window wider — a wider window buys you more slack until the next burst that's bigger than the new slack, and it costs more state held in memory the whole time, for a problem that keeps recurring at a new threshold. The fix was replacing the windowed-query ingestion path with Kafka: an append-only, offset-addressed log. A consumer reading from Kafka that falls behind a burst doesn't lose anything — it just has a growing lag, and it catches up from exactly the offset it last committed, whenever it's ready.

The consumer group reading that topic could always recover to a fully caught-up state from its own committed offset, whether it fell behind by ten seconds or ten minutes. A windowed query has no equivalent recovery path — there's no "offset" to rewind a window that already emitted and discarded its state.

So what: the fix wasn't making the fast path faster or the window bigger — it was accepting that the ingestion layer's job is to never forget an event before something downstream has actually consumed it, and only a durable log makes that guarantee true regardless of how bursty the traffic gets.

The Cutover: Dual-Write Before Trusting the New Path

We didn't flip every facility over at once. The Kafka path ran dual-write alongside Stream Analytics first — both paths live, Stream Analytics still authoritative for the control loop — on a subset of facilities, so we could compare event counts and control-loop decisions between the two paths before trusting the new one anywhere it mattered. Once parity held on that subset, we deliberately killed and restarted a consumer mid-stream to prove the offset-based recovery actually worked under a burst, not just in the design doc, before flipping authority over for real.

A recovery path you've only ever described on a whiteboard isn't a recovery path yet. We proved ours by breaking the consumer on purpose and watching it catch up.

That's the same discipline Day 76 already showed about this team's approach to Wayfair's supplier circuit breakers: the half-open recovery transition is worth deliberately exercising ahead of the moment it matters, not trusted on faith because the code is correct by construction. Here it meant killing a consumer and watching offset-based recovery actually happen under realistic burst conditions before that recovery path got trusted with 7M+ sensors' worth of ingestion.

So what: dual-write bought us a comparison before the cutover mattered, and deliberately breaking the new path before it went live bought us confidence that "offset-based recovery" wasn't just a property of the architecture diagram.

What Changed, Structurally

50+Global facilities
0Window boundary to lose events to
1Offset a consumer always recovers from

The number that actually mattered wasn't a before/after event-loss count — a silently dropped event, by definition, never left a clean count to compare against. It was the structural guarantee that changed: a windowed query's memory ends at its own boundary; a log's memory ends only when retention policy says so, and until then, any consumer can always recover from wherever it last stopped.

So what: you can't always measure the size of a problem you fixed by eliminating its cause — sometimes the honest metric is that the failure mode itself stopped being structurally possible, not that its rate went from some number to a smaller one.

Today's Code: The Same Discipline, One Layer Later

model-quality-scorer, which I extended today, leans on the identical property one layer further downstream. quality_scores keeps every judged sample as its own durable row in ClickHouse — never collapsed into a running average the moment it's computed. A 1h or 24h rollup query can always be re-run against that raw, retained table, the same way a Kafka consumer can always replay from an offset. Neither system trusts a single, one-time computation to be the last word on data it might need to revisit.

So what: "never discard the raw facts before something downstream is done with them" turned out to be the same lesson at two very different layers of the same career — a telemetry ingestion path at Walmart eight years ago, and a quality-score rollup query today.
