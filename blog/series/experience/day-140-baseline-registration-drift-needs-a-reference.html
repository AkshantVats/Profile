Day 140 — Baseline Registration — Drift Needs a Reference

Today's bridge line is a two-line design decision: push a model's eval score vector to DriftWatch the moment it's promoted, instead of waiting for the CUSUM detector to bootstrap its own history from live traffic. Wayfair's own monitoring stack draws the same line in a different place — its agile-anomaly monitors won't fire until they've accumulated weeks of history, and that gap is worth looking at directly.

The thread line behind today's ticket reads "push eval vector to DriftWatch when registering model," and the interesting part isn't the POST call itself. It's the timing decision hiding inside it — register the baseline the moment a model ships, rather than letting the drift detector work one out for itself from whatever scores happen to arrive after. I've watched that second option play out for real, on a production monitoring stack, and it's worth describing exactly what "letting it work one out for itself" costs.

A Scale Only Means Something After the First Weigh-In

A bathroom scale can't tell you you've gained weight the very first time you step on it. It reports one absolute number, with nothing recorded yet to compare that number against. The word "gained" only becomes possible once an earlier reading is already sitting somewhere in memory.

Drift detection has the identical shape. A CUSUM detector — the cumulative-sum control-chart algorithm the drift-detector service has run since day 111 — flags a score sliding away from where it started, not whether today's score is good or bad on its own. Without a first reading recorded somewhere, "away from where it started" doesn't mean anything at all.

My scope — PAS & Promotions, Nov 2024–Mar 2026
I led the PAS and Pricing, Promotions & Discounts teams at Wayfair, owning end-to-end delivery across both areas — which included the on-call rotation and the Datadog monitors underneath those services. The agile-anomaly detection itself is Datadog's own model, not something either team built; what my teams owned was which metrics it watched and where the thresholds sat.

So what: a monitor with nothing recorded to compare against isn't cautious, it's blind — and knowing that distinction is what makes today's design decision, push the baseline explicitly, worth taking seriously instead of skipping as boilerplate.

What a Freshly-Added Monitor Does for the First Few Weeks

Datadog's own machine, verified against the architecture doc
gst-acc-promotions runs a "Throughput anomaly" monitor set to a weekly agile-anomaly bound. PAS runs a "GraphQL throughput anomaly" monitor set to a daily agile-anomaly bound. Both are Datadog's built-in seasonal-baseline feature: it learns the normal shape of a metric across a day or week of history before it will flag any deviation from that shape.

Stand up a brand-new metric and wire an agile-anomaly monitor to it on day one, and that monitor is functionally decorative for its first stretch of life. It has nothing recorded yet to call "normal," so it has no basis for calling anything "abnormal" either. The monitor sits in the dashboard, green, and green means "still building its reference," not "all clear."

So what: the honest read on a fresh agile-anomaly monitor is that its silence isn't a signal for the first stretch of its life, and mistaking that silence for health is exactly the gap today's registry code is built not to leave open on a freshly promoted model.

Pushing the Baseline Instead of Waiting for It

Day 139's promote_to_production() gate already computes one eval_scores entry per task_type before it allows a promotion, each carrying a verified win_rate. Today's code adds exactly one more step to a successful promotion: that same, already-verified vector gets POSTed to DriftWatch's baseline endpoint before the function returns. Nothing about the eval run itself changes — only what happens to its result afterward.

This is the opposite choice from what Datadog's agile-anomaly monitors make. Their baseline accumulates implicitly, from whatever traffic happens to pass by once a monitor exists, with no explicit moment where anyone declares "this is now the reference." Today's registry code declares that moment on purpose, at the one point in a model's life where a trustworthy score already exists: the promotion gate that just passed it.

So what: the tradeoff is direct — an implicit, accumulated baseline needs no extra code but leaves a real coverage gap while it builds; an explicit, pushed baseline closes that gap the moment the model goes live, at the cost of one more webhook call the registry now has to get right.

What I Still Don't Know

I don't know whether a single promotion run's eval vector is a stable enough number to serve as a permanent reference. Datadog's own agile-anomaly model sidesteps this exact question by continuously re-learning its baseline on a rolling window instead of fixing it once. Today's registry code fixes the baseline at promotion time and doesn't revisit it, which is simpler but assumes that one eval run wasn't a noisy outlier.

So what: pushing a baseline explicitly solves the day-zero coverage gap cleanly, but it trades away the self-correcting property a rolling, continuously-updated baseline gets for free — and that gap is worth watching once a model has been in production long enough for its true score distribution to have shifted for reasons that have nothing to do with drift.
