Day 42 — One Dashboard for Inference and Tools

At Agoda, WhiteFalcon served one query face over two storage tiers — Redis hot, S3 cold — and a Scala engine merged histograms across the boundary so Grafana never had to know the split existed. Today's dual-write in tool-call-analyzer builds the same shape for AI agent cost: one dashboard, two pipelines.

WhiteFalcon had two storage tiers for the same metrics: Redis for the last three to seven days, S3 Parquet for everything older. From a Grafana user's perspective there was one dashboard, one query, one datasource.

The Scala query engine sitting in the middle was the piece that made that possible. It routed each time range to the right tier, fetched histogram bucket counts from both, merged them correctly, and returned a single result set — one query face, two pipelines. The user never needed to know which tier had actually answered their question.

I extended that engine to handle time ranges that crossed the hot/cold boundary, the case where neither tier alone had the full answer. That experience shaped how I think about unified observability now: the interface facing the user should be singular even when the storage underneath it is plural.

My role — Agoda, Core Infrastructure, WhiteFalcon TSDB, Apr–Sep 2024, Bangkok
Senior Software Engineer contributing to WhiteFalcon, Agoda's in-house Rust + Scala TSDB ingesting 1.5T+ events/day. Extended the Scala query engine for cross-tier Redis/S3 queries, solving the histogram merge problem needed for correct P95/P99 across arbitrary time ranges.

WhiteFalcon's split storage problem

WhiteFalcon's hot tier held the last three to seven days of metrics in Redis, bucketed by time window at per-hour granularity. This was the query load that mattered most day to day — on-call engineers, live dashboards, alerting pipelines. The tier was sized for fast random access, not for storage efficiency.

The cold tier sat behind Ceph and landed in S3 as Parquet, holding everything older than the hot window. Compaction merged files from hourly to three-hour to daily as data aged, trading granularity for storage efficiency. Once data left the hot window it was reachable only through this cold path.

Dashboards routinely asked for a fourteen-day window: “show me API error rate for the last two weeks.” That single request spans both tiers — days one through seven sit in Redis, days eight through fourteen sit in S3. Before cross-tier handling existed, a Grafana user had to split that into two manually configured queries and stitch the charts together by eye.

That's not a dashboard. That's a research project with a deadline.

Agoda's Scala query engine existed precisely to remove that seam. It took the full time range from Grafana, worked out which tiers it needed, fetched histogram bucket counts from each in parallel, and merged them into one result. The merge is where it gets interesting, because quantiles don't add the way counts do.

You cannot compute P95 on the hot tier, compute P95 on the cold tier, and average the two together — that number describes nothing real, because the underlying distributions have different shapes. WhiteFalcon stored aggregations as histogram bucket counts rather than pre-computed percentiles, and that single design decision is what makes a correct merge possible at all.

Physical analogy — the librarian who checks both rooms
Ask a librarian for every book published between 2010 and 2020, and a bad librarian tells you "new arrivals are in room A, the archive is in room B, go check both yourself." A good librarian checks both rooms and hands you one unified list. The request had one shape; the retrieval path had two branches, and the interface absorbed the difference.

The single-query-face design was, in my view, the most important architectural decision behind WhiteFalcon. Grafana dashboards could be written without any knowledge of the tier split underneath them, and alerts could fire on thirty-day windows without anyone hand-configuring a dual-datasource query. The complexity was real, but it lived in one place instead of being copied into every dashboard that consumed the data.

The cross-tier extension I built

Before my contribution, the Scala engine only handled time ranges that fell entirely within one tier — fully in Redis for anything under seven days, fully in S3 for anything older. A range spanning day one through day fourteen fell into a gap nobody had built for. Engineers worked around it by querying each tier separately and adding the two results together.

For quantile metrics, that workaround produces the wrong number. My first instinct, before I understood the histogram design underneath, was to query each tier, compute the quantile on each side, and return the larger value. If hot-tier P95 was 120ms and cold-tier P95 was 95ms, that instinct says take 120ms.

That's wrong, because the two distributions have different shapes, and the max of two quantiles is not the quantile of their union. The correct approach only becomes possible because WhiteFalcon stores histogram bucket counts instead of pre-computed percentiles — each bucket is additive on its own, so the count in a given latency bucket from Redis plus the count in that same bucket from S3 gives the true combined count for the full range.

WRONG:  max(P95(Redis, last 3d), P95(S3, days 4-14))
        → mathematically incorrect, quantiles don't add

CORRECT:
  1. Fetch histogram bucket counts from Redis (raw distribution)
  2. Fetch histogram bucket counts from S3 (raw distribution)
  3. Add corresponding bucket counts — merge the two distributions
  4. Compute the quantile once, on the merged histogram

What I built extended the Scala engine to detect when a requested range crossed the hot/cold boundary, fetch bucket counts from both tiers in parallel, add the corresponding buckets element-wise, and compute the requested quantile on the merged result. The response shape returned to Grafana was identical to a single-tier response: one time series, one point per hour, covering the full range.

The user-facing change was invisible: dashboards that already existed simply started returning correct fourteen-day results instead of an approximation nobody had flagged as wrong. That's the right outcome for infrastructure work — the win isn't a feature announcement, it's the quiet removal of an incorrect workaround that nobody knew they were relying on.

What "one query face" costs

Centralizing the tier-crossing logic in the query engine is the right trade. It keeps complexity in one place experts can manage, instead of spreading it across every team that writes a Grafana panel.

But it comes with a real cost: the query engine becomes a critical shared dependency, and any bug in the merge logic silently corrupts every metric that crosses the boundary. We caught regressions with a validation query that ran hourly against the window straddling the hot/cold boundary, computing the same metric three ways — Redis-only, S3-only, and the cross-tier merge.

The merge result had to equal the Redis figure for the hot portion and the S3 figure for the cold portion, within histogram quantization error. The more consumers depend on a piece of shared infrastructure, the more carefully it has to be tested, not because the logic is complex but because failures there are invisible by design.

A dashboard showing a wrong P95 after a query engine regression doesn't crash or throw an error. It just shows a wrong number, silently, to everyone downstream who trusts it — and the alert that should have fired on the real number stays quiet too.

One query face is still the right architecture. But it only stays right if the merge logic itself is the thing under test, not the downstream dashboards that assume it's correct: every dashboard that trusts the query engine is a test you are not writing.

The TraceForge connection

Today's pkg/dualwrite package in tool-call-analyzer sends each tool span's BillingEvent to LensAI's ingest endpoint right after writing it to ClickHouse. LensAI tracks inference cost, tool-call-analyzer tracks tool-call cost, and the Grafana board joins them on $tenant_id.

It's WhiteFalcon's architecture replayed one layer up the stack: two pipelines, one query face, one dashboard. In WhiteFalcon, hot meant Redis holding recent data and cold meant S3 holding history. In TraceForge, hot is tool-call-analyzer holding recent, granular tool-span data, and cold is LensAI holding the other half of the same bill — inference cost.

The unified BillingEvent envelope plays the role the histogram bucket schema played at Agoda: the shared shape that makes merging possible at all. tenant_id plus trace_id is the join key here, the way bucket boundaries were the merge key there.

WhiteFalcon's Redis writes never waited on S3 writes completing. The hot tier took the event first, cold-tier compaction happened asynchronously on its own schedule, and Redis availability never depended on S3 availability. tool-call-analyzer's dual-write follows the same principle: the ClickHouse write path never waits on LensAI, so if LensAI is unreachable, tool spans still land in ClickHouse.

The secondary write is best-effort, the same way cold-tier compaction was best-effort relative to hot-tier ingest. The difference is where the merge actually happens.

WhiteFalcon's query engine actively merged both tiers on read, inside the engine itself. TraceForge's unified board instead places two data sources side by side and lets the shared $tenant_id variable do the joining in the viewer's eye, not inside a query engine.

That's a deliberate trade: less infrastructure to build and run, at the cost of needing an actual ClickHouse table join whenever you want one true cross-system total instead of two numbers sitting next to each other. For a weekly budget review, visual juxtaposition is enough — for generating an invoice, only a SQL UNION over the billing events table gives the correct combined figure.

The WhiteFalcon principle was never really about time-series databases. Two storage systems, one query interface, and a shared schema that makes merging possible — that applies to any observability system stitched together from heterogeneous sources, and TraceForge is applying the same principle to AI agent cost attribution.

Building for the CFO and the on-call engineer at once

An on-call engineer asks “why is trace 7f3d9a2e costing $0.04?” A CFO asks “why did our AI bill increase 30% this week?” Both questions get answered by the same rows, grouped differently.

The engineer needs trace-level detail, the CFO needs a tenant-level weekly rollup, and it's one table with two GROUP BY clauses, not two systems. Row one of the unified board shows LensAI inference spend — token cost to the model provider. Row two shows TraceForge tool spend — cost to whichever APIs the agent called.

Both rows filtered by the same $tenant_id means a customer success manager can open a tenant's dashboard in a weekly review and see in seconds whether their costs skew inference-heavy or tool-heavy. That's a product conversation happening inside Grafana instead of a spreadsheet passed around after the fact.

At Agoda, the Grafana-facing API stayed identical no matter which tier answered a query, which meant dashboard configuration never had to change when the team adjusted retention windows or swapped a cold-tier storage format. The dashboard stayed stable because the interface contract stayed stable.

TraceForge's board generator, traceforge board, codifies that same contract for this project: the two datasource UIDs are configuration, the panel layout is fixed, and adding a new inference model or switching ClickHouse clusters touches nothing but a UID.

WhiteFalcon taught me that unified observability is a product discipline, not a data-engineering exercise. Agree on the envelope, agree on the join key, then generate the interface from code so the agreement is machine-checkable instead of a convention people forget.

The query engine was that generated artifact at Agoda. The board generator is that artifact for TraceForge — and in both cases, the discipline is what lets one dashboard stand in for two pipelines without anyone downstream having to know it.
