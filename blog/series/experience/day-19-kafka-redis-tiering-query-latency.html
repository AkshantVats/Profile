Day 19 — Kafka + Redis Tiering — Query Latency by Temperature

Agoda · decoupling hot reads from cold storage in WhiteFalcon TSDB

The SLO said p99 query latency under 50ms. It was technically passing every week. But it was lying in a way that took me two months to name precisely: the 50ms SLO measured the average p99 across all queries, and the hot tier served more than 90% of them.

The cold-tier queries — which regularly landed at 800ms or above — were being averaged away by the hot tier’s sub-10ms responses. An SLO that averages across storage temperatures is not one SLO. It’s three SLOs collapsed into one number.

The fix turned out to be an instrumentation change before it was an infrastructure change. Once we could see latency by tier, the picture was clear. Until then, the dashboard said everything was fine.

Tiered storage systems have three distinct query classes: hot, cold, and cross-tier. Each has a different latency budget and a different failure mode. Treating them as one is how you build a monitoring system that lies to you.

WhiteFalcon’s storage tiers

WhiteFalcon — Agoda’s in-house TSDB — was built around Kafka as the ingest backbone. Rust consumers drained the Kafka topic, writing time-bucketed state to Redis for the hot tier and flushing completed windows to Ceph-backed S3 as Parquet files for the cold tier. The Agoda team published their own write-ups on the architecture; I contributed to the query engine extension that makes cross-tier queries correct.

Team scope — Agoda
The Redis hot tier, Ceph/S3 cold tier, Kafka pipeline, and Rust consumer design were built by the Agoda team. Akshant contributed to the cross-tier Scala query engine extension and added k8s cardinality dimension — not the tier storage implementation itself.

The hot tier held the last 3–7 days of data at per-hour granularity. At 1.5T events per day, that’s roughly 4.5–10.5T events in Redis at any given time. Each time bucket was a Redis key with a compacted histogram structure.

When a bucket’s retention window closed, a background job flushed it to Parquet on Ceph/S3 with datetime partitioning. Compaction then merged hourly files into 3-hour, then daily chunks.

The latency gap between tiers was not a bug in the design — it was a deliberate tradeoff. Redis gave sub-10ms reads for the queries Grafana dashboards hit every 30 seconds. Parquet on Ceph gave cost-efficient cold storage for data older than the hot window.

The problem was that nobody had defined “how much higher” latency was acceptable for cold queries, or tracked it separately from hot reads.

Why the SLO was lying

A production Grafana dashboard typically queries the last 1–3 hours of data. At Agoda’s query volume, that meant more than 90% of all queries landed entirely within the Redis hot tier. The p99 across all queries was dominated by these fast reads.

An analyst running a query for the last 30 days of model latency data — the kind that requires cross-tier or pure cold-tier access — was in the remaining 10%. Their 800ms experience was invisible in the aggregate SLO.

An SLO that averages across storage temperatures is not an SLO. It is a weighted average that privileges the fast tier.

Think of a hotel review score that averages the penthouse suite and the budget rooms together. The overall score looks fine because 80% of guests stay in decent mid-range rooms. The 10% who booked the budget floor based on the aggregate score are misled.

The right metric is separate ratings by room category. Storage tiering needs the same approach.

The instrumentation change was to label every query at execution time with its tier: tier=hot for pure Redis reads, tier=cold for pure Parquet reads, and tier=cross for time ranges spanning both. Once we had that label, three separate p99 metrics replaced the single aggregate.

The cold p99 immediately showed 750–900ms. The cross-tier p99 showed 400–600ms. The hot p99 confirmed sub-10ms — the only number that had been visible in the old aggregate.

What I contributed
Adding tier labels to Scala query engine spans was part of the cross-tier query work. The histogram bucket merge for cross-tier correctness is covered in depth in When Percentiles Lie. Here I’m focusing on the SLO design problem that the tier labels solved.

Kafka flush timing and the tier boundary

The tier boundary was not a hard cutoff at a calendar timestamp. It was defined by when the Rust consumer had flushed a time bucket from Redis to Ceph/S3. That flush happened asynchronously, triggered by a combination of window close time and a background compaction job.

In practice, data from two hours ago was almost always in Redis. Data from three days ago was almost always in Parquet. Data from 12–24 hours ago was in an uncertain state depending on flush lag.

This uncertainty meant the query engine could not determine tier membership from the timestamp alone. It had to probe Redis first, then fall back to Parquet if the bucket was not present. For the hot path this was fine — one Redis GET and done.

For the cold path it meant two network hops: Redis miss, then Parquet fetch. The cross-tier path was a Redis hit for recent buckets and a Parquet fetch for older ones, with the histogram merge step on top.

The two-hop penalty for cold misses explained the 400–600ms cross-tier latency — the Redis miss itself is cheap, but the Parquet scan on Ceph added the bulk of the latency. For pure cold queries beyond the hot window, the Parquet scan was the entire read path, and Ceph’s NVMe-backed latency still landed at 700ms+ for large date ranges. Columnar formats optimize for scan throughput, not point-query latency.

Designing separate SLOs by query class

Once we had the three-tier labeling in place, separate SLO targets were the natural next step. Hot-tier queries at sub-10ms p99 were achievable because Redis is purpose-built for low-latency reads. Cold-tier queries at 800ms p99 were acceptable for historical analysis workloads.

The cross-tier class was the one that needed work. At 400–600ms, it was slow enough to degrade dashboards that happened to span the hot/cold boundary.

The cold-tier SLO at 5 seconds was not a performance aspiration — it was an honest statement about what Parquet scans on Ceph could deliver for large time ranges. The cross-tier target at 1 second was more aggressive because that class included dashboard queries at the hot/cold boundary, and users expected dashboard latency closer to hot-tier behavior. Communicating those targets to Grafana dashboard authors changed how they wrote queries: date pickers that defaulted to “last 30 days” were updated to “last 7 days” as the default, reducing inadvertent cold-tier hits.

What I didn’t expect
The biggest impact of publishing separate SLOs was on the people who write dashboards, not the people who operate the storage layer. Engineers writing Grafana dashboards stopped defaulting to 30-day views once they saw the 800ms cold-tier number. A latency-aware default range is free performance — no infrastructure change required.

Kafka ingest rate and hot-tier memory pressure

At 1.5T events per day, the Kafka ingest rate averaged around 17 million events per second at peak. The Rust consumer was the component that determined hot-tier freshness. If the consumer fell behind Kafka, recent data would not be available in Redis and hot-tier queries would miss.

A consumer lag alert was the most important SLI for hot-tier read freshness — not a query latency alert.

Redis memory pressure was managed by the time-bucket retention window. When a bucket window closed, it was eligible for flush to Ceph. If the flush was delayed — say, a compaction job was running and the Ceph write path was slow — the bucket stayed in Redis beyond its nominal retention, consuming memory.

The system had a hard eviction path: if Redis was within 10% of the memory limit, the oldest unflushed buckets were force-evicted regardless of flush status. This was a data loss path, not a graceful degradation path.

The cold-tier query latency and hot-tier memory pressure were coupled through the flush pipeline. A slow Ceph write path caused Redis to grow, which triggered force eviction, which caused cold-tier misses for data evicted before flushing.

Monitoring Kafka consumer lag, Ceph write latency, and Redis memory as a trio — not individually — was the operational lesson. Any one degrading alone was manageable. Two degrading simultaneously was a data loss scenario.

The staging discipline parallel

Day 19’s ebpf-llm-tracer demo harness proves the tracer without production API keys — a mock LLM server stands in for OpenAI, and the eBPF sidecar captures calls from a demo app without any SDK changes. The staging discipline is the same one Agoda applied to load testing WhiteFalcon before new query types went live: you don’t test correctness against production data, you build a mock that has the same shape and validate the behavior against that first.

For WhiteFalcon, the equivalent of the mock server was a synthetic event generator that produced known histogram distributions at known rates — so the query engine’s merge output could be verified against ground truth before any real production traffic hit the cross-tier path. For the demo harness, the mock LLM server produces known token counts and model IDs so the eBPF parser and mapper output can be validated end-to-end without a real API call.

The pattern is the same: isolate the system under test from production dependencies, validate the behavior with a mock that preserves the structural properties of the real thing, and only then route real traffic through it.

What I’d instrument differently

The tier label on queries should have been there from day one, not added after two months of a misleading composite SLO. The cost of adding it retroactively — finding every query emission point in the Scala engine, adding the label, redeploying, and backfilling the dashboard — was significantly higher than wiring it in at the start.

Latency classification by storage tier is not a nice-to-have. It is the minimum instrumentation for a tiered storage system.

Track Kafka consumer lag as a hot-tier freshness SLI, not just an operational alert. If the consumer falls 10 minutes behind, the hot tier’s “last 3–7 days” effectively becomes “last 3–7 days minus the lag window.” Users querying the last 30 minutes get stale data without any visible signal unless you surface lag as a dashboard metric, not just a PagerDuty trigger.

The cross-tier merge optimization was the right investment. Every millisecond saved in the histogram bucket merge — loading bucket counts, summing, re-computing the quantile — reduced p99 for the most visible query class. The hot/cold per-tier latencies were determined by Redis and Ceph hardware, respectively.

The merge step was the only part of the cross-tier path fully in software. That made it the only part with an engineering lever worth pulling.
