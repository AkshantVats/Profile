Day 82 — Delivery Hero OSRM Pool Saturation — PDBs vs. the Lunch Rush

A PodDisruptionBudget tuned to protect Route Service during routine node rotation was still in force during the lunch-rush spike — and it blocked the exact reschedule that would have relieved a saturated OSRM pool.

Delivery Hero's Route Service and Route Consumers run on AWS EKS, both reading from Order SQS and both calling into the same OSRM cluster to map-match a rider's position onto the road network. At 1M+ daily orders, that cluster's connection pool is sized for what a normal hour looks like, not for what a lunch-rush hour looks like.

Lunch rush pushed concurrent map-matching calls past the pool's capacity. Requests queued behind it, latency climbed, and a slice of them — about 8% — timed out outright before OSRM ever got to them.

The obvious fix was to scale Route Consumers out and let more pods share the OSRM load. That fix was already blocked, by a safety mechanism installed for an entirely different problem.

Mine — Route Consumers autoscaling policy, OSRM pool sizing, the PodDisruptionBudget change
I owned the Route Consumers HPA policy, the OSRM client pool configuration on our side of the connection, and the PodDisruptionBudget change this post describes. I did not own OSRM's own database tuning or the cluster's underlying map-matching engine — that sat with the platform team that ran OSRM as a shared service across several consuming teams.

The Concrete Problem: A Pool Sized for the Average Hour

OSRM's pool exists because a map-matching call isn't cheap: it holds a connection into the routing engine's in-memory road graph for the duration of the request. A pool bounds how many of those can run at once, so the graph doesn't get thrashed by more concurrent lookups than the box backing it can serve.

That bound was set against typical daytime traffic, with headroom for ordinary variance. Lunch rush isn't ordinary variance — it's a repeatable daily spike, and it pushed concurrent map-matching calls well past the pool's sizing.

Requests that couldn't get a pool slot queued instead of failing immediately, which sounds safer than it turned out to be. A queue with no depth limit just delays the failure: once enough requests are waiting, the ones at the back of the queue blow past their own timeout before they ever get a slot.

So what: a connection pool sized for the average hour doesn't fail cleanly under a repeatable peak — it fails slowly, as a growing queue, until the requests at the back start timing out anyway, which is a worse failure mode than rejecting them up front would have been.

Three Ways to Relieve a Saturated Pool

OptionMechanismWhy it loses (or wins)
A. Scale Route Consumers outHPA adds pods so more OSRM connections are available under the same per-pod pool capBlocked in practice: the PodDisruptionBudget guarding routine node rotation also gated the node-level reschedule the autoscaler needed to actually place new pods.
B. Raise the per-pod pool sizeLet each existing pod hold more concurrent OSRM connectionsMoves the bottleneck, doesn't remove it — OSRM's own road-graph reads are the limited resource, and more concurrent connections into the same box just queues at a different layer.
C. Retune the PDB to a floor, not a fixed count (chosen)minAvailable expressed relative to HPA's current desired replica count, not a static number set once for routine maintenanceKeeps the PDB's real job — protect against a rotation dropping too many pods at once — without also freezing the cluster's ability to add capacity during a legitimate scale-out event.

Option A was the right instinct and the wrong first move: the autoscaler already knew to add pods, and it tried. The PDB's fixed minAvailable count, written for a different scenario, didn't know the difference between "a node is draining for routine rotation" and "the cluster needs room to schedule pods that don't exist yet."

So what: a PodDisruptionBudget is a floor on availability during disruption, but a fixed count doesn't distinguish "protecting what's already running" from "blocking what's trying to start" — and during a legitimate scale-out, those are opposite goals wearing the same guardrail.

The PDB now expresses minAvailable as a percentage of the HPA's current desired replica count, recomputed as that count changes, instead of a number fixed at the time someone last edited the manifest for routine maintenance. A node drain during steady state still can't take out more pods than the floor allows — that protection is unchanged.

What changes is what happens when the HPA raises its desired count mid-incident: the floor rises with it, so the disruption budget scales alongside the very capacity it's supposed to be protecting, rather than staying pinned to a number set for a calmer day.

The analogy is a minimum-staffing rule at a hospital's emergency room. "Always keep three nurses on shift" is a sane floor on a normal night. The instant a mass-casualty event needs five more nurses moved in, a rule that also blocks reassigning two of the original three to make room for a triage tent works against the exact surge response it should be enabling.

So what: a safety floor that doesn't know the system is trying to grow will treat "adding capacity" and "losing capacity" as the same event — the fix isn't to remove the floor, it's to make the floor move with the thing it's protecting.

What the Fix Costs, What It Buys

1M+Daily orders
5k+Route updates/sec
8%Lunch-rush error burn (before fix)
10k+Concurrent requests at peak

The cost is one formula change in a PDB manifest and a bit more care reasoning about it — a percentage tied to a moving target is harder to eyeball than a fixed number. The harder cost was convincing the platform team owning OSRM that the pool itself didn't need resizing yet, because the real bottleneck was never inside OSRM at all.

A guardrail that can't tell "the system is shrinking" from "the system is growing" will eventually block the exact recovery it exists to protect.

What the fix buys is that Route Consumers can now actually use the autoscaling headroom it already had. The HPA was never the problem — it was reacting correctly and asking for more pods within seconds of queue depth rising. The PDB was the thing standing between "asked for" and "actually scheduled."

So what: at Delivery Hero's scale, the fix that mattered wasn't more compute — it was making sure the compute the system already knew how to request could actually land, which is a scheduling-policy problem dressed up as a capacity problem.

Today's Chain Executor, One Layer Down

Today's fallback-chain executor solves a version of the same problem at request scale instead of cluster scale. A request stuck behind a saturated primary model needs a defined moment to stop waiting and move on — that's the whole reason the 2s/5s/8s cascade exists, rather than letting a request queue indefinitely behind a model that's already struggling.

The parallel is exact: OSRM's queue had no depth limit, so saturation showed up as slow failure instead of a clean one. The chain executor's per-hop timeout is that depth limit, expressed as time instead of queue length — a request that can't get an answer from its first choice within its budget stops waiting and tries the next one, the same way Route Consumers needed a rule that would let it stop waiting on a blocked reschedule and just proceed.

So what: "know when to stop waiting and move on" is the same lesson whether the thing waiting is a Kubernetes scheduler or a fallback chain — an unbounded wait against a saturated resource always fails slower and worse than a bounded one would.
