Prometheus scrape duration was creeping while request rate was flat.

Nobody had shipped a feature. Someone had added pod as a label on a fleet metric the week before. The time-series index at Agoda had been built to survive traffic spikes — not tag explosions. Each new pod value multiplied existing series; scrape cost grew because the index had to track every combination, not because more requests arrived.

Nothing was on fire. Grafana still rendered. That is the failure mode I keep writing about: dashboards stay green while the truth quietly rots — the same family as When Percentiles Lie and Seven Million IoT Sensors. Cardinality is the upstream cause. You indexed a cross-product you never modeled on paper first.

Cardinality Is the Silent Killer

A time series is not "a metric." It is a metric name plus one unique combination of tag values. Every distinct combination is its own series in the index. Traffic can stay flat while series count climbs — because you added labels, not because users sent more requests.

Add model_id with two hundred values to a metric that already carries tenant_id with five hundred values and three statuses, and you are not adding two labels. You are inviting up to 300,000 series for that metric alone (200 × 500 × 3). The cluster does not fail loudly. It gets slower first. Then it drops series under memory pressure, or serves aggregates built on an incomplete index. Your dashboard still loads; the number on screen may be computed from a subset you never knew was missing.

The main concern with any new cardinality dimension is not the implementation. It is modeling the cross-product before you start.

How WhiteFalcon Indexes Series

Team system

WhiteFalcon at Agoda: Kafka → Rust ingestion → Redis hot tier and Parquet cold tier, with a RoaringBitmap inverted index per tag value. Public write-ups describe indexing hundreds of millions of series at Kafka volumes on the order of 1.8 trillion events per day.

My contribution

From Experience 1: a moderate-cardinality Kubernetes service tag — modeled cross-product before merge — plus cross-tier quantile work in Experience 2. I did not design the RoaringBitmap engine; I learned its constraints the hard way when proposing new dimensions.

flowchart LR
  K[Kafka events] --> ING[Rust ingestion]
  ING --> HOT[Redis hot tier]
  ING --> IDX[RoaringBitmap per tag value]
  Q[Query: filter model + cluster] --> IDX
  IDX --> SER[Series ID sets]
  SER --> MERGE[Intersect / union]
  MERGE --> HOT
  MERGE --> COLD[Parquet cold tier]

When you query, the engine intersects bitmaps: "all series where model=X AND cluster=Y." That is fast when each tag has a modest number of values. It is catastrophic when a high-cardinality tag lands on a high-traffic metric without a spreadsheet first — because every filter now walks a bitmap that grew overnight.

Agoda's public engineering posts on RoaringBitmap indexing explain why inverted sets beat naive posting lists at hundreds of millions of series. I cite them in the footnotes rather than re-derive the compression math. What mattered in review was simpler: if a tag multiplies series faster than traffic grows, you are not "adding observability." You are changing the cost of every query that touches that metric, whether or not anyone updates the dashboard.

The Cross-Product You Must Model First

Cardinality explodes with time when the number of tags and series increase — not because traffic doubled, but because each new label value creates another combination with every value that was already there. That is the cross-product. You have to multiply cardinalities on paper before you merge a pull request.

flowchart TD
  M[Metric] --> L[model / tenant / status labels]
  L --> X["~300k time series"]
  X --> MEM[Memory pressure]
  X --> SCR[Scrape duration grows]
  X --> DROP[Series dropped under limit]

Prometheus-style labels make the cross-product visible in every scrape target. WhiteFalcon's index made it visible in engineering review: "How many unique values will this tag have in six months, and what metrics already carry it?" The discipline transferred directly to today's inference pipeline. model_id and tenant_id live as ClickHouse columns for analytics. They are not multiplied into Prometheus histogram labels, because columnar stores scan dimensions; label-indexed TSDBs index every combination.

At Agoda we rejected "just add pod" on fleet counters for the same reason. Pod cardinality tracks deployment churn. Every deploy adds values. Multiplying pod against every existing tag is how you turn a one-line Helm change into a quarter of index growth — with no feature launch and no traffic spike to explain it on the incident call.

Where Prometheus Stops

Prometheus is a label-indexed TSDB built for ops metrics: a few hundred series per metric name, not hundreds of thousands. It degrades well before the cardinality AI infrastructure routinely produces. You feel it first as scrape duration growth, then as memory pressure, then as series evicted from the limit. Dashboards still load because the remaining series look fine — which is exactly why the failure is easy to miss.

That is why P99-by-model_id on a Prometheus histogram with unbounded labels is a lie waiting to happen. You are not merging tiers wrong; you are merging shards you never meant to create. The shard boundary is which labels you allowed — not Redis vs S3.

Cardinality kills the cluster before traffic does. The dashboard still renders.

The split that transferred from Agoda: Prometheus for bounded ops counters, a columnar store for analytical slices over high-cardinality inference dimensions. WhiteFalcon did not run ClickHouse; the discipline did.

model_id × tenant_id on Today's Pipeline

Each inference event carries model_id, tenant_id, token counts, phased latency, and cost_usd. Those fields belong on the row. The analytical store targets on the order of 10k+ dimension combinations — a design goal, not a production benchmark. A columnar engine can group by model_id without creating one time series per request; Prometheus cannot.

The producer keys Kafka by tenant_id; the target is hash(tenant_id:model_id) so one hot model cannot poison a tenant partition. That is placement, not cardinality — but it comes from the same instinct: bound blast radius before the noisy neighbor shows up on the dashboard.

Why the P99-by-Model Panel Is a Cardinality Bet

The P99-by-model panel only works because model_id stays a ClickHouse column rather than a Prometheus label. The difference sounds small. One creates analytical dimensions. The other creates new time series.

Request identity belongs in the event row or in a sampled trace — not on counters. Histogram labels stay bounded: tenant, cluster, status. If someone adds pod to every counter tomorrow, the panel still renders. Your P99 story quietly rots the same way Agoda's scrape duration did: the chart loads; the index behind it does not represent what you think.

How Cardinality Dies Quietly

These failures rarely throw an exception. They change what the index contains while the UI still paints green.

  • Scrape lag — series count grows; request rate stays flat; no error spike on the service.
  • Series limit drops — the TSDB evicts old series; aggregates run on a subset; P99 can look better and be wrong.
  • Sparse new label — merge paths return nonsense when one shard has data and another does not; same class as Experience 2.
  • OOM on compactor — index rebuild crosses a line you modeled in theory only.
  • "Helpful" pod label — a fleet metric becomes per-pod overnight; on-call learns on a Friday.

What Stayed With Me

RoaringBitmap set operations at Agoda scale taught me that observability is an indexing problem before it is a visualization problem. You can ship a beautiful Grafana row on day one and still be lying on day thirty if nobody multiplied tag cardinalities when the label landed.

Throughput and lag on bounded labels — enough to page when the pipe chokes. Dollars and P99 in the warehouse, where cardinality belongs in columns, not labels. Incidents fade. What stays is the spreadsheet before the label.

Traffic growth is visible. Cardinality growth hides inside labels. One shows up on dashboards. The other changes what dashboards mean.
