Day 58 — TraceForge — Agents Need a Flight Recorder

Delivery Hero's postmortems never opened with what broke — they opened with where two systems reading the same events stopped agreeing. agent-benchmark-runner's divergence report is built around that same question.

A plane's flight recorder doesn't stop the crash.

It survives the crash and tells you, second by second, where the aircraft's systems stopped agreeing with each other — airspeed sensor against altimeter, autopilot command against control surface response. Delivery Hero's postmortem format taught me the same discipline for software: don't open with "what broke," open with "where did two systems reading the same events stop agreeing." Today's rehearsal of agent-benchmark-runner against a real task, ahead of tomorrow's launch post, is built around that exact question.

What the Postmortem Format Actually Asked For

Delivery Hero's rider-tracking stack put two independent consumers — Route Service and Route Consumers — on the same Order SQS stream (AWS's managed event queue, where every consumer reads the same events independently). Both read the same lifecycle events: PLACED, RIDER ENQUE, PICKED UP, RIDER PICKED UP. Both fed OSRM, the open-source engine that turns raw GPS coordinates into a matched road-network route, and both were allowed to compute their own view of "where is this order right now."

A postmortem that just said "the ETA was wrong" was useless to the team that had to fix it. What the format actually forced onto the page was a timeline: at which lifecycle event did Route Service's view and Route Consumers' view of the same order start to disagree, and what happened between them before anyone noticed.

So what: two systems consuming the same event stream will drift, and the only useful postmortem question is when the drift started, not that the drift eventually became visible as a bad number on a dashboard.

My scope — Delivery Hero, Berlin, Jun 2022–Jul 2023, Sr. Software Engineer, Global Logistics Platform
I built end-to-end rider tracking on this stack, processing 5,000+ real-time route updates per second against 1M+ daily orders on AWS EKS at 10k+ concurrent requests, zero downtime. I also designed the async SQS + Kinesis pipeline that decoupled order processing from notifications so delivery status updates stayed sub-second for millions of active users at peak. This post describes the postmortem habit that shaped how I approached today's rehearsal, not a claim that agent-benchmark-runner ran at Delivery Hero.

The Same Shape in an Agent Run

An agent run is, structurally, the same kind of thing as a delivery: a sequence of steps with a start state and an end state, where the interesting failure is rarely "it crashed" and almost always "it took a different path than expected." Two agents given the identical task — same prompt, same seed, same success criteria — are two independent consumers of the same starting event, exactly like Route Service and Route Consumers reading the same PLACED event.

The question worth answering isn't "did agent B fail." It's "at which tool call did agent B's sequence stop matching agent A's," the same way the useful question was never "was the ETA wrong" but "at which lifecycle event did the two views diverge."

What a Flight Recorder Actually Buys You

A flight recorder is a physical box bolted into the tail of an aircraft, built to survive the one event it exists to explain. It doesn't make the flight safer by itself — nothing about its presence changes what the autopilot does mid-flight. Its entire value shows up after the fact, when someone needs to know exactly what each system believed, in order, right up to the moment things stopped matching.

agent-benchmark-runner's divergence report plays the same role for two agent runs. It doesn't make agent B better at the task. It records, tool call by tool call, the exact point where agent B's sequence stopped matching agent A's, so a reader debugging the difference doesn't have to re-run both agents and stare at two transcripts side by side, guessing.

So what: a flight recorder and a divergence report earn their keep in the same moment — after something has already gone sideways, when a guess about where isn't good enough anymore.

Today's Rehearsal, Not an Outage

Today's code isn't a postmortem of a real failure — nothing in agent-benchmark-runner broke in production, because there is no production yet. It's a rehearsal: running the full pipeline end to end against a real task, the way a go-live checklist runs a launch sequence once, fully, before anyone points a spotlight at it.

The point of the rehearsal is the same as the point of the flight recorder analogy — if two agents disagree during tomorrow's launch demo, the report has to already show where, without anyone needing to add instrumentation after the fact. Today's integration run is the test that the recorder is actually recording, before it's asked to explain something that matters.

So what: rehearsing the pipeline end to end today is cheaper insurance than debugging a silent gap in the divergence report during tomorrow's launch post, when there's no time left to add it.

What Still Isn't Proven

The honest gap: today's rehearsal proves the pipeline runs end to end and produces a divergence report someone can read. It doesn't prove the report would catch every kind of drift — a subtler divergence, where both agents call the same tools in the same order but with meaningfully different inputs, is a harder case than the one this rehearsal exercised.

So what: "the flight recorder works" and "the flight recorder catches everything worth catching" are different claims, and only the first one is something today's rehearsal actually earned.
