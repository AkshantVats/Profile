Day 123 — Dedup at 1.5T/day — Bloom vs MinHash Tradeoff

Today's dedup pass compares a few thousand rows with a plain loop, and the code comment says exactly why that's fine at this scale. A design question worth working through anyway: what changes at Agoda's real 1.5T-events-a-day ingest, and why a Bloom filter and MinHash were never competing for the same job.

Today's code has a comment in it that I want to be honest about before writing another word: pkg/dedup.ClusterNearDuplicates compares every row against every other row, an O(n²) pass, and the doc comment says plainly that this is "acceptable for data-prep-pipeline's stated scale (a 30-day high-judge-score window)." A few thousand rows, all-pairs, no problem.

Scope note — a design walkthrough, not a system Agoda ran
Agoda's WhiteFalcon (the ~5-month Senior Engineer role covered in Building a TSDB at Agoda) does not run a deduplication layer I built or watched fail — it's a time-series database, not an event-dedup pipeline. What follows uses WhiteFalcon's real, documented numbers (1.5T Kafka events/day, the RoaringBitmap indexing layer, the cardinality incident's cost lesson) as the scale and the constraints for a question today's actual code raised: if that ingest volume ever needed a dedup pass, which data structure, and why. It's reasoning grounded in a real system's real numbers, not a claim that the system already answers this question.

The Same Question, Two Very Different Scales

The comment in today's code isn't hedging — it's precise. At a few thousand candidate rows, an all-pairs comparison is a few million signature comparisons, done in milliseconds. That's a real, considered engineering decision, not a shortcut nobody thought about.

Take the same dedup problem to WhiteFalcon's documented ingest rate and the arithmetic stops being reassuring. 1.5 trillion events a day is roughly 17 million events a second. An all-pairs comparison over even one second's worth of traffic is 17 million squared — not a bigger version of today's problem, a different problem that the same algorithm cannot answer at all.

So what: "does this design scale" is not a yes/no question about the algorithm in isolation — it's a question about which N you're plugging in, and today's dedup pass is correct precisely because it names its N out loud instead of assuming the answer generalizes.

What a Bloom Filter Buys You (and What It Costs)

A Bloom filter answers one question cheaply at any scale: have I seen this exact key before? It's a fixed-size bit array plus a handful of hash functions — inserting or checking a key is O(1) regardless of how many keys came before it, and the memory footprint is sized up front from an expected item count and a target false-positive rate, not from whatever traffic actually shows up.

That fixed-cost property is not a minor convenience at 1.5T events a day. It's the exact property the cardinality incident proved WhiteFalcon's team didn't have for free elsewhere: a pod label added to one fleet metric multiplied every existing series, and the cost of that one new dimension wasn't predictable from the dimension itself — it was the product of every other dimension already in play. The schema discipline that followed (a 10k label budget, mandatory cross-product analysis before any new tag) exists because an unbudgeted, multiplicative cost model is a production incident waiting for a trigger.

A Bloom filter's cost model is the opposite shape on purpose: size it once for the expected key count and the false-positive rate you can tolerate, and every insert after that costs the same. The false positive itself has a specific, bounded meaning — occasionally claiming a genuinely new event is a duplicate, at a rate you chose in advance. It never has a false negative: it will never claim a real duplicate is new.

So what: at a scale where an unpredictable cost model is the thing that already caused an incident, "a fixed memory budget with a knowingly tunable error rate" isn't just efficient — it's the same lesson the cardinality incident taught, applied to a different data structure.

What MinHash Buys You (and What It Costs)

A Bloom filter and today's ExactHash pass answer the identical question: is this exact byte string a repeat? Neither one can tell a reworded sentence from a genuinely new prompt, because neither one looks past exact equality.

That's precisely the question MinHash exists to answer instead: not "have I seen this exact string" but "have I seen something similar enough to count as the same idea." The cost is structurally different from a Bloom filter's, not just numerically larger. A Bloom filter check is one lookup against one shared bit array.

Answering "is anything already in my set within threshold of this new item" needs an actual comparison against candidates — today's code does that comparison as an honest all-pairs loop, and the doc comment names Locality-Sensitive Hashing banding (bucketing rows by a subset of their signature slots, so only same-bucket rows ever get compared) as the real answer once N stops being a few thousand.

So what: a Bloom filter and MinHash were never two ways to solve the same problem cheaper or more expensively — they answer different questions, and picking one over the other is picking which question your pipeline actually needs answered, not picking a winner.

The Tradeoff, Side by Side

PropertyBloom filterMinHash
Question answeredExact match, yes/noApproximate similarity, how close
False positiveRare, rate chosen up frontA near match below the real threshold gets clustered anyway
False negativeNever (for keys actually inserted)A real near-duplicate below signature resolution gets missed
Per-item costO(1), fixedO(shingle count) to hash, then O(candidates) to compare
Scales to 1.5T/day bySizing the bit array once for expected volumeLSH banding to avoid true all-pairs comparison

The false-positive row is the one worth sitting with, because it's not the same kind of mistake in the two columns. A Bloom filter's false positive is a probability you set at construction time and never revisit. MinHash's is a threshold you tune against real near-duplicate examples — today's code picked 0.4 after checking what a genuinely reworded prompt's signature actually looks like against an unrelated one, because the "right" threshold isn't a constant, it's an empirical fact about your data.

A false positive rate isn't a property of the algorithm. It's a number you're choosing to pay for, and what you're willing to pay depends entirely on what a wrong answer costs downstream.

So what: neither structure's false-positive rate is free to ignore, and neither is free to set once and forget — a Bloom filter's rate is a memory-vs-accuracy dial fixed at construction, MinHash's threshold is a data-vs-recall dial that needs re-checking whenever the underlying text distribution shifts.

Back to Today's Actual Scale

None of this changes what shipped today. data-prep-pipeline's dedup pass runs over a 30-day, judge_score > 80 slice of conversations — thousands of rows, not billions, and the honest engineering call was to ship the all-pairs comparison the current scale actually needs, with the LSH-banding upgrade path named in the code rather than built speculatively against a volume this pipeline doesn't see.

That's the same instinct the schema discipline after the cardinality incident encoded: don't budget for a scale you don't have yet, but don't pretend the current design generalizes past the scale you named it for, either. The two are not the same policy.

One says "build for now." The other says "know exactly where now stops being now."

So what: the design lesson isn't "always use a Bloom filter" or "always use MinHash" — it's that the right data structure follows from the question you're actually answering and the N you're actually answering it at, and both of those are worth writing down before the next order of magnitude arrives uninvited.
