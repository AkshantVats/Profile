Day 66 — Midnight Rollover Bugs

A window boundary that starts wherever the first event after reset happens to land isn't a rounding error — it's a slow drift, invisible in every test that doesn't specifically time a request against the clock.

Writing today's unit tests — cost-budget-enforcer's rollover-at-UTC-midnight test, specifically — I caught myself phrasing the assertion the way I'd have phrased a bug ticket seven years ago: "the window shouldn't start wherever traffic happens to land." That phrasing is a scar, not a design preference. I've watched a window boundary drift for exactly that reason before, on a system where the boundary mattered a lot more than a code review comment would suggest.

The bug class is almost insultingly simple to describe and easy to miss in practice: a counter that resets "at the start of a new window" has to decide what "start" means, and if that decision is whenever the first request after expiry happens to arrive instead of a fixed point on the clock, the boundary isn't fixed at all — it's wherever traffic put it last time. Every window after that inherits the previous window's drift, and the drift only ever grows.

Daily Rollups Have to Agree on What "Today" Means

At Walmart Labs, I architected the WeIoT SmartBuildings ingestion layer on Azure IoT Hub — seven million-plus sensors, tens of millions of telemetry points a minute, feeding real-time HVAC control loops on Azure Stream Analytics that automated energy optimization across fifty-plus global facilities. A lot of that optimization runs on a daily cycle: a facility's HVAC schedule ramps against a daily energy target, and the system that tracks "how much has this facility used today, against today's target" has to agree, unambiguously, on when "today" started and when it ends.

My contribution
I architected that ingestion layer on Azure IoT Hub and the Stream Analytics jobs that turned raw telemetry into the HVAC control loops driving energy optimization. Getting a per-facility daily rollup to agree with itself, across a fleet spanning that many facilities and that much telemetry volume, was a smaller-sounding problem than the ingestion layer itself — and a much easier one to get subtly wrong.

A daily aggregation window that's anchored to "whenever the first telemetry point after the last reset arrived" looks correct in every unit test that fires a fixed sequence of events at fixed offsets from each other, because that's exactly the condition under which a drifting boundary and a fixed one produce identical output. It only diverges from a fixed boundary when real traffic timing enters the picture — a facility that goes briefly quiet right at midnight, a retry storm that delays the "first" event by a few seconds, a deploy that restarts the aggregation job mid-window. None of those are exotic; all of them are exactly the kind of thing that happens somewhere, every day, across fifty-plus facilities.

So what: a test suite that only ever sends events at clean, predictable offsets from each other will never catch a boundary that drifts, because drift is a property of when things happen in wall-clock time, not a property of the sequence of events — which is exactly the blind spot a test has to be written specifically to close.

Why the Drift Compounds Instead of Canceling Out

The intuitive hope is that a boundary drifting a few seconds early one day and a few seconds late the next would average out over a month. It doesn't, because the drift isn't symmetric random noise — it's a one-directional function of whatever delayed the window's first event, and delays are far more common than early arrivals (a quiet period, a retry, a cold start all push the boundary later; almost nothing pushes it earlier). A boundary that only ever drifts later accumulates: day 1's rollup is a few seconds short of a true day, day 2 inherits day 1's drift and adds its own, and by the end of a month the "daily" rollup has silently become something closer to a 23-hour-and-change rollup that nobody configured on purpose.

For an energy-optimization loop, that's not a cosmetic bug. A rollup that's consistently short of a true 24 hours under-reports consumption against a facility's daily target, which either makes the optimization loop look better than it is or, worse, lets the loop keep ramping HVAC load past the point a correctly-measured day would have throttled it.

So what: a boundary that drifts in only one direction doesn't average out to zero — it accumulates, which means the bug gets harder to notice the longer it runs undetected, not easier.

The Fix Is the Same Two Lines, Twice

Today's cost-budget-enforcer module hit a smaller-stakes version of the identical decision. Its DESIGN.md describes a Redis hash tracking a window_start timestamp that gets set to "now" whenever a request arrives after the previous window expired — the same first-event-anchors-the-boundary pattern, just for a token budget instead of an energy rollup. Implementing it today, I changed that one detail: instead of storing when the window started, the window's identity is computed fresh on every call as floor(now / window_seconds) — an integer division against wall-clock time, not a value read back from state that some earlier request happened to set.

That one change removes the drift mechanism entirely, because there's no longer a "first event decides the boundary" step for traffic timing to perturb. Two UTC timestamps land in the same window if and only if they divide down to the same integer, full stop — a fact about the calendar, not a fact about which request happened to arrive first. The unit test that exercises this — a request at 23:59:59 and a request at 00:00:01 landing in different windows, deterministically, regardless of what either request's payload looks like — is the direct descendant of the daily-rollup bug I'd have wanted at Walmart: a test that specifically times events against a boundary, instead of only against each other.

So what: the fix isn't more code, more monitoring, or a wider test matrix — it's removing the one place where the algorithm let something other than the clock decide where a window starts, which turns an entire bug class into a fact you can assert in two lines.

What Transferred, and What Didn't

What transferred cleanly: the boundary itself has to be a pure function of time, never a side effect of traffic. What didn't transfer: at Walmart, "midnight" meant fifty-plus different local midnights across facility timezones, which made the aggregation layer's timezone handling the harder half of the problem — a detail a single, UTC-only Redis token budget doesn't have to solve at all, because every tenant's window resets at the same instant regardless of where the request came from. Today's fix is a strictly easier version of the same problem, and it's still worth getting right the first time, because the version of this bug that ships quietly is the one that only shows up in a monthly rollup nobody's watching closely enough to catch early.

A window boundary set by whatever request happens to arrive first isn't wrong every time — it's wrong exactly often enough to be worse than being wrong every time.

So what: a bug that's invisible under normal test timing and only surfaces under real traffic patterns is precisely the kind of bug worth writing a targeted regression test for the moment you recognize the shape of it — which is what today's TestWindowRollsOverAtUTCMidnight is, seven years and one very different system later.
