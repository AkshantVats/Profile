Day 131 — FinOps GPU — Finance Asked for Cost Per Model

Day 130's ticket was about correctness — whether a checkpoint could be trusted after a crash landed mid-write. This week's ticket asks something a distributed-systems argument can't settle on its own: what did this training run actually cost, and how honest can that number be when the CLI has no live price feed to ask.

Day 130's post closed on an honest gap: the checkpoint write-order fix was sound on paper, unverified against a real preemption. This week's ticket doesn't extend that thread at all — lora-trainer's Day 131 line reads "GPU $/hr × wall time → total; expose in CLI summary," and nothing about it is a distributed-systems problem.

It's an older question than any of this arc's checkpoint or quota posts: what does a system owe a stakeholder who wants a dollar figure, when the system genuinely has no live price feed to ask. That turned out to be a more interesting design question than the arithmetic suggests.

Scope note — real design pattern, illustrative premise
Wayfair's SPCS (Supplier Cost Service) — the real "net cost calculator" documented in the same pricing-system-architecture.md file Days 124–130 have already drawn on — genuinely aggregates multiple upstream cost inputs at production traffic. I didn't own SPCS personally; I'm citing its documented shape, not a system I built. Today's plan line reads "tagged cloud resources by model_id label" — I checked resume-extracted.md, the Agoda/WhiteFalcon doc, and all of pricing-system-architecture.md for GPU cost tagging or a model_id cost-attribution scheme, and none of them document anything like it at any employer. This post doesn't claim that happened anywhere. It's a design essay about the calculator this week's code actually built, using SPCS only as a real point of comparison for calculator complexity.

Two Cost Calculators, Two Orders of Magnitude

SPCS is a Python FastAPI service backed by its own Bigtable instance (supplier-cost-bt), running at roughly 2,800 queries per second on average and up to 4,200 at peak. It sits between UCMS's supplier cost updates and Delphi's price calculation, folding in PricingAlgo's ML-estimated shipping and revenue costs before handing a net cost downstream — a documented, multi-source aggregation problem.

lora-trainer/cost.py, this week's code, does none of that aggregation. One rate, one measured duration, one multiply: total = rate × (wall_time_seconds / 3600.0).

So what: the two systems answer the same kind of question — what did this cost — but SPCS earns its Bigtable-backed complexity from a dozen real upstream inputs, and a training-cost CLI with exactly one input has no such justification for building the same machinery.

The Design Decision: A Static Table, Not a Live Feed

OptionWhat it requiresWhy
Call a cloud billing API at run endA live cloud account, credentials, network accessRejected — this is an open-source CLI; it can't assume every user has a billing API to call
Require the operator to type a dollar figure by handNothing extraRejected — loses the "printed automatically in the CLI summary" requirement the ticket asks for
Ship a static $/hr table keyed by --gpu-type, with an override flagNothing beyond the CLI itselfChosen — zero external dependencies, a defensible default, and an explicit escape hatch

The table itself is small and says so in its own docstring: GPU_HOURLY_RATES_USD holds three entries — A100-40GB at $1.50/hr, A100-80GB at $2.10/hr, H100-80GB at $3.50/hr — described in the code as "an illustrative on-demand list-price table, not a live pricing feed or a specific vendor contract." resolve_hourly_rate() checks --gpu-hourly-rate first and only falls back to the table if no explicit rate was passed.

So what: the interesting decision here wasn't the multiplication — it was choosing which two of "flexible," "zero-dependency," and "accurate out of the box" to actually keep. This design keeps the first two and hands "accurate" to whoever passes a real negotiated rate through --gpu-hourly-rate.

Wall Time, Measured, Not Estimated

A taxi meter doesn't estimate a fare before the trip starts. It ticks elapsed time against a posted rate and prints a total the moment the trip actually ends — the fare is never wrong about what happened, because it was never a prediction to begin with.

train.py's main() does the same thing: it records start = time.monotonic() right after argument parsing, and computes wall_time_seconds = time.monotonic() - start only after the run — real or --dry-run — has actually finished. That's the same clock metrics.py's MetricsLogger already uses for tokens_per_second, reused rather than re-derived.

So what: measuring instead of estimating means the printed total is always right for whatever actually happened, at the cost of never being able to preview it before a run finishes — the meter can't quote a fare mid-trip, and neither can this CLI.

That last figure is real output, not a mockup: running the dry-run path locally against --gpu-type A100-80GB and five synthetic steps, the CLI printed lora-trainer cost: run_id=day131-smoke gpu=A100-80GB wall_time=0h00m rate=$2.10/hr total=$0.01. There's no GPU in this environment and no real training happened — that's ten seconds of dry-run wall time, not an hour of a real adapter training run, and the total scales accordingly.

Two Systems, One Question

SystemWhat it aggregatesWhere the number comes fromHow it stays current
SPCS (Wayfair)UCMS supplier costs + PricingAlgo ML estimates + PAS cost adjustmentsBigtable-backed production trafficMaintained continuously by the PPD Supplier Cost team
cost.py (this week)One GPU type, one measured wall-clock durationtime.monotonic(), measured locallyManual table edit, or --gpu-hourly-rate per run

So what: SPCS's complexity is proportional to how many real cost sources feed it; this week's calculator has exactly one input and one output, and matching SPCS's sophistication here would be solving a problem this CLI doesn't actually have yet.

What I Still Don't Know

The table assumes one GPU per run — a multi-GPU job would need its rate multiplied by device count, and nothing in cost.py does that yet. The table is also a snapshot that will drift from real market pricing the moment it's read, which is exactly why the docstring tells the reader to override it rather than trust it.

A real budget decision needs a real contract rate passed through --gpu-hourly-rate, not this table's default. This post doesn't have one to offer, because no real GPU training has happened in this arc yet.

So what: this CLI answers "what did this adapter cost" as honestly as a taxi meter answers "what did this ride cost" — exactly as accurate as the rate it was given, and openly so, which is a more honest claim than a system that hides the same uncertainty behind unlabeled precision.
