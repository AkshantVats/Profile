Today's code lives in a different repo and a different pair of hands: a same-day teammate is writing vllm-deploy-kit/DESIGN.md, a Helm values contract for tensor parallel size, KV cache sizing (gpu_memory_utilization, max_num_seqs, max_model_len), and an HPA (Horizontal Pod Autoscaler — the Kubernetes controller that adds or removes pods based on a metric) scaled on GPU utilization. My part of today isn't that document — it's the lesson underneath it. Every one of those values lives in a chart meant to run across more than one environment, and that's exactly the shape of problem I spent thirteen months operating at Delivery Hero, on a chart with nothing to do with GPUs at all.

A Blueprint Photocopied Onto Every Job Site

A construction blueprint gets photocopied once for every job site it applies to. Each site's foreman then pencils in the changes their site actually needs — a different foundation depth, a different utility hookup, a different setback from the property line. Nothing about that pencil mark is wrong on its own; it's a real, local difference the master blueprint was never going to capture.

The trouble starts later, when the architect revises the master blueprint and that revision has to reach twelve photocopies that have each already been marked up by a different hand. Nobody can tell, from looking at any single copy, which lines are the architect's and which are the foreman's — and the foreman for site four has no reliable way to know the master changed at all.

So what: a values file per environment behaves exactly like that photocopy, and the failure mode isn't the first pencil mark, it's the tenth revision nobody can trace back to a single source anymore.

What Route Service's EKS Deployment Actually Looked Like

What's documented, verified against the architecture doc
Route Service is documented as an EKS deployment stack, taking inputs from Order Service and Order SQS's lifecycle events (PICKED UP, PLACED, RIDER ENQUE, RIDER PICKED UP) and producing, together with the Revisit Order System, the Route { } object the UI reads. The chart itself and its exact environment layout aren't detailed beyond that in the architecture doc I have — what's documented is the service's data flow, not its Helm directory structure.
My scope — Global Logistics Platform, Delivery Hero, Jun 2022–Jul 2023
I scaled that platform to 1M+ daily orders on AWS EKS, holding 10k+ concurrent requests with zero downtime, and built the end-to-end rider tracking on top of OSRM that processed 5k+ real-time route updates a second. Operating at that concurrency, across the environments a logistics platform needs, is where I actually lived the values-file problem this post is about.

Today's plan frames the shape of that sprawl as "12 environments × helmfile" — a number I'm using to make the pattern concrete, not a documented count from the architecture doc, which doesn't itemize Route Service's exact environment list. What the doc does confirm is the part that matters: Route Service ran as an EKS deployment stack, and an EKS deployment stack with more than a couple of environments is where a values file stops being one file and starts being a family of files that has to agree with itself.

So what: the specific environment count is a framing device, but the mechanism it's illustrating — more environments than one person can hold in their head, all sharing one chart — is exactly what an EKS deployment stack like Route Service's runs into by construction.

The Values File Sprawl Pattern

Helmfile's usual answer to "more than one environment" is a base values.yaml plus a per-environment override file — values-staging.yaml, values-prod-eu.yaml, and so on — merged at deploy time. That structure is sound on its own. What breaks it in practice is that nothing stops an override file from setting a key that has nothing to do with that environment's real differences, because a merge command doesn't know which keys were supposed to vary and which weren't.

Once one override file redefines a key it didn't need to touch — a resource limit, a probe timeout, a log level — that environment silently stops inheriting future changes to the base default for that key. The base file gets updated, every environment's Helm diff looks clean on the surface, and the one environment sitting on a stale override doesn't show up as broken until its behavior visibly diverges from every other environment running the same chart.

So what: the sprawl isn't caused by having many environments, it's caused by override files that are free to touch any key at all — and the fix has to constrain that freedom, not add a thirteenth environment's worth of documentation explaining it.

What Actually Fixes It

The pattern that held up in production was narrower override files, not smarter ones. An override file was allowed to set replica counts, resource requests tuned to that environment's real traffic, and the ingress host — the things that are supposed to differ by definition. Anything else belonged in the base file, and a CI check that diffed each override against an allowlist of permitted keys caught the rest before merge, not after a rollout.

That allowlist is boring in the way good infrastructure discipline usually is. It doesn't prevent drift by being clever; it prevents drift by making the sprawled copies structurally unable to diverge on anything that wasn't supposed to vary in the first place.

So what: the lesson wasn't "write better values files," it was "make the sprawl impossible to grow past a fixed, reviewable surface" — a decision made once in CI, not enforced by memory across a dozen environments.

Where That Lesson Lands in Today's vLLM Chart

Today's vllm-deploy-kit DESIGN.md sets tensor parallel size, KV cache sizing, and an HPA that scales on GPU utilization instead of CPU — which needs a metric from DCGM-exporter (NVIDIA's per-GPU stats collector) surfaced through Prometheus Adapter (the bridge that lets a custom metric feed the HPA's decision), since the stock Kubernetes metrics-server has no idea a GPU exists. None of that is Route Service's problem restated with new nouns; it's a different service with the exact same override-surface question sitting underneath it.

A GPU value like max_num_seqs is even less forgiving of drift than a CPU resource limit was on Route Service, because a wrong value there doesn't just misbehave, it wastes an expensive GPU or OOMs a serving pod outright. The chart is meant to serve whichever model model-registry currently has marked stage == "production", resolved by that entry's artifact_prefix — one more reason the values contract needs the same allowlisted-override discipline Route Service needed, because the model behind the chart can change without anyone touching the Helm values at all.

So what: the bridge here isn't a metaphor, it's the same values-file-sprawl problem showing up on a chart that happens to point at a GPU instead of a rider-tracking pod — and the fix I'd reach for first is the one that already worked on Route Service: a base file, a narrow override allowlist, and a CI check that enforces the boundary instead of trusting a dozen people to remember it.

What I Still Don't Know

I don't know whether today's DESIGN.md actually specifies an override-key allowlist, or leaves that decision for whoever implements the chart after the design doc is approved. I also don't know Route Service's exact environment count or its full override-key list beyond what I've described here — the architecture doc I have documents the service's data flow, not its Helm directory structure, so I'm reasoning from the general shape of the problem, not from a file I've personally read.

So what: the pattern — one base file, a narrow allowlist, CI enforcement — is the part I'd stake this post on; the exact environment count either chart runs in is a detail I'm being honest about not having verified.
