Day 39 — The Tool That Ate Your Margin

At Agoda, attribution meant finding which label exploded the index. In tool-call-analyzer, it means finding which tool ate the LLM budget. Same question, same GROUP BY, different bill.

At Agoda, the WhiteFalcon indexing team never got a bill in dollars. Their bill was index memory: how many bits the inverted index consumed per metric, per label value. When a new Kubernetes label landed on a fleet metric, the index grew as the product of every existing label dimension — and the team found out when Grafana scrape latency crept up, not when the label was deployed.

The question that followed was always the same. Not “how big is the index now,” but “which single label is responsible for most of that growth.” That question needs per-dimension attribution, and attribution needs a cost model that can disaggregate a total into its contributors.

Today’s tool_stats_1m_mv and tool_cost_rollup_mv in tool-call-analyzer answer that same question for AI tool calls instead of time-series labels.

The attribution problem at Agoda scale

WhiteFalcon ingested roughly 1.5T events per day through Kafka into Rust consumers, which wrote into a Redis hot tier before compacting down to Ceph and S3. Series were indexed by a RoaringBitmap structure — the Agoda team’s design, not mine — where each distinct label value maps to the set of series IDs that carry it.

My scope at Agoda — WhiteFalcon indexing, ~5 months
I contributed to the cross-tier query engine (correct P95 merges across the Redis/S3 boundary) and added a new cardinality dimension — Kubernetes infrastructure tags — to the indexing layer, plus 2–3 new Grafana query types. The RoaringBitmap engine, the Kafka pipeline, and the storage tiering were the Agoda team’s design; I built on top of it as a contributing engineer, not its architect.

The reason attribution is hard here is that the cost of adding one label is never the label’s own bitmap size. It is that size multiplied by every other label dimension it intersects with.

A metric already carrying model_id (200 values) and tenant_id (500 values) sits at 100,000 series before you touch it. Add a 50-value pod label and the ceiling for that metric jumps toward 5,000,000 series — from one label addition.

Before adding the Kubernetes tag dimension, I ran that cross-product analysis by hand: a spreadsheet modeling label cardinality against existing series counts. There was no automated per-label cost attribution tool at the time. You estimated, and you hoped the estimate held.

It didn’t always hold for other teams. A pod label got added to a high-cardinality fleet metric by a team that owned the service but not the metric schema. Prometheus scrape duration crept up over several days.

The alert built to catch stack degradation was itself consuming too much resource to run reliably — it went dark before anyone noticed the underlying problem, and no alert fired until scrape targets started failing outright.

The lesson from that incident was never “stop adding labels.” Labels are how you slice a metric to find a problem in the first place. The lesson was that without a cost model telling you, after the fact, which label contributed which share of the growth, cardinality controls are just restrictions with no enforcement behind them.

The shape of per-dimension cost

DS analogy — the submetered apartment building
A landlord who bills every unit the same average electricity charge has no way to tell which apartment is running a space heater all winter. A submeter on each unit turns one shared bill into an attributed one — usage grouped by the thing that caused it. tool_cost_rollup_mv is a submeter for LLM spend: it groups cost by the tool and vendor that actually incurred it, instead of leaving the whole trace holding one undifferentiated total.

Good attribution answers one question: of everything you’re spending, what fraction came from each distinct contributor? In WhiteFalcon terms, that’s a rollup over the series catalog — series count per label value, times average bitmap memory per series. In tool-call-analyzer, it’s sum(cost_usd) GROUP BY tool_name, vendor over a time window.

Any cost attribution system is fundamentally a GROUP BY with a cost function attached. The sophistication lives entirely in how you define that cost function — not in the grouping itself, which is almost always the easy part.

The 40% duration alert works the same way as an outlier signal. A single tool consuming more than 40% of a trace’s wall time is disproportionate for a multi-tool agent, the same way a single label contributing more than roughly 30% of a metric’s week-over-week index growth was the signal at Agoda that something needed a closer look. The exact threshold is tunable; the shape of the signal — one contributor eating an outsized share — is not.

tool_cost_rollup_mv uses a SummingMergeTree because cost sums are additive and merge-safe: ClickHouse’s background merges accumulate partial sums automatically, so a dashboard query reads pre-summed aggregates instead of scanning raw rows. That’s the same reason WhiteFalcon’s hot-tier rollups favored pre-aggregation over recomputing from raw series on every query.

What made the Agoda incident preventable

The team that added the pod label owned the service emitting it, but not the metric schema it was writing into — schemas were shared infrastructure, and nobody ran the cross-product check before shipping. For a metric already at 100,000 series, a 50-value pod label pushed the ceiling toward 5,000,000. The index could absorb that; it just meant every future pod deployment added series silently, with no signal until scrape latency made it visible.

After the incident, the team added a series-count budget per metric, enforced at ingest by the Rust consumer. Each metric got a maximum series ceiling, and samples that would push a metric past its budget were rejected outright — with the rejection counted in a Prometheus counter, not silently dropped.

That counter is what made the fix actionable: series_rejected_cardinality_budget_total, incremented once per rejected sample, alerting on rate(...) > 0. Simple, binary, and pointed at the team that caused it rather than the team running the database.

Attribution wasn’t just reporting after the fact — it was the precondition for enforcement. You can’t cap cardinality per label until you know which label is responsible for what, the same way you can’t optimize a tool’s cost until you know which tool owns which fraction of the budget.

The same thinking applied to AI tools

An agent with several tools accumulates cost the same way a fleet of metrics accumulates label cardinality: unevenly, and usually invisibly until someone asks. Each tool call carries token spend, latency, and an error rate, and the agent’s owner rarely knows offhand which tool is responsible for most of it.

tool_cost_rollup_mv answers that directly — of all LLM spend in a given window, how much came from search_web versus bash versus code_interpreter. It’s the same structure as asking how much of an index’s memory came from pod versus model_id, just with a different unit of cost.

The 40% duration alert is the enforcement half of that same pattern: when one tool eats more than 40% of a trace’s wall time, it’s the AI equivalent of a single label pushing a metric past its cardinality budget, surfaced before it becomes a cost crisis instead of after.

One thing is genuinely different. AI tool cost is pay-per-call and easier to model up front than cardinality explosion ever was — you can estimate expected token spend per tool per call and set a ceiling directly. WhiteFalcon’s cardinality cost was harder to bound because it depended on the combinatorial interaction of every other label dimension already on the metric, not a single predictable rate.

Today’s code has its own version of an attribution gap: LangChain tool calls come back with cost_usd: 0, because LangChain doesn’t emit token usage the way OpenAI and Anthropic do. That’s not the tool being free — it’s the instrumentation being absent, the same way a service emitting metrics with no labels isn’t cheap, it’s just unmeasured. Treating a zero as “this is fine” instead of “this is unmeasured” is exactly the mistake that let the pod label slip through without a cross-product check.

A zero-cost entry in a dashboard is not proof something is free. It’s a gap in attribution wearing the shape of a good number.

The question Finance asks

At Agoda, when the index grew 40% in a month, Finance asked what changed. Platform couldn’t answer without per-label attribution already built — the incident forced a retroactive reconstruction, pulling audit logs and estimating each label’s share after the fact.

When an AI platform’s monthly LLM bill grows 40%, Finance asks the identical question. With tool_cost_rollup_mv already running, the answer is one ClickHouse query and about thirty seconds. Without it, the answer is days of log archaeology that still might not be accurate.

Build the attribution layer before the growth happens, not after. The moment you need it is exactly the moment you have no time left to build it.
