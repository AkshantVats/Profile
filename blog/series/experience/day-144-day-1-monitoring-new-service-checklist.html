Day 144 — Day-1 Monitoring — New Service Checklist

Today's own PR clones LensAI's dashboards for a freshly promoted fine-tuned model the moment it takes its first request, instead of waiting to notice a blind spot later. Wayfair's own Monitoring Coverage Matrix already shows what happens without that discipline: the highest-traffic service in the whole pricing platform turns out to be one of the least explicitly monitored ones.

Today's code in vllm-deploy-kit isn't a routing change or a Helm value — it's a claim about timing. LensAI clones the base model's dashboard for a freshly promoted fine-tuned model the moment that model takes its first production request, not after someone opens a ticket asking why nobody can see it. Wayfair's own pricing platform, across the two teams I led there, already shows what happens to a service that never got that treatment on day one.

A Building Doesn't Get Smoke Detectors After the Fire

DS analogy — the smoke detector every unit gets
A fire marshal doesn't sign off on occupancy and leave the detector wiring for later. Every unit in a new building gets the identical detector fitted from the same supply run and tested against the same checklist before anyone moves a couch in, regardless of whether that particular unit looks like the risky one. The detector isn't a judgment about that unit's fire risk — it's a standard fitting that goes in because the building has one, period.
What's documented, verified against the pricing architecture doc
Wayfair's Monitoring Coverage Matrix runs across the services in the domain I helped lead. gst-acc-promotions, averaging under 1 RPS, shows "yes" across nearly every signal — error rate, latency, CPU saturation, deployment health, synthetics, nine active monitors in total. PAS Core, running 3,400+ RPS average and roughly 295–366M hits a day, shows "no explicit" across most of that same row: no explicit error-rate monitor, no explicit latency monitor, no deployment-health monitor. The doc lists both facts side by side as a monitoring gap to close, not as a postmortem.

So what: the service carrying the platform's single largest blast radius if it degrades wasn't the one that ended up with the fuller checklist — the smaller, newer surface did, which is the opposite of what "monitor the risky thing first" would predict.

Why the Backwards Result Isn't a Mystery

Dashboards and monitors get attached to a service in proportion to how recently someone had the monitoring config open with a reason to touch it, not in proportion to the service's actual blast radius. gst-acc-promotions is under constant feature work — new cron jobs, new Pub/Sub fan-out paths, new GraphQL operations — and every one of those changes is a moment where adding one more monitor costs nothing extra, because the file is already open.

PAS Core is the opposite case. It's a mature GraphQL surface running at 295M+ daily hits with an error rate near zero, and nobody has had a reason in a long time to go back into a thing that, by every account, keeps working. Reliability is what starves a service of the checklist, because the checklist only gets applied when someone's already in there for another reason.

So what: "this is important, surely it's monitored" is exactly backwards for a service that's gone a long stretch without failing — staying up reads as safety, and that sense of safety is precisely what keeps anyone from reopening the monitoring config.

Today's PR treats a newly registered fine-tuned endpoint the way a building's fire code treats a new unit, not the way PAS Core's monitoring history treats a mature one. The moment RouteIQ's registry sees a new artifact_prefix, LensAI clones the base model's dashboard against the new model_id label and starts collecting from the first request — same panels, same alert thresholds, before any evidence exists to argue this specific model deserves them.

That's the whole point of a checklist over an instinct: it doesn't wait to find out whether the new thing turns out to matter, because PAS Core's own history says the decision to add monitoring "later" usually just doesn't get made.

So what: cloning the dashboard on day one isn't extra caution for a model that probably didn't need it — it's the one moment the decision is cheap, and after that moment passes, Wayfair's own numbers say it tends to stay unmade for years.

What I Still Don't Know

I don't know whether gst-acc-promotions' nine-monitor coverage was deliberate day-one policy or something that accumulated feature by feature over quarters of active work — the doc shows the end state, not the sequence that produced it. I led both the PAS and the Promotions/Discounts teams, but the monitoring doc itself is dated March 2026, so I can't say whether PAS Core's specific gaps have since been closed.

So what: the shape I'm confident in is the contrast the doc actually shows — one high-traffic service under-monitored, one low-traffic service thoroughly instrumented; exactly when each state was reached, and whether it's still true today, is a detail I'd rather leave open than guess at.
