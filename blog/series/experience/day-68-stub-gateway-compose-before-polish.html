Day 68 — Stub Gateway — Compose Before Polish

A pipeline whose stage order hasn't been proven yet doesn't need faster stages — it needs the order proven first, in a form cheap enough to throw away. RouteIQ's stub gateway and a pipeline lineage I once shipped small extensions into at Agoda both hold that discipline for the same reason.

Every module RouteIQ has shipped so far has been a single stage: semantic-cache-engine answers "have I seen this prompt," cost-budget-enforcer answers "can this tenant still spend." Neither one, on its own, tells you what a real request actually looks like, because a real request touches both — in a specific order, one that neither module's own tests could ever catch getting wrong.

Today's stub gateway is the first piece of RouteIQ that isn't a stage. It's the order the stages run in, written down as code and tested directly, with fake backends standing in for the real cache and the real model call.

An Order I Inherited, Not Designed

I spent about five months at Agoda as a Senior Engineer on WhiteFalcon, the team's in-house time-series database. By the time I joined, the pipeline's stage order was already fixed: Kafka ingest, then Rust consumers, then a Redis hot tier for the last few days of data, then a compaction path out to Ceph and S3 for everything older.

I didn't design that lineage — the Agoda team built the Kafka pipeline, the Rust consumers, and the storage tiering long before I arrived. What I contributed sat one layer up: extending the query engine to read consistently across the hot Redis tier and the colder Ceph/S3 tiers, and adding a new cardinality dimension the query layer could filter on.

My contribution — Agoda, Senior Engineer, WhiteFalcon TSDB, ~5 months
I extended WhiteFalcon's cross-tier query engine to read consistently across the hot Redis tier and the colder Ceph/S3 tiers, added a new cardinality dimension the query layer could filter on, and shipped two to three new Grafana query types on top of that extension — work scoped entirely above an ingest-to-storage lineage the Agoda team had already fixed before I joined.

That scoping wasn't a limitation I ran into by accident. It's the reason my extension could be correct on its own terms: the order underneath it — Kafka before Rust, Rust before Redis, Redis before compaction, compaction before Ceph — was never a question my query-engine code had to re-answer. If that lineage had still been in flux while I was extending the query layer, I'd have been optimizing a read path against a write path that might still change shape under it.

So what: a layer built on top of a pipeline is only as trustworthy as the assumption that the pipeline's own stage order is already settled — and that assumption is exactly the one RouteIQ's own stub gateway can't yet make for itself.

RouteIQ Hasn't Earned That Assumption Yet

semantic-cache-engine shipped its own lookup path on Day 62. cost-budget-enforcer shipped its own enforcement path on Day 66. Both are real, tested, and correct in isolation — and until today, nothing in this repository proved which one a request should hit first.

That's not a hypothetical gap. A cache lookup isn't free: a real semantic cache can cost an embedding-API call on a miss, the same way Agoda's Redis hot tier costs a real write on every ingest. Check the budget after the cache lookup instead of before it, and a tenant already over their limit still pays for every lookup — and every embedding call a miss would trigger — before finally getting rejected.

The Stub That Proves the Order

Today's pkg/gateway.Gateway.Handle runs three steps in a fixed sequence: check the tenant's budget, then look up the semantic cache, then call the model — and it returns immediately on a budget block, before the cache client or the model client is ever touched. The cache and model clients are interfaces with fakes behind them today, not real backends; RouteIQ's two modules stay separate Go modules for now rather than importing across that boundary before there's a reason to.

What makes this a real test and not a description is a spy standing in for both the cache client and the model client. The block-path test asserts that neither one is ever called when the budget check fails — not just that the response says "blocked," but that no downstream client method ran at all.

So what: a stub is honest about what it doesn't prove — a real cache hit rate, a real model's price — precisely so it can be fully trusted on the one thing it does prove: that a blocked request costs nothing, provably, not just by convention.

Why the Spend Stream Needed Three Sources, Not One

The gateway dual-writes every outcome to LensAI's ingest pipeline, and it uses three distinct source values instead of one shared one: real spend on a model call, zero cost on a cache hit, zero cost on a block. Collapsing those into a single row shape would erase the exact distinction the ordering exists to protect.

A cost dashboard built on a single undifferentiated source couldn't tell "the budget enforcer just saved money" from "the model is being called less for some other reason." Keeping the zero-cost paths explicit is what makes a claim like "order matters, wrong order leaks spend" checkable after the fact, from the event stream itself, instead of trusted on faith.

The fastest cache lookup in the world is still a bug if it runs before the budget check that was supposed to gate it.

What Today's Stub Doesn't Prove

The always-miss cache and the fixed price-table model in cmd/stubgateway are exactly that — stand-ins, not a production semantic cache or a real provider call. Wiring pkg/gateway.CacheClient to semantic-cache-engine's actual lookup path is real, deferred work, and it will surface questions a stub can't: what a cache-then-budget race looks like under concurrent requests, and whether a real embedding call's latency changes which order is still the right one.

None of that unwritten work is a reason to have skipped today's step. Proving the order first, cheaply, is what makes the eventual real-backend integration a matter of swapping an interface implementation instead of discovering — after the real cache and the real model are both wired in — that the sequence between them was never actually decided.

So what: composing the order before polishing any one stage isn't a shortcut around doing the real integration later — it's what keeps that later integration from having to re-litigate a question a cheap stub could answer today.
