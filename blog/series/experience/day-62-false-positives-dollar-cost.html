Day 62 — False Positives Have a Dollar Cost

A similarity threshold and a map-match confidence score answer the same question: how sure do you need to be before you serve an answer you didn't just compute. Get the threshold wrong in either direction and the failure isn't slow — it's confidently wrong.

A cache miss costs money: you fall through to a real inference call you could have skipped. A cache hit that shouldn't have been a hit costs something worse — it serves a wrong answer with the exact same confidence as a right one, and nothing about the response tells the caller which kind it got.

That asymmetry is why semantic-cache-engine's lookup path, which I built out today, spends more of its design on the threshold than on the lookup itself.

What Shipped Today

Day 60 designed the schema and the threshold policy. Day 61 built the embedding worker that fills the table. Day 62 is the first code that reads it: pkg/lookup.Lookup takes a tenant and a prompt, checks an exact prompt_hash match first, and only pays for an embedding call and a pgvector nearest-neighbor search when there's no byte-identical prompt already cached.

A candidate match only counts as a hit if its cosine similarity clears the tenant's configured threshold — pkg/config, defaulting to 0.92, overridable per tenant. A hit serves the cached response and posts a source=cache_hit event to LensAI's existing ingest pipeline, carrying the matched entry's prompt_hash as its trace ID. A miss returns nothing special; the caller falls through to a real inference call, same as if the cache didn't exist.

So what: the interesting design decision in a semantic cache was never the nearest-neighbor query — pgvector's hnsw index does that in a few milliseconds — it's the number you compare the result against before you trust it.

A Wrong ETA Is the Same Bet, Wearing a Different Name

I spent about a year at Delivery Hero in Berlin as a Senior Software Engineer on the global logistics platform, where I built end-to-end rider tracking on top of an OSRM cluster processing 5,000+ real-time route updates a second, on a system scaled to 1M+ daily orders and 10,000+ concurrent requests with zero downtime.

My scope — Delivery Hero, Berlin, Jun 2022–Jul 2023, Sr. Software Engineer, Global Logistics Platform
Rider tracking sits downstream of Order Service and Order SQS's lifecycle events (PLACED, RIDER ENQUE, RIDER PICKED UP), feeding an EKS-hosted Route Service and Route Consumers that call into the OSRM cluster to produce the Route object a customer's app renders as an ETA. That's the pipeline this section draws on — not a claim about which specific confidence threshold OSRM used in production, which isn't a number I have on hand.

OSRM's map matcher doesn't just find the nearest road segment to a rider's GPS ping — it scores how confident that match is, because GPS is noisy and a rider's raw coordinate can sit closer to the wrong parallel street than the one they're actually on. A map matcher, like a semantic cache, has to decide: commit to the best candidate and show it, or treat the match as too uncertain and fall back to something safer, like the last confirmed position.

So what: that's the same shape of decision semantic-cache-engine's threshold makes, just measured in GPS confidence instead of cosine similarity — commit too easily and you show a wrong answer with full confidence; hold out for certainty and you pay to recompute more often than you need to.

The Threshold Is a Bet, Not a Setting

Set a similarity threshold too low, and prompts that are topically close but intent-different — "delete my account" versus "how do I delete my account" — can collide, serving a wrong cached answer as if it were correct. Set it too high, and the cache rarely fires, which only costs money: a miss just falls through to a real inference call, the same path that runs when there's no cache at all.

ThresholdWhat it buysWhat it costs
Low (loose match)High hit rate, most inference calls skippedSilent wrong answers on topically-close, intent-different prompts
0.92 (shipped default)Conservative hit rate, biased toward "safe to serve"Some genuinely-reusable near-duplicates still fall through to inference
High (near-exact match only)Very low false-positive riskCache rarely fires; most of its cost benefit goes unrealized

That asymmetry — a false hit is a correctness bug, a false miss is a cost inefficiency — is why DESIGN.md §4 sets a false-positive budget of 0.1% of hits rather than just picking a threshold and moving on. A budget with a number attached is falsifiable; "the threshold feels safe" is not.

A slow answer is annoying. A confidently wrong answer is a support ticket, and the customer doesn't know it was a shortcut that failed — they just know the ETA was wrong.

So what: a threshold you can't measure against is a guess wearing a config value's clothes; a threshold with a budget attached is a promise you can check.

Making a Wrong Hit Diagnosable, Not Just Rare

DESIGN.md §3 originally proposed 0.94 as the default — a conservative number chosen before any hit could be traced back to the prompt that populated it. Today's implementation ships 0.92 instead, and the reason isn't that 0.94 was wrong; it's that the cache_hit event this lookup path now emits changes what "safe default" means.

Every hit's LensAI event carries trace_id=<matched prompt_hash>, so a wrong hit is no longer silent — it's auditable after the fact, the same way Delivery Hero's Revisit Order System keeps immutable snapshots of a Route object so a disputed ETA can be replayed and checked, not just trusted. A threshold tuned against "we can never look" has to be more conservative than one tuned against "we can look, and rarely have to."

So what: observability doesn't just help you find a bug after it happens — it changes how conservative you have to be before it happens, because "diagnosable" and "silent" are different risk profiles for the exact same wrong answer.

What This Doesn't Prove Yet

The honest gap: 41 of 41 unit tests pass — the exact-match fast path, the threshold comparison, the event emission, and the CLI all have coverage — but there's no live pgvector instance in this sandbox to run the -tags=integration tests against, and there's no real traffic yet to measure an actual false-positive rate for the 0.1% budget in §4. The lookup path is correct against a fake store; it hasn't been correct against a real one yet.

So what: "the unit tests pass" and "the false-positive budget is being met" are two different claims, and only the first one is true today — the second is what a live deployment with real traffic would have to prove.
