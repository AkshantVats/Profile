Day 111 — PagerDuty Routing Trees — Wayfair On-Call

A supplier's failed submission gets three retries, then an email. The platform's own database going unreachable gets a page inside the hour. Same shape of failure, two different audiences — and that difference is a routing decision no single alert threshold can make on its own.

A supplier's promotion submission fails and, three retries later, a system I helped architect sends them an email telling them to try again. A pricing engineer's database connection fails and, twenty errors later, the same system pages someone at any hour. Both are the platform refusing to accept a write it can't process — and the platform treats them as opposite-urgency events on purpose.

Scope note — Wayfair, PAS & Pricing/Promotions
I've been a Sr. Software Engineer III at Wayfair since November 2024, leading the PAS and Pricing, Promotions & Discounts teams. My resume documents architecting a GCP event-driven Global Pricing & Promotion Engine that reduced price propagation from hours to sub-seconds across 20k+ suppliers, and a high-throughput bulk processing framework handling 250k+ SKU updates per supplier at 99.99% availability. The alert-routing table and failure-handling mechanics below are documented architecture from that system, not a single dated incident I'm narrating — I'm describing how the platform is built to decide who gets told what, not one specific night it told someone.

One Failure Shape, Two Audiences

Zoom out far enough and a failed promotion submission and a failed database connection look like the same event: something downstream rejected a write. Zoom in and they're not the same event at all — one is a supplier's input the platform can't yet accept, the other is the platform's own infrastructure being unavailable to anyone.

A single "did this fail" boolean can't tell those two apart. Answering "who needs to know, and how urgently" requires knowing whose resource failed, not just that something did.

So what: the routing decision has to happen before the alert fires, not after — which means it has to live in the alert's definition, not in whoever happens to be reading a dashboard when it goes red.

The Routing Table Underneath

Wayfair's pricing platform encodes that decision as a severity ladder, and every monitor is tagged onto a rung of it before it ever fires:

P1Service down → immediate page
P2Degraded → Slack, page on escalation
P3Warning → Slack, monitor only
P4Info → Slack, no escalation

A database connection failure past its threshold is tagged straight onto the on-call rotation's PagerDuty service — it's the platform's own resource, unreachable for anyone, so it starts at the top rung immediately. A throughput anomaly or an elevated-but-not-critical error rate lands in a team Slack channel first, with PagerDuty only reachable if someone escalates it by hand.

So what: severity isn't a property of the metric that crossed a threshold, it's a property of who owns the thing that broke and how many people it's currently blocking — and that has to be decided per rule, not inferred from the number alone.

Why a Supplier Gets an Email, Not a Page

A promotion submission that fails validation against the downstream pricing service gets retried three times with a fixed delay. If it's still failing after that, the project is marked failed and an email goes out to the supplier who submitted it — they retry manually, or an internal admin bulk-resubmits later. Nobody on the on-call rotation is paged for this by itself.

That's not the platform being careless about a real failure. It's closer to a courier who, after three missed-delivery attempts, leaves a note on the door instead of calling the recipient at midnight — the failure is real and the recipient needs to know, but nothing about it requires waking someone up right now, because the fix is on the supplier's side and it can wait for business hours.

So what: an async, non-paging notification isn't a lesser response to the same failure — it's the correct response to a failure whose remedy doesn't depend on an engineer doing anything at all.

Why the Same Shape of Failure Pages an Engineer

Contrast that with the database connection failure threshold — more than twenty connection errors in an hour trips a monitor that goes straight to PagerDuty, on the weekly on-call rotation, no Slack-first grace period. The submission pipeline in front of it is the same code path a supplier's failed promotion travels through; what differs is which side of the request broke.

A database being unreachable isn't one supplier's problem to retry around — it's blocking every supplier's traffic simultaneously, and no amount of manual resubmission from any of them fixes it. Only an engineer with access to the database can, so an engineer is who gets paged, immediately, regardless of the hour.

The same submission pipeline, failing two different ways, produces an email in one case and a page in the other — because urgency tracks who can fix it, not how the failure looks on a graph.

So what: two failures that are statistically identical — a spike in rejected requests — get routed to completely different audiences, and a rule that only asks "did the count cross a threshold" has already lost the information needed to make that call.

What a Threshold Alone Can't Say

DriftWatch's own alerting, before today, is a single-severity threshold: driftwatch-drift-events.yaml fires severity: warning to one Slack channel every time a drift event is recorded, with no escalation step and no distinction between a segment's first alarm this week and its fifth unacknowledged one today. That's the same gap a bare gt 0 condition leaves in any alerting system — it can say that something crossed a line, never who should hear about it, how loudly, and what happens if the first notification is ignored.

Wayfair's routing table answers that with people and Slack channels, hand-configured per monitor. Today's code asks the same question for DriftWatch's alerts, but wants the answer to be data a rule can carry, not a wiki page an engineer maintains by hand: a rule's escalation field is an ordered list of steps, each with its own delay and its own audience, so "notify Slack now, then page if nobody's acted in thirty minutes" is one YAML document instead of institutional memory.

So what: a routing tree like Wayfair's on-call ladder isn't extra polish on top of a working alert — it's the part of the alert that decides whether the right person finds out in time, and it's exactly the part a rule DSL (a small, purpose-built configuration language, here for defining alert rules) has to model as a first-class field, not bolt on after the threshold already fired.
