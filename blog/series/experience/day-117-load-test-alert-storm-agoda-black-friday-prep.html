Day 117 — Load Test Alert Storm — Agoda Black Friday Prep

The alert built to catch WhiteFalcon degrading was the first thing to go dark when label cardinality exploded — nobody had load-tested the alerting path itself. Today's 100-rule DriftWatch storm test is that lesson applied, and I want to be upfront about exactly which parts of this post are Agoda's documented history and which are today's code.

Every alerting system I've worked on has one blind spot nobody schedules time for: testing whether the alerting path itself survives the exact conditions it exists to catch. WhiteFalcon's own history at Agoda has a real example of that blind spot going wrong, and it's the honest anchor for today's post. I want to separate, clearly, what's Agoda's documented incident and what's today's DriftWatch code before going further.

Scope note — Agoda, WhiteFalcon
I was a Senior Engineer contributing to WhiteFalcon, Agoda's in-house time-series database, for about five months. The Agoda team designed and built the core system — the RoaringBitmap inverted index, the Kafka ingest pipeline, the Rust consumers, the Scala query engine, the Ceph/S3 tiering. My own contributions were narrower: extending the cross-tier query engine to merge histograms correctly across the Redis/S3 boundary, and adding a new Kubernetes-tag cardinality dimension to the index. The cardinality incident below is real and documented; the "Black Friday Prep" framing and the 10× scale-up are today's post connecting that lesson to today's DriftWatch code, not a claim that this specific storm test ran at Agoda.

The Alert That Went Dark

WhiteFalcon's own production history includes a case where Prometheus scrape duration crept upward while request rate stayed completely flat — the two numbers should move together, and they didn't. The root cause traced back to a pod label added to a fleet metric: every new pod multiplied the number of distinct series that metric produced, and cardinality does not grow linearly with the number of labels added, it grows as the product of every distinct value across every dimension.

The part that made it a real incident, not just a slow query, is what happened to the alert meant to catch it. No alert fired until scrape targets started outright failing — the alerting path degraded from the same underlying pressure it was supposed to detect, and it degraded first.

So what: an alert that shares fate with the system it monitors isn't really a safety net, it's a second copy of the same failure mode wearing a different name.

What "Ready" Meant After That

The schema discipline that followed is well documented: cross-product analysis required before adding any new tag, a hard 10,000-label budget per metric, and an explicit justification requirement for any high-cardinality label like pod or experiment_id. That discipline is real, and it's the direct ancestor of "readiness" as a peak-traffic-season practice — Black Friday-scale review windows, broadly, are when a platform re-checks whether its schemas, its indexes, and its dashboards will hold under load nobody sees on an ordinary Tuesday.

What that discipline doesn't cover, on its own, is the alerting path's own behavior under that same load. A 10k label budget keeps one metric's index from ballooning; it says nothing about whether the rule engine watching that metric can still evaluate every rule, dedupe correctly, and page the right person once traffic (and therefore cardinality, and therefore alert volume) actually spikes.

So what: schema discipline is necessary and was genuinely earned the hard way, but it answers "will the data stay queryable," not "will the alert on top of the data stay correct" — those are different questions with different failure modes.

Stress-Testing the Bridge Before Opening It

Engineers load-test a new bridge with a convoy of fully loaded trucks, driven back and forth, before the public ever crosses it — not because anyone doubts the math, but because the math describes the design, and a load test describes the built thing under the actual forces it will face.

The distinction matters here for the same reason: reviewing a rule DSL's dedupe-window math on paper (the design) is not the same claim as running a hundred of those rules concurrently and counting what actually got dispatched (the built thing under load). One is proof the design is sound; the other is proof today's specific code, running concurrently, still behaves the way the design says it should.

So what: a system can be correctly designed and still fail for reasons only concurrency and scale surface — a shared mutex nobody profiled, a map nobody expected 100 goroutines to hit at once — which is exactly what a load test, and only a load test, can rule out.

What Today's Storm Test Actually Proves

alert-rule-engine/storm_test.go is DriftWatch's version of that truck convoy: 100 rules, each its own tenant, each flapping true/false every simulated minute for a simulated four-hour storm, run concurrently against one shared evaluator and one shared dispatcher — not one evaluator per rule, the same shared objects a real deployment wires once. That's the 10× cardinality this post's subtitle refers to: every prior test in this module drove one rule, one tenant, one segment at a time.

Without dedupe, that same flap pattern sends a notification on every true tick — 12,000 across the storm window. With the 30-minute dedupe window Day 112 built, it sent 800: bounded, roughly one page per rule every 30 minutes, exactly what the window's own math predicts, holding under 100-way concurrent access to shared state.

So what: the number that matters isn't 800 on its own, it's that 800 is close to what the design predicted and nowhere near the 12,000 an unbounded storm would have produced — that gap is the concurrency-safety claim actually getting tested, not just assumed.

The Honest Bridge

I want to name the seam directly rather than let it blur: WhiteFalcon's cardinality incident is a real, documented piece of Agoda's production history, discovered after the fact, not prevented by a prior load test of the alerting path. Today's 100-rule storm test is DriftWatch code, run in this sandbox, proving a different system's dedupe logic holds at a scale no prior day tested.

The connective tissue between them is a pattern, not a shared incident: an alert is only as trustworthy as its own tested behavior under the load it will actually see, and WhiteFalcon's history is where I learned that the hard way, watching an alert go quiet at the exact moment it mattered most.

So what: borrowing the shape of a lesson from one system to justify testing a different one is honest; presenting one system's numbers as if they were measured on the other isn't, and this post is deliberately written to avoid that second thing.

What This Doesn't Prove

The storm test's throughput number — roughly 307,000 evaluations per second — times an in-process Go function call against an in-memory fake notifier. It says the evaluator and dedupe logic are not the bottleneck at this scale, and nothing more than that.

It says nothing about SlackNotifier or PagerDutyNotifier's real network latency under the same 100-way fan-out, because no real HTTP round trip happened in this test — that would need a live run, or at minimum an httptest server standing in for both channels under the same concurrent load, which today's test doesn't include.

So what: "the dedupe logic holds at scale" and "the whole notification pipeline holds at scale" are two different claims, and conflating them is exactly the kind of gap that let WhiteFalcon's own alert go dark once — naming the difference here is the discipline that incident actually taught me.
