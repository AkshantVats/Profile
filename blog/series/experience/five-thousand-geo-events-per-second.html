The support ticket said the rider was on the wrong street. The map showed him three blocks away. Both were rendered from the same pipeline — and both were defensible given what each system had seen in the last thirty seconds.

Nothing was on fire. No error budget breach. Just geometry that did not match someone's memory of where a courier should be during dinner rush. That is the class of incident textbooks barely name: the stream is healthy, the contract is ambiguous, and the label set you need to debug it was optional six months ago.

I worked on Delivery Hero's logistics platform from 2021 through 2023 — rider tracking, map-matching, and the routing plane that turns GPS noise into something a customer can trust. What follows is my scope on that stack, not the entire Delivery Hero Group. Public numbers exist to calibrate scale; they are not a claim that I personally operated every order worldwide.

The System I Was Debugging at 8pm on a Friday

Friday-night pages rarely start in OSRM. They start in the gap between fulfillment state and geometry work.

Customers and riders talk to an Order Service backed by an Order Data Service. When an order moves — placed, picked up, rider enqueued, rider picked up — the service publishes lifecycle messages to Order SQS: PLACED, PICKED UP, RIDER ENQUE, RIDER PICKED UP. Riders publish here too. That bus decouples "what happened to the order" from "what should we compute on the map."

Downstream, Route Consumers drain those events and fan work into a Route Service cluster, which calls an OSRM cluster backed by a road-graph store. OSRM is stateless CPU; durable trip state lives elsewhere. The output contract is Route JSON — the polyline, distance, and metadata support and apps render. A Revisit Order System reads immutable route snapshots when someone disputes "where was the rider?" Order Service also ships rows to GBQ for analytics. An Order Mapping Service sits in the wider ecosystem; I touched it, but the hot path I owned was stream shape + map-matching under load.

The design choice that saved us on-call sanity: routing work is async and keyed off explicit lifecycle transitions, not every GPS tick. Geometry still runs hot — but the bus tells you why a match was requested.

Five Thousand Adjustments Per Second — What Counts as an Event

Resume scope for the pipeline I built: 5,000+ geo-events per second at peak, on a logistics platform handling 1M+ daily orders in my slice. That is not "five thousand orders per second." It is the fan-out of rider GPS, map-match requests, route revisions, and downstream notifications — often multiple logical events per fix when raw and matched coordinates both flow.

I owned throughput and correctness on the rider-tracking / map-matching path — not middle-mile VRP, not the full global order book. Sustained 5k events/s is plausible for a large multi-market slice: active riders × GPS frequency × (raw + matched) fan-out. Single-node OSRM match benchmarks are tens of ops per second; production uses clustered osrm-routed, batching, and queues — compare laptop numbers to the diagram, not to my peak.3

Sanity check without over-claiming: 5,000 events/s for a day is ~432M events — large, but not absurd if you count every adjustment on a busy regional fleet. The honest sentence is always two numbers: what I operated, and what the company publishes.

Partition Keys, Hot Riders, Dinner Rush

Throughput is a schema decision before it is a cluster size decision.

We keyed the geo stream by rider_id (and market) so a single courier's fixes stayed ordered. That is correct for map-matching — you cannot reorder GPS retroactively without inventing physics. It also creates hot partitions: one rider circling a dense block during rain, or a staging lot with hundreds of couriers, can pin a shard while neighbors look idle.

Dinner rush does not raise the average. It raises the skew. P99 on the fleet mean is a vanity metric when one partition is sixty seconds behind and the support UI is showing stale geometry for exactly the riders customers are watching.

Partition for correctness first. Then instrument per-shard lag like your refunds depend on it — because they do.

SQS States — When Routing Work Actually Fires

Not every GPS point deserves a route recompute. Lifecycle messages bound the work:

  • PLACED — order exists; baseline route expectations.
  • PICKED UP — merchant handoff; geometry assumptions change.
  • RIDER ENQUE — courier assigned; matching intensifies.
  • RIDER PICKED UP — rider en route; customer-facing ETAs tighten.

Consumers translate those states into Route Service calls. Miss an enqueue event and you optimize the wrong trip. Double-process one and you may emit two Route JSON revisions with different distances — support picks whichever renders last.

At-least-once delivery is not a footnote here. It is why idempotent route writes and immutable snapshots in the Revisit Order System matter as much as OSRM latency.

OSRM Cluster — Match Latency, Radius, Backpressure

OSRM's /match API snaps noisy GPS to the road graph. Production is a cluster with a shared graph build — not a laptop container. Match radius, gap handling, and batch size trade accuracy for CPU. Under load, the failure mode is not always timeout; it is confident wrong — a plausible polyline on the wrong parallel road.

We backpressured at Route Service when OSRM p95 drifted: shed non-critical recomputes, coalesce fixes per rider, and never let unbounded queues hide lag from dashboards. Educational benchmarks on a single osrm-routed worker (~15–63 match ops/s in public threads) explain why async queues exist; they are not your dinner-rush capacity plan.3

Labels Before Benchmarks

A P99 without region, map_dataset_rev, and client_version is a story about someone else's outage.

Map data updates silently change match outcomes. A/B app builds send different GPS sampling rates. Comparing this Friday to last Friday without labels is how you "optimize" a regression. We treated observability dimensions like schema fields — required on the span, not optional query hints.

That discipline is the bridge to what I build on LensAI today: OTel spans on the ingestion path tag the same dimensions I'd use to debug a map-matching pipeline under peak dinner rush — tenant, model, batch boundaries, failure class — before I trust a percentile.

Silent Wrong — Dupes, Skew, Clock Skew

The failures that hurt are quiet:

  • Duplicate GPS — at-least-once replay inflates distance; ETAs lie without a single 500.
  • Partition hot spots — one shard lags; the mean looks fine while specific riders are wrong.
  • Missing map_dataset_rev — you cannot tell if the graph changed or the code did.
  • Clock skew — fixes arrive out of order; matchers guess; support sees time travel.

Same family as Seven Million IoT Sensors and When Percentiles Lie: green dashboards, wrong decisions.

G-03 — ClickHouse Writer on the Same Muscle

On the laptop stack in infra-ai-streaming, goal G-03 is the Go consumer's ClickHouse batch writer: flush at 1000 events or 500ms, three insert retries, then per-event DLQ. A circuit breaker opens after five consecutive insert failures, waits 30s, half-opens on retry, and drains Redis overflow when closed. Metrics I actually scrape: kafka_records_processed_total, clickhouse_write_errors_total, clickhouse_batch_size, clickhouse_flush_duration_seconds, circuit_breaker_state{state}, redis_overflow_depth, dlq_events_total.4

Route Consumers and a CH writer differ in domain. They agree on backpressure: never commit offset ahead of durable handoff, never hide lag behind an unbounded buffer, and never debug a global P99 when one partition is on fire.

The Thing That Stayed With Me

Incidents fade. What stays is respect for the contract between event, geometry, and what the UI is allowed to show. Five thousand events per second do not need heroics. They need honest scope, partition-aware observability, and Route JSON you can replay when someone's ice cream — or dinner — is late.
