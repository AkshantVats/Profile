Day 112 — Debounce Duplicate Alerts — Agoda Kafka Consumer Bug

A consumer-lag alert on Agoda's Kafka pipeline fired the same warning 400 times in about ten minutes during a routine consumer-group rebalance. The fix wasn't a bigger alert budget — it was giving the alert a notion of "is this still the same episode" it never had.

Scope note — Agoda, WhiteFalcon TSDB
I contributed to Agoda's WhiteFalcon TSDB pipeline for about five months as a Senior Engineer — the cross-tier query engine extension, a new Kubernetes cardinality dimension in the index, and, per my own resume, some work on the Kafka pipeline components feeding it. I did not design the Rust consumers, the Kafka topic layout, or the consumer-group rebalance strategy — those are the Agoda team's system. What follows is a bug in how an alert on that pipeline's own lag metric behaved, not a change to the pipeline it was watching.

A Routine Rebalance, Four Hundred Pages

WhiteFalcon's Rust consumers read from Kafka and write into the hot-tier Redis buckets, and a Grafana rule watches their consumer-group lag the way consumer-latency-zscore-anomalies.yaml watches query latency elsewhere in the stack. During a consumer-group rebalance — a normal, self-healing Kafka event where partitions get reassigned across consumers — lag briefly spikes as the reassigned partitions catch back up.

That spike oscillated a few hundred milliseconds either side of the alert's threshold for close to ten minutes. Every time it crossed back over, the rule fired again: roughly 400 identical warnings in that window, the same rebalance producing what looked, from the paging channel, like 400 separate incidents.

So what: nothing about the underlying system was actually unhealthy for those ten minutes — the alert was the thing behaving badly, not the pipeline it was watching.

Two Different Gaps, One Bug Report

The instinct is to call this "add a debounce" and move on, but that undersells what was actually missing, which is two separate things a single fix has to cover. The first gap: the rule had a threshold, but nothing like Grafana's own for field — no requirement that the condition hold continuously before it counts as real, so a single noisy sample could fire it.

The second gap is the one that actually produced 400 pages: even a rule with a proper sustained-true check has no memory of whether it already told someone about this exact episode five seconds ago. Each time lag dipped back under the threshold and rose again, the rule treated it as a brand-new alarm, because nothing in its state distinguished "still the same rebalance" from "a fresh problem."

So what: a threshold answers "is the condition true right now," and that is a materially different question from "have I already told someone about this," and conflating the two is exactly what turns one rebalance into 400 pages.

The Debounce Window, Taught Properly

The actual fix has two parts, one for each gap above. Part one is unremarkable: require the lag to stay over threshold for a fixed window — five minutes, say — before the rule is allowed to fire at all, which throws out a single-sample blip the same way Grafana's for field already does for any provisioned alert.

Part two is the one that actually stops the storm: once the rule does fire, it remembers when it last notified anyone, and it refuses to notify again for the same alerting segment until a fixed window — thirty minutes, in this case — has passed since that last notification. Crucially, that memory has to survive the condition clearing and re-triggering, or a flapping metric defeats it by resetting the clock on every flap.

A doorbell with a proper debounce circuit is the same idea in hardware: press it fifty times in a row and it rings once, then goes quiet for a fixed cooldown no matter how many more times a finger taps the button, because the circuit already knows someone is waiting at the door. The rule needed exactly that cooldown, keyed to "this alert, this segment," not to the raw count of times the doorbell got pressed.

So what: debounce isn't "ignore the alert for a while" — it's giving the alert a clock that tracks when it last spoke, independent of how many times the underlying condition flickers past its threshold in the meantime.

What This Buys DriftWatch's Alert Rules

This is the identical shape of problem DriftWatch's own alert-rule-engine needed to solve for its escalation rules, and today's code builds exactly that: a per-(rule_id, tenant) state machine that requires a condition to hold for a configured duration before it fires, then debounces further notifications within a thirty-minute window that survives a resolve-and-refire cycle the same way the doorbell's cooldown does.

A flapping drift signal without that debounce would hammer DriftWatch's FineForge retrain webhook (the endpoint an escalated rule calls to trigger a model retrain) the same way the Agoda lag alert hammered its paging channel — the failure mode transfers cleanly from a Grafana-provisioned threshold to a YAML-defined rule DSL, because the underlying gap (no notion of "still the same episode") is the same gap either way.

So what: this bug wasn't really about Kafka, or Grafana, or lag specifically — it was about any alerting system that can say a condition is true right now but can't say whether it already told someone, and that gap shows up wherever a threshold gets automated.

What a Debounce Window Doesn't Fix

A thirty-minute debounce window stops the storm, but it isn't free. Tune it too wide and a second, genuinely distinct alarm that happens to fall inside that window gets silently swallowed along with the duplicate noise it was designed to suppress — a real problem twenty minutes after the first one can look, from the paging channel, exactly like the debounce doing its job correctly.

Thirty minutes is a chosen tradeoff point for this rule, not a provably optimal one, and it doesn't fix the rebalance's brief lag spike either — that's still Kafka behaving normally under a routine operational event, not a bug to be engineered away.

So what: the debounce window fixes who gets paged and how often, not what actually happened on the pipeline — and mistaking a quiet alerting channel for a healthy system is its own kind of trap, just a quieter one than 400 pages in ten minutes.
