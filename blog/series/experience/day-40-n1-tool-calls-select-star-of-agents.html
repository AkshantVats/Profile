Day 40 — N+1 Tool Calls — The SELECT * of Agents

At Walmart, seven million sensors hammering Azure IoT Hub at once taught me what fan-out amplification looks like at 3am. In tool-call-analyzer, the same shape shows up as an agent calling search_web four times for one question.

The first time I saw N+1 in production, it wasn’t in a database. It was in a firmware update. We’d push a config change to seven million sensors on Azure IoT Hub, and every device on the network would independently poll the cloud API to check whether it had one waiting.

Seven million HTTP calls landed in the first ninety seconds. Azure IoT Hub’s rate limiter didn’t care that each call was legitimate — it just saw a thundering herd and started dropping requests. We fixed it with edge pre-aggregation: filter and batch at the edge before the cloud ever sees the traffic.

Fifteen years of distributed systems later, I’m building TraceForge, and agents have the same problem. An agent calls search_web four times in a row, each call unaware of the others, each burning tokens and adding latency.

The pattern has a name. The fix has been known since the ORM wars of 2008. We just haven’t applied it to LLMs yet.

My role — Walmart Labs, WeIoT SmartBuildings Platform, Aug 2018–May 2021
Software Engineer II on the ingestion layer for a platform automating HVAC control loops across 50+ global facilities via Azure Stream Analytics, on top of 7M+ sensors sending tens of millions of telemetry points per minute through Azure IoT Hub, plus the edge-to-cloud OTA firmware framework that pushed config updates to those same devices.

The thundering herd on Azure IoT Hub

When a firmware config update went out to the WeIoT SmartBuildings platform, the OTA framework sent a push notification to every affected device: there is an update, check now. Every device interpreted that literally. Tens of thousands of devices in the same facility, all sharing the same network egress, hit the Azure IoT Hub HTTP endpoint at once.

No single device was doing anything wrong. Each one followed its protocol correctly. But the aggregate behavior was indistinguishable from a denial-of-service attack, and the rate limiter treated it exactly that way.

This is fan-out amplification: one event at the producer becomes N events at the consumer. In database terms it’s N+1 — one query returns N records, and then N queries fetch related data for each one. The shape is identical, and so is the root cause: every consumer acts independently, with no awareness of what the others are doing at the same moment.

Fan-out amplification never looks like a bug in any individual component. It looks like a capacity problem, and blaming the rate limiter for it is like blaming a database for slow N+1 queries. The fix belongs in the architecture, not the infrastructure underneath it.

The edge pre-aggregation fix

The OTA framework was redesigned around a two-tier check. At the edge — a local gateway per facility — devices registered their current firmware version with a local coordinator. When a config push arrived, the coordinator asked one question on their behalf: which devices in this facility actually need this update?

Instead of fifty thousand individual HTTP calls from one large facility, the coordinator sent a single batched request listing the roughly 3,200 device IDs that actually needed it. Azure IoT Hub saw one API call instead of fifty thousand, and the thundering herd disappeared entirely.

DS analogy — the permission slip
A school with fifty thousand students all needing a signed permission slip has two ways to collect them. The N+1 way: every student walks to the principal’s office individually. The batched way: the teacher collects every slip in the classroom and delivers one stack. Same total information, a fraction of the trips.

The coordinator itself had to be fault-tolerant, because the complexity didn’t vanish — it moved. If it crashed mid-update, devices could be left half-updated with no record of who’d already received the push.

We solved that with coordinator state persistence in Azure Cosmos DB, checkpointed per device ID, so a crashed coordinator could resume without re-pushing to devices that had already updated. Edge pre-aggregation is an architectural pattern, not a specific technology; the tools are replaceable, but the insight — aggregate before you fan out, not after — is not.

The same pattern in agent traces

An agent given a research task — find recent papers on attention mechanisms in transformers — calls search_web("attention mechanisms transformers 2024"), reads the result, then calls search_web("self-attention transformer papers"), reads that, then calls search_web("multi-head attention recent research"). Three sequential searches, overlapping in intent, none of them batched.

The model doesn’t know that three separate tool invocations for related queries is expensive. It’s just following its own reasoning chain, one step at a time, the same way each IoT device correctly followed its own protocol.

The agent is the firmware coordinator that never got the pre-aggregation fix. Each call is independent, each one burns tokens, each one adds latency, and the total cost is N times a single call’s cost when a smarter design would make it one batched call. The structure is identical to the fan-out at Walmart; the fix is identical too — detect the N+1 pattern, then either batch the calls or redesign the tool to accept multiple inputs at once.

At Walmart the thundering herd was immediate: fifty thousand calls in ninety seconds, impossible to miss. In an agent, N+1 is diffuse — four tool calls spread across two seconds of reasoning, repeated across thousands of daily invocations, each instance too small to notice on its own.

The patterns that broke distributed infrastructure in 2018 are reappearing in AI agent infrastructure in 2026. The context changed — LLM token budgets instead of IoT rate limits — but the underlying shape didn’t.

What today’s code does about it

traceforge graph --trace-id <id> reads every tool call span for a trace from ClickHouse, builds a dependency graph with spans as nodes and parent-child relationships as edges, and runs cycle detection and N+1 analysis over it. The report is one line when it finds something:

N+1 alerts (threshold=3):
  ⚠  search_web called 4 times — possible N+1 pattern

That single line is what six weeks of OTA redesign work at Walmart eventually distilled into: a signal that says this call pattern is costing more than it should, before the bill makes that obvious on its own.

The threshold is 3, matching the consensus from ORM lint tools like Django’s nplusone and Rails’ bullet. One call is intentional, two might be a retry, but three sequential calls to the same tool inside one trace almost always represents a loop that should have been a batch.

The CLI reports after the fact, which is a real limit — the eventual goal is pre-flight detection: analyze an agent’s planned tool calls before executing them, flag the pattern, and let the agent restructure before it spends anything. That’s the edge coordinator for LLMs, filtering before the calls hit the API instead of after. Today’s code builds the detection layer; the prevention layer is a later day.

The lint rule that doesn’t exist yet

Every serious ORM ecosystem has an N+1 lint tool. Django has nplusone, Rails has bullet, Laravel has its debug bar warnings. They fire in development, the moment the pattern appears, instead of waiting for production traffic to teach the same lesson the expensive way.

Agents have nothing equivalent today. If an agent calls the same tool twelve times inside one trace, the only signal is the invoice at the end of the month — no lint rule, no dev-mode warning, no topological view of the call graph showing you the fan-out as it happens.

traceforge graph is the first step toward closing that gap: detect the pattern in a completed trace. The next step, a materialized view over the same ClickHouse adjacency data, turns it into a metric — N+1 rate per agent persona, per tool, per hour — so a spike tells you a new agent behavior is generating expensive fan-out before it shows up on the bill.

Lint rules don’t prevent bugs by being clever. They prevent bugs by being early, and the earlier N+1 is caught in an agent’s tool use, the cheaper the fix. The infrastructure for that earliness is what today’s code starts building.

Seven million sensors taught me that no individual call has to be wrong for the aggregate to be a disaster. Agents are about to relearn that lesson one token bill at a time.
