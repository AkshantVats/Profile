Day 119 — Month 4 Recap — Platform Story for Recruiters

Four connected products > four READMEs. TraceForge, RouteIQ, alert-rule-engine, and DriftWatch share a Dispatcher and an eval pipeline instead of duplicating them — this post names exactly where that reuse lives, and exactly what's still config-verified rather than run.

Month 4 of this build ends today, and the honest recruiter question isn't “did you write thirty blog posts” — it's whether the four Go modules that came out of that window add up to one coherent platform story or four unrelated side projects with good READMEs. I want to answer that directly, using only what's actually shipped: TraceForge, RouteIQ, alert-rule-engine, and DriftWatch, in the order they connect to each other.

Scope note — this repo's own products, not an employer story
Today's post narrates this build's own four products and their actual current state, not a past company engagement — the same self-referential convention Day 118 used for its own launch-readiness review. Nothing below borrows a scale number or a specific incident from Agoda, Wayfair, Delivery Hero, or Walmart.

Four Products, Not Four Side Projects

TraceForge (agent-trace-collector) is the first link: it ingests and stores traces, giving the rest of the stack somewhere real to read from instead of guessing at production behavior. RouteIQ (routeiq-launch) reads what TraceForge sees and turns it into routing and cost decisions — which model handles a given request, and at what price. alert-rule-engine takes a routed decision or a traced metric that crosses a threshold and turns it into a page, first to Slack, then to PagerDuty if nobody acknowledges it.

DriftWatch is the fourth link, and it's the one that closes the loop: it watches the quality of what's being routed, not just whether it's up, and — staged, not yet live — can ask for a retrain when quality keeps sliding. Each of these four is a real, independently shippable Go module with its own README, its own tests, its own CI run. None of them needs the others to build or pass its own test suite.

So what: independently shippable is not the same claim as connected — a recruiter skimming four separate repos has no way to tell the difference from the READMEs alone, which is exactly the gap the rest of this post exists to close.

The Sentence That Makes It a Platform

The sentence that actually makes these four a platform, and not four READMEs, lives in the code, not in this post's framing of it. DriftWatch's retrain webhook fires through the exact same alert-rule-engine Dispatcher that Days 116 and 117 built and load-tested — the component that decides who gets notified, on which channel, and how often before it gets throttled. DriftWatch doesn't ship its own notification system; it reuses the one that was already proven, two days earlier, to hold up under 100 concurrent rules.

The same reuse runs upstream. DriftWatch's drift-detector module watches a score stream for sustained drift using a CUSUM chart — a control-chart method that only flags a change once it accumulates past a threshold, so one noisy data point can't trigger a false alarm on its own — and that score stream is fed by the same shadow-traffic-and-eval pipeline this build started building around TraceForge's trace ingestion. A platform, in other words, is what you get when the fourth module's input and output both point back at work the first three modules already did.

A car's dashboard makes the same point physically. Four gauges — speed, fuel, engine temperature, oil pressure — could each be sold as a standalone gadget clipped onto the wheel, and each would work fine on its own. What makes them a dashboard instead of four gadgets is that they're wired into the same electrical system and the same sensor bus, so a change registered by one shows up correctly on another without anyone rewiring the car.

So what: the shared Dispatcher and the shared eval pipeline are this repo's wiring — the part that turns four gauges into a dashboard, and it's the part a README screenshot alone can't show.

What Staff Judgment Actually Looks Like

Today's code deliverable is DriftWatch's product essay, and its most interesting sentence isn't a feature claim — it's the one about the retrain webhook. The webhook is built and tested end to end against a stand-in for FineForge, the not-yet-built retraining system on the other end of it, and deliberately left wired-but-not-live: nothing in this build currently lets a drift alarm actually trigger a retrain without a human approving it first.

That's the decision I want to name directly, because it's the one a Staff-level hiring loop is actually screening for. Anyone can wire an alarm to an action; the harder skill is knowing which automations are safe to trust unattended on day one and which need a track record first, and then saying so plainly in a README instead of quietly shipping the safer version while the essay implies the fully automated one.

A fire sprinkler system is plumbed the same way before it's trusted. The pipes run to every room and the heads are mounted and pressure-tested, but the valve to the main water line often stays closed for a stretch after installation, until an inspector signs off — because the cost of a false trigger, a room full of water, is worse than the cost of a short delay before the system goes fully live.

So what: the retrain webhook staying wired-but-not-live isn't an unfinished feature, it's the same kind of judgment call — and the instinct to leave a powerful automation switched off until it earns trust is the same one I've watched more senior engineers apply on real production systems, long before this build existed.

The Recruiter's Actual Question

Zoom out from any single module and the real question a hiring committee is asking becomes clearer: not “can you write Go,” which four green CI badges already answer, but “can you see the whole system you built, including the parts you chose not to build yet.” Thirty-plus days of consistent posting is evidence of discipline. It is not, on its own, evidence of that.

The evidence for that is closer to what's actually in this post: a webhook that reuses an existing Dispatcher instead of shipping a second one, a CUSUM input that reuses TraceForge's trace pipeline instead of building a parallel ingestion path, and a retrain trigger left off by design rather than by accident. Four repos that share components instead of duplicating them is a specific, checkable claim, not a slogan.

So what: “four connected products” only means something if a reader can go verify the connection in the code — this post names the exact files and days where that verification lives, on purpose.

What's Verified and What Isn't

A recap making an honesty pitch has to survive being honest about its own gaps, so here they are without softening. This sandbox has never had a reachable Docker daemon — not on Day 88's RouteIQ launch, not on Day 118's DriftWatch checklist, and not today — so none of the four products' container images has ever actually been build-verified end to end in this environment.

Today's other code deliverable, the four-product docker-compose.yml that wires TraceForge, LensAI, RouteIQ, and DriftWatch together behind one --profile driftwatch flag, passed docker compose config — which confirms the YAML is well-formed and every referenced service resolves — but nobody has actually run docker compose up against it, because there's no daemon in this sandbox to run it on. That's a real limitation on the platform claim, not a rounding error.

So what: a recap that says “we verified the config parses” instead of “we verified it runs” is doing the same thing the retrain webhook does — stating exactly how far the verification actually went, instead of letting a green checkmark imply more than it proved.

What Month 4 Actually Proves

None of this makes DriftWatch, RouteIQ, alert-rule-engine, or TraceForge a finished product — each one still has its own open BENCHMARKS.md caveats, its own “not yet measured against a live broker” line, its own list of what a human still has to do manually. What Month 4 actually proves is narrower, and I think more useful to a reader deciding whether to trust the rest of this build: reuse compounds here instead of resetting on every new product.

The next module doesn't start from zero. It starts from a Dispatcher that already survived a 100-rule storm test, a CUSUM pipeline already wired to a real trace source, and a habit of writing down exactly what's proven versus assumed before calling anything done.

So what: a platform story isn't the absence of gaps — every module here still has them — it's a codebase where each new piece makes the next one cheaper to build honestly, and that compounding is the actual thing four separate READMEs can't show.
