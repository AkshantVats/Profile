Supplier APIs and Token Buckets — Wayfair's Real Circuit Breaker

Rate limits that survived 10× surprise load

AS
Akshant Sharma
May 2026
11 min read
Experience Series · 6 of N

The supplier feed was supposed to plateau at 2,000 requests per minute. That was the contract — handshake agreement, nothing enforced. On the Tuesday before a major promo, one supplier pushed 22,000 in sixty seconds. The pricing API didn't crash, but response times tripled, and three other suppliers started timing out on their own feeds. Nobody paged because no error counter spiked. Latency did.

The problem wasn't the burst. The problem was that we had no mechanism to say "slow down" that the client could actually respond to. The pricing service accepted everything, queued everything, and degraded for everyone. The system had no way to be honest about who gets served and when.

The Token Bucket as a Fairness Contract

Think of a token bucket as a contract between the server and the caller: you get N tokens per time window, one token per request. If you have tokens, your request is accepted. If you don't, you get a 429 Too Many Requests with a Retry-After header that tells you exactly when to come back. That header is the part most teams skip — and without it, a 429 is a rejection without guidance. The client guesses whether to retry in one second or sixty, and guessing under load produces retry storms.

We keyed buckets on supplier_id. Each supplier got an independent allocation in Redis, evaluated with a Lua script so the check-and-decrement was atomic. One supplier burning through their tokens didn't touch another supplier's bucket. That isolation was the entire point — because the incident that started this work was one noisy supplier degrading everyone else's experience.

Team scope

Wayfair's pricing API served 250,000+ SKUs across hundreds of suppliers. The bulk validation path, the supplier ingestion pipeline, and the upstream pricing core were team-owned systems.

My contribution

I built the per-supplier token bucket rate limiter in Redis, defined the 429 + Retry-After contract, implemented the circuit breaker on downstream pricing failures, and made the fail-open decision when Redis went unavailable.

The Lua script ran inside Redis — single-threaded, no race conditions. The caller saw one of two outcomes: proceed, or wait. We made the rejection self-documenting because supplier integrations are managed by third-party teams who read JSON before docs:

{
  "error": "rate_limit_exceeded",
  "supplier_id": "supplier_8821",
  "retry_after_seconds": 12,
  "tokens_remaining": 0,
  "bucket_refills_at": "2026-05-19T14:32:00Z"
}

When the Downstream Dies

Token buckets handle the inbound side — too many requests from a caller. But the pricing core could die independently. If we kept sending accepted requests into a dying downstream, the queue would grow unbounded and the 202 we returned would become a lie. So we added a circuit breaker: it tracked error rates over a sliding window, and when failures crossed a threshold — five consecutive timeouts, or 50% error rate in 30 seconds — the breaker opened. All requests got a 503 immediately, without touching the downstream.

The combination mattered. The token bucket said "you're sending too much." The circuit breaker said "the thing behind me is broken." A client seeing 429s should back off and retry. A client seeing 503s should stop entirely. Conflating the two is how you get retry storms against a service that's already drowning.

Same Pattern, Different Payload

So when I built the same thing for inference events on LensAI, the design decision was identical — only the partition key changed. Instead of supplier_id, the bucket key became tenant_id. The contract was the same: per-tenant token budgets in Redis, 429 + Retry-After for honest rejection, and the same fail-open decision when the bucket store disappeared. Redis Lua scripts don't care what string you partition on. What transferred was the philosophy: rate limiting is a product interface, not something you bolt on after the first incident.

The X-Tenant-ID header on the inference pipeline aligns with the Kafka partition key, which aligns with the ClickHouse sort key. The identity you rate-limit on should be the identity you partition on, because they answer the same question — whose traffic is this, and how much of the system does it consume?

429 vs 503 vs Silent Drop

The response code isn't just a status — it's an instruction to the client about what to do next. Get it wrong and you've turned a recoverable overload into a cascading failure.

ResponseMeaningClient actionRetry storm riskObservability
429You're over budgetWait Retry-After, then retryLow (guided backoff)High — explicit, countable
503Service is brokenStop, wait for recoveryMedium (depends on client)High — circuit state visible
Silent dropNothing — request vanishesRetry immediately (no signal)Severe — unbounded retriesZero — invisible failure

Silent drops are the worst outcome. The caller doesn't know the request failed, so retry logic fires immediately. You've turned one request into five, and each of those five generates another five when they also vanish. A 429 with Retry-After is the cheapest circuit breaker you can build — it delegates backoff to the client.

When Redis Dies: The Fail-Open Tradeoff

So we had per-supplier buckets in Redis, and they held. But the next question was obvious: what happens when Redis itself goes away?

This is where fail-open gets uncomfortable. Without the bucket store, you have two choices: block everyone (fail-closed, which means a Redis blip is a full outage) or admit everyone (fail-open, which means a Redis blip is a fairness holiday). We picked fail-open — because a degraded system that serves requests is more recoverable than a dark system that serves nothing.

The reasoning was specific: Redis outages were transient — seconds, occasionally minutes. During that window, suppliers' own send rates are bounded by their ingestion pipelines, so the blast radius was "unfair for a few minutes," not "unavailable for everyone." Fail-closed would have made Redis a hard dependency on every request path. A five-second restart would mean five seconds of zero throughput. For a pricing API that feeds downstream catalog pages, dark is worse than degraded.

We logged redis_rate_limit_degraded as a metric with a dedicated alert. The alert wasn't "something broke" — it was "fairness is off." That distinction mattered for on-call triage. A fairness-off alert means "watch for noisy neighbor effects." A hard-down alert means "drop everything." Different urgency, different runbook.

Rate limiting without a fallback store is a decorated denial-of-service. CHAOS.md scenario 3 exists because this lesson transferred.

What We Did Not Do

Global-only throttle. A single rate limit shared across all suppliers would punish small suppliers for large suppliers' behavior. One noisy caller burns the global budget; everyone else gets 429s they didn't earn. Per-supplier isolation was non-negotiable.

Fail-closed without ops buy-in. Making Redis a hard dependency would have required an HA cluster with a defined SLA and an on-call rotation that included Redis expertise. We didn't have that. Fail-open was the honest choice given the infrastructure we actually operated.

Unbounded retry without jitter. Early supplier integrations retried on any non-200 immediately. Under load, that turns a 429 into a thundering herd at the exact moment the bucket refills. We required exponential backoff with jitter, and the Retry-After header made compliance measurable — diff the 429 timestamp against the next request timestamp per supplier.

The Interface That Stayed

Years after leaving Wayfair, I still build rate limiters the same way. Not because the implementation is clever — Lua scripts in Redis are table stakes — but because the contract is right. A 429 with Retry-After tells the caller three things: you're over budget, here's when to come back, and this isn't an outage. That shapes how clients behave, how retry logic works, and how on-call engineers triage at 2 AM.

The cardinality problem was about what you index. This one is about what you reject. Both are about honesty — telling the system's consumers what's actually happening, instead of letting them guess from a dashboard that may or may not reflect reality.

Fairness is measurable. You can graph the moment one tenant's 429s spike while another's throughput stays flat. What you can't graph is the alternative — the silent overload where every tenant degrades together and nobody knows who to throttle first. That's why the rate limiter isn't ops tooling. It's a product interface.
