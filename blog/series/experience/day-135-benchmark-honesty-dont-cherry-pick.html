Day 135 — Benchmark Honesty — Don't Cherry-Pick 10 Prompts

The fastest way to make a new adapter look good is to run it on ten prompts you already half-know the answer to. Wayfair's pricing team never had that shortcut available to them at any sample size that mattered, and it shaped how I built today's batch runner: score the whole held-out set, or don't call it a score.

The plan line for today pairs a title with a specific number: "Wayfair pricing eval used 2k SKU sample minimum." I went looking for that figure in the context docs before writing a word of this post, because a specific number is exactly the kind of detail that's easy to invent and easy to get caught inventing.

Scope note — what's documented vs. what the plan line implies
No context doc I have access to states a "2k SKU minimum" sample-size rule for Wayfair pricing evaluation — I checked pricing-system-architecture.md for it directly and didn't find it. What is documented, and what this post actually draws on, is more useful than a round number anyway: PAS's Experiments adjustment type targets an explicit population of the catalog (the architecture doc's own example is "10% of SKUs in a category"), assigned by a deterministic hash of SKU ID rather than by hand. That's the real mechanism behind today's post, not the number in the subtitle.

The Ten Prompts That Feel Like Enough

Every adapter-training story has the same tempting shortcut at the end: run the new model on a handful of prompts you already have opinions about, read the outputs, and decide it's better because the outputs you looked at got better. It's not dishonest exactly — it's just a sample size chosen by how much patience is left at the end of a long day, not by what would actually let you trust the answer.

The failure mode isn't that ten prompts are always wrong. It's that ten prompts you picked, after training, tend to quietly become ten prompts the new model happens to do well on — not because anyone's cheating, but because a person skimming outputs stops skimming once they've seen three or four that confirm what they were hoping to see.

So what: a benchmark that only reports what a person chose to look at isn't measuring the adapter. It's measuring how persuadable the person doing the looking was that day.

A Pricing Run Never Got to Cherry-Pick

Wayfair's pricing experiments couldn't get away with the equivalent shortcut, and the reason is structural, not cultural. An Experiments adjustment set targets a defined population — the architecture doc's example is 10% of SKUs within a category — and which SKUs land in that population is decided by a deterministic hash of SKU ID, not by a pricing manager picking the ones expected to respond well.

ApproachWho picks the sampleWhat it actually measures
Cherry-picked demoWhoever's presenting the result, after seeing early outcomesHow good the best-looking cases look
Hash-assigned populationA deterministic function of ID, fixed before results existHow the change performs across the population it's meant to cover

Deterministic assignment isn't a bigger sample for its own sake — it's a sample nobody can quietly shrink toward the flattering end after the fact, because the assignment rule was fixed before anyone had a result to be tempted by.

So what: the thing that made Wayfair's pricing experiments trustworthy wasn't a specific SKU count. It was that the population was picked by a formula, not a preference, and the formula ran before any outcome existed to bias it.

Why Today's Runner Scores Everything It's Given

The batch inference runner I shipped today takes whatever prompt list the held-out set hands it and calls three runners — the adapter under test, the base model, and a GPT-4o reference — on every single one, writing one row per (prompt, runner) pair to Parquet. There's no code path that samples a flattering subset, and no argument that lets a caller pass in "just the first ten."

That's a direct, deliberate answer to the cherry-picking problem: the easiest way to stop a person from eyeballing ten favorable outputs and calling it done is to make scoring the whole set no harder than scoring ten prompts would have been. A runner that batches the full list costs about the same wall-clock effort per prompt as a small hand-picked sample would — so there's no longer a convenience argument for the smaller, biased one.

So what: benchmark honesty isn't a promise people keep through willpower. It's a property of the tool, and today's tool makes the honest path the fast path.

What I Still Don't Know

The runner produces rows, not scores — the metrics that turn those rows into exact-match, judge, and latency numbers per DESIGN.md §3 are a later ticket, so there's no real result to report yet from a real held-out set. I also don't know yet how the runner behaves once the held-out set is genuinely large; every test against it so far has used a small synthetic prompt list, and "no cherry-picking allowed" is easy to promise at ten prompts and harder to keep cheap at ten thousand.

So what: today's honesty is structural, not proven under load. The real test of whether scoring everything stays the fast path is what happens the day the held-out set stops being small enough that skipping it was never even tempting.
