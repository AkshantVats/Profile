Day 125 — Data Quality Dashboards — Walmart Sensor Null Rates

Today's dataset_manifest.json buckets a training export by token count, script, and task_type so a broken slice shows up as a shape change instead of hiding inside a healthy-looking average. WeIoT SmartBuildings' real 7M-sensor fleet needed the identical instrument for a different kind of broken slice.

Today's CLI mode doesn't clean anything. dataprep dashboard reads the same rows Day 123's dedup step already wrote and produces one file, dataset_manifest.json: a token-count histogram, a script-based language mix, and the exact task_type label distribution. Nothing in that file fixes a bad export — it only describes one.

That's the entire point of a distribution dashboard, and it's easy to undersell in a design doc: an aggregate number like "40,000 rows, average judge score 0.87" can look completely healthy while one slice of that export — one task_type, one script, one length bucket — is quietly broken. A manifest's job is to make that slice visible before a training run finds it the expensive way.

Scope note — a real system I built, an illustrative scenario I'm reasoning through
I architected the WeIoT SmartBuildings ingestion layer at Walmart Labs on Azure IoT Hub — 7M+ sensors, tens of millions of telemetry points per minute, feeding real-time HVAC control loops via Azure Stream Analytics across 50+ global facilities, plus the fault-tolerant edge-to-cloud OTA firmware framework that kept config syncs reliable for millions of distributed devices under intermittent network conditions. Those are the real system and the real numbers. The specific scenario below — a null-rate spike in one firmware cohort surfacing a bug roughly two days before it caused a visible HVAC failure — is an illustrative worked example built from that system's real failure surface (a device going quiet under bad firmware is exactly the class of problem the OTA framework existed to catch), not a claim that this exact timeline is a specific incident on record.

The Failure an Average Can't See

Picture a building's HVAC system reporting temperature every thirty seconds from a hundred sensors. If five of those sensors go quiet for an hour, the building-wide average temperature barely moves — ninety-five readings still arrive on schedule, and the control loop that averages across the floor doesn't notice five missing inputs the way it would notice one wildly wrong one.

A quiet sensor isn't a loud failure. It's a null where a number used to be, in a dataset that's still 95% intact and still looks fine from the top.

Today's manifest has the same blind spot by design if you only look at the top-line count. Forty thousand rows with a healthy average judge score can still contain one task_type whose prompts are all getting truncated by a broken exporter, or one script whose rows are all one bad batch job's garbled output. The aggregate doesn't lie — it just doesn't look where the problem is.

So what: a dashboard that only reports totals is a report, not a diagnostic — the whole reason to bucket by token length, script, and label instead of just counting rows is that a broken slice is invisible until you look at slices.

WeIoT SmartBuildings' Real Version of the Same Question

The WeIoT ingestion layer answers a structurally identical question at a much larger scale: is every device cohort still reporting the way it's supposed to, or has one silently gone quiet. At 7M+ sensors and tens of millions of telemetry points a minute, a handful of missing devices moves the fleet-wide ingestion rate by a fraction of a percent — nothing a top-line dashboard would flag, and nothing a duty engineer glancing at "ingestion rate: nominal" would catch.

The instrument that catches it is the same shape as today's manifest: slice the incoming stream by a dimension that actually varies — firmware version, device model, facility — and watch each slice's null rate independently, the same way dataset_manifest.json watches each task_type's row count and each script's share independently instead of trusting one dataset-wide average.

That's precisely the gap the fault-tolerant OTA firmware framework exists to close on the other end: devices under intermittent network conditions need reliable config syncs specifically because "device went quiet" has to be recoverable, not just detectable. A per-cohort null-rate view is the detection half of that same problem — it can't fix a bad firmware push, but it can point at exactly which cohort needs the fix pushed first.

So what: "slice by the dimension that actually varies, and watch each slice on its own" isn't a training-data-specific idea — it's the standard answer anywhere a fleet-wide average is large enough to hide a cohort-sized problem.

What a Fleet-Wide Average Would Miss

Here's where the shape of the failure matters more than the top-line number. A firmware bug that causes a device to intermittently drop its telemetry payload doesn't announce itself as a hard failure — the device is still online, still responding to health checks, just silently missing a growing fraction of its readings. Sliced by firmware version, that shows up early: one cohort's null rate climbing while every other cohort's stays flat.

Not sliced — averaged across the whole fleet — that same climbing null rate on one firmware cohort can stay statistically invisible for days, especially if the affected cohort is a minority of the fleet. By the time the failure is loud enough to show up in a facility-wide average (an HVAC loop actually misbehaving because it's control-looping on stale or missing readings), the root cause is a firmware bug that's been silently degrading a slice of the fleet the whole time. A per-cohort dashboard is the difference between finding that bug from a null-rate chart and finding it from a facilities complaint.

The training-data version of the same gap is smaller in stakes but identical in shape: a broken exporter silently truncating one task_type's prompts doesn't crash the pipeline, and it doesn't move the dataset's average judge score enough to trip any threshold. It shows up as that one task_type's token histogram collapsing toward the shortest bucket — visible in a slice, invisible in an average.

So what: the cost of not slicing isn't "you miss a rare edge case" — it's that the failure mode a slice-level dashboard exists to catch is, by construction, exactly the kind that doesn't move the number you'd otherwise be watching.

The bottom row is the point worth sitting with, same as it was for yesterday's stratified split. Slicing isn't a heavier system bolted onto a simpler one — in both cases, the field you slice on was already sitting in the schema. The dashboard's whole cost is deciding to look at it independently instead of folding it into one number.

A dashboard that only reports the total row count answers "how much data do I have." A dashboard that reports it per slice answers "which part of my data is lying to me" — and only one of those questions catches a silent failure before it's loud.

So what: the value of a manifest isn't the numbers it reports at the top — it's that reporting them per slice turns a question nobody was asking ("is task_type X still healthy?") into one the dashboard answers automatically, every run.

Back to Today's Actual Manifest

pkg/dashboard.Build ships exactly this shape: three independent slices — token-count bucket, dominant script, task_type — each with its own row count and share, computed over the whole export before Day 124's train/eval split is applied. None of the three numbers are exact in the tokenizer-accuracy sense (the histogram buckets a whitespace word count, and the language mix buckets a Unicode script, both documented as approximations in the package's own doc comment rather than presented as more precise than they are) — but exactness was never the point. A slice that's collapsed toward one bucket, or gone from three scripts to one, or lost a task_type entirely, is visible at a glance regardless of whether the underlying count is a real BPE token or a word.

That's the same tradeoff the WeIoT null-rate view makes: a per-cohort null percentage doesn't need to be perfectly calibrated to be useful. It needs to move visibly when a cohort actually breaks, and stay flat when nothing has — a coarse instrument watching the right slice beats a precise one watching only the aggregate.

So what: neither dashboard's job is to be exact. Both exist to make one question answerable at a glance — "did any one slice just change shape" — that a single top-line number can never answer, no matter how precisely it's computed.
