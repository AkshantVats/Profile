Platform economics · control plane vs data plane · the DH real-time config bridge

The number that changed how I think about SaaS tooling wasn’t in an incident post-mortem — it was in a quarterly infrastructure cost review, in a row labeled “Feature Flag Evaluations.” The number wasn’t large in absolute terms. It was large relative to what the service was doing: evaluating a single flag per request, in a service that handled 1,000 requests per second around the clock.

That is 2.6 billion monthly active context evaluations. At enterprise pricing, this becomes a budget line item that competes with engineering headcount — not for the value it delivers, but for the volume it touches.

For AI inference specifically, the problem compounds. Every LLM request needs to know which model version to route to before the request can be sent. The flag evaluation is on the critical path — a network round-trip to a SaaS flag service adds latency you cannot absorb at inference time.

DS analogy — the toll road GPS
Imagine paying a toll every time your GPS checks which route to take. At one check per trip, the toll is irrelevant. At 1,000 checks per second, the toll collector’s queue becomes the bottleneck, and the GPS defeats its own purpose. A feature flag system that costs a network round-trip per evaluation has the same problem on a high-frequency request path.

What real-time config propagation looks like at scale

At Delivery Hero, the routing plane — Route Service and Route Consumers running on AWS EKS — handled 1M+ daily orders with the Route Consumers processing 5k+ real-time route updates per second and 10k+ concurrent requests at peak. The routing plane needed to react to dynamic configuration without pod restarts. These were values that adjusted routing behavior in response to demand signals, and they needed to propagate to all running pods within seconds of a change.

During one deploy, a config update reached 40% of pods before the other 60% saw it. For a brief window — a matter of seconds — the routing plane applied two different parameter values to simultaneous requests from the same zone. The fix wasn’t faster propagation; it was atomic broadcast: all pods see the change in the same event loop tick, or none do.

Think of updating a price on a shelf while customers are already filling their carts. If only some shelves update, the shelf price and the checkout price disagree for a window. Config propagation with a non-atomic rollout has the same inconsistency window. Real-time config propagation isn’t a new problem; what’s new is that it’s now on the hot path for every LLM inference request, which raises the bar from “nice to have” to “must be sub-millisecond.”

Why LaunchDarkly’s pricing breaks for infrastructure services

LaunchDarkly prices on monthly active contexts (MACs) — each unique evaluation context in production counts. For a marketing A/B test, MACs are a reasonable proxy for value: more unique users evaluated means more potential conversion. For an infrastructure service evaluating “which model version” on every request, MACs are the wrong unit entirely.

At 1,000 requests per second, you accumulate 2.6 billion MACs per month. That isn’t 2.6 billion customers — it is 2.6 billion individual evaluations of a single routing flag. The fundamental mismatch: LaunchDarkly was designed for product teams making per-user decisions, not infrastructure teams making per-request routing decisions at continuous high volume.

Imagine renting a storage unit priced per door-open rather than by size. At one opening per quarter (quarterly campaign flags), the pricing model is fine. At a thousand openings per day (per-request model routing), you’d buy the unit outright. A self-hosted flag system changes the cost model to a one-time engineering investment; the marginal cost of running flagd on an etcd cluster you already operate for Kubernetes is close to zero. Before choosing a SaaS tool, price it at the traffic level it will actually operate at — not your current traffic, but the ceiling of the system it will instrument.

The propagation problem: why etcd + gRPC streaming

Three requirements shaped the technical choice. Flag changes must propagate to all running pods in under 50ms. Flag evaluation must be in-process — no network call on the hot path. Every flag change must be durably logged before any pod sees the new value, with the audit entry and flag mutation written atomically.

Polling fails the first requirement without absurd load. Database watches like PostgreSQL LISTEN/NOTIFY fail the third — neither guarantees atomic commit of the audit entry alongside the flag value. etcd’s Txn primitive gives you atomicity: flag mutation and audit entry commit together or neither does. etcd’s Watch gives you propagation: any write to the /flags/ prefix fires a watch event to all flagd server replicas immediately.

gRPC streaming satisfies the second requirement. On connect, the client receives a full flag SNAPSHOT and stores it in-process. Subsequent flag changes arrive as DELTA messages over the open stream. Flag evaluation is a local hash-map read — roughly 100ns, no serialization, no network. The propagation mechanism determines both your flag change latency and your audit guarantees; they are not independent design decisions.

AI model rollout flags: what boolean flags don’t give you

Standard boolean flags are binary: all traffic sees model A, then all traffic sees model B. For AI model version changes, this is dangerous. A new model may underperform on a specific request type that appears in only 5% of traffic — you won’t know until you’re already at 100% rollout.

Percentage rollout flags send 10% of requests to gpt-4o and 90% to gpt-3.5-turbo simultaneously. Deterministic hashing on request_id (FNV-1a) ensures the same request always hits the same model — critical for multi-turn conversations where model context must remain consistent across turns. Standard product flags use user_id as the stable key; for LLM routing, the stable entity is the conversation, not the user.

Think of adjusting a dimmer switch rather than flipping a toggle. Boolean flags are binary — on or off. Percentage rollout flags let you hold at 10% brightness for an hour, verify the room temperature (model quality metrics), and increase slowly. The evaluation_count_snapshot in the audit log is a timestamp burned into each dimmer position — you can always reconstruct exactly how many requests experienced each brightness level, and attribute cost changes to specific flag mutations. For AI model version changes, the flag type matters as much as the flag system.

The DH bridge: same problem, different payload

At Delivery Hero, the Route Service needed dynamic config values propagated to all EKS pods within seconds. The technical requirement was identical to what distributed-flagd solves: consistent store, watch-based propagation, atomic broadcast to all running instances. The payload was a config value that adjusted routing behavior during peak demand; in distributed-flagd, the payload is a model version weight distribution. The propagation infrastructure is the same.

This pattern — consistent store, watch mechanism, in-process cache — recurs throughout distributed systems engineering. Service discovery uses it (etcd + client-side DNS cache). Config management uses it (etcd + Envoy xDS). AI model routing flags use it now. The implementation details differ; the architecture is the same.

The hardest conversation about building distributed-flagd wasn’t the technical design — it was explaining to stakeholders why spending two engineering days on something that “already exists” made sense. The SaaS product and the infrastructure primitive look similar on a feature matrix; they are different things in production. Build when the off-the-shelf product and your operational requirements diverge at the mechanism level, not just in features.

What I’d do differently

Build the percentage rollout evaluator before the propagation layer. The evaluator is the core value — deterministic hashing, variant selection, and unit test coverage. The propagation layer (etcd + gRPC streaming) is well-trodden infrastructure. Proving evaluation semantics with unit tests first would have saved two redesigns of the variant selection algorithm.

Size the etcd audit log retention from day one. Unbounded audit keys mean the keyspace grows forever; a 90-day TTL with an etcd lease should be built into the initial schema, not retrofitted. Add a dry-run mode to the flagd CLI so operators can see what would change — how many evaluation contexts would be affected — before committing a weight change on a high-traffic flag.

Plan the migration from any existing flag system early. Dual-write — sending flag changes to both systems simultaneously and comparing evaluation results in shadow mode — is the only safe migration path for a service evaluating flags on 1k+ RPS. The shadow period is what gives you confidence to cut over; skipping it is the operational debt that surfaces at the worst moment. The propagation architecture is table stakes; the operational tooling is what makes the system trustworthy.
