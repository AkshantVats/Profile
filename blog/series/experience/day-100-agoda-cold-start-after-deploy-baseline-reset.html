Day 100 — Agoda Cold Start After Deploy — Baseline Reset

A new binary can shift query latency by tens of milliseconds the moment it ships — and an alert comparing today's numbers to a baseline that still remembers the old binary will keep firing until enough new data arrives to replace that memory.

At Agoda I spent about five months on WhiteFalcon, the in-house time-series database Agoda's team built on Kafka ingest, a RoaringBitmap inverted index, and a Scala query engine that Grafana talks to for dashboards and alerts. My own contribution was the cross-tier query engine extension: teaching that Scala layer to serve a single query across a time range spanning the Redis hot tier and the S3/Parquet cold tier, instead of forcing the caller to run two queries and merge the results by hand.

Before that extension existed, a query touching only the hot tier fetched one histogram of bucket counts and computed a percentile once. After it shipped, a query crossing the hot/cold boundary fetched two histograms — one from Redis, one from S3 — merged the bucket counts together, then computed the percentile once on the combined distribution. That's a real, documented change to the query path the moment the new binary went live, not an incidental side effect.

Scope note — Agoda, WhiteFalcon TSDB
My role is documented directly: Senior Engineer on WhiteFalcon for roughly five months (Apr–Sep 2024), where I extended the Scala query engine's cross-tier quantile merge — fetching histogram bucket counts from both Redis and S3/Parquet, merging them, then computing the percentile once on the combined distribution. What follows is the general shape of a problem that kind of deploy structurally creates for anything watching query latency: the extra histogram fetch and merge step is a real change to the code path, not a specific dated incident, page, or dollar figure my sources don't itemize.

A Deploy Changes the Shape of the Signal

The Scala query engine reports its own latency continuously, and Grafana panels built on top of that signal don't know anything about what changed inside the binary between one deploy and the next. The moment the cross-tier merge logic went live, every query spanning the hot/cold boundary started paying for two fetches and a merge step that single-tier queries never paid for. That's not a bug — it's the new binary doing exactly what it was built to do — but the latency distribution it reports genuinely moved.

Picture a bathroom scale that keeps a rolling seven-day average instead of showing one raw number, specifically so a single heavy dinner doesn't read as a real weight gain. The day you switch from weighing yourself right after waking up to weighing yourself after dinner, every number the scale reports afterward is honestly different from before — not because your weight changed, but because what's being measured changed, and the rolling average hasn't finished absorbing the new normal yet.

So what: a deploy that changes a system's latency profile isn't automatically a regression, but a rolling average watching that latency has no way to know the difference between "this is worse" and "this is just what normal looks like now."

What a Baseline-Driven Alert Can't Tell

An alert built on top of that latency series has one job: decide whether today's reading is anomalous relative to what it has recently seen. Scoped honestly to what a Grafana-connected query-latency panel can actually see, that job doesn't include knowing a deploy happened at a specific timestamp — it only sees a stream of numbers before and after, blended together in whatever window the alert's baseline uses.

The moment the underlying binary's latency profile takes a real, permanent step up — the two-fetch-merge cost is now just how cross-tier queries work — the alert can't distinguish "this is the new normal" from "this is degrading." Both look identical from inside a rolling window that spans the deploy boundary: a run of readings that don't match what the window remembers.

So what: an alert that only ever sees a blended window has no structural way to separate a deploy-caused step change from an actual regression, no matter how well-tuned its threshold is.

The Root Cause Is the Baseline's Memory, Not the Deploy

The deploy itself isn't the root cause here — shipping code that changes a system's latency profile is expected and, in this case, was the entire point of the change. The root cause is a baseline computed as a rolling window that blends pre-deploy and post-deploy readings together without ever being told a step change happened at a specific point in that window.

A baseline that blends pre-deploy and post-deploy readings into one number isn't lying — it's answering a question ("is today's reading unusual") with an average that was never told the ground it's standing on just moved.

So what: fixing the wrong layer — tuning the threshold, or silencing the alert until it "settles" — treats the symptom, because the underlying window keeps mixing two different regimes of normal until enough time passes for the deploy-era readings to age out on their own.

The Fix Is a Warmup Window, Not a Quieter Alert

The structural fix is telling the alerting layer, explicitly, not to trust comparisons against the baseline until enough post-deploy data exists for that baseline to honestly represent the new normal — a warmup window keyed to the deploy timestamp itself, not a vague "give it some time" instinct. Until that window closes, the alert holds; once it closes, the baseline it's comparing against was actually computed from the binary that's currently running.

Today's llm-judge-eval rolling-baseline work (Phase 2A) builds exactly this discipline for a different signal: a per-segment 7-day rolling mean and standard deviation of judge scores, feeding a check that alerts when a 24-hour window's mean drops more than two standard deviations below that baseline. The same cold-start problem applies the moment the scoring pipeline's own model or prompt changes — a 7-day rolling baseline computed straight through that change quietly blends old-model and new-model scores into one number that describes neither regime honestly, and the alert either misfires on drift that never happened or, worse, goes quiet on real drift hiding inside a muddied average.

So what: a deploy that changes a system's real behavior isn't the problem — a baseline with no memory of when that change happened is. Whether the signal is WhiteFalcon query latency after a cross-tier merge extension ships, or a judge model's score after the scoring pipeline itself changes, the same guardrail applies: give the rolling window an explicit warmup period after a deploy before letting it arm alerts, instead of asking a threshold to somehow already know the difference between a regression and a new normal.
