Day 92 — Walmart Feature Flags on Firmware Channels

A firmware push to millions of distributed devices was never a flip of a switch — it went out to a small device cohort first, and widened only if nothing broke. That's the same dial today's code PR just wired up for shadow traffic.

Today's code PR gives shadow-traffic-router a shadow_percent flag — a per-tenant dial, resolved through distributed-flagd, that decides what slice of production traffic gets mirrored to a shadow model. Default 1%. Wiring it up made me think back to a much older rollout dial, on hardware instead of Kafka topics.

At Walmart Labs, the WeIoT SmartBuildings platform I helped build pushed firmware to sensors and controllers spread across facilities on Azure IoT Hub — devices that could, individually, go dark or corrupt their config if a bad build reached them all at once. Nobody ever shipped an OTA (over-the-air) firmware update as one global push. It went out to a small device cohort first, and only widened if that cohort came back healthy.

A Rollout Percentage Is a Risk Dial, Not a Load Switch

It's tempting to think of a percentage rollout as a performance concern — something you'd reach for if a fleet of devices might overwhelm a config server all checking in at once. That's not actually the reason it exists here.

The real reason is blast radius. A firmware build that bricks a device, or leaves it stuck in a boot loop under a flaky network connection, is expensive to recover from one device at a time — sometimes it needs a truck roll, sometimes it needs the device to get lucky enough to reconnect and self-heal. Shipping to 2% of a cohort first turns "how many devices does a bad build break" from a fleet-wide number into a small, contained one.

Team scope — Walmart Labs, WeIoT SmartBuildings
From my resume: "7M+ sensors, tens of millions of telemetry points/min: Architected WeIoT SmartBuildings ingestion layer on Azure IoT Hub; engineered real-time HVAC control loops via Azure Stream Analytics automating energy optimisation across 50+ global facilities." A separate line names the piece this post is about directly: "Fault-tolerant edge-to-cloud OTA firmware framework — reliable config syncs and updates for millions of distributed devices under intermittent network conditions." These were two related but distinct workstreams — the ingestion/HVAC-control pipeline and the OTA firmware framework — not one merged system.

Intermittent connectivity made the percentage dial matter twice over. A device that missed its update window because it was offline at rollout time couldn't be assumed to have failed — it just hadn't checked in yet, and the framework had to tell that apart from an actual bad sync before it panicked and paused a rollout that was actually fine.

So what: a staged rollout percentage isn't there to protect a server from load — it's there to bound how much damage one bad build, or one flaky network window, can do before someone notices and stops widening it.

Cohort, Watch, Widen — the Same Loop Either Way

The mechanics of a device-cohort rollout and a request-level shadow-traffic rollout look almost nothing alike on the surface. One assigns devices to a percentage bucket and waits hours or days for sync telemetry to come back; the other assigns individual requests to a percentage bucket and gets an answer inside a single request's lifetime.

Underneath, both run the same loop: pick a small percentage, watch a health signal, only widen the percentage once that signal says it's safe.

This is the same shape as watering a new lawn one section of sprinkler heads at a time instead of running every zone at once: you find the broken head or the low-pressure section while it's only costing you one patch of grass, not the whole yard's water bill before you notice anything is wrong.

So what: "percentage rollout" is really shorthand for a watch-and-widen loop — the percentage itself is just how much you're willing to risk before the next health check runs.

A rollout percentage only does its job if there's a well-defined answer to "what happens when the thing controlling it can't be reached" — the dial is useless without a documented rest position.

The Default That Matters More Than the Dial

Every percentage rollout eventually has to answer a question nobody likes designing for: what happens when the control plane itself is unreachable. For OTA firmware under intermittent connectivity, that question came up constantly, not as an edge case.

The answer the framework had to give was "stay on the known-good build" — a device that couldn't confirm its rollout eligibility simply didn't update, rather than guessing and applying a firmware image it hadn't actually been cleared to install. Guessing wrong in either direction was worse than waiting: updating without confirmation risked a build that hadn't finished its cohort validation, and refusing every update whenever connectivity blipped would have meant a flaky network permanently froze the fleet on old firmware.

That's exactly the fail-open shape today's shadow_percent flag needed. If distributed-flagd is unreachable or times out, the sampling decision falls back to the 1% default — not 0%, which would silently blind DriftWatch's shadow evaluation, and not 100%, which would blow past the cost and volume budget the design assumes.

So what: the interesting design decision in a rollout dial was never the widen logic — it's the one line that says what the system does the moment the dial itself goes silent, and getting that line wrong is worse than getting the percentage wrong.

The Same Shape, Different Fleet, Same Code PR

shadow_percent is modeled as a weighted-variant flag in distributed-flagd — the same primitive this repo's earlier model-routing flags already use to send a percentage of traffic to a new model version. Reusing it here means shadow sampling gets a live-updatable rollout percentage, a documented fail-open default, and per-tenant overrides without inventing a second flag system alongside the one already operated correctly for routing.

The parallel to a decade-old OTA framework isn't nostalgia for its own sake. It's a reminder that "roll it out gradually and watch a health signal before widening" is a pattern that outlives the specific technology it's applied to — sensors on Azure IoT Hub then, Kafka-bound shadow-eval events now.

So what: any staged rollout — firmware to a device fleet, a new model to a shadow-eval sample, a risky migration to a subset of tenants — needs the same two decisions made explicit up front: what percentage moves first, and what the system does when the thing deciding that percentage can't be reached.
