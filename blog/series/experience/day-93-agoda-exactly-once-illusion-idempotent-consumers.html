Day 93 — Agoda Exactly-Once Illusion — Idempotent Consumers

Today's code commits a Kafka offset only after a ClickHouse write succeeds — which sounds safe, right up until you ask what happens if the process dies in between. It doesn't. Nothing here is exactly-once yet, and that gap has a name.

Today's code PR adds the consumer side of shadow-eval: a batching loop that reads messages off Kafka, hashes the production response, writes a row to ClickHouse, and only then commits the offset back to the broker. That ordering — write first, commit second — is the textbook way to avoid losing a message. It is not, on its own, the textbook way to avoid duplicating one.

If the process dies after the ClickHouse write lands but before the commit reaches Kafka, the broker still thinks that message is unacknowledged. It gets redelivered. The row gets written again.

I used to think "exactly-once" was a setting you turned on. Contributing to the Kafka pipeline behind Agoda's WhiteFalcon time-series database is where that stopped being true.

What Kafka Actually Promises, and What It Doesn't

Kafka's delivery guarantee, in the shape most consumers actually use it, is at-least-once. A message is redelivered whenever a consumer can't prove it already processed it — a crash before the offset commits, a rebalance that reassigns a partition mid-batch, a network blip on the commit call itself.

None of those are exotic failures. They're the ordinary cost of running a consumer group at any real scale for long enough.

Kafka does offer stronger guarantees — idempotent producers, transactional writes — but those cover Kafka-to-Kafka pipelines: producing into one topic while consuming from another, wrapped in the same transaction. The moment a consumer writes to something that isn't Kafka — a database, an object store, a ClickHouse table — that external write is on its own. Kafka's transaction can't reach across the boundary and undo a ClickHouse insert.

So what: "exactly-once" as most engineers use the phrase isn't a delivery guarantee at all — it's a property the consumer's own write has to supply, because the messaging layer stops covering you the moment you leave it.

Team scope — Agoda WhiteFalcon TSDB
From the resume line: "1.5 trillion events/day TSDB: Contributed to WhiteFalcon, Agoda's in-house Rust + Scala TSDB on Kafka." My five months there were spent extending the cross-tier query engine and adding a new cardinality dimension — not designing WhiteFalcon's Kafka ingestion path itself, which the core team owned. But sitting next to that pipeline for five months, reading its Rust consumers to understand how data reached the hot tier, is where the at-least-once-by-default shape of Kafka consumption stopped being an abstract fact and became something I'd internalized: any consumer reading from that pipeline had to assume a message could show up twice, because at that event volume, over any long enough window, one eventually does.

The Illusion, and the One Fix That Actually Works

The tempting fix is to make the write-then-commit window smaller — commit faster, batch less, hope the crash window shrinks past the point of mattering. It never fully closes. Any nonzero window between "the write is durable" and "the offset is durable" is a window a crash can land in, no matter how narrow you make it.

The fix that actually works doesn't try to close the window. It makes what happens inside the window harmless. Give every message a deterministic identity — commonly a composite like (tenant, event_id) — and make the write itself refuse to apply that identity twice, whether through a unique constraint, an upsert keyed on it, or a dedup table checked before the write commits.

Redelivery still happens. It just stops mattering, because processing the same message twice produces the same end state as processing it once.

That loop back into Write to sink is not a bug to eliminate. It's the shape at-least-once delivery always has. The only question worth designing for is whether looping back through Write to sink a second time is free or expensive.

So what: you can't out-engineer the crash window with faster commits — you can only make landing in it cost nothing, and that cost is decided entirely by whether the write on the other end is idempotent.

My Own Code Still Has This Gap — On Purpose, For Now

The shadow-eval consumer I wrote today does not have a dedup key. It writes request_id, tenant_id, and a hash of the production response into a plain MergeTree table, ordered by (tenant_id, captured_at) for query performance — not deduped on anything at write time. If a crash lands between a successful WriteBatch call and the offset commit that follows it, the same batch gets redelivered, and the same rows land twice.

I left that gap in on purpose rather than close it today, and said so directly in the code: infra_ai.shadow_eval is append-only for now, and a duplicate row here doesn't corrupt anything downstream yet — there's no evaluator reading it and computing an aggregate that a duplicate would double-count, because that evaluator doesn't exist yet either. Closing the gap now would mean guessing at a dedup shape before there's a real reader to design it against. Closing it later, once a real evaluator query exists and duplicates actually cost something, means I'll know exactly what shape the fix needs to be.

So what: not every idempotency gap needs closing the day it's discovered — but it does need to be written down as a gap, in the code, where the next person extending it (possibly me, in three days) can't miss it and mistake "append-only" for "exactly-once."

The General Shape, Past One Pipeline

Every consumer that writes to something outside Kafka inherits this same choice, whether it's Rust reading into Redis at Agoda's event volume or a Go batch loop reading shadow-eval into ClickHouse today. The messaging layer's guarantee ends at "you will eventually see every message, possibly more than once." Whatever happens next is the consumer's problem, not the broker's.

That's not a knock on Kafka. It's a fair division of responsibility — a delivery system that also guaranteed exactly-once end-to-end into an arbitrary external store would need transactional visibility into that store, which is a much bigger promise than a messaging system should be making on your behalf.

So what: "exactly-once" is a property you build at the edge where a message stops being a message and becomes a row — never something you get by picking the right broker configuration and walking away.
