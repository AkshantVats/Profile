Day 70 — Exact Match Before Fuzzy

A cheap, exact check ahead of an expensive, approximate one isn't a shortcut — it's the same tiering discipline WhiteFalcon's hot Redis tier and cold Ceph/S3 tier already run on, just applied to a cache instead of a database. Today's prompt-fingerprinter design doc is that discipline written down one layer earlier than WhiteFalcon ever needed it.

Today's ticket opens a new module instead of extending an existing one: prompt-fingerprinter, a SHA-256 exact-match cache that sits ahead of semantic-cache-engine's embedding-similarity lookup, RouteIQ's third module in six weeks. Design-only, same shape as Day 60 and Day 65 — a written decision before any Go code exists to enforce it.

The decision itself is small enough to say in one line: check the cheap, exact thing before the expensive, approximate thing. I'd already lived inside a system that made that exact call, just for a different reason than caching.

A Query Router I Extended, But Didn't Design

I spent about five months at Agoda as a Senior Engineer on WhiteFalcon, the team's in-house time-series database. WhiteFalcon keeps the last three to seven days of data in Redis, bucketed in time windows, queried at per-hour granularity because that window is where almost all query load lands. Everything older lives in Ceph, backing S3, as compacted Parquet — coarser granularity, a real disk read instead of an in-memory bucket lookup.

A query that falls entirely inside the hot window never touches Ceph at all. The Agoda team built that routing into the query engine before I joined: check whether the requested range fits inside the retention boundary, and only reach for the colder, slower tier when it doesn't. I didn't design that boundary or the compaction jobs that feed it — that's Agoda team infrastructure, not mine.

My contribution — Agoda, Senior Engineer, WhiteFalcon TSDB, ~5 months
I extended the Scala query engine to handle the case the router alone couldn't solve: a time range that spans both tiers. That meant fetching histogram bucket counts from Redis and from Parquet/S3 separately, then merging the two distributions before computing a single correct quantile — because a query answer that silently skipped the cold tier, or merged two already-computed percentiles instead of two raw distributions, would have been wrong in a way nobody querying Grafana could see.

So what: the cross-tier merge work only existed because the hot-tier-first routing decision already existed underneath it — I was extending a system whose cheap-tier-first shape was a given, not something I chose.

Why Checking Redis First Was Never a Close Call

The order WhiteFalcon's router picks isn't a stylistic preference. A Redis bucket read for an in-window range is a single in-memory lookup. A cold-tier read means Ceph resolving object placement across its OSDs, then a Parquet file scan over NVMe-backed storage, then decompression — real work, even before the query engine merges anything. Checking the hot tier first isn't an optimization layered on top of a working design; it's the design, because the cost gap between the two tiers is large enough that getting the order backwards would make every recent-data query pay a cold-tier tax it never needed to pay.

So what: an ordering choice earns its place when the cost gap between the two options is real and measured, not assumed — and WhiteFalcon's hot/cold split is exactly that kind of measured gap, not a guess.

The Same Shape, One Layer Earlier

prompt-fingerprinter takes that identical discipline and applies it one layer earlier than WhiteFalcon ever needed to. A SHA-256 fingerprint of a normalized prompt is a Redis GET — one round trip, sub-millisecond. semantic-cache-engine's lookup needs an embedding-model call before its pgvector similarity search can even run — a network hop the fingerprint check never pays. Checking the fingerprint cache first means a byte-identical retry, a replayed batch job, or a double-submitted request never reaches the embedding pipeline at all.

Where the Parallel Breaks

The honest gap matters as much as the parallel. WhiteFalcon's hot and cold tiers are the same data at different ages — a bucket's contents flow from Redis into Ceph on a schedule, whether or not anyone queries them again. There's a lifecycle connecting the two tiers even when nothing is actively reading from them.

prompt-fingerprinter and semantic-cache-engine have no equivalent lifecycle. A fingerprint miss doesn't mean the prompt "ages into" the semantic tier — it means a second, independent lookup runs against a different index entirely, and either cache can be populated, evicted, or expire without the other one noticing. The two caches share a design principle and, per Day 70's DESIGN.md, a hash definition — they don't share a pipeline the way WhiteFalcon's tiers do.

So what: borrowing an ordering principle from one system doesn't mean borrowing its whole architecture — the part that generalizes is "cheap check first," and the part that doesn't is whatever machinery happens to connect the two tiers in the system the idea came from.

Checking the cheap tier first isn't an optimization bolted onto a working design — when the cost gap is real and measured, it is the design.
