Day 44 — Event Sourcing — But the Events Hallucinate

At Wayfair, a pricing simulation was a replay: freeze the supplier costs, run them through a stateless pricing engine, compare the output to what's live. Today's agent-replay-engine is the same pattern with one enforcement point instead of a dozen scattered snapshot timestamps.

The pricing engine at Wayfair ran simulations before any price adjustment went live. A simulation was a replay: take the current adjustment set, freeze the supplier cost inputs, run them through Delphi — our internal pricing engine — and see what retail prices would come out. If the simulated prices diverged from expected values by more than a threshold, the adjustment was blocked before it ever reached a customer.

The mechanism that made this work was that Delphi was a stateless pure function: same inputs, same output, every time, no exceptions. The simulation's frozen inputs guaranteed that two runs of the same simulation always produced the same result. I did not think of this as event sourcing — the pattern of recording every state change as an immutable, replayable event — at the time.

I thought of it as "pricing simulation." The pattern underneath is identical: freeze the inputs, replay the computation, compare the output.

My role — Wayfair, Sr. Software Engineer III, Nov 2024 – Mar 2026
I led the Price Adjustment System (PAS) and Pricing Promotions & Discounts teams, and architected the event-driven pricing engine that propagated price changes from hours to sub-seconds across 20k+ suppliers. The simulation and Kafka pipeline described below are systems I owned and shipped, not systems I observed from the sidelines.

What a Pricing Simulation Is and Why Idempotency Is Not Optional

A price adjustment at the scale of 250k+ SKUs per supplier is not something you push live and see what happens. A bug in the adjustment logic — wrong discount percentage, off-by-one in the effective date, a misconfigured supplier exclusion — affects every retail price that reads from our Bigtable read model within milliseconds of the adjustment committing. There is no "undo" for a price error that reaches the customer-facing storefront before an on-call engineer can respond.

The pricing simulation runs the exact same calculation pipeline as a live pricing run but against a frozen snapshot of inputs. Frozen means: supplier costs from a fixed BigQuery snapshot timestamp, adjustment sets from the current PAS database state, SKU metadata from a fixed Bigtable row version. Delphi receives the same input vectors it would receive in a live run, but every input is pinned to a point in time instead of read live.

Delphi being a stateless pure function — no internal state, no cache that could have changed between calls, no background job that could have run — is what makes the simulation trustworthy. Run it once: price X. Run it again five minutes later with the same inputs: price X, every time, because there is nothing inside Delphi that could have drifted.

So what: the simulation is only as reliable as the idempotency guarantee underneath it. If Delphi had been designed with any mutable state, the simulation would have been unreliable from day one regardless of how carefully we froze the inputs. The decision to make Delphi a stateless pure function was made before the simulation existed, but it was the decision that made the simulation possible at all — architecture choices made for one reason often enable capabilities their designers never anticipated.

Frozen Inputs as the Source of Truth

Freezing inputs means pinning every data source the computation reads to a specific version: BigQuery snapshot at timestamp T, Bigtable row versions as of timestamp T, PostgreSQL queries against a read replica with a fixed transaction snapshot. Any data source that reads live — one that could return different values between run one and run two — breaks the simulation's reproducibility guarantee entirely.

Our PAS read model used Bigtable for low-latency price lookups, running a Google Cloud wide-column store called pricing-cost-adjustment-bt at 13K average queries per second and peaks to 57K during pricing runs. That table was constantly being written to as new adjustment runs committed, which meant pinning reads to a fixed row version for simulation purposes required explicitly passing a snapshot timestamp to every Bigtable read call in the simulation path — never the live path.

Physical analogy — the photograph vs. the window
A live read is a window: look through it twice and the street outside has changed. A frozen read is a photograph taken through that same window: look at it twice, minutes apart, and it shows the identical street every time. The simulation needed every input to be a photograph, and any input that was accidentally still a window broke the guarantee without announcing itself.

Supplier cost inputs for pricing run simulations came from BigQuery via Cloud Dataflow, Google's managed batch/stream processing service. Dataflow jobs were parametrized with a snapshot timestamp, and every BigQuery read used the FOR SYSTEM_TIME AS OF clause — BigQuery's built-in time-travel feature — to read data exactly as it existed at timestamp T.

So what: frozen inputs are a system property, not a policy you can decide to apply at debug time. You cannot retroactively pin reads if the infrastructure was never built to support them, which is exactly why BigQuery's time travel and Bigtable's read timestamps mattered so much — they turned "freeze the inputs" from a wish into a mechanism the simulation could actually rely on.

When the Inputs Are Not Frozen (And What Happens)

The simulation would occasionally produce prices that diverged from the live prices by more than the threshold, blocking an adjustment the pricing team believed was correct. The usual diagnosis: a data source that was supposed to be frozen had not been properly pinned, most often a Bigtable read somewhere in the simulation path that had missed the snapshot timestamp parameter and was quietly reading live data instead.

Diagnosing this required replaying the simulation with logging added at every data read — log the timestamp parameter passed to each Bigtable and BigQuery call, log the row version returned, compare both against the snapshot timestamp the simulation was supposed to be using. A read returning a row version newer than the snapshot timestamp was the unfrozen read, and the fix was almost always mechanical: pass the missing timestamp parameter to the call that had dropped it.

Freezing inputs across a distributed system is brittle because there is no single enforcement point. Delphi receives frozen inputs from the simulation orchestrator, but it calls other internal services, and if any one of those services reads live data instead of the snapshot-pinned version, the simulation is only partially frozen. Guaranteeing full freezing meant threading the snapshot timestamp through every service, every Bigtable read, every BigQuery query in the call chain — and verifying it stayed threaded as the codebase evolved.

So what: agent-replay-engine solves this differently on purpose. Instead of freezing inputs at the data-source level — pass a timestamp to every read, hope nothing was missed — it freezes the outputs of tool calls: record the response payload once, serve it back verbatim on replay, and never let the agent see a live API during that replay. There is no "missed snapshot timestamp" failure mode because there is no snapshot timestamp at all; the frozen response is the only response that exists.

Event Sourcing in the Pricing Kafka Pipeline

Our pricing_refresh Kafka topic, running 40 partitions, carried price change events from Delphi through Aletheia — our storefront price cache — to the customer-facing storefront. Every price change was an event: a record of "SKU X's retail price changed from Y to Z at timestamp T." Internally we described the pattern explicitly as event-sourcing: the current price is the result of replaying the event stream from the beginning, or from a checkpoint.

Aletheia ran as an autoscaled deployment of 20–50 pods across seven production clusters, consuming from pricing_refresh. When a pod restarted, it replayed events from its last committed offset, and those events had to be idempotent at the consumer side — applying the same price change event twice had to produce the same final price as applying it once, never a doubled or corrupted value.

Forty partitions meant up to forty Aletheia pods could process price changes in parallel, and Kafka's partition assignment guaranteed every event for a given SKU landed on the same partition by keying on SKU ID. That prevented the race condition where two concurrent updates to the same SKU could be processed out of order and produce the wrong final price.

So what: pricing_refresh is a distributed event log for price state, and it is exactly the same pattern as agent-replay-engine's event log for agent state — both are append-only records of state transitions that can be replayed to reproduce any point-in-time state. Kafka was the right tool for pricing because partitioning, consumer groups, and replay-from-offset-zero were already solved problems; agent-replay-engine is a purpose-built implementation of the same idea for a domain where standing up a Kafka cluster would be overkill.

What agent-replay-engine Gets Right That Pricing Simulations Got Wrong

The pricing simulation's freezing mechanism was distributed: snapshot timestamps had to be threaded through every data read in the system, and any read that missed the timestamp silently produced a non-deterministic simulation. The ToolMocker in agent-replay-engine is a single enforcement point instead — every tool call during replay goes through it, every response it returns is frozen, and no tool call can reach a live API by accident, because the architecture makes bypassing the mocker structurally impossible.

The pricing simulation keyed frozen data by timestamp: "give me this Bigtable row as of T." That works for databases with time travel, but not for external APIs with no exposed history. ToolMocker keys responses by SHA-256(tool_name + ":" + input_hash) instead — a hash over the call signature, not a point in time — which works for any tool call: internal databases, external APIs, in-process functions, all the same.

The pricing simulation had no built-in way to explain a divergence: if simulated prices differed from expected, the investigation started from scratch, comparing outputs and tracing backwards through the computation by hand. agent-replay-engine's CallHistory() method records every tool call the model issues during replay, in order, and comparing it to the recorded call sequence makes the first diverging index visible immediately — that index is exactly where the replay's behavior departed from the original run.

The lesson from Wayfair isn't "here is how to build a pricing simulation." It's "here is what happens when a replay system has no single enforcement point, and here is how the next one avoids that failure mode."

So what: agent-replay-engine is not a novel invention — it is the pricing simulation pattern applied to a different domain, with three design improvements the pricing simulation's distributed architecture could never provide: one enforcement point for frozen inputs, call-signature-keyed responses that work for any tool type, and built-in divergence detection instead of manual forensics. Bridge: replay mocks are idempotent consumers, no different in spirit from Wayfair's price replay against frozen inputs, and today's code in agent-replay-engine implements that lesson directly.
