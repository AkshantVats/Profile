Day 25 — Distributed Redis Rate Limits — Lua Scripts and Race Conditions

Wayfair · sliding window in production — the race condition that surfaces under concurrent load and why atomicity is non-negotiable

The bug that almost broke Wayfair’s Black Friday supplier submissions was not in the business logic. It was in the rate limiter. More precisely, it was in the gap between two Redis commands that looked atomic but were not.

The Pricing and Promotions Submission (PAS) system received supplier pricing submissions via gst-acc-promotions and routed them to the Supplier Price and Cost Service (SPCS). SPCS had a hard limit: no more than eight concurrent batch API calls per client, with each batch capped at 100 parts. Eight parallel calls at 100 parts each — 800 parts in-flight simultaneously — was the ceiling the API could handle before returning 429 errors. Exceeding that ceiling did not cause a graceful backoff. It caused failed submissions that required manual resubmission. During Black Friday, that meant supplier pricing corrections sitting in an error queue while the storefront was live.

The rate limiter was the gatekeeper. It was wrong.

DS analogy — the club with a broken counter
Imagine a nightclub with a 100-person capacity. The bouncer counts people in on a clicker. Two bouncers working the door simultaneously both look at the counter, both see 99, both let someone in, and the club hits 101 before either counter updates. The clicker itself is the problem: reading and writing are two separate operations, and two bouncers doing them concurrently break the invariant. A distributed rate limiter running on multiple PAS service replicas has the same problem. The bouncer is your Redis GET. The clicker update is your Redis SET. They are not atomic.

The naive implementation

The original rate limiter used the classic Redis counter pattern: INCR the key, check if the result exceeds the limit, call EXPIRE to set the TTL. Three commands. If the key did not exist, INCR would create it at 1. The logic read cleanly in a single replica context.

# What the original rate limiter did
count = redis.incr("rate:spcs:client-A")
if count == 1:
    redis.expire("rate:spcs:client-A", 1)  # 1-second window
if count > 8:
    raise RateLimitExceeded()

The problem appeared under the 12 pods of gst-acc-promotions processing submissions concurrently. Pod 3 and Pod 7 both receive supplier submissions at the same millisecond. Both call INCR. Both get back 1 — because their increments are processed sequentially by Redis and each starts from 0 on a fresh key. But between the INCR returning 1 and the EXPIRE being set, another pod increments to 2. The EXPIRE from Pod 3 then sets the TTL on a key that now has a value of 2. This is a minor version of the race. The more dangerous version is when a new window has just opened — the key expired, and now 12 pods simultaneously hit an INCR on a non-existent key in the same millisecond, all getting back 1, all believing they are the first in the window, and all proceeding to call SPCS concurrently.

This is the thundering herd at window reset. Every pod reads the same expired-key state, every pod creates the counter at 1, and the SPCS rate limit is violated by a factor of 12 before any of the EXPIRE calls have even been sent.

Why Lua fixes the race

Redis executes Lua scripts atomically. Not “sort of atomically” or “usually atomically” — the Redis documentation guarantees that no other client command runs while a Lua script is executing. This is the same guarantee a database gives for a stored procedure inside a transaction. The check-and-set that would be a race across two commands becomes a single, uninterruptible unit of work.

-- Sliding window token bucket via Redis Lua (atomic)
local key     = "ratelimit:" .. KEYS[1]
local now     = tonumber(ARGV[1])   -- current unix ms
local rps     = tonumber(ARGV[2])   -- requests per second
local burst   = tonumber(ARGV[3])   -- burst multiplier
local cost    = tonumber(ARGV[4])   -- tokens this request costs

local capacity = math.floor(rps * burst)

local data       = redis.call("HMGET", key, "tokens", "last_refill")
local tokens     = tonumber(data[1]) or capacity
local last_refill = tonumber(data[2]) or now

local elapsed_ms = now - last_refill
local refilled   = (elapsed_ms / 1000.0) * rps
local new_tokens = math.min(capacity, tokens + refilled)

if new_tokens >= cost then
  redis.call("HMSET", key, "tokens", new_tokens - cost, "last_refill", now)
  redis.call("EXPIRE", key, 60)
  return {1, math.floor(new_tokens - cost)}
else
  local needed   = cost - new_tokens
  local retry_ms = math.ceil((needed / rps) * 1000)
  return {0, retry_ms}
end

Every field access, the arithmetic, the comparison, the conditional write — all happen inside the same atomic execution. There is no window between reading tokens and writing the decremented value where another pod can interfere. The 12 gst-acc-promotions pods can all call this script simultaneously. Redis will execute them one at a time. The first one to run gets the current token count. The second gets the count after the first deducted its cost. The limit holds.

What the Wayfair PAS team owned
The SPCS integration, the batch partitioning logic, and the retry strategy were built and maintained by the PAS engineering team. The rate limiting layer — including the transition from the naive counter to the Lua-based token bucket — was part of the PAS backend infrastructure work I contributed to. The SPCS API limits (8 parallel calls, 100 parts per batch) are the upstream API’s constraints; the rate limiter’s job was to enforce them without exceeding them.

Sliding window vs fixed window

The Lua script above implements a token bucket, which is a continuous sliding window: tokens refill at a constant rate proportional to elapsed time. This is different from a fixed window counter, which resets to zero at a fixed time boundary (every second, on the second). The fixed window has a well-known failure mode: two bursts, one at the end of window N and one at the start of window N+1, can both be within their individual window limits but together exceed 2× the intended rate over the boundary period.

For the SPCS integration, the token bucket was the right choice. SPCS did not reset its concurrency limit on a clock boundary — it enforced a hard ceiling on in-flight requests at any moment. A fixed window counter would allow the burst-at-boundary problem to hit exactly when Black Friday traffic was heaviest. The token bucket’s continuous refill matched the continuous nature of SPCS’s constraint.

The burst multiplier in the Lua script is what made the distinction practical. Setting a burst multiplier of 1.0 gives you a strict rate limit with no headroom. Setting it to 1.5 allows the bucket to accumulate 1.5× the per-second capacity during a quiet period and spend it in a burst — useful for submission workflows that arrive in waves rather than at a constant rate. Supplier submissions do not arrive uniformly: they cluster at business hours, at promotion deadlines, and on Black Friday mornings. A small burst headroom meant the limiter absorbed natural traffic shape without false 429s while still protecting SPCS from sustained overload.

The Black Friday near-miss

What brought this to my attention was a staging load test that preceded Black Friday prep. We ran the supplier submission flow at 4× normal load — simulating the burst from 70,000 active suppliers submitting pricing updates simultaneously. The naive rate limiter let through more concurrent SPCS calls than intended. Not dramatically — the test environment SPCS mock did not reject requests — but the concurrency counters showed 11 or 12 simultaneous calls where 8 was the ceiling.

The issue was the thundering herd. Every 1-second window boundary, the rate limiter key expired, and all 12 pods would attempt a new submission in the same millisecond. All 12 saw a zero counter. All 12 considered themselves within the limit. SPCS in production would have rejected 4 of those 12 with 429 errors, requiring manual resubmission.

The Lua token bucket fixed it because there is no boundary reset. Tokens accumulate continuously, and the atomicity guarantee means only one pod can decrement the count at a time. Twelve simultaneous callers on the same Redis instance serialize through the script. The first 8 drain the available tokens. The remaining 4 receive a retry delay. No request is lost; it just waits for the correct retry interval before resubmitting.

The bridge: flagctl and the same atomicity guarantee

The flagctl kill-switch I built for distributed-flagd today relies on the same principle. A kill-switch must be atomic. If two operators simultaneously run flagctl kill-switch model_route --model gpt-4o-mini from different machines, the second write must not race the first into an inconsistent state. etcd’s MVCC serializes concurrent writes the same way Redis serializes Lua scripts — one write at a time, with each write seeing the post-commit state of the previous one.

The Redis Lua script and the etcd put are both instances of the same architectural pattern: a check-then-act that must be atomic. The rate limiter checks whether tokens are available before deducting them. The kill-switch checks the current flag value before overwriting it. In both cases, the “check” and “act” being non-atomic is not a theoretical concern — it is a Black Friday incident waiting to happen.

The flagctl kill-switch is the pricing freeze switch we wished we had during that load test. One command. One write. All traffic to the safe model. No race window between reading current state and writing the new value.

What I took from this system

The lesson I keep returning to is that correctness under concurrency requires explicit serialization, not hoping that requests arrive at different times. The naive counter worked in development because a single developer’s test runs did not hit the boundary race. It worked in staging under low load for the same reason. It failed the 4× load test because load testing is when you finally give the race condition the conditions it needs to manifest.

The second lesson is that Redis atomicity via Lua is underused. Most engineers know about Redis transactions (MULTI/EXEC) for batching commands, but those are optimistic: if a watched key changes, the transaction fails and you retry. Lua scripts are stronger: they execute serially, no optimistic retry needed. For a rate limiter, where every failed check is a dropped request, optimistic retry is the wrong model. Lua’s serial execution is the right model.

The third lesson is about burst multiplier as a first-class parameter. The SPCS integration taught me that rate limits are not just about the steady state — they are about the traffic shape. Building the burst headroom into the limiter explicitly, as a tunable parameter, made the system honest about what it was allowing rather than hiding a fixed assumption inside the implementation.

DS analogy — the hospital triage desk
A hospital triage desk has one nurse who can assess one patient at a time. The form says “fill this out, then hand it back.” If 12 patients walk up simultaneously and all grab the same pen to write their name on the same form, the form ends up with 12 names scribbled over each other. You need the nurse to take the pen, assess one patient, return the pen, then take the next patient. The Redis Lua script is the nurse taking the pen. The atomicity guarantee is the physical fact that only one person holds the pen at a time.
