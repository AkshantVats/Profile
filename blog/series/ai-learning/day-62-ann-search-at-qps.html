IVFFlat vs HNSW — pick like you pick a MergeTree order key.

A MergeTree table's ORDER BY defines which columns are physically sorted together on disk, and that choice determines which queries get a fast index-assisted scan and which ones fall back to reading everything. You pick it once, before you know the exact shape of every future query, and changing it later means rewriting the table. A vector index type is the same kind of decision, just for nearest-neighbor search instead of range scans — and semantic-cache-engine's schema already made that call today's lookup path depends on.

Why Exact Nearest-Neighbor Search Doesn't Scale

Finding the truly closest vector to a query is simple to describe: compute the distance to every stored vector, keep the smallest. It's also linear in the number of rows, which is fine at a few thousand vectors and unusable at millions — a cache table that's supposed to save latency can't spend more time searching for a match than the inference call it's trying to avoid.

So what: approximate nearest-neighbor (ANN) search exists because exact search's correctness guarantee isn't worth its cost at scale — trading a small, bounded chance of missing the true closest match for a large, predictable speedup is the better deal once the table is big enough to matter.

DS analogy — an airport terminal's two-tier signage, not a single long hallway
Finding your gate by reading every door in a mile-long terminal is exact search: correct, but slow enough to miss your flight. Real terminals use two tiers of signage instead — big overhead signs that jump you to the right wing in a few glances, then small gate-number signs that narrow it down once you're close. You give up the guarantee of reading every door and accept that, on the rarest occasion, a sign might be angled wrong — in exchange for finding your gate in under a minute instead of an hour.

IVFFlat: Zones Decided Before You Know How Full They'll Get

IVFFlat clusters the vector space into a fixed number of buckets — the lists parameter — chosen by running a clustering pass over a representative sample of the data before the index can answer a single query. A search only checks the handful of buckets nearest the query vector instead of every row, which is where the speedup comes from.

The catch is in that word "representative": the clustering pass needs enough rows to produce buckets that reflect the data's actual shape, so an index built on a mostly-empty table starts with poorly-shaped zones and keeps that shape as more rows arrive. A cache table starts at zero rows per tenant and grows continuously — the exact condition IVFFlat's training step handles worst.

So what: IVFFlat's zones are drawn on a map before the city is built, and a cache that starts empty and grows forever is a city that never stops changing shape.

HNSW: A Layered Graph That Builds as It Goes

HNSW (Hierarchical Navigable Small World) takes a different approach: instead of pre-computing zones, it builds a multi-layer graph where each new vector gets linked to a handful of its nearest existing neighbors — m links per node — as it's inserted. The top layer has few nodes and long-range links for big jumps across the space; each layer below adds more nodes and shorter links, until the bottom layer holds every vector with only its closest neighbors connected.

A search starts at the top layer, hops toward the query vector using the long-range links, then drops down a layer and repeats with progressively finer links — the same two-tier structure the airport analogy described, except the graph builds itself one insertion at a time instead of requiring a training pass over a finished dataset. ef_construction controls how thorough that per-insertion linking search is: higher values produce a better-connected graph at the cost of slower writes.

Why This Is a MergeTree-Key Decision, Not a Runtime Flag

A MergeTree table's ORDER BY shapes which columns sit next to each other on disk, and Day 34's post on this series covered why getting that wrong means rewriting the table rather than tuning a setting. A pgvector index type is the same category of decision: schema/001_semantic_cache_entries.sql builds hnsw (embedding vector_cosine_ops) once, at table-creation time, and switching to IVFFlat later means dropping and rebuilding the index against however much data has accumulated by then — not flipping a query-time flag.

So what: the reason to reason about IVFFlat vs HNSW before writing a single query is the same reason to reason about a MergeTree ORDER BY before the first insert — both are physical layout decisions wearing an index-type name, and physical layout decisions are exactly the ones that punish being deferred.

What Today's Code Actually Does With It

pkg/cachestore.FindNearest doesn't specify the index by name in its query — it runs ORDER BY embedding <=> $1 LIMIT 1 and lets Postgres's planner choose the hnsw index the schema already declared, the same way a query that filters on a MergeTree's sort columns lets ClickHouse's planner use the primary index without being told to. pkg/lookup.Lookup then compares the single nearest candidate's cosine similarity against the tenant's configured threshold before deciding it's a hit — a decision layered entirely on top of the index, not inside it.

So what: the index type determines whether the nearest-neighbor candidate is found fast and reliably; the threshold determines whether that candidate is trusted — two separate decisions that only work correctly if each one is right on its own terms.

What This Post Doesn't Prove

The honest gap: this post argues HNSW's incremental-build property from how the algorithm works, not from a measured recall or query-per-second number against semantic-cache-engine's actual table, because there's no live pgvector instance in this sandbox to run either index against real data. m=16 and ef_construction=64 are the schema's chosen values, not benchmarked ones — they're reasonable defaults, not numbers earned by measurement yet.

So what: "HNSW handles a growing table better than IVFFlat" is a claim about the algorithms that's true independent of this specific deployment; "16 and 64 are the right values for this workload" is a claim only a QPS and recall benchmark against real traffic can make, and this post only earns the first one.
