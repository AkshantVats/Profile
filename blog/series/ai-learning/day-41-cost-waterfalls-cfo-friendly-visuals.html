Day 41 — Cost Waterfalls — CFO-Friendly Visuals

A table of numbers tells you which tool costs the most. A waterfall chart makes someone act on it. Waterfall beats table when persuading a team to drop a tool, and today's code builds the pipeline from trace spans to Grafana waterfall.

I’ve watched an engineering team spend thirty minutes debating a cost breakdown spreadsheet and reach no conclusion. I’ve watched the same underlying numbers, redrawn as a stacked bar chart, produce an immediate decision: “cut that tool, it’s eating 60% of our per-trace budget.”

The difference isn’t the data. It’s the cognitive load of comparing bar heights versus parsing decimal columns, and that difference is the entire reason today’s code exists: waterfall beats table when persuading a team to drop a tool.

What exclusive time is and why it matters for cost

A span’s total duration is how long it ran, start to finish. Its exclusive time is how long it ran excluding the time spent waiting on its own children — the parent wasn’t doing anything expensive while its children were running, it was just waiting for them to finish.

For cost, exclusive time is the more honest number, because the tokens burned during a child span belong to that child, not to the parent that called it. Flame graphs popularized this exact idea for CPU profiling: the width of a frame represents time actually spent in that function, not delegated to something it called.

exclusive_time(span) = span.duration - Σ(direct child span durations)

A root span that ran for 848ms with children totaling 840ms has 8ms of exclusive time. That 8ms is the agent’s own reasoning step — the decision-making between tool calls — and the remaining 840ms belongs entirely to whichever child actually did the work.

Ranking spans by exclusive time instead of total duration reorders the whole list: the slow-looking root span drops near zero, and the leaf tool that actually consumed 840ms of compute rises to the top. That reordering is rarely where anyone expected to look first.

Why cost waterfalls work on executives

Humans compare lengths faster than they compare numbers. A bar where code_interpreter is six times the height of search_web communicates in one glance what a table communicates in thirty seconds of column-scanning — this isn’t a design preference, it’s the pre-attentive visual system doing work the cortex would otherwise have to do manually.

A waterfall chart sorts bars largest to smallest, left to right, and that shape has a name in cost accounting: a Pareto chart. It shows the total, the dominant item, and how much the long tail matters, all in one glance, with zero arithmetic required from the viewer.

DS analogy — the sorted grocery receipt
A grocery receipt sorted by price instead of by aisle instantly shows you that the lobster costs more than everything else on the list combined. You don’t need to sum the vegetables and compare totals by hand. The sort order does the arithmetic for you, before you’ve read a single number.

Engineers reading a cost table ask “what’s the percentage,” and reach for a calculator. Engineers reading a waterfall chart ask “what replaces that top bar,” and reach for alternatives instead. The first question is arithmetic; the second is architecture, and the chart produces the better question automatically.

Building the waterfall data pipeline

The ClickHouse tool_calls table already carries cost_usd per span, computed from token count times model price back on Day 39. The waterfall query filters to costed spans and orders them descending before Go ever sees them:

SELECT span_id, tool_name, vendor, cost_usd
FROM tool_calls
WHERE trace_id = ?
  AND cost_usd > 0
ORDER BY cost_usd DESC

Aggregation groups by tool and vendor together, because an agent calling search_web four times in one trace should produce one bar with the summed cost, not four separate slivers. The N+1 problem from Day 40 and the cost-visualization problem here are the same shape viewed from different angles.

Four steps — query, aggregate, sort, render — and none of them individually interesting; the value is that they compose without a line of custom frontend code.

Exclusive time and bottleneck rank

traceforge bottleneck --trace-id <id> layers exclusive time on top of the dependency graph from Day 40. For every span it computes the same formula from the top of this post, then ranks the results descending — rank one is the bottleneck, the span consuming the most time on its own behalf.

Rank  Tool             Vendor     Excl. Time   Total Time
1     code_interpreter anthropic    840ms        840ms
2     search_web       openai       380ms        380ms
3     plan_task        openai          8ms        848ms

plan_task shows a total time of 848ms but an exclusive time of 8ms — it spent 840ms waiting on code_interpreter, not doing anything itself. Optimizing plan_task would save 8ms; optimizing code_interpreter would save 840ms, and the ranking makes that choice obvious without anyone having to reason about it by hand.

The CFO version vs the engineer version

The same underlying data answers two different questions for two different audiences. traceforge graph gives the engineer version: topological order, cycle check, N+1 alerts, an exclusive time table — it answers “what happened in this trace, and what’s wrong with it.”

traceforge waterfall gives the CFO version: one Grafana bar chart, one number per tool, sorted by cost — it answers “where is our AI budget going, and which tool should we cut.” Grafana’s Bar Gauge panel already handles currency formatting, threshold color gradients, and drill-down links, so feeding it sorted JSON takes an hour instead of the weeks a custom dashboard would cost.

The one missing piece is an HTTP wrapper, because traceforge waterfall writes JSON to stdout and Grafana’s Simple JSON datasource needs an endpoint to poll instead:

http.HandleFunc("/query", func(w http.ResponseWriter, r *http.Request) {
    traceID := r.URL.Query().Get("trace_id")
    payload := waterfall.Build(traceID, fetchSpans(traceID))
    json.NewEncoder(w).Encode(payload)
})

Ten lines, not production-hardened, but enough to wire a real Grafana panel for a team demo that produces an actual budget conversation. The CFO version deliberately shows less than the engineer version — not everything, just the one thing that produces a decision.

A table answers "how much." A waterfall answers "so what do we do about it." Same numbers, different chart, completely different meeting.

The lens this post and Day 40’s graph package share is the same one: model the trace correctly — as a DAG, with exclusive time computed per node — and both the engineer’s debugging table and the CFO’s waterfall chart fall out of the same underlying structure, rendered for two different readers.
