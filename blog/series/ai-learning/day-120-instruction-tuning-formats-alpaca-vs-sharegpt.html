Day 120 — Instruction Tuning Formats — Alpaca vs ShareGPT

Schema choice affects tokenizer efficiency: a fixed three-field form versus a named-turn transcript, and why a single export CLI has to support both instead of picking a winner.

AS
Akshant Sharma
AI Learning · Day 120 of 150
August 19, 2026
8 min read

Export CLI supports both formats. That's today's hook, and it's a decision fixed on paper today, not code shipped today — data-prep-pipeline/DESIGN.md, the design doc that opens FineForge's first module, specs two different JSON shapes a training row can leave the pipeline in in.

The two shapes are Alpaca and ShareGPT, and the first thing worth saying is that neither one is a de facto standard everyone just agrees on. They're two different bets about what an instruction-tuning example looks like, and the bet you make changes how many tokens your fine-tuning run spends before it sees a single real word.

This post is about why a pipeline that could pick one format and move on instead builds a router that picks per row — using the same field names and the same routing signal data-prep-pipeline/DESIGN.md fixes today.

Where a Training Row Comes From

Before either format enters the picture, a row has to earn its way into the export at all. infra_ai.judge_scores (Day 99) is the quality gate: an automated LLM judge grades every production response and stores the weighted result as judge_score, and Day 121's connector pulls the last 30 days of rows above the high-quality threshold, the same one this arc's own dataset dashboard (Day 125) will later chart against.

Passing that gate only proves a response was good. It says nothing about whether the underlying request was a single question-and-answer or a multi-step agent run with tool calls in between — and that distinction is exactly what decides which export format a row gets.

So what: a judge score can tell you a row is worth training on, but it can't tell you what shape to train on it in — that answer lives in a completely different table.

Alpaca: The Fixed Three-Field Form

Alpaca format is flat: every row is exactly three fields, no more, no fewer, regardless of what actually happened in the underlying conversation.

{
  "instruction": "Summarize the customer's refund request in two sentences.",
  "input": "",
  "output": "The customer is requesting a refund for order #48213 due to a damaged item received on delivery. They have already attached photo evidence and are asking for either a replacement or full refund within 5 business days."
}

instruction is the task, input is optional extra context (often left empty, as above, when the instruction is self-contained), and output is the one span of text the model is actually being trained to produce. There's no field for "and then the model called a tool" — if that happened, Alpaca has nowhere to put it.

That constraint is a feature for the common case, not a limitation someone forgot to fix: the overwhelming majority of LensAI's traffic is one prompt, one response, no intermediate steps.

So what: a three-field form is the smallest shape that can carry a single-turn exchange honestly, which is exactly why it stays the default rather than something the pipeline reaches for only when nothing simpler will do.

ShareGPT: The Named-Turn Transcript

ShareGPT format drops the fixed field count entirely and replaces it with a list of role-tagged turns, as many as the conversation actually took:

{
  "conversations": [
    { "from": "system", "value": "You are a support agent with access to the order lookup tool." },
    { "from": "human", "value": "Where is my order #48213?" },
    { "from": "function_call", "value": "lookup_order(order_id=\"48213\")" },
    { "from": "observation", "value": "{\"status\": \"in_transit\", \"eta\": \"2026-08-21\"}" },
    { "from": "gpt", "value": "Order #48213 is in transit and expected to arrive by August 21." }
  ]
}

Every turn names who spoke (system, human, function_call, observation, gpt) and what they said, in order. A tool call and its result are just two more turns in the same list, not a shape Alpaca would have to bolt on as an afterthought.

The cost of that flexibility is verbosity: the same simple refund-summary example from the Alpaca block above would be three turns in ShareGPT (system, human, gpt) for information Alpaca already carried in two fields. So what: ShareGPT isn't strictly richer, it's differently shaped, and using it for a row that never needed more than instruction/output is paying a tax for a capability that row doesn't use.

DS analogy — a recipe card versus a group chat transcript
A recipe card has exactly three sections, always: ingredients, method, result. It's perfect as long as the dish really is one self-contained thing — but try to fit a five-course tasting menu, with a substitution decided mid-meal, onto one card and you either cram unrelated steps into "method" or start stapling extra cards together in the wrong order. A group chat transcript has no fixed section count; it's just named messages in sequence, exactly as many as the conversation actually took. That's needless overhead for a two-line "what's your return policy?" exchange, but it's the only shape that can honestly represent someone asking a question, a bot calling a tool, the tool replying, and only then the bot answering.

So what: the format that wins isn't the more powerful one in the abstract, it's the one whose shape matches how many things actually happened — a recipe card for one dish, a transcript for a conversation with real back-and-forth.

Routing by Trace ID, Not by Guessing

data-prep-pipeline/DESIGN.md doesn't leave the Alpaca-vs-ShareGPT choice to a human eyeballing each row. It routes on a signal that already exists: lensai.agent_spans.trace_id (TraceForge, Day 34), the same column that groups every tool call and sub-agent hop under one agent run.

A request_id whose trace_id has exactly one non-root span is a single-turn call — one prompt, one response, no chained steps — and gets exported as Alpaca. A trace_id with more than one non-root span means a tool was called or a sub-agent ran, and that row gets exported as ShareGPT, because Alpaca has no field to hold the intermediate step.

Why Tokenizer Efficiency Actually Differs

Here's the part the format choice actually costs you at train time. Alpaca's three fields aren't tokens on their own — they only become tokens once a prompt template wraps them, and the common one looks like ### Instruction:\n{instruction}\n\n### Input:\n{input}\n\n### Response:\n{output}.

Every single Alpaca example pays that template's fixed overhead, and worse, the template is a hand-rolled guess about where the model's own output starts — get the loss-masking boundary wrong (train on the instruction text too, not just the response) and the model learns to echo its own prompt back some fraction of the time.

ShareGPT's role-tagged turns sidestep both problems by mapping directly onto a tokenizer's built-in chat template (apply_chat_template, in most tokenizer libraries): the wrapping tokens are the exact ones the model will see at inference time, not a hand-rolled approximation of them, and masking every non-gpt turn out of the loss is a mechanical role check instead of a string-offset guess.

So what: "schema choice affects tokenizer efficiency" isn't an abstract framing — it's the difference between every training example paying a hand-rolled template's overhead and possible masking bugs, versus every example using the same chat template the model already speaks at inference time.

The Gap This Design Names Instead of Hiding

Both schemas above assume a row has a prompt_text and a response_text to put into them. Every ClickHouse table this pipeline actually reads — judge_scores, quality_scores, agent_spans, even inference_events — stores scores, token counts, and hashes, and deliberately never the words themselves.

006_shadow_eval.sql's own header comment says as much directly: full request/response bodies live only in a Kafka message, "never duplicated permanently in ClickHouse." That's not an oversight this design papers over — it's the reason data-prep-pipeline/DESIGN.md proposes a new table, infra_ai.conversation_text, with a 30-day TTL matching the pipeline's own read window, rather than assuming the text was sitting there all along. (A TTL — time-to-live — is ClickHouse automatically deleting rows once they age past that window, so raw text never accumulates longer than the pipeline actually needs it.)

So what: naming a real gap in plain language, in the same document that specs the two export formats around it, is worth more to Day 121's connector than a design that quietly assumed the text already existed and left that assumption to be discovered mid-implementation.

A format isn't a syntax choice. It's a claim about how many things happened — and the row that decides between them never has to know that; it just counts spans.

The generalizable shape underneath today's two JSON blocks is simple: match your data's actual structure to your schema's actual structure, and let a real signal already in your system — not a human glancing at each row — make the call. That's a smaller idea than "instruction tuning," but it's the one that decides whether a fine-tuning run spends its first few thousand steps learning your prompt template's quirks or learning the task you actually wanted it to learn.
