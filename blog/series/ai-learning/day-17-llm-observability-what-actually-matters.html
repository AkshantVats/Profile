Add the fields for tool spans and cache hits now. Don’t wait. Retrofitting an observability schema after 100 million events are already in ClickHouse is the Agoda cardinality migration all over again: painful, expensive, and entirely avoidable if you had asked the right question earlier.

I hit this exact wall while designing the InferenceEvent schema for LensAI. The instinct was to start minimal — just model_id, latency_ms, prompt_tokens, completion_tokens, tenant_id. Ship fast, add later. The problem is that “add later” in a high-throughput ClickHouse table with billions of rows means a migration that takes hours and potentially rebuilds materialized views.

Schema is an infrastructure decision, not a data decision. Get the field list right before the first row lands.

The cardinality lesson from Agoda

At Agoda, WhiteFalcon’s TSDB ingested 1.5 trillion events per day. A cardinality mistake at the schema level — adding a label that was actually an identifier, not a dimension — could silently double index memory usage. The WhiteFalcon team had a rule: before any new label, enumerate the bounded set of values it can take. If you cannot enumerate it, it is a metric field, not a label.

LLM observability has the same cardinality problem in a different shape. Think of it as a filing cabinet with drawers. Each drawer is a dimension (model_id, tenant_id, provider). Each drawer has a bounded set of folders inside. A request_id is not a drawer — it is a unique label on each individual document. Storing it as a Prometheus label would mean one time series per API call. Instead, it belongs in ClickHouse as a row attribute, not a metric dimension.

The schema question is always the same: which fields go in the index (dimensions, bounded cardinality) and which go in the row (attributes, unbounded)? Getting this wrong creates two failure modes: under-dimensioned data that can’t answer “which model is slow?” and over-dimensioned data that explodes the index.

What actually matters at the infrastructure layer

The fields that drive operational decisions are not the same as the fields that are interesting for ML evaluation. SDK-oriented platforms like Arize optimize for the full prompt + response cycle because their use case is model quality evaluation: did the model answer correctly, did it use tools correctly, did it hallucinate? That requires prompt text, response text, and structured tool spans.

Infrastructure-layer observability has a different question: is the system healthy and is the cost under control? That requires a different field set.

The infrastructure layer questions are: which tenant is spending the most on gpt-4o? Is the claude-opus-4-8 prefill latency trending up across all tenants or just one? Are there processes making OpenAI calls without going through the approved gateway? These are answerable from the eight fields eBPF captures without any SDK.

The four fields to add now

After the schema diff, four fields should be in the initial schema even though LensAI does not yet capture them. Not capturing them is fine. Not having the column is a migration debt.

cache_hit (boolean): OpenAI and Anthropic both have prompt caching. A request that hits the prompt cache costs 10–50% less and runs in less time. Without a cache_hit field, your cost and latency numbers are a blend of cached and uncached requests. When prompt caching is adopted widely, every ClickHouse query that aggregates cost will silently underestimate uncached cost. The fix is a nullable boolean now.

tool_call_count (integer): Tool calls are a growing share of production LLM workloads. They do not require full span tracing to be useful — just knowing how many tool calls occurred in a request tells you whether latency anomalies come from multi-hop agent loops vs. single-request inference. A count is capturable from the response body.

streaming (boolean): Streaming responses have fundamentally different latency profiles. Mixing streaming and non-streaming requests in the same latency_ms P99 is like mixing OLAP and OLTP query times. Knowing which is which before you have millions of rows is essential for correct SLO computation.

model_version (string): Model providers alias their models. gpt-4o is a moving target — the model behind that alias has changed multiple times. When a latency regression appears after a model update, distinguishing gpt-4o-2024-08-06 from gpt-4o-2025-01-29 requires the model version, not just the alias. Some providers return this in the response; it is capturable now.

LensAI schema decision
All four fields are now in the InferenceEvent struct as nullable fields. None are populated by the current eBPF capture — they are zero values. The column exists in ClickHouse from day one. When a future capture path adds cache hit detection or streaming response parsing, there is no schema migration required.

The eBPF observability gap

The fields eBPF cannot capture without full TLS interception are worth naming honestly. Prompt text and response text are the big gap. SDK-based platforms like Langfuse collect the full conversation; eBPF sees only the HTTP metadata.

This is a feature, not a limitation, for the infrastructure use case. Storing prompt text at LLM API volumes is a significant storage and privacy concern. A model_id + prompt_tokens + latency_ms + tenant_id row is roughly 100 bytes. A full prompt + response at 4K tokens is 8–16KB. The storage ratio is 80–160×. For infrastructure cost attribution and SLO monitoring, the metadata is the right layer.

The two layers are complementary, not competing. LensAI’s value is zero-SDK coverage — every process making LLM API calls is captured, including shadow usage that never went through the SDK. The SDK layer goes deeper on the calls the application team intentionally instruments.

Takeaway

Three decisions to make before the first event lands in your LLM observability store:

  1. Separate index dimensions from row attributes. model_id, tenant_id, provider are bounded dimensions — they belong in the index. request_id is an attribute — it belongs in the row only. Mixing them creates the cardinality explosion Agoda spent months unwinding.
  2. Add nullable columns for fields you don’t capture yet. Cache hit, tool call count, streaming, model version. Zero value in the column is fine. Missing the column is a debt that compounds with every GB of data you write.
  3. Decide which layer each field belongs to. Metadata (eBPF) or full content (SDK). These are not the same system. Build the infrastructure layer first — it covers 100% of processes at low cost. Add the SDK layer where you need conversation-level tracing.

The schema is the contract. Everything downstream — Grafana dashboards, cost attribution queries, anomaly detection — builds on it. Get it right before the first row, not after the first million.
