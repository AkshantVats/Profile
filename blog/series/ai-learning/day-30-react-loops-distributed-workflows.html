Day 30 — ReAct Loops as Distributed Workflows

Planner → tools → memory — state machine, not magic

AS
Akshant Sharma
AI Learning · Day 30 of 150
July 3, 2026
14 min read

When I first encountered ReAct — the reasoning-then-acting loop that underlies most tool-using AI agents — my instinct was to model it like a human decision process: fluid, contextual, hard to decompose. That instinct was wrong, and it led me to treat agent failures as inherently mysterious. The mental model that actually works — the one that makes agent behaviour predictable and debuggable — is a state machine borrowed from distributed systems: the saga pattern.

Draw the loop as a saga. Make each tool call a compensatable step with a timeout. Track state transitions in a durable log. Suddenly, the “thinking” between steps is just the orchestrator deciding which compensating transaction to execute next.

When an AI agent fails — wrong output, stuck loop, incomplete result — diagnosis is much faster if you know which state transition failed. “The AI is confused” gives you nothing. “The saga is stuck at Step 4 — tool call returned ERROR and the orchestrator has no compensating path defined” gives you exactly the right fix.

ReAct: The State Machine Underneath

DS analogy — saga orchestrator
A ReAct loop is a distributed saga. The planner is the saga orchestrator. Each tool call is a compensatable step with a timeout and a defined rollback. Memory updates between steps are the saga’s durable log — the record of what has been done that survives a crash.

ReAct stands for Reasoning and Acting. The loop has four states: Observe (read current context), Reason (generate a thought — this is the LLM’s inference pass), Act (call a tool or produce a final answer), Update (write tool result back into context). The loop continues until Act produces a final answer rather than a tool call.

What makes this a state machine is the durable dependency between steps. The Observe step at iteration N reads accumulated tool results from iterations 1 through N-1. The Reason step generates a thought conditioned on accumulated context. The Act step selects a tool or terminates based on Reason output. Each iteration’s Act output modifies the context for the next iteration’s Observe — this is a state machine.

The “magic” of ReAct is that the state transition function (Reason → Act) is implemented by an LLM rather than a hardcoded if-else tree. That’s interesting but doesn’t make it fundamentally different from any other state machine. The state is still defined, transitions deterministic given fixed inputs, terminal condition observable. You can instrument it exactly like any other state machine: trace each state transition, log inputs and outputs, alert on loops that don’t terminate.

A ReAct loop is a state machine with a model-implemented transition function — instrumentable, debuggable, and observable using the same techniques you’d apply to any async multi-step process.

The Saga Pattern: Tool Calls as Compensatable Steps

In distributed systems, a saga is a sequence of local transactions where each transaction publishes an event triggering the next. If a transaction fails, compensating transactions undo the partial work. The saga pattern solves the same problem a ReAct loop solves: how do you perform a multi-step operation reliably when each step might fail, and when you can’t lock all resources for the entire duration?

Mapping ReAct to saga: each tool call is a local transaction that reads from context (the saga’s durable log) and produces a result written back into context. If the tool call fails, the saga needs a compensating path: retry with different parameters, try a different tool, or terminate with partial result. The language model’s Reason step is the saga orchestrator making this decision.

The critical saga property that applies to ReAct loops is compensatability: every step that can fail should have a defined compensating action. For a file-editing agent, “write a file” should have “restore the backup.” For a web-browsing agent, “navigate to URL” should have “return to previous URL.” In practice most ReAct implementations don’t define explicit compensations — they rely on the model to “figure out” recovery. This works until it doesn’t, and when it doesn’t, there’s no structured way to diagnose why.

Non-software analogy — airport check-in
An airport check-in process with multiple steps is a saga. Passenger scans passport (step 1), selects seat (step 2), pays for baggage (step 3), prints boarding pass (step 4). If step 3 fails — payment declined — compensating transactions release the held seat (compensate step 2) and invalidate the passport scan session (compensate step 1). Without defined compensations, a failed payment leaves the seat permanently held. A ReAct loop with no compensating paths is that check-in system.

Thinking of each tool call as a compensatable step forces you to define what “undo” means for every action the agent can take — exactly the discipline that prevents an agent from getting stuck in a partially-applied state with no recovery path.

Timeouts, Loops, and Terminal Conditions

Every distributed system has timeout semantics — a maximum duration after which an operation is declared failed and a compensating path triggered. ReAct loops without explicit timeouts per tool call have an implicit timeout determined by the LLM’s context window limit and max-tokens setting. This is not a design choice — it’s an accident of implementation. When a tool call hangs, the agent has no way to detect it and trigger a compensating path without an explicit timeout.

Terminal condition detection is the second gap. A saga terminates when all transactions complete successfully or a compensating transaction fails to produce a consistent state. A ReAct loop terminates when the model produces a final answer. But what prevents an agent from an infinite sequence of tool calls, each moving the plan slightly forward without ever reaching a final answer? Nothing, unless the loop has an explicit maximum step count or termination condition checker.

Both problems have the same root cause: the distributed systems engineering concepts governing saga design haven’t been applied to agent design. Saga implementations have explicit timeout specifications per transaction and explicit terminal failure states. Agent frameworks typically delegate both to the model — the model must execute the task AND govern its own execution. Separating concerns — putting timeouts and terminal conditions in the agent harness, not the model — is the architectural improvement that makes agents more reliable.

Non-software analogy — traffic light maximum
A timeout in a ReAct loop is like a traffic light cycle with a maximum green duration. Without a maximum, a particularly busy road could hold the light green indefinitely, starving cross traffic. The maximum isn’t about the common case — most cycles complete well under the maximum. It’s about the rare case where the detector loop fails and keeps the light green forever. Timeouts handle the rare case where a tool call hangs.

Explicit per-step timeouts and maximum iteration counts in the agent harness, not the model, are the two structural properties that separate a reliable ReAct agent from an unreliable one — both have direct precedents in saga pattern design.

Memory as the Saga's Durable Log

A saga’s durable log records which transactions completed successfully. It allows a saga to resume after a crash: read the log, determine which transactions completed, determine which compensating transactions need to run, continue from the last consistent state. Without durability, a crash requires starting the entire saga from the beginning.

In a ReAct loop, the context window is the memory. It records which tool calls were made, what results they returned, what reasoning the model produced after each. For a single-session run, the context window is durable in the sense that it accumulates across iterations. But the context window is not durable across sessions — if the agent process crashes, context is lost. Resuming requires starting the loop from scratch.

This is the gap that motivates externalising memory. An external memory store — a vector database, a key-value store, a structured span log — is the saga’s durable log. Each tool call’s result is written to the external store as it completes. If the agent crashes at step 7, the next run can query the store to find steps 1 through 6 completed and resume from step 7. This is exactly what agent-trace-collector’s span schema enables: each span is a record of a completed saga step, persistent across agent restarts, queryable to reconstruct execution state.

Non-software analogy — construction punch list
External agent memory is like a construction project’s punch list. The punch list records every completed task: “drywall installed — room 3, floor 2” is checked off when the crew finishes and cannot be un-checked. If a crew is replaced mid-project, the new crew reads the punch list to find what’s done and what remains. The context window is the crew’s verbal briefing at the start of each shift — useful, but lost when the crew goes home. The external memory store survives restarts.

Externalising memory as a structured log — one record per completed step, persistent across agent restarts — converts a ReAct agent from a single-session process into a resumable distributed workflow, with the same durability properties as a properly implemented saga.

Once you think of a ReAct loop as a saga, the instrumentation question answers itself. A saga’s durable log needs to record: which transaction ran, when it started, how long it took, what its result was, which transaction triggered it. This is exactly an OTel span: span_id, start_time, latency_ms, status, and parent_span_id. The saga’s dependency graph — “transaction 4 was triggered by the result of transaction 3” — is the span’s parent_span_id. The execution tree of a ReAct loop is a span tree.

The practical consequence: building observability for a ReAct agent is not a new problem. It’s the same problem as building observability for a microservice call chain. Same tooling: OTel spans, Jaeger or Grafana Tempo for visualisation, ClickHouse for aggregation queries. Same schema: trace ID for root operation, span ID per step, parent span ID for dependency. What’s new is that the “service” is an LLM inference pass and the “operation” is a tool call — the schema needs to capture tool_name, model, tokens, and cost_usd, which standard OTel schemas don’t include. The schema extension is small. The infrastructure reuse is large.

This is exactly what agent-trace-collector encodes. The Span schema in pkg/schema/span.go is a standard OTel span with four additional fields: tool_name, model, input_tokens/output_tokens, and cost_usd. Everything else — trace ID, span ID, parent span ID, status, latency — is standard OTel. The span forwards to a standard OTel Collector, which routes to ClickHouse via the same pipeline built in OSS-03. The agent observability infrastructure reuses every component from the LLM inference observability infrastructure.

Non-software analogy — package scanning + GPS
Instrumenting a ReAct loop with OTel spans is like adding GPS tracking to a delivery route that already has package scanning. The scanning system tracks: when a package was scanned, where, which delivery it belongs to. Adding four new fields (tool_name, model, tokens, cost_usd) to each scan record gives you richer information without building a new tracking system. The new fields extend the existing schema. The existing infrastructure handles collection, storage, and visualisation.

A ReAct agent’s execution is naturally representable as an OTel span tree, which means the entire observability problem is solved by adding four fields to a standard span schema — no custom UI, no agent-specific visualisation tooling, no new storage system.
