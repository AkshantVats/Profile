Day 7 of Learning LLM Inference — Prompt Caching at the Infrastructure Layer

7 of N — AI Learning Series. Prefix reuse as KV-cache hit rate for dollars — provider caches, cache keys, and the third input bucket on your rate card.

AI Learning · Day 7 of N

I was sending the same system prompt on repeat — a long tool schema plus a fixed RAG blob, about eight thousand tokens — while wiring LensAI's POST /ingest endpoint. Request two came back faster and cheaper. Completion tokens matched request one exactly. The provider was not suddenly more efficient at decode; it had skipped most of prefill because the prefix bytes had not changed.

The usage block named what happened: cache_read_input_tokens and cache_creation_input_tokens on Anthropic, prompt_tokens_details.cached_tokens on OpenAI. The provider had stored the prefix KV from the first call and served it back on the second — same idea as a CDN edge hit, except the "origin fetch" is a full prefill pass billed at input rate.

Day 3 split prompt vs completion on the rate card and argued that cost_usd must land on every row. Prompt caching adds tiers on the input side — cached read, cache creation, and fresh uncached bytes — each priced differently. That is the third dimension this post covers: what hashes together, what invalidates, and what LensAI's InferenceEvent needs before dashboards can explain dollars and TTFT diverging while completion length stays flat.

Two different KV caches

Day 1 was about the session KV cache: one request, growing through decode, living in GPU VRAM, memory-bandwidth-bound at each step. Provider prompt caching is a different mechanism — a shared prefix held across requests on the provider's fleet, billed at a discounted tier.

Session KV cache (Day 1)Provider prompt cache (Day 7)
ScopeOne request; grows through decodeShared prefix across requests
LivesYour GPU / vLLM VRAMProvider infrastructure
Miss costBandwidth per decode stepFull prefill charge + latency
Hit benefitAvoid recomputing prior tokens in this requestAvoid recomputing shared prefix across requests

Day 6 shrank weight tensors with quantization; prompt caching shrinks repeated prefill work. Orthogonal knobs on the same bill — do not confuse them.

Cache-control at the API boundary

Anthropic makes the contract explicit. You mark content blocks with cache_control: { "type": "ephemeral" } at breakpoints — the prefix must exceed a minimum token length for caching to engage. The usage response carries input_tokens, output_tokens, plus cache_creation_input_tokens and cache_read_input_tokens. Cache read is cheaper than base input; cache creation pays a small premium to warm the prefix. TTL is short — on the order of five minutes, so think Cache-Control: max-age, not durable storage.

OpenAI is more automatic on supported models: identical long prefixes can hit without explicit breakpoints, and the cached-tokens detail surfaces under usage.prompt_tokens_details. The mechanics differ from Anthropic's opt-in model, but the economic shape is the same: repeated bytes cost less than fresh ones because the provider already holds the prefix KV.

What actually hashes together

Cache keys are bytes, not intentions. Five rules I keep in code review:

  1. Byte-stable prefix — Same text, same bytes. Whitespace, JSON key order, tool definition order all matter.
  2. Pin immutable blocks first — System prompt, tool schemas, long RAG context go at the top; the user message lives in the suffix that changes every turn.
  3. Breakpoints are placement — On Anthropic, moving a cache_control boundary changes what enters the key.
  4. Per-tenant isolation — Include tenant_id in logical key material where the API allows. LensAI already keys rollups on tenant_id at ingest, so do not rely on "probably different" traffic patterns for cache separation.
  5. Model version in the key — A model_id bump is a new origin. Routing changes that swap the backing model invalidate every warm prefix.
[ system │ tools │ RAG corpus ]  ← cache breakpoint(s)
[ user message + session state ] ← usually outside cache

I burned an afternoon on zero percent hit rate with "the same" RAG blob in my local test harness. Two serializers were emitting tool JSON with different key ordering — semantically identical, byte-different. Every request was a miss and I paid creation on every call until I pinned one canonical byte layout. The lesson is the same one that makes content-addressable storage fragile: semantic equivalence does not guarantee byte equivalence, and the hash only sees bytes.

Stuffing the user id into the cached prefix destroys hit rate the same way random per-request trace ids destroyed comparability in Day 5's sampling story: you optimized for uniqueness when the system rewards reuse.

Third bucket on the rate card

Day 3 split prompt vs completion tokens. Prompt caching adds tiers on the input side:

cost_usd ≈ (fresh_input_tokens / 1e6) × rate_input
         + (cache_read_input_tokens / 1e6) × rate_cache_read
         + (cache_creation_input_tokens / 1e6) × rate_cache_write
         + (completion_tokens / 1e6) × rate_output

Illustrative Sonnet-class tiers as of May 2026: base input ~$3/M, cache write ~$3.75/M, cache read ~$0.30/M. The read tier is an order of magnitude cheaper than warming the prefix — so the amortization story is clear. One creation charge pays for itself after a handful of cache reads, and every subsequent hit within TTL is nearly free on the input side.

Worked example

8,000-token stable prefix, 200-token user suffix, 400 completion tokens. Request one (cold prefix) pays creation on most of the prefix plus full-rate suffix plus completion. Request two within TTL sees ~8k cache_read_input_tokens, ~200 fresh input, same 400 completion — TTFT drops because prefill only runs on the 200-token suffix, and cost_usd drops because eight thousand tokens moved from $3/M to $0.30/M.

Once cache tiers land on every event row, LensAI can chart cache_hit_ratio = cache_read / (cache_read + cache_creation + fresh_input) grouped by tenant_id and model_id in ClickHouse. Alert on creation spikes — they mean prefix churn — not only on sum(cost_usd), because a cost spike caused by cache invalidation looks different from one caused by longer completions.

A prompt cache hit is a KV-cache hit for the prefix — priced like a CDN hit, invalidated like one.

What LensAI needs next

Today in infra-ai-streaming: InferenceEvent in ingest.rs carries prompt_tokens, completion_tokens, and producer-computed cost_usd. Ingest rejects cost_usd < 0 and latency_ms == 0, aligns X-Tenant-ID with each event's tenant_id, and forwards facts. It does not yet break out cache tiers — and that gap is why this post exists. You cannot debug prefix economics from prompt_tokens alone when half the prompt was a cache read priced at a tenth of base rate.

Producers map provider usage into cost_usd using the tiered formula; ingest keeps validating obvious lies and forwarding facts the way Day 3 described. The Grafana work that follows is a column chart of cache hit percentage by tenant and an estimated-dollars-saved panel whose counterfactual is documented in the panel footnote — not guessed.

The gateway pattern I am building against treats prompt cache like CDN rules: pin byte-stable system + tool + RAG prefixes, map provider usage into tiered cost_usd at the producer, and let ingest validate without re-pricing. Prompt caching is a prefill economics lever — complementary to pod scale-out, not a substitute for it. Today's Experience companion covers the other side: Experience 7 is about lag-driven consumer scale-out when CPU looks fine.

What I am taking away

Prefix stability is both an SLO and a FinOps control. When TTFT drops but completion_tokens stays flat, read cache fields in usage before blaming quantization, batching, or model routing — the provider may have just served your prefix from its fleet cache. The next LensAI change I owe is mapping those tiers into InferenceEvent and extending the Day 3 cost formula so that prompt_tokens stops lying about which bytes were cheap reads and which were not.
