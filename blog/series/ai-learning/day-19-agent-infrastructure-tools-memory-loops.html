Day 19 — Agent Infrastructure — Tools, Memory, Loops

Production agents need queues, idempotency, and traces — the same primitives your streaming stack already has

AI Learning · Day 19 of 150

Tool calling is RPC with hallucination risk. Your streaming stack already handles worse RPC fan-out every day. The infrastructure problem of running a production agent is not a new category — it is the same distributed systems problem dressed in a different API: durable execution, idempotent side effects, and observability over a loop that runs for seconds or minutes instead of milliseconds.

What makes agents distinct is that the “business logic” — the part that decides which tool to call and what to do with the result — is a language model call, not deterministic code. A model call has latency measured in seconds, output that varies by temperature and sampling, and the possibility of generating a tool name that doesn’t exist. The infra answer is the same one you’d apply to any non-deterministic long-running process: make it observable, make side effects idempotent, and make failures retryable without restarting from scratch.

Agent infrastructure is distributed systems infrastructure with a model on the hot path. The model is a slow, non-deterministic RPC call you can’t directly debug. Your existing queues, caches, and traces are the right answer.

Tool calling as RPC

A tool call from a model’s perspective is: “I need the result of function X with argument Y before I can continue my reasoning.” From the infrastructure perspective, it is a synchronous RPC call made by the agent loop on behalf of the model. The model generates a JSON object with the function name and arguments; the agent loop executes the function and returns the result as a new message in the conversation.

DS analogy — tool call as RPC
A single agent step is a map-reduce job with one reducer. The model generates the map instructions (which tools to call with which arguments). Your tool executor is the map layer. The model call with all results is the reduce. Unlike real map-reduce, the output of the reduce step is another set of map instructions.

The hallucination risk in tool calling is specific: the model may generate a tool name that is not in the schema, or generate arguments that fail validation. A well-designed tool layer validates the schema before executing anything. The validator is the first circuit breaker — a malformed tool call fails fast, before any side-effecting execution occurs.

Parallel tool calls matter for latency. If a model generates three tool calls in one step, executing them sequentially adds their latencies in series. Executing them concurrently cuts latency to the slowest tool.

The agent framework decides whether to execute in parallel; the underlying tool execution is standard async HTTP or function dispatch. Your existing connection pooling and timeout policies apply directly.

Tool execution is where your existing observability pays off immediately. Each tool call should emit a span: tool name, arguments (redacted if sensitive), latency, success/failure, and the token budget consumed by the result. Agents that make 10 tool calls per task generate 10 spans of tool latency data that are more actionable than the aggregate LLM call latency alone.

Memory as a tiered cache

Agent memory has three tiers that map exactly onto storage tiering: in-context (hot), retrieval (warm), and persistent (cold). In-context memory is the conversation history the model sees on every call — bounded by the context window, measured in tokens, sub-millisecond access.

Retrieval memory is a vector store lookup at each step — tens of milliseconds, semantically filtered. Persistent memory is a structured store that survives agent restarts — the equivalent of a database, with full latency of a network call.

The in-context tier is the only one that directly affects model quality. What the model sees is what it reasons about. Retrieval and persistent memory are only useful when their output enters the context.

The management problem is: what to keep in context versus what to retrieve on demand.

Think of a restaurant order pad. The server’s working memory (in-context) is what they hold at the table. The printed menu is retrieval memory — consulted when needed. The kitchen order log is persistent — survives across shifts.

A server memorizing the full menu makes errors. One looking up every item mid-conversation is slow. The right operating point is between those extremes.

Context window management is the hot-tier equivalent of Redis bucket eviction. When the context approaches the token limit, old messages get truncated or summarized. The model never sees what was truncated.

A critical fact from step 3 that was truncated by step 8 is the agent equivalent of a Redis key force-evicted before flush — gone from the reasoning path. The agent may hallucinate what it no longer remembers.

The mitigation is the same as in tiered storage: before evicting, persist to the next tier. Summarize long conversations into a compressed state that fits in context. Treat context eviction as a deliberate flush, not a silent discard.

Agent loops and durable execution

An agent loop is: call model → execute tools → check termination condition → repeat. The termination condition is the hard part. A model that never generates a “done” signal will loop forever.

Every production agent loop needs a maximum step count and a wall-clock budget, checked at each iteration before the model call.

What caught me off guard
The hardest loop failure is not infinite iteration — a step counter catches that. It’s idempotency: a tool that creates a resource (database row, Stripe charge, email send) called twice in a retry loop creates the resource twice. Idempotency keys at the tool layer are not optional. They are the difference between a retryable agent and a dangerous one.

Durable execution means: if the agent process crashes mid-loop, it resumes from the last committed step rather than starting over. The mechanism is a WAL for agent state — the same design as ebpf-llm-tracer’s consumer WAL.

Before executing a tool, write the call intent to durable storage. After receiving the result, write it. On restart, replay from the last written result.

Without durable execution, a crash at step 7 of a 10-step agent means re-executing steps 1–6 with all their side effects. With durable execution, it means re-reading steps 1–6 from the log and continuing from step 7. The difference matters in proportion to the cost of the tools being called: a web search is cheap to retry, a database mutation or API call with a fee is not.

Observability for agent loops

A single agent task generates a trace with a variable number of spans. The root span is the task; child spans are model calls and tool executions. The depth is variable because the number of loop iterations is not known in advance.

Standard distributed tracing handles this well — the trace is a tree of spans with parent-child relationships. The root span’s duration covers the entire task.

Three metrics matter most for agent health: step count per task (watches for runaway loops), token consumption per step (watches for context bloat), and tool error rate (watches for schema drift between model output and tool definitions). Step count is the agent equivalent of Kafka consumer lag — a leading indicator that something upstream is not terminating as expected.

Tracing tool calls with eBPF — which is what LensAI does — gives you the tool latency data without requiring instrumentation in the agent framework itself. An agent making HTTP calls to external APIs has those calls visible in the eBPF trace, even if the agent framework has no built-in observability. The zero-SDK instrumentation is particularly valuable for agents that use third-party frameworks where adding spans manually is impractical.

The LensAI connection

The demo harness from Day 19’s code shows the tracer working against a mock LLM server — a single-step inference call. An agent making 10 LLM calls per task generates 10 traced HTTP events in the eBPF ring buffer.

The InferenceEvent schema captures latency_ms, prompt_tokens, and completion_tokens per call. Multiply across steps and you have per-task token cost and latency breakdown without any agent-framework changes.

The eBPF overhead at 12 µs per parse+map operation is negligible relative to agent task latency of 1–60 seconds. The probe does not slow the agent. What it gives you is the full HTTP trace of every LLM call the agent made, labeled by model and tenant, in the same Kafka topic that feeds your existing ClickHouse dashboards.

Agents that make 10 HTTP calls per user request are the use case where the zero-SDK approach is most valuable. You cannot add spans to every third-party framework your agents call into. The eBPF sidecar captures the full call graph regardless of how the agent is implemented.
