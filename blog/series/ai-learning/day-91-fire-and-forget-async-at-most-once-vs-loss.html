Day 91 — Fire-and-Forget Async — At-Most-Once vs Loss

Dropping shadow traffic under load is an acceptable tradeoff. What decides that isn't the drop itself — it's whether the data was ever meant to be complete.

Akshant Sharma

Bounded channel drop metric for shadow producer. That's the one counter today's shadow-traffic-router code PR adds, and it's a strange thing to build a metric around until you sit with what it actually measures: not an error, not a bug, but a design decision working exactly as intended.

Every fire-and-forget publish is, by construction, at-most-once delivery — a message either arrives once or it doesn't arrive at all, and nothing retries it if it doesn't. The interesting engineering question was never "should we accept that." It was "what happens, precisely, at the moment the local buffer can't hold one more event."

At-Most-Once Is a Promise About the Ceiling, Not the Floor

Delivery semantics come in three flavors an inference pipeline actually has to choose between. At-least-once retries until it gets an acknowledgment, which means a message might land twice but never zero times. Exactly-once adds deduplication on top of that so it lands precisely once, at the cost of extra coordination.

At-most-once gives up the floor entirely: a message lands zero or one times, and the system never spends effort finding out which.

Fire-and-forget mirroring is at-most-once by definition, not by accident. There's no retry loop, no acknowledgment tracked, no second attempt if the first one fails — DESIGN.md ruled retries out explicitly, because a retry is still bounded work sitting on request-adjacent resources, and "request-adjacent" is exactly what this middleware isn't allowed to be.

So what: choosing at-most-once isn't choosing to be sloppy about delivery — it's choosing which of the three costs (latency, coordination, or occasional loss) a given pipeline can least afford to pay, and paying a different one instead.

Three Choices When the Buffer Fills

Once a message is fire-and-forget, exactly one design question remains: what does the sender do when its local buffer between "accepted" and "actually sent" is full. There are only three shapes that question can resolve to.

PolicyWhat happensCost
BlockCaller waits for buffer spaceSteals latency from the real request — exactly what fire-and-forget exists to prevent
Unbounded growBuffer expands to hold everythingNo latency cost until the process runs out of memory, then every request pays for it at once
Drop-and-countNewest event discarded, counter incrementedBounded memory, bounded latency, and a quantifiable, honestly-reported amount of loss

Drop-and-count is the only one of the three whose worst case is a number on a dashboard instead of an incident. That's why shadow-traffic-router's Mirror.Capture uses a fixed-size buffered channel and a non-blocking send: room available, the event goes in; no room, the event is dropped and shadow_mirror_dropped_total increments.

DS analogy — a mail slot, not a mail room
Picture an apartment building's mail slot: a narrow opening in the door that holds maybe twenty letters before it's physically full. A mail carrier who arrives to a full slot doesn't force the door, and doesn't stand there waiting for someone to come empty it — the twenty-first letter goes back in the bag, and the carrier moves on to the next building on the route. The slot's fixed size is a feature, not an oversight: it guarantees the door frame never has to expand to fit an unbounded pile of mail, at the cost of an occasional letter that never gets delivered. A bounded channel with a drop policy is the same trade in software — a fixed opening, a hard stop instead of a bulging front door, and a countable number of letters that didn't make it in.

The branch matters more than either endpoint: the decision of yes-or-room happens once, synchronously, inside Capture, and it's the only thing standing between "the caller never notices" and "the caller waits on a queue." Everything downstream of that branch runs on its own schedule, on its own goroutine, with its own timeout.

So what: the entire non-blocking guarantee lives in one select statement with a default case — the rest of the pipeline can be as slow as it wants, because the branch that protects the caller has already resolved before any of that slowness is visible.

A dropped shadow event isn't a bug report. It's the system telling you, honestly and by design, exactly how much of a best-effort sample it chose not to collect.

Why Shadow Traffic Specifically Can Afford This

Loss is only acceptable when the thing being sent doesn't need to be complete to be useful. Shadow-eval events feed a statistical comparison between a production model and a candidate — the evaluator needs a large-enough, reasonably unbiased sample of paired responses, not literally every request that ever passed through RouteIQ.

A dropped event under load is equivalent to a slightly smaller sample that day, the same way yesterday's post on sampling volume treated a low-traffic tenant's thin sample as a statistical-power problem rather than a correctness bug. Neither case is data corruption; both are the sample size moving, which a large-enough remaining sample can usually absorb.

So what: at-most-once is only "acceptable loss" when the consumer of the data is doing statistics on a population, not reconstructing a specific, individually-important record — the guarantee has to match the job, not just the pipeline's convenience.

Why the Same Codebase Chooses the Opposite Guarantee Elsewhere

The same repository already makes the opposite choice for a different kind of event, which is what makes the contrast worth naming instead of assuming.

Project scope — infra-ai-streaming, primary ingestion path
LensAI's primary Rust ingestion path — the one recording real inference events, not shadow samples — is built for the opposite guarantee: WAL durability, per-tenant rate limiting, a circuit breaker backed by a Redis overflow buffer, and Helm/HPA scaling keyed to Kafka consumer lag, targeting 1M events/min at under 100ms P99. Every one of those pieces exists to avoid losing a primary inference record, even under the same kind of load spike that shadow-traffic-router is explicitly allowed to shed.

Primary inference telemetry is the record a billing or anomaly-detection system reconciles against later — losing one row there is a correctness bug, not a sampling footnote, so that path pays for a WAL and a Redis overflow buffer to avoid it. Shadow-eval traffic exists purely to estimate whether a candidate model's behavior differs from production's, and estimation tolerates gaps that a ledger cannot.

So what: not every pipeline in the same system needs the same delivery guarantee — matching at-most-once vs at-least-once to what the data is actually for is what keeps a bounded channel from becoming either an unnecessary latency tax or a silent correctness bug wearing a shadow-traffic disguise.
