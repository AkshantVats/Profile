Day 121 — Mining Production Logs for SFT Data

A SELECT statement is a feature store the moment its output has a join key. Why the connector's whole design collapses to that one requirement — and what happened when two of the four candidate tables didn't have it.

Akshant Sharma

8 min read

The connector's query filters high judge_score, and that's genuinely the whole first stage of a fine-tuning dataset: SELECT request_id, tenant_id, task_type, model_id, judge_score, judged_at FROM infra_ai.judge_scores WHERE judged_at >= $1 AND judged_at < $2 AND judge_score > $3. No feature-engineering pipeline, no separate serving layer — the production ClickHouse database LensAI already writes to is the feature store, three months late and with zero new infrastructure.

That framing only holds up if every row this query returns can actually be used downstream. Building data-prep-pipeline/pkg/connector today, I found out the hard way that "used downstream" has one specific, non-negotiable requirement, and that two of the four tables Day 120's design doc named as candidate sources don't meet it.

A Candidate Is Only as Good as Its Join Key

The design for this connector named four ClickHouse tables as sources: judge_scores (the quality gate), quality_scores (an older, overlapping judged-sample table), agent_spans (to tell single-turn from multi-turn), and routing_log (to drop cache-hit replays). Reading each table's actual migration file before writing a query against it, I found judge_scores and agent_spans both carry a request_id column. quality_scores and routing_log don't.

DS analogy — a card catalog entry with no call number
A library's card catalog is a candidate list: title, author, subject, one card per book. But a card only gets you to a shelf if it also has a call number — the join key between "this book exists" and "here is where to find it." A card with a beautiful, detailed subject description and no call number is still useless for actually retrieving the book; you'd have to walk every shelf yourself. quality_scores is a card with no call number: it can tell you a sample was judged well, tenant by tenant, task by task — but it can't tell you which specific request that was, so there's no shelf to walk to and fetch the conversation off of.

So what: a table can be full of real, correct information about training-data quality and still be unusable as a candidate source, if nothing in it points back to one specific request — quality is necessary but the join key is what makes a row actionable.

Why This Matters More Than It Sounds

It would be easy to read "no request_id" as a minor schema inconvenience — add a join on tenant_id and task_type and move on. That doesn't work here, and the reason is what a training row is actually for: Day 122's PII audit and Day 123's dedup pass both need to act on one exact request, and the connector's own output feeds a future join into infra_ai.conversation_text, which is keyed by request_id and nothing else.

A (tenant_id, task_type, model_id) join from quality_scores would match every request in that bucket, not the one request the score was actually about — silently fusing an unrelated conversation's text onto a different sample's quality label. That's not a smaller version of the right answer; it's a wrong answer that looks plausible enough to ship.

So what: the honest fix wasn't a clever join — it was recognizing that a table without the right key can only ever be a coverage signal ("was anything judged in this window at all"), never a source of individual candidates, no matter how the query is written.

What Shipped Instead of the Fallback

Day 120's design described a preference order — prefer judge_scores, fall back to quality_scores for windows it doesn't cover — and a routing_log cache-hit filter to drop replayed rows before scoring. Today's connector ships neither fallback. pkg/connector.SelectCandidates does exactly one thing: pull judge_scores rows in a window with judge_score > 0.8, sorted by judged_at then request_id for a deterministic, diffable output.

So what: shipping the one query the schema actually supports, with the two unsupported ideas named in the code and the PR instead of quietly dropped, keeps the gap visible to whoever writes the migration that eventually closes it — the alternative was pretending a query against columns that don't exist was ever going to compile.

A SELECT statement only earns the name "feature store" once its output can be joined back to the thing it describes. Everything else is a report.

The Generalizable Lesson

The design doc that specified this connector got the quality gate right, the window right, and the threshold right — it just didn't check that every table it named as a fallback source could actually be joined to the thing being selected. That's an easy category of design mistake to make on paper: two tables both plausibly contain "judged samples," and it's tempting to treat them as interchangeable sources for the same kind of row.

So what: mining production logs for training data isn't really a modeling problem at the connector stage — it's a join-key audit, and the table that fails that audit doesn't get a lesser role in the pipeline, it gets no role until a migration gives it one.
