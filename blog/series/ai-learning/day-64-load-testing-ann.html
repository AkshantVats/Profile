Same k6 discipline as ingestion — p99 under SLA.

The ingestion pipeline's README states its target in exactly that shape: 1 million events a minute, P99 under 100 milliseconds, measured with k6 against a running service. Today's ticket asked for the same discipline applied to semantic-cache-engine's cache lookup: 1,000 queries a second, p99 under 15 milliseconds. Same shape of number, very different harness underneath it, and the harness is where the interesting part actually lives.

Closed-Loop vs. Open-Loop, and Why the Difference Matters

A load generator has to decide what happens when a request is slow. A closed-loop generator waits: fire the next request only once a worker is free, whether that's immediately or after a slow call finally returns. An open-loop generator doesn't wait at all — it fires at a fixed rate no matter what the system under test is doing, the way independent real clients actually behave, because no real client waits for someone else's request to finish before sending its own.

That difference sounds academic until a real slowdown hits. A closed-loop harness's workers stall on the slow calls and simply stop generating new load — fewer requests get sent during the slowdown, not more, so the harness quietly measures less traffic exactly when there was more to measure. An open-loop generator keeps firing at the same rate regardless, and the requests that would have piled up behind the slow ones actually do pile up, which is what a real production traffic spike would do too.

This gap between what a closed-loop harness reports and what really happened has a name: coordinated omission.

So what: a closed-loop p99 is a lower bound on what an open-loop generator at the same nominal rate would report, never an upper bound — it can only look better than reality, not worse.

DS analogy — a toll booth with one lane
A toll booth with one lane open times each car as it passes through, and the average wait per car looks fine right up until a burst of traffic arrives. A closed-loop measurement is like a stopwatch that only starts once a car reaches the booth — it never counts the cars still waiting in the growing line behind the burst. An open-loop measurement counts the whole line, including everyone who hasn't reached the booth yet, which is the only way to see the queue building before it clears.

So what: the harness's job is to measure the tail, and coordinated omission is exactly the failure mode that hides the tail from a harness that isn't built to see it.

What pkg/loadtest Actually Measures

Today's harness (pkg/loadtest, cmd/loadtest) is closed-loop, deliberately, and the doc comments say so rather than pretending otherwise: a ticker fires at the target QPS, each tick dispatches onto a bounded worker pool, and a worker that's still busy on the previous call just doesn't pick up the next tick. That's a real, documented limitation, not an oversight — it means today's p99 numbers describe "is this index's own query cost within budget at this concurrency," not "what would a real, uncoordinated burst of production traffic actually do to the tail."

The harness also measures one specific call, FindNearest — the hnsw index query itself — and deliberately not the full lookup path that also calls an embedding API first. Embedding latency and index latency are two different systems with two different SLAs; folding them into one number would mean a slow OpenAI response gets blamed on index tuning, which is the wrong team fixing the wrong problem.

What Today's Numbers Actually Say

No Docker daemon is available in this sandbox — a live probe confirmed it, the same gap a prior day logged for the root docker-compose stack — so every number below is against pkg/loadtest.MemStore, an in-memory store that sleeps a fixed simulated latency instead of a real pgvector round trip. At 1,000 target QPS and a 2 millisecond simulated latency, the harness reported a p99 of 2.71 milliseconds; raising the simulated latency to 15 milliseconds — the ticket's own SLA boundary — correctly pushed p99 to 16.15 milliseconds instead of silently rounding down.

The concurrency-starved run is the most useful one of the three: at 16 workers and 20 milliseconds per call, the pool can only sustain about 800 requests a second, and the harness's achieved throughput dropped to match — not a bug, the harness correctly surfacing "not enough concurrency" instead of pretending it hit 1,000 QPS anyway.

So what: a load-test harness that degrades honestly under an undersized pool is more useful than one that hides the shortfall, because "raise concurrency or lower per-call latency" is a real, actionable finding and a silently-inflated QPS number is not.

What This Doesn't Prove

The honest gap: MemStore's latency is a flat number applied to every call, with a single synthetic tenant seeded once. A real pgvector index's cost depends on how many vectors are actually in it and how unevenly traffic lands across tenants, and neither effect exists in a flat simulated number. Today's companion Experience post works through why that specific gap — skew, not average load — is the harder and more realistic failure mode, using an index Akshant watched blow up unevenly in production as the concrete example.

So what: "the harness computes percentiles correctly under bounded concurrency" is a claim today's runs actually support; "semantic-cache-engine's production p99 is under 15ms" is a claim only a live pgvector instance under realistic, skewed traffic could make, and today's numbers don't reach far enough to make it.
