Day 52 — Statistical Rigor — N Runs, Confidence

Don't benchmark once. Run 30 times; report median cost and p95 steps. Agent runs are non-deterministic even holding the task, seed, and prompt fixed — one run is an anecdote, not evidence, and a benchmark needs a distribution with an error bar attached instead of a single pass/fail bit.

Run 30 times; report median cost and p95 steps.

That's the whole methodology in seven words. Day 51 fixed the scenario — one task, one seed, one prompt, so two agents could be compared fairly. Day 52 asks a different question about that same fixed scenario: how many times do you actually have to run it before a number coming out the other end means anything?

One Flip Doesn't Tell You If a Coin Is Fair

DS analogy — the coin you only flipped once
Flip a coin once and it lands heads. You have exactly one data point, and it says nothing about whether the coin is fair, weighted, or two-headed — a fair coin lands heads on a single flip half the time anyway. Flip it thirty times and get eighteen heads, and now you have something to say: not "the coin is biased toward heads," but a rate with a range around it, one that gets narrower the more you flip.

An agent run graded once against a task's success criteria is the one-flip case. The run passed or it didn't, and that single bit can't distinguish "this agent reliably solves this task" from "this agent got lucky on this exact draw of tool latency and provider-side sampling." Both produce the identical pass/fail bit from a single run.

So what: a single run's pass/fail bit is compatible with wildly different underlying reliabilities — it just doesn't carry enough information to tell them apart.

Where the Variance Actually Comes From

Day 51 pinned the task, the seed, and the prompt specifically so an agent-to-agent comparison couldn't be confounded by a different scenario. That fix doesn't make a single agent's own runs identical to each other, because the sources of run-to-run variance live below the task boundary: tool latency jitter that changes retry timing, transient tool errors that trigger different recovery paths, and provider-side sampling that isn't fully pinned down by one seed value alone.

None of that variance is a bug in the task specification — it's the agent operating in a system that has real timing and real randomness in it, the same way a network call's latency varies run to run even when the request bytes are byte-for-byte identical. A benchmark that assumes one run is representative is assuming that variance away instead of measuring it.

So what: fixing the task removes scenario noise between agents; it doesn't remove execution noise within one agent's own repeated runs — that noise needs N runs to be seen at all.

N Repetitions Under a Concurrency Budget

pkg/orchestrator.Run executes a task's N repetitions against one agent, bounded by a fixed-size worker pool rather than firing all N at once — the companion Experience post walks through why unbounded fan-out turns a benchmark batch into a self-inflicted rate-limit test instead of a measurement of the agent. Each repetition gets its own seed, derived by hashing the task's base seed together with the repetition index, so the full batch reproduces exactly from one recorded number while no two repetitions draw from a correlated random stream.

A Rate With an Error Bar, Not a Single Number

Summarize turns the batch into a pass rate plus a 95% confidence interval, using the Wilson score formula instead of the more familiar normal (Wald) approximation. Wald computes a symmetric margin around the observed rate and can push the interval below 0% or above 100%, or collapse it to zero width at 0 or 100 percent observed — exactly the small-sample, extreme-rate territory a 10-to-30-run benchmark batch lives in.

That 45-point-wide interval on a 10-run batch is not a bug in the math — it's the honest answer. Ten runs genuinely cannot distinguish an 80%-reliable agent from a 55%-reliable one; the interval says so instead of hiding it behind one confident-looking 80% headline number. Running more repetitions narrows the interval; nothing about a wider prompt or a smarter model narrows it faster than more data does.

So what: the width of the confidence interval is itself the signal — a narrow one on a large batch means the rate has actually converged, and a wide one means the honest answer is "run more," not "trust the point estimate."

The Honest Gap

Everything here still takes AgentFunc and RunOutcome as caller-supplied inputs, exactly as Day 51 left them — pkg/orchestrator and pkg/store don't invoke a live agent process themselves. A CLI that reads a task YAML, drives real repetitions end to end against an actual agent, and writes the results to ClickHouse is a natural next step, not something today's code quietly pretends to already do.
