Helm values set max_num_seqs is today's hook, and I want to slow down on it instead of reading past it. It looks like an infrastructure knob — one line in a values.yaml a same-day teammate is writing for vllm-deploy-kit — but it's actually a ceiling on a specific piece of vLLM's memory system: how many sequences the scheduler will admit into the KV cache's paged memory at once. Understanding what it bounds means going back to PagedAttention itself.

A Parking Garage With Numbered Stalls, Not a Reserved Curb

DS analogy — the parking garage with numbered stalls
Reserve a car a stretch of curb sized for the longest trip it might ever take, and that curb sits mostly empty for every shorter trip — the space is contiguous, but almost all of it goes unused. A parking garage solves the same problem differently: every car gets assigned individual numbered stalls as it needs them, scattered anywhere open in the garage, tracked by a directory at the entrance that maps each car to its stalls. The car never notices its stalls aren't next to each other; only the directory has to know.

PagedAttention is the parking-garage answer applied to a sequence's key-value cache. Reserving one contiguous VRAM block per sequence, sized for the worst case, is the reserved curb; allocating small blocks on demand from anywhere free in memory, tracked by a lookup table, is the numbered stalls.

So what: the memory-management idea underneath vLLM isn't specific to transformers at all, it's the decades-old observation that contiguous reservations waste space and indirection through a directory recovers most of it — which is exactly why Day 2's table lined up virtual memory paging against PagedAttention in the first place.

What PagedAttention Actually Pages

Every token a transformer generates leaves behind a key vector and a value vector, per attention layer, per head — together, its KV cache entry. Before PagedAttention, an inference engine had to reserve one contiguous block of VRAM per sequence, sized for the longest sequence that request was allowed to reach (max_model_len), the moment the sequence started. That's the reserved-curb approach, sized for a trip that might never happen.

PagedAttention instead splits each sequence's KV cache into fixed-size blocks — 16 tokens per block in vLLM's default configuration — and allocates blocks on demand as a sequence actually grows, from anywhere free in GPU memory. A block table, one per sequence, maps each logical position in the sequence to whichever physical block currently holds it; the attention kernel reads that table and gathers scattered blocks as if they were contiguous, the same trick a CPU's memory-management unit performs for virtual memory.

Where a Helm Value Actually Touches This

Three of today's chart values map directly onto that mechanism. gpu_memory_utilization sets the fraction of each GPU's memory vLLM is allowed to claim in total — model weights plus every block in the paged KV cache pool — so it's the ceiling on how many blocks can ever exist at once. max_model_len bounds how many blocks a single sequence could theoretically need if it ran to its longest allowed length.

max_num_seqs is the value the hook names directly, and it bounds the scheduler's admission decision, not the memory allocation itself: it's a hard cap on how many sequences vLLM will run concurrently, regardless of how much paged memory those sequences would actually use. Set it too high against a fixed gpu_memory_utilization budget and the scheduler admits more sequences than the block pool can back, forcing it to preempt or swap sequences mid-decode; set it too low and paged memory sits unused while requests queue. tensor_parallel_size is a different axis — it splits the model's weights across GPUs, changing how much of each GPU's memory is left over for the KV cache pool to begin with, but it doesn't touch paging directly.

So what: max_num_seqs isn't a rate limit dressed up as a Helm value, it's a direct dial on how aggressively the scheduler is allowed to lean on PagedAttention's ability to pack many partial sequences into memory that was never reserved for any one of them specifically.

Why the HPA Has to Watch the GPU, Not the CPU

A decode-heavy vLLM pod can sit at low CPU utilization while its GPU runs at full occupancy, because the CPU is mostly waiting on the GPU, not computing. A Kubernetes HPA (Horizontal Pod Autoscaler, the controller that adds or removes pods based on a watched metric) reading only the stock metrics-server would see a quiet pod and never scale, no matter how full the paged KV cache actually is. Today's chart wires the HPA to GPU utilization instead, sourced from DCGM-exporter (NVIDIA's per-GPU stats collector) and surfaced through Prometheus Adapter (the bridge that lets a custom metric feed the HPA's decision), because that's the number that actually reflects whether the paging system has room left.

So what: pairing max_num_seqs with a GPU-aware HPA is the same idea as pairing a resource limit with the metric that actually predicts pressure — the wrong signal doesn't just under-scale, it hides the exact bottleneck PagedAttention exists to relieve.

What I Still Don't Know

I don't know which model the chart resolves at install time versus at reload — whether it reads model-registry's stage == "production" entry and its artifact_prefix once, at deploy, or watches for that entry to change and reloads a running pod. Days 138–140 built the registry side of that contract; today's DESIGN.md, per the plan line, documents the Helm values, not the resolution timing between the two systems.

So what: the paging mechanism and the values that bound it are the part I've verified against Day 2's own material; the exact handoff between model-registry's production stage and the vLLM chart is a real open question the code, once it exists, will have to answer.
