Day 138 — Model Registry — Artifacts + Metadata

Git for weights with semver tags. Today's post is about the gap between "the file is saved somewhere" and "I can prove exactly which file this is, what trained it, and whether it was any good" — and why a registry row closes that gap while a bucket path alone can't.

"Registry row: artifact_uri, eval_scores" is today's hook, and it undersells the point slightly. The interesting part isn't that the row stores a URI and a score — a filename can already encode both of those, badly. The interesting part is what a row can do that a filename structurally cannot: be queried, compared, and trusted.

A Catalog Card Doesn't Store the Book

DS analogy — the card catalog, not the shelf
A library's card catalog doesn't hold any books. It holds a card per book: title, author, edition, call number, which copies are checked out. The shelf is where the physical object lives; the card is what lets a librarian answer "do we have the second edition, and where is it" without walking every aisle. A model registry plays the card's role, not the shelf's — the artifact still lives in object storage, exactly where it already did.

Delete the card catalog and every book is still physically on the shelf. What's gone is the ability to answer any question about them faster than a manual search, or to prove a claim like "this is the second edition" instead of just asserting it. That's the same gap between a folder of .safetensors files and a registry: the weights aren't the missing piece, the provable metadata about the weights is.

So what: a registry's value isn't storage, it's the queryable claim layer on top of storage — which is exactly why today's ticket is "upload artifact + metadata," two different jobs bundled into one API, not one job with an extra field.

Three Fields, Three Different Questions

The ticket names three metadata fields, and each one answers a question the artifact file alone can't: eval_scores answers "was this version actually better," reusing the same win-rate-plus-Wilson-interval shape this series' eval-harness module already built rather than inventing a second scoring format. git_sha answers "what exact code produced this," the same discipline a Docker image's build provenance label gives a container. dataset_hash answers "what data did it see" — today's module accepts it as a caller-supplied sha256 hex string rather than trusting a filename like v3-final-FINAL.pkl to mean anything.

Honest gap — dataset_hash isn't wired to a real producer yet
Yesterday's eval-harness DESIGN.md reserved a test_set_hash field explicitly for this module to consume. Grepping that codebase for it turns up exactly one hit — a comment citing it as precedent, not a function that computes one. So dataset_hash today is a caller-supplied string with a documented shape, not a value joined against a real upstream hash yet. Naming that now is cheaper than someone discovering it by reading two modules that don't actually connect.

None of those three questions has a good answer if the only artifact of a training run is a file with a human-chosen name. A human-chosen name is optimized for being memorable, not for being provably tied to the run that produced it — the two goals aren't the same, and a registry row is what makes the second one possible.

So what: three metadata fields sound like bookkeeping until you notice none of the three questions they answer is answerable from the artifact bytes themselves — the row isn't decoration on top of the file, it's the only place those answers exist at all.

Why the Row Commits Last, Not First

This series already solved a version of this problem: Day 132's finalize() writes a run's final adapter files first, and only writes the final marker object after every file lands — so a crash mid-write leaves no marker at all, never a marker pointing at a half-written adapter. Today's registry upload takes the same shape one layer up: the artifact uploads to its object-store key first, and the registry row that makes it discoverable and queryable commits only after the upload is confirmed.

Get that order backwards — write the row first, upload the artifact after — and a crash between the two steps leaves a registry entry pointing at a URI with nothing behind it. Any consumer that trusts the registry (a rollback, a deploy, a comparison query) would find a row and reasonably assume the artifact exists, because that's what a committed row is supposed to mean.

So what: a registry is only as trustworthy as its worst-case ordering guarantee — "row exists" has to mean "artifact exists," which is a promise you only get by writing the artifact first and the row last, the same lesson Day 132's checkpoint marker already taught this pipeline once.

What I Still Don't Know

"Git for weights with semver tags" is the hook's framing, and it's a useful shorthand, not a literal claim — today's registry records a git sha and an eval score, not a full content-addressed diff history the way git tracks every commit's changes. Whether this registry ever grows a real diff/lineage view between two artifact versions, the way git log -p shows you between two commits, is an open question this module doesn't answer yet.

So what: "git for weights" is the right intuition to reach for — provable identity, a queryable history, no more trusting a filename — even though today's implementation is closer to git's object store and commit metadata than to its full diffing toolchain, and that gap is worth naming rather than implying this is a finished analogy.
