Day 6 of Learning LLM Inference — Quantization vs Compression Tradeoffs

6 of N — AI Learning Series. INT8/INT4 as Snappy-vs-Zstd for weight tensors — precision is a deployment budget you negotiate, not a fixed property of the model.

AI Learning · Day 6 of N

A 7-billion-parameter model in FP16 weighs about 14 GB. An A10G has 24 GB of VRAM. That arithmetic looks comfortable — until you remember the KV cache needs room too. At batch size two the leftover 10 GB evaporates, and suddenly a model that "fit" yesterday does not fit today. The reflex is a bigger GPU. The better question is whether you actually need all sixteen bits per weight.

The problem was not the model's size. The problem was that I had been treating precision as a fixed property of the artifact instead of a deployment budget I could negotiate. You already do this in data systems: you pick a codec by access pattern, accept some CPU overhead for a smaller footprint, and move on. Weights deserve the same conversation.

That framing — precision as a budget — rhymes with something I keep running into. Losing your Redis rate-limiter removes enforcement but not storage; deploying INT4 without running an eval suite saves memory but loses the quality contract. Both are budget decisions where skipping the check turns a tradeoff into a silent failure.

The VRAM arithmetic that breaks

Every parameter in FP16 costs two bytes. BF16 costs the same two bytes but trades mantissa bits for a wider exponent range — same footprint, different rounding behavior at the tails. INT8 halves that to one byte. INT4 halves again to half a byte. For a 7B model, the numbers look like this:

FormatBytes / param7B model weight sizeWhat it buys
FP16 / BF162~14 GBFull precision baseline
INT81~7 GB2× compression, minimal eval loss
INT40.5~3.5 GB4× compression, quality depends on calibration

Those numbers matter because GPU bills are denominated in VRAM tiers. Fitting a model in 8 GB instead of 16 GB is not a 50% saving on paper — it is the difference between an A10G and an A100, which can be a 3–4× difference in hourly cost. So the precision decision is a capacity-planning decision, the same way choosing a Kafka partition count is a throughput-planning decision.

Quantization is codec selection for weight tensors

The analogy that made this click for me was compression codecs. You already pick codecs by access pattern: Snappy or LZ4 when you need fast decompression and can tolerate a lower ratio; Zstd at high compression levels when you need the smallest file and can afford a slower offline pass. Uncompressed is fine for dev, wrong at scale.

INT8 dynamic quantization is Snappy. You round weights at inference time — no offline calibration, minimal setup. Decompression is fast because the dequantize step is cheap. Compression ratio is modest (2×) but the quality hit is usually negligible. When I first saw INT8 benchmarks on Hugging Face's Optimum docs, what I didn't expect was how often eval scores held within a point of FP16. For latency-sensitive, memory-bound decode — the access pattern Day 1 described — INT8 is the default knob.

INT4 with GPTQ or AWQ is Zstd at level 19. You need an offline calibration pass: the algorithm walks a calibration dataset and finds weight groupings that minimize error under tighter precision. The ratio is better (4×), but you are now coupling your deployment artifact to a specific calibration set — the way a Zstd dictionary is tuned to a corpus. Change the input distribution and the dictionary stops helping. Change the task distribution and the INT4 quantization stops holding. GPTQ and AWQ differ in how they search for those groupings, but the core tradeoff is the same: offline cost buys online savings, and the savings are only as good as the calibration.

Uncompressed FP16 is raw WAV. Simple, wastes capacity. Fine when you are debugging locally and VRAM is not the constraint. Wrong default when you are serving hundreds of concurrent users and paying by the GPU-hour.

The codec analogy extends one layer deeper. Random access vs sequential read maps to prefill vs decode. Prefill is a one-shot matmul over the full prompt — random access across the weight matrix, compute-bound. Decode is sequential, memory-bound, reading a growing KV cache step by step. INT8 helps decode more than prefill because decode is bandwidth-limited: fewer bytes per weight means more weights per memory read, which means more tokens per second at the memory wall.

When quantization fails — and where you fall back

The happy path is clean: quantize, eval passes, deploy, save money. The failure path is where teams get hurt. I have seen INT4 models pass perplexity benchmarks and still produce garbage on domain-specific tasks — because the calibration dataset was generic and the deployment task was narrow. The eval score looked fine on paper. The users saw hallucinated structured output that broke downstream parsers.

So the decision is not "INT8 or INT4?" in isolation. It is a flowchart with fallback branches, and every branch goes through an eval gate:

flowchart TD
  START[VRAM pressure?] -->|no| FP[FP16/BF16 baseline]
  START -->|yes| LAT{Latency SLO strict?}
  LAT -->|yes| INT8[INT8 dynamic / W8A16]
  LAT -->|no| INT4[INT4 GPTQ/AWQ + calibration]
  INT8 --> EVAL[Run eval suite]
  INT4 --> EVAL
  EVAL -->|pass| SHIP[Deploy]
  EVAL -->|FAIL: quality below threshold| FALLBACK[Fall back to FP16 or try INT8]
  FALLBACK --> COST{Bigger GPU affordable?}
  COST -->|yes| FP
  COST -->|no| RECAL[Re-calibrate INT4 with different dataset]
  RECAL --> EVAL
  style FALLBACK fill:#ff6b6b,color:#fff
  style COST fill:#ffa94d,color:#fff

The red node is the one teams skip. They quantize, eyeball a few outputs, and ship — because running a proper eval suite on every precision change feels like overhead. It is not overhead. It is the quality contract. Skipping it is the quantization equivalent of deploying without tests because "it compiled."

Memory bandwidth under precision

The throughput ceiling during decode is set by how fast you can read weights from DRAM into the GPU's compute units. Smaller weights mean less bandwidth consumed per parameter, which means more tokens per second before you hit the memory wall. But this only holds if the eval score holds too — otherwise you are generating garbage faster.

flowchart LR
  DRAM[(Weights in DRAM)] -->|FP16: 14 GB| BW[Memory bandwidth bound decode]
  DRAM -->|INT8: 7 GB| BW
  DRAM -->|INT4: 3.5 GB| BW
  BW --> TOK[Tokens/sec ceiling]
  TOK --> EVALCHECK{Eval score holds?}
  EVALCHECK -->|yes| SERVE[Serve in prod]
  EVALCHECK -->|no| REGRESS[Quality regression — users see garbage]
  style REGRESS fill:#ff6b6b,color:#fff

What I didn't expect: the throughput gain from INT8 over FP16 is often larger than the gain from INT4 over INT8. Because INT4 requires dequantization arithmetic that partially offsets the bandwidth savings — and because INT4 grouping metadata adds overhead that INT8 does not carry. According to NVIDIA's TensorRT-LLM benchmarks, INT8 on an A100 can push 1.8–2× the tokens/sec of FP16 on memory-bound decode, while INT4 adds another 20–40% on top of INT8 — not the full 2× you would expect from halving the bits again.

What cost_usd does not capture

The inference event schema carries model_id, cost_usd, and latency fields. But cost_usd only captures the dollar cost of the request — it does not capture quality regression. A quantized model can serve requests faster and cheaper while producing outputs that are subtly wrong. The model_id label already distinguishes llama-7b-fp16 from llama-7b-int4-gptq, so the data is there for per-precision dashboards. The discipline is remembering to look at task accuracy alongside sum(cost_usd) — because a 40% cost reduction that comes with a 5% accuracy drop is not a win if that 5% breaks a downstream contract.

The Wayfair supplier-API story has the same shape: a rate-limit "budget" that looked generous in aggregate hid per-supplier 429 spikes. Precision budgets hide the same way — fleet-average eval looks fine while one task vertical is regressing. Rate limit budget, token budget, precision budget: the word "budget" keeps showing up because the failure mode is always the same. You optimized the aggregate, ignored the tail, and the tail bit you in production. That same instinct — measure the tail, not the fleet average — is the difference between a cost saving and a quality incident.

Precision is a deployment budget. Skipping the eval gate turns a tradeoff into a silent failure.

Pick precision the way you pick a codec: measure decompression speed (latency), measure distortion (eval), and ship the tightest format your quality budget allows. Parameter count is storage size. Precision is fidelity. Confuse them and you will deploy a model that is small, fast, and wrong.
