Day 76 — Exact-Match vs Semantic Cache — Two-Tier Memory Hierarchy

L1 exact, L2 embedding, the same shape as a CPU's cache levels: the router checks the fingerprint table before it ever pays for a pgvector round-trip.

A cache tier isn't just "faster" or "slower" than another one — it can be answering a genuinely different question. prompt-fingerprinter's L1 tier and semantic-cache-engine's L2 tier don't compete to answer the same lookup fastest. They answer two different questions, one strictly easier than the other, and that difference is the entire reason the ordering between them isn't arbitrary.

Two Questions, Not One

L1 answers "have I seen this exact prompt before" — a yes/no on byte-identical input, once Normalize() has trimmed and canonicalized it. L2 answers "have I seen something similar enough to this prompt before" — a fuzzier, strictly harder question that needs an embedding model to convert the prompt into a vector before a similarity search can even run.

Those aren't the same lookup running at two speeds. L1's question has a fixed, cheap answer procedure: hash the bytes, check Redis. L2's question needs a model call before the actual search logic even starts, because "similar enough" isn't decidable from raw bytes the way "identical" is.

So what: asking L2 to also handle L1's job would work, but it would mean paying an embedding call on every request just to answer a question a Redis GET could have answered for free.

DS analogy — a CPU's L1/L2 memory hierarchy
A CPU's L1 cache sits right next to the core and answers in a couple of cycles — but it's small, and it can only ever say "is this exact address cached right now." L2 is larger and answers in tens of cycles instead of a handful, catching what L1 missed. Neither level is "the cache" on its own: the hierarchy's entire value is that most memory accesses get answered by the fast, narrow level, and only the ones that need it pay the slower, broader level's cost. prompt-fingerprinter's Redis exact-match tier in front of semantic-cache-engine's embedding tier is the identical shape at a different latency scale — microseconds versus milliseconds instead of cycles versus tens of cycles, but the same narrow-cheap-first reasoning underneath.

Why L1 Can't Just Be a Smaller L2

It's tempting to think of L1 as "L2, but with a tighter similarity threshold." It isn't. L2's broader hit criterion — catching a rephrased duplicate, not just a byte-identical one — is bought directly by the extra work an embedding call and a vector search do. Narrowing L2's threshold to only match near-identical vectors wouldn't turn it into L1; it would just be an expensive way to answer the question L1 already answers for free.

L1 (exact match)L2 (semantic)
Question answeredByte-identical after normalization?Similar enough by embedding distance?
Lookup costOne Redis GETEmbedding call + pgvector search
What it catchesRetries, replayed batches, double-submitsRephrasings, paraphrases, near-duplicates

So what: the cost and the capability aren't two independent design choices — they're the same tradeoff, seen from two sides. You can't get L2's broader hit criterion without paying for the work that makes it possible.

Today's Code: A Tenant-Configurable L1 Question

The admin endpoint shipped today, PUT /tenants/{id}/fingerprint-rules, lets a tenant configure strip_punctuation and lowercase — widening what L1 treats as "the same prompt" without touching L2's logic at all. Two prompts differing only in case and punctuation used to miss L1 and fall through to an embedding call every time; once a tenant opts in, they collide at L1 instead.

TestIntegration_AdminRulesExpandDuplicateDetection proves the concrete payoff directly: configure the rule, send both prompt variants, and confirm the second one resolves from Redis instead of reaching the (simulated) embedding API a second time. That's the same experiment as TestIntegration_DuplicatePromptSkipsEmbeddingAPI, just with L1's definition of "duplicate" widened first.

So what: L1's question was never fixed at "byte-identical" by necessity — it was fixed at "byte-identical after a specific normalization contract," and today's admin API is what makes that contract tenant-configurable instead of hardcoded.

Closing the Observability Loop

cache_hit_type=exact now actually reaches LensAI, through the same /ingest envelope every other producer in this stack posts through. DESIGN.md reserved that source value back on Day 70 without ever populating it — "how much of our traffic is a literal duplicate" was a documented intent until today, and now it's a queryable number.

A two-tier cache isn't two independent caches bolted together. It's one hierarchy where the cheap tier's entire justification is catching enough traffic that the expensive tier's real cost gets paid only when the cheap tier's narrower question genuinely can't answer it.

So what: the same reasoning governs a CPU deciding what belongs in L1 versus L2 and a request router deciding what gets an exact-match check before an embedding call — cheap and narrow in front, expensive and broad behind, and the split only pays for itself if the front tier actually catches a meaningful share of the traffic.
