I have spent seven years building high-throughput distributed systems across Agoda, Delivery Hero, and Walmart. I understand what breaks systems at scale and why. I have never trained a model. I have never written a loss function. I have zero ML background. (Day 0 explains how this series is organized.)

I am now building an AI inference observability pipeline — and I realized I cannot build good observability for a system I do not understand from the inside. So I am documenting my learning publicly, one concept at a time, from the perspective of someone who thinks in queues, buffers, memory hierarchies, and throughput — not tensors and gradients.

This is Day 1. Today I learned how LLMs actually generate text — and why the mental model I walked in with was wrong in an interesting way.

What I expected vs what is actually happening

My assumption going in: LLM inference is like a batch compute job. You send a prompt, the model runs expensive computation over it, and you get an answer back. High GPU utilization throughout, latency proportional to work size.

That is not what happens.

There are two completely distinct phases. They have different computational characteristics, different bottlenecks, and different implications for serving infrastructure. Understanding this split is the first thing any infra engineer needs to internalize.

Phase 1: Prefill

When you send a prompt, the model processes your entire input in one parallel pass. Every token in your prompt gets processed simultaneously. The attention mechanism computes relationships between all input tokens at once.

This is compute-bound. GPU utilization is high. It scales well with hardware. A longer prompt means more work, but the parallelism is high. This is the phase that matched my initial mental model.

Prefill produces two things: the first generated output token, and the KV cache.

Phase 2: Decode

After prefill, the model generates output tokens one at a time. Each token depends on every token before it — all your prompt tokens and every output token generated so far. This is autoregressive decoding.

Prefill output: "The" (first token)

Decode step 1:  Context = [prompt] + ["The"]
                → generates "CAP"

Decode step 2:  Context = [prompt] + ["The", "CAP"]
                → generates "theorem"

Decode step 3:  Context = [prompt] + ["The", "CAP", "theorem"]
                → generates "refers"

...one token at a time until the model stops.

Each decode step is a single forward pass through the model. You cannot start step N+1 until step N is complete. The output of step N is the input to step N+1.

This is inherently serial. For a 500-token response, that is 500 sequential forward passes. Each one reads model weights from VRAM. Each one is a round trip to GPU memory.

The KV cache — where it gets interesting

In transformer attention, for each token the model computes a Query, a Key, and a Value. Computing attention for a new token requires the Keys and Values of every previous token in the context. Without optimization, every decode step would recompute Keys and Values for the entire context from scratch — work that grows quadratically with context length.

The KV cache stores those Keys and Values from previous steps. When you generate token N+1, you only compute fresh Keys and Values for the new token. Everything else is read from cache in VRAM.

                    PREFILL
             (parallel, compute-bound)

  Prompt: [T1][T2][T3][T4][T5]
                    |
          All tokens processed in
          one parallel forward pass
                    |
          KV Cache written to VRAM
          First output token generated


                    DECODE
           (sequential, memory-bound)

  ┌─────────────────────────────────┐
  │  Read full KV Cache from VRAM   │
  │             ↓                   │
  │  Compute attention for new tok  │
  │             ↓                   │
  │  Generate next token            │
  │             ↓                   │
  │  Append new K,V to cache        │
  └──────────── ↓ ──────────────────┘
               loop until done

The cache eliminates redundant recomputation. But it introduces a different cost: every decode step reads the entire accumulated KV cache from VRAM. As context grows, so does the cache. As the cache grows, so does the memory read per decode step.

This is where the bottleneck shifts. Decode is not primarily compute-bound. It is memory-bandwidth-bound. The GPU cores are not always the constraint — the speed at which data moves from VRAM to the compute units is.

The analogy that made this concrete

I have dealt with this exact pattern before.

At Agoda, our TSDB had a hot/cold tiering problem. Recent metrics — the last few hours — got queried constantly. The bottleneck for those hot-path queries was not CPU. It was how fast we could read the relevant series data into the query path. We put recent data in Redis because the access pattern was memory-bandwidth-bound in exactly the right way.

TSDB hot-path read:
  Query engine → reads hot series from Redis
  Bottleneck: memory bandwidth, not CPU compute

LLM decode path:
  Attention layer → reads KV Cache from VRAM
  Bottleneck: memory bandwidth, not GPU compute

Same problem. Different hardware. Different names.

This is why high-end inference hardware like the H100 advertises memory bandwidth (3.35 TB/s) prominently alongside compute (989 TFLOPS). For decode-heavy workloads, the bandwidth number is often the one that matters more.

The KV cache starts as a compute optimization — it avoids recomputing Keys and Values. But during decode it becomes a memory access problem. That is an important distinction. If you treat decode as a compute problem you will reach for the wrong solutions.

What this means for the KV cache in practice

The KV cache lives in VRAM. Its size grows with context length, number of transformer layers, model size, and the precision of stored values. For large models serving long contexts, the cache can become very large — in some configurations rivaling or exceeding the model weights themselves.

The exact size varies significantly by architecture, attention head configuration, KV precision, and whether the model uses grouped-query attention. The rough point is this: the KV cache is not a small bookkeeping structure. It is a primary consumer of VRAM, and it grows with every token of context you allow.

This creates a resource management problem that has nothing to do with ML. It is the same problem as Redis memory pressure under concurrent queries. Serve multiple concurrent requests and those caches stack. Run out of VRAM and you either evict cache (hurting decode performance) or reject requests (hurting availability).

Multi-tenant resource isolation in an LLM serving system is fundamentally a memory management problem.

Prefill vs decode: two different latency problems

PrefillDecode
MetricTime to First Token (TTFT)Time per Output Token (TPOT)
BottleneckGPU computeVRAM memory bandwidth
GPU utilizationHighOften lower
Scales withPrompt token countContext length + output length
ParallelismHigh — all input tokens at onceNone — strictly sequential per request

If you measure only end-to-end latency — time from request to complete response — you are mixing two completely different problems into one number. A slow TTFT means something different than a slow TPOT. One is a compute problem. The other is a memory bandwidth problem. Aggregating them into a single inference_latency_ms field makes the data nearly useless for diagnosing actual serving issues.

For my observability pipeline this means separate fields from day one: prefill_latency_ms and decode_latency_ms. Not optional. Core schema.

The open question: GPU utilization during decode

Decode is serial per request — but that does not mean the GPU has to sit underutilized. While one request is generating token N, other requests can be generating their own tokens in the same GPU pass. Batching decode steps across concurrent requests is how serving systems recover GPU utilization.

This is the next thing I am trying to understand — how vLLM's continuous batching works, what it actually does to throughput and latency, and what it means for observability. That is Day 2.

What I am taking away

The mental shift from "LLM inference is expensive compute" to "decode is expensive memory access" changes how I think about the entire problem space.

The surprising thing about LLM inference is that it does not feel like distributed compute. It feels like operating a large shared memory system under adversarial workloads — where the resource you are actually managing is VRAM, not FLOPS, and where context length is a cost lever, not a feature.

I have managed memory pressure, hot-path read bottlenecks, and noisy neighbor problems before. The hardware is different. The vocabulary is different. The underlying problems are the same ones I have been solving for seven years.
