Day 123 — MinHash Dedup — Near-Duplicate Prompts

A ticket that says "Hamming threshold config" is picturing a bit-string. MinHash's signature is an array of hash minimums, not a bit-string — and working out why that distinction changes which vocabulary actually helps you tune the threshold is this whole post.

The prep pipeline's design doc handed today's ticket a specific phrase to implement: "defines its own Hamming threshold config for near enough to be a duplicate." I built the near-duplicate pass, and the function that decides "near enough" is called EstimateJaccard, not HammingDistance.

Both names describe the same number. Only one of them tells you what the threshold means.

Shingles: Turning Text Into a Set

MinHash doesn't operate on a prompt's raw characters or its word order. It operates on a set — so the first step is turning "where is my order 48213" into one. Split the normalized text into overlapping windows of a few consecutive words, and each window (a "shingle") becomes one element of the set.

"Where is my order 48213 it has not arrived" becomes a set of 3-word shingles: {where is my, is my order, my order 48213, order 48213 it, ...}. Two near-duplicate prompts — the same request with a greeting added, a clause reworded — end up as two sets that overlap heavily but aren't identical, because the shingles touching the edit differ while the rest of the sentence's shingles match exactly.

So what: shingling is the step that turns "is this text similar" into "how much do these two sets overlap," and everything downstream — MinHash included — is really answering that second, more tractable question.

The MinHash Trick

DS analogy — one shuffled deck, drawn from two hands
Picture every possible 3-word shingle in the language as a card in one enormous deck, shuffled once into a random order. A prompt's shingle set is a hand of cards drawn from that deck — not physically, just conceptually: whichever cards from the full deck happen to match this prompt's shingles. That prompt's MinHash value for this shuffle is whichever of its own cards landed earliest in the shuffle. Two prompts whose hands overlap almost completely are very likely to share that earliest card, because it's a property of the shuffle applied to their shared cards. Two prompts with almost no shared cards will only rarely have the same earliest card, by pure chance. Run 64 independent shuffles and count how often both prompts' earliest card matches, and that fraction is an unbiased estimate of how much their hands actually overlap.

That's the entire trick, stated formally: for a random permutation of the universe of possible shingles, the probability that two sets share the same minimum element equals their Jaccard similarity — the size of their intersection divided by the size of their union. It's not an approximation of a different quantity; it's an exact probability, and running many independent permutations turns that probability into an estimate with shrinking variance.

NumHashes = 64 is what fixes the shuffle count. Each additional permutation, the estimator's standard error is a term shaped by the true Jaccard value, roughly halved every time you quadruple the number of hashes — there's no free lunch, just a knob between compute cost and estimate precision, and 64 is the point where that error comfortably clears the gap between a real near-duplicate and an unrelated pair.

So what: MinHash isn't approximate because the algorithm is sloppy — it's approximate the same way a poll is approximate, and the estimate gets tighter the same way a poll does: by sampling more independent shuffles, not by inventing a cleverer single shuffle.

SimHash Is a Different Machine

SimHash is the technique the "Hamming threshold" phrasing most naturally describes, and it's worth being precise about why it isn't what this ticket needed. SimHash starts from a weighted feature vector — term frequencies over a document's words or shingles — not a plain set.

It projects that vector against a fixed set of random hyperplanes. The sign of the dot product against each hyperplane becomes one bit of a fixed-width signature: positive, a 1; negative, a 0. Two vectors pointing in similar directions produce signatures differing in very few bits, because a random hyperplane is unlikely to separate two nearly-aligned vectors.

That signature genuinely is a bit-string, and Hamming distance — literally, how many bits differ — is the exactly right metric for it, bounded by the hyperplane count the same way MinHash's estimate is bounded by its hash count. SimHash approximates cosine similarity between weighted vectors; it's the technique behind large-scale near-duplicate web page detection, where "mostly the same words, similar proportions" is the notion of duplicate that matters.

MinHashSimHash
Input representationA set (shingle membership)A weighted vector (shingle/term frequency)
Similarity it estimatesJaccard (intersection over union)Cosine (angle between vectors)
Signature shapeArray of independent hash minimumsFixed-width bit-string
Natural comparisonFraction of matching array slotsHamming distance (bits differing)

So what: the two techniques solve related but genuinely different problems — whether two prompts share the same short phrases (MinHash's set-overlap question) is not the same question as whether two prompts use similar words in similar proportions (SimHash's vector-angle question), and picking the wrong one answers a question nobody asked.

The Vocabulary That Fits the Shape

Here's the part worth being exact about instead of just calling the ticket wrong. Hamming distance is formally defined for any two equal-length sequences over any alphabet — counting positions that differ works whether those positions hold bits or 64-bit integers. A MinHash signature is a sequence of 64 numbers, so a Hamming distance between two signatures is a perfectly well-formed quantity: count the slots where they disagree.

The thing that changes is not correctness, it's legibility. "38 of 64 signature slots differ" doesn't tell you anything until you divide by 64. "Estimated Jaccard similarity of 0.41" tells you directly: these two prompts share roughly 41% of their shingles, which is the actual quantity DefaultNearDupThreshold needs to be tuned against, because "how much text do these two prompts actually share" is the question a human reviewing false positives asks first.

So what: naming the function EstimateJaccard instead of HammingDistance isn't a stylistic preference — it's choosing the framing that makes the threshold's real-world meaning legible to whoever tunes it next, and that choice is exactly as load-bearing as picking the right algorithm in the first place.

Picking Shingle Size Empirically

The other number this ticket left open is shingle width. Broder's original near-duplicate detection work, built for full web documents, uses a larger window — five or more words — on the reasoning that one edited word only ever costs a document a small fraction of its total shingles.

Prompts aren't documents. They're a sentence or two, so one inserted word (a greeting, a rewording) shifts alignment across every shingle window that touches it, and that's a much bigger fraction of a short prompt's total shingle count. I checked shingle-set overlap for realistic near-duplicate prompt pairs at four window sizes before picking one.

Shingle sizeReworded near-dup pairUnrelated pair
1 word0.790.00
2 words0.640.00
3 words0.500.00
4 words0.350.00

Size 1 degrades to a plain bag-of-words comparison — it can't tell "the driver cancelled the order" from "the order cancelled the driver," because word order carries no signal once shingles are single words. Size 4 drove the genuine near-duplicate pair down near the noise floor, close enough to unrelated pairs that a threshold able to catch it would catch far too much else.

The paper's shingle size assumed a document long enough that one edit barely moves the needle. A prompt is short enough that the same edit moves the whole needle — the right constant depends on what you're hashing, not on which paper you read first.

So what: a parameter borrowed from a paper solving a superficially similar problem at a different scale is a starting guess, not an answer — the only way to know if it transfers is to measure it against the actual data the code will see.

The Generalizable Lesson

The specific thing I built today estimates whether two prompts are near-duplicates. The transferable part is smaller and applies past MinHash entirely.

  1. A metric being technically well-defined for your data (Hamming distance over any sequence) doesn't make it the metric that best communicates what the number means.
  2. A constant borrowed from a related technique's literature (shingle size, from full-document near-dup detection) needs re-deriving against your actual scale, not just re-used.
  3. When two techniques look similar from the outside (MinHash and SimHash both output "small signatures for fuzzy matching"), the useful question is which underlying similarity notion your problem actually needs — set overlap, or vector angle — not which one is more popular.

Naming a function honestly turned out to be the same discipline as picking the right algorithm in the first place: both are decisions about which mental model the next person reading the code inherits.
