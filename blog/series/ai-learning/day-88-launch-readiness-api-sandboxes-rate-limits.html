Day 88 — Launch Readiness — API Sandboxes and Rate Limits

Public demo keys need hard spend caps. Every tenant config cost-budget-enforcer has shipped so far assumed a paying, known tenant — a public demo key breaks that assumption in every direction at once.

AS
Akshant Sharma

9 min read

Sandbox tenant uses cost-budget-enforcer defaults.

That was the whole assumption quietly sitting inside today's routeiq-launch ticket: polish the README, ship a Helm umbrella chart, and put a live demo API key on the landing page so a visitor can hit RouteIQ's real routing pipeline without signing up for anything. The budget enforcement was already built — Days 65 through 69 shipped the thresholds, the Redis-backed counter, and the outage policy. Reusing it for the sandbox key looked like zero new work.

It's a reasonable assumption right up until you ask who the tenant actually is.

The Tenant With No Invoice

Every cost-budget-enforcer config written so far describes a real company: a signed relationship, a monthly invoice, a person who reads an alert webhook and calls someone if the number looks wrong. Day 69's whole argument for defaulting to fail-open rests on that relationship — a missed budget check during a Redis blip is a bounded cost, because there's an invoice at the end of the month that reconciles it, and a human who can explain the spike if anyone asks.

A public demo key has none of that. The "tenant" is anyone who lands on routeiq-launch's page and clicks the sandbox button. There's no signature, no billing contact, no relationship to repair with an apologetic email if the number runs high.

If the budget store goes down and the enforcer forwards every sandbox request unmetered rather than reject it, nobody is going to notice a large bill next month, because there is no bill. The cost lands directly on whoever pays the OpenAI invoice for the whole product, with no tenant on the other end to explain it or absorb it.

So what: fail-open's entire justification depends on someone downstream being able to make sense of the overage after the fact — a sandbox key has no such someone, so the same default that's safe for a paying tenant is unbounded risk for a demo key.

DS analogy — a prepaid gift card, not a credit card
A credit card has a limit, but the limit can be raised with a phone call, and if the merchant's terminal can't reach the bank, most readers still let the swipe through and settle later — the bank trusts you to still be there next month. A prepaid gift card has no such trust to draw on: it has a fixed balance, no reload, and the card issued no promise about tomorrow. When a gift-card reader can't reach the bank to check the remaining balance, it doesn't wave the purchase through and bill someone later — there's no "someone" to bill — it declines the purchase outright. FailClosed: true is that reader. A sandbox demo key isn't a smaller credit line; it's a card with nobody's name on it, so an unreachable balance check has to mean "no," not "probably fine."

Rate Limits Are a Spectrum, Not a Constant

Once the sandbox tenant's config sits next to a real tenant's, the difference isn't a matter of degree — it's a different answer to almost every field config.TenantConfig exposes. A paying tenant like acme gets a budget sized to real usage, a daily window, and the Go zero-value default on FailClosed, which is false. The sandbox tenant gets the opposite on every axis that matters.

FieldPaying tenant (acme)Sandbox tenant (routeiq-launch-demo)
budget_tokens5,000,00020,000
window_seconds86,400 (daily)3,600 (hourly)
fallback_modelgpt-4o-minigpt-4o-mini
fail_closedomitted — defaults falsetrue
Cost of a wrongful rejectA real customer's request failsA visitor clicks the button again
Cost of an unmetered outage hourBounded — one tenant's invoice, reconciledUnbounded — nobody's invoice, nobody notices

Nothing about the enforcer's code changes between these two rows — enforcer.Check reads the same struct fields regardless of who's asking. The config file is the only place the decision lives, and reading a tenant's config is really reading a statement about how much the person who wrote it trusts that tenant to behave, and how much it costs to be wrong in either direction.

So what: a rate limit isn't a fixed policy the enforcer enforces uniformly — it's a spectrum of trust encoded per-tenant, and where a given tenant sits on it says more about the relationship than about the traffic.

One Enforcer, Two Failure Philosophies

The same enforcer.Check function serves both tenants. What differs is which threshold each one is built to hit, and what happens when the store it depends on stops answering.

The sandbox key's budget is deliberately small enough that ordinary sandbox usage lives near the hard threshold already — the point isn't to let it run comfortably under budget the way acme does, it's to keep the ceiling low enough that abuse costs nothing worth abusing. A paying tenant's budget is sized the opposite way: generous enough that the alert and soft thresholds fire long before the hard one, giving a real customer room to be warned and degrade gracefully instead of getting cut off.

The branch that matters most is the one on the right of each path: what happens when store.CheckAndIncrement can't reach Redis at all. pkg/middleware.Wrap and pkg/gateway.Handle both already had this branch from Day 66 onward; Day 69 just gave it a second outcome.

For acme, that branch forwards the request unmetered. For the sandbox key, it returns 503 instead.

So what: the interesting design decision was never the happy-path threshold math — it's what a single dependency failure should mean for a request, and that answer inverts completely depending on who's making the request.

Why FailClosed Is the Cheap Path, Not Just the Safe One

The instinctive read on FailClosed is that it trades speed for safety — reject-and-let-them-retry sounds like the slower, more cautious option next to forward-and-move-on. BENCHMARKS.md measures the opposite on this repo's loopback Redis: a fail-closed 503 costs roughly 6 microseconds, because rejecting skips the Lua EVAL round trip to Redis entirely, while a successful fail-open check that actually runs the counter script costs roughly 250 microseconds. Fail-closed isn't the expensive, careful choice here — it's the fast one.

~6μsFailClosed reject
~250μsFail-open check
20KSandbox tokens/hr
5Macme tokens/day

What fail-closed actually costs is availability, not latency — and availability is worth a different amount to each tenant. A 503 during a Redis blip is a customer-visible outage for acme, the kind of thing that generates a support ticket. For the sandbox key, the same 503 is a visitor's demo button not working for a few seconds, with no support contract to violate and no invoice to protect.

The asymmetry that makes fail-open the right default for a paying tenant — a missed check is bounded and self-correcting — simply doesn't hold for a tenant nobody is billing.

So what: the same one-line config change, fail_closed: true, means something completely different depending on who's on the other end of the request — for acme it would be an unnecessary outage risk, for the sandbox key it's the only default that doesn't leave the bill with nobody to send it to.

Today's Experience Post, Same Question

Today's companion Experience post covers preparing WhiteFalcon's dashboards for a stakeholder review — compressing a dense technical view down to the one screenshot an executive with five minutes of attention actually needs to see. That's a human-scale version of the same design question this post spends its whole length on: what should a limited-attention, limited-trust audience be allowed to see and touch, and what has to stay behind a harder boundary than a trusted audience would need.

An exec reviewer isn't untrusted the way an anonymous demo key is, but the shape of the decision is identical — narrow the surface area on purpose, for the audience in front of you, instead of reusing the surface area built for someone else. Read Day 88's Experience post →

So what: the sandbox tenant's hard cap and the stakeholder dashboard's single screenshot are the same move at different scales — deciding what a limited audience gets to see is itself the design work, not a compromise on top of it.

What's Still Missing

This design reuses cost-budget-enforcer's existing fields rather than inventing sandbox-specific ones, which means it also inherits that module's honest gaps. There's still no metrics counter for fail-closed rejections — no budget_store_fail_closed_total-shaped signal exists anywhere in this repo yet, so today there's no dashboard that would show the sandbox key rejecting requests during an outage versus simply having no traffic. BENCHMARKS.md's 6μs/250μs numbers are also loopback miniredis only — there's no Docker daemon in this sandbox, so no number here has been measured against Redis over a real network.

The landing page ticket itself is also broader than this post: key rotation, expiry, and abuse detection beyond the hard token cap aren't designed yet, only the budget-enforcement slice of "make a public demo key safe" is. That's a real gap, not a rounding error, and it's a fair thing for the launch checklist to flag before the demo key actually goes live.

So what: reusing a well-tested module for a new, riskier audience is the right instinct, but it only covers the part of the risk that module was built to cover — naming the rest honestly is what keeps "we reused the enforcer" from quietly becoming "we assumed the enforcer handled everything."
