Day 29 — The AI Infrastructure Stack — Full Map

Training → inference → observability → agents — where you fit, drawn once for reference

AS
Akshant Sharma
AI Learning · Day 29 of 150
July 2, 2026
19 min read

Drawing a map of the AI infrastructure stack is useful exactly once and then wrong forever in its specifics. Technologies shift every six months, companies add proprietary layers, and the terminology changes with each wave of frameworks. But the broad architecture is stable at the level I care about as a distributed systems engineer: training pipelines, model registries, inference serving, observability, and agent orchestration sit in roughly the same positions relative to each other regardless of which specific tool occupies each slot.

This post is that map. It is not a tutorial on any individual layer — there are better resources for each one. It is a reference document: the kind of diagram you draw once, put on a wall, and return to when you are trying to understand where a new problem sits or how two systems relate to each other. I want you to be able to open this post six months from now and orient yourself quickly, even after the specific tools have changed.

I will cover five layers, the distributed systems problem that makes each one hard, one concrete analogy per layer, and a synthesis at the end on where LensAI sits and what Day 30 (TraceForge) adds. Think of it as the engineer’s field guide to the stack, not the researcher’s introduction to the theory.

Layer 1: Training infrastructure

Training infrastructure is where you make the model. The compute is a GPU cluster — typically A100s or H100s — running distributed training jobs using PyTorch with FSDP (Fully Sharded Data Parallel) or DeepSpeed for splitting model parameters across cards. The data pipeline preprocesses raw text or examples into token sequences and loads them into the training loop from object storage. Experiment tracking tools like MLflow or Weights & Biases record hyperparameters, loss curves, and evaluation checkpoints across runs.

The distributed systems problem in training is not the GPU math. It is the data pipeline. If your tokenizer workers cannot keep GPUs fed, the expensive cards sit idle, waiting for the next batch. This is called a data bottleneck and it shows up as GPU utilization below 80% on the training server dashboard — a wall of expensive cards doing nothing while a cheaper CPU cluster scrambles to catch up. The bottleneck shifts between compute, network, and storage depending on model size, batch schedule, and dataset locality.

Non-software analogy — printing press factory
Training infrastructure is like a printing press factory. The GPU cluster is the expensive press: slow to start, costly per hour, and consuming materials at a fixed rate. The data pipeline is the paper and ink supply chain. If the supply chain cannot keep the press fed, the press stops — and idle press time costs money without producing output. FSDP and model parallelism are like running multiple presses in parallel on the same job, each one handling a section of the plate. The coordination overhead is real and the speedup is not linear.

The “so what” for training infrastructure: most engineers never own the training loop. What they do own is the artifact it produces — the model checkpoint — and the data pipeline that feeds it. Getting the data pipeline right matters as much as getting the model architecture right. A model trained on a stale or miscleaned dataset is wrong from the first token.

Layer 2: Model registry

The model registry is version control for model artifacts. A model artifact is the checkpoint (the weights, a binary blob of hundreds of gigabytes), the tokenizer configuration, the model architecture parameters, and optionally an evaluation record — what benchmarks it scored, what dataset it trained on, what training commit produced it. The registry tracks which artifact is deployed to which environment (staging, production, canary) and who promoted it and when.

The distributed systems problem in the model registry is lineage. A model deployed to production last Tuesday was trained on data from which date range, preprocessed by which tokenizer version, on which architecture configuration? Without a registry with rigorous lineage tracking, debugging a model quality regression becomes archaeology: you are digging backward through Slack messages and Jupyter notebooks trying to reconstruct what changed. The registry that connects training run ID to deployment record to evaluation score is the artifact that makes post-incident analysis tractable.

Non-software analogy — library card catalog
The model registry is a library card catalog for very expensive books, except each “book” is a machine-learning model taking up hundreds of gigabytes on the shelf. The card records not just title and location but edition, printing date, editorial review scores, and which reading room it has been checked out to. When a researcher returns a bad edition (a model quality regression), you need the card to know exactly which printing it was and which previous edition to restore. Without the card, you know something went wrong but not what.

The registry layer is often under-invested. Teams track training runs in a spreadsheet, deploys in a wiki, and end up with a version gap when something goes wrong. The investment in a proper model registry pays off the first time you need to roll back a production model and can do it in minutes instead of hours.

Layer 3: Inference serving

Inference serving is where requests go. A user or application sends a prompt to an API endpoint; a serving framework loads the model weights into GPU VRAM, runs the forward pass (prefill for the prompt, then autoregressive decode for each output token), and streams the token output back. The major open-source serving frameworks — vLLM, TGI (Text Generation Inference), and NVIDIA Triton Inference Server — differ in their batching strategies, memory management, and API surface. Each makes a different trade-off on throughput versus latency versus operational complexity.

The most important innovation in inference serving in the last two years is continuous batching. Traditional static batching fills a batch to a fixed size and runs it — if one request finishes early, its GPU slot sits idle until the full batch completes. Continuous batching schedules at the token step: as soon as one sequence finishes a decode step and is complete, a new sequence is admitted to the batch. The effect is dramatically higher GPU utilization under mixed-length traffic, which is what production workloads look like.

Non-software analogy — short-order diner
Inference serving is a short-order diner counter. The GPU is the cook: it can handle several orders simultaneously because each dish has idle time (waiting for the toast to pop, waiting for the egg to set). Static batching is like the cook who takes exactly four orders, starts all four simultaneously, and won’t take a fifth until all four plates are done. Continuous batching is the experienced short-order cook who takes the next order the moment one dish is plated, keeping the grill full at all times. The throughput difference is significant, the diner analogy is exact, and the scheduling discipline is the hard part.

The KV cache — the attention key-value matrices computed during the prefill phase — is the memory management problem that defines inference serving capacity. These matrices take variable memory depending on prompt length and must be stored in VRAM for the lifetime of the request. vLLM’s paged attention treats the KV cache like virtual memory with fixed-size pages, allocating on demand rather than pre-reserving max sequence length. The analogy to OS virtual memory is intentional and the engineering is genuinely similar.

Layer 4: Observability

Observability for AI inference is different from traditional service observability in two ways. First, the questions are different: not just “is the service up” and “what is the P99 latency” but also “what model actually served this request,” “how many tokens were consumed,” and “what was the quality of the output.” Second, the interesting failures are silent: a model serving incorrect output does not throw an exception or return a 5xx code. The only way to detect quality degradation is to measure it explicitly.

The standard observability trio — logs, metrics, traces — covers availability and latency but misses cost attribution and quality. Cost attribution requires correlating each inference event with the specific model version that handled it, the token counts consumed, and the per-token pricing of that model. This is what the resolved_model_id field in LensAI’s schema does: it records not the model the application requested but the exact model checkpoint that actually ran, including fine-tuned variants and flagd-controlled canary percentages.

Non-software analogy — receipt system and inspector
Traditional service observability is the restaurant reservation system: it tells you whether tables were filled, how long people waited to be seated, and whether they complained. AI inference observability is the itemized receipt combined with the health inspector’s report. The receipt knows what was ordered, how many items, and what the bill was by dish. The health inspector verifies the kitchen is operating at spec. A restaurant can fill tables efficiently and still have a cost problem (wrong supplier) or a safety problem (kitchen running outside temperature range) that only the receipt and inspector combination reveals.

LensAI is built in this layer. The eBPF tracer (in ebpf-llm-tracer) captures LLM API calls by hooking TLS socket operations at the Linux kernel level — no SDK changes required, no application code to instrument. ClickHouse (in infra-ai-streaming) stores the inference events in a columnar format optimized for cost attribution aggregations. Grafana sits on top for alerting and dashboards. The full LensAI stack is the receipt system and the health inspector in one.

Layer 5: Agent orchestration

Agent orchestration is the newest and least standardized layer. An agent is a control loop: it calls a model with a prompt, the model produces text or tool calls, the agent executes the tool calls (querying a database, calling an API, running code), the results go back into the next model call, and the loop continues until a stop condition is met. The orchestration layer manages the loop structure, the tool registry (which tools are available and how to call them), and the memory system (what gets passed back to the model versus stored externally).

The distributed systems problem in agent orchestration is durable state. A long-running agent loop can be interrupted by a network timeout, a model API error, or a context window overflow after many tool call iterations. Recovering from an interruption requires that intermediate tool call results be persisted somewhere durable — not just held in the in-process context array. Frameworks like LangGraph checkpoint each step of the agent graph so that an interrupted run can resume from its last successful node rather than starting over.

Non-software analogy — air traffic control
An agent orchestrator is an air traffic controller. The ATC does not fly the planes — the models do that, each request being one plane in the pattern. The ATC knows which runways are open (which tools are callable), enforces separation (prevents the agent from calling the same tool recursively in a tight loop), sequences arrivals and departures (orders tool calls to avoid conflicts), and decides when a plane is cleared to land (when the agent loop terminates). Without the ATC, multiple planes try to land simultaneously. Without an orchestrator, an unbounded agent loop exhausts its context window and crashes without producing output.

The interesting infrastructure question for agents is observability: when a multi-step agent loop produces a wrong answer, which step went wrong? Was it the first model call (bad planning), a tool call (incorrect retrieval), or a later model call (failure to synthesize)? This is a different observability problem from tracing a single inference call, and it requires capturing the full loop trace rather than individual spans. This is the gap TraceForge addresses at Day 30.

Where LensAI fits in the map

LensAI sits in Layer 4 (observability) but its observation points span three layers. The eBPF tracer watches below Layer 3 — at the kernel syscall level, it sees every TLS socket operation that carries LLM API traffic, regardless of which Layer 3 serving framework generated it. ClickHouse stores the resulting events in a format that references Layer 2 — the resolved_model_id field connects each inference event to the specific model version from the registry. Grafana at the top connects to Layer 5 — agent tool call telemetry will flow through the same ClickHouse store once TraceForge is integrated.

What I find clarifying about drawing this map is where LensAI is not. It is not in the training pipeline — it has no visibility into gradient descent, dataset preprocessing, or experiment tracking. It is not in the model registry — it does not manage checkpoints or deployment state. It is not in the agent orchestration loop itself — it observes the inference calls the loop makes, but it does not record tool call structure or planning steps. Each of these gaps is real, and naming them helps define the boundary of what LensAI is for.

The boundary that matters most is between Layer 4 (what LensAI does) and Layer 5 (agent traces). A single inference call from an agent loop looks identical to a single inference call from a direct API call at the kernel level. The eBPF tracer sees both the same way. What it cannot see is that the agent call was step three of a five-step planning loop, that the previous step returned a context that influenced this call, and that the next step will use this response to decide whether to retry. That context — the agent loop structure — requires a different instrumentation layer.

Day 30: TraceForge fills the agent observability gap

Day 30 introduces TraceForge, a lightweight agent trace collector. Where LensAI observes Layer 3 (inference serving) from below via eBPF, TraceForge observes Layer 5 (agent orchestration) from above via a thin SDK wrapper. Each agent tool call, each model invocation within the loop, each intermediate result, and each loop iteration is captured as a structured trace event and written to the same ClickHouse store that holds LensAI’s inference events.

The integration goal is a trace that spans from the initial user request through every tool call to the final response, with cost attributed to each model invocation from LensAI and loop structure attributed to each step from TraceForge. This gives the full picture: how much did this five-step agent run cost, which model calls were expensive, and which step produced a wrong intermediate result that caused the final answer to fail. The stack map is only useful when you can observe the whole stack, not just one layer.

What I didn’t expect when I started building LensAI was that the observability problem would be more interesting than the inference problem. Inference serving is largely solved by excellent open-source frameworks. Observability at the resolution needed for cost attribution and quality tracking — especially across multi-step agent loops — is not solved. That gap is what makes the next week of building genuinely interesting work.
