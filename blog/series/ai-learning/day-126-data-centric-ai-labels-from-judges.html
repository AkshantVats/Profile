Day 126 — Data-Centric AI — Labels from Judges

"Filter judge_score>0.8 in export." That's the entire hook this ticket gave me, and it reads like a one-line filter nobody needs to think twice about. It's also, taken literally against the real schema, close to not a filter at all — which is the whole subject of this post.

The Instruction That Was Almost a No-Op

Day 121's connector shipped exactly what the ticket said: a threshold constant, 0.8, compared against every row's judge_score with a strict greater-than. It built, it tested clean, and it looked done. What it didn't do — because nothing in a unit test against a fake reader would catch this — is filter much of anything.

infra_ai.judge_scores.judge_score is documented in its own migration file as a weighted 0-100 score, not a 0-1 fraction. Against that column, a literal 0.8 threshold admits every row scoring above eight-tenths of one point out of a hundred — which is to say, essentially every row a judge model has ever scored, including the bad ones.

So what: the ticket's own wording wasn't wrong, and the code that implemented it literally wasn't buggy in the way a test suite checks for — the gap was between a plain-English "0.8" and the actual unit that number was supposed to be measured in, and that gap doesn't throw an exception. It just quietly stops filtering.

The Thermostat Mechanism

DS analogy — a threshold that's the right number on the wrong scale
A smart thermostat set to "alert below 20" is a perfectly sensible instruction if 20 means twenty degrees Celsius, room temperature. Wire that same thermostat to a sensor reporting Fahrenheit and leave the threshold at 20, and the alert almost never fires — 20°F is far colder than any room a person is standing in, so the "below 20" condition the instruction meant to catch essentially never triggers on the scale the sensor actually reports. The thermostat isn't broken. The number "20" is correct English and wrong physics, and the failure mode isn't an error message — it's a room that quietly never gets flagged as cold, no matter how cold it gets, because the threshold and the reading were never speaking the same scale.

That's precisely judge_score>0.8 against a 0-100 column: a threshold that's syntactically valid, semantically reasonable-sounding, and numerically almost meaningless on the scale the data actually uses.

So what: a scale mismatch between a threshold and the data it's applied to is one of the quietest failure modes in a data pipeline, precisely because nothing about it looks wrong — the code compiles, the query runs, and the only symptom is a filter that passes almost everything through.

Labels, Not Facts

"Data-centric AI" gets described as spending more effort on the dataset than the model, which is true but incomplete. The sharper version, after fixing this bug, is that a judge score is a label — something a separate model produced about a row, on a scale and a convention someone has to get right — not a fact baked into the row itself the way request_id or tenant_id is.

A label can be miscalibrated, mis-scaled, or silently reinterpreted by the next person who reads it, in a way a structural column mostly can't. Treating judge_score as self-evidently correct is exactly what let a 0.8-versus-80.0 mismatch ship in a PR whose own tests passed, because the tests checked that the comparison ran — not that the comparison meant what the ticket intended.

So what: "the judge already scored it" answers whether a label exists, not whether every consumer of that label agrees on its scale — and a data-centric pipeline's actual job is closing that second gap, which a model-centric mindset has no reason to even look for.

Today's Quartile, on Top of the Corrected Threshold

Today's ticket ran the corrected 80.0 threshold, plus Day 123's dedup and bottom-quartile quality filter, over 10,000 synthetic rows end to end. The threshold from Day 122's fix isn't the only quality gate in this pipeline anymore — it's the first of two, and the quartile filter downstream computes its own threshold fresh from whatever distribution survives scrub and dedup.

That 55.10 is not a constant anyone chose — it's the 25th percentile of whatever judge_score values happened to survive scrub and dedup in this run, recomputed every time QualityFilter runs. A fixed threshold like Day 121's 80.0 and a recomputed percentile like Day 123's quartile filter are answering different questions: one asks "does this row clear an absolute bar," the other asks "is this row in the bottom slice of whatever I actually have today."

So what: a pipeline with only the fixed threshold would have shipped the Day 121 scale bug forever, since 0.8-on-a-100-scale never throws an error to catch it — the quartile filter downstream doesn't fix that bug, but it's a second, independently-computed signal that a badly miscalibrated first gate would eventually make visible as a distribution shift, which is exactly the kind of check a purely model-centric pipeline has no equivalent of.

A judge score is a label someone else computed, on a scale someone else chose. The moment a pipeline treats it as ground truth instead of as data with its own provenance to check, a mismatch this quiet gets to ship clean.

The Generalizable Lesson

The specific bug here was a decimal-versus-percentage mismatch on one column. The transferable part is smaller and applies to any pipeline that filters on a label produced by a separate system.

  1. A threshold that's syntactically valid and semantically plausible can still be numerically wrong for the data it's compared against — and unlike a type error or a null pointer, a scale mismatch produces no exception, only a filter that quietly does less than intended.
  2. A label from an external scorer (a judge model, a human rater, a heuristic) carries its own units and conventions that the label's own name doesn't state — "judge_score" says nothing about whether it's 0-1 or 0-100, and the schema, not the field name, is the only place that's actually pinned down.
  3. A second, independently-computed quality signal downstream (like a recomputed quartile) doesn't prevent a scale bug in an earlier fixed threshold, but it's the kind of redundancy that eventually surfaces one as a distribution anomaly — a single gate has no such backstop.

Writing "filter judge_score>0.8" took one line. Confirming that 0.8 meant what the person who wrote the ticket meant took reading a migration file's own comment — the part of data-centric AI that never shows up in a ticket's one-line hook.
