Day 68 — Gateway Middleware Ordering

Order matters — wrong order leaks spend. A budget check, a cache lookup, and a model call are three stages in a chain, and the chain's entire cost guarantee lives in which one runs first.

A middleware chain is usually presented as a list: request comes in, passes through stage one, then stage two, then stage three, response comes out. The list framing hides the one property that actually determines whether the chain is correct — not which stages exist, but which one gets to run first.

Today's stub gateway has exactly three stages: check the tenant's budget, look up the semantic cache, call the model. Reorder those three and the code still compiles, the types still line up, and the chain still "works" in the sense that a request still gets a response — it just stops being the chain that was supposed to protect anyone's spend.

A Chain Where Order Isn't Cosmetic

Chain of Responsibility, the design pattern this shape belongs to, is usually taught as if the stages were interchangeable — each handler decides whether to act and whether to pass the request along, and the pattern's job is just wiring them together. That framing quietly assumes every stage is cheap and side-effect-free to invoke, which is exactly the assumption a cost-control chain can't make.

A cache lookup isn't free. A real semantic cache can cost a paid embedding-API call on a miss, and a model call obviously costs money outright. The moment even one stage in the chain has a real cost to invoking it, the chain's order stops being a style choice and becomes the thing that decides whether an over-budget tenant gets stopped before any of that cost happens, or after.

DS analogy — a bouncer's line, not a self-serve bar
A bar with a bouncer checks ID at the door, before anyone reaches the counter to order a drink. A bar that let people order first and checked ID on the way out would still "work" in the sense that drinks get served and IDs eventually get checked — but every underage order already cost the bar a poured drink it can't get back. The ID check has to be the first stage specifically because every stage after it has a cost that, once incurred, can't be un-incurred.

So what: a chain of stages with different costs isn't fully specified by which stages exist — it's only fully specified once you've also fixed which one has the right to run first, and that decision belongs to whichever stage's failure mode is "reject before spending," not to whichever stage happens to be cheapest to write first.

Three Orderings, One Correct

Put the same three stages in different orders and the failure mode changes shape each time. Budget, then cache, then model — the order today's gateway implements — means a blocked tenant never reaches the cache or the model, so a block's cost is provably zero.

Cache, then budget, then model looks almost identical on a fast path, because a cache hit never reaches the budget check either way. It diverges exactly on a miss: a tenant already over budget still pays for the cache lookup — and whatever that lookup itself costs — before the budget check ever gets a chance to reject the request.

So what: the three orderings aren't three equally valid designs with different tradeoffs — only one of them makes "a block costs zero" a claim that's actually true, and the other two just move the leak to a different stage instead of closing it.

Proving Order With a Spy, Not a Log Line

The tempting way to test an ordering claim is to assert on the outcome: send a request that should be blocked, check that the response says blocked, check that cost_usd came back zero. That test would pass even if the implementation quietly ran the cache lookup anyway and just discarded its cost — the assertion never looks at whether the downstream stage was invoked, only at what the final number says.

Today's test suite asserts on the call itself instead. TestHandleBlockedNeverTouchesCacheOrModel wraps both the cache client and the model client in a spy that records whether it was ever invoked, then checks that spy directly — not the response, the spy.

1Fixed order the gateway enforces: budget, then cache, then model
3LensAI event sources — one per way a request can actually leave the chain

That distinction matters because an outcome-only test and a call-only test can both pass against a correct implementation, but only the call-only test fails against a specific class of regression: someone reordering the stages while leaving the final response shape untouched. A refactor that swapped Cache and Budget would still return the right JSON on a block — it just wouldn't be free anymore, and only a spy watching the calls themselves would catch that.

So what: when the property under test is "stage X never runs," the only test that actually verifies it watches the call itself, because any test that only watches the final output can be satisfied by an implementation that does the expensive thing and hides the receipt.

A chain of responsibility with real costs attached to its stages doesn't have an arbitrary order to wire together — it has exactly one order where the guarantee is true, and every other order that compiles.

What Getting the Order Right Doesn't Fix

Fixing the order solves the sequencing problem, not every problem the chain will eventually face. A real cache and a real model, called concurrently across many requests for the same tenant, can still race on the budget counter itself — that's a different hazard, the one pkg/store's Lua-script atomicity already closes at the counter level, one layer below where pkg/gateway operates.

Today's stub also can't say anything about a real cache's actual hit rate or a real provider's actual latency, because both clients are fakes standing in for a fixed order this post is entirely about proving. Getting the sequence right is a precondition for a trustworthy cost guarantee, not a substitute for the concurrency and integration hardening a real backend will still need.

So what: ordering is the first bug class a cost-sensitive chain has to eliminate, because every other correctness property — concurrency safety, real backend behavior — is being measured against a sequence of stages that has to already be the right one, or none of those later guarantees mean what they claim to.
