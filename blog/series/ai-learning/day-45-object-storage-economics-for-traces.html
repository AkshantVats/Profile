Day 45 — Object Storage Economics for Traces

JSONL, zstd, lifecycle policies. Traces are logs; price them like logs. pkg/export compresses pkg/eventlog output with zstd, checksums the compressed bytes with SHA-256, and classifies every object into a hot/cold/expired retention tier — tested entirely against an in-memory ObjectStore fake.

Traces are logs; price them like logs.

That single sentence is the entire design brief behind today's pkg/export package, and it took a specific kind of arithmetic to make it obvious. A metrics counter compresses forever — a million requests and ten requests both cost one integer to store, because a counter only keeps the aggregate. An agent trace does not get that discount: every tool call, every model turn, every retry is its own immutable event, and Day 44's event log already established that you cannot throw any of them away without losing the ability to replay a failure.

So the event volume that pkg/eventlog records on Day 44 becomes, on Day 45, a storage bill. A single agent run with five tool calls writes five KindToolCall events plus five KindToolResponse events plus the prompt, the model turns, and the final output — more than a dozen JSON records for one run, and a production agent making decisions all day produces that shape thousands of times over.

The right mental model for that volume is log data, not metrics and not a queryable database. A metrics system stores an aggregate and discards the events that produced it; a database stores current state and overwrites the old value on every update. A trace log has to keep every individual event, unmodified, for as long as its retention window says — which is exactly the storage problem logging infrastructure solved decades before agents existed, so today's code borrows the solution instead of reinventing it.

So what: once you accept that a trace log is priced like Kafka's log retention or a web server's access log — per byte, per day kept — the three levers that actually matter become obvious: how small can you make each byte, how do you prove a byte wasn't corrupted in transit, and how long do you have to keep it before it's safe to let go.

DS analogy — the freight depot that vacuum-seals and weighs at the gate
A freight depot vacuum-packs every pallet before it goes into storage: same cargo, a third of the volume, cheaper warehouse space per unit stored. The depot doesn't trust the pallet's own paperwork to prove nothing was swapped in transit — it staples a weigh ticket to the outside of the sealed pack and checks that ticket against the pack itself every time it changes hands, because the ticket is on the tamper-evident wrapper, not buried inside cargo nobody wants to unpack just to verify it. Aisle assignment — loading dock, back warehouse, or the scrapyard queue — is decided purely by how long the pallet has sat there, never by what's inside it.

The Export Path: EventLog to Object Store

The pallet is an eventlog.EventLog — the append-only record Day 44 built, one JSON line per event. pkg/export's Exporter takes that log, serializes it to JSONL (JSON Lines: a file format where every line is a standalone JSON object, so a reader can start decoding from any line without parsing the whole file first), and writes it under a deterministic key: traces/{trace_id}/{first_seq}-{last_seq}.jsonl.zst.

The write is not one object, it's two: the compressed .jsonl.zst payload and a sibling .sha256 file holding the hex digest of the compressed bytes. Both go through the same ObjectStore interface — a Go interface with just Put, Get, Delete, and List — which is the abstraction that lets everything downstream in this post stay agnostic about whether the destination is MinIO or a fake.

So what: the key layout mirrors how any log-shipping pipeline names its files — predictable, prefix-scannable, no separate index needed to find a trace's objects — because a trace export that requires a lookup table just to find its own data has reintroduced the exact complexity a flat object key was supposed to avoid.

Compression: Why zstd, Not gzip

zstd (Zstandard) is a general-purpose compression algorithm, and the choice over the more familiar gzip comes down to two numbers: compression ratio and decode speed. At comparable settings zstd produces smaller output than gzip while decompressing faster, and faster decompression matters specifically because these objects get read back mid-investigation, when an on-call engineer is waiting on the download to start a replay.

zstd is also frame-based, meaning it compresses data in self-contained chunks rather than requiring the entire input in memory at once before it can start. That property lets the exporter stream a large event log through compression instead of buffering the whole JSONL blob first, which keeps memory use flat regardless of how long a trace ran.

klauspost/compress/zstd is the library pkg/export uses, and it's pure Go with no cgo dependency — no C toolchain required to build the package on any platform CI runs on. That's a small detail with an outsized payoff: a compression choice that complicates the build is a compression choice that gets quietly reverted the first time someone can't get the binary to compile.

So what: zstd isn't chosen because it's newer or trendier than gzip — it's chosen because a trace store that's expensive to read back defeats its own purpose, and decode speed is the number that determines how long an incident stays open while someone waits for a download.

The Checksum Sidecar: Why Hash the Compressed Bytes

A checksum is a short fixed-size fingerprint computed from a file's bytes, and it changes if even a single bit of the input changes. pkg/export uses SHA-256, a cryptographic hash algorithm chosen because the fingerprint needs to be practically impossible to forge, and stores it as a checksum sidecar — a small companion object that holds the fingerprint next to the data it verifies, instead of inside the object's own metadata fields.

The deliberate design decision is that the checksum covers the compressed bytes, not the original JSONL. That means Verify can re-download an object, hash exactly what it received, and compare that hash against the sidecar without ever needing to decompress first — verification and decompression become two independent operations instead of one that silently depends on the other succeeding.

Checksumming pre-compression bytes instead would create a blind spot: it would prove the original data was intact at the moment of compression, but say nothing about whether the compression step itself, or the write to the object store, corrupted anything afterward. Hashing after compression means the sidecar verifies exactly what left the process and exactly what a fresh download will produce — the two things someone actually needs to know when they're deciding whether to trust a trace before replaying it.

The sidecar lives as its own object rather than as store metadata for a portability reason: S3-compatible metadata can be dropped or altered across a copy, a replication job, or a backend migration depending on configuration, while a plain object survives any of those operations and can be inspected by hand with nothing more than sha256sum. Exporter.Verify automates that check, but the fact that it's inspectable without the exporter's own code is what makes it trustworthy years later.

So what: the checksum sidecar turns "did this object survive intact" from a question you have to trust the storage layer to answer honestly into a question any tool with a SHA-256 implementation can answer independently — which is the entire point of a tamper-evidence mechanism.

Retention Tiering: Why 30 and 90 Days

A retention tier is a named bucket — hot, cold, or expired — that determines how an object should be treated based purely on its age. RetentionPolicy.Classify(age) is a pure function: given a duration, it returns a tier, with no I/O, no side effects, and no dependency on anything other than the number handed to it.

Zero to thirty days is hot, thirty to ninety is cold, and anything past ninety is expired, with the boundary inclusive on the lower edge — an object exactly thirty days old classifies as cold, and one exactly ninety days old classifies as expired. Those specific boundaries echo the hot/cold split from today's Experience post on WhiteFalcon's tiering, adapted down from a metrics time series to how often anyone actually re-opens a trace after an investigation closes.

Retention bugs live at boundaries, not in the middle of a window, which is why the test suite exercises 29, 30, and 31 days, then 89, 90, and 91 days explicitly rather than trusting a handful of round numbers to prove the logic. A pure function makes that kind of edge-case testing trivial — no store to set up, no clock to fake, just a duration in and a tier out.

Sweep scans an ObjectStore under a prefix and returns every key currently classified as expired, but it does not delete anything — it returns candidates only. That's a deliberate step back from a pure cost-optimization design, which would auto-delete on a schedule; a debug-oriented system loses its entire reason to exist the day a trace someone needed vanishes silently as a side effect of a cron job.

So what: separating "what tier is this object in" from "should this object be deleted" means the retention logic can be tested exhaustively as pure math, while the actually irreversible decision — deletion — stays a step a human takes on purpose.

Testing Against a Fake, Not a Live MinIO

An in-memory fake (sometimes called a test double) is a stand-in implementation of an interface that lives entirely inside the test process and mimics the real thing's observable behavior without any of its infrastructure. pkg/objectstore/memory.go implements the same four-method ObjectStore interface that the real MinIO-backed client does, and every test in pkg/export runs against that fake instead of against a running MinIO container.

This works because the Exporter and RetentionPolicy code never call anything on *minio.Client directly — they only ever call Put, Get, Delete, and List on the narrow ObjectStore interface. Programming against a narrow interface instead of a concrete client is what makes the fake possible at all: if the exporter had reached past the interface for a MinIO-specific feature, the fake could no longer stand in for it.

The payoff shows up directly in CI: no MinIO service to start, no network calls to time out, no flaky container health check between test runs. Retention-boundary tests, checksum-corruption tests, and round-trip export tests all become deterministic — the same inputs produce the same outputs every single run, which is not something you can promise about a test that depends on a live network service being reachable and healthy at that exact moment.

The real pkg/objectstore/minio.go implementation still exists and still gets compiled — go build ./... and go vet ./... cover it for type errors even though no unit test exercises it against a live server. That's a conscious tradeoff: build-time coverage catches a broken method signature, while genuinely exercising the MinIO client end to end is a job for an integration environment that has a real object store running, not for the fast unit suite that runs on every commit.

So what: testing against a fake isn't a shortcut taken because standing up MinIO in CI is hard — it's the correct architectural consequence of the interface being narrow enough to fake convincingly, and a narrow interface is a design goal worth optimizing for on its own.

The checksum proves a byte wasn't corrupted. The retention tier decides how long you're allowed to ask that question. Neither lever knows the other exists, and that's exactly why the interface stays small enough to fake.

What This Sets Up for Day 46

None of today's code replays anything — it only makes sure a trace survives long enough, cheaply enough, and provably enough to be replayed later. That ordering is deliberate: Day 46's replay runner needs to trust that the event log it's reading is the same one that was written, or every replayed failure is just as unreliable as the live API call it was meant to replace.

JSONL on an S3-compatible store is Ceph for traces — cheap bytes, replayable history — and today's contribution is making that phrase literally true instead of aspirational: compressed for cost, checksummed for trust, tiered for a retention window somebody actually chose on purpose.

So what: storage is boring compared to replay logic, and that's exactly why it has to be built first and built solid — a replay engine sitting on top of untrustworthy storage is a system that reproduces bugs it can't actually prove happened.
