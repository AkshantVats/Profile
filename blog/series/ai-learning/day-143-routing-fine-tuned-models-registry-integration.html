Day 143 — Routing Fine-Tuned Models — Registry Integration

Auto-register on promotion event is today's hook, and my own PR is the one that wires it: RouteIQ learns about a newly promoted model only when model-registry says so, not from a human editing a config file. It doesn't hand that model the full traffic either — it trials the new endpoint at 10% while the endpoint that already earned its trust keeps the other 90%.

Two days ago, vllm-deploy-kit/DESIGN.md named a gap on purpose and left it open: something needs to read model-registry's current production entry and turn it into a running endpoint, but nothing in that PR built it. Today's own PR is that something. It reads model-registry for the entry a promotion just approved, registers a new endpoint with RouteIQ — the weighted-routing proxy that already sits in front of every model call — and starts that endpoint at a fraction of RouteIQ's traffic instead of the whole thing.

A Diner Soft-Launches a New Special

DS analogy — the diner that soft-launches a special
A kitchen tests a new dish on staff for weeks before it's a menu item, and none of that testing puts the dish in front of a paying customer. The chalkboard on the wall doesn't get updated the moment the recipe is good — it waits for the health inspector to actually sign off, because "tastes good to the cooks" and "cleared to serve the public" are two different bars. Even once the chalkboard changes, the host doesn't seat every walk-in at the new dish's table: for the first stretch, roughly one party in ten gets sat there while the rest still order the dish that's already proven out.

Every piece of that analogy maps onto a real gate in this repo. Recipe-testing-on-staff is a run's eval_scores while it sits at stage="staging", and the inspector's signature is promote_to_production().

The chalkboard update is today's auto-register step, which fires only on that promotion event. The one-in-ten seating is the weighted routing trial — nothing here reaches full traffic on day one.

So what: every step in this chain exists to keep an unproven model from a customer's plate on the strength of a good kitchen test alone — the same posture a health inspector takes toward a cook's own opinion of their cooking.

The Gate Before Any of This Fires

model-registry/model_registry/registry.py's promote_to_production() is the inspector's signature, and it's a strict one. It gates on the worst task_type in a run's eval_scores, not the average — every entry has to individually clear a minimum win-rate and, by default, pass a significance check, so a model that's great at one task and mediocre at another does not get called "production ready" because the mean looks fine. Refuse the promotion, and today's auto-register step never sees the entry at all: RouteIQ can't register an endpoint for a model that never crossed the bar in the first place.

That refusal is also permanent in one direction. A RegistryEntry can only move from stage="staging" to stage="production" once, ever — there's no demote_to_staging() in this module by design. Once an entry is production, its artifact_prefix is the one field the rest of today's pipeline cares about; everything else on the entry exists to justify why it was promoted, not to describe how to run it.

So what: by the time today's auto-register step is even triggered, a model has already survived the strictest reading of its own eval results — the routing decisions from here on are about how much to trust that result operationally, not whether to trust it at all.

vllm-deploy-kit/DESIGN.md §5 already named the interface boundary in plain language: a production-stage entry's artifact_prefix is the one fact that crosses from model-registry into anything that serves the model, and nothing else on the entry — not eval_scores, not dataset_hash, not git_sha — is the serving side's concern. What that document explicitly reserved and left unbuilt was the controller: something that, given a model_name, scans list_versions() for the highest-semver entry with stage="production" and resolves it into a real pod spec or a real registered route.

Today's PR is that controller, scoped to RouteIQ instead of a pod spec. On a promotion event it does exactly the scan §5 described, then calls into RouteIQ to register a new endpoint pointed at that artifact_prefix. No human edits a routing config to make a freshly promoted model reachable.

So what: this isn't a new mechanism bolted onto two unrelated systems, it's the specific reserved seam §5 drew two days ago, built to the exact contract that document already fixed — the interface and the code that crosses it arrived on different days on purpose.

Weighted Routing Reuses a Shape That Already Existed

The 10%-vs-90% split isn't a new flag format either. distributed-flagd already has a weighted-variant shape — a flag with Variants carrying a Value and an integer Weight out of 100 — that "model-rollout:{tenantID}" flags use to split traffic between two named models. shadow-traffic-router's own shadow_percent sampler reuses that identical shape for a completely different purpose: deciding whether a request also gets mirrored for offline comparison, with a "mirror" vs "skip" variant pair instead of two model names.

Today's weighted trial is the third reuse of the same shape, not a fourth flag format invented to fit this case. The freshly-registered endpoint becomes one Variant at weight 10; the existing production endpoint keeps weight 90; the flag resolves per request exactly the way a shadow_percent flag or a model-rollout flag already does.

So what: the interesting design decision here already happened, on an earlier day, for an unrelated reason — today's PR is a consumer of that decision, not the author of a new one, which is exactly the kind of reuse a design doc's own §2 justification ("fix the interface first, in a place both sides can read") is supposed to produce two modules later.

What I Still Don't Know

I haven't read today's actual diff line by line the way I read registry.py's promote_to_production() for this post — the code is being written on its own track today, and what I've verified directly is the interface it's built against: DESIGN.md §5's reserved contract and the weighted-variant shape distributed-flagd and shadow-traffic-router already use. I also don't know whether the controller polls the registry on an interval or reacts to an actual promotion event/webhook — §5 explicitly left "however that call happens" open, and I have no evidence pinning down which one today's implementation picked.

So what: the mechanism — a promotion event has to happen before RouteIQ knows anything, and even then the new endpoint earns traffic gradually instead of all at once — is the part grounded in a design document and a code shape I've actually read; the exact trigger mechanics are a gap I'd rather name than guess past.
