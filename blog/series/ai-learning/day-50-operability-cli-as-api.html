Day 50 — Operability — CLI as API

If it's not scriptable, on-call won't run it at 3am.

That's not a complaint about laziness. It's a fact about working memory: a tool with five undocumented ways to combine its flags is a tool nobody fully trusts under pressure, no matter how correct its logic is. Trust in a debugging tool isn't earned by the mechanism alone — it's earned by the interface being predictable enough that a tired person doesn't have to guess.

A Labeled Panel vs. an Unlabeled Junction Box

DS analogy — the panel you can read vs. the one you can't
A well-labeled circuit breaker panel lets anyone cut power to one specific room by reading a printed label and flipping one switch. A junction box with unlabeled wires technically lets you do the same thing — cut power to that room — but only if you already know which wire is which, which means only the person who wired it can safely touch it. Both boxes have the same mechanism inside. Only one of them is an interface anyone else can operate.

A CLI is the same kind of box. traceforge replay and traceforge diff could each have grown their own bespoke flag conventions, their own ad-hoc output formats, their own "you had to be there when it was built" quirks. Instead both take --log plus one or two --trace-* ids, and both signal success or failure the same way: stdout for the result, a nonzero exit code for failure. That's the printed label on the panel.

So what: two commands that behave the same way under the hood are worth less than two commands that are also predictable from the outside — the second property is what makes a tool safe for someone other than its author to operate.

Every step in the seven-step on-call runbook shipped alongside this post reduces to that same diagram: pick a runbook step, run the flag it names, read the exit code, decide the next action. Nothing in that chain depends on whether a human typed the command or a CI job invoked it programmatically — the contract doesn't know the difference, which is exactly the point.

Compare that to a tool whose success is only legible by reading prose in the middle of its stdout, or whose failure mode is a silent zero exit code with an error buried in a log line. Neither of those is wrong, technically. Both are more expensive for anything downstream — a script, a human, a future version of the same CLI — that needs to act on the result without re-reading the whole implementation first.

So what: an API's real interface is its exit codes and its output shape, not its help text — the help text is documentation about the contract, not the contract itself.

The Smoke Test Is a Contract Test

The unit suite already proves pkg/replay, pkg/diff, and pkg/mocker are individually correct — each package's tests build an eventlog.EventLog in memory and assert on its behavior directly. None of that exercises the compiled binary a human actually types, which is a different question: does the CLI still honor the contract described above, end to end, flags in and exit code out.

scripts/smoke_test.sh answers that question specifically. It builds the real traceforge binary, runs it against a checked-in sample bundle, and asserts on actual stdout, stderr, and exit codes — not on any Go function call. A regression that broke flag parsing, or changed an exit code's meaning, or silently dropped a message the runbook depends on, would pass every package's unit tests and still fail this one script.

So what: a contract test and a unit test answer different questions — one checks that the logic is right, the other checks that the promise made to whoever calls the CLI is still being kept.

The Same Invocation, Twice

The payoff of building the CLI this way shows up in what didn't need to be built: there's no separate "automation mode" flag, no JSON-output variant reserved for scripts while humans get the friendly version. The exact command a runbook tells an on-call engineer to type — traceforge replay --log run.jsonl --trace-id trace-1 --inject-timeout 4 — is the same command CI runs unattended against the sample bundle every time this repo changes.

A tool doesn't get "made scriptable" after the fact — it either was designed with one contract from the start, or it accumulates two: one for people, one for scripts, that quietly drift apart.

That's also why the runbook and the smoke test could share a fixture. If the human path and the automation path were genuinely different interfaces, testing one would say nothing about the other, and the runbook's commands could silently rot the moment nobody happened to run them by hand.

Operability Decided at the Flag-Parsing Layer

None of this changed what replay or diff actually do — Day 50 added no new replay mechanics. What changed is the confidence that the interface built across Days 44 through 49 still means what the README says it means, checked by the same CI that checks the code, not by a human remembering to try it.

A debugging tool's operability is a property of its flag-parsing layer and its exit codes, decided when the CLI is designed — not a feature bolted on after the mechanism works. That's as true for a two-command tool like traceforge as it is for any production API a distributed systems engineer ships.
