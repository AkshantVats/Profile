Day 11 of Learning LLM Inference — Semantic Caching vs Exact-Match Redis

Embeddings as cache keys — false positive risk as SLA

AI Learning · Day 11 of N

At 4 ms, the exact-match Redis cache looked like a win: the request returned fast, the cache hit counter smiled, and nobody paged. But the user question was semantically different from the stored prompt, so the answer was wrong with high confidence—fast wrong, not slow wrong.

A semantic cache hit is approximate nearest neighbor with business consequences — tune the similarity threshold like a tail-latency SLO. The anomalies topic is where exact rules end — semantic cache false positives will land in the same operational queue; in Experience 11, that mindset shows up as idempotent apply for at-least-once OTA.

The cache hit that was wrong (cold open)

Benchmarks that report latency only tell half the story. A cache hit changes the semantics of “success”: exact-match Redis returns the cached completion only when bytes are the contract; semantic caches return when embeddings are “close enough.” The operational question is not “did we save tokens?” — it’s “what is the worst acceptable wrongness, and where does that event go?”

That is why this post treats semantic caching as architecture, not a micro-optimization: it is an approximate nearest neighbor lookup, and the similarity threshold τ becomes an SLA dial.

Three cache layers — do not conflate them

Day 7 covered provider prefix caching: byte-identical prompt prefixes get a deterministic hit. Day 1 covered session KV caching: decode state is deterministic inside one request. Today’s layer is an application semantic cache: store (prompt embedding → completion) (or retrieval bundles) under your own service-level contract.

Exact caches fail on drift; semantic caches fail on similarity.

Exact-match Redis — when bytes are the contract

Mechanism: build a deterministic cache key from normalized prompt bytes plus routing attributes (for example model_id, temperature, and any tool/schema version). Store the completion blob with TTL + LRU eviction. On a hit, you return the cached JSON without touching the full LLM inference path.

Strengths: if your normalization pipeline is stable, exact-match caches have zero semantic false positives and predictable latency. Debugging is audit-friendly: the key tells you exactly which bytes produced which answer.

Weaknesses: near-duplicate prompts miss (paraphrase = new bytes), context ordering breaks byte identity, and multilingual paraphrase can crush hit rates even when meaning is unchanged.

DS analogy (required bridge):

At Wayfair, deterministic caching worked when the bytes represented a stable contract (canonical offer identity), not when the “same data” arrived as different raw strings. Exact caches don’t fail because Redis is wrong; they fail because the bytes stopped being the contract.

Semantic cache — embeddings as keys

Mechanism: embed the incoming prompt (using the same embedding model used to build the index), run ANN search (top-1 or top-k), and compare the similarity score against τ. If sim ≥ τ, return the cached completion without calling the full LLM path; otherwise fall back to full inference.

False positive mode is different: exact caches fail because bytes drift; semantic caches fail because similarity lies. A wrong answer at 10 ms can look like a perfect latency metric while quietly spending trust.

Options table — exact vs semantic vs hybrid

Exact Redis when bytes are the contract; semantic cache when paraphrase is the traffic. In practice the safest default is a hybrid path: exact key first, semantic lookup only when you can tolerate approximate meaning.

False positive risk as operational SLA

Define an error budget for semantic cache false positives the way SRE defines an error budget for availability: latency metrics can stay green while trust is spent. A “semantic hit” has to carry its own wrongness budget.

Detection paths (today vs future wiring):

  • User thumbs-down / regeneration signal
  • Downstream task failures (tool parse error spikes, workflow rejects)
  • Human review on the high-similarity band just below τ (the gray zone)

Day 5: deterministic hash routing for eval keeps comparisons fair—semantic caching breaks determinism unless you exclude eval traffic or key on a trace bucket.

Day 3: cost accounting must reflect avoided tokens; a semantic hit should emit cache_hit=true plus fields like llm_tokens_saved and embedding_cost_usd.

A semantic cache optimizes dollars and milliseconds; a false positive spends trust — price both.

LensAI bridge — exact anomalies meet fuzzy cache events

The z-score anomaly detector on latency_ms per model_id (sliding window 100, flag when >3σ, warm-up skip when σ=0) emits structured events into ai_anomalies and increments anomalies_detected_total. It catches statistical drift — the kind you only trust when your timers are phase-aware.

Semantic cache false positives are different: they are “fast wrong” events created by approximate nearest neighbor matches above τ. They shouldn’t disappear into Redis/vector logs; they should be represented as anomalies with the same fan-in path so on-call triages one operational stream.

Exact z-score on latency catches “slow wrong.” Semantic cache monitoring catches “fast wrong.” Both belong in the same anomalies topic, so on-call doesn’t split brain across Redis logs and Grafana P99.

Takeaway — pick your failure mode deliberately

Exact Redis when bytes are the contract; semantic caches when paraphrase is the traffic. Hybrid is the sensible default when you can make the exact path deterministic, and keep the semantic path as a bounded-risk accelerator.

Never ship semantic cache without a false-positive budget, and never treat it as “just a faster cache.” Wire false positives into the same anomalies queue as your z-score latency detection so on-call triages one stream.
