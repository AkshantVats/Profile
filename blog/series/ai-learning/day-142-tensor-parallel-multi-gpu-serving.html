Day 142 — Tensor Parallel — Multi-GPU Serving

tensor_parallel_size in chart values is today's hook, and it names something easy to mis-read as "run more copies of the model." It doesn't. It splits a single copy's weight matrices across GPUs, and every layer has to resync those GPUs before the next layer can even start.

tensor_parallel_size in chart values is today's hook, and my own PR is the one that wires it — vllm-deploy-kit/chart/values.yaml passes it straight through to vLLM's --tensor-parallel-size flag. The name invites a wrong first guess: that a higher number means more replicas of the model answering more requests. It means the opposite kind of split, and the mechanism underneath it is worth slowing down on before the value ever gets tuned.

One Mural, Four Painters, Not Four Murals

DS analogy — one mural, four painters
Four painters covering four separate walls each finish their own complete picture independently — that's four murals, and it's the shape of data parallelism: whole, independent copies working on different input. Four painters sharing one wall, each covering only a vertical strip of the same continuous image, is a different shape entirely: none of them has a complete picture on their own, and all four have to lift their brushes at the same checkpoints so the strips still line up into one mural instead of four disconnected fragments.

Tensor parallelism is the second shape. It doesn't give any one GPU a full copy of the model's weights; it splits individual weight matrices — the ones inside attention and the feed-forward layers — into column-wise or row-wise slices, one slice per GPU. Every GPU holds only its slice, computes only its slice's share of each matrix multiply, and none of them has the complete answer until the slices are combined back together.

So what: the reason tensor parallelism needs constant coordination isn't a design flaw, it's the direct consequence of no single GPU ever holding a complete weight matrix on its own — the mural analogy isn't decoration, it's the actual shape of the computation.

Where the Brushes Have to Lift at Once

That combining step is an all-reduce: every GPU's partial result for a layer gets summed across all GPUs in the tensor-parallel group, and every GPU needs the summed result before it can start the next layer's computation. This is why tensor parallelism is usually confined to GPUs on the same physical node — an all-reduce running once per layer, for every layer, needs the kind of bandwidth NVLink provides between GPUs on one node, not the kind a normal network link between separate nodes provides.

So what: pipeline parallelism (splitting whole layers across GPUs, each GPU owning a complete layer) tolerates the higher latency of a normal network link because it only hands off a full activation between stages, not a partial sum every single layer — tensor parallelism can't make that trade, which is exactly why it stays node-local.

Where tensorParallelSize Actually Touches the Chart

tensorParallelSize has one hard constraint: it must evenly divide the model's attention head count, since each GPU ends up responsible for a whole number of heads' worth of the split. My own deployment.yaml derives the pod's nvidia.com/gpu resource request directly from this same value, through one shared gpuCount helper, rather than accepting a second, independently-set GPU count that could silently disagree with it — a mismatch there wouldn't fail loudly, it would either strand a GPU unused or crash at model-load time on a shard-count the launch command can't satisfy.

So what: tensorParallelSize isn't a scaling knob in the replica sense at all, it's a single number that has to simultaneously satisfy the model's own architecture, the launch command's shard count, and the pod's resource request — three things that all have to agree because they're really one fact expressed three times.

Why the Node-Affinity Lesson From Today Matters Here Too

Today's Experience post is about a tainted node pool needing both a toleration and a node affinity, not just one. That pairing matters even more for a tensor-parallel deployment than it does for an ordinary single-GPU pod: if a tensor-parallel group's GPUs ever landed on separate nodes instead of the same one — because a pod tolerated the GPU taint but had no affinity actually pulling it toward the right pool — every layer's all-reduce would suddenly be crossing a normal network link instead of NVLink, and the pod would still start, still pass its readiness probe, and simply serve far slower than the same chart on a correctly-scheduled node.

So what: a scheduling mistake here isn't cosmetic the way an ordinary CPU pod landing on the wrong node is — it silently turns tensor parallelism's cheap, fast synchronization into an expensive, slow one, without ever producing an error the readiness probe would catch.

What I Still Don't Know

I don't know whether vLLM's launch command validates that tensorParallelSize evenly divides the attention head count itself, or whether it fails later and less clearly if the two disagree — nothing in today's chart checks this ahead of time, it only derives the GPU resource request from the same value. I also don't know whether a real GPU interconnect topology check will ever live in this chart; today's Helm values pass the number through, they don't inspect the cluster's actual NVLink topology to confirm the assumption this whole post rests on.

So what: the mechanism — why tensor parallelism needs node-local, per-layer synchronization, and why that makes it a different kind of split than replicating the model — is the part I've verified against how vLLM and Megatron-style tensor parallelism actually work; whether this specific chart will ever check its own topology assumption is an open question the code doesn't answer yet.
