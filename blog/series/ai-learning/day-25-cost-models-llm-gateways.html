Day 25 — Cost Models for LLM Gateways

Cache hit rate × cheaper model route × prompt cache — the spreadsheet that justifies the repo

AS
Akshant Sharma

11 min read

The most common mistake I see in LLM infrastructure is building the routing layer before building the cost model. Teams deploy a gateway, route 100% of traffic to gpt-4o because it’s the best model they tested, and receive the first monthly API bill with a mix of shock and regret. The cost per request is not a surprise — the prices are published. What surprises people is the volume × cost product at scale, and the realization that a 5× cheaper model would have served 80% of those requests equally well.

Build the spreadsheet before the Rust. The numbers justify the repo.

This post covers the three primary cost levers in an LLM gateway: prompt cache hit rate, model routing to cheaper variants, and prompt caching (prefix caching). Each lever is independently useful, but the maximum savings come from understanding how they compound. I’ll also cover how LensAI’s event schema is designed to measure each lever in production, because a cost model you cannot measure is a cost model you cannot optimize.

DS analogy — the taxi dispatch board
A city’s taxi dispatcher has three dials: which tier of car to send (economy vs executive), whether the passenger was a repeat caller with a known destination (faster dispatch), and whether to hold a car near a busy zone based on historical demand (cache warming). Each dial saves money independently. The dispatcher who turns all three at once and understands how they interact saves the most. An LLM gateway’s cost levers work the same way: model tier, prompt cache, and routing rules are each a dial. The cost model is the dashboard that tells you where each dial is set and how much each position is costing.

The three cost components

LLM API pricing has three line items that matter for a gateway operator: input tokens (the prompt), output tokens (the completion), and cached input tokens (input tokens served from a provider-side prompt cache). Output tokens are the most expensive — they require sequential generation from the model, one token at a time. Input tokens are cheaper per token but often dominate in volume because long system prompts and context windows dwarf the completion in many applications. Cached input tokens are dramatically cheaper: OpenAI charges roughly 10% of the normal input token price for tokens served from cache.

The cost formula for a single request is:

cost = (input_tokens - cached_tokens) * input_price
     + cached_tokens * cache_price
     + output_tokens * output_price

At scale, the dominant term depends on your application. A RAG (Retrieval-Augmented Generation) application with a large fixed system prompt, few retrieved documents, and a short user question will find that cached_tokens dominates the input. A code generation application with long context windows and long completions will find that output_tokens dominates. A structured extraction application with short outputs and no repeated prompt prefix will find that input_tokens dominates. Understanding which term dominates determines which lever to pull first.

Prompt caching: the 90% discount

Prompt caching, also called prefix caching, is a provider-side optimization that detects when an input prompt shares a common prefix with a recent request and serves the KV cache from the previous computation rather than recomputing it. The first request pays full input token price to fill the cache. Subsequent requests with the same prefix pay the cache price, which is roughly 10% of the full price on OpenAI’s API and free on Anthropic’s API for Claude models.

The cache key is the prompt prefix itself — the first N tokens of the input, where N is determined by the cache block size. For most providers, the cacheable prefix must be at least 1,024 tokens. Your system prompt, which might be 500–2,000 tokens of instructions and examples, is the primary candidate. If your system prompt is identical across all requests for a tenant, every request after the first pays only 10% of the system prompt’s token cost.

The catch is prefix order. The prompt must be structured so that the stable, long-lived content comes first and the variable content (the user’s question, the retrieved documents) comes last. A gateway that appends retrieved context between the system prompt and the user question breaks the cache key on every request, because the cacheable prefix is now “system prompt + these specific 3 documents” rather than just “system prompt.” Structuring prompts for cache hit rate is an API design decision, not a performance tuning step.

Model routing: the 5× multiplier

The second lever is routing requests to a cheaper model when the task does not require the most capable one. gpt-4o-mini costs roughly one-fifth of gpt-4o for both input and output tokens. For tasks like intent classification, entity extraction, summarization of short documents, and simple question-answering, gpt-4o-mini performs at parity with gpt-4o on most benchmarks. The cost difference per request is not 5× in favor of mini — it is 5× in favor of mini only when output quality is equivalent.

The routing decision is a quality gate, not a random split. A naive 50/50 split between gpt-4o and gpt-4o-mini reduces average cost by ~2.5× but sacrifices quality on the half of requests that needed gpt-4o. The right model for this split is distributed-flagd: the model_route flag carries a percentage weight for each model variant. Starting at 10% gpt-4o-mini and advancing the weight based on quality metrics (user satisfaction scores, downstream task performance, evaluation pass rates) is the safe path to capturing the 5× savings without degrading quality.

The flag weight is not the end of the routing logic — it is the starting point. A production router should also consider request characteristics. A request with a short system prompt, a simple instruction, and no RAG context is a strong candidate for gpt-4o-mini. A request with a long multi-document context and a complex synthesis task is a candidate for gpt-4o. Routing rules encoded as flag variants — “if prompt length < 2000 tokens, use gpt-4o-mini” — reduce cost without a quality A/B test because the selection criterion correlates with task complexity.

Building the cost model first

What I did before writing the LensAI ingestion schema was build a cost model spreadsheet. Not a fancy tool — a Google Sheet with five columns: model, input_price, output_price, cache_price, and cache_hit_rate. Then a simulation row per traffic shape: high-volume short prompts, low-volume long-context RAG, and medium-volume code generation. For each row, compute the expected monthly cost at 100k requests/day at three routing splits: 100% gpt-4o, 80/20 gpt-4o/mini, 50/50.

The spreadsheet surfaced two non-obvious insights. First, the break-even point for prompt cache investment depends on your cache hit rate. At 20% cache hit rate, the savings from caching a 1,000-token system prompt at gpt-4o prices are $0.45 per 1M requests. At 80% cache hit rate, the savings are $1.80 per 1M requests. The 80% scenario requires designing your prompt structure for cache efficiency — that design decision has a measurable dollar value before you write a line of code. Second, the combination of gpt-4o-mini routing and 80% cache hit rate produces a cost reduction of roughly 4× compared to 100% gpt-4o with no caching. The two levers compound, not add.

Measuring each lever in LensAI

A cost model is only useful if you can measure it in production. LensAI’s ingestion event schema carries four fields that map directly to the cost formula: prompt_tokens, completion_tokens, cached_tokens, and resolved_model_id. The cached_tokens field is populated from the provider’s usage response — most LLM APIs return cached token counts in the usage object alongside prompt and completion counts.

With those four fields, ClickHouse can compute the actual cost of every request: not an estimate, not a projection, but the exact dollar amount based on the per-model pricing table. The Grafana cost panel shows cost split by model variant, which is exactly what you need to evaluate whether advancing the gpt-4o-mini flag weight from 10% to 50% changes the weekly invoice. The BENCHMARKS in distributed-flagd’s flag evaluation QPS are the complementary metric: they prove that the control-plane latency of evaluating the model routing flag adds at most 0.2 ms per request, which is invisible against the 200–2000 ms of LLM API latency.

Why QPS benchmarks justify the flag system
The distributed-flagd system evaluates flags on every inference request. At 50k requests per day and 0.2 ms per flag evaluation, the flag system costs 10 CPU seconds per day — completely negligible. The cost savings from routing 80% of traffic to gpt-4o-mini at correct quality could be $2,000–$5,000 per month at moderate scale. The flag system’s QPS benchmark is the evidence that the control-plane overhead does not eat the savings from the data-plane optimization.

The third field I want to add to the schema is cache_creation_tokens — the number of input tokens that were not cached and therefore filled the cache for subsequent requests. This field lets you compute the “cache write tax”: the first requester pays full price to fill the cache that subsequent requesters draw on. For high-QPS tenants with a stable system prompt, the cache write tax is amortized across thousands of requests and is negligible. For low-QPS tenants with a changing system prompt, the cache write tax is never amortized and caching provides no benefit. Routing these tenants to a non-cached path reduces their costs and frees provider-side cache entries for higher-QPS tenants.

What the numbers actually show

I ran the cost model for LensAI’s own usage — the API calls it makes for the evaluation pipeline, not for external tenants. At current scale (roughly 5,000 evaluation requests per day), 100% gpt-4o with no caching costs approximately $18/month. Adding prompt caching with an 80% hit rate on the system prompt brings it to $9/month. Routing 70% of evaluation requests to gpt-4o-mini brings it to $3/month. The combination brings it to $1.50/month. The engineering effort to get from $18 to $1.50 is: add a system prompt prefix that never changes (1 hour), add the cached_tokens field to the ingestion schema (30 minutes), and advance the model routing flag to 70% gpt-4o-mini based on evaluation quality scores (1 hour).

The spreadsheet makes this calculation explicit before any code is written. The savings are not a post-hoc discovery — they are a pre-planned outcome. That is why I built the cost model before building the routing layer. Numbers justify the architecture; architecture without numbers is just convention.
