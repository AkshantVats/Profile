"Stratify on task_type hash." That's the entire hook line this ticket gave me. It doesn't say why a hash on request_id alone wouldn't already do the job, and working that out turned out to be the actual content of the day.

What Leakage Means for a Re-Exportable Dataset

"Train/eval leakage" usually means one example showing up in both sets at once — a duplicate that lets a model memorize its own eval question. Today's dataset already has a separate defense against that: Day 123's dedup pass runs before the split ever sees a row, so an exact or near-duplicate prompt shouldn't reach this code twice.

The leakage this split has to prevent is a different shape: the same prompt landing in different sets across two separate runs of the exact same export. Add a hundred new rows to the source and re-run the split, and if the assignment isn't a pure function of the row's own identity, some existing row can flip from eval to train or back — and a model checkpoint evaluated against one export's eval set is no longer comparable to a checkpoint evaluated against the next export's, because "eval" quietly stopped meaning the same set of prompts.

So what: the fix for exact-duplicate leakage is deduping before the split; the fix for this leakage is a split that can't forget which side a row was already on, which is a property of the assignment function, not the data.

The P.O. Box Mechanism

DS analogy — sorting mail by a fixed rule, not a daily lottery
A post office that assigns P.O. boxes by the last digit of a customer's account number always routes that customer's mail to the same box, forever — the rule is a fixed function of an identity that doesn't change. Compare that to a post office that reshuffles which box gets which route every morning: mail for the same customer can land in a different box tomorrow, not because the customer moved, but because the sorting rule itself has no memory of yesterday's assignment. split.Bucket(taskType, requestID) is the first kind of post office. Its input never changes for a given row, so its output never can either — there's no state to lose, no log to consult, no yesterday's assignment to remember. The determinism isn't stored anywhere; it falls out of the function only depending on things that don't change.

That's the entire mechanism worth naming: a pure function of stable identity is automatically leak-proof against the "same prompt, different run" failure, because there's no channel through which a re-run could learn a different answer than last time.

So what: you don't need to persist which set a row landed in to keep a split stable — you need an assignment rule that never had anywhere else to put it in the first place.

Why request_id Alone Looks Sufficient

request_id is already unique per row in this pipeline — no two rows, of any task_type, ever share one. A hash of a unique key is, on its own, already a deterministic, leak-proof assignment by the P.O.-box logic above. So why does today's code hash task_type and request_id together instead of just request_id?

Not because request_id alone is non-deterministic — it isn't. It's because "FNV hashing a unique ID produces an output uncorrelated with any other field of that row" is an assumption about the hash function's behavior, not a property this code enforces. If request_ids were ever generated in a scheme that correlates with task_type — sequential IDs issued in task-type-grouped batches, say — a hash with any structural weakness could turn that correlation into a skewed split, silently, for exactly the categories where you'd least want it to happen.

So what: folding task_type directly into the hash input doesn't fix a bug in request_id-only hashing — it removes the need to trust an assumption about the hash function at all, by making independence something the code's structure guarantees rather than something its input data happens to provide.

Measuring What "90/10" Actually Means at Small N

Determinism is provable by reading the code. Balance isn't — it has to be measured. I ran split.Split against a synthetic single-task_type stratum at six sizes to see where the 90/10 target actually starts holding.

At 12 rows the eval share is 25%, not 10% — two and a half times the target, from the exact same deterministic, correctly-implemented hash function. Nothing is broken at n=12. A decile bucketing of a dozen items was never going to land at a precise 10% cut; there just aren't enough rows for the law of large numbers to do its usual smoothing.

A mixed run against a real-shaped dataset (3,000 support rows next to 40 codegen rows) shows the same pattern at a scale closer to this pipeline's actual traffic: the large stratum lands at 10.4%, close to target; the small one lands at 7.5%, noticeably off, for no reason other than having fewer rows to average over.

A hash function being deterministic tells you the split won't drift between runs. It tells you nothing about whether the split was close to 90/10 in the first place — those are two separate guarantees, and only the notebook checks the second one.

So what: this is exactly why split_stats.json and its notebook exist as a separate deliverable from the split itself — a correct, deterministic mechanism and a balanced outcome are not the same claim, and the small-task_type case is precisely where they come apart.

The Generalizable Lesson

The specific thing today's code does is bucket training rows for a fine-tuning export. The transferable part is smaller and shows up anywhere a hash decides which side of a line something lands on.

  1. A key that's already unique doesn't automatically make a hash of it independent from every other field — that independence is an assumption about the hash function, and assumptions are cheaper to remove than to audit later.
  2. Determinism and balance are different guarantees. A hash-based split proves the first for free; the second has to be measured against the actual output, every run, not assumed from the mechanism being correct.
  3. A parameter that looks fine at the scale you tested (a 90/10 split checked against thousands of rows) can look completely different at the scale a rare category actually has — check the tail, not just the average.

Folding one more field into a hash function is a one-line change. Knowing which field, and knowing it's not enough on its own, is the actual work the ticket was asking for.
