Day 81 — Fallback Chains — Graceful Degradation in Inference

When the model you asked for doesn't answer, what tries next isn't luck — it's an ordered list, a widening clock, and a breaker that already knows which endpoints aren't worth calling.

13 min read

Schema: an ordered ModelRef list with timeout_ms on each entry. That's the entire seed of today's design — a tenant's fallback preference stored as an ordered slice, one number per hop — and everything else in this post exists to justify why that tiny schema is harder to get right than it looks.

Day 77 through 80 built model-quality-scorer and pkg/decision: a system that scores candidate models on quality, cost, and latency, and picks a winner. What none of that code answers is what happens the instant the winner doesn't answer back — a timeout, a 5xx (an HTTP status code meaning the server itself failed, not the request), or a connection that just drops. That gap is fallback-chain, RouteIQ's fifth module, and today's work is a design document, not runtime code.

The Schema: One Ordered List, Not a Primary Plus a Backup

The easy version of this feature is "try the primary, and if it fails, try some generic backup." That's the wrong shape, because a tenant's second choice is a real preference, not a detail RouteIQ should be deciding on the tenant's behalf.

type Chain struct {
    TenantID string
    Models   []ModelRef
}

type ModelRef struct {
    ModelID   string
    TimeoutMs int
}

A tenant might rank Claude Sonnet above GPT-4o for cost reasons, or rule out a vendor entirely for a data-residency requirement. Order in the Models slice encodes that preference directly: index 0 goes first, and the chain isn't exhausted until every entry has been tried or skipped.

Notice that TimeoutMs lives on the individual ModelRef, not as one constant shared by the whole chain. A request that has already waited through one failed attempt has different patience left than a request on its first attempt, which is the whole reason the next section's cascade exists.

There's also no default chain for an unconfigured tenant. Silently routing a tenant with no configured preference through someone else's implicit fallback order would quietly violate the same per-tenant scoping that Day 77's quality rubrics and Day 79's budget windows already treat as non-negotiable, so an unconfigured tenant is a gap to surface, not a case to paper over.

So what: the schema is deliberately boring — an ordered list and a number — because "second choice" needs to always mean the same specific model, never "whatever's left after the primary."

A timeout here just means "no response arrived within the allowed wait," whether the cause is a slow model, a network hiccup, or an outright error. The obvious instinct is to give every hop in the chain the same fixed budget — try for 2 seconds, try again for 2 seconds, try a third time for 2 seconds.

That instinct is wrong for a specific reason: a request that already waited 2 seconds for a primary that never answered is not well served by a second attempt capped at that same 2 seconds. The alternative to a slightly more patient second attempt is a guaranteed failure, so the budget widens instead of repeating — 2s for the primary, 5s for the second choice, 8s for the third.

2sPrimary hop
5sSecond-choice hop
8sThird-choice hop
15sWorst-case total, all three

The cascade is additive, not one 15-second deadline pre-split three ways. A chain that succeeds on the first hop costs 2 seconds or less, never the full worst-case budget up front, because the cost of a fallback attempt should scale with how many attempts actually happen.

Chain length caps at three hops in this design, matching the plan's three named tiers. A fourth configured entry is accepted by the schema, but the cascade reuses the 8-second tier for every hop past the third rather than inventing a timeout value this design never committed to.

So what: the widening budget is really a statement about patience — by the time hop two starts, the alternative to waiting a little longer isn't "waiting the short way instead," it's failing the request outright.

Three States, Not Two: Closed, Open, HalfOpen

Trying a chain in strict order only works if every entry is actually reachable. Spending 2 seconds of a request's fallback budget re-discovering that the primary has been down for the last ten minutes is 2 seconds this design has no business charging the request for — which is exactly what a circuit breaker exists to prevent: a component that tracks an endpoint's health separately from any single request, so a known-down endpoint can be skipped instead of retried.

DS analogy — the breaker panel in your basement
A household circuit breaker doesn't wait for a fire to decide a circuit is unsafe — it trips the instant it detects an overload, and once tripped, every outlet on that circuit goes dark until someone resets it. You also don't just flip it back to full power the moment you suspect the short is fixed: you reset it once, cautiously, and if it trips again immediately, you leave it off and call an electrician instead of testing your luck a second time. That's the exact shape of Closed, Open, and HalfOpen — healthy and live, tripped and skipped, and one cautious test before trusting it with real load again.

Closed is the default, healthy state: the endpoint is a normal candidate in its position in the chain, tried under its own ModelRef.TimeoutMs like any other hop. Open means three consecutive health probes have failed, so the chain executor skips this entry entirely and spends zero timeout budget on it. HalfOpen is a single cautious probe issued after a fixed cooldown — success returns the endpoint to Closed, and failure sends it straight back to Open for another full cooldown.

So what: the breaker's whole job is to make sure the 2s/5s/8s budget in the previous section is spent only on hops that have a real chance of answering, not on rediscovering the same outage on every single request.

Why Health Is Probed, Not Inferred

It would be simpler to fold a request's own timeout straight into the breaker's failure count — a hop that times out counts as one strike against that endpoint. That shortcut has a real cost: one slow response during a genuine traffic spike isn't evidence an endpoint is down, it's just one noisy sample.

Health in this design is measured out-of-band instead — a lightweight HEAD /v1/models check running on its own loop, decoupled from any tenant's live traffic. A dedicated probe means the breaker's state depends on the endpoint's actual reachability, not on whichever request happened to hit it hardest.

This mirrors a split RouteIQ has already leaned on: Day 70's prompt fingerprinter keeps its admin-configured rules on a separate write path from its fast L1 lookup read path. Measuring health and consulting it inline are two different jobs, and conflating them makes the breaker only as reliable as its noisiest recent request.

So what: a breaker that trusts live request timeouts as its only signal will flap open during ordinary load spikes — a separate probe loop is what lets "down" actually mean down.

The Proxy's Only Job: Copy Bytes Through

A fallback proxy that buffers a model's entire streamed response before forwarding it defeats the point of streaming — the client waits for the whole generation to finish either way, just with an extra hop of latency stacked on top. This design's proxy relays chunks as they arrive using chunked transfer encoding, an HTTP mechanism that lets a server send a response in pieces without knowing the total length up front.

The target is under 10 milliseconds of added latency, measured as time-to-first-byte through the proxy versus a direct call to the same winning endpoint. Almost that entire 10ms budget is spent on the decision of which hop to call — the chain lookup and the breaker check — not on anything that happens after a connection opens.

Once a hop is chosen, the proxy's job is to copy bytes through as they arrive, not to inspect, transform, or re-buffer them. Any added latency past the routing decision itself is treated as a proxy bug in this design, not a rounding error to shrug off.

So what: the moment the proxy starts doing anything to a chunk besides forwarding it, every millisecond spent doing that is latency this module exists specifically not to add.

Backpressure: The One Risk a Fast Path Creates

A proxy that forwards chunks as fast as the upstream model produces them still has to handle a client that reads slower than that. Backpressure means the point where a slow reader can't keep up with a fast writer, and the correct response is for the writer to pause, not to keep buffering in memory.

If the downstream client's read is slow, this design's proxy pauses its read from the upstream model rather than accumulating an unbounded buffer. An unbounded buffer under backpressure is a memory-exhaustion risk under exactly the traffic pattern — many concurrent slow clients — that a production proxy is most likely to actually see.

This document commits to the mechanism, not yet to a measured number: a future implementation day runs a k6 load test at 500 RPS (requests per second) with injected primary failures to find out what the real overhead is.

So what: a streaming proxy's speed is only real if it survives its slowest client, and that's a backpressure problem, not a bandwidth one.

Today's Experience Post, Same Shape

Today's companion Experience post covers Wayfair's pricing_refresh Kafka topic, where partition-key ordering guaranteed arrival order but not true recency — a retry could still let a stale price computation publish after a newer, correct one. The fix there was stamping a version at the moment computation started, not at publish time, so a consumer could always tell which update was actually newer regardless of arrival order.

Fallback-chain config has the same shape of problem waiting for it once it's live across multiple proxy replicas: if a tenant's chain gets reconfigured, every replica needs to agree on which version of that chain is current, and "whichever update arrived last" is exactly the arrival-order trap Wayfair's shadow-mode testing caught. Ordering a chain's config updates correctly is an event-sourcing problem, not a database-write problem, in the same way Wayfair's price updates turned out to be.

So what: "newer must win consistently, not just arrive last" turned out to be the same lesson at two different layers of today's work — a SKU's price at Wayfair's scale, and a tenant's fallback chain at RouteIQ's.

What's Still Design, Not Code

Nothing in this post is running yet. No runtime code, no migrations, no new Kafka topics, and no live model endpoints called in this sandbox — today's output is the Chain/ModelRef schema, the 2s/5s/8s cascade, the three breaker states, and the chunked-relay streaming strategy as committed decisions.

There's also no wiring yet into Day 80's pkg/decision output to auto-seed a chain's ordering from a routing decision — a tenant's fallback chain is configured independently for now, the same way Day 77's quality-scorer design deferred its own gateway wiring.

So what: naming the commitments before writing the code is what let this post explain the reasoning cleanly — the executor, the probe loop, and the Redis-backed unhealthy set all land on days that get to build on a design that's already been argued through once.
