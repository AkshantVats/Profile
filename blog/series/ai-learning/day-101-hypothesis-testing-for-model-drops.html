Day 101 — Hypothesis Testing for Model Drops

A drop in judge-score pass rate can be real drift or it can be noise from a small window — the two-proportion z-test is what tells them apart, and today's helper exposes the verdict directly in the drift API response.

Expose significance in drift API response. That's the entire fix this post is about, and the rest of it is explaining the test that has to run before that field can honestly say anything. Today's llm-judge-eval work (Phase 2A) implements is_significant(drop, n): a Go helper wrapping the two-proportion z-test DESIGN.md §4 already specifies, and wiring its verdict — not just the raw drop — into what DriftWatch's drift endpoint returns.

A Drop in Pass Rate Isn't Automatically Drift

DriftWatch buckets every judge score pass or fail at a threshold, then tracks what fraction of a segment's scores passed — a proportion, a value between 0 and 1 describing how often something happens out of how many chances it had to happen. A current window's pass rate sitting a few points below its baseline window's pass rate looks, on a raw dashboard number, exactly like drift.

It can also just be noise: two independently drawn samples from the exact same underlying model will differ by a few points more often than intuition expects, especially when either window is small. A raw drop with no sample-size context can't tell you which one you're looking at, and treating every drop as drift means paging someone every time chance alone produces a below-average window.

So what: "the pass rate dropped" is a fact about two numbers, and "the model is drifting" is a claim about why those numbers differ — conflating the two is exactly the gap a hypothesis test exists to close.

The Two-Proportion z-Test, in Plain Terms

A hypothesis test starts by assuming the boring explanation is true — here, that the current window and the baseline window are really the same underlying pass rate, and any gap between them is sampling noise — then asks how surprising the observed gap would be if that boring explanation held. A two-proportion z-test is the specific version of that question for two proportions measured on two different sample sizes.

It starts by pooling both windows' pass counts into one combined rate: p_pool = (x1 + x2) / (n1 + n2), where x1 and x2 are pass counts and n1 and n2 are sample sizes. It then measures how many standard deviations apart the two windows' individual pass rates are, using that pooled rate to estimate how much spread pure chance should produce: z = (p1 − p2) / sqrt(p_pool · (1 − p_pool) · (1/n1 + 1/n2)).

DS analogy — the orchard inspector's two crates
A quality inspector checking two crates of apples for bruising doesn't panic because crate B has three more bruised apples than crate A — a crate of 20 apples can easily land three bruises apart from another crate of 20 pulled off the exact same healthy tree, just by which apples happened to get picked. The inspector only flags the orchard once the gap is bigger than two crates of the same apples would normally produce, and that judgment gets sharper, not fuzzier, the more apples are actually in each crate.

So what: z isn't measuring the size of the gap in isolation, it's measuring the size of the gap relative to how much gap two identical distributions would produce by chance at that sample size — which is exactly why the same percentage-point drop can be meaningless at 40 samples and alarming at 4,000.

The 30-Sample Floor and the 1.96 Threshold

is_significant(drop, n) flags real drift only when |z| > 1.96 — the standard two-tailed 95% cutoff, not a value tuned against this pipeline's own false-positive history, because DESIGN.md §4 is explicit that there isn't real-world data yet to justify tuning it away from the default. Below that threshold, the gap is reported as ordinary variation, not drift.

Below a 30-sample floor on either window, the helper doesn't compute a z-score at all — it reports insufficient_data. A z-score computed on 8 samples is technically a number, but it's not a trustworthy one, and reporting it next to a z-score computed on 8,000 samples with no distinction between the two would let a low-traffic segment's pure noise look exactly as authoritative as a high-traffic segment's real signal.

A dropped pass rate and a statistically significant dropped pass rate are two different claims — and the gap between them is exactly the gap a sample-size floor and a z-score threshold exist to close.

So what: an alert that can't distinguish "not enough data yet" from "confirmed stable" is one bug away from staying silent on a real drop simply because a segment hasn't accumulated traffic — keeping insufficient_data as its own explicit outcome, distinct from both a significant and a non-significant result, is what prevents that silent failure.

Exposing the Verdict, Not Just the Drop

The old version of DriftWatch's drift endpoint returned a raw drop number and left the reader to guess whether it mattered. Today's change adds the is_significant(drop, n) verdict — and the insufficient_data case — directly into that same API response, so any dashboard or alert consuming it inherits the sample-size discipline instead of having to reimplement it.

That's the same shift today's companion Experience post describes from the infrastructure side: a Delivery Hero rollout that almost shipped an OSRM tuning change on a 200-order "win" needed the identical two-proportion z-test, on a different proportion, to tell a real lift from ordinary noise before calling it a result.

So what: a raw drop in pass rate and real drift are two different claims, and a two-proportion z-test with an explicit sample floor is what separates them — whether the proportion being watched is an LLM judge's pass rate across two windows, or an on-time delivery rate across two A/B groups, as today's companion Experience post covers. Exposing the significance verdict itself in the API response, not just the raw number, is what keeps that discipline from depending on every downstream consumer remembering to ask "was that enough samples" on their own.
