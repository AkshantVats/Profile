Day 35 — Silent Failures in Multi-Step Agents

Empty tool results, swallowed exceptions, max iterations — and why alerting on zero-byte tool responses is the new 500.

AS
Akshant Sharma
AI Learning · Day 35 of 150
July 25, 2026
12 min read

A timeout raises an exception. An exception shows up in your error tracker. A 500 triggers your alert. But when a tool in step 7 of a 10-step ReAct agent returns an empty string — no exception, no log line, exit code 0 — nothing fires. The agent continues to step 8 with corrupted context, produces a plausible-looking answer, and charges you for 8 LLM calls. You discover the problem when a customer emails.

This is the class of failure I call a silent failure: an operation that completes without error but produces no output. Traditional observability is blind to it. A span exists, the latency is recorded, the status is OK. But result_bytes: 0 tells the real story.

Three modes of silence

Silent failures in multi-step agents cluster into three patterns. Each looks different in code but produces the same observable symptom: the agent moves to the next step with less information than it started with.

The first is the empty tool result. The tool executes, returns a value, but the value is "", None, [], or {}. No exception is raised. The agent receives the empty value, cannot parse anything useful from it, treats it as “no data available,” and continues. The currency converter in today’s demo does exactly this on step 7: it hits a mocked rate limit, returns "", and the orchestrator logs nothing.

The second is the swallowed exception. The tool wraps its work in a broad except Exception: return None. The exception is gone. The caller receives None, which it handles the same way as “no data.” This pattern is common in wrapper functions around external APIs, where engineers add catch-all handlers to avoid crashing the caller — not realising they’ve turned every API error into invisible data loss.

The third is max iterations without finish. The agent hits its loop limit while still reasoning. It never calls finish(). It exits with whatever partial answer it had at the time. The caller receives a truncated response, and the truncation leaves no fingerprint in the standard logs.

Why they’re hard to detect classically

DS analogy — the library book
Imagine ordering a book from the library. The librarian confirms the order, marks it complete, charges your account, and hands you an empty bag. No error. The transaction succeeded. You only notice the problem when you open the bag at home.

Classical observability monitors the transaction. The order was placed, confirmed, and completed — all green. It has no concept of “but the bag should contain a book.” To detect the empty bag, you need to inspect the output, not just the operation.

HTTP APIs make this easy: a 204 is a deliberate “no content,” a 200 with empty body is suspicious, and a 500 is unmistakably wrong. Agent tool calls have none of this vocabulary. They return arbitrary Python values. There is no protocol-level concept of “this result is unexpectedly empty.”

The fix is to add that vocabulary at the instrumentation layer. Every tool call that produces an output should record result_bytes. A TraceForge span with result_bytes: 0 is the 500 that empty tool results never raise.

Instrumenting with ManualSpan

TraceForge’s wrap_openai() decorator handles LLM calls automatically. But tool calls inside the agent loop — Python functions, API clients, subprocess calls — are not LLM calls. They need manual instrumentation.

The start_span() SDK extension added in today’s commit provides this. It returns a ManualSpan that you set attributes on and call end() when the work is done. The span emits to the same ClickHouse pipeline as the automatic LLM spans, giving you a single waterfall view across both.

import traceforge

span = traceforge.start_span(
    "tool_call",
    trace_id=trace_id,
    parent_span_id=root_span_id,
)
span.set_attribute("tool_name", tool_name)
span.set_attribute("step", step_num)

observation = tool_fn(*args)

span.set_attribute("result_bytes", len(observation.encode()) if observation else 0)
span.set_attribute(
    "status",
    "EMPTY_RESPONSE" if not observation else "OK"
)
span.end()

Two attributes do the work: result_bytes quantifies the output size, and status: EMPTY_RESPONSE is the searchable label. The rest of the waterfall infrastructure — ClickHouse queries, Grafana panels, materialized views — treats this span exactly like any other.

The span exists before the alert. Before TraceForge, the span did not exist — you had LLM call spans with no tool call spans, and no way to correlate the missing Tokyo conversion with any specific step. The waterfall collapsed the mean time to diagnose from hours to under ten minutes in the demo.

The alert rule

Once result_bytes is in ClickHouse, writing the alert is a five-line SQL query. Grafana can run this every 60 seconds against a ClickHouse data source and fire a webhook when the count crosses zero.

-- Grafana alert: silent failures in the last 15 minutes
SELECT count() AS silent_count
FROM agent_spans
WHERE status = 'EMPTY_RESPONSE'
  AND start_time > now() - INTERVAL 15 MINUTE;

The alert fires on the first occurrence. There is no threshold to tune, no percentile to pick. Zero-byte tool responses are always wrong — there is no valid case where a tool should return empty and the agent should continue as if nothing happened. Alert on count > 0, not count > some-threshold.

Alert on zero-byte tool responses — they’re the new 500. A timeout raises an exception; a silent empty response looks like success.

The max-iterations case

Max iterations is easier to detect but equally easy to miss. The agent has a loop counter. When it reaches the limit, the loop exits. If you don’t instrument that exit explicitly, no span records it. The agent produced some output — whatever partial answer it had — so from the caller’s perspective, it succeeded.

The fix is a sentinel span at the loop exit. When the loop exhausts without calling finish(), emit a span with status: MAX_ITERATIONS and step: <limit>. The ClickHouse query for max-iteration traces is the same shape as the empty-response query; only the status string changes. You can count both with a single WHERE status IN ('EMPTY_RESPONSE', 'MAX_ITERATIONS') clause.

The cost dimension

Silent failures are not just correctness problems. They are billing problems. In today’s demo, the agent completes 8 LLM calls. Step 7’s tool failure does not shorten the loop — the agent cannot detect the failure, so it reasons forward to step 8 as planned. You pay for 8 calls to produce an answer that is missing the Tokyo conversion.

The trace_cost_rollup materialized view already tracks cost_usd per trace. Adding countIf(result_bytes = 0) AS empty_calls to the rollup gives you a cost-per-empty-call breakdown across all traces. A trace that spent $0.003 and had one empty call is recoverable. A batch job that ran 500 traces and had 200 empty calls charged you $1.50 for corrupted answers. The alert on the second scenario is the same SQL query with a different time window.

The three-attribute contract

Silent failure detection reduces to three span attributes that every tool call span must carry. result_bytes quantifies output. status classifies the outcome: OK, EMPTY_RESPONSE, or MAX_ITERATIONS. step locates the failure in the agent loop. Everything else — the alert, the waterfall, the cost query — is downstream of those three fields.

The investment is one start_span() call and four set_attribute() calls per tool invocation. The return is the ability to alert on a class of failure that previously produced no signal at all. That is the deal TraceForge’s ManualSpan extension is designed to make cheap.
