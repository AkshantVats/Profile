Day 98 — Judge Model Selection — Cost vs Capability

Haiku judges Sonnet. Not because the judge is the better model at answering — because grading against a fixed rubric and generating a good response are different jobs, and paying generation prices for a grading job is the cost most rubric-judge pipelines never notice they're carrying.

Config judge_model is separate from the production model on purpose. It would be simpler to reuse whatever model is already generating responses to also grade them — one model, one config value, one thing to reason about. DESIGN.md rejects that simplicity for a reason worth sitting with: judging isn't the same job as answering, even when the same underlying technology could technically do both.

Grading Is Classification, Not Generation

Generating a good support response is open-ended: the model has to compose language, reason about policy, and produce something novel that fits the specific situation in front of it. Grading that same response against llm-judge-eval's rubric is a much narrower task — given five weighted criteria and a response, output a score for each one, consistently, every time.

That's structured classification wearing a chat-shaped interface. model-quality-scorer (RouteIQ, Day 77) already established this reasoning for its own grading pipeline, and DriftWatch's judge model reuses it rather than re-deriving it from scratch: the cheapest model that scores consistently against a fixed rubric beats a larger model scored inconsistently, because consistency is what a drift comparison actually depends on.

DS analogy — the health inspector and the chef
A restaurant health inspector doesn't need to be a better cook than the chef whose kitchen they're checking. Their job is narrower and different: walk a fixed checklist — food storage temperature, handwashing, expiration dates — and mark each item pass or fail, the same way on a good day and a bad one. A world-class chef inspecting their own kitchen isn't obviously better at that checklist; they're just more expensive per hour for a job that was never about cooking skill in the first place.

So what: the inspector's value is a consistent checklist applied the same way every time, not culinary talent — and a judge model's value is the same thing, applied to a rubric instead of a kitchen.

The Economic Hierarchy This Creates

Once grading is understood as classification, a natural hierarchy falls out: an expensive, high-capability model generates the response, because generation is the hard, open-ended part. A cheap, fast model grades it, because grading against a fixed rubric doesn't need that same capability. Haiku judging Sonnet isn't a downgrade in the pipeline's quality bar — it's routing each half of the job to the tier of model actually built for it.

Two separate config values, prod_model and judge_model, is what makes that routing an explicit decision instead of an accident. Collapsing them into one model would silently overpay for grading on every single response — a cost that compounds the moment sampling volume grows, and one that a shared-model config would make invisible until the bill arrived.

Why the Cap Is Hard, Not a Degrade Path

DESIGN.md's $50/day/task_type cap is a hard stop, not a fallback to an even cheaper model once spend crosses the line. That choice only makes sense once judging is framed as classification: swapping to a cheaper judge mid-window would change what "consistent scoring" means partway through a comparison window, the same failure mode a breaking rubric edit causes if it doesn't bump RubricID.

A capped task_type simply stops collecting new samples for the rest of the day instead. Losing coverage for a few hours is a recoverable gap; comparing scores computed under two different judge models inside the same baseline window is a silent, unrecoverable one.

A judge model's job was never to be as good as the model it's grading. It was to be exactly as consistent, every time, for the smallest bill that guarantees it.

Today's Code Makes the Rubric Half Real

Phase 2A's llm-judge-eval rubric CRUD API doesn't touch the judge model itself yet — no Haiku call happens in this PR. What it does build is the other half the config-separation argument depends on: a JudgeRubric the judge model will eventually grade against, with Validate enforcing that its five criteria weights sum to 1.0 before any grading call could ever run on it.

store.Create's refusal to overwrite an existing rubric version matters here for exactly the reason a shared judge_model/prod_model config would have mattered wrong: once a cheap judge model starts scoring against a rubric, that rubric's meaning has to stay fixed for the comparison to mean anything, the same way the judge model itself has to stay fixed within a window.

So what: separating judge_model from prod_model and versioning the rubric they grade against are the same underlying discipline applied twice — once to which model is allowed to change what "consistent" means, and once to which config values are allowed to change what "good" means, on purpose and only on purpose.
