Today's load_test module replays one batch of prompts against a fine-tuned vLLM endpoint and a GPT-4o baseline, then writes a CSV a stakeholder chart can read directly: cost, latency, and a quality proxy score, one row per endpoint. The interesting part isn't the harness itself — it's the shape the resulting data takes once you plot cost, latency, and quality against each other. That shape has a name in distributed systems and optimization theory: a Pareto frontier.

The Restaurant You'd Actually Pick

DS analogy — the restaurant that gets filtered out
Open a food-delivery app filtered by price, distance, and rating, and most restaurants disappear immediately — not because they're bad, but because some other restaurant beats them on all three axes at once, and nobody picks a strictly worse option on purpose. The restaurants left after that filtering are the interesting set: each one wins on at least one axis against every other survivor, so choosing between them is a real tradeoff, not a mistake waiting to be corrected. That surviving set, where no option is beaten on every axis at once, is the everyday version of a Pareto frontier.

A point is Pareto-dominated when another point matches or beats it on every axis and beats it on at least one — a restaurant that's pricier, farther, and worse-rated than another gets dropped instantly, the same way a model config that's slower, costlier, and lower-quality than another would be. So what: "frontier" describes the set an executive should actually be choosing between, not every option that technically exists.

Two Points Aren't a Frontier Yet

Today's harness produces exactly two data points — the fine-tuned endpoint and the GPT-4o baseline — not the many-point curve a real frontier implies. A proper frontier needs enough configurations plotted (different quantization levels, batch sizes, model sizes) that the non-dominated survivors actually trace a curve, the same way one restaurant doesn't tell you much about a whole city's price/distance/rating landscape.

What the cost column actually measures, checked against the code
load_test.tokens.approx_token_count is a whitespace-split word count, not a real BPE tokenizer call — the module's own docstring states it lands within roughly 25-35% of a real token count for English prose, close enough for a synthetic harness whose completions are already fabricated text, not close enough to bill a real account against. The cost column in today's CSV inherits that same margin, since cost here is token count times a configured dollar-per-token rate.

So what: two points with an honestly-labeled proxy on one axis is a real starting seed for a frontier, but calling today's chart "the frontier" would overstate both the point count and the cost column's precision at once.

Why Quality Can't Just Be a Tiebreaker

Cost and latency are both cheap to measure precisely — a clock and a token count get you most of the way there. Quality is the axis most likely to lean on a proxy: an automated judge, often another model, standing in for a human reviewer's opinion because no human reads every request in a load test. That proxy inherits whatever blind spots the judge model itself has, the same concern this series raised when picking a judge model back on Day 98.

Treating quality as a simple tiebreaker — "use it only if cost and latency tie" — understates how much weight it actually carries, since a cheap, fast endpoint that quietly produces worse answers isn't a win, it's a different kind of cost pushed downstream to whoever reads the output.

So what: a Pareto frontier only tells the truth if every axis on it is measured with comparable honesty, and today's harness is explicit that one of its three axes is a rougher proxy than the other two.

What I Still Don't Know

I don't know how many more configurations it would take before two points become a real frontier curve worth trusting, versus staying a comparison between exactly one alternative and one baseline. I also don't know whether the 25-35% token-count margin matters at the scale a single comparison needs, or whether it only becomes a problem once someone tries to rank many close configurations against each other.

So what: the mechanism I'm confident in is the shape — non-dominated points across cost, latency, and quality are the ones worth a stakeholder's attention — while how precisely today's two points sit on that shape is a narrower, still-open question.
