Replay JSON defines expected alert latency. That's the whole idea in one sentence: a chaos drill's real output was never just a yes/no on whether the alarm fired — it's a number, how long, and that number is the difference between "we built a detector" and "we know what our detector actually buys us."

Why Infra Chaos Drills Don't Translate Directly

Kill a Kafka broker and the signal is unambiguous: up, then down, at a timestamp you chose yourself. Replaying that as a test fixture is almost trivial — record the instant, assert the alert fired within some window of it.

A model quality regression offers none of that. judge_score — an automated quality rating an LLM-as-judge assigns to a model's output — drifts gradually and noisily across many hours, and "the incident" is a shape, a sustained shift in the mean, not a single event with a clean start time.

So what: a broker drill's fixture is a light switch; an ML quality fixture has to capture a shape instead, which is a genuinely different, harder engineering problem than it first looks.

What a Replayable ML Incident Fixture Has to Capture

Not a kill switch — a captured or realistically modeled time series. Today's fixture format needs a baseline window's worth of scores, enough to compute a mean and standard deviation against, plus an hourly sequence of scores spanning the modeled incident itself.

It also has to encode ground truth, the same way a broker drill's ground truth is simply "the broker is down now": which side should alarm, and within how many windows counts as success. Without that, replaying the fixture produces a number with nothing to check it against.

So what: a broker drill only needs to record one instant; an ML incident fixture has to record an entire baseline, an entire incident window, and the answer key for both — three things, not one.

The Mechanism: Running the Real Evaluation Path

A CUSUM chart — the statistic pkg/cusum has run since Day 105 — accumulates z-scored evidence window over window instead of judging each window in isolation, which is what lets it catch a shift too small for any single window to trip a simple threshold.

Replaying a fixture means running that identical accumulation logic against captured data instead of a live ClickHouse query, through two new adapters — fixtureBaselineReader and fixtureHourlyReader — that implement the exact same baseline.Reader/trend.Reader interfaces the live path already used. The evaluation function, EvaluateRange, never knows or cares whether its input came from ClickHouse or a JSON file on disk.

So what: the replay is only as trustworthy as its distance from the real evaluation path, and here that distance is exactly zero — a fixture that ran through a simplified re-implementation instead would be a rehearsal of the wrong thing.

DS analogy — a flight recorder replay, not a flight simulator
A chaos replay fixture is a flight recorder's black-box replay, not a flight simulator. A simulator generates plausible-looking data from a model of how a plane behaves, and testing against it only proves the system handles the model's idea of a failure. A black-box replay instead feeds a system the actual recorded sequence of a real, or realistically reconstructed, event and checks what the system does with it — the detector under replay never knows the difference between that tape and a live feed, which is exactly what makes its verdict trustworthy.

So what: the fixture here is the black-box tape, not a simulation of one, and that distinction is the entire reason a passing replay means something.

The Concrete Result: Three Verdicts, One Fixture

The fixture models a sustained 15% judge_score drop — a baseline mean of 80 falling to 68 and staying there. Replaying it once per sensitivity preset produced three genuinely different, measured latencies, not an abstract precision/recall argument.

6hstrict windows to alert
8hbalanced windows to alert
14hnoisy windows to alert
15%injected score drop

So what: this isn't a hypothetical tradeoff argued from first principles — it's the same shift, the same fixture, replayed three times, producing three re-runnable numbers instead of three guesses.

The Honest Limitation

Today's replay proves exactly one thing: the detector catches a shift it should catch, and how fast, per preset. It says nothing about false positives — whether any of these presets would also alarm on a quiet, ordinary day with no real incident hiding in it.

That requires a second fixture, one that captures ordinary noise and asserts nothing should fire, and it doesn't exist yet. Say this plainly rather than let the passing test imply more than it proved: one rehearsal proves one thing, and this rehearsal proved only the true-positive side.

The Experience Bridge

Today's Experience post reaches this identical idea from the operations side, a step ahead of where this post lands on it: a rehearsal — whether a human-run broker-failure drill or an automated replay of a JSON fixture — only earns trust for the specific failure shape it tested.

The chart's math didn't change today. What changed is that "it should catch this" became "it caught this, in six hours" — a measured claim instead of an assumed one.

So what: two systems, two vocabularies, the identical discipline — a broker-failure drill and a chaos-replayed judge-score fixture both trade an assumption for a measurement, and neither one gets to claim more than the specific shape it actually rehearsed.
