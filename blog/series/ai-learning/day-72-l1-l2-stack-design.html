Day 72 — L1/L2 Stack Design

A CPU's L1/L2/L3 hierarchy never reports one blended cache-hit number, because each level costs a materially different multiple of the level before it. A prompt cache backed by Redis then pgvector needs the identical discipline — and the identical decision about when a slow hit gets promoted into the fast tier.

A single hit/miss counter is a fine question for a one-tier cache and a misleading one for a two-tier cache.

Today's code gives prompt-fingerprinter's stack three outcomes instead of two: l1_hit when a Redis GET resolves the request, l2_hit when it falls through to semantic-cache-engine's embedding search, miss when neither does. Collapsing those into one "cache hit: yes/no" number would still be technically true and would still hide the one thing worth knowing.

What a Blended Rate Can't Tell You

Picture a 92% hit rate on a two-tier cache. That number alone can't distinguish two very different systems: one where almost every hit resolves at the fast tier, and one where the fast tier barely helps and most hits are quietly paying the slow tier's cost every time.

Both report 92%. Only one of them is healthy.

So what: the moment a cache has more than one place an answer can come from, "did it hit" stops being the question that matters — "which level answered it" is what actually tells you where your latency budget is going.

The CPU Already Solved This

DS analogy — how a CPU profiler reports its own cache hierarchy
A CPU's L1/L2/L3 cache hierarchy never reports a single blended hit rate, for exactly this reason: L1 answers in a few cycles, an L2 hit costs several times that, and a full miss to main memory costs an order of magnitude more again. A profiler that only said "cache hit: 95%" would be useless for deciding whether to grow L1, grow L2, or accept the miss rate — so every real CPU profiler reports hits per level, not one collapsed number. prompt-fingerprinter's l1_hit/l2_hit/miss is the identical accounting scheme, borrowed by name, applied to a prompt cache instead of a memory hierarchy.

The parallel holds past the naming. A CPU's L1 is fast because it's small and physically close to the core, while L2 is slower and bigger, and main memory is slower still and effectively unbounded. Redis L1 is fast because a fingerprint lookup is one key-value round trip, while L2 is slower because it pays an embedding-model call before a similarity search can even run.

Different substrates, same shape: each level trades capacity and generality for speed, and the whole point of measuring per-level is deciding whether that trade is paying off.

So what: "L1/L2" isn't a naming convenience borrowed from hardware for flavor — it's an admission that a software cache hierarchy has the same cost-per-level shape a memory hierarchy does, and deserves the same per-level accounting.

The Part CPUs Don't Do: Backfill

Here the analogy runs out. A CPU's L2 doesn't get permanently rewritten just because L1 missed and L2 answered — cache lines get evicted and refilled constantly, by hardware policy, at nanosecond timescales, with no notion of "this response now belongs one level up forever." prompt-fingerprinter's stack does something a hardware cache never needs to: when L2 resolves a request, the response gets written back into Redis at that exact fingerprint key.

The next byte-identical repeat of that same prompt then resolves as an l1_hit instead of paying the embedding cost again. That's a real design decision, not free structure borrowed from the hardware metaphor — a software cache gets to decide whether a slow hit is worth promoting, in a way silicon's fixed replacement policies were never built to ask.

So what: borrowing the L1/L2 accounting scheme doesn't mean borrowing the whole cache-eviction story — a software stack that can choose to promote a slow hit has a policy question a fixed hardware hierarchy never has to answer.

Fail-Open: A Degraded Fast Tier, Not a Dead Request

One more decision this design had to make explicit: what happens when the Redis GET itself errors, not merely misses. The stack treats a connection failure the same as a miss — fall through to L2 — rather than failing the request outright. A prompt that would have been an l1_hit during a Redis outage still gets an answer; it just costs what an l2_hit always costs.

A cache hierarchy's fast tier failing shouldn't mean the request fails — it should mean the request pays what the slow tier always costs, and the accounting should say so honestly.

So what: fail-open turns a Redis outage into a latency regression instead of an outage of its own — the system degrades to its own slower, still-correct path rather than falling over entirely.

What This Doesn't Prove Yet

No live Redis or Postgres instance runs in this sandbox — no Docker daemon, the same constraint every prior day touching either dependency has logged. The backfill policy's actual effect on steady-state hit rate is a documented design property here, tested against in-memory fakes, not yet a number measured against real traffic.

So what: the three-way accounting and the backfill policy are both correct by construction against the interfaces this stack depends on — whether they shift the real hit-rate mix the way the CPU analogy predicts is a claim for a future day with a live instance to check against.
