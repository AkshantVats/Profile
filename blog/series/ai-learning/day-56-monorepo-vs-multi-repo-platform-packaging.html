Day 56 — Monorepo vs Multi-Repo — Platform Packaging

Compose files as integration contract. Buyers install compose, not git clone four times — and agent-benchmark-runner needed its first CLI before docker-compose.yml had anything real to point a container at.

Buyers install compose, not git clone four times.

A platform made of several independently-evolving components has to answer one packaging question before it has any users: does installing it mean cloning one thing, or several? Get that answer wrong and every user pays the integration cost the platform should have paid once, upfront.

The Packaging Question Every Platform Answers

DS analogy — a shipping container vs. a pallet of loose boxes
Loose boxes each survive the trip fine on their own — nothing about any single box proves the others will stack with it at the destination. A shipping container is what makes "arrives as one load" a property of the shipment instead of a hope. Four separate repos are the loose boxes; a compose file that boots all four together is the container.

Four separate repos — agent-replay-engine, agent-benchmark-runner, tool-call-analyzer, traceforge — each with an independent go.mod, independent CI, independent release cadence is the more "correct" separation on paper: each component versions on its own schedule, and a consumer who wants only one doesn't pay for the other three. But it pushes the integration cost onto every single user — four clones, four READMEs to reconcile by hand, and no single artifact proving the four pieces actually work together, only four sets of docs each asserting they should.

So what: "each component is independently correct" and "the four components work together" are different claims, and only one of them is what a user installing a platform actually needs proven.

The Monorepo Only Solved Half of It

Day 44 already answered the "one clone or four" question for source code, when agent-replay-engine landed inside infra-ai-streaming instead of as its own repo. Day 56's actual decision sits one level up: given one monorepo, does docker-compose.yml become the integration contract, or does each component ship its own Dockerfile and leave composition as an exercise for the reader?

A Dockerfile per component proves that component builds in isolation. It proves nothing about whether agent-benchmark-runner's container can actually reach the traceforge collector it's meant to benchmark against, or whether Redpanda's topic names match what tool-call-analyzer expects. One root compose file that wires all four together — with the CLI-only components under a tools profile so they don't block docker compose up waiting on an invocation — is the thing a user can run and watch fail or pass as a single system, not four separate claims.

So what: a per-component Dockerfile answers "does this build"; a shared compose file is the only artifact that answers "does this work," and platforms live or die on the second question.

The Decision Forced a Real Feature

0cmd/ entrypoints through Day 55
1CLI added to make it containerizable
4components unified in one compose file

The honest engineering cost, not just a rhetorical one: agent-benchmark-runner had zero cmd/ entrypoint through Day 55 — a library only, exercised entirely through go test. Today's pkg/subprocess and cmd/traceforge exist because the compose file needed something runnable to point a benchmark: service at. A packaging decision is not free of implementation debt: choosing "compose file as integration contract" forced a real feature — a CLI, and the process-group-kill fix that came with wrapping a shell command safely under a timeout — that a docs-only, four-separate-repos world would never have surfaced.

So what: a packaging decision that looks like pure plumbing can quietly demand real product work upstream of it — the compose file didn't just wrap an existing CLI, it's the reason the CLI exists at all.

The Honest Gap

No Docker daemon was available in the environment this was built in, so the integration claim above is validated by docker compose config — the file parses, its structure is well-formed, its four Dockerfile references exist — not yet by docker compose up actually building and running all four together. The packaging decision is made and the code exists to back it; whether it boots cleanly on a real Docker host is the next thing to prove, not something this post can claim it already has.

So what: a design decision and its verification are two different milestones — writing the compose file down is the design; someone (or some CI job) actually running it is the verification, and conflating the two is how "should work" quietly becomes the claim instead of "works."
