Day 22 — Feature Flags for Model Rollouts

Canary models with audit trails — deterministic session assignment, evaluation_count_snapshot, and resolved_model_id

AS
Akshant Sharma
June 9, 2026
14 min read
AI Learning · Day 22 of 150

A model rollout without an audit log is a production incident waiting for a postmortem. Three weeks into building this system, I merged a model version bump on a Friday afternoon the same way I’d merge any dependency upgrade — bump the version string, ship it, watch metrics. By Monday morning I had a cost spike I couldn’t explain because I had no record of which requests had hit the new model, at what percentage, and when the weight changed. The audit trail wasn’t a nice-to-have. It was the only thing that would have let me answer the question “did the new model cause this?”

This post walks through the mechanics: a percentage rollout flag backed by FNV-1a hashing for deterministic session assignment, an audit log that snapshots evaluation counts at every weight change, and a resolved_model_id field written on every inference event so ClickHouse can tell me the exact cost diff between flag versions. By the end, every dollar of inference cost is traceable back to a flag state.

The core frame: feature flags for models are a rollout instrument, not a configuration switch. A configuration switch takes effect immediately and is reversible with a revert. A rollout instrument has state — it records who got what, when, and at what cost.

DS analogy — load balancer with health checks
Feature flags for model versions are like traffic routing at a load balancer — except the “server” is a model version and the health metric is quality score, not latency. You don’t switch all traffic to the new model at once; you canary it. The flag is the routing rule. The audit log is the health-check history.

Why code deploys and model rollouts are different

A code deploy is stateless with respect to users. If I roll back a service, the next request hits the old binary and the user gets a valid response. A model rollout is not stateless for multi-turn conversations. If a user is three turns into a conversation started under model v2 and I swap them to v3 mid-session, the new model receives a context window it was never calibrated on. The quality regression isn’t in any single response — it’s in the coherence of the turn sequence. I hit this wall when I tried a simple percentage flag without a stickiness constraint and got complaint reports that conversations felt “forgetful.”

A latency regression in a code deploy shows up in P99 within minutes. A quality regression in a model shows up in downstream metrics — user satisfaction scores, re-query rates, escalation rates — with lag measured in hours. You can’t use the same rollout velocity for models that you use for code. The observation window has to be longer.

Cost is a step function, not a gradient. When you swap from GPT-3.5 to GPT-4, every request that hits the new model costs at the new tier’s rate. At 5% rollout on a high-traffic system, that’s a meaningful absolute cost increase even if the percentage sounds small. Without an audit log, you can’t separate “the new model is expensive” from “we routed more traffic to it than we intended.”

What I didn’t expect
The hardest part wasn’t the flag mechanics — it was defining what “ready to advance to the next percentage” actually meant. For code, it’s “error rate below threshold after N minutes.” For models, I had to instrument a quality proxy metric before I could even write the advance condition. The advance condition is a product decision, not an engineering one.

The percentage rollout flag: mechanics and semantics

The flag lives in a configuration that flagd — a self-hosted feature flag control plane — evaluates at request time. The relevant fields are the variant names (e.g., model-v1 and model-v2), the defaultVariant, and a fractional evaluation rule that maps a hash of the targeting key to a bucket. The percentage is not a probability — it’s a deterministic bucket assignment. If 20% of hash space maps to model-v2, then exactly 20% of distinct targeting keys will consistently resolve to model-v2.

The targeting key is what you hash, and this choice is a product decision disguised as a configuration detail. If you hash request_id, you get request-level randomization with no stickiness. If you hash session_id, you get session-level stickiness — the same session always hits the same model. If you hash user_id, you get user-level stickiness across sessions. For multi-turn chat, session_id is the right key.

When I change the flag weight from 20% to 50%, the change takes effect on the next evaluation for every new session. Existing sessions that were sticky to model-v1 stay on model-v1 for the duration of that session. Weight changes are not instantaneous across the fleet — the rollout advances as new sessions start. This is correct behavior for model rollouts; it would be a bug for feature flags where you want immediate rollback.

DS analogy — paint mixing formula
Think of a paint mixing machine at a hardware store. When you dial in a color formula, the machine dispenses precise fractions of each pigment by weight, not by probability. The result is deterministic — the same formula always produces the same color. The percentage rollout is the formula. The hash is the dispensing mechanism. You’re not rolling dice; you’re following a recipe.

Deterministic hashing for session consistency

FNV-1a (Fowler–Noll–Vo) is a non-cryptographic hash function that produces a 32-bit or 64-bit output from an arbitrary byte input. It is fast (single-pass, no state accumulation), has good avalanche properties (a 1-bit input change produces roughly 50% output bit changes), and produces a reasonably uniform distribution. For bucket assignment, you take the hash output modulo 10,000 to get a bucket number between 0 and 9,999, then compare it against the cumulative weight thresholds.

Given the same session_id string and the same flag weight configuration, FNV-1a always produces the same bucket number. This is the sticky assignment guarantee. It means that once a session is assigned to model-v2, every subsequent evaluation of the flag for that session will resolve to model-v2 — not because there’s a database entry recording the assignment, but because the hash is deterministic. The consistency is implicit in the session ID and the current weight configuration.

The subtle edge case: if the flag weight changes from 20% to 50% while a session is active, a session whose bucket number was in the v1 range at 20% might flip to v2 at 50% — because its bucket is now within the enlarged v2 range. Weight changes can re-assign active sessions. The fix is to snapshot the assignment at session creation or enforce a policy that weight changes only take effect for new sessions.

DS analogy — postal sorting rules
Think of a postal sorting office that routes packages by zip code. Zip code 10001 always goes to the Manhattan facility — deterministic. But if the routing rules change mid-day, packages already in transit don’t get re-routed. They follow the rule in effect when they entered the system. Session stickiness works the same way: the assignment rule at session creation is the one that counts.

The audit log: cost attribution, not just change tracking

Every flag weight change writes an audit entry with six fields: flag_key, changed_at (ISO 8601 with timezone), changed_by, old_weight, new_weight, and evaluation_count_snapshot. That last field — the snapshot of how many evaluations had accumulated at the moment of the change — is what transforms the audit log from a change record into a cost attribution instrument.

The evaluation_count_snapshot field works like a utility meter reading. The meter records cumulative kilowatt-hours at each billing period boundary. The difference between two readings gives you consumption for that period. Two consecutive audit entries give you the evaluation count for a specific flag weight — exactly how many requests experienced the old configuration before you changed it. Multiply by the model’s cost per token and you have the cost attributable to that flag state.

The reason field is not optional. It forces the actor making the change to record why: “Advancing canary to 50% — quality score 0.87 over 24h” is a reason. “bump” is not. Three weeks in, a cost anomaly appeared on a Tuesday at 2:14 AM. The audit log showed an automated canary advance triggered by a quality score threshold crossing. Without the audit log, I would have filed an incident. With it, I closed the investigation in four minutes.

resolved_model_id: closing the loop to ClickHouse

resolved_model_id is a field written on every inference event by the flagd sidecar at evaluation time. When a request comes in, the sidecar evaluates the flag, resolves to a model variant, and writes the exact model ID — not the variant name, but the fully qualified model identifier like gpt-4-turbo-2024-04-09 — into the inference event before it hits the router. This field is carried through the entire request lifecycle: inference event → Kafka topic → ClickHouse inference_events table.

The variant name is model-v2. The fully qualified model ID is gpt-4-turbo-2024-04-09. These are not interchangeable. If you log the variant name, your ClickHouse query can tell you how many requests hit the model-v2 variant. But it can’t tell you the per-token cost, because different model versions under the same variant name might have different pricing. The fully qualified model ID is what you join against the pricing table.

With resolved_model_id in the table, the cost attribution query is a join against the pricing table grouped by model version. Add a join against the flag_audit table on timestamp ranges and you have cost by flag state. The loop closes: flagd policy → evaluation → inference event → Kafka → ClickHouse → cost report → flag change decision → flagd policy.

DS analogy — supplier lot number
Think of a warehouse inventory system that records the exact supplier lot number on every outgoing package. If a product recall happens, the lot number is what lets you trace which customers received affected stock — not the product name, not the SKU, but the specific manufacturing batch. resolved_model_id is the lot number for inference requests. It’s the traceability field that makes every other analysis possible.

What a real canary rollout looks like

The 5% step is not statistically significant. You are not trying to measure quality at 5% — you are trying to catch catastrophic failures: model API errors, timeout rates, malformed response formats, and cost anomalies. The observation window is one to two hours. The advance condition is error rate on model-v2 requests below 0.5%, P99 latency within 20% of the model-v1 baseline, no cost anomaly triggered.

At 20%, you have enough volume for a preliminary quality signal. This is where you start reading the quality proxy metric. The observation window is four to eight hours or 10,000 requests, whichever comes first. The advance condition adds: quality score for model-v2 requests at least equal to model-v1 within a ±3% tolerance band.

At 50%, you have a true A/B split. Every metric — quality, cost, latency, error rate — is now comparable with statistical significance. The observation window is 12 to 24 hours. The advance condition includes a cost delta acceptance: this is a business decision, not a technical one. At 100%, the observation window continues for 24 to 48 hours post-full-rollout before the flag is retired and the audit log entry is retained permanently.

What I didn’t expect
The hardest step was the 50% cost-delta acceptance at Step 3. “Cost delta understood and accepted” requires a product or finance decision, not an engineering one. The canary process forced me to build a handoff point into the workflow — a meeting, not a threshold — that I hadn’t anticipated. The technical conditions automate; the cost acceptance does not.
