Day 94 — Latency SLO Verification — A/B Instrumentation

k6 scenario tags shadow on/off runs. Proving a component adds zero latency isn't a matter of measuring it once — it's a matter of measuring it twice, against a twin that differs in exactly one thing.

k6 scenario tags shadow on/off runs. That's the instrumentation today's ticket asked for: two runs of the same load profile against routeiq-proxy, one with shadow-traffic-router's mirroring middleware wired in, one without, tagged so their http_req_duration histograms can sit side by side afterward.

It sounds like a smaller ask than it is. "Measure the latency with shadow mirroring on" is one number. "Prove shadow mirroring adds zero latency" is a claim about the difference between two numbers — and a difference is only meaningful if everything else that could have produced it stayed fixed.

A Harder Claim Than "On Has a P99"

A single p99 number is easy to get and easy to misuse. Run the proxy with mirroring on, measure, get a number. Run it again next week with mirroring off, measure, get a second number.

If the second number is lower, did mirroring cost you the difference? Not necessarily. Traffic mix might have shifted between the two runs.

The host might have been under different load from something unrelated. Cold caches on the first run, warm on the second. Any of those differences alone is enough to produce a gap that has nothing to do with mirroring at all.

DS analogy — two stopwatches, one backpack
Two identical runners start at the same signal, on the same track, in the same weather. One carries a light backpack, the other doesn't. If the backpack runner finishes half a second slower, you can credit that half-second to the backpack — because it's the only thing that differed between them. Swap the track, the weather, or the starting signal between the two runs instead, and a half-second gap stops meaning anything about the backpack at all; it just means the runs weren't comparable.

So what: a latency claim about one component's overhead is really a claim about two runs' comparability first, and a number second — get the comparability wrong and the number is just noise wearing a decimal point.

What Has to Stay Identical, Not Just "Similar"

TestShadowMirroring_AddsNoMeasurableLatency (fallback-chain/cmd/routeiq-proxy/latency_shadow_test.go) keeps every variable fixed except one. Both runs use the same httptest.Server loopback, the same instant-responding stub backend, the same 1,000-iteration count, the same tenant. The only thing that changes between the "shadow off" run and the "shadow on" run is whether mirrorShadowTraffic sits in the handler chain at all.

That single-variable discipline is what makes the resulting p99 delta — 0.018ms — attributable to the mirroring middleware specifically, rather than to noise from a dozen other things that could have differed between two less careful runs.

Nothing about that diagram is specific to Go, k6, or HTTP proxies. It's the shape of every valid A/B latency comparison: one generator, two configurations, one load shape shared between them, and a diff computed only after both sides have been measured the same way.

So what: the load-generation harness is not the part of an A/B latency test worth the least attention — it's the part that decides whether the diff at the end is measuring the thing you think it is.

A number from a run where five things could have changed isn't evidence about any one of them. A number from a run where exactly one thing changed is evidence about that one thing, and nothing else.

The k6 Gap, and What Actually Fills It Today

The ticket's original ask was a k6 run at 1,000 requests per second, shadow on and shadow off, comparing http_req_duration p99 across the two. shadow-traffic-router/load-test/k6-script.js now exists and commits to exactly that scenario — a SHADOW_MIRROR=on|off environment switch routes to differently-configured tenants at a constant-arrival-rate of 1,000/sec.

This sandbox still has no k6 binary to run it with, the same standing gap this repo's other k6 scripts already log rather than pretend around. Skipping the measurement entirely wasn't the alternative to that gap — reproducing the same shape of comparison at a layer that does run here was.

An httptest.Server loopback isn't 1,000 real concurrent TCP connections arriving at a constant rate the way k6's executor would generate them. What it does preserve is the part of the methodology that actually proves the claim: two configurations, one load shape, one variable. A future k6 run, once a binary exists, adds concurrency and network realism to the measurement — it doesn't change what the measurement is trying to establish.

So what: when the exact tool a ticket names isn't available, the fallback worth building is one that keeps the comparison's logic intact — not one that keeps the tool's name and drops the discipline that made its result meaningful in the first place.
