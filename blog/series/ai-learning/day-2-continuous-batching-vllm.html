Day 2 of Learning LLM Inference — Continuous Batching in vLLM: The Scheduler Design That Keeps GPUs Busy

2 of N — AI Learning Series. From GPU bubbles and static batching to token-step scheduling, OS parallels, and what continuous batching means for observability.

AI Learning · Day 2 of N

One request generates 20 tokens.

Another generates 2,000.

If both are placed into the same static GPU batch, the short request finishes quickly — and then sits idle in VRAM while the long request continues decoding for seconds.

That idle time is called a GPU bubble.

And once you notice it, you realize early LLM serving systems were wasting enormous amounts of GPU capacity simply because the scheduler operated at the wrong granularity.

Continuous batching fixes this by changing one thing:

The scheduler stops thinking in requests.
It starts thinking in tokens.

The more I read about vLLM, the more I realized I was not reading about machine learning infrastructure. I was reading about a scheduling problem I had seen before — in Kafka consumers, OS schedulers, RPC multiplexers, and stream processing systems.

LLM inference serving is a systems engineering problem wearing an ML costume.

And continuous batching is where that becomes impossible to ignore.

The Real Problem: Decode Phase Variance

Before batching exists at all, imagine a naive inference server.

A request arrives.
The model runs prefill.
Then decode.
Then returns the response.
Then starts the next request.

Sequential execution.

The GPU sits partially idle between requests, throughput collapses under load, and latency grows linearly with concurrency.

So every serving system batches requests.

The first instinct — and the approach most early serving systems used — is static batching.

Collect N requests.
Run them together.
Wait for all requests in the batch to finish.
Then start the next batch.

This works well for image classification because every input produces one output.

It breaks badly for autoregressive text generation because output lengths vary enormously.

One request may generate:

  • 10 tokens
  • 50 tokens
  • 500 tokens
  • 2,000 tokens

And the batch cannot complete until the longest sequence finishes.

Static Batching Creates GPU Bubbles

Requests A and C finish quickly.

But their GPU slots remain occupied while Request B continues decoding.

Those idle periods are GPU bubbles:

  • VRAM allocated
  • scheduler slot occupied
  • almost no useful compute happening

At scale, these bubbles become catastrophic for utilization.

A GPU with 32 active decode slots might effectively use only half of them for most of the batch duration.

The hardware cost stays constant.
The throughput collapses.

The Mental Model Shift

The key mental model shift:

Static batching treats:
    REQUEST = scheduling unit

Continuous batching treats:
    TOKEN STEP = scheduling unit

That single change is the entire breakthrough.

Static Batching Is the Wrong Scheduling Granularity

The issue is not the GPU.

The issue is the scheduler.

Static batching schedules entire requests as atomic units:

  • admit request
  • run until completion
  • free slot

This is equivalent to cooperative multitasking in old operating systems where one process runs until it voluntarily yields.

Continuous batching changes the scheduling granularity entirely.

Instead of scheduling complete requests, it schedules:

one decode iteration at a time

That means:

  • every active sequence generates one token
  • scheduler runs again
  • completed sequences are removed
  • new sequences are admitted immediately

The GPU never waits for the slowest request.

Continuous Batching

In continuous batching, the batch is no longer a fixed group of requests.

It becomes a dynamic pool of active decode slots.

When a sequence finishes:

  • its KV cache is freed
  • its slot becomes available immediately
  • a waiting request is admitted into the next decode iteration

The batch evolves continuously while inference is running.

This is the core idea behind vLLM scheduling.

The batch never fully completes.

It continuously mutates.

Short requests stop blocking long ones.
Long requests stop wasting GPU slots.
The scheduler keeps the GPU saturated.

Decode Scheduling Happens Every Iteration

sequenceDiagram
    participant Scheduler
    participant GPU
    participant ReqA
    participant ReqB
    participant ReqC

    Scheduler->>GPU: Decode step
    GPU->>ReqA: token
    GPU->>ReqB: token
    GPU->>ReqC: EOS

    Scheduler->>ReqC: remove slot
    Scheduler->>GPU: admit ReqD

    Scheduler->>GPU: Next decode step

This is token-level scheduling.

Every decode step becomes a scheduling boundary.

That is the entire utilization gain.

Continuous batching turns GPU utilization from:

“wait for the slowest request”

into:

“keep every slot occupied every decode iteration.”

Static vs Continuous Scheduler

The scheduling difference becomes obvious in pseudo-code.

Static batching

while True:
    batch = collect_fixed_batch()

    run_prefill(batch)

    while batch_not_finished:
        decode_step(batch)

    return_results(batch)

The batch is fixed for its entire lifetime.

Short sequences finish early and become idle.

Continuous batching

while True:

    fill_available_slots()

    decode_step(active_sequences)

    completed = identify_completed_sequences()

    free_slots(completed)

    admit_waiting_requests()

The scheduler runs between every decode step.

Slots are continuously recycled.

Why Utilization Improves So Much

Suppose:

  • 32 GPU slots
  • half the requests are short
  • half are very long

With static batching:

  • short requests finish early
  • their slots remain idle
  • GPU utilization collapses

With continuous batching:

  • completed slots are immediately refilled
  • active slot count stays near maximum
  • GPU remains saturated

Approximate utilization:

Static batching:
  ~40–60% effective utilization

Continuous batching:
  ~90–95% effective utilization

Same GPU.
Same model.
Same hardware cost.

Massively different throughput.

The vLLM paper reported roughly 2–4x throughput improvements from scheduling and memory management alone.

That is the power of choosing the correct scheduling granularity.

The Systems Engineering Parallel

I had seen this failure mode before in Kafka ingestion systems:
slow items inside fixed batches create idle workers and throughput collapse.

Continuous batching applies the same solution:

keep workers busy, not batches fixed.

Production Problems Continuous Batching Creates

Continuous batching improves throughput dramatically.

It also creates entirely new operational failure modes.

Scheduler starvation

Short requests free slots faster.

A naive scheduler may continuously prefer short requests while long prompts wait indefinitely.

Fairness policies become necessary.

KV cache thrashing

Aggressive slot turnover creates constant KV cache allocation and deallocation.

Poor memory management can create VRAM churn and fragmentation.

Tail latency instability

Continuous batching improves average latency.

But under burst traffic:

  • queue depth fluctuates
  • admission timing changes constantly
  • P99 TTFT becomes unstable

High throughput systems often pay for utilization gains with worse tail latency predictability.

Noisy neighbor effects

One tenant generating huge prompts can:

  • consume KV cache aggressively
  • occupy decode slots longer
  • reduce throughput for every other tenant sharing the GPU

This becomes a multi-tenant resource isolation problem.

Backpressure complexity

Queue depth and active decode slots are no longer tightly coupled.

A GPU may appear saturated even while queue growth accelerates.

Admission control becomes significantly harder than fixed-size batching systems.

Continuous Batching Requires Sophisticated KV Cache Management

Continuous batching only works if KV cache allocation is extremely efficient.

In static batching:

  • allocate KV cache once
  • free it when the batch completes

Simple.

In continuous batching:

  • sequences arrive continuously
  • sequences complete continuously
  • KV cache must be allocated and freed constantly

This creates fragmentation pressure.

Without careful memory management, VRAM becomes unusable despite large amounts of free memory.

Why PagedAttention Exists

This is exactly why vLLM introduced PagedAttention.

Instead of allocating one contiguous VRAM block per sequence, KV cache is divided into fixed-size pages.

Logical sequence memory remains contiguous.

Physical VRAM allocation does not need to be.

Without paging:
  [Seq A][Seq B][free][Seq C][free]
  → fragmented VRAM

With paging:
  [Page][Page][Page][Page]
  sequences map virtually to pages
  → near-optimal VRAM utilization

This is virtual memory for GPUs.

PagedAttention and continuous batching are deeply connected:

  • continuous batching creates dynamic allocation pressure
  • PagedAttention makes that pressure manageable

Without PagedAttention, continuous batching fragments VRAM badly at scale.

What This Means for AI Observability

This became directly relevant to the observability pipeline I am building.

Continuous batching changes the shape of inference traffic entirely.

Events become:

  • bursty
  • interleaved
  • slot-oriented instead of request-oriented

A single request's lifecycle is now scattered across many decode iterations while other requests overlap between them.

That changes what must be observable.

The schema now needs:

  • request_id
  • slot_id
  • queue_wait_ms
  • prefill_latency_ms
  • decode_latency_ms
  • kv_cache_utilization_pct
  • prompt_tokens
  • completion_tokens

Without these fields:

  • you cannot reconstruct scheduler behavior
  • cannot diagnose GPU starvation
  • cannot separate prefill bottlenecks from decode bottlenecks
  • cannot identify KV cache pressure

Continuous batching fundamentally changes what “good observability” means for inference systems.

The Bigger Insight

The deeper insight here is not about transformers.

It is that GPU inference serving eventually converges toward the same problems operating systems solved decades ago:

  • scheduling
  • memory management
  • fragmentation
  • fairness
  • resource isolation
  • throughput vs latency tradeoffs

Continuous batching matters because it changes the scheduling granularity from requests to token steps.

That single design decision is responsible for a huge fraction of the throughput gains that made modern LLM serving economically viable.
