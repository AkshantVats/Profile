I kept reading "tensor parallelism" as a GPU trick and "Kafka partitions" as a messaging trick. They are the same assignment problem with different hardware.

Scale a 70B model across four GPUs and you are choosing which layer shards live on which device, then synchronizing partial results. Scale inference observability across four consumer instances and you are choosing which tenant_id (soon tenant_id:model_id) events land on which partition, then batching inserts without breaking per-key ordering. Triton's model repository is just a partition assignment table with GPUs instead of brokers.

Tensor parallelism vs pipeline parallelism

When one GPU cannot hold the weights, you split the model. The two patterns I actually encounter in serving docs:

  • Tensor parallelism (TP) — split individual layers across devices; each forward step needs an all-reduce so every shard sees the full activation for the next op. Great when a single layer is too wide; expensive on network between GPUs.
  • Pipeline parallelism (PP) — assign contiguous layer stages to devices; micro-batches pipeline through the stages like an assembly line. Great when depth dominates; introduces bubble time unless you keep the pipe full.
flowchart LR
  R[Request router] --> G0[GPU 0 shard]
  R --> G1[GPU 1 shard]
  R --> G2[GPU 2 shard]
  R --> G3[GPU 3 shard]
  G0 --> AR[All-reduce / sync]
  G1 --> AR
  G2 --> AR
  G3 --> AR
  AR --> OUT[Next layer or response]

Alt text: Request router fans out to four GPU shards, synchronizes via all-reduce, then continues the forward pass.

Staff-engineer takeaway: TP optimizes width; PP optimizes depth. Pick wrong and you pay for NCCL chatter or pipeline bubbles instead of FLOPs. Multi-GPU serving is a placement problem first and a kernel problem second.

Triton model repository as routing table

NVIDIA Triton does not "run a model." It maintains a model repository — versioned directories with config.pbtxt that declare instance groups, GPU IDs, dynamic batching windows, and which physical replicas exist. A client sends model_name + version; Triton maps that to a concrete instance group. Sound familiar?

It is Kafka's partition assignment table with different nouns:

TritonKafka / observability
model_nametopic or stream name (ai_inference_events)
instance_group countpartition count
GPU id per instancebroker + partition id
dynamic batching windowconsumer micro-batch (1000 events / 500ms)
model version policyschema / compat version on ingest

When ops says "scale model foo," they mean add instances or widen the instance group — the same conversation as "add partitions and consumers for tenant traffic."

Partitions, keys, and ordering

Topic ai_inference_events carries the Rust producer's batch envelope {"events":[...]}. Today the producer keys by tenant_id only; DESIGN.md targets hash(tenant_id:model_id) so one noisy model cannot hot-spot a partition shared with quiet tenants — the same reason you would not put every DH city on one Kinesis shard.

Kafka guarantees order within a partition, not across partitions. That is a feature: you scale consumers horizontally until either CPU or ClickHouse insert rate caps you. The cost is cross-partition analytics — you cannot assume global ordering when debugging a spike; you filter by tenant_id and time range instead.

ClickHouse wants the same discipline. deploy/clickhouse/init.sql on G-03 defines:

ORDER BY (tenant_id, model_id, timestamp)

Monthly PARTITION BY toYYYYMM(timestamp) keeps merges bounded. Rows for one tenant/model cluster on disk the way Kafka keeps them ordered in the log — so hourly sum(cost_usd) does not scan the universe.

The data-systems analogy

Data-systems lens
LLM serving / observabilityData-systems parallel
Tensor parallel shardHDFS block replica — same logical row split across workers; merge before next stage
Pipeline parallel stageSpark stage boundary — shuffle between stages, micro-batch keeps pipe full
Triton instance groupKafka partition + consumer group member — assign work, preserve local order
Dynamic batching windowFileStream commit interval — latency vs throughput knob
Cross-partition rollupGlobal aggregate after map-side combine — correct only with commutative ops (sum, count)
Redis overflow bufferWAL / dead-letter staging — durability when sink is unhealthy

At Agoda we spent years teaching people that percentiles do not merge across tiers. Cross-partition percentiles lie the same way. For finance rollups, stick to sum(cost_usd) and counts — commutative metrics that survive sharding. Latency percentiles need careful merge or per-partition dashboards (Experience 1).

Cross-partition batching vs in-GPU batching

Day 2 batching happens inside one replica: fill GPU slots per token step. Consumer batching happens across unrelated keys that share a process — you are amortizing ClickHouse round-trips, not matmuls.

Do not confuse them when tuning:

  • Shrink vLLM batch → lower per-GPU latency, possibly lower throughput.
  • Shrink CH flush window (500ms) → fresher dashboards, more insert QPS.
  • Enlarge CH batch (1000 events) → higher throughput, coarser lag visibility.

Partitioning decides who shares fate. Batching decides how often you pay the network tax.

G-03: batch writer, breaker, overflow, DLQ×3

Ticket G-03 lands in consumer/internal/clickhouse/writer.go on feat/consumer-clickhouse-batch-writer. The writer buffers decoded events and flushes on whichever comes first: 1000 events or 500ms. That dual trigger is the same latency–throughput trade as Triton dynamic batching — wait for volume, but not forever.

flowchart TB
  K[Kafka ai_inference_events] --> C[Go consumer]
  C --> B{Batch buffer}
  B -->|flush 1000 or 500ms| CB{Circuit breaker}
  CB -->|closed| CH[(ClickHouse infra_ai.inference_events)]
  CB -->|open| R[(Redis overflow LIST)]
  CB -->|3 insert retries failed| DLQ[Kafka ai_inference_dlq]
  R -->|drain when closed| CH

Alt text: Consumer batches events, circuit breaker routes to ClickHouse, Redis overflow, or DLQ after retries.

Circuit breaker (from OBSERVABILITY.md): five consecutive insert failures → open (skip CH, push to Redis). After 30s → half-open (probe). One success → closed. Overflow drain runs every 5s (up to 5000 events) while closed.

DLQ×3: each batch gets three insert retries; per-event publish to ai_inference_dlq if still failing. Kafka offsets commit only after every event in the record is handed off — CH row, overflow, or DLQ — so you do not silently drop poison payloads.

Example rollup — the query Grafana panel (3) will run tomorrow:

SELECT
  tenant_id,
  model_id,
  toStartOfHour(timestamp) AS hour,
  sum(cost_usd) AS cost_usd,
  sum(prompt_tokens) AS prompt_tokens,
  sum(completion_tokens) AS completion_tokens,
  count() AS requests
FROM infra_ai.inference_events
WHERE timestamp >= now() - INTERVAL 24 HOUR
GROUP BY tenant_id, model_id, hour
ORDER BY hour DESC, cost_usd DESC;

Observability for the pipeline itself

Inference metrics are useless if the consumer is lying. G-03 exports on :9091/metrics (see OBSERVABILITY.md):

  • kafka_records_processed_total — records fully handed off
  • clickhouse_batch_size / clickhouse_flush_duration_seconds — batching health
  • circuit_breaker_state{state} — open should be rare and loud
  • redis_overflow_depth — backpressure signal
  • dlq_events_total — poison or schema drift

SLO sketches from the doc: rate(dlq_events_total[5m]) == 0 and breaker open < 1% of the hour. That is how I prove routing did not drop events under load — same discipline as labeled benchmarks in the daily thread.

Same assignment problem at Delivery Hero scale

Today's Experience sibling — Five Thousand Geo-Events Per Second — Shape of the Stream — is the map-matching side of this story: GPS fixes partitioned by order or region, route consumers that must not reorder a single delivery's events, OSRM clusters that look like instance groups. DH SQS shards and tenant_id:model_id Kafka keys are the same design question — who shares fate when load spikes? Get it wrong and one hot city or one hot model paints misleading lag while the cluster looks healthy.

The IoT post (Experience 3) is the failure-mode mirror: poison payloads belong in quarantine or DLQ, not in the rollup table.

What I am taking away

Multi-GPU inference and multi-partition ingestion both reduce to placement + commutative aggregates + backpressure. TP/PP name the GPU placement; Kafka keys and Triton instance groups name the ops placement; ClickHouse ORDER BY names the query placement. G-03 ties it together — batched inserts, breaker-gated Redis overflow, triple-retry DLQ — so cost_usd from Day 3 finally lands where finance can sum it.
