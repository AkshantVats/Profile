Day 4 of Learning LLM Inference — Tensor Parallelism Meets Kafka Partitions

4 of N — AI Learning Series. Model serving scale-out as a sharding problem — and why Triton's model repository is just a partition assignment table with GPUs instead of brokers.

AI Learning · Day 4 of N

I kept reading "tensor parallelism" as a GPU trick and "Kafka partitions" as a messaging trick. They are the same assignment problem with different hardware — and the same way to lie to yourself with a healthy global chart while one shard is on fire.

Scale a 70B model across four GPUs and you are choosing which layer shards live on which device, then synchronizing partial results on every forward step. Scale inference observability across four consumer instances and you are choosing which tenant_id (soon tenant_id:model_id) events land on which partition, then batching inserts without breaking per-key ordering. NVIDIA Triton's model repository is a partition assignment table with GPUs instead of brokers.

Staff engineers often inherit systems already distributed across workers. The hard problem is usually not adding nodes; it is deciding where state lives and what remains correct after you split work. Placement first — then kernels, then dashboards.

Previously: Day 3 → cost at ingest; Day 2 → batching inside one replica. This week I shipped the ClickHouse batch writer on the pipeline I am building in public — the consumer graduates from stdout to a sink that can answer sum(cost_usd) by tenant and hour.

When one machine is not enough

When one GPU cannot hold the weights, you split the model. Tensor parallelism (TP) shards individual layers and all-reduces activations every step — good when a layer is too wide. Pipeline parallelism (PP) assigns layer stages to devices and pipelines micro-batches through — good when depth dominates, costly when the pipe runs dry. TP optimizes width; PP optimizes depth. I have watched teams buy a fourth GPU, shard badly, and end up slower — the same failure mode as adding Kafka partitions without fixing a hot key.

Triton model repository as routing table

NVIDIA Triton maintains a model repository — versioned directories with config.pbtxt that declare instance groups, GPU IDs, dynamic batching windows, and which physical replicas exist. A client sends model_name + version; Triton maps that to a concrete instance group. That is the mental model I want to stick with: Kafka's partition assignment table with different nouns.

When ops says "scale model foo," they mean add instances or widen the instance group — the same conversation as "add partitions and consumers for tenant traffic." The debugging move is the same too: find the shard or GPU group whose queue depth diverges while the fleet chart still looks fine.

Partitions, keys, and ordering

Topic ai_inference_events carries the Rust producer's batch envelope {"events":[...]}. Today the producer keys by tenant_id only; the design doc targets hash(tenant_id:model_id) so one noisy model cannot hot-spot a partition shared with quiet tenants.

Kafka guarantees order within a partition, not across partitions. That is a feature: you scale consumers horizontally until CPU or ClickHouse insert rate caps you. The cost is cross-partition analytics — you filter by tenant_id and time range instead of assuming global ordering.

ClickHouse wants the same discipline: ORDER BY (tenant_id, model_id, timestamp) and monthly PARTITION BY toYYYYMM(timestamp) so hourly sum(cost_usd) does not scan the universe. For finance rollups, stick to commutative metrics — sum, count — that survive sharding. Cross-partition percentiles lie the same way merged tier percentiles do; latency needs per-partition dashboards or careful merge, not a fleet average you trust at 8pm.

Two batching layers

Day 2 batching happens inside one replica: fill GPU slots per token step. Consumer batching happens across unrelated keys in one process — you amortize ClickHouse round-trips, not matmuls. Shrink the vLLM batch for latency; shrink the flush window (500ms) for fresher dashboards; enlarge the batch (1000 events) for throughput. Tune the layer you are actually in.

Partitioning decides who shares fate. Batching decides how often you pay the network tax.

Batch writer under load

The work lives in infra-ai-streaming (consumer/internal/clickhouse/writer.go). The writer buffers decoded events and flushes on whichever comes first: 1000 events or 500ms — the same latency–throughput trade as Triton dynamic batching.

flowchart TB
  K[Kafka ai_inference_events] --> C[Go consumer]
  C --> B{Batch buffer}
  B -->|flush 1000 or 500ms| CB{Circuit breaker}
  CB -->|closed| CH[(ClickHouse)]
  CB -->|open| R[(Redis overflow)]
  CB -->|retries exhausted| DLQ[Kafka DLQ]
  R -->|drain when closed| CH

Five consecutive insert failures open the breaker and push to Redis; after 30s it half-opens and probes. Each batch gets three insert retries; failures land on ai_inference_dlq. Kafka offsets commit only after every event in the record is handed off — ClickHouse row, overflow, or DLQ — so poison payloads do not vanish from the rollup.

The Grafana panel I want next is simple:

SELECT tenant_id, toStartOfHour(timestamp) AS hour, sum(cost_usd)
FROM infra_ai.inference_events
GROUP BY tenant_id, hour;

Full query and DDL in GitHub — infra-ai-streaming, batch-writer branch.

Prove the consumer is honest

Inference metrics are useless if the consumer is lying. On :9091/metrics I watch records fully handed off, batch size and flush duration, breaker state, Redis overflow depth, and DLQ rate. Breaker open should be rare and loud; dlq_events_total at zero is the sketch SLO that says routing did not drop events under load.

What I am taking away

Multi-GPU inference and multi-partition ingestion both reduce to placement, commutative aggregates, and backpressure. Triton instance groups and Kafka keys name who shares fate; ClickHouse ORDER BY names where queries stay cheap; the batch writer names what happens when the sink hiccups. The dollars from Day 3 finally have somewhere finance can sum them.
