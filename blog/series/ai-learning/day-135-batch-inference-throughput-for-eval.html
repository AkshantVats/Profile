Day 135 — Batch Inference — Throughput for Eval

Runner uses shared prompt batch API. The interesting part isn't that eval-harness calls three models per prompt — it's that it calls them in a mode built for throughput, not the mode a live chat request would use, and the difference between those two modes is the whole lesson.

Yesterday's design fixed which rows an eval run is allowed to score against. Today's code fixes how those rows actually get scored — and the honest answer is: not one at a time. Three separate models run against the same fixed prompt list, and the mode that makes that finish in reasonable time is the same idea Day 2's continuous-batching post described for live serving, aimed at a workload with the opposite constraint.

The Print Shop and the Walk-In Counter

DS analogy — same machine, opposite goal
A commercial print shop runs a walk-in counter during the day: one customer's job at a time, started immediately, because nobody waiting at the counter will accept "come back once we've queued forty other jobs." At night, the same presses run a completely different way — every job for the next morning's delivery loaded at once, run back to back with no gaps, because nobody is standing at the counter waiting on any single page. Same machine. The only thing that changed is which one the shop is optimizing for: never making one customer wait, or getting through the whole stack by sunrise.

Online model serving is the walk-in counter — a real request arrives, and continuous batching (the mechanism Day 2's post walked through) exists specifically to keep that one request's latency low even while other requests share the same GPU. Eval is the overnight run: nobody is refreshing a browser tab waiting on prompt #40 of 2,000. The goal inverts from "answer this one fast" to "get through all of them by the time anyone checks."

So what: the same underlying model can be called two structurally different ways, and picking the wrong one for the job either wastes GPU sitting idle between requests, or makes a live user wait behind a batch that was never meant to include them.

Three Models, One Prompt List, One Batch Call

eval-harness's batch runner takes a fixed list of prompts from the held-out set and, for each one, calls three separate runner_names: the LoRA adapter under test, the un-adapted base model as an ablation, and a GPT-4o reference. The "shared prompt batch API" isn't three different code paths bolted together — it's one GenerationBackend interface, the same Protocol Day 133's sanity-sample script already defined, called once per (prompt, runner) pair and written to one output row.

Reusing that interface instead of writing a bespoke comparison harness means a batch eval run and a five-prompt sanity check are the same mechanism at two different scales — one runs five prompts against one adapter for a human to skim, the other runs the full held-out set against three runners and writes every row to Parquet instead of stdout.

Why the Latency Column Carries a Label

The output schema records a latency_ms per row alongside the completion text, because DESIGN.md's third metric is exactly that: is the adapter fast enough to serve, independent of whether it's correct. But a number measured inside an overnight batch run and a number measured against a single live request answer different questions, even if both are technically "latency."

This sandbox has no live GPU and no real GPT-4o credential, so every runner here is a stub — deterministic, clearly labeled, not a production measurement dressed up as one. The latency_ms column exists so the schema is ready the day a real HFGenerationBackend and a real BaselineRunner exist, but today's numbers describe stub call overhead, not inference speed.

3Runners per prompt: adapter, base, GPT-4o
1Shared GenerationBackend interface, not three
1Parquet file, one row per (prompt, runner)
0Live GPU or GPT-4o credential in this sandbox

So what: labeling a stub number honestly costs nothing today and saves someone from citing a fabricated latency figure in a real decision six months from now, once this schema is full of numbers that actually came off real hardware.

What Batch Mode Doesn't Change

Switching from one-request-at-a-time to a full-list batch changes throughput, not correctness. Each (prompt, runner) pair still gets its own row, its own completion, its own timing — batching is a scheduling decision about how work gets grouped on the way to the GPU, not a shortcut that merges or approximates results across prompts.

That distinction matters here specifically because eval scores have to be trustworthy per-row before they get aggregated by task_type in a later ticket. A batch mode that quietly blended results across prompts to go faster would make every downstream metric in DESIGN.md §3 meaningless, no matter how fast it ran.

So what: throughput and correctness are two separate axes, and today's runner only touches one of them — batching runs are what makes it feasible to score a whole held-out set instead of a hand-picked handful, without changing what "scoring one prompt" actually means.
