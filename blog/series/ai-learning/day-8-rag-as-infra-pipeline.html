Day 8 of Learning LLM Inference — RAG as an Infrastructure Pipeline

8 of N — AI Learning Series. Five stages, one latency budget — chunking as ETL, embedding as batch job, HNSW vs IVF indexing, and the retrieval bottleneck nobody profiles.

AI Learning · Day 8 of N

I was feeding PDFs into a vector store and watching end-to-end latency — assuming the LLM generate step would dominate. It did not.

The p50 request was spending more time in retrieval and embedding than in token generation. The generate step — the part everyone pictures when they say "RAG" — was the minority of the wall-clock budget. The majority was upstream: splitting documents into chunks, computing embeddings, querying a vector index, and ranking results before the model ever saw a single retrieved token.

That surprised me because I had been thinking of RAG as "search then prompt." The reality is closer to a five-stage data pipeline — chunk, embed, index, retrieve, generate — where each stage has its own throughput ceiling, failure mode, and cost structure. Day 1 described decode as memory-bandwidth-bound; Day 3 split prompt vs completion on the rate card. RAG adds infrastructure upstream of both — and until you instrument each stage separately, latency regressions hide behind "the model was slow."

Five stages, one latency budget

Every RAG request passes through the same pipeline. The stages are sequential in the hot path — a query cannot reach the LLM until retrieval returns — so the total latency is the sum, not the max.

Stages 1–3 run at ingest time — when documents enter the system. Stage 4 runs at query time, and stage 5 is the LLM call. The common mistake is optimizing stage 5 (model selection, prompt caching, temperature) while stages 1–4 are unmonitored. Day 7 covered prompt caching — a stage-5 optimization. Today is about everything before the model.

The pipeline analogy is not decorative. Each stage is a transformation with schema-in and schema-out. Chunk takes raw bytes and produces text segments with metadata. Embed takes text and produces float vectors. Index takes vectors and builds a searchable structure. Retrieve takes a query vector and returns ranked document IDs. Generate takes retrieved text plus a user query and produces an answer. It is ETL for knowledge — and like ETL, the quality of your output depends on the quality of every upstream stage.

Chunking — the ETL nobody respects

Chunking is the partition strategy for your knowledge base. The analogy to database partitioning is exact: too coarse and you drag irrelevant context into every query; too fine and you shatter meaning across boundaries that retrieval cannot reassemble.

A 20-page PDF with 500-token chunks produces about 60–80 chunks. A 200-token chunk strategy triples that count. The decision matters because each chunk becomes an independent retrieval candidate — if the answer spans two chunks and the boundary splits a critical sentence, no amount of downstream sophistication recovers it. The partition boundary corrupts the data.

StrategyPartition analogyFailure mode
Fixed-size (token count)Hash partitioning — uniform, context-blindSplits mid-sentence, mid-table
Recursive/semanticRange partitioning — respects boundariesUneven chunk sizes, hotspots in retrieval
Document-levelNo partitioning — one shard per docExceeds context window, retrieves noise

What I found building LensAI's document pipeline: the right chunk size depends on the downstream use case, not the document structure. Summarization tolerates larger chunks because the model can compress. Factual QA needs smaller, precise chunks because retrieval recall matters more than coverage. Treating chunk size as a constant instead of a parameter per use case is the same error as using one partition count for every Kafka topic — it works until it does not.

Overlap between chunks (sliding window) is the equivalent of replication factor for partitions: it costs storage but prevents boundary-split data loss. I default to 10–15% overlap, which means a 500-token chunk shares about 50–75 tokens with its neighbors. Enough to preserve sentence continuity at boundaries without doubling storage.

Embedding — the batch job

Embedding is the most expensive stage at ingest time and the most misunderstood at query time. Each chunk gets mapped to a dense vector — typically 768 to 1536 dimensions — by an embedding model. The cost structure rhymes with the batch-processing economics I know from data engineering: you pay per token, throughput is bounded by the embedding API's rate limit, and re-embedding a corpus because you changed models is a full reprocessing job.

768–1536Typical dimensions
~$0.10Per M tokens (ada-class)
~8192Max tokens per call

Two costs hide in the embedding step. The first is dollar cost: embedding a 100k-token corpus at ada-class pricing (~$0.10/M tokens) costs pennies, but re-embedding weekly because your chunking strategy changed costs the same amount again every time. The second is dimensionality cost: a 1536-dimensional vector per chunk means your index stores 1536 floats (6 KB in FP32) per entry. At a million chunks, that is 6 GB of raw vector data before the index structure adds overhead.

Day 6 covered quantization as codec selection for weight tensors. The same tradeoff applies to embedding vectors: you can store them in FP16 or even INT8, halving or quartering the index footprint. The recall hit depends on the index algorithm and the query distribution — the same "run an eval before you ship" discipline Day 6 argued for with weight quantization applies here with vector quantization.

One operational lesson: embed once, version immutably. Changing the embedding model invalidates every vector in your index — the same way a schema migration invalidates cached query plans. If you are going to change models, plan for a full re-index, not an incremental update. I track embedding_model_id in LensAI's chunk metadata so that mixed-model indexes are detectable, not silently wrong.

Indexing — a data structure decision

Once you have vectors, you need a structure that answers "give me the k most similar vectors" without scanning every entry. This is approximate nearest neighbor (ANN) search, and the data structure choice is a capacity-planning decision — not a correctness decision, because all ANN structures are approximate by design.

The two structures I keep running into are HNSW and IVF. The analogy to traditional databases helps:

HNSWIVF (Inverted File)DB analogy
StructureNavigable small-world graphClustered partitions + scanB-tree index vs partition scan
Build costO(n log n) — expensiveO(n) — cheaperIndex creation time
Query costO(log n) — fastO(n/k) — depends on nprobeIndex seek vs partition prune + scan
MemoryHigh (graph + vectors in RAM)Lower (vectors can page to disk)In-memory index vs disk-backed
Recall at scale95–99% with tuned M, efSearch90–95% with tuned nprobe—
Update costIncremental inserts possibleRequires periodic re-clusteringOnline index vs offline rebuild

HNSW is the B-tree of vector search: high memory, fast lookups, good for workloads where query latency matters more than build cost. The graph has layers — top layers for coarse navigation, bottom layers for fine-grained similarity. The tuning parameters (M for connections per node, efConstruction for build quality, efSearch for query quality) map to the same recall-vs-latency tradeoff you see when tuning B-tree page sizes and cache hit ratios.

IVF is partition-and-scan: cluster the vectors into Voronoi cells, then at query time probe the nearest nprobe cells and scan within them. Cheaper to build, lower memory, but query latency depends on how many partitions you probe — and setting nprobe too low drops recall the same way setting too few Kafka consumer partitions drops throughput. IVF is better suited for large-scale indexes where HNSW's memory overhead becomes untenable.

The decision is a secondary index analogy: HNSW is the always-in-memory covering index you build when p99 query latency is your SLO. IVF is the disk-friendly composite index you build when the corpus grows beyond what fits in RAM and you accept trading latency for capacity.

Retrieval — where the budget breaks

Retrieval is the only stage that runs in the hot path of every user query, and it is where I have seen latency budgets break most often. The query arrives, gets embedded (one embedding model call), then hits the vector index for top-k results. Each step adds latency, and the sum determines how much time is left for generation.

The bottleneck is usually not the ANN search itself — HNSW can return top-10 from a million vectors in single-digit milliseconds on a warm index. The bottleneck is the fan-in pattern: query embedding + ANN search + optional re-ranking + context assembly, all sequential, all before the LLM sees a token. At 50 QPS, each query gets 20ms of wall clock. If embedding alone takes 30ms because you are calling an external API, you are already over budget before retrieval starts.

Three retrieval failure modes I have hit in practice:

  1. Embedding latency dominance. Remote embedding APIs add network round-trip to every query. At high QPS, this becomes the ceiling. Self-hosted embedding models (distilled, quantized) trade dollar cost for latency control — the same build-vs-buy tradeoff as self-hosted LLMs, but at a fraction of the complexity because embedding models are small.
  2. Top-k inflation. Retrieving 20 chunks "to be safe" when the model only needs 3 wastes context window tokens and increases prompt cost. Day 3 showed that prompt tokens are the setup charge — stuffing irrelevant chunks into the prompt is paying for noise.
  3. Cold index on restart. HNSW indexes load into memory on startup. A pod restart means the first few queries hit a cold index with higher latency — the same cold-start penalty you see with JVM warmup or Redis cache rebuilds. This is operationally identical to the KV cache cold start from Day 1: the first request pays the full cost, subsequent requests amortize it.

Generate — the LLM is last, not first

By the time the model receives retrieved chunks, four pipeline stages have already run. The generate step is what everyone associates with RAG, but it is the consumer at the end of the pipeline, not the producer. Its job is to synthesize an answer from pre-selected context — and its quality is bounded by what retrieval delivered.

Day 7 covered prompt caching as a way to reduce prefill cost when the system prompt and tool schema are stable. In RAG, the retrieved chunks change on every query — so the prompt prefix is rarely cache-friendly unless you structure the prompt to pin a stable system block before the dynamic RAG context. The differentiation matters for cost modeling:

The operational implication: prompt caching and RAG are complementary, not alternatives. You can cache the stable system prompt while injecting fresh RAG context after the cache breakpoint. The cached prefix saves money on the static part; RAG handles the dynamic knowledge part. Treating them as either/or means leaving one lever untouched.

LensAI — proposed InferenceEvent RAG fields

Today in infra-ai-streaming: InferenceEvent carries token counts and cost_usd, but nothing about the retrieval stage. When a RAG-powered request is slow, the dashboard shows high latency_ms and cannot distinguish "the model was slow" from "retrieval took 400ms before the model saw a token." That gap is why this section exists.

Proposed RAG fields for InferenceEvent
FieldTypeWhy
retrieval_latency_msu32Time from query embed to top-k return — the pre-LLM budget
chunks_retrievedu16Top-k count — correlate with prompt token inflation
chunks_usedu16Chunks that survived re-ranking and fit in context window
embedding_model_idStringVersion the vector space — detect mixed-model index drift
retrieval_score_maxf32Highest similarity score — proxy for retrieval confidence
retrieval_score_minf32Lowest included score — threshold monitoring
index_typeStringHNSW / IVF / flat — correlate latency with structure choice

Producers map the retrieval stage into these fields at call time; ingest validates ranges (e.g., retrieval_latency_ms > 0 when chunks_retrieved > 0) and forwards facts. The Grafana work that follows: a retrieval_latency_ms histogram by tenant_id, a scatter plot of chunks_retrieved vs latency_ms to find the top-k inflation point, and an alert on retrieval_score_max < threshold — because low-confidence retrieval feeding the LLM produces grounded hallucinations that look authoritative but cite the wrong document.

The key constraint: retrieval_latency_ms + generate_latency_ms ≈ latency_ms should hold within measurement noise. If they do not add up, there is an uninstrumented gap — context assembly, re-ranking, or queue wait — that needs its own field. The discipline is the same one Day 3 applied to cost_usd: if the components do not sum to the total, the schema is lying.

Takeaway — complements, not alternatives

RAG is an infrastructure pipeline with the same operational properties as any ETL system: partition boundaries matter (chunking), batch job economics govern ingest (embedding), data structure selection drives query performance (indexing), and the hot-path bottleneck is rarely where you expect it (retrieval, not generation).

Prompt caching and RAG are complementary — one reduces cost on stable prefixes, the other grounds the model in dynamic knowledge. The system needs both.

The mistake I kept making was treating RAG as a model feature — "add retrieval to reduce hallucination" — instead of as infrastructure that needs the same monitoring, capacity planning, and failure-mode analysis as any other pipeline. The LLM is the last stage, not the whole system. Until InferenceEvent carries retrieval fields alongside token counts and cost, the observability story has a hole exactly where latency hides.
