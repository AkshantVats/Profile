Day 114 — Live A/B — Traffic Splitting for Models

Candidate model ID in an escalation step's routing config. Not a new deploy, not a new binary, not even a restart — a firing rule's escalation reaches a step, that step names a candidate model and a percentage, and from that moment on some slice of live requests quietly mirrors to it while everything else keeps running exactly as it did yesterday.

A Canary With No Deploy Attached

A canary release usually means shipping a new binary to a small slice of instances and watching it before a full rollout. Today's ab_test_candidate escalation step does the same job at a different layer: the binary never changes, only which model ID a request's inference call targets, decided per request by pkg/abtest.Router.Decide.

That's the same trick a feature-flag service plays on a boolean code path, just pointed at a model ID instead of an if branch. Yesterday's evaluator decided when a rule has fired long enough to escalate; today's router decides, for each request after that point, which model actually serves it.

So what: treating a candidate model rollout as a routing decision instead of a deployment means the blast radius of "try the candidate" is a percentage in a config value, not a binary someone has to build, ship, and be ready to roll back.

Deterministic, Not a Coin Flip Per Request

Router.Decide takes a stable key — a request ID, never a value regenerated per call — hashes it with FNV-1a, and buckets the result into one of 10,000 slots. A request whose bucket falls under the configured sample_percent threshold mirrors to the candidate; everything else doesn't, and no shared counter or coordination between processes is needed for the observed rate to land where the config says it should.

DS analogy — a raffle with pre-printed numbers
A raffle drum drawn fresh each night gives every ticket-holder a new chance every time, which is exactly wrong for this job — the same person could win Monday and lose Tuesday with no code change in between. A raffle where each ticket's outcome was fixed the moment it was printed is the opposite: check ticket #4471 on any night, at any booth, and it says the same thing every time, because the outcome was never redrawn, only looked up. Router.Decide is the second kind of raffle — a request's bucket is a fact about its key, computed the same way everywhere, not a fresh roll each time it shows up.

So what: a request routed by a coin flip can land in the candidate arm on one attempt and the baseline on a retry of the identical logical request, which makes "did the candidate see this case" an unanswerable question — a deterministic hash makes it answerable by construction, every time, from any process.

Two Scores, or No Comparison

Routing to the candidate on its own proves nothing — a request that only ever sees the candidate has no baseline to compare against, and a request that only ever sees the baseline was never part of the experiment at all. Today's second piece, Collector, exists to close that gap: it never lets the candidate arm replace the baseline call, both run, both get scored, and the collector pairs the two scores by the same key Router.Decide used to route in the first place.

Whichever score arrives first — baseline or candidate — waits in a pending map keyed by request key until its counterpart shows up; a duplicate report for the same arm is dropped, first write wins, so a retried scoring call can't silently overwrite a value that already got paired. Summarize() reduces every completed pair down to one number that actually answers the question: the mean difference between what the candidate scored and what the baseline scored, on the exact same requests.

So what: an unpaired candidate score and an unpaired baseline score are two different, differently-distributed samples that happen to share a time window — pairing by key is what turns "we also ran a candidate" into "we know whether the candidate is better, on the requests that actually saw both."

The Honest Limitation

Collector.Pending() reports how many requests are stuck waiting on their other half, and today's code never expires one on its own. A candidate call that errors before it ever scores leaves its baseline half sitting in the pending map indefinitely — not wrong, exactly, since nothing corrupts, but a caller running this for a long-lived rule needs to add its own timeout or garbage-collection pass, because Collector itself will hold that half forever.

The router has the same shape of gap in the other direction: nothing in today's code stops an ab_test_candidate step from routing traffic indefinitely once a rule fires, because neither Router nor the escalation step it comes from carries an expiration. A percentage answers "how much," never "for how long."

So what: today's code answers the sampling and pairing questions correctly, but a production rollout of this needs a caller-owned TTL on both the pending map and the routing decision itself — leaving that out here is an honest scope boundary, not an oversight to paper over.

The Experience Bridge

Today's Experience post reaches the exact same deterministic-bucketing idea from Wayfair's pricing platform: PAS's live A/B price experiments hash a SKU ID modulo 100 into a percentile bucket, for the same reason Router.Decide hashes a request key into one of 10,000 — so the same entity gets the same treatment every time a rule re-evaluates, not a fresh coin flip that makes "was this SKU in the experiment" unanswerable.

A deterministic hash answers who's in the experiment; a paired collector answers whether the experiment found anything — neither one alone is a complete answer, and today's code only ships the first two-thirds of that story on purpose.

So what: a candidate model rollout that only samples traffic, without pairing its scores against the baseline it ran beside, isn't an experiment — it's just traffic going somewhere new and nobody watching closely enough to say if that was a good idea.
