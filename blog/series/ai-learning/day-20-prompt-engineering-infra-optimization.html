Day 20 — Prompt Engineering as Infra Optimization

Prompt cache and prefix reuse in dollars per million requests — the math your PM will actually read

At 1,000 requests per day, prompt engineering is a craft question. At 1 million requests per day, it is a cost engineering decision worth $100,000 a month or more. The framing changes not because the techniques are different, but because the stakes are high enough to justify treating your system prompt like infrastructure — versioned, reviewed, monitored, and optimized with the same discipline you bring to a Kafka partition key strategy.

What I didn’t expect when I first dug into this is how much the “engineering” part is already solved. Prompt caching is not a clever trick — it’s a KV cache lookup keyed on a prefix hash. Every model provider that offers it has built the same mechanism underneath: hash the shared prefix, store the computed KV pairs, serve them for a fraction of the original compute cost. Your job is to structure the prompt so the expensive static part is always at the front.

Prompt engineering at scale is prefix management. Put the static content first, the variable content last, and let the cache do the rest.

What prompt caching is (and isn’t)

Prompt caching works on the shared prefix: the portion of the input that is identical across requests. A system prompt describing an AI assistant’s behavior, a set of reference documents, or a library of few-shot examples — any of these can be cached if they appear at the start of every request and don’t change between requests.

Think of it like a printer where the first 20 pages are always the same legal boilerplate. Without caching, you typeset all 20 pages every time you print. With caching, you typeset them once, keep the typeset plates in a drawer, and pull them out for each new document. The variable part — the actual letter, the unique content — still gets typeset fresh each time.

Anthropic’s implementation reads cached tokens at 10% of the normal input rate, with a 125% surcharge on the first write (the “plate typesetting” step). The cache TTL is 5 minutes by default — if 5 minutes pass without a cache hit, the prefix is evicted and must be rewritten on the next request. OpenAI’s implementation discounts input tokens by 50% for prefixes longer than 1,024 tokens, with automatic caching and no explicit write step.

DS analogy — prompt prefix as CDN edge cache
The prompt prefix is a static asset. A CDN caches static content at the edge after the first request; subsequent requests for the same asset serve from cache without hitting the origin. Prompt caching does the same: the model compute (origin) is bypassed for cached prefixes; only the variable user query (the “personalized” content) requires fresh processing. The cache key is a hash of the prefix bytes, exactly like a CDN cache key on a URL path.

What the cache does not cover: output tokens are always generated fresh. The cache only affects input processing — the KV attention computation over the prefix. Every new response is a full generative pass.

Dollar math at 1M requests per day

Let’s make this concrete. Assume you’re running a customer-facing AI assistant on Claude. The system prompt is 2,000 tokens (persona, behavior rules, safety guidelines). The user query is 200 tokens on average. Using mid-2026 Claude Sonnet pricing ($3.00 per million input tokens), the baseline cost without any caching is:

Per request:  (2,000 + 200 tokens) × $3.00 / 1,000,000 = $0.0066
At 1M req/day: $0.0066 × 1,000,000 = $6,600/day → $198,000/month

Now enable prompt caching on the 2,000-token system prompt with a 90% cache hit rate. The 10% of requests that miss cache pay the full $0.006 for the system prompt plus a 125% write surcharge on that first write. The 90% that hit cache pay just 10% of the system prompt cost:

Cache hit  (90%): 2,000 tokens × $0.30/M + 200 tokens × $3.00/M = $0.00066
Cache miss (10%): 2,000 tokens × $3.00/M × 1.25 + 200 tokens × $3.00/M = $0.00810
Blended:          0.9 × $0.00066 + 0.1 × $0.00810 = $0.00141/request
At 1M req/day:    $0.00141 × 1,000,000 = $1,410/day → ~$42,300/month

The gap: $198,000/month versus $42,300/month. That’s $155,700/month in savings from a prefix ordering change and two lines of API config. At 5 engineers with full-loaded cost of $30k/month each, this is equivalent to 5 engineering-months freed per month.

Prefix reuse: structuring prompts for cache hits

The single rule for maximum cache efficiency is: static content first, variable content last. Any departure from this order breaks the cache hit. If the user ID appears in the middle of the system prompt, the prefix hash changes with every user, and you get 0% cache hits on the system prompt portion that follows it.

The Anthropic API accepts a cache_control marker on the last content block you want cached. Everything before that marker is treated as the cacheable prefix. A minimal implementation looks like this:

import anthropic

client = anthropic.Anthropic()

response = client.messages.create(
    model="claude-sonnet-4-6",
    max_tokens=1024,
    system=[
        {
            "type": "text",
            "text": SYSTEM_PROMPT,  # 2,000 tokens of static config
            "cache_control": {"type": "ephemeral"}  # mark as cacheable prefix
        }
    ],
    messages=[
        {"role": "user", "content": user_query}  # variable per request
    ]
)

The "ephemeral" cache type means the provider caches it for the TTL window (5 minutes for Claude). The response object includes cache_creation_input_tokens and cache_read_input_tokens usage fields — those are the counters to put in your Prometheus metrics.

A subtle gotcha: conversation history breaks the cache if you include it in the system prompt or prepend it to the cacheable block. Multi-turn conversations should keep the system prompt truly static and append history as user/assistant message pairs after the cache boundary. The static prefix gets cached; the growing history does not.

Beyond caching: prompt compression

Caching reduces the cost of static tokens. Compression reduces the number of tokens in the first place. Both techniques compound: fewer tokens in the prefix means cheaper cache writes and faster cache reads.

The 80/20 rule for prompt compression: 20% of the tokens in a typical system prompt carry 80% of the behavioral signal. The remaining 80% is hedging language, redundant rephrasing, and prose connective tissue that the model doesn’t need. A 40-token prose instruction like "Always respond in a professional and friendly manner, avoiding technical jargon that the user might not understand" compresses to a 12-token structured instruction: "Tone: professional, friendly. Avoid jargon."

Compression doesn’t mean destroying nuance. It means treating the system prompt like a configuration file rather than a memo — structured keys with concise values, not flowing explanations written for human readers. The model reads your instructions as token sequences, not prose. The prose is for you.

Instruction formatTokensBehavioral signal
Prose: "Always respond in a professional and friendly manner..."40Same
Structured: "Tone: professional, friendly. Avoid jargon."12Same
Prose: "If the user asks about pricing, always tell them to..."35Same
Structured: "Pricing queries: redirect to sales@company.com"9Same

The compressibility limit is real. Below a certain density, structured instructions lose nuance that matters — "be empathetic" compresses poorly because the model needs examples of what empathy looks like in context. Know when prose earns its tokens.

The request volume threshold

Prompt caching has a real implementation cost: restructuring prompts, adding cache markers, monitoring cache hit rates. That investment only makes sense above a certain request volume. Below the threshold, the engineering time costs more than the token savings.

Here is the rough breakeven analysis I use. Assume one engineer-day to implement caching (restructure prompt, add markers, add monitoring). At $30k/month fully-loaded engineer cost, one day is $1,364. The savings per day from caching a 2,000-token system prompt at 90% hit rate: roughly $4.75/day per 1,000 requests/day of volume. The breakeven day count is: $1,364 ÷ ($4.75 × daily_req_volume_in_thousands).

At 1k req/day:   breakeven in 287 days — not worth it
At 10k req/day:  breakeven in 28 days — marginal
At 100k req/day: breakeven in 3 days — do it now
At 1M req/day:   breakeven in <1 day — do it before launch

The crossover point is roughly 10,000–50,000 requests per day. Below that, focus on correctness and reliability. Above that, treat caching as a standard infrastructure decision, not an optimization.

The infra engineer’s mental model

The most useful mental shift is treating the prompt as a configuration file, not a document. Configuration files get versioned, reviewed in PRs, and rolled back when they cause regressions. They get tested against a golden set of inputs before deployment. They have owners who are paged if they change unexpectedly.

The Prometheus metric to add is llm_prompt_cache_hit_rate, computed as cache_read_input_tokens / (cache_read_input_tokens + cache_creation_input_tokens). A sudden drop in hit rate means something changed in the prefix — a new feature flag wrote a user-specific string into the static section, or a dependency injected dynamic content at the wrong position. That alert fires before the invoice arrives.

Context budgeting is the third lever after caching and compression. Set a maximum token budget per request type — a customer query gets 4k tokens context window, a document summarization task gets 32k. Enforce the budget at the application layer before the API call. A context budget that grows unchecked is a cost anomaly that compounds with every additional feature that adds to the prompt.

The LensAI connection

The llm_prompt_cache_hit_rate metric requires knowing how many tokens were served from cache versus recomputed. That data lives in the API response’s usage fields — but only if you capture it. An eBPF tracer that intercepts the full HTTP response body gives you those usage fields from every request across every service, without requiring each team to instrument their own API client.

Today’s code PR — the ebpf-llm-tracer README overhaul — makes the comparison explicit in the buyer’s guide table. The “token-level visibility” row shows that eBPF extraction of prompt_tokens and completion_tokens works without SDK changes. That same extraction path includes cache_creation_input_tokens and cache_read_input_tokens when the response includes them — the parser reads the full usage object, not just the top-level token counts.

The README is the buyer’s guide for the observability tool. This post is the CFO’s guide for why the metric it surfaces — cache hit rate per tenant — is worth tracking. Both arguments are the same at root: measure the signal that controls cost, not the signal that’s easiest to capture.
