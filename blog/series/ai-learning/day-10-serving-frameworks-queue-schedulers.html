vLLM vs TGI vs Ollama — scheduling policies, not logos

I compared vLLM, TGI, and Ollama from README throughput tables — then watched queue wait dominate P99 while the GPU looked idle, and the reverse: GPU saturated, queue flat. The benchmark table lied because it never named the queue discipline.

Before "what's the benchmark score?", ask "what's the queue model?" FCFS? Prefill-first? Single-slot local? Anomaly detection on model_id latency is only trustworthy if you understand how each serving framework reports time — the same question I asked reading VictoriaMetrics ingest tonight in Experience 10.

The benchmark table lied

Serving frameworks are queue schedulers with different admission policies — logos and tokens/sec hide that. A framework-reported latency_ms may exclude admission wait, fold prefill and decode together, or feel instant on localhost because no network queue exists. Comparing numbers without naming the queue is how you ship a false SLO.

Prefill and decode are two queues wearing one jacket

Day 1: prefill is parallel scan; decode is serial and memory-bandwidth-bound. Day 3: prefill_latency_ms + decode_latency_ms should explain latency_ms. If the framework folds queue wait into "latency", your z-score lies.

PhaseScheduler questionDominant resource
Queue waitWhen does work enter the GPU?CPU / socket backlog
PrefillHow many prompt tokens per step?Compute + HBM bandwidth
DecodeContinuous batch or static batch?KV cache + memory bandwidth

Total latency is a sum of queue disciplines — not a single number the framework prints.

Continuous batching is the scheduler default

Day 2 covered continuous batching at decode-iteration granularity — not repeated here. vLLM and modern TGI assume it for throughput; Ollama often optimizes single-user simplicity over multi-tenant slot packing. Observability needs queue_wait_ms, slot_id, and phase splits.

GPU memory sets the batch ceiling

Day 9: four VRAM tenants; schedulers admit until KV pressure triggers preemption or reject — same cliff, different policies. Long-context RAG (Day 8) inflates prefill; two frameworks with "the same continuous batching" diverge when KV headroom differs.

What production metrics still miss

Benchmarks measure one queue discipline; production mixes tenants, context lengths, and model swaps. Failure modes without incident narrative: hidden queue growth (GPU util fine while backlog grows), prefill storms from RAG fan-in, false SLO green when latency_ms excludes admission wait — the same class of bug as timers that included retry wait after a broker kill (Experience 9), applied to inference.

LensAI bridge — model_id × latency you can trust

LensAI's InferenceEvent already carries model_id, latency_ms, and optional prefill_latency_ms / decode_latency_ms. That is necessary but not sufficient: latency_ms without serving_framework and queue-phase splits is a cardinality-friendly lie.

Field (proposed)TypeWhy
serving_frameworkStringvllm / tgi / ollama — do not infer from model_id alone
framework_versionStringScheduler behavior changes release-to-release
queue_wait_msu32Admission wait — Day 2 observability gap
batch_size_at_startu16Admission snapshot — ties to Day 9 cliff
scheduler_policyStringe.g. continuous, static, unknown

Z-score on latency_ms per model_id only works if serving_framework and phase fields are stable. Mixing Ollama local timings with vLLM cluster timings under one model_id is aggregating P99 across shards without labels — the cardinality lesson applied to time semantics.

Constraint from Day 3: queue_wait_ms + prefill_latency_ms + decode_latency_ms ≈ latency_ms (within noise). If not, the framework is hiding a phase.

Takeaway — read the scheduler, then the benchmark

Framework choice is queue discipline choice. vLLM, TGI, and Ollama differ less in "model quality" than in admission, batching, and memory packing. I am not claiming datacenter benchmarks here — this is the schema discipline LensAI producers need before Day 12's semantic cache lands in the same operational queue as latency anomalies.
