Day 122 — PII in Training Data — NER + Regex

An email address has a grammar. A person's name does not. That single asymmetry decides which half of a scrubber can be a regex, which half needs a model — and why the honest answer to "did we catch everything?" is to make the pipeline refuse rather than guess.

Here is the table today's scrubber writes into, and the most interesting thing about it is a column that isn't there:

CREATE TABLE infra_ai.pii_redaction_audit
(
    request_id      String,
    category        LowCardinality(String),  -- email|phone|person_name|address|secret|cross_tenant
    field           LowCardinality(String),  -- prompt_text|response_text|criteria_json|rationale
    span_start      UInt32,                  -- byte offset into the ORIGINAL text
    span_end        UInt32,
    detector        LowCardinality(String),  -- regex|ner|constraint
    redacted_at     DateTime64(3)
)
ENGINE = MergeTree
ORDER BY (redacted_at, request_id);

There is no value column. An audit log that stored the thing it redacted would just be a second, unscrubbed copy of the same liability — sitting in a table nobody remembers to include in the next cleanup.

So the row records the shape of a redaction: which record, which field, which byte range, which detector fired. That is enough to prove a redaction happened at a specific place and not enough to reconstruct what was there. The detector column is the part worth reading closely, because it names two mechanisms that are not remotely equivalent.

Some Data Has a Grammar. Names Don't.

An email address is defined by a specification. There is an @, there is a domain with at least one dot, there are character classes that are allowed on each side. That is a format, and a format is exactly what a regular expression is built to recognise.

Phone numbers are looser but still shaped — digit runs, optional country prefix, conventional groupings. Credit card numbers, API keys, connection strings: all defined by shape. You can write a pattern for each of them, and the pattern is correct in a checkable way.

Now try to write a regular expression that matches person names. Not "capitalised words," which matches the first word of every sentence, every product name, and every city. Actual names.

You can't, and the reason isn't that the regex would be long. It's that names are not a format at all — they are an open, unbounded set of tokens whose only distinguishing property is that some community of humans uses them as names.

The set grows, it differs by language, and it overlaps with ordinary words: Rose, Mark, Baker, Summer, Hope.

So what: the split inside a PII scrubber isn't arbitrary engineering taste — it falls exactly along the line between data defined by a grammar and data defined by convention, and those two need fundamentally different machinery.

DS analogy — a barcode scanner, a guest list, and a doorman
Three ways to check who gets into a building. A barcode scanner reads a badge: the badge has a mandated format, so the scanner needs no knowledge of any individual person — it validates shape and is exactly right every time. That's regex. A guest list is a hash set: O(1) lookup, perfectly accurate for names on it, and completely blind to a legitimate guest whose name nobody wrote down. That's a gazetteer. A doorman who can look at someone not on the list and tell they belong is the only one who generalises — and the only one who can be wrong in a fuzzy, hard-to-audit way. That's NER. The scrubber uses all three, and the interesting design question is what happens on the night the doorman doesn't show up.

What NER Actually Is

Named Entity Recognition is token classification: a model reads a sequence of tokens and labels each one with an entity type or "none." PERSON, LOC, ORG, and so on. It's the doorman — it generalises to names it has never seen, because it learned the contextual and morphological patterns that surround names rather than memorising a list.

That generalisation is real and it is also probabilistic. An NER model has a recall number, and that number is not 100%. It misses names in unusual contexts, in code blocks, in languages underrepresented in its training data, in text mangled by a copy-paste.

Which means the honest description of a scrubber's coverage is not "we detect names." It's "we detect names at whatever recall this model achieves on text that looks like this," and nobody measured the second half on production prompts.

So what: adding NER doesn't turn an incomplete scrubber into a complete one — it turns a knowably incomplete one into an unknowably incomplete one, which is a different problem requiring a different response.

The Two Errors Do Not Cost the Same

Every detector has two failure modes, and treating them as symmetric is where scrubbing designs usually go wrong.

ErrorWhat happensRecoverable?
False positive — redacts text that wasn't PIIOne training row loses a few tokens, or gets droppedYes. You have thousands more rows, and the loss is visible in the audit log
False negative — misses real PIIPersonal data enters a training set, and then a model's weightsNo. You cannot un-train a model on a row you shouldn't have used

That asymmetry is enormous, and it is specific to training data in a way it isn't for logs. A leaked PII string sitting in a log file is a storage problem you can go delete. A leaked PII string that trained a model is now diffused into weights, and large models are known to sometimes emit training data verbatim when prompted the right way.

So the scrubber is not a filter that tries to be accurate. It's a filter whose errors are deliberately biased toward over-redaction, because one direction costs you a row and the other direction cannot be undone.

You can always throw away one more row. You cannot un-train a model on a row you should never have used.

So what: when the two error costs differ by orders of magnitude, "maximise accuracy" is the wrong objective — the right one is to minimise the expensive error and accept a lot of the cheap one.

Fail Closed Means the Doorman's Absence Is an Answer

This is where the subtitle's comparison earns its place. Payment-card scrubbers are built on the same stance: when the component that validates a card number can't run, the transaction doesn't quietly proceed unvalidated — it stops.

The scrubber applies the same rule in three places, and all three write an audit trail before dropping anything:

  TEN -->|yes| RX["Regex pass"]
  RX -->|secret found| DROP

  NER -->|error| DROP
  NER -->|yes| RED["Redact spans"]
  RED --> OUT["Keep for export"]

The middle branch is the ordinary one: email, phone, person name and address get replaced in place and the row survives. The two drop branches are for categories where a partial redaction still leaks the dangerous part — a pasted credential, and a row from the wrong tenant.

The third path is the one that matters most and looks strangest. If the recognizer errors, the row is dropped even though nothing was detected in it. No detection is not evidence of no PII when the detector didn't run.

In code that means the constructor refuses a nil recognizer outright, rather than silently degrading to regex-only. A scrubber that quietly ran with half its detectors missing would report zero name detections and look, in the audit log, exactly like a clean corpus.

So what: fail-closed isn't a try/catch policy — it's the decision that "we couldn't check" and "we checked and it was clean" must never produce the same output.

What a Gazetteer Actually Buys You

Today's implementation ships the guest list, not the doorman. A gazetteer — a dictionary of known names, plus a street-suffix heuristic for addresses — matches whole tokens against a set and finds nothing outside it.

The reason is unglamorous: a statistical NER pass needs a model artifact, no such artifact exists in this repo or its dependency graph, and the CI job that would run it has no network egress to fetch one at test time. Vendoring megabytes of weights to satisfy a ticket's wording would be a worse trade than being explicit about the gap.

But the interface is the real thing. EntityRecognizer is one method, and swapping a served model in behind it is a constructor change rather than a rewrite. What ships is a floor, and it's labelled as a floor in the package documentation rather than in a PR description that ages out of view.

And here's the design payoff of having built the fail-closed tier first: a scrubber whose recognizer is honestly weak is safe, because the pipeline was never allowed to interpret silence as a clean bill of health. The weak recognizer degrades coverage, not correctness of the claim.

So what: when you can't ship the strong version of a component, the thing that keeps the system honest is not a better stub — it's a policy that treats the component's uncertainty as a first-class outcome.

Why the Offsets Point at the Original Text

One last schema detail with a real bug hiding behind it. span_start and span_end index the original field text, never the redacted output.

The reason is that redaction changes lengths. Replacing a 15-character email with [REDACTED_EMAIL] shifts every subsequent byte, so an offset captured against the output would point somewhere arbitrary — and worse, the drift compounds with each additional redaction in the same field.

Recording against the original keeps every row independently meaningful: text[span_start:span_end] is exactly the thing that was removed, for anyone who still legitimately holds the original. That property is what makes the audit table a verification tool rather than a log of assertions.

Overlapping detections get the same treatment. When two detectors claim intersecting ranges, redaction takes the widest span — a narrower match winning would leave the bytes outside it sitting in the output — while both detections still get their own audit row, because both are true statements about what fired.

So what: an audit trail is only useful if each row means something on its own, and that requires deciding up front which version of the record the row is describing.

The Generalizable Lesson

The specific thing I built today is a PII scrubber for fine-tuning data. The transferable part is a way of deciding how a filter should behave when it isn't sure.

Three questions, in order:

  1. Does this data have a grammar, or only a convention?
  2. What do my two error types actually cost, and do they cost the same?
  3. What should the system output when the check itself couldn't run?

Most filters answer that third question by accident — usually by letting the row through, because that's what a caught exception and a default-empty return naturally do. Answering it on purpose is most of the difference between a scrubber and a claim that you have one.
