Day 21 — Production Reliability for LLM APIs

Rate limits, provider outages, streaming disconnects — mapped to patterns you know

I’ve spent years designing retry logic, circuit breakers, and fallback paths for distributed systems. The first time I wired up a production LLM API, I expected the same engineering vocabulary. What I found is that providers speak the same language — but the consequences of getting the classification wrong are different from anything in a standard HTTP service.

In a standard microservices mesh, you classify responses into three buckets: retry on 5xx, don’t retry on 4xx, circuit break on sustained failure. LLM providers add a fourth category that traditional HTTP services don’t have: fail loud. The request is fundamentally unsound, and retrying or falling back won’t help. The user must fix their prompt.

Getting the classification wrong doesn’t just affect the current request. A retry loop on a context_length_exceeded error will exhaust your entire rate limit budget retrying a request that will fail every time. The classification is the precondition for every other reliability decision you make.

DS analogy — the post office with four counters
Think of LLM providers as post offices with four counters. The retry counter is temporarily closed — come back in 30 seconds. The circuit break counter is the building with a power outage — stop sending for five minutes. The fallback counter is the express window — slower service, but open. The fail loud counter is the one where you’ve brought an oversized package — no counter can help; you need to repack it first.

The error classification framework

Every LLM provider error maps to exactly one of four responses: retry, circuit break, fallback, or fail loud. The mapping requires reading the error.type field in the response body, not just the HTTP status code. An HTTP 400 covers both “your prompt is too long” (fail loud) and “your JSON is malformed” (fail loud, different fix). An HTTP 503 covers both “we’re overloaded” (retry) and “we’re doing maintenance” (circuit break for longer).

Retry means the request is valid and the system is temporarily unavailable. Circuit break means the provider is experiencing a sustained outage — stop sending requests for a defined window. Fallback means the primary provider is unavailable but a secondary can serve the request. Fail loud means the request itself is broken; no amount of retrying or rerouting will fix it.

What I didn’t expect: the boundary between “retry” and “circuit break” is time-based, not error-based. The same 429 means “retry” if it’s a one-off and “circuit break” if it’s happened 10 times in 60 seconds. You need a sliding window counter per provider endpoint to make this distinction correctly — the error code alone is never enough.

Rate limit errors (429): the retry class

Provider rate limits come in two flavors: requests per minute (RPM) and tokens per minute (TPM). RPM limits fire when you send too many requests regardless of size. TPM limits fire when the aggregate tokens in your requests exceeds the tier cap. Both return 429, but the mitigation is different.

For RPM limits: use exponential backoff with jitter. If the provider returns a Retry-After header, read it — don’t hardcode a backoff. For TPM limits: estimate tokens per request before sending using len(prompt) / 4 as a rough chars-to-tokens ratio for English, and track running consumption in a leaky bucket with 10% headroom. After 100 requests, rounding errors compound to 5–8%; the headroom absorbs this drift before you hit a limit mid-batch.

Think of your electricity provider’s soft cap: they don’t cut your power the instant you exceed your plan limit, they let you run briefly over, then throttle. LLM TPM limits work the same way — you get brief bursts above the cap, then a 429 tells you to slow down. Rate limit retries require both a backoff strategy and a token budget model; one without the other either wastes time or exhausts your quota.

Provider outages: the circuit break class

A circuit breaker exists for one reason: to stop amplifying a provider’s problem into your own. When a provider is experiencing a sustained outage, each retry you send is a request that will fail, occupy a connection slot, and delay your caller. The circuit breaker cuts this amplification loop before it becomes a cascade.

Three states: closed (normal operation), open (failure threshold crossed — all requests fail fast without hitting the provider), half-open (probe state — send one request to check recovery). Threshold configuration for LLM providers: open after 5 consecutive 5xx errors or a 50% failure rate over a 60-second rolling window. Wait 30 seconds in open state before moving to half-open. Require 2 consecutive successes to close.

What I didn’t expect: half-open state is where most implementations get hurt. The probe fires one request. If that request hits a still-degraded provider and takes 30 seconds to time out, the probe blocks the state machine for 30 seconds. The fix: the half-open probe must use an aggressive timeout — 3 seconds, not 30 — because a healthy provider responds fast. Circuit breaking is not a retry with a longer delay; it is a different state machine that requires its own timeout, threshold, and probe logic.

Streaming disconnects: the reconnect class

Most modern LLM APIs return responses as server-sent events: a stream of delta chunks. The stream can disconnect mid-response for transport reasons entirely unrelated to the provider’s health — a network timeout, a TCP RST, a load balancer timeout. A mid-stream disconnect is not a provider error; it is a transport error.

Most LLM providers don’t support resume-from-offset. If the stream disconnects mid-response, you must restart the full request — expensive for long-generation tasks like 2,000-token code generation. The mitigation is to checkpoint the partial response: as each delta arrives, append to an in-memory buffer. On disconnect, the partial buffer is the recoverable state; deliver it if the caller accepts partial responses, restart the full request only if they require completeness.

Recording a phone call where the line drops halfway through: you can’t resume from the dropout, you have to call back. But if you took notes during the call, you know what was said and can start the second call from where the first left off. Streaming checkpoints are your notes — the partial response is valuable data, not an error to discard. Streaming disconnects require a distinct handling path from request failures.

The decision table: error code to action

The error.type field, not the HTTP status code, is the definitive signal. Provider error taxonomy is also not standardized: OpenAI and Anthropic use similar structures (error.type, error.message) but different type strings. A production-grade LLM client needs a normalization layer that maps provider-specific error codes to your own internal taxonomy before the retry/circuit-break/fallback decision logic runs.

A production-grade LLM client library needs a normalization layer that maps provider-specific error codes to your own internal error taxonomy before any decision logic runs. Without this layer, your circuit breaker conditions are written in provider-specific strings — which change when providers update their APIs.

Putting it together: a minimal reliability layer

The reliability layer has three components that run in sequence. Before sending: token budget check (do I have TPM headroom?), then circuit breaker state check (is the provider marked degraded?). After receiving the response: error classifier (which of the four buckets?). The classifier runs before any retry logic — fail-loud errors must exit immediately.

After classification: retry schedules a re-attempt with backoff; circuit break events increment the breaker counter; fallback switches the provider; fail loud propagates the error to the caller with a structured message. Every request through the reliability layer should emit a tracing span with: provider, model, error_class, attempt_number, token_count_estimate. Without this tracing contract, debugging reliability incidents in production is guesswork.

Think of a mail sorting room with four chutes. The value is the sorter, not the individual chutes — nothing bypasses the sorter. The reliability layer’s value is not the retry logic itself; it is the upfront classification that prevents the wrong logic from running on the wrong error. Getting this ordering right is what separates a reliability layer that improves stability from one that amplifies failures.
