Day 26 — Fine-Tuning vs RAG vs Prompting — Infra Cost View

Staff engineers pick the cheapest path that meets SLO — not the coolest paper

AS
Akshant Sharma
AI Learning · Day 26 of 150
June 11, 2026
12 min read

Every six months there is a new paper arguing that fine-tuning beats RAG on some benchmark, followed immediately by a paper arguing the opposite. Neither paper includes an AWS bill. The conversation engineers actually need is not “which technique is superior” but “what does each technique cost to operate at my traffic volume, and does it meet my quality SLO?” Those are infrastructure questions, not research questions.

I learned this framing the hard way. At Walmart Labs, we evaluated whether to fine-tune an anomaly detection model for our IoT sensor pipeline or use a fixed retrieval strategy with a frozen base model. The fine-tuning team produced genuinely better F1 scores. The infra team produced a monthly GPU cost estimate that was four times the saving from the better F1 score. We went with retrieval. The cost spreadsheet was not a creative constraint — it was the decision.

This post builds the cost comparison from scratch. Prompting adds zero infrastructure. RAG adds a retrieval layer. Fine-tuning adds GPU compute, model storage, and a retraining pipeline. Each is justified at a different traffic volume and quality threshold. I’ll connect this to LensAI’s resolved_model_id field, which is how you measure which strategy is actually running in production and what it is costing you.

DS analogy — the restaurant kitchen
A restaurant facing a new cuisine on the menu has three options. Train the existing chef from scratch on the new dishes (fine-tuning): high upfront cost, permanent capability uplift, expensive if the menu changes next month. Give the chef a binder of reference cards to consult during service (RAG): low upfront cost, requires a good indexing system, adds a few seconds to each dish. Hire a specialist chef who already knows the cuisine (a better base model with a richer prompt): you pay per hour, no training investment, but the specialist is expensive at volume. The cost/quality crossover between these three is the decision. The restaurant that defaults to training every chef on every new dish will eventually go bankrupt.

Prompting: zero infra, max flexibility

Prompting is the technique with no infrastructure footprint. You pay the per-token API rate, nothing more. The model is the same one you were already calling; you are just giving it richer instructions. For a surprising fraction of tasks — entity extraction, classification, summarization, translation — a well-crafted prompt on a capable base model meets the quality SLO without any additional machinery.

The infrastructure cost of prompting is entirely in token economics. A prompt that provides ten few-shot examples to steer the model costs ten examples × their token length on every request. At 500 input tokens per request, 100k requests per day, and $2.50 per million input tokens on gpt-4o, that is $125/day. Add prompt caching (covered in Day 25) and the effective rate drops to roughly $12.50/day for the cached portion. Prompting’s cost scales linearly with request volume; there are no fixed infrastructure costs.

The quality ceiling for prompting is real. Tasks that require knowledge the base model was never trained on — your internal API documentation, your company’s product catalog, last week’s incident reports — cannot be solved by prompting alone, because the information is not in the model’s weights. That is the boundary condition where RAG becomes relevant.

RAG: when the knowledge is external

Retrieval-Augmented Generation (RAG) is the pattern of fetching relevant documents from an external store and injecting them into the prompt before calling the model. The model sees the retrieved context as part of its input and reasons over it as if it were always there. From the model’s perspective, RAG is just a longer, better-informed prompt. From the infrastructure perspective, RAG is an entirely new system you now have to build and operate.

The RAG infrastructure tax has four line items. First, a vector database: embedding every document and storing the vectors. Pinecone’s hosted service costs roughly $70/month for 1M 1536-dimension vectors (OpenAI text-embedding-3-small format). Qdrant self-hosted on a $50/month VM is cheaper but requires your time. Second, an embedding call for every query at inference time: at $0.02 per million tokens and 100 tokens per query, that is $0.002 per 1000 queries, essentially free. Third, the retrieval operation itself: vector similarity search is fast (under 10ms at 1M scale) but adds one network round trip per request. Fourth, the latency tax: P99 latency for a retrieval-augmented request is the retrieval P99 plus the model P99, not the model P99 alone.

RAG also requires an indexing pipeline. Every time the knowledge base changes — new documents added, old documents updated — the vectors must be recomputed and the index updated. For a product catalog that changes daily, the incremental reindex is a background job you now own. For a static document set that never changes, the maintenance cost is near zero. The “RAG is simpler than fine-tuning” claim is true only when the knowledge base is mostly static.

Fine-tuning: when nothing else works

Fine-tuning is the technique of updating a model’s weights by training it on your domain-specific examples. The result is a model that has absorbed your patterns into its weights — it no longer needs them in the prompt, which means shorter prompts, lower latency, and sometimes better quality on narrow tasks. The tradeoff is that the training data must be prepared, the fine-tune run must be paid for, and the resulting model must be served and maintained.

The cost of a single fine-tune run on OpenAI’s API is approximately $8 per million training tokens for gpt-4o-mini. A dataset of 10,000 examples at 1,000 tokens each is 10M tokens, costing roughly $80. A larger dataset of 100k examples at the same length costs $800. These are one-time costs per run — but “one-time” is optimistic. A fine-tuned model trained on data from six months ago starts to drift as the world changes. Customer support models need retraining when products change. Code generation models need retraining when internal APIs evolve. The actual cost is the training cost amortized over the useful life of the model, which is often shorter than teams expect.

The serving cost is the more important number. A fine-tuned model requires dedicated hosting. OpenAI charges $0.0025 per 1K tokens for fine-tuned model inference on gpt-4o-mini, which is roughly double the base model rate. If the fine-tuning benefit is shorter prompts (eliminating few-shot examples), the per-token rate increase may be offset by lower token volume per request. Whether the math works out depends on your specific prompt structure — and most teams do not run this calculation before starting fine-tuning.

The four-question decision framework

Before starting any fine-tuning project, I work through four questions in order. The answers determine which technique is justified.

Question 1: Does the task require knowledge that is not in the base model? If yes, RAG or fine-tuning. If no, prompting first. Most teams jump past this question and assume their task is hard because it feels domain-specific. Concrete test: write a zero-shot prompt and measure quality. You will be surprised how often gpt-4o-mini passes the bar with a well-crafted instruction.

Question 2: Is the missing knowledge static or frequently changing? If static, fine-tuning is viable. If it changes faster than you can retrain (weekly or faster), RAG is the only option that stays current. The fine-tuned model’s knowledge is frozen at training time; the RAG index can be updated incrementally.

Question 3: What is the monthly cost crossover between RAG and fine-tuning? RAG has a fixed infrastructure cost (vector store) plus a per-query retrieval cost. Fine-tuning has a periodic training cost plus a higher per-token serving cost. The crossover point depends on traffic volume. At low volume, RAG is cheaper because the fixed cost is amortized across fewer requests. At high volume, a well-tuned fine-tuned model with shorter prompts may win on per-request economics. Compute the crossover at your actual traffic volume before deciding.

Question 4: Do you have enough labeled examples to fine-tune reliably? OpenAI recommends at least 50–100 examples to see any improvement, and several hundred to see consistent gains. If you have fewer than 100 labeled examples, fine-tuning is gambling. RAG or few-shot prompting is the right answer until you have enough data.

The cost numbers at real traffic volumes

Let me make the comparison concrete at three traffic levels: 10k, 100k, and 1M requests per day. I am using a task that requires domain-specific knowledge: answering questions about an internal product catalog with 500k entries.

Technique10k req/day100k req/day1M req/day
Prompting (few-shot)$45/mo$450/mo$4,500/mo
RAG (Qdrant + gpt-4o-mini)$120/mo$250/mo$1,800/mo
Fine-tune (gpt-4o-mini)$95/mo + $80 run$310/mo + $80 run$2,200/mo + $80 run

At 10k requests/day, prompting wins on cost but fails the knowledge requirement, so RAG is the practical choice despite the higher base cost. At 100k requests/day, the fixed RAG cost is amortized and RAG becomes competitive with fine-tuning. At 1M requests/day, RAG is cheapest because the short retrieved-context prompts are highly cache-friendly. Fine-tuning’s advantage — shorter prompts without few-shot examples — appears only when the serving volume is high enough to amortize the per-run training cost and the prompt shortening outweighs the higher per-token serving rate.

The latency story is different from the cost story. Fine-tuned models produce faster responses because shorter prompts mean less prefill compute. At 1M requests/day with a P99 SLO of 500ms, the prompting approach with ten few-shot examples at gpt-4o-mini rates costs more tokens per request than a fine-tuned model with no examples. If your SLO is the binding constraint rather than cost, fine-tuning may be justified even when RAG is cheaper.

Cost attribution in LensAI via resolved_model_id

Knowing which technique is cheapest in theory is only half the problem. In production, you need to know which technique is actually running and what it is costing. This is where LensAI’s event schema earns its keep. Every inference request that passes through the LensAI ingestion pipeline carries a resolved_model_id field: the actual model identifier used, not the model the caller requested.

For a RAG-augmented request, resolved_model_id is gpt-4o-mini (the generation model), but the total cost also includes the embedding call that drove the retrieval. The schema captures this as a separate event with operation: "embed" and the same request_id. A ClickHouse query that joins on request_id and sums across all operation types gives the true cost per user request, not just the generation cost.

SELECT
  resolved_model_id,
  operation,
  avg(prompt_tokens + completion_tokens)  AS avg_tokens,
  count()                                  AS requests,
  sum((prompt_tokens - cached_tokens) * input_price_per_token
      + cached_tokens * cache_price_per_token
      + completion_tokens * output_price_per_token) AS total_cost_usd
FROM lensai.inference_events
WHERE toDate(ts) = today()
GROUP BY resolved_model_id, operation
ORDER BY total_cost_usd DESC

If you are A/B testing RAG versus prompting via distributed-flagd’s retrieval_strategy flag, the flag_variant field on the event lets you slice this query by variant. Day 26’s benchmark work for distributed-flagd provides the flag evaluation QPS numbers that prove the flag system adds under 0.2ms to each request — invisible against the 200ms+ model latency.

The flag_variant + resolved_model_id combination gives you a cost ledger split by technique. You can see in real time whether the RAG variant is costing more per request than the prompting variant, and whether the quality delta (measured by downstream evaluation events in the same pipeline) justifies the extra cost. The infrastructure cost comparison that took a spreadsheet and two days of estimation pre-deployment now takes a single ClickHouse query post-deployment. That is the measurement loop that makes the cost framework actionable rather than theoretical.
