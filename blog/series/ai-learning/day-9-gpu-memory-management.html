AI Learning · Day 9 of N

I hit an OOM deploying a 7B model on an A10G at batch size four. The model loads fine. A single request completes. Two requests — fine. Three — fine. Four requests in the batch and PyTorch throws CUDA out of memory without a useful breakdown of where the 24 GB went.

The instinct was to assume the model was too big. It was not. The 7B model in FP16 weighs 14 GB. The A10G has 24 GB. That leaves 10 GB — which sounds generous until you account for the other tenants sharing that VRAM. Activations scale with batch size. The KV cache grows with sequence length times batch size. CUDA itself reserves workspace. And during load_state_dict, the weights briefly exist twice in memory. The OOM was not a model-size problem. It was a capacity-planning problem — four tenants competing for a fixed budget, with no visibility into who was consuming what.

That framing connects two things I have already written about. Day 1 described the KV cache as a memory-bandwidth problem — each decode step reads the entire cache, and bandwidth determines tokens per second. Today flips the lens: the KV cache is also a capacity problem because it grows linearly with context length and batch size, competing with everything else for a fixed VRAM envelope. Day 6 covered quantization as a way to shrink the weight footprint — which buys headroom for the other tenants. This post maps the full layout so the tradeoffs connect.

The four tenants of VRAM

GPU memory is a single address space shared by four categories of allocation. They are not managed by separate allocators or isolated by quotas — they coexist in one pool, and the first allocation that pushes the sum past the hardware limit triggers OOM. The tenants:

At batch size one, the activations are small and the KV cache holds one sequence — total consumption is around 16–17 GB, leaving comfortable headroom. At batch size four, activations quadruple and the KV cache holds four sequences. The sum pushes past 22 GB, leaving less than 2 GB of headroom on a 24 GB card. One slightly longer prompt — a 3k-token context instead of 2k — and the budget overflows.

The capacity-planning parallel is exact. In a database system, you track working set memory, connection pool overhead, OS buffers, and page cache — and you size the instance so the sum stays below the limit with headroom for spikes. GPU memory is the same discipline applied to a different hardware surface. The problem is that most serving frameworks report only total VRAM utilization, not per-tenant breakdown — so you cannot tell whether you are weight-bound, activation-bound, or KV-cache-bound until you hit OOM and start guessing.

Weight loading — the transient 2× cliff

Loading a model is not a single allocation. The standard PyTorch pattern — model.load_state_dict(torch.load(path)) — creates the weights in CPU memory, then copies them to GPU. But before the copy completes and the CPU-side tensors are freed, both copies exist simultaneously. For a 7B FP16 model, that is 14 GB on GPU plus 14 GB in the process of being transferred — a transient peak of 28 GB, which exceeds the A10G's 24 GB.

The workaround is well-known: device_map="auto" in Hugging Face, or torch.load(path, map_location="cuda") to load directly onto GPU. But the failure mode is subtle. If you are deploying with a container that also runs a health-check model or a tokenizer warm-up before the main model loads, the memory timeline has a spike that exceeds steady-state by nearly 2×. Sizing your GPU for steady-state means the startup crashes.

Day 6 showed that INT8 cuts the weight footprint to 7 GB. That changes the transient story too — the load peak drops to 14 GB, well within budget. So quantization is not only a steady-state optimization; it is a startup-reliability optimization. The same decision that saves money at serving time also prevents OOM at boot time.

One practice I adopted after debugging this: always check torch.cuda.max_memory_allocated() after model load, not just during inference. The max-memory watermark captures the transient peak. If the watermark is within 2 GB of the hardware limit, any increase in model size or batch configuration will OOM at startup before a single request is served.

Activations — the per-request cost nobody quotes

Activations are the intermediate tensors computed during the forward pass. Every layer produces an activation tensor that gets consumed by the next layer — and at FP16, these tensors are large. For a typical transformer layer processing a batch of sequences, the activation memory scales as:

activation_bytes ≈ batch_size × seq_len × hidden_dim × num_layers × 2 bytes × factor

The factor depends on which intermediate tensors the framework keeps alive simultaneously — typically 2–4× the single-layer size because attention and FFN intermediates overlap in the computation graph. For a 7B model (hidden_dim=4096, 32 layers) processing batch=4 at seq_len=2048, the activation footprint is in the 2–6 GB range depending on the framework's memory strategy.

The critical difference between activations and weights: weights are constant, activations scale linearly with batch size. Doubling the batch doubles the activation memory. This is why OOM happens at batch=4 but not batch=2 — the weight and overhead tenants stay fixed, but activations jump by enough to cross the threshold.

Activation checkpointing — trading compute for memory

The standard mitigation is activation checkpointing (gradient checkpointing in training contexts, but the technique applies to inference too). Instead of keeping all layer activations alive for the backward pass or for later reuse, you recompute them on demand. This trades compute (rerunning layers) for memory (not storing their outputs).

In inference serving, the tradeoff is: keep all activations alive and maximize throughput at the cost of VRAM, or checkpoint aggressively and serve higher batch sizes at the cost of extra FLOPs per request. The decision depends on whether you are VRAM-bound or compute-bound — and on a 24 GB card serving a 14 GB model, you are almost certainly VRAM-bound, which means checkpointing buys you real headroom.

The analogy to traditional systems: activation checkpointing is the GPU equivalent of swapping hot data to disk when memory pressure is high. You accept higher latency per request in exchange for the ability to serve more concurrent requests. The same capacity-vs-latency tradeoff you make when choosing between fewer fast instances and more slow instances — applied at the CUDA allocator level.

KV cache revisited — from bandwidth to capacity

Day 1 framed the KV cache as a bandwidth problem: at decode time, the entire cache is read once per token generated, so memory bandwidth determines tokens per second. That analysis was about throughput. Today the question is different: how much VRAM does the KV cache actually consume, and how does that consumption interact with the other tenants?

The formula for KV cache size is mechanical:

kv_bytes = 2 × num_layers × num_kv_heads × head_dim × seq_len × batch_size × bytes_per_element

For a 7B model (32 layers, 32 KV heads, head_dim=128) in FP16, a single sequence at 2048 tokens costs:

2 × 32 × 32 × 128 × 2048 × 2 bytes = ~1.07 GB per sequence

At batch=4, that is ~4.3 GB for KV cache alone. Combined with 14 GB of weights and 1 GB of CUDA overhead, you are at 19.3 GB before activations even enter the picture. This is why the batch-size cliff is so sharp — each additional sequence in the batch adds a full gigabyte of KV cache on top of the linear activation growth.

RAG workloads intensify this problem. When you retrieve 5–10 document chunks and prepend them to the context window, the effective sequence length jumps from a short user query (maybe 200 tokens) to 2000–4000 tokens of retrieved context plus the query. The KV cache balloons by an order of magnitude compared to a bare query — and this happens on every request, not just occasionally. Day 8 described RAG as a five-stage pipeline; today's lens adds that stage four (retrieval) directly inflates the KV cache tenant in stage five (generate). Optimizing retrieval top-k is not just about prompt cost — it is about VRAM pressure on the serving GPU.

The batch-size cliff

The OOM at batch=4 is not a gradual degradation — it is a cliff. At batch=3, total VRAM sits at ~21 GB (comfortable). At batch=4, it jumps to ~23.5 GB (barely fits). At batch=5, it exceeds 24 GB and crashes. There is no graceful warning, no backpressure signal, no "running low" state. You go from serving requests to a hard crash with one additional concurrent sequence.

The connection-pool analogy makes this intuitive. In a web server, each connection holds memory for buffers, session state, and stack frames. You can serve N connections with M megabytes of RAM — but the (N+1)th connection that pushes past the OS limit does not get a "slow" response; it gets a connection-refused error. The batch-size cliff is the GPU equivalent of hitting max_connections. One more request and the process dies.

The operational consequence: you need to know your batch-size ceiling before production traffic discovers it. The ceiling is not a model property — it is a function of the model, the GPU, the sequence length distribution, and the serving framework's memory strategy. Change any one variable and the ceiling moves. A model that safely runs batch=8 on 2k-token queries might OOM at batch=3 on 8k-token queries because the KV cache and activations scale with sequence length.

What I wish existed: a pre-flight memory estimator that takes (model, GPU, max_seq_len, target_batch_size) and returns "fits" or "will OOM at step N." The arithmetic is deterministic — the formula above is not approximate. But no standard serving framework surfaces this as a first-class API. You either run the empirical test (start the server, send concurrent requests, see if it crashes) or you do the arithmetic by hand and hope your accounting of the overhead tenant is correct.

Day 6 vs Day 9 — precision vs memory layout

Day 6 covered quantization — reducing bytes per parameter to shrink the weight tenant. Today covers the full memory layout — all four tenants and how they interact. The distinction matters because teams often reach for quantization as the only GPU memory lever, when the actual bottleneck might be the KV cache or activations, not weights.

The correct sequence is: quantize first (Day 6) to right-size the weight tenant, then plan the remaining VRAM budget (today) across activations, KV cache, and overhead for your target batch size and sequence length. Doing it in reverse — trying to fit batch=8 with FP16 weights and hoping activation checkpointing alone saves enough — usually fails because 14 GB of weights leaves too little room for anything else.

LensAI — proposed GPU memory observability fields

Today in infra-ai-streaming: InferenceEvent carries latency_ms, token counts, and cost_usd. When a serving pod hits memory pressure or OOMs, the dashboard shows the pod restarting — but cannot show why. Was it a KV cache spike from a long-context request? Activation growth from a batch-size surge? A new model version with larger embeddings? Without per-tenant memory telemetry, the root-cause investigation is guesswork.

The exporter polls torch.cuda.memory_allocated() and torch.cuda.max_memory_allocated() per forward pass, attaches batch size from the scheduler, and enriches the InferenceEvent before publishing. On the Grafana side: a VRAM utilization heatmap by pod, a time-series of batch_size_current overlaid with gpu_vram_used_bytes, and an alert when gpu_vram_peak_bytes crosses 90% of hardware capacity — the "approaching the cliff" early warning.

The gap these fields close: today, when a pod OOMs and restarts, the post-mortem says "memory pressure." With per-tenant fields, the post-mortem can say "KV cache grew to 6 GB because three 8k-token RAG requests landed on the same pod within the same batch window." That specificity turns a generic "need bigger GPU" conclusion into an actionable "cap max_seq_len at 4k or shard long-context requests to dedicated pods" recommendation.

Takeaway — memory is a capacity plan

GPU memory management is not a model-tuning exercise. It is capacity planning — the same discipline that sizes database instances, sets connection-pool limits, and provisions Kafka partitions. The budget is fixed by hardware, the tenants are known, and the arithmetic is deterministic. The only variable is visibility: do you know how much each tenant is consuming before the OOM tells you?

A GPU's VRAM is a fixed-size connection pool shared by four tenants with no isolation. The batch-size cliff is not a bug — it is the capacity limit you failed to measure.

The sequence that now makes sense to me: Day 6 quantizes the weight tenant to buy headroom. Today maps the headroom across activations, KV cache, and overhead for a target batch size. The result is a deployment configuration that you can reason about before traffic arrives — not a prayer that the first spike will not OOM the pod. Next, I want to understand how serving frameworks actually schedule requests within that memory budget — the runtime that decides which sequences get batched, evicted, or queued when VRAM is tight.
