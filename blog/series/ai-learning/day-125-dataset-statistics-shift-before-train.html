Day 125 — Dataset Statistics — Shift Before Train

"Manifest JSON captures distributions" was the whole ticket. "Manifest JSON captures distributions." That's the entire hook this ticket gave me. It doesn't say which distribution matters, or why capturing one in a JSON file is worth a day's work when the dataset it describes hasn't changed at all — working that out is the actual content below.

A File That Changes Nothing About the Data

dataprep dashboard is unusual among this week's subcommands in that it writes zero new training rows. Day 122's scrub drops rows, Day 123's dedup drops more, Day 124's split partitions what's left — each of those steps changes what a downstream trainer will actually see. Today's manifest reads the same rows Day 123 already wrote and produces one summary file that no trainer reads back.

That makes it easy to undervalue: a step that touches nothing and gets read by nobody automated looks like the one you could skip under deadline pressure. What it actually buys is a number that's otherwise invisible until a training run has already spent compute discovering it — a label's real share of the dataset, at the granularity a single gradient step will actually see it.

So what: the manifest's value isn't in what it changes, it's in what it makes visible before the far more expensive step — an actual training run — would have revealed the same fact anyway, just after paying for the compute to find out.

The Candy Jar Mechanism

DS analogy — a jar's total mix ratio vs. what one scoop actually contains
A jar of mixed candy, shaken and weighed, might come out an honest 90% wrapped candy and 10% gumballs by count — a true, useful fact about the whole jar. That fact tells you almost nothing about what a single scoop contains: at ten candies per scoop and a 10% share, plenty of scoops come up with zero gumballs, purely from how few of them there are relative to scoop size. The jar's label (the aggregate ratio) and a scoop's actual contents (what one grab experiences) are two different measurements of the same jar, and only one of them predicts what any given handful looks like. dashboard.Build computes the jar's label — label_distribution's task_type shares, across the whole export. It doesn't, and can't, tell you what one training batch will draw. Reading the label is still the right first move, because a jar labeled "10% gumballs" tells you in advance that a ten-candy scoop is exactly the wrong size to reliably get one — something you'd otherwise only learn by scooping.

That's the generalizable point: an aggregate distribution and a per-draw distribution are related but not identical measurements, and knowing the first lets you reason about the second before you ever draw.

So what: a manifest that reports the dataset's overall shares isn't answering "what will one batch look like" directly — it's giving you the input to work that out yourself, for whatever batch size you're about to choose.

So what: the branch this diagram adds — checking label share against a threshold before training starts — is the one step a trainer that only logs aggregate loss has no equivalent of, because aggregate loss can't distinguish "every class is learning slowly" from "one class is never seen."

Why an Aggregate Judge Score Already Looked Fine

Every row in this pipeline already passed a judge-score threshold before Day 121's connector ever selected it, and Day 123's dedup pass already filtered the bottom quartile by quality. By the time a row reaches today's manifest, "is this a good dataset" already has a reassuring answer at the aggregate level — high average judge score, deduplicated, PII-scrubbed.

None of those steps look at task_type share at all. A dataset can pass every quality gate this pipeline has and still have one label sitting at a fraction of a percent, for the entirely mundane reason that the source system that generated these rows produced far more of one kind of request than another. Quality and balance are orthogonal properties — a row can be simultaneously high-quality and part of a badly underrepresented class, and every check before today's manifest only measures the first one.

So what: "the dataset looks clean" and "the dataset is balanced" are two separate claims, and a pipeline that only checks the first can ship a dataset that's fine in aggregate and broken for exactly the classes a manifest's label distribution would have flagged.

Measuring What a Rare Label Actually Gets Per Batch

Day 124's own post ran a mixed export — 3,000 support rows next to 40 codegen rows — and found codegen landing at roughly 1.3% of the total. That's a real number from this pipeline's own test run, not a synthetic one, so I used it here instead of inventing a fresh ratio: at that share, what does a single training batch actually see?

At a batch size of 32 — an ordinary choice for a LoRA fine-tune on a single GPU — two out of every three batches contain no codegen row at all. The model's codegen-relevant weights get a gradient signal roughly once every three steps, while every other task_type gets one on nearly every step. A per-class loss curve for codegen would look flat for long stretches not because the model has converged on it, but because it's barely being trained on it — and an aggregate loss curve, dominated by the majority class's steady progress, would show nothing unusual at all.

So what: "flat loss" and "converged" are not the same event, and the only way to tell them apart for a specific label is to already know that label's share — which is precisely the number the manifest computes before any of this is spent finding out empirically.

A dataset can be clean, deduplicated, and pass every judge-score gate this pipeline has, and still starve one label of gradient signal for a reason none of those gates were built to catch.

The Generalizable Lesson

The specific thing today's code does is bucket a training export by token count, script, and label. The transferable part is smaller and applies anywhere a fixed batch size draws from an unevenly distributed pool.

  1. An aggregate quality metric and a per-class representation metric answer different questions — a dataset can score well on the first and fail silently on the second, because nothing about "average judge score" constrains how any one label is represented.
  2. A rare class's real constraint isn't its row count in isolation, it's that count relative to batch size — the same 1.3% share is a non-issue at batch 128 and a near-starvation at batch 8, so the manifest's number only becomes actionable once you do the batch-size arithmetic yourself.
  3. A per-class training problem can be statistically invisible in an aggregate loss curve, because the majority class's steady progress dominates the average — if you only ever look at the aggregate, you only ever see what the majority class is doing.

Building a token histogram, a language mix, and a label distribution is a few hours of work against data that's already sitting in Parquet shards. Knowing which number in that file to check against your actual batch size, before day one of a training run instead of after day four of a flat loss curve, is the part the ticket's one-line hook didn't spell out.
