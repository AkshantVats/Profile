Day 109 — Sensitivity Tuning — Precision/Recall Tradeoff

Three preset names — strict, balanced, noisy — are a proxy for a number almost nobody wants to pick directly. Underneath, every one of them is the same multiplier on the same threshold.

Today's ticket adds three named presets to a CUSUM chart, and each one turns out to be exactly one number: a multiplier on h. A reader's fair first question is why not let a tenant pick h directly — and the answer is that almost nobody wants to type "multiply the decision threshold by 1.8," even when that is precisely what they mean.

What h Actually Controls

A CUSUM chart accumulates evidence across consecutive windows into a running statistic, and h is the line that statistic has to cross before the chart pages anyone. It is not a threshold on one sample — it is a threshold on the sum of deviations the chart has seen since its last reset.

Raise h and the chart demands more accumulated evidence before it acts. Fewer false alarms on ordinary noise, but a genuine sustained shift also takes longer to cross the line and get flagged.

So what: h is not "how big a shift counts as drift" — that is a different parameter's job, and keeping the two separate is the whole design of today's fix.

Precision/Recall, Made Concrete

A strict tenant runs at h × 0.6: less accumulated evidence required, so a real shift gets caught sooner. The cost is a chart that also reacts sooner to ordinary noise — higher recall, lower precision.

A noisy tenant runs at h × 1.8: more evidence required before paging, tuned for a segment whose own baseline naturally swings wider than most. The cost is a real shift sitting unflagged longer — higher precision, lower recall on a small shift.

Neither setting is more correct than the other. They are calibrated to what a false alarm costs a given tenant against what a missed drift costs the same tenant, and that cost ratio is not the same number for every tenant on the fleet.

Why h, Not k

k sets the size of shift the chart is tuned to catch — DESIGN.md frames it as "half the shift size" the design targets, a property of the underlying signal itself. h sets how much accumulated evidence is required before acting on a shift of that size.

Scaling k per tenant would quietly redefine what counts as drift, tenant by tenant — two segments could see the identical shift and disagree on whether it was even a shift worth counting. Scaling h only changes how cautious the chart is before acting; every tenant's chart still agrees on what a shift is.

A Retry Policy, Not a Different Algorithm

DS analogy — a backoff multiplier, not a different retry loop
A sensitivity preset is a retry policy's backoff multiplier, not a different retry algorithm. Every tenant runs the identical CUSUM math — the same accumulation rule, the same warm-up gate, the same post-alarm cooldown — and only the threshold that decides "enough evidence has accumulated" changes. An aggressive retry policy and a conservative one share one retry loop and differ only in how long they wait between attempts; neither one is running a smarter retry. A preset works the same way: it does not make the chart cleverer about any one tenant, it only changes how patient the identical chart is told to be.

So what: the presets are not three different drift detectors wearing different names — they are one detector, three settings on the same dial.

The Same Drop, Three Verdicts

The ticket's integration test injects a 15% relative drop in judge score — a baseline mean of 80 falling to 68 — sustained across six consecutive hourly windows, and evaluates the identical sequence three times, once per preset.

strict reaches an alarm inside that six-hour window. balanced, DESIGN.md's own default, does not — it is still accumulating evidence when the window ends. noisy is further still from its threshold.

So what: this is not a hypothetical tradeoff argued from first principles — it is the same drop, the same six hours, three genuinely different outcomes, purely as a function of one multiplier.

The Honest Limitation

A preset is a static label someone assigned by hand. Nothing here measures a tenant's actual volatility and proposes a preset automatically, and nothing re-evaluates the choice once it is made.

A tenant marked noisy whose traffic pattern quietly settles down keeps that same wide tolerance long after it stopped earning it — the chart is just as patient with a real shift from that tenant as it was on day one. Say this plainly, the same posture Day 108's flat-line-at-zero limitation took: a static default is a real gap, not a rounding error.

Same root cause, two vocabularies: a fleet built from segments with genuinely different baselines cannot be served honestly by one number. Solve it once, as a tunable multiplier chosen per segment, and the fix generalizes to a request-rate alert and a control chart alike.

A preset is not a smarter detector. It is an admission that one threshold was never going to be honest about every segment at once.

So what: today's actual contribution wasn't a new statistic — every tenant still runs the exact CUSUM math Day 105 wrote. It was recognizing that "one h for everyone" was a default that happened to be easiest to write down first, not a neutral one, and that fixing it costs exactly one multiplier.
