Day 33 — Context Propagation in Polyglot Agents

When your Python orchestrator calls a Go tool, the trace_id has to travel with the HTTP request or the spans arrive as strangers. W3C TraceContext is the handshake that keeps them family.

The hook
A trace is only as strong as its weakest hop. One missing header and every downstream span becomes a root span — untethered, unsearchable, useless.

I had a debug session that took four hours to resolve. The agent was making calls to two downstream tools, both instrumented, both emitting spans. The trace UI showed three separate traces. There was no parent. There was no connection. The spans arrived like strangers who had never met, even though they were all part of a single agent turn that took twelve seconds end-to-end.

The fix was two lines of Go. Not a refactor, not a schema change — two lines that read the traceparent HTTP header and populated the parent span ID in the context. After that, all three trace fragments collapsed into one waterfall diagram that immediately showed a 9-second tail latency in the second tool call.

That story is the argument for context propagation. Today’s code — the Day 33 TraceForge Go SDK propagation.go — is the implementation of that argument.

The Problem With Shared Context Across Runtimes

Think of a distributed trace like a relay race baton. Every time a request crosses a service boundary — from your Python orchestrator to a Go weather tool, from the weather tool to a Rust cache layer — the baton has to be handed off explicitly. There is no shared memory. There is no implicit thread-local storage that crosses the network. If you don’t pass the trace ID in the request, the next service starts a brand-new race.

Single-language systems hide this problem. When everything runs in Python and you use OpenTelemetry’s context module, the framework propagates trace context automatically through HTTP middleware. You instrument once and forget. Polyglot systems — where the orchestrator is Python, tools are Go microservices, and the cache layer is Rust — expose the seam. Each language has its own tracing SDK. Each SDK lives in its own process. The only shared medium is the HTTP request headers.

So the problem reduces to a protocol question: what exactly goes in the header? What format? What fields? Who writes it, who reads it, and what happens when you mix a Python writer with a Go reader?

W3C TraceContext: A Standard Handshake

The W3C TraceContext specification (Recommendation since 2021) answers that protocol question with two headers: traceparent and tracestate. The first carries the essential identifiers. The second carries vendor-specific metadata and is optional.

traceparent is the one that matters for basic propagation. It looks like this:

traceparent: 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01

Four fields, hyphen-separated. Version (00, the only version defined so far). Trace ID (32 hex chars, 128-bit UUID without dashes). Parent span ID (16 hex chars, 64-bit). Flags (01 means “sampled”, 00 means “not sampled”).

The trace ID is the baton. It is generated once — by the first service in the chain, the one that starts the root span — and every subsequent service copies it unchanged. The parent span ID changes at each hop: it is the span ID of the calling service, telling the called service “you are a child of this span.”

What makes W3C TraceContext the right choice for polyglot agents specifically is that every major tracing SDK already implements it. OpenTelemetry Python propagates it. OpenTelemetry Go reads it. Jaeger supports it. Datadog supports it. If you emit W3C-format headers, any compliant receiver picks them up without negotiation.

The Header Format, Field by Field

Let me walk through the format concretely, because getting it wrong is easy and the failure mode is silent — no error, just a broken parent-child relationship that shows up as two separate traces in your dashboard.

Version  Trace ID (128-bit)                   Parent Span ID    Flags
  00  -  4bf92f3577b34da6a3ce929d0e0e4736  -  00f067aa0ba902b7  -  01

The trace ID must be exactly 32 lowercase hex characters. UUID v4 with dashes stripped works perfectly: 4bf92f35-77b3-4da6-a3ce-929d0e0e4736 becomes 4bf92f3577b34da6a3ce929d0e0e4736. The spec is strict about this — uppercase is non-conforming and some receivers will reject it.

The parent span ID must be exactly 16 lowercase hex characters. This is where I hit a subtle bug in early implementations: Go’s uuid.New().String() returns a 36-char UUID with dashes, and stripping the dashes gives 32 chars — valid for a trace ID, too long for a span ID. The fix is to take the first 16 chars of the raw UUID bytes, not the string. The Day 33 SDK uses uuid.New().String() and then takes the first 16 hex chars, which matches the 64-bit span ID requirement.

The flags byte is a bitmask. Bit 0 is the “sampled” flag. When set to 01, downstream services know to record this trace. When 00, they know to skip it (for sampling). For agent tracing, where you want to capture everything, hardcoding 01 is correct.

Inject: Stamping the Outbound Request

Injection is the write side of propagation. Before you make an outbound HTTP call, you read the active span from the context and write its trace ID and span ID into the request headers. The called service will find those headers and use them to set its own parent span ID.

Here’s what InjectTraceContext does in the Day 33 Go SDK:

// propagation.go
func InjectTraceContext(ctx context.Context, h http.Header) {
    s := SpanFromContext(ctx)
    if s == nil {
        return
    }
    h.Set("traceparent", fmt.Sprintf("00-%s-%s-01",
        cleanID(s.TraceID),
        cleanID(s.SpanID)[:16],
    ))
}

func cleanID(id string) string {
    return strings.ReplaceAll(id, "-", "")
}

The SpanFromContext call retrieves the active span from Go’s context.Context. If there’s no active span — maybe this is a standalone HTTP call outside any trace — the function returns early without writing any header. That’s the right default: do nothing rather than write a malformed header.

The cleanID helper strips UUID dashes before writing. The [:16] slice takes the first 16 hex chars of the span ID for the parent span ID field. The result is a spec-compliant traceparent that any W3C-compliant receiver can parse.

In the weather-calculator example from the Day 33 SDK, injection looks like this:

weatherCtx, weatherSpan := traceforge.StartSpan(rootCtx, "weather_api")
req, _ := http.NewRequestWithContext(weatherCtx, http.MethodGet,
    "http://localhost:8081/weather", nil)
traceforge.InjectTraceContext(weatherCtx, req.Header)
// req.Header["Traceparent"] is now set

The weather service receives the request, reads traceparent, and knows its parent span ID without any out-of-band coordination.

Extract: Picking Up the Thread on the Other Side

Extraction is the read side. The called service — the Go weather tool, the Rust cache layer — reads traceparent from the incoming request headers and populates its context with the parent trace ID and parent span ID.

// propagation.go
func ExtractTraceContext(ctx context.Context, h http.Header) context.Context {
    tp := h.Get("traceparent")
    if tp == "" {
        return ctx
    }
    parts := strings.Split(tp, "-")
    if len(parts) != 4 || parts[0] != "00" {
        return ctx
    }
    s := &Span{
        TraceID:      parts[1],
        ParentSpanID: parts[2],
    }
    return context.WithValue(ctx, contextKey{}, s)
}

The extract function is deliberately conservative. If the header is missing, it returns the context unchanged — the next StartSpan call will create a new root span, which is correct behavior for a service that receives uninstrumented requests. If the header is present but malformed, it returns the context unchanged for the same reason. Only a well-formed 00-*-*-* header updates the context.

After extraction, the next StartSpan(ctx, "my_operation") call reads the parent span ID from context and wires the new span as a child. The trace tree is intact.

The called service can’t trust that every caller will send a valid header. Extract must degrade gracefully — a missing header means “start a new root,” not “crash.”

What Breaks Without Propagation

Without propagation, each service starts its own root span. The trace UI shows three separate single-span traces instead of one waterfall. You can’t see that the weather call happened before the calculator call. You can’t see the total agent turn duration. You can’t correlate a user complaint (“the response was slow”) with a specific tool call.

The failure is silent in the instrumentation layer. No errors are thrown. Each service emits valid JSON spans. The spans land in your collector. They just don’t know about each other. Debugging feels like trying to reconstruct a conversation from three separate monologues with no timestamps.

The second failure mode is subtler: if the propagation is partial — inject in Python, but the Go service doesn’t extract — the spans still arrive as orphans even though the header was sent. This is why you need to verify both sides. The Day 33 SDK test suite includes TestExtractTraceContext and TestInjectNoOpWhenNoSpan precisely to catch this asymmetry.

Day 33’s Go SDK: propagation.go in Practice

The full propagation.go in the TraceForge Go SDK is 42 lines. Here is how the inject and extract pair works in the weather-calculator agent from the examples directory:

// Root span — represents the full agent turn.
rootCtx, rootSpan := traceforge.StartSpan(ctx, "agent_turn")

// Weather tool call — inject trace context into outbound request.
weatherCtx, _ := traceforge.StartSpan(rootCtx, "weather_api")
req, _ := http.NewRequestWithContext(weatherCtx,
    http.MethodGet, "http://localhost:8081/weather", nil)
traceforge.InjectTraceContext(weatherCtx, req.Header)
// req.Header["Traceparent"] = "00-{trace_id}-{weather_span_id}-01"

// Calculator tool call — same pattern, same trace ID.
calcCtx, _ := traceforge.StartSpan(rootCtx, "calculator")
req2, _ := http.NewRequestWithContext(calcCtx,
    http.MethodGet, "http://localhost:8082/calc", nil)
traceforge.InjectTraceContext(calcCtx, req2.Header)
// req2.Header["Traceparent"] = "00-{trace_id}-{calc_span_id}-01"

The weather service and calculator service each call ExtractTraceContext in their HTTP middleware. Their spans become children of the root span automatically. No out-of-band trace ID passing. No shared state. Just two header fields on two HTTP requests.

What’s satisfying about this design is that the interface is symmetric. InjectTraceContext(ctx, header) writes. ExtractTraceContext(ctx, header) reads. The Go service can play both roles: it extracts the parent from the incoming request and injects into its own outbound requests. The trace tree can be arbitrarily deep — Python calls Go calls Rust calls another Go service — and as long as each hop injects and the next hop extracts, the single trace ID threads through all of them.
