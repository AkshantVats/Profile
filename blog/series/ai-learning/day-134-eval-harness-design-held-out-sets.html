Day 134 — Eval Harness Design — Held-Out Sets

Never tune on the eval set. It's one sentence, everyone learns it early, and it still gets violated constantly — almost never on purpose, almost always because a pipeline changed and nobody re-checked whether the held-out set was still actually held out.

"Never tune on the eval set" is the first rule anyone learns about held-out data, and it survives as a rule precisely because it's so easy to break without noticing. Nobody sits down and decides to cheat. What actually happens is a pipeline gets re-run, a dataset gets refreshed, and a handful of rows that used to be safely on the training side end up close enough to the test side that the model has effectively seen the answer already.

The Sealed Envelope

DS analogy — what a locked hash actually buys you
A standardized exam board seals the answer key in an envelope before the exam, and writes the envelope's seal number into the official record right then, before anyone opens it. On grading day, the seal number in the record has to match the seal on the envelope in the room. If it doesn't, everyone knows immediately that the key was swapped at some point — not because anyone watched it happen, but because the numbers no longer agree.

A held-out test set works the same way once it has a hash locked into a registry: the hash is the seal number, computed once, at the moment the set is confirmed clean, and written down somewhere nobody scoring a model can quietly edit. Every later eval run recomputes the hash of whatever set it's about to score against and compares it to the locked value. A mismatch doesn't prove what changed — it proves something did, which is the whole point of a seal.

So what: a held-out set with no locked hash is just a file with a name that says "test." Nothing stops it from silently becoming a slightly different file next month, and nothing would tell you if it had.

How a Test Set Drifts Without Anyone Touching It

The FineForge pipeline this design sits at the end of makes the drift concrete. data-prep-pipeline splits rows into train and eval once, by a deterministic hash of each row's ID, stratified so every task type gets its own 90/10 split rather than one global split a large category could dominate. That split is correct the day it runs.

The pipeline keeps running, though. A later pull of production traffic can add new rows that never went through the original split logic at all — and nothing in a fresh pull checks whether one of those new training rows happens to be a near-duplicate of something already sitting in the eval bucket from months earlier.

The split fixed membership once. It said nothing about what gets added around it later.

So what: the leakage check has to run against the held-out set every time an eval fires, not once when the split was created — otherwise the seal number gets written down and then never checked again, which defeats the reason for sealing it in the first place.

Why a Hash, and Not Just a Filename

A filename or a version tag records intent — "this is supposed to be the v3 held-out set" — but it records nothing about content. A file can be silently overwritten, re-exported with a slightly different row count, or regenerated from a pipeline whose logic changed since the last run, all while keeping the exact same name. A reader trusting the filename has no way to know any of that happened.

A hash of the actual row contents — in this design, sha256 over the sorted list of row IDs the set contains — changes if and only if the actual membership changes. Two runs against a set with the same hash are provably scoring the same rows, no matter what either run happened to call the file. That provability is the entire reason to compute a hash instead of trusting a name: a name is a claim, a hash is a fact you can check.

So what: the registry to actually store this hash doesn't exist yet in this arc — it's Day 138's module. Reserving the field now, ahead of the table that will hold it, means the eval harness isn't redesigned the day that registry ships; it just gets somewhere real to write a value it was already computing.

What a Hash Doesn't Solve

A locked hash proves a test set didn't silently change between two eval runs. It says nothing about whether that test set was ever clean to begin with. A held-out set that had a leak baked in from day one will hash consistently every single time — the seal matches the envelope, and the envelope was compromised before it was ever sealed.

So what: hashing and leakage-checking are two different jobs, done in a specific order — check for leaks first, lock the hash of a set that has already passed that check, and only then treat a stable hash as meaning something. A hash locked before the leakage check runs is just a very precise record of a mistake.
