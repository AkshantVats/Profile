Day 129 — QLoRA — 4-bit Training

Quantized base weights save memory — but only because the 4 bits are spent where the weight distribution actually has values, the scale constants get quantized a second time, and none of it ever touches the LoRA adapter that's actually being trained.

6 min read

The bitsandbytes config in this week's training script is four lines: load in 4-bit, use the nf4 quant type, turn on double quantization, compute in bf16. Every one of those four lines is doing real work, and none of them is the obvious "just use fewer bits" you'd guess from the word "quantization" alone.

Four Bits Aren't Evenly Spaced

A naive 4-bit type gives you 16 possible values, evenly spaced across some range — call it -1 to 1 in steps of about 0.133. That's the right choice if your data is uniformly spread across that range. Neural network weights aren't: they cluster tightly around zero and thin out fast toward the extremes, closer to a bell curve than a flat line.

bnb_4bit_quant_type: "nf4" (NormalFloat4) spaces its 16 values by quantile instead of by fixed step — each of the 16 buckets is sized so roughly the same number of real weight values falls inside it. Buckets near zero, where most weights actually live, end up narrow and precise; buckets out at the tails, where almost nothing lives, end up wide because there's nothing there to lose precision on.

DS analogy — a tailor's size chart, not a ruler
A ruler marked every centimeter treats every measurement as equally likely, which is correct for measuring wood but wrong for sizing shirts: almost no one needs a 30cm or a 70cm collar, so a chart with evenly spaced sizes wastes most of its range on customers who don't exist and under-serves the crowded middle where most necks actually fall. A tailor's real size chart is denser exactly where the population is denser — more sizes clustered around the common range, fewer wasted on the rare extremes. NF4's 16 buckets are that chart applied to a weight distribution instead of a population of necks: precision spent where the values are, not spread evenly across a range most of which nothing ever occupies.

So what: "4-bit" tells you how many buckets you get, not where they're placed — and where they're placed is the entire reason NF4 beats a linear int4 at the same bit width on the same weights.

Quantizing the Quantizer

NF4 doesn't quantize a whole 70B-parameter tensor with one global scale factor; it quantizes in small blocks (64 values each), each with its own float32 scale constant, because a single global scale would be dragged around by the tensor's most extreme outlier and waste precision on every ordinary value. That's more accurate, and it has a cost nobody mentions on first pass: one float32 scale per 64 values is itself a real amount of memory once you're storing it for 70 billion parameters.

bnb_4bit_use_double_quant: true quantizes those per-block scale constants a second time — the scales themselves get bucketed the same quantile way the weights did. The QLoRA paper measures this saving at roughly 0.4 bits per parameter with no accuracy loss; at 70B parameters that's not a rounding error, it's on the order of 3.5GB freed up before a single adapter weight has been loaded.

So what: double quantization isn't a second, separate compression pass on the weights — it's compressing the bookkeeping the first pass needed, which is free precision to reclaim precisely because nobody was using it as precision in the first place.

Never the Adapter

Everything above applies to one tensor category only: the frozen base model's weight matrices, the ones nothing in this training run ever updates. The LoRA A/B matrices — the part actually being trained — and their AdamW optimizer state stay in bf16, full precision, for the entire run.

The reason isn't caution, it's arithmetic: the frozen base is read a fixed number of times per forward pass and never rewritten, so NF4's quantization error is a one-time, bounded cost paid once at load time. The adapter is read and rewritten every single optimizer step, and gradient descent needs an accurate signal about which direction reduces loss — quantizing a target that's actively moving would corrupt the very update the whole training run exists to compute.

So what: bf16 compute dtype in that four-line config isn't a leftover default, it's the explicit boundary marking where compression stops and training-sensitive precision starts.

The Arithmetic This Buys

Yesterday's post used a number without deriving it: a local-Llama-3-70B base in NF4 with double quantization needs roughly 35.9GB just for frozen weights, before any adapter, optimizer state, or activation memory. That number is 70{,}000{,}000{,}000 × 4.1 bits ÷ 8 ÷ 1{,}000{,}000{,}000 — 4 bits for NF4 itself, plus roughly 0.1 bits of residual overhead double quantization doesn't fully erase.

Compare that to storing the same 70B parameters in bf16 (2 bytes each, no quantization at all): roughly 140GB, before anything else loads. NF4 with double quantization isn't a modest optimization on top of that number — it's the difference between a model that fits on a single high-end GPU and one that structurally can't.

So what: every rank/alpha row in this arc's grid, and every VRAM check pkg/configgen.Recommend runs, is arithmetic layered on top of that ~35.9GB floor — it's the fixed cost the rest of this week's config decisions all get measured against.

What This Post Hasn't Verified

Every number above is arithmetic from the QLoRA paper's own published bits-per-parameter figures, not a measurement taken this week: there's no GPU in this environment to actually load a quantized local-Llama-3-70B and read real VRAM usage off it. bitsandbytes' 4-bit kernels are CUDA-only, so this week's training script imports it lazily and only exercises its actual quantization path outside this sandbox.

What is verified is the config itself — lora_trainer/config.py's bnb_config_kwargs() returns exactly the four values this post walked through, checked against a real loraconfig JSON shape in this week's test suite. The arithmetic is trustworthy; whether it holds up against an actual GPU is next week's question, not this one's.

So what: understanding why NF4 and double quantization work doesn't require running them, but knowing that is also the honest limit of what a design doc and a config generator can tell you before a real training run has happened.
