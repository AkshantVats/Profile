Day 89 — Product Thinking — Routers as Control Planes

RouteIQ is control plane; models are data plane. Naming the split is what turns five separate day-tickets into one product essay instead of five loosely related repo links.

Essay ties routing, cache, quality into one SKU.

That's the whole compression docs/hn-launch-routeiq.md had to perform today: five modules — semantic-cache-engine, prompt-fingerprinter, cost-budget-enforcer, model-quality-scorer, fallback-chain — each shipped on its own day-ticket over the last month, with no shared abstraction connecting them beyond a Go convention (per-tenant, `net/http` middleware) and a repo. Writing the essay forced the question a reader would ask first: why is this one product and not five?

The Split Networking Already Named

The answer was sitting in networking vocabulary the whole time. A router's control plane decides which path a packet takes — reading headers, consulting a routing table, applying policy. Its data plane is the fast path that actually moves the packet's bytes, and it never inspects what those bytes mean.

fallback-chain's proxy is a control plane in that exact sense. ServeHTTP reads a tenant ID and a chain of candidate models, decides which model gets tried and in what order, and once a hop is selected, streams that hop's response through unmodified — DESIGN.md's own commitment is that the proxy never inspects, transforms, or re-buffers the winning bytes. The GPT-4o / Claude / Llama call itself, the part that actually produces the completion, is the data plane.

So what: once "control plane" and "data plane" are the labels, the question of which of RouteIQ's five modules belong together stops being a judgment call — every one of them either decides something about a request or carries something, and none of them do both.

DS analogy — a router forwarding by header, never reading the payload
A network router looks at a packet's destination address and a routing table, decides which interface to forward it out of, and does this without ever parsing what the packet's payload actually contains — an HTTP request and a video frame get the identical treatment at that layer. RouteIQ's control-plane modules work the same way: cost-budget-enforcer reads a tenant ID and a token estimate, semantic-cache-engine reads an embedding of the prompt, model-quality-scorer reads a rolled-up quality aggregate — none of them read or understand the model's actual completion text, the same way a router never reads a packet's application-layer payload. The completion itself only exists on the data-plane side, in the one hop fallback-chain actually calls.

Five Modules, Two Planes

Laid out against that split, RouteIQ's five modules sort into exactly two groups — and the group each one lands in explains why it was buildable independently in the first place.

ModulePlaneWhat it decides or carries
prompt-fingerprinterControlIs this prompt an exact repeat? (L1, before anything else runs)
semantic-cache-engineControlIs this prompt a near-repeat? (L2, cosine similarity ≥ 0.92)
cost-budget-enforcerControlCan this tenant afford this request right now?
model-quality-scorerControlWhich candidate models are actually good at this task type?
fallback-chainControl + data plane boundaryWhich hop wins, then streams that hop's bytes through untouched

Every row above the last one is pure control plane: none of them touch a token of the actual model response. fallback-chain is the one module that straddles the line on purpose — it makes the last control-plane decision (which hop) and then, deliberately, gets out of the way for the data-plane part.

So what: a product isn't five modules that happen to share a repo — it's five modules that all resolve into the same boundary, and naming that boundary is what makes "one product" a claim you can defend instead of a marketing label.

Every box in the control-plane subgraph can reject or short-circuit the request before a single token of the actual model call is spent — a fingerprint hit, a semantic cache hit, or a budget block all end the request without ever reaching the data plane. Only a request that clears all four control-plane checks pays for an actual inference.

That ordering isn't arbitrary either: cheapest and most certain check first (exact-match fingerprint), then a more expensive but still-cheaper-than-inference check (semantic similarity), then budget, then the quality-weighted routing decision that picks which specific model gets the data-plane call. Each stage only runs if the cheaper stage ahead of it didn't already resolve the request.

5Modules, two planes
4Control-plane checks per request
1Data-plane call, at most
0Control-plane modules that read completion text

So what: the request path itself is the essay's argument made executable — four independent control-plane decisions ordered cheapest-first, gating one data-plane call, is what "cache, budget, and quality as one product" actually compiles down to.

Why the Split Is the Reusable Part

The control plane doesn't need to know what a model said. It only ever needs to know whether this request should reach one.

The control/data-plane split is what makes adding a sixth signal — per-region latency, say, or a per-model incident flag — a small, well-scoped argument instead of an architecture change. A new signal is a new control-plane check with the same shape as the four that already exist: read something about the request, decide pass or reject, never touch the response bytes.
