Day 24 — GPU Scheduling as Resource Management

MIG, tensor parallelism, Kubernetes extended resources — VRAM is finite and the scheduler needs to know it

AS
Akshant Sharma
June 10, 2026
14 min read
AI Learning · Day 24 of 150

The GPU scheduling problem looks exotic until you realize you have already solved it for CPU and memory. A GPU is a compute device with a fixed RAM budget — VRAM — and a fixed parallel execution capacity — streaming multiprocessors. A model that does not fit in VRAM cannot run. Two models that each claim the full VRAM cannot coexist. The question the scheduler must answer is the same question a Linux kernel answers for CPU processes: how do you multiplex finite compute and memory across competing workloads with isolation guarantees?

What makes the GPU case interesting is that the unit of work — a forward pass through a neural network — is not preemptible at low cost. You cannot interrupt a matrix multiplication halfway through and resume it on another device. The batch window, the KV cache, and the weight tensors are all in VRAM for the duration of the request. The scheduler has to know this, because Kubernetes’ default resource model does not.

This post covers the three mechanisms that give you real control: MIG partitions (isolated VRAM slices), tensor parallelism (sharding a model across multiple GPUs), and Kubernetes extended resources (making VRAM a first-class scheduler input). The goal is to be able to reason about GPU placement decisions the same way I reason about pod resource requests.

DS analogy — parking garage floors
A GPU without MIG is a parking garage with one enormous floor: every car (model) parks on the same level, and a truck that fills the entire floor prevents any other car from entering. MIG divides the garage into separate floors with their own ramps and barriers — a 3GS MIG instance is one floor, a 7GS instance is the whole garage. Cars on different floors cannot collide, and a full floor does not affect the others. Kubernetes extended resources are the parking attendant who checks available floors before letting a car in.

Why VRAM is not like RAM

RAM in a CPU system is addressed linearly and managed by the kernel memory allocator. If a process exceeds its allocation, the kernel pages it out to disk. The process slows down but continues running. VRAM has no paging equivalent in production inference. An OOM on a GPU during a forward pass kills the process immediately, or in the best case, forces a full model reload from CPU RAM into GPU memory — an operation that takes seconds, not milliseconds.

The second difference is that VRAM fragmentation is not recoverable at runtime. A 40 GB model loaded into an 80 GB A100 leaves 40 GB free, but if you load a second 24 GB model and then unload the first, the freed 40 GB is contiguous, but only if the allocator is friendly. Real workloads allocate and release KV cache tensors for active requests, activation buffers during batching, and static weight tensors for multiple loaded models. The memory layout is not clean, and the only robust strategy is to pre-plan occupancy before loading models, not to react after OOMs.

This is why static VRAM budgeting — deciding at deployment time which models fit on which GPUs — is more reliable than dynamic allocation. It is less flexible, but it eliminates the entire class of failures caused by models failing to load under concurrent traffic.

MIG: guaranteed partitions

Multi-Instance GPU (MIG) is NVIDIA’s hardware-level partitioning for the A100 and H100. Each MIG instance is a separate GPU Instance (GI) with its own memory slice, its own compute slices (Streaming Multiprocessors assigned exclusively), and its own L2 cache partition. Two MIG instances on the same physical GPU cannot access each other’s memory or starve each other’s compute.

The available configurations on an A100 80GB are defined by NVIDIA and are not arbitrary. A 7GS (7 GPU Slices, full GPU) is the whole A100 undivided. A 3GS instance gets approximately 40 GB VRAM and 28 SMs. A 2GS instance gets roughly 20 GB and 14 SMs. You can combine instances that add up to the physical GPU — three 2GS instances plus one 1GS, or two 3GS instances, and so on. You cannot define a custom split.

The practical effect is that a 13B parameter model that needs 26 GB VRAM at fp16 fits comfortably in a 3GS MIG instance. A 7B model at fp16 needing 14 GB fits in a 2GS instance. A 70B model at fp16 needing 140 GB spans two full A100s in tensor parallel mode, because no single MIG instance is large enough.

Tensor parallelism: sharded inference

Tensor parallelism is the inference-time equivalent of horizontal partitioning in distributed databases. A single model too large for one GPU’s VRAM is split across multiple GPUs, with each GPU holding a shard of the weight tensors. During the forward pass, each GPU computes its shard of the matrix multiply, then the results are aggregated via an all-reduce operation across the GPU group before passing to the next layer.

The coordination primitive is the all-reduce: every GPU in the tensor parallel group must exchange results at each transformer layer boundary. This requires a high-bandwidth, low-latency interconnect. On NVIDIA DGX systems, NVLink provides 600 GB/s bidirectional bandwidth between GPUs in the same node. Across nodes, InfiniBand is the standard. The rule of thumb is that tensor parallelism within a node over NVLink is efficient; across nodes it becomes communication-bound for large models.

The practical split for a 70B model is tensor parallel degree 4 (four A100s, each holding 25% of the weight tensors) or degree 8 (a full DGX node). At degree 4 with 80 GB A100s, each GPU holds 35 GB of weights in fp16, leaving 45 GB for KV cache and activation buffers. The all-reduce at each layer adds 3–5 ms of latency, which is acceptable for time-to-first-token budgets above 50 ms but is a real cost at lower latency targets.

Kubernetes extended resources and the device plugin

Kubernetes does not know about GPUs natively. It models compute resources as CPU millicores and memory bytes. A GPU is exposed to Kubernetes through a device plugin — a DaemonSet that runs on each GPU node, discovers the available GPU devices (or MIG instances), and advertises them as extended resources on the node.

NVIDIA’s device plugin advertises nvidia.com/gpu extended resources for full GPUs, and nvidia.com/mig-3g.40gb (and similar) for specific MIG profiles. A pod that requests nvidia.com/mig-3g.40gb: 1 in its resource spec is asking the Kubernetes scheduler to place it on a node that has that MIG profile available. The scheduler treats extended resources exactly like CPU and memory — it will not schedule the pod if no node has the requested resource available.

DS analogy — connection pool limits
A database connection pool has a fixed size: 100 connections. A service that requests 10 connections at startup is telling the pool manager to reserve 10 slots. If every service requests 10 and the pool is 100, you can run exactly 10 service instances. The device plugin is the pool manager for GPU resources. Kubernetes resource requests are each service’s claim against the pool. The scheduler refuses to start a pod that would exceed the pool, the same way a connection pool blocks if all slots are taken.

The gap in the default model is that nvidia.com/gpu: 1 requests a full GPU but does not specify VRAM. A node with one A100 and a pod requesting nvidia.com/gpu: 1 will be scheduled together, whether the pod needs 10 GB or 75 GB of VRAM. MIG profiles close this gap by making VRAM part of the resource name: requesting nvidia.com/mig-3g.40gb is requesting 40 GB of isolated VRAM, not just “a GPU.”

Scheduling for cost accuracy

The reason GPU resource scheduling matters for LensAI is cost attribution. LensAI tracks inference cost per request, per model version, and per tenant. If two models share a physical GPU without MIG, and one model runs 60% of the requests while the other runs 40%, attributing GPU cost is a best-effort estimate based on request count. If the two models run on separate MIG instances, cost attribution is exact: each MIG instance has a known VRAM allocation, a known SM allocation, and a known utilization metric.

The distributed-flagd canary rollout from Day 24 demonstrates why this precision matters. When the flag weight advances from 10% gpt-4o to 50% gpt-4o, the GPU cost profile changes. If gpt-4o runs on a MIG 3GS instance and gpt-4o-mini runs on a MIG 2GS instance, the Grafana cost split panel shows not just request volume but actual GPU resource consumption per model version. The cost jump at the 50% transition is measurable, not inferred.

The ingestion event schema already carries resolved_model_id from the Day 23 model evaluator. The next addition is gpu_partition — the MIG instance ID or full GPU ID that served the request, read from the container’s device plugin allocation. With that field, cost-per-request becomes cost-per-VRAM-slice-per-request, which is the granularity you need to make economic canary rollout decisions rather than quality-only decisions.

What I took from this

The clearest insight from reading about MIG and tensor parallelism is that GPU infrastructure forces you to make the same decisions you make in any multi-tenant distributed system: how do you carve finite shared resources into isolated, predictable allocations? MIG is the answer for single-GPU multi-tenancy. Tensor parallelism is the answer for models that exceed single-GPU capacity. Kubernetes extended resources are the scheduler integration that makes both visible to the control plane.

What surprised me is how closely MIG mirrors CPU NUMA node affinity. A NUMA node pins processes to a CPU group with local memory bandwidth. A MIG instance pins a model to a compute group with local VRAM. The topology matters in both cases — a process that crosses NUMA boundaries pays a memory latency penalty, and a tensor parallel job that crosses NVLink boundaries pays a communication latency penalty. The hardware topology is a constraint the scheduler should respect, not paper over.

For LensAI, the practical takeaway is that the observability pipeline needs a GPU topology dimension in the event schema. Not just which model, but which GPU, which MIG profile, and whether the request was served from a tensor parallel group. That dimension is what turns “GPU costs went up” into “the gpt-4o workload is consuming a 3GS MIG instance at 94% utilization during peak, and we can either reduce the canary weight or provision another MIG instance.” The first statement is an alert. The second is a decision.
