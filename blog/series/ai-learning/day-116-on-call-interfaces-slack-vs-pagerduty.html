Day 116 — On-Call Interfaces — Slack vs PagerDuty

Severity routing is product design, not a code path: today's pkg/notify ships one Envelope struct and two adapters that translate it into a Slack message and a PagerDuty event, and neither adapter needs to know the other exists.

Adapter interface in alert engine. That's the whole ticket in four words, and it undersells what actually shipped today: alert-rule-engine/pkg/notify is the first code in this module that talks to the outside world at all. Days 111 through 115 built a rule DSL, an evaluator, a webhook client, and an integration test — four packages that decide whether to fire and prove they fire correctly, none of which ever sent a human being anything they could actually read on their phone.

One Envelope, Two Channels

Envelope is deliberately small: RuleID, Severity, Summary, EscalationStep, Tenant, and RunbookURL — six fields, no channel-specific data anywhere in the struct. SlackNotifier and PagerDutyNotifier each take the identical Envelope and produce a completely different wire request: Slack gets a plain-text message where a bare URL auto-unfurls into a preview card; PagerDuty gets a structured trigger event on its Events API v2, with the same fields folded into a custom_details map its incident view renders inline.

Neither adapter imports the other, and neither knows the other exists. That's not an accident of file layout — it's the entire point of writing Notifier as a one-method interface in the first place.

So what: an escalation step's notify field can name a channel this module has never heard of yet, and adding support for it means writing one new struct that satisfies one interface method — not touching the evaluator, the dispatcher, or either existing adapter.

The Universal Travel Plug

DS analogy — a universal travel adapter
A universal travel plug has exactly one socket on the inside — the shape every laptop charger and phone cable already expects — and a different set of prongs on the outside for every country's wall socket. Nobody rewires the wall for a trip to a new country; the adapter absorbs that difference so the device on the inside never has to change. Envelope is the inside socket here: SlackNotifier and PagerDutyNotifier are two different prong shapes for two very different "wall sockets" — a JSON webhook that wants plain text and unfurls URLs for free, versus a structured Events API that wants a severity enum and a nested payload — and the rule evaluator producing the Envelope never has to know which wall it's plugging into.

So what: the moment a system has more than one external consumer of the same internal fact, the choice isn't "webhook or API" — it's whether every future consumer gets its own adapter or the internal fact gets reshaped every time a new one shows up.

Dispatcher is a map[string]Notifier with a Register method and a Dispatch method — nothing resembling a plugin loader, a service registry, or anything that discovers adapters at runtime. A rule's escalation step names a channel string, Dispatch looks it up in the map, and calls Notify on whatever's registered there. That's the entire routing layer.

The one deliberate choice worth naming: an unregistered channel returns an error instead of silently doing nothing. A rule author who typos slak instead of slack, or a deployment that never wired up a pagerduty adapter, gets a loud failure in the process's own logs — not a page that silently never arrives while every other signal says the system is healthy.

So what: the simplest possible routing table (a map and two methods) is also the one that fails loud instead of quiet, and those two properties aren't in tension — the map is simple enough that "no entry for this key" is the only failure mode there is to handle.

Severity Routing Is Product, Not Code

Nothing in pkg/notify decides that a step 0 escalation should go to Slack and a step 2 escalation should page. That decision lives entirely in a rule's YAML — escalation[i].notify names the channel, full stop — which means changing who gets woken up for what is a config edit to a rule file, not a pull request against this package.

That's the sense in which severity routing is product design: the interesting decision — how loud is too loud, how many minutes of silence justifies escalating from a chat message to a phone call — belongs to whoever authors the rule, informed by what the on-call rotation actually needs. The code's job is narrower and more boring: guarantee that whichever channel a rule names, the same six fields arrive there intact.

So what: a bug in which channel gets notified is almost always a rule-authoring mistake, while a bug in what the notification says is a code bug in one specific adapter — two different failure classes that this split keeps from ever looking like the same problem.

The Piece Day 112 Already Solved

It's worth being precise about what's new today and what isn't. Day 112's evaluator already decided when a step becomes due — sustained-true for the rule's for duration, then gated by a 30-minute dedupe window that survives a resolve-then-refire cycle without resetting. Today's adapters never re-litigate any of that; by the time Dispatcher.Dispatch runs, the "should this fire right now" question is already closed. pkg/notify only answers "given that it's firing, what does channel X actually receive."

So what: keeping the dedupe state machine and the wire-format translation in separate packages means a bug in one can't masquerade as a bug in the other — a duplicate page is an evaluator problem, a malformed PagerDuty payload is an adapter problem, and nothing about today's code makes that boundary blurrier.

The interface has one method. The interesting decisions all happen on the other side of it.

So what: a one-method Notifier interface looks almost too simple to be worth naming — until the alternative is remembered: a rule evaluator that has to know Slack's JSON shape and PagerDuty's Events API in the same function, growing a new if channel == "..." branch every time this platform adds a third way to get someone's attention.
