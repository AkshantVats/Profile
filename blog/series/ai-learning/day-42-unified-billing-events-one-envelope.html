Day 42 — Unified Billing Events — One Envelope

Inference cost and tool cost usually land in two tables that were never designed to JOIN. A single BillingEvent envelope, keyed on tenant_id and trace_id, is the schema decision that turns an observability system into a billing system.

10 min read

An agent's cost comes from two places: inference calls to a model API and tool calls to external services. In most observability setups these land in different tables, different dashboards, and different budget owners — the inference team looks at token usage, the infrastructure team looks at tool latency.

Nobody looks at a single trace and sees the total spend, because the join that would answer “what did this one customer request actually cost us” doesn't exist. It doesn't exist because the two systems never agreed on an envelope in the first place.

Today's code adds a BillingEvent struct that both systems emit, with tenant_id plus trace_id as the join key. One envelope is what makes the join possible.

Why two systems can't share a dashboard today

LensAI tracks inference: model, token count, prompt tokens, completion tokens, cost in dollars, latency. tool-call-analyzer tracks tool calls: tool name, vendor, span ID, duration, cost in dollars, trace ID.

Both have a cost field. Neither has the other's primary identifier, and you can't JOIN two tables without a shared key that both systems populate at write time.

Multi-tenant agent systems need per-tenant cost breakdowns — “how much did tenant T17 spend this week on inference versus tool calls?” Without a unified envelope you run two queries, get two numbers, and add them in a spreadsheet. That's not a dashboard. That's manual accounting with extra steps.

A unified envelope is a single JSON schema that both systems write into the same ClickHouse table, or into two tables with identical schemas. The fields that matter for cost attribution — tenant ID, trace ID, span ID, source, cost — stay the same whether the event came from a model API call or a web-search tool call.

Everything else is optional context specific to the source. The shared keys are what make the join work at all.

DS analogy — two departments, one invoice number
A company where shipping and manufacturing each keep their own spreadsheet can't answer "what did order #4471 actually cost us" until both spreadsheets agree to write the same order number on every row. The order number doesn't replace either spreadsheet's own columns. It just gives accounting one key to join on.

Schema divergence between observability systems isn't a data engineering problem, it's an agreement problem. Once both teams agree on the envelope — even if the extra fields differ — every dashboard, query, and alert can be written once and applied to both sources at the same time.

The BillingEvent envelope design

The envelope carries nine fields, and the same struct serves both event types:

{
  "tenant_id":    "t17",
  "trace_id":     "7f3d9a2e-1234-5678-abcd-ef0123456789",
  "span_id":      "a1b2c3d4",
  "source":       "tool",
  "tool_name":    "search_web",
  "vendor":       "openai",
  "cost_usd":     0.0031,
  "duration_ms":  380,
  "timestamp_ns": 1721234567890000000
}

For an inference event, source is "inference", tool_name is empty, vendor names the model provider, and cost_usd is computed from token counts instead of a vendor invoice. The struct doesn't change shape — only the source field tells a downstream consumer which pipeline produced the row.

Separate tables feel cleaner right up until you need to query across them. A single table with a low-cardinality source discriminator column keeps every cost query a plain WHERE tenant_id = ? AND trace_id = ?, with no UNION required, and ClickHouse filters that column efficiently because it isn't a nullable type.

trace_id answers “what happened in this request?” tenant_id answers “who owns this cost?” For an agent platform, tenant is the billing unit — a single tenant can generate thousands of traces a day.

Aggregating by tenant_id gives the invoice line item; joining on trace_id gives the individual request breakdown. Both are necessary, and neither is sufficient on its own.

The envelope doesn't erase the difference between inference and tool calls — it makes the difference navigable. The source field tells you which system produced an event, and the shared fields let you aggregate across all of them regardless of source.

Dual-write: fire-and-forget

tool-call-analyzer's primary write path is ClickHouse, and adding LensAI ingest as a second destination must not gate that write. If LensAI is down, tool spans still have to land in ClickHouse; if LensAI is slow, the tool span write still has to complete in under fifty milliseconds.

The dual-write is additive, not dependent, and Go's goroutines make that distinction easy to express directly in code:

func Send(ev BillingEvent) {
    url := os.Getenv("LENSAI_INGEST_URL")
    if url == "" {
        return
    }
    go func() {
        body, _ := json.Marshal(ev)
        ctx, cancel := context.WithTimeout(context.Background(), 2*time.Second)
        defer cancel()
        req, _ := http.NewRequestWithContext(ctx, http.MethodPost, url, bytes.NewReader(body))
        req.Header.Set("Content-Type", "application/json")
        resp, err := http.DefaultClient.Do(req)
        if err != nil {
            return
        }
        resp.Body.Close()
    }()
}

The goroutine carries a two-second context deadline. If LensAI doesn't respond in that window the goroutine exits cleanly on its own — no leak, no blocked caller waiting on a response nobody needs.

LensAI ingest is idempotent, with span_id as the dedup key. A span that fails to arrive on the first attempt shows up as a gap in the tenant's inference-versus-tool breakdown, but it won't produce a duplicate cost entry if a retry happens to land later.

The tradeoff is deliberate: occasional gaps at LensAI in exchange for never blocking the ClickHouse write path. For billing, gaps are visible and recoverable; latency spikes in the primary write path are invisible and compounding.

If LENSAI_INGEST_URL is unset, Send() returns immediately without spawning a goroutine at all. That makes the dual-write strictly optional — tool-call-analyzer works standalone with zero LensAI dependency, and only integrates once the environment variable is present.

DS analogy — the accountant's copy
Dual-write is like mailing a copy of every invoice to your accountant while the original goes straight to the client. The client's invoice is what matters, and the business doesn't stop if the accountant's copy gets lost in the post. You never delay the client's invoice to wait for a delivery receipt on the copy.

Fire-and-forget dual-write is the right pattern whenever the secondary destination is observability infrastructure rather than primary business data. Treating both writes identically — both blocking, both retried — couples your primary write path to a dependency's availability, and that's the wrong direction for that coupling to point.

The unified Grafana board

The board has two rows, each fed by a different datasource but both filtered on the same template variable:

Row 1 — Inference (LensAI datasource)
  [Stat]        Total inference cost today (filtered by $tenant_id)
  [Bar Gauge]   Cost breakdown by model
  [Time Series] Token usage over time

Row 2 — Tools (TraceForge ClickHouse datasource)
  [Bar Gauge]   Cost waterfall by tool name
  [Time Series] Exclusive time P99 trend by tool
  [Stat]        N+1 alerts fired today

Switch the $tenant_id variable to T17 and both rows update together: the inference row shows T17's model spend, the tool row shows T17's tool spend, and total cost for T17 is the sum of the two stat panels.

Grafana panels from two datasources don't join inside a database. They join in the viewer's eye, because the shared $tenant_id variable makes both panels show the same tenant at the same time, and the user reads the total by adding two numbers.

For most purposes — a team review, a budget conversation, spotting an anomaly — that visual juxtaposition is enough. A real SQL JOIN is only needed when you want one number from one query, which matters for invoice generation but not for the weekly dashboard.

Grafana dashboards are JSON files under the hood, so a board with a deterministic shape — same panels, same datasource mapping, same variable, on every deployment — is a better fit for a generator than for click-and-drag editing. A change to the ClickHouse schema then triggers a change to the generator function, not a manual edit inside Grafana that nobody remembers to repeat on the next environment.

Unified observability doesn't require a unified database. It requires a unified variable and two datasources registered in the same Grafana instance, and the board generator is the artifact that encodes that agreement as code instead of as a convention someone has to remember.

What tenant_id plus trace_id makes possible

Before the unified envelope, a per-tenant cost split was two queries and a manual sum. With both event types in one table, it's a single query with two filtered sums:

SELECT
    tenant_id,
    SUM(cost_usd) FILTER (WHERE source = 'inference') AS inference_cost,
    SUM(cost_usd) FILTER (WHERE source = 'tool')      AS tool_cost,
    SUM(cost_usd)                                      AS total_cost
FROM billing_events
WHERE tenant_id = 'T17'
  AND toDate(timestamp_ns / 1e9) = today()
GROUP BY tenant_id

The same shape works one level down, ranking traces instead of tenants:

SELECT
    trace_id,
    SUM(cost_usd) FILTER (WHERE source = 'inference') AS inference_cost,
    SUM(cost_usd) FILTER (WHERE source = 'tool')      AS tool_cost
FROM billing_events
WHERE tenant_id = 'T17'
ORDER BY (inference_cost + tool_cost) DESC
LIMIT 10

That surfaces the ten most expensive traces for tenant T17 today, across both systems at once, and shows whether the expensive traces are inference-heavy, tool-heavy, or a mix of both. That breakdown points at two different optimizations, and you can't tell which one applies without the join.

When every API call a tenant makes produces a BillingEvent, the invoice becomes a SELECT instead of a monthly reconciliation job. There's no gap-filling script and no separate aggregation pass — the billing envelope is the invoice record, and the unified table is the billing database.

tenant_id plus trace_id isn't metadata bolted on afterward. It's the schema decision that turns an observability system into a billing system, and it does that without touching either LensAI's or tool-call-analyzer's primary write path.

The envelope doesn't make inference and tools the same thing. It makes them addable — and addable is the only property a billing system actually needs.
