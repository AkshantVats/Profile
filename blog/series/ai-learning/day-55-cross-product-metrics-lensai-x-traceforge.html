One tenant_id to rule cost — design the join on Day 1.

A distributed system rarely gets to choose its dashboard's join key after the fact. By the time two pipelines both have data flowing and a stakeholder asks to see cost and quality on one screen, retrofitting a shared key means backfilling history that was never tagged with it, or living with two screens forever.

Day 55 asks a narrower, earlier version of that question: when a second pipeline's first event ever gets built, what has to be true about it for a join to even be possible someday?

The Join-Key-First Design Principle

DS analogy — the phone system's country code
Every phone number carries a country-code prefix, whether or not a given call ever crosses a border. Reserving that field costs nothing when a numbering plan is designed — it's an empty slot most calls never use. Retrofitting a prefix onto a numbering scheme already in use by millions of subscribers, after the fact, is a different order of problem entirely: every existing number is ambiguous until it's re-tagged, and re-tagging has to happen without breaking calls already in flight.

LensAI's /ingest envelope already had tenant_id — every inference event since Day 1 carried one, because tenant-scoped billing was the pipeline's reason to exist. The only open question Day 55 had to answer was whether agent-benchmark-runner's first ingest event would reuse that field or invent its own.

So what: the cheapest time to decide a join key is before the second pipeline has any data to migrate — reusing an existing field costs a design decision; adding one later costs a backfill.

The Wide-Event, Structured-Log Parallel

The systems-engineering version of the same trade is a request ID threaded through every service a request touches. Most services that carry it don't need it for their own logic — a request ID doesn't change how a service processes a request, only how a reader can later reconstruct what happened to it across service boundaries.

The alternative — correlating logs after the fact by timestamp and rough proximity — fails exactly when it matters most: under load, with clock skew, with two requests arriving close enough together that timestamp correlation becomes a guess. A field that costs nothing at write time and pays off only during an investigation is an easy trade to skip, right up until the investigation happens.

orchestrator.Summary — the batch statistics a benchmark run produces — has no tenant concept of its own; grading a batch correctly never required one. The event pkg/lensai.ToEvent builds from that Summary does, because the event's only job, unlike the Summary it's built from, is to be joinable later.

So what: a field a component doesn't need for its own correctness can still be the single most important field on the event it emits — "does this help future me" is a different question from "does this help today's logic."

Why the Shared Envelope Is Safe to Reuse

2source values sharing one envelope
0deny_unknown_fields on InferenceEvent
1table both land in

Reusing LensAI's envelope instead of standing up a second endpoint only works because of a specific, checkable property: LensAI's Rust InferenceEvent struct derives Deserialize without #[serde(deny_unknown_fields)]. Serde's default behavior on a struct like that is to silently drop JSON fields it doesn't recognize, rather than reject the whole payload. That's what Day 42 (tool-call-analyzer/pkg/lensai) already relied on to add trace_id and source as additive fields, and it's exactly what makes it safe for Day 55 to add a second source value onto the same wire format instead of forking it.

Without that property, the two dual-writers couldn't coexist this cheaply: either LensAI's ingest handler would reject every event carrying an unrecognized field, or every additive field would need a schema migration blessed on both sides before either dual-writer could ship it.

So what: "safe to extend" is a fact about the current implementation, not a promise the schema makes — and a design built on that fact needs to know which one it's leaning on.

What Breaks If the Property Changes

  • LensAI's ingest handler adds #[serde(deny_unknown_fields)] to InferenceEvent for input validation reasons unrelated to either dual-writer — both tool_call and benchmark_run events start failing deserialization at once.
  • The failure is silent from each dual-writer's own vantage point: Writer.Insert still gets an HTTP response, and only a downstream metric — ingest volume for source:"benchmark_run" dropping to zero — reveals anything changed.
  • Two independently-deployed modules (tool-call-analyzer, agent-benchmark-runner) now share a coupling neither one's go.mod expresses: both assume the same fact about a Rust struct in a third repo they don't import.

So what: reusing a schema is cheaper than owning one, and the price of that cheapness is an invisible dependency — worth taking here, but worth writing down, which is what this post and the code's own DESIGN.md addendum both do.

The Honest Gap

A shared tenant_id and a shared envelope make two products joinable; neither one, on its own, joins them. Nothing in today's code aggregates a LensAI inference event and a benchmark_run event for the same tenant into a single number — that's a future aggregation point's job, the same way LensAI's own envelope reuse only worked because Day 42 already existed to reuse.
