Day 67 — Live Config for Spend

Budget PATCH is a feature flag for money. And the moment a config change has to span two systems with no shared transaction between them, the answer isn't a bigger lock — it's a compensating action.

Budget PATCH is a feature flag for money. A feature flag flips a boolean and changes what code path a request takes; today's Admin API flips a number and changes how much of a tenant's spend gets through before the enforcer starts degrading or blocking — same shape of lever, applied to a dollar amount instead of a rollout percentage.

That framing makes the endpoint sound simple, and the endpoint itself mostly is: parse a tenant ID, merge a patch, validate, done. What isn't simple is the constraint sitting one layer underneath — the change has to land in two places, an in-memory config store and a Kafka audit topic, and there is no database transaction spanning both of them. That constraint is where today's post actually lives.

Two Systems, No Shared Transaction

A single-database write has an easy answer to "what if it fails partway through": the transaction aborts, nothing committed, retry from a clean slate. pkg/admin.Handler doesn't get that answer, because the two things it needs to happen — commit the config change, durably record why — live in different systems that have never heard of each other's commit log.

Kafka doesn't know about the in-memory LiveStore; the store doesn't know about Kafka. Wrapping both in one ACID transaction isn't an engineering choice available here — it isn't available at all, the same way it isn't available for a payment service updating its own ledger and calling a third-party processor, or an order service writing a row and publishing an event. Two systems, one logical operation, zero shared transaction: that combination shows up constantly once you're looking for it, and it has a name.

DS analogy — a two-key safe deposit box, not a bigger vault door
A bank vault door is one lock: turn the key, everything inside is accessible, in one atomic action. A safe deposit box is different on purpose — it takes two separate keys, held by two separate parties, and neither key alone opens anything. Today's Patch-then-Publish pipeline is the second design, not the first: two separate, non-atomic steps, each of which can fail independently, coordinated by an explicit rule for what happens when only one of them succeeds — not one bigger lock that makes the coordination problem disappear.

So what: reaching for a bigger transaction is the wrong instinct the moment two systems don't share a commit log — the actual tool is a protocol for what happens when step one succeeds and step two doesn't, not a lock wide enough to pretend the two steps are one.

The Saga Pattern, in Fifteen Lines

The pattern that names this situation is the saga: a sequence of local transactions, each in its own system, where every step that changes state has a corresponding compensating step that undoes it if a later step in the sequence fails. No two-phase commit, no distributed lock manager — just an explicit "if this fails, here's how we undo that" written into the code path itself.

pkg/admin.Handler.ServeHTTP is a two-step saga with one compensating action, and it fits in about fifteen lines. Step one: LiveStore.Patch commits the new config locally. Step two: audit.Publish sends the record to Kafka.

If step two fails, the compensating action is LiveStore.Set(tenantID, before) — the store's undo, applied synchronously, in the same request, before the client ever sees a response.

So what: a saga doesn't require a framework, an orchestrator, or even a name in the code — it requires knowing, for every step that changes shared state, exactly what "undo this" means, and calling that function on the failure path instead of hoping the failure path never runs.

Why the Order of the Two Steps Isn't Arbitrary

The sequence matters as much as the compensation. Patch runs before Publish, not after, because the audit event needs a committed before/after pair to describe — publishing first would mean auditing a change that might still fail to commit. Committing first and compensating on audit failure is the right order specifically because the audit record is the thing that must never be wrong, not merely the thing that must never be missing.

Flip that priority — imagine a variant that published the audit record first and committed the config change second — and the compensating action would have to un-publish a Kafka message, which Kafka's append-only log makes structurally impossible. The direction chosen here (mutate an undoable in-memory store, then commit to an unforgeable append-only log) isn't incidental; it's the saga's compensating step landing on the one side of the pipeline where undoing is actually a thing you can do.

So what: which half of a two-system operation gets the compensating action isn't a coin flip — it belongs on whichever side can actually be undone, and an append-only log by design volunteers to be the side that can't.

What a Passing Test Suite Proves, and What a Real Cluster Would Add

TestPatchRollsBackWhenAuditPublishFails proves the compensating action fires correctly against a fake publisher configured to fail — the logic is exercised, deterministically, on every test run. What it doesn't prove is what happens under a real Kafka cluster's failure modes: a publish that times out ambiguously rather than failing cleanly, a partial write the producer can't tell succeeded or didn't, a retry that double-publishes after the handler already compensated once.

Those are real saga hazards — the literature calls the ambiguous case "the coordinator's dilemma," and it's the reason production saga implementations often add idempotency keys and retry-safe compensations rather than treating a single compensating call as sufficient. Today's implementation is the pattern's core shape, tested against its core failure mode, not yet hardened against Kafka's messier ones — the same honest gap this module has logged since Day 65's DESIGN.md: no live broker in this sandbox to exercise the messy cases against.

A saga doesn't remove the seam between two systems — it just makes the seam a place you designed on purpose, instead of a place you discover during an incident.

So what: "the compensating action runs when it should" is a claim a unit test against a fake can fully earn; "the compensating action is safe under every way a real Kafka cluster can half-fail" is a claim that needs a live cluster and a much longer list of injected failures to earn, and the gap between those two claims is exactly what separates a saga's core logic from a saga that's production-hardened.
