Day 40 — Graph Algorithms on Traces

N+1 tool calls are SELECT in a loop, but agents have never had a linter to catch them. Model a trace as a directed graph and cycle detection, topological sort, and N+1 lint all fall out of algorithms that are decades old.

Every ORM developer knows N+1 by feel before they know it by name. Fetch a list of orders, then run one query per order to fetch its customer — a linter catches the pattern before it ships, in Django, in Rails, in Laravel.

Agents have the exact same pattern. search_web gets called fifteen times in a row, each call unaware of the fourteen others, and no linter exists to catch it. Today’s code builds one, and the trick is modeling the trace as a directed graph so that graph algorithms can find structure a flat list hides.

What a trace looks like as a graph

A trace is a set of spans, and every span carries a span_id and a parent_span_id. That parent-child relationship is already a directed edge, so the entire trace is a directed acyclic graph almost by construction — a span finishing and then re-entering itself as its own ancestor would require time travel.

The mapping is direct: each node is one tool call span (tool_name, vendor, duration_ms), each edge runs from a parent_span_id to its span_id, and the root is whichever span has no parent — the agent’s top-level reasoning step.

DS analogy — the relay race
A relay race isn’t one long line of runners. Each runner starts when the baton comes from the previous one, and some legs fan out — two runners can start at once if the handoff allows it. A flat list of finish times can’t show you that structure; the graph, where each runner is a node and each handoff is an edge, captures the fan-out exactly.

Modeling traces as graphs instead of lists unlocks the entire standard toolkit — cycle detection, topological sort, shortest path, centrality — and most observability tools never make this model explicit. TraceForge does, starting with the two algorithms that matter most for tool-call traces.

Why cycle detection matters even if cycles “shouldn’t happen”

A span can’t legitimately be both ancestor and descendant of itself — that would require a bug in the instrumentation or a loop in the agent’s tool-call router. “Shouldn’t happen” and “never happens” are different guarantees, though, and production trace data eventually tests the difference.

A broken retry mechanism can re-emit a span reusing an old span_id. A buggy SDK that reuses parent_span_ids across retries produces an apparent cycle just as easily, and a graph reader that assumes acyclicity and skips the check will hang: Kahn’s algorithm deadlocks when in-degree never reaches zero for the nodes caught in the cycle.

The fix is depth-first search with an inStack set: mark a node in-stack when first visited, unmark it once every child is processed, and any edge into a node that’s still in-stack is a back edge — a cycle. It runs in O(V+E) and costs milliseconds, which is why it’s the first check, run before topological sort or N+1 detection, both of which silently assume the graph they’re handed is acyclic.

Topological sort as execution replay

Topological sort orders nodes so every parent appears before its children, which for a trace means the order tool calls were initiated in — not necessarily the order they finished, but the causal chain that produced them. Kahn’s algorithm gets there with an in-degree queue: compute each node’s parent count, seed the queue with the zero-in-degree roots, and each time a node is emitted, decrement its children’s in-degree until they hit zero and join the queue themselves.

Sorting the queue alphabetically whenever multiple roots or ties exist keeps the output deterministic, which matters for tests and for diffing two runs of the same agent. The first node in that order is where the agent started; the last nodes are the leaf calls that actually produced the results feeding the agent’s response.

Gaps in duration between a parent and child in topological order are coordination overhead — time the agent spent deciding what to call next rather than waiting on a tool. Timestamp order tells you wall-clock sequence; topological order tells you which tool results actually fed which decisions, and for debugging an agent, the second question is almost always the one that matters.

N+1 detection — the lint rule agents don’t have

In a database ORM, N+1 means one query returns N records, and then N more queries fetch related data one record at a time — the fix is a JOIN or an eager load that collapses N round trips into one. In an agent trace, N+1 means one invocation triggers N calls to the same tool, each unaware of the others, and the fix is a batched tool that accepts multiple inputs in one call.

Detection is a single pass: count tool_name occurrences across the graph, and any tool appearing at or above the threshold generates a finding.

counts := map[tool_name]int{}
for each node in graph:
    counts[node.tool_name]++

for name, count := range counts:
    if count >= threshold:
        emit N1Finding{ToolName: name, Count: count}

The threshold is 3, matching the convention in ORM query analyzers like Python’s nplusone and Rails’ bullet. One call is intentional, two might be a retry, and three sequential calls to the same tool in one trace is almost always a loop that should have been a batch.

N+1 detection gives agents the ORM lint rule they’ve never had. It catches cost bleed — four search calls cost four times the tokens of one — and it catches latency waste, since sequential calls that could have been parallel or batched can’t be un-spent after the fact.

The traceforge graph CLI in practice

traceforge graph \
  --trace-id 7f3d9a2e-1234-5678-abcd-ef0123456789 \
  --min-n1-count 3 \
  --format text

The text report reads like a debugging session, not a dashboard query:

Trace ID : 7f3d9a2e-1234-5678-abcd-ef0123456789
Nodes    : 6
Cycle    : false

  1. [7f3d9a2e] plan_task (openai) 12ms
  2. [a1b2c3d4] search_web (openai) 380ms
  3. [e5f6g7h8] search_web (openai) 410ms
  4. [i9j0k1l2] search_web (openai) 395ms
  5. [m3n4o5p6] search_web (openai) 420ms
  6. [q7r8s9t0] summarize (anthropic) 180ms

N+1 alerts (threshold=3):
  ⚠  search_web called 4 times — possible N+1 pattern

The same command with --format dot pipes straight into Graphviz — traceforge graph --trace-id <id> --format dot | dot -Tpng > trace.png — for the traces dense enough that text output stops being readable. No dashboard is required for either path; an engineer on call can run it against a trace ID pulled straight from a Grafana alert and get the structural diagnosis in one command.

Connection to distributed systems primitives

Graph-based trace analysis isn’t new — Google’s Dapper paper modeled traces as trees in 2010, and Jaeger uses a DAG model internally today. What’s missing industry-wide isn’t the graph model; it’s running algorithmic detectors automatically on every trace instead of leaving the graph for a human to eyeball only after something breaks.

Apache Airflow validates a DAG for cycles before it ever schedules a run — it refuses a cyclic workflow at registration time, before any task executes. TraceForge’s graph CLI does the equivalent after the fact: it validates the trace DAG post-execution, surfacing the cycles and N+1 patterns that actually happened in production rather than the ones a static check ruled out in advance.

Every algorithm in today's code ships in a textbook. The value isn't novelty — it's pointing decades-old graph algorithms at a domain that has never had them before.

The graph lives in memory today, rebuilt fresh from a ClickHouse query on every CLI invocation. The next move is persisting the adjacency structure itself — an Array(String) column queried with arrayJoin — so N+1 alerting becomes a materialized view running continuously, not a command someone has to remember to run.
