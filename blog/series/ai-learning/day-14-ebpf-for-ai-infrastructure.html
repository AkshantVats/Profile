Day 14 — eBPF for AI Infrastructure: Kernel Probes vs SDK Patches

14 of N — AI Learning Series. Kernel probes vs SDK patches — when zero-instrumentation wins. eBPF socket probes capture LLM HTTP calls with zero application code changes.

AI Learning · Day 14 of N

Cilium proved network observability without app changes — LLM HTTP is the next syscall surface.

Every LLM SDK ships with a tracing hook.

Almost no one enables it.

The OpenAI Python SDK has callback hooks. The Anthropic client exposes middleware interfaces. LangChain wraps everything in trace spans. Yet if you instrument a real production fleet, you will find that the majority of LLM calls are invisible — not because engineers made a deliberate choice to skip tracing, but because the friction of SDK instrumentation compounds across every service, every language, every version bump.

A microservice running Go doesn’t use the Python SDK. A legacy Java service calls the API directly over HTTP. A data science team prototyping in a notebook never wired in the OpenTelemetry exporter. The SDK instrumentation gap is not a discipline problem. It is an architecture problem.

eBPF solves this at the wrong layer — and that’s exactly why it works.

If you can attach probes at the kernel socket layer and parse the HTTP payload in BPF maps, you capture every LLM call regardless of language, SDK version, or whether the application team knows observability exists. The same way Cilium provided network policy and flow visibility without requiring every pod to run a sidecar proxy, eBPF can provide LLM call visibility without requiring every service to update its dependencies.

The SDK Instrumentation Gap — Why Apps Skip It

Let me be precise about what the gap looks like in practice.

Imagine a platform team that decides to instrument all LLM calls for cost attribution. They publish a wrapper library. They document the integration. They send a migration guide to every team.

Six months later:

  • the Python services that run openai SDK — partially instrumented
  • the Go services that call the REST API directly — zero instrumentation
  • the internal ML platform that uses a vendor-specific client — different trace format, not compatible
  • third-party SaaS tools that call OpenAI on behalf of the company — completely opaque
  • the data pipeline that calls an embedding endpoint in a Spark UDF — no one thought to add tracing

Each gap has a legitimate reason. The team can’t force a Go rewrite to use the Python wrapper. The SaaS vendor won’t accept patches. The Spark UDF runs in a context where adding heavyweight dependencies breaks the cluster image build.

The result: you’re flying blind on a large fraction of your actual LLM spend. You don’t know which models are being called, you can’t see token counts, you can’t detect unauthorized API key usage, and you can’t build cost-by-team attribution that closes against the invoice.

This is the instrumentation gap that motivated me to look at eBPF.

eBPF Basics — Probe Attachment Points

eBPF (extended Berkeley Packet Filter) is a kernel subsystem that lets you run sandboxed programs in the Linux kernel without loading kernel modules or modifying kernel source. The BPF verifier guarantees safety: infinite loops are rejected, memory access bounds are checked, and the program cannot crash the kernel.

For LLM HTTP tracing, the relevant attachment points are:

  • kprobe/tcp_connect — fires when a process opens a TCP connection. Captures the destination IP and port, plus the PID and file descriptor (FD). This is where we record that PID 1234 opened FD 7 to api.openai.com:443.
  • kprobe/tcp_sendmsg or kprobe/__sys_sendto — fires when data is written to a socket. At this point we can read the userspace buffer and parse the HTTP request headers and body from the process’s address space.
  • kprobe/tcp_recvmsg or kprobe/__sys_recvfrom — fires on receive. We can extract the HTTP response, parse the x-request-id, status code, and response body for token count hints.
  • tracepoint/sock/inet_sock_set_state — fires on TCP state transitions. Useful for detecting connection reuse vs new connections and correlating FD lifecycle to request lifecycle.

The critical design constraint: BPF programs run in the kernel and are extremely size-limited. The verifier imposes a complexity bound. You cannot do arbitrary string parsing in BPF. The strategy is to do minimal extraction in kernel space — capture the raw bytes of the HTTP payload into a ring buffer event — and do the full HTTP parsing in userspace.

HTTP Parsing via eBPF Maps — Extracting model_id, Auth, Token Hints

The data flow has three stages.

Stage 1: Connection tracking in BPF hash map

When tcp_connect fires, the BPF program checks whether the destination resolves to a known LLM endpoint. Since DNS resolution happens in userspace, the BPF program maintains a map of known destination IPs that the userspace agent populates.

// BPF hash map: PID+FD -> connection metadata
struct conn_key {
    u32 pid;
    u32 fd;
};

struct conn_val {
    u64 ts_connect_ns;
    u32 dst_ip;
    u16 dst_port;
    u8  is_llm_endpoint;  // set by userspace agent
};

When tcp_connect fires for a connection to a known LLM IP, we write a conn_val entry keyed by {pid, fd}. This is the correlation anchor for everything that follows.

Stage 2: Payload capture on send

When tcp_sendmsg fires, we look up the connection map. If this FD belongs to an LLM endpoint, we read the first N bytes of the send buffer from userspace memory using bpf_probe_read_user:

// In the kprobe handler for tcp_sendmsg
struct conn_val *conn = bpf_map_lookup_elem(&conn_map, &key);
if (conn && conn->is_llm_endpoint) {
    struct send_event ev = {};
    ev.pid = pid;
    ev.fd  = fd;
    ev.ts  = bpf_ktime_get_ns();
    // read first 512 bytes of the send buffer
    bpf_probe_read_user(ev.payload, sizeof(ev.payload), iov_base);
    bpf_ringbuf_output(&ring_buf, &ev, sizeof(ev), 0);
}

512 bytes is enough to capture the HTTP request line (POST /v1/chat/completions HTTP/1.1), the Authorization: Bearer sk-... header, the Content-Type, and the beginning of the JSON body which contains "model": "gpt-4o". For most OpenAI-compatible API calls the model field appears within the first 200 bytes of the body.

Stage 3: Response correlation

When tcp_recvmsg fires for an LLM endpoint FD, we capture the response bytes. The response body contains the usage object with prompt_tokens and completion_tokens. We also capture the HTTP status code and the x-request-id header for correlation with provider-side logs.

Userspace Agent — BPF Ring Buffer Consumer

The userspace agent is a Go or Rust daemon that runs on each node. Its responsibilities:

  • Ring buffer consumer — polls the BPF ring buffer for send_event and recv_event records
  • HTTP parser — reconstructs the HTTP request and response from the captured payload bytes
  • Field extraction — parses JSON to extract model, max_tokens, and from the response usage.prompt_tokens, usage.completion_tokens
  • Correlation by PID+FD — joins the send and recv events using the {pid, fd, ts} tuple
  • Kafka producer — emits a structured LLMCallEvent to the infra-ai-streaming topic
  • IP resolver — resolves LLM provider hostnames and writes IP-to-endpoint mappings back into a BPF map so the kernel program can filter efficiently

The correlation by PID+FD is where the real work happens. A single process may have multiple concurrent LLM calls open on different file descriptors. The agent must correctly pair each send event to its matching recv event without cross-contaminating records from different requests.

// Correlation table in userspace
type PendingRequest struct {
    PID       uint32
    FD        uint32
    SendTS    uint64
    Model     string
    AuthHash  string
    MaxTokens int
}

// On recv_event, look up matching send by PID+FD
func (a *Agent) correlate(recv RecvEvent) *LLMCallEvent {
    key := fmt.Sprintf("%d:%d", recv.PID, recv.FD)
    pending, ok := a.pending[key]
    if !ok {
        return nil // no matching send — HTTP keep-alive mid-stream
    }
    delete(a.pending, key)
    return &LLMCallEvent{
        PID:             recv.PID,
        Model:           pending.Model,
        AuthKeyHash:     pending.AuthHash,
        PromptTokens:    parseUsageFromResponse(recv.Payload),
        CompletionTokens: parseCompletionFromResponse(recv.Payload),
        LatencyMs:       (recv.TS - pending.SendTS) / 1e6,
        Endpoint:        a.resolveEndpoint(recv.FD),
    }
}

There is an important edge case: HTTP/2 multiplexing and TLS. If the application uses HTTP/2 over TLS (which OpenAI’s API supports), the payload captured by tcp_sendmsg will be encrypted ciphertext, not plaintext HTTP. In this case the kernel-side BPF program cannot directly read the model name from the payload.

Two workarounds exist:

  1. uprobes on SSL_write/SSL_read — attach at the OpenSSL or BoringSSL function boundary in userspace, where the data is still plaintext. This requires knowing the library path and works per-process rather than globally.
  2. LD_PRELOAD interception — inject a shim that intercepts TLS write calls. More portable across TLS libraries but requires more deployment ceremony.

For internal microservices calling self-hosted models over plain HTTP, neither workaround is needed. The LLM endpoint IP filtering plus unencrypted payload capture is sufficient.

eBPF Maps as Kafka Compacted Topics — The Distributed Systems Analogy

DS analogy — mine

eBPF maps are like Kafka compacted topics. The kernel maintains the latest state per key — in our case PID+FD → connection metadata — exactly the way a compacted Kafka topic retains only the most recent value per message key. When a connection closes (FD is released), the BPF program deletes the map entry, just as a tombstone message removes a key from a compacted log. The userspace agent reading from the BPF ring buffer is the consumer: it processes events in order, joins them with state from the map, and produces downstream records. You have already operated this exact pattern — compacted topics as state stores, ring buffer as the event stream, consumer as the enrichment join. The mental model transfers directly. The only difference is that the “broker” is the kernel and the “retention policy” is enforced by the verifier.

This analogy is load-bearing for thinking about failure modes too. A Kafka compacted topic can lag if the consumer falls behind. A BPF ring buffer can drop events if the userspace agent is too slow to drain it. The same backpressure thinking applies: if the agent is blocked on a slow Kafka producer, ring buffer events get dropped silently. The fix is the same as in stream processing — async producer with local buffering and a drop counter exposed as a metric.

Why This Matters for AI Observability

The eBPF approach delivers three things that SDK instrumentation cannot.

Shadow LLM usage detection

If an engineer on a team builds a quick internal tool that calls GPT-4o directly — not through the platform gateway, not through any instrumented wrapper — their costs will be invisible to every SDK-based monitoring system. The eBPF probe catches it regardless. The auth_key_hash field in the event will reveal which API key was used, even if that key was never registered with the platform.

This is the “shadow LLM” problem: usage that exists on the invoice but not in any observability dashboard. It is the AI infrastructure equivalent of shadow IT.

SDK-less microservices

Any service that calls an LLM endpoint over raw HTTP — whether by design or because the team is using a language without a maintained SDK — is fully covered. This is especially relevant for polyglot shops where Rust, Go, and Java services coexist with Python ML services.

Retroactive instrumentation

Once the eBPF agent is deployed to the node, all existing services on that node are instrumented without redeployment. No SDK version bumps. No restart required. No coordination with application teams. This is the same operational model as Cilium: you deploy it to the cluster, and network observability appears for all pods simultaneously.

100% Language coverage
<2% CPU overhead

Security and CAP Constraints

eBPF is powerful and the Linux security model reflects that. Deploying an eBPF probe agent requires elevated privileges that have real security implications.

Required capabilities

To load BPF programs and attach probes, the agent needs one of:

  • CAP_SYS_ADMIN — the traditional catch-all; required on kernels older than 5.8
  • CAP_BPF + CAP_PERFMON — introduced in Linux 5.8 as a more granular split; preferred for new deployments

In Kubernetes, this means the DaemonSet pod must run with securityContext.capabilities.add: [BPF, PERFMON, NET_ADMIN] or with privileged: true. Neither option is comfortable in a shared multi-tenant cluster, which is why eBPF-based observability tools typically run as cluster-level infrastructure rather than tenant workloads.

seccomp implications

seccomp profiles whitelist which syscalls a process may make. A container with a strict seccomp profile that doesn’t allow bpf(2) syscalls will fail to load BPF programs. The runtime default seccomp profile in most Kubernetes distributions blocks bpf(2). The agent needs either a custom seccomp profile that permits it or the Unconfined seccomp setting (which is broader than necessary).

The privilege-vs-coverage tradeoff

This is the core tension of the eBPF approach for LLM observability:

Approach Coverage Privilege Required Deployment Friction
SDK instrumentation Only SDK-using services None Per-service integration work
LLM gateway proxy Only calls routed through gateway None (app-level) Requires routing migration
eBPF probe agent All calls on the node CAP_BPF + CAP_PERFMON One DaemonSet, cluster admin approval
eBPF + uprobes (TLS) All calls including HTTPS CAP_BPF + CAP_PERFMON + library paths Higher complexity, per-runtime tuning

For most organizations, the practical deployment is a hybrid: SDK instrumentation for services that already have it, an LLM gateway proxy for new services, and the eBPF agent as the backstop that catches everything else. The three sources feed the same Kafka topic with a source tag; the cost attribution system deduplicates on request_id.

BCC Tools and the Proof-of-Concept Pattern

Before writing production BPF programs in C, it is worth prototyping with BCC (BPF Compiler Collection) or bpftrace. Both let you write BPF programs in a higher-level syntax and run them interactively.

A one-liner to trace all sendmsg calls to port 443:

sudo bpftrace -e '
kprobe:tcp_sendmsg {
  $sk = (struct sock *)arg0;
  $dport = $sk->__sk_common.skc_dport;
  if ($dport == 0xBB01) {  // port 443 in big-endian
    printf("PID=%d COMM=%s send to :443\n", pid, comm);
  }
}'

This proves the probe attachment works before you invest in the full ring buffer + userspace agent stack. BCC provides Python bindings that let you write the kernel BPF program in C but drive it from Python, which is excellent for iteration speed:

from bcc import BPF

prog = """
#include <linux/ptrace.h>
#include <net/sock.h>

BPF_HASH(conn_map, u64, u32);

int kprobe__tcp_sendmsg(struct pt_regs *ctx, struct sock *sk) {
    u64 key = (u64)bpf_get_current_pid_tgid() << 32 | (u32)sk;
    u32 dport = sk->__sk_common.skc_dport;
    if (dport == htons(443)) {
        conn_map.increment(key);
        bpf_trace_printk("LLM send pid=%d\\n", bpf_get_current_pid_tgid() >> 32);
    }
    return 0;
}
"""
b = BPF(text=prog)
b.trace_print()

The Cilium team’s tetragon project is the production-grade version of this pattern: a Kubernetes-native eBPF security observability tool that attaches probes at the system call boundary and streams events to a gRPC endpoint. The LLM tracing use case follows the same architecture.

The Bigger Picture — What eBPF Changes for AI Infrastructure

We are at an early moment in AI infrastructure observability where the tooling gap is significant. Application Performance Monitoring (APM) vendors are adding LLM tracing features, but they all require SDK integration. The cloud providers are adding per-request logging APIs, but you have to opt in and they only cover calls through their own endpoints.

eBPF represents a different bet: instead of instrumenting the application layer, instrument the syscall layer. This is the same architectural decision that Cilium, Falco, and Pixie made for network observability, security monitoring, and service mesh metrics respectively. All three have seen production adoption at significant scale.

The LLM HTTP tracing use case is actually easier than the network policy enforcement case (Cilium’s primary use case) because:

  • we are read-only (no packet modification required)
  • we only care about a small set of destination IPs and ports
  • the payload structure is predictable JSON over HTTP/1.1 or HTTP/2
  • latency requirements are loose (we tolerate ring buffer batching delays)

The harder part is the organizational and security story. Getting CAP_BPF granted to a DaemonSet in a production cluster requires security team review. The argument is straightforward — this is the same privilege model that Cilium already runs under — but it takes time.

Zero-SDK LLM tracing via eBPF is not a replacement for SDK instrumentation. It is the backstop that makes SDK instrumentation optional — and turns observability from a best-effort practice into a structural guarantee.

The Cilium Parallel — Why This Architecture Wins

Cilium’s key insight was that the sidecar proxy model (Envoy, Linkerd) required injecting a new process into every pod, creating operational overhead and latency. eBPF network policies run in the kernel and require nothing from the application or the pod spec.

The LLM observability parallel is identical.

SDK instrumentation is the sidecar model: you must modify every application. The eBPF probe agent is the Cilium model: deploy it once to the node and get coverage for free.

The performance characteristics are also similar:

Property Sidecar proxy (Envoy) SDK instrumentation eBPF agent
Latency overhead 1–5ms per request ~0.1ms (in-process) ~0.01ms (kernel hook)
Memory overhead 50–150MB per pod SDK library (~10MB) BPF maps + agent (~20MB total)
Coverage All traffic through proxy Only SDK-using code paths All TCP calls on the node
Deploy ceremony Mutating webhook, pod restart Dependency + code change DaemonSet, one-time cluster setup
TLS handling Terminates and re-encrypts Before encryption Needs uprobes for TLS
