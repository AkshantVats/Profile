Day 31 — OpenTelemetry Semantics for Agents

Span kinds, attributes, and what to standardise now

AS
Akshant Sharma
AI Learning · Day 31 of 150
July 3, 2026
15 min read

When I started building TraceForge, I reached for OpenTelemetry the same way I’d reach for it when adding observability to any HTTP service. I expected to find a semantic conventions page for agents the same way I find one for http.method or db.statement. I found a GitHub issue with 47 comments and no resolution instead.

That’s not a failure of the OTel project — it’s actually the right moment to be building here. The OpenTelemetry GenAI SIG (Special Interest Group) is actively drafting conventions for LLM calls right now, in 2026, which means the choices I make today in TraceForge’s ClickHouse schema are being made while the standard is still forming. Some of those choices will align with the final spec. Some won’t.

The concrete question I kept returning to: which attribute names do I put in a ClickHouse ORDER BY today, knowing I’ll still be reading them in two years? This post is how I arrived at an answer.

What OTel Gives You Without Any Standard

OpenTelemetry has two layers that are completely stable and universal, requiring no domain-specific conventions: identity and classification. Every span, regardless of what it represents, gets both for free.

The identity layer consists of three fields: TraceId (128-bit hex, 32 chars), SpanId (64-bit hex, 16 chars), and ParentSpanId (empty for root spans). These are wire format, not semantic. A Jaeger instance receiving your agent spans via OTLP will reconstruct the full execution waterfall from these three fields alone — no convention required. The tree structure is implicit: a span with no parent is a root; every other span attaches to its parent by ID.

The classification layer is SpanKind, and four values matter for agent work. CLIENT means your code is calling an external service — the right kind for an LLM API call, a vector database query, any outbound HTTP. INTERNAL means a step inside your own process — the right kind for tool dispatch logic, planning loop iteration, in-process computation. SERVER means your agent is acting as the responder — receiving a request from an orchestrator above it. PRODUCER means your agent is emitting work to a queue, not waiting for a response — a Kafka publish, an SQS send, a sub-agent handoff over a message bus.

For a Claude Code agent run
The top-level model call is CLIENT — your orchestrator is calling the Anthropic API. The tool calls dispatched by the model response are INTERNAL — your harness is running them inside the same process. A sub-agent spawn that hands work to a separate process via Kafka is PRODUCER. The sub-agent’s own model call is CLIENT again.

With just these three identity fields and SpanKind, Jaeger and Grafana Tempo will visualise your agent’s execution tree correctly, with swimlane grouping and waterfall timing. The entire observability frontend — built for microservices — works for agents before you add a single agent-specific attribute.

Attributes Are Kafka Message Headers

The mental model that unlocked attribute design for me came from Kafka. Every Kafka message carries a payload and an optional set of headers: arbitrary key-value pairs attached alongside the message, readable by any consumer that knows to look for them. You can add a new header without changing the message schema. Consumers that don’t read the new header are unaffected. Headers are the extensibility mechanism.

OTel span attributes work the same way. A span’s identity and timing — trace ID, span ID, start time, end time, status — are fixed in the wire format. Attributes are arbitrary typed key-value pairs you attach to a span. Adding traceforge.cost.usd to every span today doesn’t touch the consumers that only read http.method. You can add, remove, and rename attributes in your instrumentation without breaking existing queries, as long as you don’t break anything that’s been promoted to a first-class column.

The difference from Kafka headers: OTel attributes are typed (string, int64, float64, bool, or arrays thereof), not opaque bytes. And OTel has semantic conventions — agreed attribute names — so two teams independently instrumenting their LLM calls end up with gen_ai.usage.input_tokens in both datasets and can be joined without a mapping table.

Non-software analogy — luggage tags
An airline’s baggage system attaches a printed tag (identity: barcode, flight, destination) to every bag. The tag format is standardised. Airlines also attach optional sticky labels: fragile, priority, oversized. These labels are attributes — arbitrary key-value pairs that any handler can read and act on. Adding a new label type (say, “lithium battery inside”) doesn’t require redesigning the tag format. Handlers that don’t need to act on lithium battery status ignore it. OTel attributes work the same way.

The practical consequence is that you can evolve your agent instrumentation incrementally: add new attributes as you discover what you need, promote the frequently-queried ones to ClickHouse columns, leave the rest in an attributes map. You’re not committing to a final schema on day one — you’re committing to the three attributes that drive your most important queries.

Where the Standard Is Today

The OpenTelemetry GenAI SIG is drafting semantic conventions for LLM calls. As of mid-2026, the draft is still in-progress — not stable, not a formal release — but stable enough to read and plan against. The current proposal covers the single LLM API invocation span with these attributes:

AttributeTypeMeaning
gen_ai.systemstringLLM provider: openai, anthropic, vertexai
gen_ai.request.modelstringModel ID requested by the caller
gen_ai.response.modelstringActual model ID used (may differ from requested)
gen_ai.usage.input_tokensintPrompt token count
gen_ai.usage.output_tokensintCompletion token count
gen_ai.operation.namestringchat, text_completion, embeddings

This is a good foundation for the model call span — the single LLM API invocation. What it doesn’t yet cover is the broader agent execution model. There are no conventions for tool calls as child spans of a model call, for sub-agent invocations, for a tool kind taxonomy that distinguishes retrieval from code execution, or for cost in USD.

Cost in USD is notable by its absence. The SIG classifies it as a business attribute rather than a technical one, which is a reasonable distinction: two teams can instrument the same LLM call and get identical token counts, but cost depends on their contract pricing, their discount tier, their region. The SIG is defining the technical measurement layer, not the billing layer. Cost belongs in a project namespace, not gen_ai.*.

The practical guidance: use gen_ai.* for model call spans when these attributes are stable enough to adopt — they’re close. For everything else — tool calls, tool kind, sub-agent spans, cost — use a project namespace (traceforge.*) until the standard catches up. You can migrate the column names later; the data doesn’t care what the column was called when it was written.

Three Attributes to Lock In Before v1

The question isn’t whether to follow the standard versus use your own names. It’s: which attributes are you putting in a ClickHouse ORDER BY or PRIMARY KEY? Those are the ones that hurt to rename because renaming them requires a table migration and rewriting every query that touches them.

In TraceForge’s lensai.agent_spans table, the ORDER BY is (started_at, trace_id, span_id). Those are OTel identity fields — never changing. The three mutable attributes that also deserve a stable name are these:

1. tool_kind — a LowCardinality(String) in ClickHouse. This is the column most likely to anchor a GROUP BY in cost analytics: “total cost by tool category this week.” Lock in the enum values now: retrieval, code_execution, browser, file_io, sub_agent, model_call, unknown. Adding new values later is cheap. Renaming an existing value breaks every dashboard that has it hardcoded as a filter.

2. model — a plain string. Every cost query groups by model: “which model did this agent run use, and what did it cost?” The value format matters: use the full model ID (claude-sonnet-4-6, not claude-sonnet or sonnet) because you will eventually want to compare cost across patch versions of the same model family. Abbreviated model names make this impossible without a lookup table.

3. cost_usd — a Float64 column, not buried in an attributes map. The GenAI SIG draft doesn’t include cost — this is the one genuinely new field in the agent span schema versus a standard gRPC span. It must be a first-class column because you run sum(cost_usd) constantly: per-trace cost rollups, per-agent budget tracking, per-user spend limits. Extracting a float from a JSON attributes map is possible in ClickHouse, but it’s slow and the query is ugly.

Everything else — input_tokens, output_tokens, error_message, agent_id, tenant_id — can live as columns today but migrate without pain tomorrow. They’re not in the ORDER BY and not in the GROUP BY of your most important queries. The three you lock in are the three that would require a full table rebuild to rename.

What the Spans Look Like in Practice

A complete agent run produces two kinds of spans: the root model call span (SpanKind CLIENT) and child tool call spans (SpanKind INTERNAL). The model call span carries the gen_ai.* attributes alongside the TraceForge fields. The tool call span carries only TraceForge fields — there are no GenAI SIG attributes for tool calls yet.

The root model call span, from lensai.agent_spans:

Span tree anatomy
The two spans above share a trace_id. The Bash span’s parent_span_id is the model call span’s span_id. Jaeger reads these two rows from ClickHouse and renders: a root “claude-sonnet-4-6” span of 7800ms containing a child “Bash” span of 4200ms. The waterfall shows exactly when the model finished reasoning and when the tool execution completed.

The model field is empty for the Bash span because model is a model identifier — it only has meaning for spans that invoke an LLM. Setting it to an empty string rather than null means ClickHouse can use the column in a WHERE model != '' filter without handling nulls, which matters when the column is in a hot query path.

The ClickHouse Query This Unlocks

The design decision in section 4 — tool_kind as a first-class column — directly enables this query:

SELECT
    tool_kind,
    count()           AS span_count,
    sum(tokens)       AS total_tokens,
    sum(cost_usd)     AS total_cost_usd,
    avg(latency_ms)   AS avg_latency_ms
FROM lensai.agent_spans
WHERE started_at >= now() - INTERVAL 7 DAY
GROUP BY tool_kind
ORDER BY total_cost_usd DESC;

Without tool_kind as a first-class column, this query doesn’t run cleanly — you’d need a JSONExtractString(attributes, 'tool_kind') call inside the GROUP BY, which forces ClickHouse to deserialise the attributes JSON for every row in the scan, eliminating the column projection optimisation that makes this query fast even at tens of millions of rows.

You can argue about the attribute naming prefix — traceforge.tool_kind versus gen_ai.tool_kind versus just tool_kind — but the query above works regardless of the prefix, as long as you made the column choice before the first row was written. Align on attribute names with the standard when it stabilises. What you can’t change cheaply is whether a value is a column or a JSON key — that’s the decision to make before v1.
