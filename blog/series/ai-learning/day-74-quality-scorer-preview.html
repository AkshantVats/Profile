Day 74 — Quality Scorer Preview

A router that only weighs cost and latency is optimizing half the problem. RouteIQ's fourth module, model-quality-scorer, is what lets quality join that formula — scored the same way a Kubernetes scheduler scores a node: asynchronously, off the critical path, from numbers computed before the decision ever had to be made.

Tomorrow, model-quality-scorer closes the loop RouteIQ has been building toward since Day 60. Today's ticket is prompt-fingerprinter polish, but its DESIGN.md update previews the shape of that closing piece — and the preview is worth its own post, because the scoring problem it describes doesn't fit the request path at all.

A Router That Can't See Quality Yet

RouteIQ's arc so far has built two of three signals a routing decision needs: semantic-cache-engine (Day 60) and cost-budget-enforcer (Day 65) both feed a router's cost and latency picture. Neither says anything about whether the model actually answered well. A router optimizing cost and latency alone will happily route every request to the cheapest, fastest model available — right up until "cheapest and fastest" stops correlating with "good enough," and nothing in the formula would have noticed.

So what: a two-signal router isn't wrong, it's incomplete — it optimizes the two things that are cheap to measure synchronously and stays blind to the one thing that isn't.

Why Quality Can't Be Measured Inline

Cost is a lookup. Latency is a timer. Quality requires judgment — in this design, a second model (Haiku) scoring the first model's output against a rubric defined per task_type. That judge call costs its own latency and its own money, on top of the request it's evaluating. Blocking the router on it would mean paying the exact cost RouteIQ exists to avoid, just to decide where to route.

DS analogy — Kubernetes scheduler node scoring
A Kubernetes scheduler picking a node for a pod doesn't live-benchmark every candidate node's actual future performance before deciding — it scores nodes against already-known signals (resource balance, affinity, spread) computed ahead of the decision, then picks the highest-scoring one in milliseconds. Live-measuring "how well would this pod actually run here" for every candidate, for every pod, would make scheduling itself the bottleneck. The scheduler's whole design assumes scores are precomputed and cheap to read, never computed fresh on the critical path.

model-quality-scorer's Day 78 plan takes the identical position: a Kafka consumer on judge-requests batches calls to the judge model against the shared rubric template, off to the side of the request path entirely, and persists raw scores plus rationale to a ClickHouse quality_scores table. The router, when it eventually reads a quality signal, reads a precomputed number — the same shape as a scheduler reading a node's precomputed score.

So what: "async" here isn't an implementation convenience, it's the only shape that keeps quality's cost off a path that's supposed to stay cheap — exactly the constraint a synchronous design would have no way to satisfy.

From Scores to One Number a Router Can Use

Day 79's plan normalizes judge outputs to a 0–1 scale and rolls them up per model_id × task_type on 1h and 24h windows, with a documented statistical noise floor — a rollup built on a handful of samples isn't a confident signal, and the plan calls that out explicitly rather than letting a thin rollup masquerade as a solid one.

200Target samples/hour/tenant
2Rollup windows — 1h and 24h
0Judge calls on the request path

Day 80 spends that rollup: a weighted utility U = w_q·quality − w_c·cost − w_l·latency, tenant-overridable weights, tying quality's rollup number together with the cost and latency signals the arc's first two modules already produce — and tie-breaking toward the cheaper model when two candidates land within an epsilon of each other on U.

So what: the utility function is where three independently-computed signals stop being three separate dashboards and start being one routing decision — and it only works because none of the three had to be computed at decision time.

A router can only combine signals it already has. Everything model-quality-scorer builds is really just making sure quality has a number waiting when RouteIQ finally asks for it.

So what: today's DESIGN.md preview isn't scope creep on a polish day — it's the same discipline as writing a design doc before any other RouteIQ module got its first line of runtime code, applied one module early because the shape of the dependency was already clear.
