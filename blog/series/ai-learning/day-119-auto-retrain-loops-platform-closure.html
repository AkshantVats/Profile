Day 119 — Auto-Retrain Loops — Platform Closure

DriftWatch→FineForge is event-driven architecture: five packages, four separate build days, and a loop that only closes because each hop's output happens to be the next hop's input — not because anyone drew a feedback controller.

Product essay narrates closed loop. That's today's hook, and the literal source is driftwatch-launch/PRODUCT_ESSAY.md — the doc that, for the first time, pitches DriftWatch's four modules as one product instead of four separate READMEs, and ends with a paragraph naming the one link in its own chain that's "built, tested, and deliberately not trusted with unattended authority yet."

That sentence is doing more work than it first looks like. It's claiming an architecture pattern — event-driven, closed-loop — and admitting in the same breath that the loop isn't closed in production.

This post is about what actually makes a chain of independently-shipped Go packages a closed loop at all, using DriftWatch's real code as the worked example instead of a diagram invented for this post.

A Loop Is Just Matching Contracts

Event-driven architecture means components talk by emitting and reacting to discrete events instead of calling each other's functions directly — a detector doesn't invoke a notifier, it produces a fact, and something downstream decides what to do with that fact.

The word "loop" adds one more requirement on top of that: somewhere downstream, an action gets taken that would, if it actually ran, change the thing the first stage is measuring. A pipeline that only ever produces alerts is a chain, not a loop — nothing it does ever feeds back into what the detector sees next.

DriftWatch's chain earns the word "loop" specifically because its last hop is a retrain request: if FineForge retrained the model and the new model shipped, the CUSUM detector's next window would see the effect of that retrain, closing the circle back to stage one.

The Real Chain, Hop by Hop

Strip the product name off and count the actual packages: four, shipped across four separate days, each tested in isolation before any of them had run in the same process as the others.

drift-detector/pkg/cusum.EvaluateRange (Day 105) walks a segment's hourly means against a rolling baseline and flags a sustained shift — a cumulative-sum control chart, the same statistical tool factories have used on manufacturing lines since the 1950s, not a single noisy sample triggering an alarm.

On an alarm, cusum.BuildAlertPayload (Day 107) attaches up to 20 redacted worst-scoring samples and the alarm's window boundaries to an AlertPayload struct — evidence a human can act on, not just a boolean.

alert-rule-engine/pkg/rule.Evaluator (Day 111–112) then walks a compiled escalation ladder against that alarm, keyed by (rule_id, tenant), and applies a 30-minute dedupe window so a flapping condition doesn't refire the same step twice.

Each due escalation step names a notify channel and, on the ladder's last rung, an action. Two different packages pick that step up from there: pkg/notify.Dispatcher (Day 116) routes the channel name to a SlackNotifier or PagerDutyNotifier, and pkg/fineforge.HTTPRetrainClient (Day 113) is what the fineforge_retrain action calls.

So what: naming five hops instead of one "DriftWatch pipeline" isn't pedantry — each package was tested against fakes on its own day, long before any of them met each other, and that's the entire reason today's question ("does this compose") was still open until it was checked.

DS analogy — a smart thermostat's break-in period
A smart thermostat automates two things the day it's installed: reporting the current temperature to an app, and pushing an alert if the house drifts outside a comfort band while nobody's home. What it doesn't do on day one — even though the relay to the furnace is already wired — is take unattended action, running the furnace on its own judgment without a human confirming the pattern first. Manufacturers gate that last step behind a break-in period of observed, approved decisions, not because the relay is hard to wire, but because a wrong automatic furnace cycle costs real money and, on a gas system, carries real risk, while a wrong push alert costs someone ten seconds of reading a notification they didn't need. DriftWatch's retrain webhook sits in exactly that break-in period: fineforge.HTTPRetrainClient is wired and tested against an httptest stand-in for the furnace, and it still isn't the thing deciding on its own when to fire.

So what: a wiring diagram that includes the auto-action arrow doesn't mean the system is ready to pull that trigger — readiness is earned per stage, on its own timeline, the same way a thermostat earns the right to run the furnace unattended only after its detector-and-alert stage has a track record.

Three of those five arrows are solid because nothing downstream of them decides anything irreversible: an alert payload is just evidence, a dedupe check just decides whether to speak this tick, and a Slack or PagerDuty message just costs a human a few seconds of attention if it turns out to be nothing.

The dashed edge is dashed because it's the one arrow where a false positive has a qualitatively different cost — it would kick off real compute against a real model, unsupervised, on a product (FineForge) that doesn't have a repo yet and by extension has no accumulated false-positive track record to earn trust against.

So what: an architecture diagram is allowed to draw an edge before that edge is trusted to run unattended — the mistake isn't drawing it, it's reading "the diagram shows it" as "the system does it."

One Test Already Proved Three of These Compose

Day 115's integration test is the answer to "does this actually compose," and it predates pkg/notify by a day, so it's scoped to the detector-to-webhook half of the chain: a synthetic drift fixture walks, unmodified, through the real cusum.EvaluateRange, a real BuildAlertPayload, a real rule.Evaluator, and a real fineforge.HTTPRetrainClient, landing as one deduplicated request at an httptest stub.

The detail worth citing without re-deriving the whole test: it asserts a correlation ID survives unchanged from the injected fixture all the way through BuildAlertPayload, because AlertPayload carries that identity on a RequestID field, not a separately-invented trace ID the day's own brief had guessed at three days early.

cmd/demo (Day 118's README) shows the same linkage a different way — it builds a real fineforge.RetrainRequest whose Window field is copied directly from the AlertPayload.WindowStart/WindowEnd that the same run's CUSUM alarm produced, printed live rather than asserted in a test.

So what: "these packages compose" isn't an architectural claim taken on faith here — it's a passing assertion on one specific field (RequestID) surviving one specific handoff, which is a narrower and more honest claim than "the pipeline works," and exactly the kind of claim a closed-loop diagram needs backing it up hop by hop, not as one blended promise.

The Notify Side Is a Parallel Branch, Not a Later Step

pkg/notify.Dispatcher (Day 116) is a map[string]Notifier that routes an escalation step's channel name to a SlackNotifier or PagerDutyNotifier, both of which consume the same six-field Envelope struct — RuleID, Severity, Summary, EscalationStep, Tenant, RunbookURL — and translate it into a completely different wire request each.

That's worth naming precisely because it isn't a fourth sequential hop after the retrain webhook; it's a second consumer of the same escalation step, running alongside fineforge_retrain rather than before or after it.

One rule evaluation, two independent downstream actions with two very different blast radii — a page a human reads and dismisses, or a POST that would, if live, retrain a production model — is the actual shape of "closed loop" here, not a single straight line.

A closed loop doesn't require one big feedback controller. It requires every hop's output type to already be the next hop's input type — and the one hop where that's still true only in a test and a demo, not in production, is the one everyone should be watching.

So what: the moment a "loop" fans out into two branches with different risk profiles, the honest question stops being "is the loop closed" and becomes "which branch is closed, and which one is still earning that" — which is exactly the question Day 118's post asked about DriftWatch on its own, one level down from where this post is asking it.

The Generalizable Shape Underneath DriftWatch

None of the five packages above know they're part of a "closed loop." cusum doesn't import rule, rule doesn't import notify or fineforge, and nothing here has a class named Loop or Pipeline.

What makes the chain read as one system from the outside is narrower than that: each package's public output type is exactly the type the next package's public function already expects, so wiring two of them together is a function call, not a translation layer.

That's the pattern worth carrying past DriftWatch specifically — an event-driven closed loop is a chain of small, independently-testable producer/consumer contracts that happen to compose, not one monolithic feedback-control system designed as a single unit from day one.

Every arrow in today's diagram is either a passing test assertion, a printed demo run, or an honestly-dashed line — and that's a more useful map of a platform's actual maturity than a wiring diagram that draws every edge the same weight regardless of what backs it.
