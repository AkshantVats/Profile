Day 27 — OpenTelemetry Collector as Integration Hub

Exporters, processors, and why LensAI speaks OTel natively

AS
Akshant Sharma
AI Learning · Day 27 of 150
June 10, 2026
13 min read

Collector processors are middleware — you’ve shipped worse middleware under more load. The OpenTelemetry Collector is a binary you run between your services and your observability backends. It receives telemetry in any of a dozen formats, transforms it, filters it, samples it, and routes it to one or more destinations.

Every production observability system eventually re-invents this pipeline from scratch using homegrown code. The Collector is the version of that code that other people have already debugged at scale.

I came to OTel through a frustrating experience. At Delivery Hero, we had four separate telemetry agents running on each Kubernetes node: one for metrics to Prometheus, one for traces to Jaeger, one for logs to Elasticsearch, and a custom shipper for our event bus. They consumed more CPU together than some of the business logic pods they were observing.

Each agent had its own configuration syntax, its own failure mode, and its own on-call rotation. When OpenTelemetry’s Collector reached production stability, it was immediately obvious that this was what we should have built — a single data plane for all signal types, configured in one YAML file, operated by one team.

This post is about understanding the Collector’s architecture: how receivers, processors, and exporters compose into pipelines, where the interesting engineering problems live, and why LensAI’s ingestion layer emits OTLP natively rather than inventing a proprietary format. The goal is to be able to read a Collector config and understand what it is doing, not to memorize flags.

DS analogy — airport baggage system
Think of the Collector as an airport baggage sorting facility. Receivers are the check-in desks: bags arrive from different airlines in different formats (carry-on tags, checked-bag barcodes, priority stickers). Processors are the conveyor belts and sorting machines: they read the tags, re-route bags with connecting flights, strip tags that are no longer valid, and merge carts heading to the same gate. Exporters are the departure gates: each bag ends up at exactly the gate (backend) it is supposed to, regardless of which desk it checked in at. The facility does not care what airline the bag came from. It only cares about routing it correctly to the right destination, without losing it.

Receivers: how signal enters the pipeline

A receiver listens for telemetry in a specific format and protocol, converts it to OTel’s internal representation (pdata), and hands it to the processor chain. The two most important receivers for LensAI’s use case are otlpreceiver (accepts OTLP gRPC and HTTP/protobuf from instrumented services) and kafkareceiver (consumes from a Kafka topic for event-driven ingest). A third, prometheusreceiver, scrapes Prometheus-format metric endpoints for anything that doesn’t speak OTLP yet.

The receiver model has an important invariant: receivers are push or pull, not both. The OTLP receiver is push — services call it. The Prometheus receiver is pull — it calls services on a configured interval.

This distinction matters for firewall rules, service discovery configuration, and backpressure semantics. A pull receiver that cannot reach a target just misses a scrape and logs a warning. A push receiver that cannot process fast enough must signal backpressure to the sender — getting this wrong is how you create invisible data loss at the collection layer.

For LensAI, the ingestion service emits spans over OTLP gRPC. Each span carries inference event attributes: resolved_model_id, tenant_id, prompt_tokens, completion_tokens, cached_tokens, flag_variant, and latency. The Collector receives these spans and fans them out to ClickHouse (for cost queries) and Kafka (for downstream consumers like the evaluation pipeline).

The ingestion service does not know or care about either destination — it only knows about the Collector endpoint.

Processors: transform while in flight

Processors are where the Collector earns its “integration hub” title. They run between receivers and exporters, and they can do anything to the signal: add attributes, remove attributes, sample, filter, batch, transform field values, or route to different pipelines based on attribute predicates. The processor chain is ordered and deterministic — processors run in the order they are declared in the pipeline, and each processor sees the output of the previous one.

The three processors I reach for first are batch, attributes, and filter. The batch processor buffers spans before exporting, dramatically reducing the number of write RPCs to ClickHouse at the cost of a small latency increase (the timeout parameter, default 200ms). For LensAI at moderate traffic, batching reduces ClickHouse insert RPCs by 50× with no meaningful latency impact, since inference events are analyzed minutes to hours after they occur.

The attributes processor adds or modifies span attributes before export. I use it to inject collector.host (which node collected this span) and normalize resolved_model_id values that differ by casing between SDK versions. The filter processor drops spans that match a predicate — health check spans, internal heartbeats, or test traffic tagged with env=ci.

processors:
  batch:
    timeout: 200ms
    send_batch_size: 512

  attributes/normalize:
    actions:
      - key: resolved_model_id
        action: convert
        converted_type: string
      - key: collector.host
        action: insert
        value: "${HOSTNAME}"

  filter/drop-ci:
    spans:
      exclude:
        match_type: strict
        attributes:
          - key: deployment.environment
            value: ci

The most powerful and least understood processor is transform, which uses OTel Transformation Language (OTTL) to write arbitrary expressions over signal attributes. It can parse JSON from a string attribute into structured fields, compute derived metrics from existing ones, and conditionally set attributes based on other attributes.

OTTL is a small expression language — not Turing-complete, but expressive enough for the field manipulation tasks that otherwise require a custom processor plugin. Knowing OTTL exists is the difference between writing a 200-line Go plugin and writing a 10-line config block.

Exporters: routing to backends

Exporters translate OTel’s internal pdata representation into the format expected by each backend and send it. The Collector contrib distribution ships over forty exporters: ClickHouse, Kafka, Prometheus remote write, Elasticsearch, Jaeger, Zipkin, Datadog, New Relic, and more. Each exporter runs its own retry loop with configurable backoff, its own send queue (to absorb backend slowdowns without blocking the processor chain), and its own telemetry metrics (so you can observe the Collector itself via its own pipeline).

The ClickHouse exporter is the one LensAI uses most heavily. It bulk-inserts spans using the native ClickHouse protocol, with configurable LZ4 compression (a fast byte-level compression algorithm) and a TTL on the destination table. Every span attribute lands in a Map(String, String) column by default, but you can promote frequently queried attributes to top-level typed columns via the attribute_mappings block.

Promoting resolved_model_id, tenant_id, and prompt_tokens from the map to typed columns reduces ClickHouse query time by roughly 3× for the cost attribution queries that hit these fields in every WHERE clause.

Pipeline composition: connecting the pieces

A Collector pipeline is declared in YAML under service.pipelines. Each pipeline has a type (traces, metrics, or logs), a list of receivers, a list of processors (in order), and a list of exporters. A signal received on the receivers is passed through all processors in sequence, then fanned out to all exporters in parallel.

You can declare multiple pipelines of the same type, and a receiver or exporter can appear in more than one pipeline.

service:
  pipelines:
    traces/inference:
      receivers: [otlp, kafka]
      processors: [batch, attributes/normalize, filter/drop-ci]
      exporters: [clickhouse, kafka/downstream]

    metrics/infra:
      receivers: [prometheus]
      processors: [batch]
      exporters: [prometheusremotewrite]

The separation of pipelines by signal type is not just organizational. Traces, metrics, and logs have different cardinality characteristics, different retention requirements, and different downstream consumers. A single pipeline that mixes traces and metrics would force every processor to handle both, which is logically confusing and operationally fragile.

Keeping them separate means you can tune the batch processor independently for each signal type. Inference traces benefit from small batches and short timeouts for near-real-time ClickHouse queries, while infrastructure metrics can afford larger batches because Grafana dashboards refresh at 30-second intervals anyway.

The Collector also supports connectors, which allow the output of one pipeline to feed the input of another. LensAI uses a connector to compute a spanmetrics summary from the traces pipeline — request rate, error rate, and latency histograms by resolved_model_id — and pipe those metrics into the metrics pipeline for Prometheus export. This means the Grafana dashboards show live per-model error rates without any additional instrumentation in the application code; the metrics are derived from the trace data the Collector already has.

Why LensAI speaks OTel natively

LensAI’s ingestion service was designed from the start to emit OTLP rather than a custom event format. Every language SDK for OTLP already exists and is maintained by the OpenTelemetry community. The Collector’s fan-out capability means LensAI can route inference events to any backend without touching application code.

OTLP’s structured attribute model maps naturally to LensAI’s inference event schema — each span attribute is a named, typed field in the ClickHouse table.

The alternative was to invent a proprietary event format, write a custom schema, and maintain a custom ingest server. At Delivery Hero, that custom ingest server started as fifty lines and grew to three thousand lines over eighteen months as we bolted on retry logic, dead-letter queues, schema validation, and multi-tenant routing — all things the OTel Collector provides for free.

Proprietary formats are fine when you are the only consumer. The moment a second team wants the same data in a different shape, you are building a Collector from scratch anyway, just with a worse API surface.

Day 27’s code work adds an OpenAPI spec and SDK client to distributed-flagd, and the integration between flagd and LensAI’s ingestion layer depends on this OTel pipeline. When the ingestion service evaluates the model-version flag via distributed-flagd, the resolved variant is written as flag_variant on the OTLP span. The Collector routes that span to ClickHouse, where a single query shows the cost split between the gpt-4o-mini (90% traffic) and gpt-4o (10% canary) variants.

No custom metrics code, no separate dashboard — the cost attribution flows directly from the flag evaluation through the OTel pipeline to the ClickHouse query. The infrastructure composes instead of accumulating.

Operating the Collector in production

The Collector emits its own telemetry on port 8888 (Prometheus format by default). The metrics that matter most are otelcol_processor_batch_timeout_trigger_send (how often batches flush on timeout vs. on size — timeout-driven flushing means you are batching efficiently), otelcol_exporter_send_failed_requests (the first sign of backend trouble), and otelcol_receiver_refused_spans (backpressure from the pipeline to the sender). Set alerts on the refused-spans metric before anything else — refused spans are silent data loss and the first symptom of a saturated Collector.

Memory management is the Collector’s sharp edge. The memory_limiter processor should always be the first processor in every pipeline. It checks available memory before accepting each batch and applies soft and hard limits: at the soft limit it begins refusing new data; at the hard limit it forces a GC cycle.

Without this, a traffic spike can OOM-kill the Collector, taking its in-memory queue with it. The default soft limit is 80% of GOMEMLIMIT; the hard limit is 90%. These are sensible starting points, but measure the Collector’s memory footprint at your peak traffic and set GOMEMLIMIT explicitly.

An unconstrained Collector is a liability on a shared Kubernetes node. Container runtime defaults are not tuned for a process that holds unbounded in-flight telemetry.
