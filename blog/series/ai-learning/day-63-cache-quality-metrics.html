Day 63 — Cache Quality Metrics

Hit rate, precision proxy, TTL. Track thumbs-down rate on cache hits if you can — a hit rate alone tells you how often the cache fired, never whether firing was the right call.

Track thumbs-down rate on cache hits if you can.

A classifier that always predicts "yes" gets a great accuracy score on any dataset where "yes" is the common answer, and a useless one everywhere else — the score looks good precisely because it stopped measuring anything. A similarity threshold that's slightly too loose gets the same shape of lie: hit rate climbs, because a looser threshold matches more prompts, and nothing in that number distinguishes a match that was actually correct from one that merely cleared the bar.

Precision, Recall, and a Dial With Two Failure Modes

semantic-cache-engine's similarity threshold is a single dial with two distinct failure directions. Raise it — require a closer match before calling something a hit — and precision goes up: fewer of the prompts you call "duplicate" actually aren't. Recall goes down at the same time, because fewer real duplicates clear the stricter bar, so more of them fall through to a real inference call that a looser threshold would have caught.

Lower the threshold and both effects invert. There's no setting that maximizes precision and recall simultaneously — DESIGN.md's 0.94 design estimate and the shipped 0.92 default are both single points on that curve, chosen by judgment rather than read off a measured tradeoff, until something actually sweeps the curve and shows where the points fall.

So what: a single number like "0.92" describes a point, not a policy — you can't know whether it's a good point without seeing the curve it sits on.

DS analogy — a smoke detector, not a single sensitivity setting
A smoke detector tuned to never miss a real fire will also scream at burnt toast — high recall, low precision, and a lot of false alarms you learn to ignore. Tune it to only alarm on unmistakable smoke and it stays quiet through some real fires that looked ambiguous early on — high precision, lower recall, and a fire that got a few extra minutes to grow. There's no dial setting that eliminates both failure modes at once; the manufacturer's default is a stance about which one they'd rather you risk.

So what: the cache's similarity threshold makes the exact same bet, just in cosine similarity instead of parts-per-million smoke density — too loose and "close enough" prompts get treated as duplicates they aren't; too tight and the cache stays quiet on prompts that really were reusable.

A Threshold Sweep Makes the Curve Visible

Today's code adds cmd/threshold-sweep: given a held-out set of labeled prompt pairs (true near-duplicates and true distinct pairs), it classifies every pair at several candidate thresholds and reports precision, recall, and false-positive rate at each one. That's the difference between assuming 0.92 is reasonable and actually seeing what happens on either side of it.

So what: the sweep doesn't tell you the one right threshold — it turns "I chose 0.92" into "here's what 0.92 costs and buys compared to 0.88 and 0.96," which is the only form of that decision you can actually defend.

A Precision Proxy Without Ground Truth

The threshold sweep above needs labels: pairs marked "duplicate" or "distinct" ahead of time. Production traffic doesn't come pre-labeled — nobody tags a live prompt as "this was actually a duplicate of that cached one," so a live false-positive rate needs some other source of truth.

DESIGN.md's original answer was a sampled human or LLM-judge review pass over cache hits. Today's code ships the smallest real slice of that instead: a thumbs-down webhook a user can hit when a cached answer was visibly wrong, which is the hook's opening line made literal — track thumbs-down rate on cache hits if you can, because it's the cheapest real signal available before a full review pipeline exists.

The honest framing matters here: thumbs-down count divided by hit count is a lower bound on the true false-positive rate, not the rate itself. A wrong hit a user didn't notice, or noticed and didn't bother to flag, never shows up in that ratio — so a proxy reading low is evidence of "not many complaints," not proof of "few wrong hits."

So what: a proxy metric is still useful precisely because it's honest about being a proxy — the moment it gets presented as the real number, its floor becomes an invisible ceiling on how bad anyone thinks the problem is.

What Today's Sweep Actually Found

Running the sweep required a real embedding call to score similarity the same way production does — and this sandbox's OpenAI key is out of quota, confirmed by a live probe before falling back to anything. The fallback is a local bag-of-words cosine similarity over shared words, not shared meaning, run purely so the sweep tooling itself could be exercised against real numbers instead of none.

That proxy's numbers turned out to be instructive on their own: "delete my account" and "how do I delete my account" — two prompts with opposite intent, DESIGN.md's own example of a dangerous false hit — scored higher on word overlap than several genuine paraphrases that happened to use different words for the same request. Word overlap and semantic similarity are measuring different things, and this sweep's numbers are only honest evidence about the first one.

So what: every signal in this pipeline is a proxy for something you'd rather measure directly, and the useful move isn't picking the "best" proxy — it's knowing exactly which question each one is answering, and which question it just looks like it's answering.

What This Post Doesn't Prove

The honest gap: nothing here validates whether 0.92 is well-chosen against real embedding-space cosine similarity, because the sweep that ran today used a lexical proxy on a small, deliberately adversarial 24-pair set, not production traffic scored by text-embedding-3-small. The precision/recall tradeoff this post argues for is real and general; the specific numbers in today's benchmark are not evidence about the deployed threshold.

So what: "a threshold needs a measured tradeoff, not a guess" is a claim this post earns; "0.92 is that measured tradeoff's answer" is a claim only a real embedding-backed sweep against real traffic could make, and today's code took the first step toward that without pretending to have taken the second.
