Day 92 — Feature Flags Driving Experiments

Shadow percent as flag variant. A sampling rate that only a redeploy can change is a design decision hiding as a constant — modeled as a flag, it becomes something an operator can actually run an experiment on.

Shadow percent as flag variant. That's the design choice underneath today's shadow-traffic-router code PR — the fraction of production traffic DriftWatch mirrors to a shadow model isn't a number baked into a deploy, it's a distributed-flagd flag with a name, a default, and a documented behavior for when the flag service itself goes quiet.

That distinction sounds small until you ask what each option actually lets an operator do. A constant only changes on the next deploy. A flag can change while the system is running, per tenant, without anyone touching a build pipeline.

A Constant Is a Decision Hiding From the People Who'd Want to Change It

Picture shadow_percent shipped as a plain environment variable, SHADOW_PERCENT=0.01, read once at process start. It works. It's also frozen the moment the process boots — widening the sample from 1% to 5% because a candidate model needs more statistical power means a config change, a build, and a redeploy, no matter how urgent the need.

Worse, a single env var can't vary by tenant. Every tenant gets the same sampling rate whether they're a high-volume account whose 1% is already thousands of requests a day, or a low-volume tenant whose 1% is a handful — the exact asymmetry yesterday's post on shadow sampling variance flagged as a statistical-power problem.

So what: a config value that only a redeploy can change isn't neutral infrastructure — it's a decision about who gets to adjust the sampling rate and how fast, made implicitly by whoever chose to hardcode it.

Three Places a Sampling Rate Can Live

Once you accept that shadow_percent needs to be adjustable without a redeploy, there are really three places to put it, each with a different cost.

OptionChanges without redeploy?Per-tenant?Cost
Env var / static configNoNoSimplest, but frozen at boot and fleet-wide only
Database row, polledYesYesAdds a datastore dependency and a staleness window equal to the poll interval
Flag service (distributed-flagd)YesYesNeeds the flag service itself, but that infra already has to exist and be operated correctly for model-routing flags

The database option looks reasonable until you notice it's really a bespoke, weaker version of the third option — a datastore, a polling loop, and a staleness window that a real flag service already had to solve once, correctly, for a different flag.

So what: the choice isn't really "config vs. flag" — it's "build a second, smaller flag system" vs. "reuse the one that already exists and is already trusted for a harder problem."

DS analogy — a thermostat with a hard-coded safe position
A smart thermostat normally takes its target temperature from a live setting an app controls over the network. Pull the network cable, though, and a well-designed thermostat doesn't freeze at whatever it last saw, and it doesn't shut the heating off entirely — it falls back to one fixed, pre-programmed safe temperature until the connection comes back. The live setting is the flag; the safe fallback temperature is the default a flag service's fail-open behavior has to guarantee. Neither piece works without the other: a live setting with no safe fallback bricks the house on a network blip, and a safe fallback with no live setting is just a constant again.

The fail-open branch is not an afterthought bolted onto the happy path — it's resolved by the same select-shaped decision the sampled/not-sampled branch already needs, just with one more outcome. A flag lookup that errors doesn't propagate an error to the caller; it resolves to the documented default and moves on.

So what: the branch that matters most in this diagram isn't "sampled vs. not" — it's the one guaranteeing a flag-store outage degrades to a known, non-zero default instead of silently going dark.

0Redeploys needed to widen the rate
2Variants: mirror vs. skip
1Flag primitive reused, not duplicated

A sampling rate an operator can only change by redeploying isn't a tunable parameter — it's a constant wearing a config file's clothes.

Why the Weighted-Variant Model Already Fits

distributed-flagd's sdk already models a percentage rollout as a set of weighted variants — the same shape earlier flags in this repo use to send a slice of traffic to a new model version. shadow_percent reuses that exact primitive: a "mirror" variant and a "skip" variant, weights summing to the configured split, resolved per tenant.

Nothing about shadow sampling needed a new kind of flag. It needed the same kind of flag model-routing already trusted, pointed at a different decision.

So what: reusing an existing weighted-variant primitive instead of inventing a bespoke percentage field means shadow sampling inherits a fail-open contract that was already battle-tested for a different, harder-to-get-wrong decision — which model a paying tenant's request actually reaches.

What a Flag Buys That a Constant Never Could

Shadow sampling is exactly the kind of parameter that benefits from being tuned live. Widen it when a candidate model needs more statistical power to reach a confident verdict, per Day 90's variance discussion. Narrow it when the Kafka cost of the shadow-eval topic outgrows its budget.

Both of those are operational decisions that show up in a dashboard, not in a design review three weeks earlier. A flag can respond to that signal the same day; a constant waits for the next release train.

So what: a config value modeled as a flag — with a name, an owner, a default, and a documented failure mode — is what actually lets an operator run a live experiment instead of guessing the right number at deploy time and hoping it still fits three weeks later.
