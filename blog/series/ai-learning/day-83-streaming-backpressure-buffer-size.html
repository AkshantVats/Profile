Day 83 — Streaming Token Delivery — Backpressure Basics

Buffer size ties to TTFB vs memory — the same flow-control problem TCP's receive window solved at the packet layer shows up again in a streaming proxy's chunk relay, and the fix looks nothing like reading as fast as possible.

Buffer size ties to TTFB (time-to-first-byte, the delay before a client sees any response at all) vs memory. That's the entire tuning knob this post exists to explain — and the reason it needs explaining is that "just read the model's response as fast as possible and forward it" sounds like the obvious design for a streaming proxy, right up until a slow client is on the other end of the connection.

Today's fallback-chain streaming proxy relays a model's token-by-token response to a client over HTTP chunked transfer — the same "send pieces as they're ready" shape Server-Sent Events (SSE) uses to stream tokens from an LLM API. Getting that relay wrong doesn't fail loudly; it fails as a slow memory leak the first time a client can't keep up.

Why a Proxy Can't Just Read as Fast as Possible

A model streaming a response produces bytes at its own pace — a token at a time, as fast as inference allows. A client consuming that response also reads at its own pace, which might be much slower: a mobile connection, a client doing its own per-token processing, or just an ordinary network hiccup.

If a proxy sitting between them reads from the model as fast as it possibly can and stores whatever the client hasn't accepted yet, that storage grows for exactly as long as the client stays slow. One slow client costs a bounded amount of memory; a thousand concurrent slow clients, each accumulating an unbounded buffer, is how a proxy exhausts memory under a traffic pattern that looks completely ordinary from the outside.

So what: "read as fast as possible" is a design that works perfectly in every test where the client is fast, and fails specifically under the one condition — concurrent slow clients — that a production proxy is most likely to actually see.

The DS Analogy: TCP's Receive Window

DS analogy — TCP's receive window
TCP solved this exact problem decades before HTTP streaming existed. Every TCP connection has a receive window: a number the receiver advertises back to the sender, saying "this many bytes of buffer space are free right now." A sender that ignores it and blasts data anyway doesn't get punished with a crash — the receiver just drops what it can't hold, and the sender ends up retransmitting the very bytes it wasted bandwidth sending in the first place. A garden hose with someone's thumb over the end works the same way: pressure builds at the source the moment the exit is restricted, and the sender has to notice that pressure and slow down, not push harder and hope.

So what: backpressure at the application layer — a streaming proxy noticing a client has stopped accepting bytes and pausing its own upstream reads — is the identical idea TCP already proved out at the packet layer, just without a formal "window" field to read from.

The Real Knob: Chunk Size, Not a Yes/No Decision

Backpressure itself isn't a design choice a proxy gets to skip — it falls out for free the moment reads and writes happen in the same sequential loop, because a blocked write simply stops the next read from happening. The actual decision left on the table is how large a chunk to read and relay at a time, and that's where TTFB and memory pull in opposite directions.

A large buffer delays the first flush to the client: nothing goes out until enough bytes have accumulated to fill it, which directly worsens time-to-first-byte — exactly the number a streaming API's whole value proposition depends on. A small buffer flushes almost immediately, but multiplies the number of write (and network) calls per response, trading a memory saving for more per-chunk overhead.

The tempting alternative design is a goroutine reading from the model into a channel, and a second goroutine draining that channel to the client — decoupled, concurrent, feels idiomatic. It also needs its own bounded channel to avoid recreating the exact unbounded-buffer risk backpressure exists to prevent, at which point it's strictly more moving parts for the same guarantee a single sequential loop already gives for free.

A manual read-write-flush loop gets backpressure without asking for it: Write is an ordinary blocking call, so a slow client's TCP stack simply doesn't let that call return until the client has actually accepted the bytes. The next upstream Read can't happen until the write before it returns — which means at most one chunk's worth of bytes is ever in flight, no matter how far client and model drift apart in speed.

So what: the simplest implementation — one loop, ordinary blocking calls, no extra concurrency primitives — turns out to be the one that gives the exact backpressure guarantee a more "sophisticated" concurrent design would need extra code to reconstruct.

Today's Experience Post, Same Shape

Today's companion Experience post covers a compression codec migration on Agoda's WhiteFalcon cold tier — Snappy to Zstd, trading a smaller stored file for more CPU spent decoding it on every read. That's the identical shape of tradeoff this post just walked through for buffer size: one resource (storage, or memory) traded against another (decode latency, or time-to-first-byte), tuned by a single knob rather than resolved by picking an extreme.

Neither tradeoff has a universally correct setting. A cold-tier archive optimizes differently than a hot read path, the same way a bulk file-transfer proxy would tune its chunk size differently than a token-by-token LLM stream where every millisecond before the first byte is user-visible.

So what: "which resource can this system afford to spend more of" turned out to be the same question at two different layers of today's work — storage vs. CPU at Agoda's cold tier, and memory vs. TTFB in a streaming proxy.

What Comes Next

Today's chunk-size choice (32KiB, matching io.Copy's own default) is a reasonable starting point, not a measured optimum — nothing in today's work swept a range of buffer sizes against real streaming traffic to find where TTFB and memory actually cross over for this specific workload. That's a natural follow-up once the proxy has a live deployment generating a traffic shape worth tuning against, rather than the loopback-and-stub-model traffic this week's tests used.

So what: today's decision is the part worth trusting first — the mechanism is correct and tested — while the specific number (32KiB) stays a starting point until it's tuned against a workload that actually exists.
