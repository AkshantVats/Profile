Day 115 — Closing the Loop — One Integration Test, Four Products

Days 111-114 each unit-tested one package against fakes: the rule DSL, the dedupe state machine, the FineForge webhook client, the A/B router. Today's test is the first one that wires the real packages to each other and asks whether a drift signal survives every handoff intact.

Integration test asserts webhook 202.

That's the smallest possible claim, and it hides a much bigger diagram: one test file now proves that a synthetic quality-score drop can walk, unmodified, from a LensAI-shaped inference event through a real CUSUM detector, a real rule evaluator, and a real retrying HTTP client, and land as one deduplicated 202 Accepted at a webhook receiver. CUSUM here is a cumulative-sum control chart — a running tally that flags a sustained shift in a metric, not just one noisy sample, the same statistical tool factories have used on manufacturing lines since the 1950s. Days 111 through 114 built the four packages this test finally wires together; none of them had ever run in the same process before today.

In-Process, Not a Docker-Compose Stack

This platform already has a way to run its products together: INTEGRATION.md, written on Day 87, wires LensAI, TraceForge, and RouteIQ into one docker-compose stack for demos. Today's test doesn't reuse that container topology. It imports pkg/cusum, pkg/rule, and pkg/fineforge directly into one Go test binary, substituting an httptest.Server for FineForge — a product that doesn't have a repo yet.

That substitution isn't new to this test. fallback-chain/pkg/trace/integration_test.go, written on Day 86, faked a missing agent-trace-collector the exact same way, for the exact same reason: a live external dependency that's expensive or impossible to stand up on every CI push gets faked at its boundary, while everything upstream of that boundary runs for real. An in-process test is also faster and more deterministic than a container topology, and it tests exactly the code boundary that matters here — not "does the demo stack start," but "does the drift signal survive intact across three packages that were each only ever unit-tested against fakes before today."

So what: a green docker-compose demo proves the products can be deployed next to each other, which is a different claim from proving the actual function calls between them return what the next function expects — today's test is aimed at the second claim, not the first.

The correlation leg is worth a pause, because the plan going into today assumed a trace_id field that turns out not to exist. drift-detector/pkg/lensai has no Event type at all — cusum.AlertPayload carries its correlation identity on RequestID instead, the field a TraceForge span lookup would actually key off. The test asserts RequestID survives unchanged from the injected fixture through cusum.BuildAlertPayload, because that's the real contract, not the one the brief guessed at three days early.

DS analogy — a relay race baton
Each of the four packages had already been individually timed — a rule DSL clocked on Day 111, a dedupe state machine on Day 112, a webhook client on Day 113, an A/B router on Day 114 — the same way four sprinters can each run a fast solo 100 meters on separate afternoons. A relay isn't proven by four solo times, though; it's proven by one continuous run where the baton never touches the ground between handoffs, because a dropped baton at any exchange zone ends the race regardless of how fast each leg ran alone. Today's test is the first full relay this rule engine has run, not a fifth solo sprint with a slightly longer track.

So what: a passing unit test for each of four packages tells you every runner is fast; it says nothing about whether the baton — the drift signal, carrying its request ID — actually survives the handoff between any two of them, which is the specific claim this test and only this test makes.

The Concrete Result

The fixture drives a 30-sample alternating 70/90 baseline (mean 80) into a sustained drop to a raw hourly mean of 68 across 16 consecutive hourly windows — a 15% relative decline, the same shape and window count Day 110's chaos-replay fixture already verified alarms within its own sensitivity presets. Real cusum.EvaluateRange flags the drop, the real evaluator walks a three-step escalation ladder (warn at 0 minutes, page at 30 minutes, retrain at 2 hours), and the retrain step's real HTTPRetrainClient POSTs to the stub.

A second assertion inside the same test matters as much as the call count: a synthetic re-trigger, replayed a few seconds after the real firing, lands well inside that 30-minute dedupe window and produces zero additional due steps, which is why the webhook still fires exactly once. A second, fully separate test runs the identical evaluator and client against a flat, no-drift fixture across the same 16-hour span and confirms zero calls — the negative case, proving the pipeline stays quiet on a quiet signal instead of firing on anything that merely runs through it. Both tests decode the request body FineForge's stub actually received and check it field-for-field against DESIGN.md §3 Contract 1 — rule_id, segment.task_type, segment.model_id, window.start, window.end, triggered_at — not just the 202 status code sitting on top of it.

So what: a webhook that fires once with the right body and a webhook that fires zero times on silence are two different proofs that both had to pass for this pipeline to be trustworthy, and a test that only checked the happy path would have missed the second one entirely.

The Honest Limitation

This test proves the Go-level contract between three packages is correct. It does not prove the real Kafka-to-ClickHouse ingestion path that would produce a LensAI event in production, and it cannot test against a real FineForge server, because FineForge doesn't exist as a deployed service yet — only the stub does.

There's a smaller honest correction too: the original plan called for a dedicated CI job named integration to run this file. That job doesn't exist in .github/workflows/ci.yml — every module's tests, unit and integration alike, run under one go job's per-module go test -race ./... step, the same way fallback-chain/pkg/trace/integration_test.go already gets picked up with no build tag and no special wiring. A green integration test and a correctly deployed production pipeline are different claims, and no amount of in-process testing collapses them into one.

So what: writing down what this test doesn't cover is what keeps a green checkmark from being mistaken for a finished platform — the same discipline that matters more, not less, on the day a test finally spans four packages instead of one.

The Experience Bridge

Today's Experience post reaches this same trade-off from the opposite direction: BrowserStack's FaceID and TouchID automation needed a real physical device, a camera-injection rig, and real biometric hardware for a fully honest end-to-end run, which made that full stack too slow and too flaky to run on every change — so most of what needed verifying became a contract test against a faked API response instead, with only a thin layer of true end-to-end runs on top.
