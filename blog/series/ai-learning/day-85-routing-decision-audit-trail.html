Day 85 — Routing Decision Logs — Audit Trail Design

Event sourcing for which model served whom — why routing_log has to be an append-only log of every decision, not a table that only remembers the latest one.

AS
Akshant Sharma
AI Learning · Day 85 of 150

8 min read

routing_log table is source of truth for FinOps — that's today's design commitment in one sentence, and the reason it needs a full post is that "source of truth" is a much stricter requirement than it sounds. A table finance can query without a caveat attached has to survive questions nobody asked when it was designed, including questions about last month, not just right now.

Why "Currently Preferred Model" Isn't Enough for a Cost Question

The obvious way to track routing is a table keyed by tenant, holding whatever model that tenant is routed to right now. It answers "who is acme routed to today" in one indexed lookup, and it's small — one row per tenant, updated in place every time a routing choice changes.

It cannot answer "how much did acme actually spend on model calls last Tuesday," because last Tuesday's routing choice was overwritten the moment a newer one replaced it. The row that could have answered that question existed once, briefly, and then it didn't.

So what: a table that only stores the latest state has already discarded the exact history a cost question needs — not lost it somewhere recoverable, discarded it, the moment the next update landed.

DS analogy — a bank ledger vs. a bank balance
A bank balance is one number: what you have right now. A bank ledger is every transaction that ever moved that number, in order, each one keeping its own timestamp and amount forever. You could reconstruct today's balance from the ledger by replaying it — you cannot reconstruct last month's balance from today's number alone, because the number itself has no memory of how it got here. routing_log is the ledger; a "current routing state" table is the balance. FinOps needs the ledger, because "how much did we spend and on what" is a question about transactions, not about the current number.

So what: the choice isn't "log or state" as a matter of taste — it's that state is a derived, lossy summary of a log, and once a system has irreversibly kept only the summary, no later cleverness recovers the detail it threw away.

Today's routing.Event has five fields worth their place, each answering a question a thinner schema couldn't: chosen_model answers who served the request; scores answers why, carrying every candidate's score, not just the winner's, so a later question like "was the winner ever a close call" doesn't require re-running a scoring pass that already happened once; cache_hit answers whether a model was even involved, since a cache answering first is a real outcome worth a row of its own; cost_estimate_usd answers the dollar question directly, in the same row as the decision that caused it, rather than requiring a join against a separate pricing table that may have since changed its numbers.

A cache-hit row carries an empty chosen_model and a zero cost, and that's deliberate, not a gap to fill in later. A FinOps query computing "cost per request this month" needs the full request count in its denominator, cache hits included — leaving those requests out of routing_log entirely would make every request look more expensive than it actually was, on average, by simply hiding the free ones.

So what: a $0 row is still informative — the schema's job is to make every outcome representable, including the outcome where nothing was spent, because a query that can't see the free requests will always overstate the paid ones.

The Log Has to Be the System of Record, Not a Side Effect

The tempting shortcut is treating the audit log as a nice-to-have byproduct: serve the request first, and if there's time, emit an event about it afterward. That ordering quietly demotes the log to "best effort," which is the opposite of what "source of truth" is supposed to mean — a log FinOps can trust has to be as reliable as the thing it's recording, not a lower-priority afterthought bolted on next to it.

Today's design keeps that discipline structural rather than aspirational: Event.Validate runs inside Marshal itself, so a caller cannot produce wire bytes for an event that wouldn't be a trustworthy row — the schema refuses to let a malformed record leave the process that created it, rather than hoping validation happens correctly downstream.

So what: "source of truth" is a property you have to design into where validation happens, not a label you can attach after the fact to whatever log already exists — a log that can silently accept bad rows was never really a source of truth, just a table that happened to be right most of the time.

A balance tells you where you are. A ledger tells you how you got there — and FinOps was always asking the second question.

Today's Experience Post, Same Backpressure Discipline

Today's companion Experience post covers a bounded, blocking channel inside WhiteFalcon's Rust consumer — sized at 10,000 events, chosen specifically so a slow Redis writer stalls the fetch loop instead of either dropping events or growing an unbounded buffer toward an OOM. The routing_log consumer landing today needs that same property for a different reason: an audit log that silently drops events under load stops being a source of truth exactly when load is high enough to make the cost data matter most.

It gets that property for free rather than needing its own channel to size: the batch loop fetches one Kafka message at a time and only asks for the next once the current batch has been handed to the ClickHouse writer, so it never accepts more decisions than it can currently account for. Same rule, arrived at through a simpler mechanism because the scale is smaller.

So what: an audit trail's reliability and a hot ingestion path's reliability turn out to be the same engineering problem wearing different scale — both need "never accept more than you can durably keep," whether that's enforced by a sized channel or by a loop that simply never gets ahead of itself.

What Comes Next

Nothing calls routing.Publisher.Publish automatically yet. Today's schema is deliberately caller-supplied — Scores and CostEstimateUSD are inputs, not computations this package performs itself — so that wiring a real call site later, one combining Executor.Execute's outcome with pkg/decision's per-candidate utility scores, won't require touching this event's shape at all. The schema was the part that had to be right today; the call site that fills it in is deliberately tomorrow's problem.

So what: designing the record before the thing that produces it exists is the same ordering discipline the ledger analogy already argued for — get the shape of the source of truth right first, because it's much harder to fix a schema after real rows depending on it are already flowing through it.
