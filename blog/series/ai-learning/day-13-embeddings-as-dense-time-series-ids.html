Operating the pipeline: freshness, model version migration, and SLOs for vector search

AS
Akshant Sharma

14 min read
AI Learning · Day 13 of N

Day 12 covered what embeddings are in the data-systems sense: dense IDs in metric space, ANN indexes as storage engines, write amplification under HNSW. Today is the operational question — how do you run this machinery through a model version upgrade without losing recall, degrading query latency, or creating a three-hour rebuild window that on-call dreads every quarter?

HNSW under write load feels like SSTable compaction under read pressure. You have already ops'd this class of problem. But the analogy goes deeper than write amplification: model version migrations in vector systems behave almost exactly like dropping and rebuilding a materialized view. Once you see it that way, the playbook becomes obvious.

The materialized view analogy

In a column store, a materialized view is a precomputed result stored as a first-class table — fast to query, expensive to maintain. When the underlying schema changes, you rebuild from source. You don't surgically patch existing rows; you compute the new projection, swap the read pointer, and drop the old view when confidence is high.

Embedding indexes are materialized views over your text corpus. The model is the projection function. When you upgrade from text-embedding-ada-002 to text-embedding-3-large, you are changing the coordinate system. Every existing vector is now in the wrong coordinate space. You cannot update row by row; the geometry of the entire index has to be recomputed against the new model before a single query can use it.

The mistake most teams make is treating a model version bump as a config change. It is not. It is a full materialized-view rebuild with a mandatory read-side cutover.

The embedding pipeline as an event stream

Before you can reason about migrations, you need a clear picture of the insert path. Most teams sketch it as "chunk → embed → store," which is accurate but hides the latency and failure mode surfaces that matter in production.

  CHK --> EMB[Embed model]
  EMB --> BUF["Insert buffer\n(throttle gate)"]
  BUF --> ANN[ANN index]
  ANN --> QRY[Query path]

  CHK --> META[Metadata store]
  META --> QRY

Three surfaces you need to instrument separately:

  • Chunker throughput — how fast you produce chunks. This sets the upper bound on embed model load. Chunker parameter changes (overlap, size) silently rewrite the unit of identity.
  • Embed model latency — p50 and p99 per batch size. API-hosted embedding models have rate limits; self-hosted models have GPU memory pressure. Either one can back-pressure the insert buffer.
  • Insert buffer depth — the gate between embed throughput and ANN write amplification. Unbounded write bursts are what turn HNSW maintenance into a p99 spike on the read path. This is your compaction throttle knob.

The metadata store sits beside the ANN index, not inside it. Chunk boundaries, source document IDs, model version, and ingestion timestamp live there. On retrieval, you join ANN results to metadata before returning to the caller. If you store these fields inside the vector index, a model version migration forces a metadata migration simultaneously — always split them.

Freshness, staleness, and retention policy

Time-series systems have explicit retention policies: data older than N days is dropped or downsampled. Vector indexes don't have retention by default, but the operational need is identical. Documents that are updated, deleted, or superseded need to leave the index. Stale vectors in a retrieval system don't just waste memory — they generate false retrievals that erode user trust faster than any latency regression.

ConcernTime-series analogyVector index equivalent
Data freshnessWrite-ahead lagEmbed-and-insert pipeline lag
Stale readsCompaction lag in CassandraTombstone accumulation without rebuild
RetentionTTL + downsamplingHard delete + index compaction
BackfillTopic replay from offset 0Re-embed corpus against new model

Hard deletes in HNSW are tombstones, not immediate removals. Recall degrades silently as tombstone depth grows because traversal still visits those nodes during graph search. If you don't schedule periodic index compaction (rebuild or prune), you are running compaction-free LSM trees — query quality is slowly leaking.

Model version migration: the blue/green playbook

The canonical mistake: re-embed in place. You update the model config, kick off a background job that writes new vectors over old ones, and serve queries against a half-migrated index. Recall is undefined during the window. You can't tell from a p50 query latency metric whether you are getting the old model's results or the new model's results or a mix of both.

The correct playbook is blue/green. It maps directly to shadow index: you build the new index entirely before shifting any read traffic.

flowchart TB
  CORP[Corpus] --> OLD[Re-embed: old model]
  CORP --> NEW[Re-embed: new model]

  OLD --> BIDX[Blue index\ncurrent reads]
  NEW --> GIDX[Green index\nshadow / validating]

  BIDX --> PROD[Production queries]
  GIDX --> SHA[Shadow queries\nrecall validation]

  SHA --> CMP["Recall diff\np50 / p99 / nDCG"]
  CMP --> CUT{Recall ≥ threshold?}
  CUT -->|yes| SWAP[Swap read pointer]
  CUT -->|no| TUNE[Tune ef_search / nprobe]
  SWAP --> DROP[Drop blue index]

Shadow queries are cheap if you sample — run 5–10% of live queries against the green index in parallel, compare top-k overlap, and track nDCG if you have ground truth labels. You want to see ≥90% top-3 overlap before cutting over. If the new model improves recall significantly, you may see that number go above 1.0 on your quality metrics — but watch p99 query latency independently. A new model with better recall but 40ms higher p99 requires a separate infra conversation.

The parameters that matter most during a green-index build:

  • ef_construction — graph quality during insert. Higher = better recall at build time, more write amplification. Set once per model class; don't tune per-document.
  • M (HNSW connectivity) — memory footprint per vector. Increasing M for a new model may require a VRAM capacity check before you switch read traffic.
  • ef_search — graph traversal depth at query time. The tunable you adjust during validation if recall is below threshold without rebuilding the whole index.

SLO design for vector search

The hardest part of running a vector search system is that "it works" can mean three different things: index is queryable, results are fresh, recall meets the quality bar. Most teams instrument only the first. You need all three in your SLO definition.

flowchart LR
  Q[User query] --> QE[Embed query]
  QE --> ANN[ANN search]
  ANN --> RR[Re-rank / filter]
  RR --> RES[Response]

  QE --> L1["query_embed_ms\np99 ≤ 20ms"]
  ANN --> L2["ann_search_ms\np99 ≤ 40ms"]
  RR --> L3["rerank_ms\np99 ≤ 15ms"]
  RES --> L4["total_p99 ≤ 80ms"]

  ANN --> RCL["recall@10\n≥ 0.90 weekly eval"]
  ANN --> FSH["index_freshness_lag\n≤ 5 min p95"]

Three distinct SLO buckets:

  • Latency SLO: break down the total budget across embed, ANN search, and rerank. If you only track end-to-end p99, you cannot tell whether a regression came from the embed API rate-limiting or from index write amplification degrading search.
  • Recall SLO: weekly offline evaluation against a labeled eval set. Not a real-time metric — you run it on a schedule, store results, and alert when the rolling 4-week average drops below threshold. A single bad week isn't a page; a trend is.
  • Freshness SLO: time from document ingest to queryable state. This is where the insert buffer depth metric pays off — if freshness lag is growing, the buffer is backing up, and the compaction knob needs adjusting before p99 query latency is affected.

One more alert worth wiring: model_version_mix. If you ever have documents from two different model versions in the same index (migration in progress, or a backfill that stalled), every recall number is unreliable. Make it impossible to miss.

LensAI bridge: InferenceEvent fields for vector ops

For LensAI-style observability, the fields that turn "something is slow" into "this specific path is slow" during a vector operation are:

embedding_model_id     -- which model version produced these vectors
index_operation        -- "insert" | "delete" | "rebuild" | "query"
ann_search_ms          -- query-time graph traversal only
embed_ms               -- time spent calling the embed model
insert_buffer_depth    -- current queue depth at the throttle gate
index_freshness_lag_ms -- age of most-recently-inserted chunk
model_version_mix      -- true if index contains >1 embedding model version
recall_at_10           -- from offline eval, not per-query

Without embed_ms and ann_search_ms separated, you cannot root-cause a p99 regression. Without embedding_model_id on every event, you cannot tell which model class is responsible for a recall dip. Without model_version_mix, a half-migrated index looks healthy right up until it doesn't.

This ties directly to the Week-2 README polish on infra-ai-streaming: an architecture diagram that is honest about which components produce which fields is more useful to a hiring committee than a feature list.

Takeaway

Embedding systems earn their operational complexity. The insert path is a throttled event pipeline. Model version migrations are materialized-view rebuilds with mandatory cutover gates. Freshness, recall, and latency are three distinct SLO surfaces that can diverge independently.

If you treat embedding ops like a cache — set it, query it, update config — you will discover these failure modes in production under load rather than in a controlled migration. The distributed-systems muscle you already have for data pipelines, compaction scheduling, and blue/green rollouts transfers directly. The only new vocabulary is ANN-specific: ef_construction, ef_search, nDCG. The failure modes are familiar.
