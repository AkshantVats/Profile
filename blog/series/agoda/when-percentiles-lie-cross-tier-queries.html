When Percentiles Lie: Cross-Tier Queries in a 1.8T/day TSDB

Post 2 of 5 — Agoda TSDB Series

AS
Akshant Sharma

Post 2 of 5 — Agoda Series

The first time I pulled a 7-day Grafana panel on WhiteFalcon and compared it against the sum of its daily sub-ranges, the numbers disagreed.

Not by a rounding error.

By enough to matter at an SLO boundary.

The 7-day P95 showed one number. Seven daily P95 values — weighted by request count — showed another. Same metric. Same time range. Same system.

One of them was wrong.

The dangerous part was that nothing crashed.

No alerts fired. No exceptions were thrown. The dashboard rendered perfectly. The numbers looked believable enough that most engineers would never question them.

That is the quantile merge problem.

And once you run infrastructure at scale, you eventually discover it hiding inside almost every observability system.

The Mistake Almost Everyone Makes

The naive logic sounds reasonable:

Cold tier P95 = 450ms
Hot tier  P95 = 380ms

Weighted average:
≈ 426ms

Looks correct.

It is mathematically invalid.

Because percentiles are not additive.

A P95 value only tells you:

“95% of requests were faster than this threshold.”

It tells you nothing about:

  • the shape of the distribution
  • the tail behavior
  • where requests sit relative to another dataset

And that means this operation is fundamentally impossible:

P95(A ∪ B) = f(P95(A), P95(B))

No arithmetic function f exists that can reconstruct the true percentile from already-compressed percentiles.

Once distribution shape is discarded, it is gone forever.

The Wrong Mental Model vs The Correct One

This realization shaped how WhiteFalcon handled cross-tier queries.

Because once data spans multiple storage systems, you either preserve the distribution shape — or you silently return wrong answers.

Why WhiteFalcon Needed Multiple Storage Tiers

WhiteFalcon is Agoda’s in-house TSDB, inspired by Apache Druid, processing roughly 1.8 trillion Kafka events per day.

At that scale, storage architecture becomes an economics problem.

Recent data needs:

  • low latency
  • fast filtering
  • real-time dashboards
  • alert responsiveness

Historical data needs:

  • cheap storage
  • high compression
  • efficient scans
  • long retention

Trying to optimize both with one storage layer is the wrong tradeoff.

So the system used two tiers.

flowchart LR

    K[Kafka Events] --> ING[WhiteFalcon Ingestion]

    ING --> HOT[Redis Hot Tier]
    ING --> IDX[RoaringBitmap Index]

    HOT --> FLUSH[Background Flush]

    FLUSH --> CEPH[Ceph / S3 API]
    CEPH --> PARQUET[Parquet Files]

    PARQUET --> NVME[Local NVMe-backed Storage]

Hot Tier vs Cold Tier

Hot Tier — Redis

The hot tier stored:

  • recent windows
  • in-memory aggregates
  • active query traffic
  • low-latency dashboard reads

Most Grafana panels never left this layer.

Cold Tier — Parquet on S3/Ceph

Once windows closed:

  • data flushed from Redis
  • serialized into Parquet
  • compacted over time
  • stored cheaply for long retention

Historical queries hit this tier.

This architecture worked extremely well operationally.

Until a query crossed the boundary.

The Cross-Tier Boundary Problem

Imagine a Grafana query:

Last 24 hours
Aggregation: P95

Redis contains:

Last 3 hours

Parquet contains:

Previous 21 hours

The query engine has to split the request:

flowchart TD

    Q[Incoming Query: Last 24h P95]

    Q --> SPLIT[Query Planner]

    SPLIT --> HOT[Redis Hot Range]
    SPLIT --> COLD[Parquet Cold Range]

    HOT --> MERGE[Merge Layer]
    COLD --> MERGE

    MERGE --> P95[Compute Final P95]

Fetching from two systems is easy.

Merging them correctly is not.

Histograms Changed Everything

The key insight was simple:

Histograms are additive. Percentiles are not.

Instead of storing:

P95 = 450ms

the system stores bucket distributions:

[0-10ms]    = 1200
[10-25ms]   = 3400
[25-50ms]   = 2800
[50-100ms]  = 1600
...

Now merging becomes trivial.

merged_bucket[i] =
    hot_bucket[i] + cold_bucket[i]

Element-wise addition preserves the full shape of the distribution.

Only after merging do we compute the percentile.

That is the entire trick.

Why This Works

Because histograms preserve information about:

  • density
  • tail distribution
  • skew
  • request concentration

Percentiles discard all of it.

Think about it this way:

P95 is a conclusion.

Histograms are evidence.

You can combine evidence.

You cannot combine conclusions.

The Query Engine Changes

Once we adopted histogram merging, three things became load-bearing invariants.

1. Bucket Schema Consistency

Every tier had to use identical bucket boundaries.

This became a system-wide schema contract.

GOOD:
[0-10), [10-50), [50-100)

BAD:
Redis:   [0-10), [10-50)
Parquet: [0-25), [25-100)

If bucket layouts diverged, merges became meaningless.

This is the kind of operational constraint that sounds trivial until you run schema evolution across distributed storage systems.

2. Parallel Tier Fetching

Hot and cold fetches ran concurrently.

t=0ms
 ├─ Redis fetch
 └─ Parquet fetch

t=45ms
 └─ merge histograms

t=46ms
 └─ return result

Without parallelism:

Redis → Parquet → Merge

Cross-tier latency would have compounded linearly.

3. Merge Before Percentile Computation

This ordering mattered enormously.

Wrong:

compute P95
compute P95
merge results

Correct:

merge distributions
compute P95 ONCE

That distinction sounds subtle.

It is the entire correctness guarantee.

The Operationally Annoying Part: Compaction

The clean diagrams hide the ugliest production detail: compaction state.

Parquet files compacted over time:

1 hour files
    ↓
3 hour files
    ↓
daily files

During compaction, the same logical time range could temporarily exist in multiple representations.

hour0.parquet
hour1.parquet
hour2.parquet

AND

3hour_0_3.parquet

Now the query planner must avoid:

  • double counting
  • partial visibility
  • stale compaction windows

This is where “simple storage architecture diagrams” stop matching reality.

Most distributed storage complexity lives here:

transitional state management

not steady-state reads.

The Real Lesson

The deepest lesson from this project was not about histograms.

It was about information loss.

Every pre-aggregation system makes a choice:

What information are we willing to destroy
to make queries cheaper later?

Raw samples preserve everything.

Percentiles preserve almost nothing.

Histograms sit in the middle.

And once you understand that framing, many infrastructure systems start looking similar:

  • stream processors
  • OLAP systems
  • observability pipelines
  • LLM telemetry systems
  • distributed caches

All of them trade storage cost against recoverable information.

Why This Matters Again in AI Infrastructure

I keep running into this exact problem again while building observability systems for LLM inference.

The architecture is almost identical:

Recent inference metrics
    → Redis hot tier

Historical inference telemetry
    → Parquet cold tier

And the metrics that matter most are also percentiles:

  • Time To First Token (TTFT)
  • decode latency
  • token throughput
  • queue latency

The same mistake appears immediately:

P95(TTFT_hot) + P95(TTFT_cold)

Still wrong.

Exactly the same reason.

LLM Systems Add One More Problem

Inference latency distributions are naturally bimodal.

Because inference has two fundamentally different phases:

1. Prefill
   - compute heavy
   - parallel
   - large KV writes

2. Decode
   - memory bandwidth bound
   - token iterative
   - latency sensitive

Combining both into one histogram produces a distribution that explains neither.

So now observability systems need:

  • separate histograms
  • separate distributions
  • separate percentile tracking
  • cross-tier correctness for both

The histogram lesson comes back again.

The Thing That Stayed With Me

There is a class of production bug worse than crashes.

Systems that return confidently wrong answers.

Crashes are visible.

Silent mathematical corruption is not.

And observability systems are uniquely dangerous here because engineers make:

  • SLO decisions
  • capacity plans
  • incident escalations
  • staffing decisions

based on those numbers.

Once engineers stop trusting dashboards, the damage lasts longer than the incident itself.

That is why this problem mattered.

Not because the math was elegant.

Because infrastructure trust is cumulative — and very easy to lose.
