Building a Production-Grade AI Inference Observability Pipeline: Architecture, Tradeoffs, and Benchmarks

May 2026 · 12 min read

I spent five months at Agoda working on a time-series database that ingested 1.5 trillion events per day. When I started thinking about what AI infrastructure actually needs from an observability layer, I kept running into the same problem — the existing tools were built for application metrics, not for the specific shape of LLM inference data. So I built one.

This post covers the architecture, the three design decisions that matter most, and the benchmark results from the first version. The code is at github.com/AkshantVats/infra-ai-streaming.

Why existing observability tools fail for LLM inference

The problem isn't volume — it's cardinality combined with high-frequency multi-dimensional data. A single LLM inference event has at minimum: model_id, tenant_id, latency_ms (broken into prefill and decode phases), prompt_tokens, completion_tokens, cost_usd, and request metadata. At scale, the cross-product of model versions and tenants creates a label cardinality that Prometheus simply wasn't designed for.

I hit this wall at Agoda. Prometheus starts degrading well before you reach the cardinality that AI infrastructure routinely produces. ClickHouse handles it cleanly because it stores data as column families — querying "give me P99 latency for model gpt-4o across all tenants last hour" is a single columnar scan, not a label lookup across millions of time series.

The core insight: LLM inference observability is a TSDB problem with a different access pattern. You need analytical queries (aggregations across model/tenant dimensions), not just alerting dashboards. That means ClickHouse, not Prometheus, as the storage layer.

Architecture overview

The pipeline is deliberately simple at the component level. Complexity lives in the reliability guarantees, not the topology:

HTTP /ingest → Rust ingestion engine → Kafka topic
                                           ↓
                                    Go consumer
                                       ↙    ↘
                                ClickHouse   Redis (circuit breaker buffer)
                                    ↓
                                 GrafanaArchitecture

The Rust ingestion engine is an Axum HTTP server that accepts batched JSON events, validates the schema, appends to a Write-Ahead Log, and produces to Kafka. The Go consumer handles the downstream write path — batching 1000 events or 500ms, whichever comes first, before flushing to ClickHouse.

The three decisions that matter

1. Write-Ahead Log before Kafka, not after

Most ingestion pipelines trust Kafka as the durability layer. The problem is the window between HTTP receipt and successful Kafka produce — if the ingestion engine crashes mid-batch, those events are gone. The WAL closes that window. Every batch is written to a local append-only log before the Kafka produce call. On restart, un-acked WAL segments replay automatically.

The cost is an extra fsync per batch. At our target throughput (1M events/min), the overhead is under 3ms P99 on NVMe. Worth it for financial and compliance workloads where event loss is unacceptable.

2. Circuit breaker with Redis overflow, not backpressure alone

When ClickHouse is slow or down, you have two options: apply backpressure upstream (drop or block ingest) or buffer the overflow somewhere. Backpressure propagates failure to the caller — the LLM gateway starts seeing 429s or timeouts, which is worse than slightly stale observability data.

The circuit breaker trips when ClickHouse write latency exceeds 2 seconds for 5 consecutive attempts. The overflow buffer goes to a Redis sorted set keyed by timestamp. When ClickHouse recovers, the consumer replays from Redis before resuming normal Kafka consumption.

3. Per-tenant rate limiting in Rust, shared state in Redis

A single high-volume tenant can starve the pipeline for others. Token bucket rate limiting per tenant_id solves this, but the state needs to be shared across multiple ingestion engine instances. A single Redis INCR with expiry is sufficient — the race condition window is small enough that brief over-admission is acceptable, and the atomic Lua script alternative adds ~0.5ms per request at high concurrency.

Benchmark results

Tested on a single MacBook Pro M3 (local Docker Compose stack with Redpanda). Production deployment would be different, but these numbers establish a performance floor:

50k events/sec12ms74ms~4k11.2k/sec

The ClickHouse write rate plateaus around 11k/sec on local hardware — this is the bottleneck. In production with a proper ClickHouse cluster and the Go consumer scaled horizontally, the ingestion side handles significantly more. The Kafka consumer lag at 50k/sec recovers within 30 seconds of load dropping.

What I'd do differently

The anomaly detection layer (z-score on sliding window per model) is too simple for production. It generates too many false positives during model rollouts when the latency distribution legitimately shifts. A proper implementation would use CUSUM or exponentially weighted moving average with separate baselines per deployment version.

The WAL segment management is also manual right now — segments don't compact or expire automatically. For a long-running deployment, this needs a background compaction job similar to what LevelDB does.
