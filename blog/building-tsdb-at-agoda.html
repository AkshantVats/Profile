The system: WhiteFalcon

Built by the Agoda team — published in their engineering blog
WhiteFalcon is Agoda's in-house TSDB, inspired by Apache Druid. Rust consumers read events from Kafka. The query engine is in Scala. Grafana sits on top for visualization. Audit data from Kafka ends up in WhiteFalcon and Hadoop for longer-term storage. The full Kafka pipeline architecture is documented in the Agoda engineering blog — linked at the bottom.

The storage architecture from my time on the team: Rust consumers read from Kafka into Redis as the hot tier, bucketed in time windows. When a window closes, a background job flushes the data to S3 as Parquet files partitioned by datetime. Ceph sits as the storage layer between the pods and S3. Compaction jobs merge hourly files into 3-hour, then daily files. The system keeps per-hour granularity for the last 3–7 days — because that is where almost all the query load is — and coarser granularity for older data.

The indexing layer uses a RoaringBitmap-backed inverted index. For each tag value, the system stores the set of series IDs where that value has been seen. A query becomes a set operation — union across values within a tag, intersect across tags, subtract exclusions. RoaringBitmap handles sparse integer distributions efficiently. The Agoda team published a detailed breakdown of this design.

What I worked on: cross-tier query engine

My contribution
Extended the Scala query engine to support queries spanning both the Redis hot tier and S3 cold tier in a single request, with correct merge logic at the tier boundary. Added 2-3 new query types accessible via Grafana.

Before this work, queries hit one tier only. If a Grafana user requested a time range that crossed the hot/cold boundary — say, the last 30 hours when the hot tier holds 3 hours — the system could not serve it natively. You'd have to query twice and stitch manually.

The query engine change is conceptually straightforward: determine what portion of the time range lives in Redis vs S3, fetch from both, merge. In practice, the merge is where it gets interesting.

The quantile merge problem

For simple metrics — sums, counts, averages — merging across tiers is arithmetic. Redis returns the sum for the last 3 hours. S3 returns the sum for the 27 hours before that. Add them. Done.

Quantile metrics are different. P95 from Redis covering the last 3 hours and P95 from S3 covering the prior 27 hours do not add up to the 30-hour P95. Quantiles are not additive.

WRONG:
  P95(Redis, last 3h) + P95(S3, hours 3-30) = 30h P95
  This is mathematically incorrect.

CORRECT:
  1. Fetch histogram bucket counts from Redis (raw distribution, last 3h)
  2. Fetch histogram bucket counts from S3 (raw distribution, hours 3-30)
  3. Merge bucket counts: add each corresponding bucket
  4. Compute P95 from the merged histogram
  This gives a mathematically correct result.

WhiteFalcon stores aggregations as histograms — bucket counts rather than pre-computed percentiles. This makes the cross-tier merge correct: merge the underlying distributions, then compute quantiles once on the merged result.

The additional query types I added gave Grafana engineers more flexibility — things like wildcard tag matching that spans both tiers, and combined range queries that the Scala query API did not previously expose.

What I worked on: new cardinality dimension

My contribution
Added a Kubernetes infrastructure tag to the indexing layer — pod and service level labels that teams needed to filter metrics by as Agoda's infrastructure moved to k8s. Required changes to both the Rust ingestion path and the RoaringBitmap index.

As infrastructure moved to Kubernetes, engineers needed to query metrics filtered by k8s-level identifiers — "show me latency for this service" or "show me error rate for this pod." That required WhiteFalcon to track those dimensions as first-class tag types.

Adding a new tag dimension touches both ends of the system:

  • Rust ingestion consumers: parse and extract the new tag from the incoming Kafka event payload
  • Series creation: include the new tag in the metric + tag combination that generates the series ID
  • RoaringBitmap index: maintain a per-value series set for the new tag key
  • Scala query layer: expose the new tag in the query API so Grafana dashboards can filter on it

The risk that has to be modeled before touching the index is the cardinality cross-product. A new tag with 500 unique values added to a metric that already has 10,000 series creates 5,000,000 series for that metric alone. The tag I added was a service-level label — moderate cardinality, predictable growth — specifically to avoid this explosion.

The main concern with any new cardinality dimension is not the implementation. It is modeling the cross-product before you start.

What I worked on: Parquet compression on S3

My contribution
Evaluated compression algorithms for the Parquet files written to S3. Moved from Snappy (the default) to Zstd, the current industry standard for Parquet on cold storage tiers.

Parquet files support pluggable compression at the column level. The system was using Snappy — the default for most Parquet implementations and a reasonable starting point. Snappy optimizes for decompression speed over compression ratio, which makes sense for hot workloads where you read data frequently under latency pressure.

For a cold storage tier, this tradeoff is backwards. Data on S3 is written once when a time window closes and read infrequently — only when a query spans historical data. The fast decompression advantage barely matters. The compression ratio determines your storage cost directly.

AlgorithmCompression ratioSpeedBest for
Snappy~1.12xFastestHot tier, low-latency reads
Zstd level 315-20% better than SnappyNear-Snappy reads, <1% overheadAnalytics, cold storage
Zstd level 6-9Significantly betterSlower writes, fast readsArchival, rare access
GzipGood ratioSlow write and readLegacy, max compatibility

Zstd at level 3 gives 15–20% better compression than Snappy with under 1% read latency impact — that is the sweet spot for analytics workloads. For archival partitions that are rarely accessed, higher Zstd levels give even better ratios since write frequency is low and read speed is not the primary concern. This is the same compression migration that Facebook, Twitter, and most production data platforms have made for Parquet on S3 over the last few years. Zstd was developed at Facebook and is now used in the Linux kernel, Kafka internals, and across the Hadoop ecosystem.

The query engine needed no changes — Parquet readers handle decompression transparently on the read path regardless of codec.

What this taught me

The most useful thing about working in a mature system at this scale is that every design decision has a history. The RoaringBitmap choice, the two-tier storage model, the Rust/Scala split — all of these have scars from things that didn't work before them. Understanding why the system is the way it is turns out to be most of the actual engineering work.

The cross-tier query problem connects directly to what I'm working on now. AI inference observability has the same structure: a hot tier for recent data (dashboards, alerts, real-time cost tracking) and a cold tier for historical analysis. The quantile merge problem is the same problem. The cardinality concerns are the same — model_id, tenant_id, prompt_type cross-products behave exactly like server, cluster, status cross-products. The storage optimization playbook transfers directly.
