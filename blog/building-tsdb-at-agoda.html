Post 1 of 5 — Agoda Series

1.5 trillion events. Per day. And every off-the-shelf monitoring solution hit a wall before we were anywhere close to that number. Not because of throughput. Not because of cost, at first. Because of a property of the data that most monitoring tools weren't designed to handle: cardinality.

I worked as a senior engineer on the Agoda platform team working on WhiteFalcon — Agoda's in-house time series database. This post covers the core architectural decisions that made it work at hyperscale. A lot of this is grounded in what the Agoda engineering team has published (links at the bottom), filtered through the lens of what I actually had to understand and work with day to day.

The cardinality problem, precisely

A time series is defined by a metric name plus a set of tag key-value pairs. Every unique combination of those tags creates a new series. If you have a metric like http.request.duration and you tag it with service, endpoint, status_code, datacenter, and server_id — you don't get five series. You get one series for every combination across all values of all five dimensions.

Metric: service.a.request.duration

Tags:
  server     → A1, A2, A3, ... (100s of hosts)
  cluster    → C1, C2, C3, ... (dozens of clusters)
  status     → 200, 400, 500, ...
  endpoint   → /v1/search, /v1/book, ... (100s of endpoints)

Unique series = 100 × 20 × 5 × 100 = 10,000,000
                                         for one metric

Now multiply that by thousands of metrics across a platform with millions of daily users. You're in the hundreds of millions of active series. Prometheus's in-memory inverted index — the structure it uses to look up which series match a given label selector — degrades hard at this scale. It was built for the cardinality profile of a single microservice or a fleet of a few hundred hosts, not for a travel platform processing 50M+ bookings a year.

InfluxDB and TimescaleDB had analogous ceilings. Storage costs grew exponentially with cardinality rather than linearly with event volume. You could engineer workarounds for a while, but not at this write volume indefinitely.

The real test isn't peak throughput. It's whether your cost per million events stays flat as the system doubles in size.

WhiteFalcon: the architecture

The system is built on a clean split: Rust handles storage, Scala handles queries. This isn't a performance stunt — it reflects what each language is actually good for in this context.

The storage path is write-heavy, latency-sensitive at the tail, and requires careful control over memory layout and I/O behavior. Rust gives you zero-cost abstractions, explicit memory management, and no garbage collector pausing at the worst possible moment. The query path is complex transformation logic — aggregations, time-window resampling, label filtering — where the JVM ecosystem (Akka, Cats, etc.) and Scala's expressive type system make the code significantly cleaner without a meaningful performance penalty.

The Ceph decision: bypassing POSIX entirely

The standard approach to storage in a system like this is to write to local disk via the OS filesystem, then periodically flush and compact. The problem at this write rate is that the POSIX filesystem abstraction carries overhead you can't fully escape: inode management, directory operations, OS buffer cache contention, fsync semantics that don't map cleanly to your actual durability requirements.

The team chose to write directly to Ceph via the RADOS object API — Ceph's native interface that operates below the filesystem layer. This gives you object-level control: you decide the write semantics, the object sizing, and the replication behavior directly, without a filesystem mediating those decisions. For sequential writes at high volume, this removes a meaningful layer of overhead.

The Rust storage engine built on top of this uses zero-copy buffer management — events are not copied into intermediate buffers between receipt and the RADOS write call. At 1.5 trillion events per day, "touching each event twice instead of once" has a measurable throughput cost.

The tiering decision: Kafka + Redis for hot data

A monitoring system has a strongly bimodal access pattern. The last few hours of data — what your alert rules and dashboards query — gets read orders of magnitude more often than month-old data. Putting everything in Ceph and querying it cold ignores this.

Recent data lives in a Redis tier, fed by Kafka. Kafka serves the dual role of durable event bus (buffer against Ceph write pressure) and the feed for the Redis hot layer. Queries against recent windows hit Redis first; historical queries go to Ceph. This is conceptually similar to what any read-heavy system does with an LRU cache, but the implementation details — what "recent" means given your retention window, how you handle the edge of the hot/cold boundary — require care.

The indexing problem at this scale

The cardinality problem doesn't go away once you've got the storage layer right. You still need to answer the query: "give me all series matching server in [A1, A2] AND cluster = C1 AND status NOT IN [400, 500]." At hundreds of millions of series, this is a non-trivial set operation.

The naive approach — iterate through all series for the queried metric and filter — is O(N) per query where N is the series count. Fine for a small fleet, unusable at this scale.

WhiteFalcon uses an inverted index: for each tag value, it maintains the set of series IDs where that tag value has been observed. A query becomes a series of set operations — union across values within a tag (server=A1 OR server=A2), then intersection across tags (server match AND cluster match), then subtraction for exclusions.

Query: server in [A1, A2], cluster = C1, NOT status in [400]

Step 1: union(series[server=A1], series[server=A2]) → set_S
Step 2: get series[cluster=C1]                       → set_C
Step 3: intersect(set_S, set_C)                      → set_SC
Step 4: get series[status=400]                       → set_excl
Step 5: subtract(set_SC, set_excl)                   → result

The data structure for those sets matters enormously. HashSets give you O(1) membership checks but O(N) for union/intersection (you have to iterate one set and check each element against the other). More critically, each HashSet entry for an integer series ID costs 32–40 bytes on the JVM — memory you don't have at this cardinality.

BitSets are the right answer here. Series IDs are allocated as sequential integers. A BitSet stores N integer IDs in N/8 bytes — bit K of the byte array represents series K. Union is a bitwise OR across two long arrays; intersection is AND; subtraction is ANDNOT. All three operations run in O(N/64) where N is the series count — 64 IDs per 64-bit long, vectorizable by the JVM's JIT compiler. Memory footprint drops by roughly two orders of magnitude compared to HashSets.

Operation HashSet complexity BitSet complexity Memory (1M IDs)
Union O(N) O(N/64) 125 KB vs ~40 MB
Intersection O(N) O(N/64) —
Subtraction O(N) O(N/64) —
Membership check O(1) O(1) —

The caveat the Agoda team documented carefully: BitSets work well when series IDs are dense. If your series IDs are sparse — a metric where only IDs 1, 50,000, and 4,000,000 exist — a naive BitSet wastes most of its allocated memory. The solution is a compressed bitmap structure (Roaring Bitmaps are the standard choice here) that handles sparse ID distributions without the memory waste. The core insight remains: set operations on integers should never use HashSets at this scale.

The Kafka pipeline: 1.8 trillion events with a forwarder layer

The event pipeline feeding WhiteFalcon doesn't send data directly from application services to Kafka. Agoda uses a two-step logging architecture: application services write events to local disk via a lightweight client library, and a separate daemon process (the Forwarder) reads those files and produces to Kafka.

This looks like added latency and complexity. In practice it's a deliberate tradeoff that makes the system significantly more operationally tractable at their scale:

  • The Kafka team can change Kafka client configuration, batching settings, and compression without touching application code deployments
  • Disk-buffering before Kafka provides a durable local buffer against transient Kafka unavailability
  • The Forwarder handles schema enforcement (AVRO serialization with a Schema Registry) centrally rather than per-service

The tradeoff is a P99 end-to-end latency of ~10 seconds for analytics data. For dashboard and alerting workloads, 10 seconds is fine — most alert rules aren't evaluating at sub-second granularity. For genuinely time-sensitive use cases, services bypass the forwarder and write directly to Kafka.

The scale context: Kafka usage at Agoda grew roughly 2x year-over-year, reaching 1.8 trillion events per day by 2023. That growth rate is the reason the two-step architecture exists — it decouples Kafka infrastructure decisions from application deployment cycles, which matters a great deal when you're managing a Kafka cluster at that volume.

What this means for AI inference observability

I keep returning to this work now that I'm building observability tooling for LLM inference. The cardinality problem is essentially the same. An AI inference event carries dimensions like model_id, tenant_id, prompt_type, routing_tier, user_cohort — and the cross-product of those dimensions explodes in exactly the same way as server-level application metrics do.

The architectural patterns transfer directly: BitSet indexing for series lookup, Kafka as the event bus, a Redis hot tier for recent data, ClickHouse (rather than Ceph) for analytical queries at volume. The new dimension is cost — an AI inference event carries cost_usd as a first-class field, which means the TSDB becomes the cost accounting system as well as the latency monitor.

That's what I'm building now. The Agoda work gave me the indexing and storage intuition. The AI layer adds the economic observability problem that existing tools don't handle.
